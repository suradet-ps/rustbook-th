## เผยแพร่เครตไปยัง Crates.io

เราได้ใช้แพ็กเกจ (package) จาก [crates.io](https://crates.io/)<!-- ignore --> เป็นดีเพนเดนซี (dependency) ของโปรเจกต์ของเรา แต่คุณยังสามารถแบ่งปันโค้ดของคุณกับผู้อื่นได้โดยการเผยแพร่แพ็กเกจของคุณเอง เรจิสทรีเครต (crate) ที่ [crates.io](https://crates.io/)<!-- ignore --> แจกจ่ายซอร์สโค้ดของแพ็กเกจของคุณ มันจึงโฮสต์โค้ดที่เป็นโอเพนซอร์สเป็นหลัก

Rust และ Cargo มีฟีเจอร์ที่ทำให้แพ็กเกจที่คุณเผยแพร่นั้นค้นหาและใช้งานได้ง่ายขึ้นสำหรับผู้คน เราจะพูดถึงฟีเจอร์เหล่านี้บางส่วนต่อไป จากนั้นจะอธิบายวิธีเผยแพร่แพ็กเกจ

### การเขียนคอมเมนต์เอกสารประกอบที่มีประโยชน์

การทำเอกสารประกอบแพ็กเกจของคุณอย่างถูกต้องจะช่วยให้ผู้ใช้คนอื่นรู้ว่าควรใช้มันอย่างไรและเมื่อใด จึงคุ้มค่าที่จะลงทุนเวลาเขียนเอกสารประกอบ ในบทที่ 3 เราได้พูดคุยถึงวิธีคอมเมนต์โค้ด Rust โดยใช้เครื่องหมายทับสองตัว `//` Rust ยังมีคอมเมนต์ชนิดพิเศษสำหรับเอกสารประกอบ ซึ่งเป็นที่รู้จักกันอย่างสะดวกในชื่อ _คอมเมนต์เอกสารประกอบ_ (documentation comment) ที่จะสร้างเอกสารประกอบ HTML ขึ้นมา HTML นี้แสดงเนื้อหาของคอมเมนต์เอกสารประกอบสำหรับรายการ API สาธารณะ ซึ่งมุ่งหมายสำหรับโปรแกรมเมอร์ที่สนใจอยากรู้วิธี_ใช้_เครตของคุณ ตรงกันข้ามกับวิธีที่เครตของคุณถูก_อิมพลีเมนต์_

คอมเมนต์เอกสารประกอบใช้เครื่องหมายทับสามตัว `///` แทนที่จะเป็นสองตัว และรองรับสัญกรณ์ Markdown สำหรับการจัดรูปแบบข้อความ วางคอมเมนต์เอกสารประกอบไว้ก่อนหน้ารายการที่มันทำเอกสารประกอบให้พอดี ลิสติ้ง 14-1 แสดงคอมเมนต์เอกสารประกอบสำหรับฟังก์ชัน `add_one` ในเครตชื่อ `my_crate`

#### หัวข้อที่ใช้บ่อย

เราใช้หัวเรื่อง Markdown `# Examples` ในลิสติ้ง 14-1 เพื่อสร้างหัวข้อใน HTML ที่มีชื่อเรื่อง “Examples” นี่คือหัวข้ออื่นๆ ที่ผู้เขียนเครตมักใช้ในเอกสารประกอบของพวกเขา:

- **Panics**: นี่คือสถานการณ์ที่ฟังก์ชันที่กำลังทำเอกสารประกอบอยู่สามารถแพนิก (panic) ได้ ผู้เรียกฟังก์ชันที่ไม่ต้องการให้โปรแกรมของพวกเขาแพนิกควรทำให้แน่ใจว่าพวกเขาไม่เรียกฟังก์ชันในสถานการณ์เหล่านี้
- **Errors**: หากฟังก์ชันคืนค่า `Result` การอธิบายชนิดของข้อผิดพลาดที่อาจเกิดขึ้นและเงื่อนไขใดที่อาจทำให้ข้อผิดพลาดเหล่านั้นถูกคืนกลับได้จะเป็นประโยชน์ต่อผู้เรียก เพื่อให้พวกเขาเขียนโค้ดจัดการข้อผิดพลาดแต่ละชนิดด้วยวิธีที่แตกต่างกันได้
- **Safety**: หากการเรียกฟังก์ชันเป็น `unsafe` (เราพูดคุยถึงความไม่ปลอดภัยในบทที่ 20) ควรมีหัวข้อที่อธิบายว่าทำไมฟังก์ชันจึงไม่ปลอดภัย และครอบคลุมอินวาเรียนต์ (invariant) ที่ฟังก์ชันคาดหวังให้ผู้เรียกรักษาไว้

คอมเมนต์เอกสารประกอบส่วนใหญ่ไม่จำเป็นต้องมีหัวข้อเหล่านี้ทั้งหมด แต่นี่เป็นเช็กลิสต์ที่ดีเพื่อเตือนคุณถึงแง่มุมของโค้ดของคุณที่ผู้ใช้จะสนใจอยากรู้

#### คอมเมนต์เอกสารประกอบในฐานะเทสต์

การเพิ่มบล็อกโค้ดตัวอย่างในคอมเมนต์เอกสารประกอบของคุณช่วยสาธิตวิธีใช้ไลบรารีของคุณได้ และยังมีโบนัสเพิ่มเติมอีก: การรัน `cargo test` จะรันตัวอย่างโค้ดในเอกสารประกอบของคุณในฐานะเทสต์! ไม่มีอะไรดีไปกว่าเอกสารประกอบที่มีตัวอย่าง แต่ก็ไม่มีอะไรแย่ไปกว่าตัวอย่างที่ใช้ไม่ได้เพราะโค้ดเปลี่ยนไปนับตั้งแต่เอกสารประกอบถูกเขียนขึ้น หากเรารัน `cargo test` กับเอกสารประกอบสำหรับฟังก์ชัน `add_one` จากลิสติ้ง 14-1 เราจะเห็นส่วนหนึ่งในผลลัพธ์เทสต์ที่มีหน้าตาดังนี้:

#### คอมเมนต์ของรายการที่ครอบอยู่

สไตล์ของคอมเมนต์เอกสาร `//!` เพิ่มเอกสารประกอบให้กับรายการที่*ครอบ*คอมเมนต์อยู่ มากกว่าจะให้กับรายการที่*ตามหลัง*คอมเมนต์ เรามักใช้คอมเมนต์เอกสารเหล่านี้ภายในไฟล์รากของเครต (_src/lib.rs_ ตามธรรมเนียม) หรือภายในมอดูล เพื่อทำเอกสารประกอบให้กับเครตหรือมอดูลโดยรวม

### การส่งออก API สาธารณะที่สะดวกต่อการใช้งาน

โครงสร้างของ API สาธารณะของคุณเป็นข้อพิจารณาสำคัญเมื่อเผยแพร่เครต ผู้ที่ใช้เครตของคุณคุ้นเคยกับโครงสร้างน้อยกว่าคุณ และอาจมีปัญหาในการค้นหาส่วนที่พวกเขาต้องการใช้หากเครตของคุณมีลำดับชั้นของมอดูลขนาดใหญ่

ในบทที่ 7 เราได้ครอบคลุมวิธีทำให้รายการเป็นแบบสาธารณะด้วยคำสงวน `pub` และวิธีนำรายการเข้าสู่สโคปด้วยคำสงวน `use` อย่างไรก็ตาม โครงสร้างที่สมเหตุสมผลสำหรับคุณขณะพัฒนาเครตอาจไม่สะดวกมากนักสำหรับผู้ใช้ของคุณ คุณอาจต้องการจัดระเบียบ struct ของคุณในลำดับชั้นที่มีหลายระดับ แต่แล้วผู้ที่ต้องการใช้ชนิดข้อมูลที่คุณนิยามไว้ลึกในลำดับชั้นนั้นอาจมีปัญหาในการค้นพบว่าชนิดข้อมูลนั้นมีอยู่ พวกเขาอาจหงุดหงิดที่ต้องพิมพ์ `use my_crate::some_module::another_module::UsefulType;` แทนที่จะเป็น `use my_crate::UsefulType;`

ข่าวดีก็คือ หากโครงสร้างนั้น_ไม่_สะดวกสำหรับผู้อื่นในการใช้จากไลบรารีอื่น คุณไม่จำเป็นต้องจัดเรียงการจัดระเบียบภายในของคุณใหม่: แต่คุณสามารถส่งออกรายการอีกครั้งเพื่อสร้างโครงสร้างสาธารณะที่แตกต่างจากโครงสร้างส่วนตัวของคุณได้โดยใช้ `pub use` *การส่งออกอีกครั้ง* (re-exporting) นำรายการสาธารณะจากตำแหน่งหนึ่งและทำให้มันเป็นแบบสาธารณะในอีกตำแหน่งหนึ่ง ราวกับว่ามันถูกนิยามไว้ในอีกตำแหน่งนั้นแทน

### การตั้งค่าบัญชี Crates.io

ก่อนที่คุณจะเผยแพร่เครตใดๆ ได้ คุณต้องสร้างบัญชีบน [crates.io](https://crates.io/)<!-- ignore --> และรับโทเค็น API ในการทำเช่นนั้น โปรดไปที่หน้าแรกที่ [crates.io](https://crates.io/)<!-- ignore --> และลงชื่อเข้าใช้ผ่านบัญชี GitHub (ปัจจุบันบัญชี GitHub เป็นข้อกำหนด แต่เว็บไซต์อาจรองรับวิธีอื่นในการสร้างบัญชีในอนาคต) เมื่อคุณลงชื่อเข้าใช้แล้ว โปรดไปที่การตั้งค่าบัญชีของคุณที่ [https://crates.io/me/](https://crates.io/me/)<!-- ignore --> และดึงคีย์ API ของคุณ จากนั้นรันคำสั่ง `cargo login` แล้ววางคีย์ API ของคุณเมื่อถูกขอ เช่นนี้:

```console
$ cargo login
abcdefghijklmnopqrstuvwxyz012345
```

คำสั่งนี้จะแจ้งโทเค็น API ของคุณให้ Cargo ทราบและจัดเก็บไว้ในเครื่องที่ _~/.cargo/credentials.toml_ โปรดสังเกตว่าโทเค็นนี้เป็นความลับ: อย่าแชร์มันกับใครอื่น หากคุณแชร์มันกับใครด้วยเหตุผลใดก็ตาม คุณควรเพิกถอนมันและสร้างโทเค็นใหม่บน [crates.io](https://crates.io/)<!-- ignore -->

### การเพิ่มเมทาดาทาให้เครตใหม่

สมมติว่าคุณมีเครตที่คุณต้องการเผยแพร่ ก่อนการเผยแพร่ คุณจะต้องเพิ่มเมทาดาทาบางอย่างในส่วน `[package]` ของไฟล์ _Cargo.toml_ ของเครต

เครตของคุณจะต้องมีชื่อที่ไม่ซ้ำใคร ในขณะที่คุณทำงานกับเครตในเครื่อง คุณจะตั้งชื่อเครตอะไรก็ได้ตามใจ แต่ชื่อเครตบน [crates.io](https://crates.io/)<!-- ignore --> ถูกจัดสรรตามหลักมาก่อนได้ก่อน เมื่อชื่อเครตถูกใช้ไปแล้ว ไม่มีใครอื่นสามารถเผยแพร่เครตด้วยชื่อนั้นได้ ก่อนพยายามเผยแพร่เครต โปรดค้นหาชื่อที่คุณต้องการใช้ หากชื่อนั้นถูกใช้ไปแล้ว คุณจะต้องหาชื่ออื่นและแก้ไขฟิลด์ `name` ในไฟล์ _Cargo.toml_ ใต้ส่วน `[package]` เพื่อใช้ชื่อใหม่ในการเผยแพร่ เช่นนี้:

<span class="filename">ชื่อไฟล์: Cargo.toml</span>

```toml
[package]
name = "guessing_game"
```

แม้ว่าคุณจะเลือกชื่อที่ไม่ซ้ำใครแล้ว เมื่อคุณรัน `cargo publish` เพื่อเผยแพร่เครต ณ จุดนี้ คุณจะได้คำเตือน (warning) แล้วจึงได้ข้อผิดพลาด:

<!-- manual-regeneration
Create a new package with an unregistered name, making no further modifications
  to the generated package, so it is missing the description and license fields.
cargo publish
copy just the relevant lines below
-->

```console
$ cargo publish
    Updating crates.io index
warning: manifest has no description, license, license-file, documentation, homepage or repository.
See https://doc.rust-lang.org/cargo/reference/manifest.html#package-metadata for more info.
--snip--
error: failed to publish to registry at https://crates.io

Caused by:
  the remote server responded with an error (status 400 Bad Request): missing or empty metadata fields: description, license. Please see https://doc.rust-lang.org/cargo/reference/manifest.html for more information on configuring these fields
```

สิ่งนี้นำไปสู่ข้อผิดพลาดเพราะคุณขาดข้อมูลสำคัญบางอย่าง: คำอธิบายและสัญญาอนุญาตเป็นสิ่งที่จำเป็น เพื่อให้ผู้คนรู้ว่าเครตของคุณทำอะไรและใช้มันได้ภายใต้เงื่อนไขใด ใน _Cargo.toml_ ให้เพิ่มคำอธิบายสักหนึ่งหรือสองประโยค เพราะมันจะปรากฏพร้อมกับเครตของคุณในผลการค้นหา สำหรับฟิลด์ `license` คุณต้องระบุ_ค่าไอเดนทิฟายเออร์สัญญาอนุญาต_ [Linux Foundation’s Software Package Data Exchange (SPDX)][spdx] แสดงรายการไอเดนทิฟายเออร์ที่คุณใช้เป็นค่านี้ได้ ตัวอย่างเช่น หากต้องการระบุว่าคุณได้ให้สัญญาอนุญาตเครตของคุณภายใต้ MIT License ให้เพิ่มไอเดนทิฟายเออร์ `MIT`:

<span class="filename">ชื่อไฟล์: Cargo.toml</span>

```toml
[package]
name = "guessing_game"
license = "MIT"
```

หากคุณต้องการใช้สัญญาอนุญาตที่ไม่มีอยู่ใน SPDX คุณต้องวางข้อความของสัญญาอนุญาตนั้นไว้ในไฟล์ รวมไฟล์นั้นไว้ในโปรเจกต์ของคุณ แล้วใช้ `license-file` เพื่อระบุชื่อไฟล์นั้นแทนการใช้คีย์ `license`

คำแนะนำว่าสัญญาอนุญาตใดเหมาะสมกับโปรเจกต์ของคุณนั้นอยู่นอกขอบเขตของหนังสือเล่มนี้ ผู้คนจำนวนมากในชุมชน Rust ให้สัญญาอนุญาตโปรเจกต์ของพวกเขาในแบบเดียวกับ Rust โดยใช้สัญญาอนุญาตคู่แบบ `MIT OR Apache-2.0` แนวปฏิบัตินี้แสดงให้เห็นว่าคุณยังสามารถระบุไอเดนทิฟายเออร์สัญญาอนุญาตหลายตัวคั่นด้วย `OR` เพื่อให้โปรเจกต์ของคุณมีสัญญาอนุญาตหลายแบบได้

เมื่อมีชื่อที่ไม่ซ้ำใคร เวอร์ชัน คำอธิบาย และสัญญาอนุญาตแล้ว ไฟล์ _Cargo.toml_ สำหรับโปรเจกต์ที่พร้อมเผยแพร่อาจมีหน้าตาดังนี้:

<span class="filename">ชื่อไฟล์: Cargo.toml</span>

```toml
[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"

[dependencies]
```

[เอกสารของ Cargo](https://doc.rust-lang.org/cargo/) อธิบายเมทาดาทาอื่นๆ ที่คุณสามารถระบุได้ เพื่อทำให้แน่ใจว่าผู้อื่นสามารถค้นพบและใช้เครตของคุณได้ง่ายขึ้น

### การเผยแพร่ไปยัง Crates.io

ตอนนี้คุณได้สร้างบัญชี จัดเก็บโทเค็น API เลือกชื่อให้เครต และระบุเมทาดาทาที่จำเป็นแล้ว คุณพร้อมที่จะเผยแพร่! การเผยแพร่เครตจะอัปโหลดเวอร์ชันที่เจาะจงไปยัง [crates.io](https://crates.io/)<!-- ignore --> เพื่อให้ผู้อื่นใช้งานได้

โปรดระวัง เพราะการเผยแพร่เป็นสิ่งที่_ถาวร_ เวอร์ชันไม่สามารถถูกเขียนทับได้เลย และโค้ดไม่สามารถลบได้ยกเว้นในสถานการณ์บางอย่าง เป้าหมายสำคัญประการหนึ่งของ Crates.io คือการทำหน้าที่เป็นคลังเก็บโค้ดถาวร เพื่อให้การบิลด์ของทุกโปรเจกต์ที่พึ่งพาเครตจาก [crates.io](https://crates.io/)<!-- ignore --> ยังคงทำงานได้ การอนุญาตให้ลบเวอร์ชันจะทำให้การบรรลุเป้าหมายนั้นเป็นไปไม่ได้ อย่างไรก็ตาม ไม่มีขีดจำกัดจำนวนเวอร์ชันของเครตที่คุณเผยแพร่ได้

### การเผยแพร่เวอร์ชันใหม่ของเครตที่มีอยู่

เมื่อคุณได้ทำการเปลี่ยนแปลงเครตของคุณและพร้อมที่จะปล่อยเวอร์ชันใหม่ คุณจะเปลี่ยนค่า `version` ที่ระบุในไฟล์ _Cargo.toml_ ของคุณและเผยแพร่ใหม่ ใช้[กฎการกำหนดเวอร์ชันเชิงความหมาย (semantic versioning)][semver] ในการตัดสินว่าเลขเวอร์ชันถัดไปที่เหมาะสมคืออะไร โดยอิงจากชนิดของการเปลี่ยนแปลงที่คุณได้ทำ จากนั้นรัน `cargo publish` เพื่ออัปโหลดเวอร์ชันใหม่

### การเลิกใช้เวอร์ชันจาก Crates.io

แม้ว่าคุณจะลบเวอร์ชันก่อนหน้าของเครตไม่ได้ แต่คุณสามารถป้องกันไม่ให้โปรเจกต์ในอนาคตเพิ่มมันเป็นดีเพนเดนซีใหม่ได้ สิ่งนี้มีประโยชน์เมื่อเวอร์ชันของเครตเสียด้วยเหตุผลใดเหตุผลหนึ่ง ในสถานการณ์เช่นนี้ Cargo รองรับการถอน (yanking) เวอร์ชันของเครต

_การถอน_ (yanking) เวอร์ชันหนึ่งป้องกันไม่ให้โปรเจกต์ใหม่พึ่งพาเวอร์ชันนั้น ขณะที่อนุญาตให้โปรเจกต์ที่มีอยู่ทั้งหมดซึ่งพึ่งพามันทำงานต่อไปได้ โดยพื้นฐานแล้ว การถอนหมายความว่าโปรเจกต์ทั้งหมดที่มี _Cargo.lock_ จะไม่พัง และไฟล์ _Cargo.lock_ ใหม่ใดๆ ที่ถูกสร้างขึ้นในอนาคตจะไม่ใช้เวอร์ชันที่ถูกถอน

ในการถอนเวอร์ชันของเครต ในไดเรกทอรีของเครตที่คุณได้เผยแพร่ไว้ก่อนหน้านี้ ให้รัน `cargo yank` และระบุว่าเวอร์ชันใดที่คุณต้องการถอน ตัวอย่างเช่น หากเราได้เผยแพร่เครตชื่อ `guessing_game` เวอร์ชัน 1.0.1 และเราต้องการถอนมัน เราจะรันคำสั่งต่อไปนี้ในไดเรกทอรีโปรเจกต์ของ `guessing_game`:

<!-- manual-regeneration:
cargo yank carol-test --version 2.1.0
cargo yank carol-test --version 2.1.0 --undo
-->

```console
$ cargo yank --vers 1.0.1
    Updating crates.io index
        Yank guessing_game@1.0.1
```

ด้วยการเพิ่ม `--undo` ต่อท้ายคำสั่ง คุณยังสามารถย้อนกลับการถอนและอนุญาตให้โปรเจกต์เริ่มพึ่งพาเวอร์ชันนั้นได้อีกครั้ง:

```console
$ cargo yank --vers 1.0.1 --undo
    Updating crates.io index
      Unyank guessing_game@1.0.1
```

การถอน_ไม่ได้_ลบโค้ดใดๆ ตัวอย่างเช่น มันไม่สามารถลบความลับที่ถูกอัปโหลดไปโดยไม่ตั้งใจได้ หากสิ่งนั้นเกิดขึ้น คุณต้องรีเซ็ตความลับเหล่านั้นทันที
