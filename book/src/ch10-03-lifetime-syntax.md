## การตรวจสอบความถูกต้องของเรเฟอเรนซ์ด้วยไลฟ์ไทม์

ไลฟ์ไทม์ (lifetime) เป็นเจเนอริกอีกรูปแบบหนึ่งที่เราเคยใช้งานกันมาแล้ว แต่แทนที่จะเป็นการรับประกันว่าชนิดข้อมูลจะมีพฤติกรรมตามที่เราต้องการ ไลฟ์ไทม์จะช่วยรับประกันว่าเรเฟอเรนซ์ (reference) จะยังคงถูกต้องและใช้งานได้ตราบเท่าที่เรายังจำเป็นต้องใช้มัน

รายละเอียดอย่างหนึ่งที่เรายังไม่ได้พูดถึงในหัวข้อ[“เรเฟอเรนซ์และการยืม”][references-and-borrowing]<!-- ignore --> ในบทที่ 4 ก็คือ ทุกเรเฟอเรนซ์ใน Rust ต่างก็มีไลฟ์ไทม์ ซึ่งก็คือขอบเขต (scope) ที่เรเฟอเรนซ์นั้นสามารถใช้งานได้อย่างถูกต้อง โดยส่วนใหญ่แล้ว ไลฟ์ไทม์จะถูกอนุมาน (infer) ขึ้นมาโดยปริยาย เช่นเดียวกับชนิดข้อมูลที่คอมไพเลอร์มักอนุมานให้เอง เราจำเป็นต้องระบุชนิดข้อมูลกำกับไว้เฉพาะเมื่อมีชนิดข้อมูลที่เป็นไปได้หลายแบบเท่านั้น ในทำนองเดียวกัน เราต้องระบุไลฟ์ไทม์เมื่อความสัมพันธ์ระหว่างไลฟ์ไทม์ของเรเฟอเรนซ์ต่างๆ อาจเป็นไปได้หลายรูปแบบ Rust กำหนดให้เราระบุความสัมพันธ์เหล่านั้นด้วยพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริก (generic lifetime parameters) เพื่อให้มั่นใจได้ว่าเรเฟอเรนซ์จริงที่ใช้งานตอนรันไทม์จะยังคงถูกต้องและใช้งานได้อย่างแน่นอน

การระบุไลฟ์ไทม์ (lifetime annotation) เป็นแนวคิดที่ภาษาโปรแกรมส่วนใหญ่ไม่มีด้วยซ้ำ จึงอาจทำให้คุณรู้สึกไม่คุ้นเคยอยู่บ้าง แม้ว่าในบทนี้เราจะไม่ได้ครอบคลุมเรื่องไลฟ์ไทม์อย่างครบถ้วนทุกแง่มุม แต่เราจะอธิบายรูปแบบวากยสัมพันธ์ของไลฟ์ไทม์ที่คุณมักพบเจอบ่อยๆ เพื่อให้คุณเริ่มคุ้นเคยกับแนวคิดนี้

### วากยสัมพันธ์ของการระบุไลฟ์ไทม์

การระบุไลฟ์ไทม์ (lifetime annotation) ไม่ได้เป็นการเปลี่ยนแปลงช่วงชีวิตของเรเฟอเรนซ์ใดๆ เลย แต่มีไว้เพื่ออธิบายความสัมพันธ์ระหว่างช่วงชีวิตของเรเฟอเรนซ์หลายๆ ตัวเข้าด้วยกัน โดยไม่ส่งผลกระทบต่อไลฟ์ไทม์เดิมของพวกมัน เช่นเดียวกับที่ฟังก์ชันสามารถรับชนิดข้อมูลใดๆ ก็ได้เมื่อในซิกเนเจอร์มีพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก ฟังก์ชันก็สามารถรับเรเฟอเรนซ์ที่มีไลฟ์ไทม์ใดๆ ก็ได้โดยการระบุพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริกเช่นกัน

การระบุไลฟ์ไทม์มีวากยสัมพันธ์ที่ค่อนข้างแปลกตาเล็กน้อย: ชื่อของพารามิเตอร์ไลฟ์ไทม์จะต้องขึ้นต้นด้วยเครื่องหมายอะพอสทรอฟี (`'`) และมักจะเป็นตัวพิมพ์เล็กทั้งหมดที่มีความยาวสั้นมากๆ เช่นเดียวกับชนิดข้อมูลเจเนอริก โดยธรรมเนียมแล้วคนส่วนใหญ่มักจะตั้งชื่อ `'a` เป็นการระบุไลฟ์ไทม์ตัวแรก เราจะวางการระบุพารามิเตอร์ไลฟ์ไทม์ไว้หลังเครื่องหมาย `&` ของเรเฟอเรนซ์ และคั่นด้วยการเว้นวรรคหนึ่งช่องก่อนจะตามด้วยชนิดข้อมูลของเรเฟอเรนซ์นั้น

นี่คือตัวอย่างบางส่วน—เรเฟอเรนซ์ที่ชี้ไปยัง `i32` แบบไม่มีพารามิเตอร์ไลฟ์ไทม์, เรเฟอเรนซ์ที่ชี้ไปยัง `i32` ที่มีพารามิเตอร์ไลฟ์ไทม์ชื่อ `'a` กำกับอยู่, และเรเฟอเรนซ์แบบแก้ไขได้ (mutable reference) ที่ชี้ไปยัง `i32` ซึ่งมีไลฟ์ไทม์ `'a` กำกับไว้เช่นกัน:

```rust,ignore
&i32        // a reference
&'a i32     // a reference with an explicit lifetime
&'a mut i32 // a mutable reference with an explicit lifetime
```

การระบุไลฟ์ไทม์โดดๆ เพียงตัวเดียวจะไม่มีความหมายอะไรมากนัก เนื่องจากการระบุไลฟ์ไทม์มีจุดประสงค์หลักเพื่อบอก Rust ว่าพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริกของเรเฟอเรนซ์หลายๆ ตัวนั้นสัมพันธ์กันอย่างไร มาดูกันว่าการระบุไลฟ์ไทม์มีความเกี่ยวข้องกันอย่างไรในบริบทของฟังก์ชัน `longest`

โปรดจำไว้ว่า การระบุพารามิเตอร์ไลฟ์ไทม์ในซิกเนเจอร์ของฟังก์ชันนี้ เราไม่ได้ไปเปลี่ยนแปลงไลฟ์ไทม์ของค่าใดๆ ที่ส่งเข้ามาหรือส่งคืนกลับไปเลย แต่เป็นการระบุข้อกำหนดเพื่อให้ตัวตรวจการยืมปฏิเสธค่าใดๆ ก็ตามที่ไม่สอดคล้องกับเงื่อนไขเหล่านี้ โปรดสังเกตว่าฟังก์ชัน `longest` ไม่จำเป็นต้องรู้ว่า `x` และ `y` จะมีอายุอยู่ได้นานเท่าใดกันแน่ ขอเพียงแค่มีสโคปบางสโคปที่สามารถนำมาแทนค่า `'a` แล้วทำให้ซิกเนเจอร์นี้ถูกต้องสมบูรณ์ได้ก็เพียงพอแล้ว

เมื่อระบุไลฟ์ไทม์ในฟังก์ชัน คำระบุเหล่านั้นจะวางอยู่ในซิกเนเจอร์ของฟังก์ชัน ไม่ใช่ในเนื้อหาของฟังก์ชัน การระบุไลฟ์ไทม์จึงกลายมาเป็นส่วนหนึ่งของสัญญา (contract) ของฟังก์ชัน คล้ายกับการระบุชนิดข้อมูลในซิกเนเจอร์ การมีสัญญาเรื่องไลฟ์ไทม์อยู่ในซิกเนเจอร์ของฟังก์ชันทำให้การวิเคราะห์ของคอมไพเลอร์ Rust ทำได้ง่ายขึ้นและตรงไปตรงมา หากมีจุดผิดพลาดเกี่ยวกับการระบุไลฟ์ไทม์หรือวิธีการเรียกใช้งานฟังก์ชัน ข้อผิดพลาดจากคอมไพเลอร์ก็จะสามารถชี้ไปยังตำแหน่งของโค้ดและข้อจำกัดต่างๆ ได้อย่างแม่นยำ ในทางตรงกันข้าม หากคอมไพเลอร์ Rust พยายามอนุมานเจตนาความสัมพันธ์ของไลฟ์ไทม์เอาเองมากเกินไป คอมไพเลอร์อาจชี้ได้เพียงแค่จุดที่เรียกใช้โค้ด ซึ่งอาจอยู่ห่างจากต้นตอของปัญหาจริงๆ ไปหลายขั้นตอน

เมื่อเราส่งเรเฟอเรนซ์จริงๆ เข้าไปยัง `longest` ไลฟ์ไทม์ที่แท้จริงซึ่งจะถูกนำมาแทนที่ `'a` ก็คือส่วนของสโคปของ `x` ที่ทับซ้อนกับสโคปของ `y` กล่าวอีกนัยหนึ่ง ไลฟ์ไทม์แบบเจเนอริก `'a` จะได้รับไลฟ์ไทม์จริงที่มีขนาดเท่ากับไลฟ์ไทม์ที่สั้นกว่าระหว่าง `x` กับ `y` และเนื่องจากเรากำกับเรเฟอเรนซ์ที่ส่งคืนด้วยพารามิเตอร์ไลฟ์ไทม์ `'a` ตัวเดียวกัน เรเฟอเรนซ์ที่ส่งคืนจึงมีอายุใช้งานได้ยาวนานเท่ากับไลฟ์ไทม์ที่สั้นกว่าระหว่าง `x` กับ `y` ด้วยเช่นกัน

เมื่อฟังก์ชันมีการส่งคืนเรเฟอเรนซ์ พารามิเตอร์ไลฟ์ไทม์ของชนิดข้อมูลที่ส่งคืนจะต้องตรงกับพารามิเตอร์ไลฟ์ไทม์ของพารามิเตอร์ตัวใดตัวหนึ่งเสมอ หากเรเฟอเรนซ์ที่ส่งคืนไม่ได้อ้างถึงพารามิเตอร์ตัวใดตัวหนึ่ง ก็แสดงว่ามันจะต้องอ้างถึงค่าที่ถูกสร้างขึ้นภายในฟังก์ชันนั้นเอง ซึ่งนั่นจะทำให้กลายเป็น dangling reference ไปทันที เพราะค่านั้นจะหลุดออกจากสโคปและถูกทำลายไปเมื่อสิ้นสุดการทำงานของฟังก์ชัน ลองพิจารณาความพยายามอิมพลีเมนต์ฟังก์ชัน `longest` ต่อไปนี้ ซึ่งจะคอมไพล์ไม่ผ่าน:

เหตุผลที่ฟังก์ชันนี้สามารถคอมไพล์ผ่านได้โดยไม่ต้องระบุไลฟ์ไทม์นั้นเป็นเรื่องราวทางประวัติศาสตร์: ในยุคแรกเริ่มของ Rust (ก่อนเวอร์ชัน 1.0) โค้ดนี้จะไม่สามารถคอมไพล์ได้เลย เพราะทุกเรเฟอเรนซ์จำเป็นต้องมีการระบุไลฟ์ไทม์อย่างชัดเจน ในยุคนั้น ซิกเนเจอร์ของฟังก์ชันจะต้องถูกเขียนดังนี้:

```rust,ignore
fn first_word<'a>(s: &'a str) -> &'a str {
```

หลังจากเขียนโค้ด Rust ไปเป็นจำนวนมาก ทีมพัฒนา Rust ก็พบว่าเหล่านักพัฒนาต่างต้องเขียนระบุไลฟ์ไทม์แบบเดิมซ้ำๆ ในสถานการณ์เดิมๆ อยู่เสมอ ซึ่งรูปแบบเหล่านี้สามารถคาดเดาได้และเป็นไปตามแพตเทิร์นที่แน่นอนไม่กี่แบบ นักพัฒนาคอมไพเลอร์จึงได้บรรจุแพตเทิร์นเหล่านั้นลงในตัวคอมไพเลอร์ เพื่อให้ตัวตรวจการยืมสามารถอนุมานไลฟ์ไทม์ในสถานการณ์ดังกล่าวได้เองโดยไม่จำเป็นต้องระบุอย่างโจ่งแจ้งอีกต่อไป

ประวัติศาสตร์ส่วนนี้ของ Rust มีความสำคัญ เพราะเป็นไปได้ว่าในอนาคตอาจมีแพตเทิร์นที่แน่นอนเพิ่มเติมถูกนำมาใส่ในคอมไพเลอร์อีก ทำให้เราอาจต้องเขียนระบุไลฟ์ไทม์น้อยลงไปกว่าเดิม

แพตเทิร์นที่ถูกกำหนดไว้ในการวิเคราะห์เรเฟอเรนซ์ของ Rust นี้เรียกว่า _กฎการละไลฟ์ไทม์_ (lifetime elision rules) กฎเหล่านี้ไม่ใช่กฎที่โปรแกรมเมอร์ต้องคอยท่องจำเพื่อปฏิบัติตาม แต่เป็นชุดเงื่อนไขเฉพาะที่คอมไพเลอร์จะนำมาพิจารณา และหากโค้ดของคุณตรงตามเงื่อนไขเหล่านี้ คุณก็ไม่จำเป็นต้องเขียนระบุไลฟ์ไทม์ด้วยตนเอง

กฎการละไลฟ์ไทม์ไม่ได้ครอบคลุมการอนุมานในทุกกรณี หากคอมไพเลอร์ประยุกต์ใช้กฎเหล่านี้แล้วยังคงมีความคลุมเครือว่าเรเฟอเรนซ์ควรมีไลฟ์ไทม์ใด คอมไพเลอร์จะไม่คาดเดาไปเอง แต่จะรายงานเป็นข้อผิดพลาดออกมาเพื่อให้คุณแก้ไขด้วยการระบุไลฟ์ไทม์ด้วยตนเอง

ไลฟ์ไทม์ที่อยู่บนพารามิเตอร์ของฟังก์ชันหรือเมธอดจะเรียกว่า _ไลฟ์ไทม์ขาเข้า_ (input lifetimes) ส่วนไลฟ์ไทม์ที่อยู่บนค่าที่ส่งคืนจะเรียกว่า _ไลฟ์ไทม์ขาออก_ (output lifetimes)

คอมไพเลอร์จะใช้กฎ 3 ข้อในการหาไลฟ์ไทม์ของเรเฟอเรนซ์เมื่อไม่มีการระบุไว้อย่างชัดแจ้ง โดยกฎข้อแรกจะใช้กับไลฟ์ไทม์ขาเข้า ส่วนกฎข้อที่สองและสามจะใช้กับไลฟ์ไทม์ขาออก หากคอมไพเลอร์พิจารณาจนครบทั้งสามข้อแล้วยังมีเรเฟอเรนซ์ที่ระบุไลฟ์ไทม์ไม่ได้ คอมไพเลอร์จะหยุดการทำงานพร้อมแจ้งข้อผิดพลาด กฎเหล่านี้ใช้ได้กับทั้งนิยามของ `fn` และบล็อก `impl`

กฎข้อแรกคือ คอมไพเลอร์จะกำหนดพารามิเตอร์ไลฟ์ไทม์ให้แก่พารามิเตอร์ทุกตัวที่เป็นเรเฟอเรนซ์ กล่าวคือ ฟังก์ชันที่มีพารามิเตอร์หนึ่งตัวจะได้พารามิเตอร์ไลฟ์ไทม์หนึ่งตัว: `fn foo<'a>(x: &'a i32)` ส่วนฟังก์ชันที่มีสองพารามิเตอร์ก็จะได้พารามิเตอร์ไลฟ์ไทม์แยกกันสองตัว: `fn foo<'a, 'b>(x: &'a i32, y: &'b i32)` และเป็นเช่นนี้เรื่อยไป

กฎข้อที่สองคือ หากมีพารามิเตอร์ไลฟ์ไทม์ขาเข้าเพียงตัวเดียวเท่านั้น ไลฟ์ไทม์นั้นจะถูกกำหนดให้กับพารามิเตอร์ไลฟ์ไทม์ขาออกทั้งหมดโดยอัตโนมัติ: `fn foo<'a>(x: &'a i32) -> &'a i32`

กฎข้อที่สามคือ หากมีพารามิเตอร์ไลฟ์ไทม์ขาเข้าหลายตัว แต่มีตัวใดตัวหนึ่งเป็น `&self` หรือ `&mut self` (เนื่องจากเป็นเมธอด) ไลฟ์ไทม์ของ `self` จะถูกกำหนดให้กับพารามิเตอร์ไลฟ์ไทม์ขาออกทั้งหมด กฎข้อที่สามนี้ช่วยให้การเขียนและอ่านเมธอดสะดวกสบายขึ้นมาก เพราะไม่ต้องใส่สัญลักษณ์ให้รกตา

ลองสมมติตัวเราเป็นคอมไพเลอร์ แล้วนำกฎเหล่านี้มาใช้หาไลฟ์ไทม์ของเรเฟอเรนซ์ในซิกเนเจอร์ของฟังก์ชัน `first_word` ในลิสติ้ง 10-25 ซิกเนเจอร์เริ่มต้นจะไม่มีไลฟ์ไทม์ใดๆ ผูกอยู่กับเรเฟอเรนซ์:

```rust,ignore
fn first_word(s: &str) -> &str {
```

จากนั้น คอมไพเลอร์จะใช้กฎข้อแรก ซึ่งระบุว่าพารามิเตอร์แต่ละตัวจะได้ไลฟ์ไทม์เป็นของตัวเอง เราจะตั้งชื่อว่า `'a` ตามปกติ ซิกเนเจอร์จึงเปลี่ยนเป็นแบบนี้:

```rust,ignore
fn first_word<'a>(s: &'a str) -> &str {
```

ต่อมากฎข้อที่สองจะถูกนำมาใช้ เนื่องจากมีไลฟ์ไทม์ขาเข้าเพียงตัวเดียวพอดี กฎข้อที่สองระบุว่าไลฟ์ไทม์ของพารามิเตอร์ขาเข้าจะถูกนำไปกำหนดให้กับไลฟ์ไทม์ขาออก ซิกเนเจอร์จึงกลายเป็นแบบนี้:

```rust,ignore
fn first_word<'a>(s: &'a str) -> &'a str {
```

ในตอนนี้ เรเฟอเรนซ์ทั้งหมดในซิกเนเจอร์ของฟังก์ชันต่างก็มีไลฟ์ไทม์ครบถ้วนแล้ว คอมไพเลอร์จึงสามารถวิเคราะห์โค้ดต่อไปได้ โดยที่โปรแกรมเมอร์ไม่ต้องมาคอยระบุไลฟ์ไทม์ในซิกเนเจอร์ของฟังก์ชันนี้เลย

มาดูอีกตัวอย่างหนึ่ง คราวนี้ใช้ฟังก์ชัน `longest` ที่ยังไม่ได้ระบุพารามิเตอร์ไลฟ์ไทม์ตอนที่เราเริ่มเขียนในลิสติ้ง 10-20:

```rust,ignore
fn longest(x: &str, y: &str) -> &str {
```

เมื่อนำกฎข้อแรกมาใช้: พารามิเตอร์แต่ละตัวจะได้ไลฟ์ไทม์ของตัวเอง คราวนี้เรามีพารามิเตอร์สองตัว จึงได้ไลฟ์ไทม์สองตัวแยกกัน:

```rust,ignore
fn longest<'a, 'b>(x: &'a str, y: &'b str) -> &str {
```

คุณจะเห็นว่ากฎข้อที่สองไม่สามารถนำมาใช้ได้ เพราะมีไลฟ์ไทม์ขาเข้ามากกว่าหนึ่งตัว และกฎข้อที่สามก็ใช้ไม่ได้เช่นกัน เพราะ `longest` เป็นฟังก์ชันธรรมดาไม่ใช่เมธอด จึงไม่มีพารามิเตอร์ที่เป็น `self` เลย หลังจากพิจารณาผ่านกฎทั้งสามข้อแล้ว คอมไพเลอร์ก็ยังคงไม่สามารถระบุได้ว่าไลฟ์ไทม์ของชนิดข้อมูลที่ส่งคืนคืออะไร นี่คือสาเหตุที่เราพบข้อผิดพลาดเมื่อพยายามคอมไพล์โค้ดในลิสติ้ง 10-20: คอมไพเลอร์ไล่ดูกฎการละไลฟ์ไทม์จนครบแล้ว แต่ก็ยังไม่สามารถหาไลฟ์ไทม์ของเรเฟอเรนซ์ทั้งหมดในซิกเนเจอร์ได้

เนื่องจากกฎข้อที่สามนั้นจะใช้กับซิกเนเจอร์ของเมธอดเท่านั้น ต่อไปเราจะมาดูเรื่องไลฟ์ไทม์ในบริบทของเมธอดกัน เพื่อดูว่าทำไมกฎข้อที่สามจึงช่วยให้เราแทบไม่ต้องระบุไลฟ์ไทม์ในซิกเนเจอร์ของเมธอดเลย

### ในนิยามของเมธอด

เมื่อเราอิมพลีเมนต์เมธอดให้กับ struct ที่มีไลฟ์ไทม์ เราจะใช้วากยสัมพันธ์แบบเดียวกับพารามิเตอร์ชนิดข้อมูลแบบเจเนอริกดังที่แสดงในลิสติ้ง 10-11 ตำแหน่งที่เราจะประกาศและนำพารามิเตอร์ไลฟ์ไทม์ไปใช้นั้น ขึ้นอยู่กับว่ามันเกี่ยวข้องกับฟิลด์ของ struct หรือเกี่ยวข้องกับพารามิเตอร์และค่าที่ส่งคืนของเมธอด

ชื่อของไลฟ์ไทม์สำหรับฟิลด์ของ struct จำเป็นต้องประกาศไว้หลังคีย์เวิร์ด `impl` เสมอ และนำไปใช้หลังชื่อของ struct เพราะไลฟ์ไทม์เหล่านั้นถือเป็นส่วนหนึ่งของชนิดข้อมูลของ struct

ในซิกเนเจอร์ของเมธอดภายในบล็อก `impl` เรเฟอเรนซ์อาจจะผูกติดอยู่กับไลฟ์ไทม์ของเรเฟอเรนซ์ในฟิลด์ของ struct หรืออาจจะเป็นอิสระต่อกันก็ได้ นอกจากนี้ กฎการละไลฟ์ไทม์ยังช่วยให้เราแทบไม่ต้องระบุไลฟ์ไทม์ในซิกเนเจอร์ของเมธอดเลย มาดูตัวอย่างบางส่วนโดยใช้ struct ชื่อ `ImportantExcerpt` ที่เรานิยามไว้ในลิสติ้ง 10-24

อันดับแรก เราจะใช้เมธอดชื่อ `level` ที่มีพารามิเตอร์เพียงตัวเดียวคือเรเฟอเรนซ์ไปยัง `self` และมีค่าที่ส่งคืนเป็น `i32` ซึ่งไม่ใช่เรเฟอเรนซ์:

```rust
{{#rustdoc_include ../listings/ch10-generic-types-traits-and-lifetimes/no-listing-10-lifetimes-on-methods/src/main.rs:1st}}
```

การประกาศพารามิเตอร์ไลฟ์ไทม์หลัง `impl` และการนำไปใช้หลังชื่อชนิดข้อมูลนั้นเป็นสิ่งจำเป็น แต่ด้วยกฎการละไลฟ์ไทม์ข้อแรก เราจึงไม่จำเป็นต้องระบุไลฟ์ไทม์ให้กับเรเฟอเรนซ์ที่ชี้ไปยัง `self` เลย

ต่อไปนี้เป็นตัวอย่างที่กฎการละไลฟ์ไทม์ข้อที่สามถูกนำมาใช้งาน:

```rust
{{#rustdoc_include ../listings/ch10-generic-types-traits-and-lifetimes/no-listing-10-lifetimes-on-methods/src/main.rs:3rd}}
```

ในที่นี้มีไลฟ์ไทม์ขาเข้าสองตัว Rust จึงนำกฎการละไลฟ์ไทม์ข้อแรกมาใช้ โดยกำหนดไลฟ์ไทม์เฉพาะตัวให้กับทั้ง `&self` และ `announcement` จากนั้น เมื่อพิจารณาว่ามีพารามิเตอร์ตัวหนึ่งเป็น `&self` ชนิดข้อมูลที่ส่งคืนจึงได้รับไลฟ์ไทม์ของ `&self` ไปโดยอัตโนมัติ ทำให้เรเฟอเรนซ์ทั้งหมดได้รับการระบุไลฟ์ไทม์อย่างครบถ้วนสมบูรณ์

### ไลฟ์ไทม์ `'static`

ไลฟ์ไทม์พิเศษตัวหนึ่งที่เราต้องกล่าวถึงคือ `'static` ซึ่งระบุว่าเรเฟอเรนซ์ดังกล่าว _สามารถ_ มีอายุอยู่ได้ตลอดระยะเวลาการทำงานทั้งหมดของโปรแกรม โดยสตริงลิเทอรัล (string literal) ทั้งหมดต่างก็มีไลฟ์ไทม์เป็น `'static` ซึ่งเราสามารถเขียนกำกับได้ดังนี้:

```rust
let s: &'static str = "I have a static lifetime.";
```

ข้อความของสตริงนี้จะถูกฝังและจัดเก็บไว้ในไฟล์ไบนารีของโปรแกรมโดยตรง ซึ่งพร้อมใช้งานอยู่ตลอดเวลา ดังนั้น ไลฟ์ไทม์ของสตริงลิเทอรัลทุกตัวจึงเป็น `'static` เสมอ

คุณอาจเคยเห็นคำแนะนำในข้อความแสดงข้อผิดพลาดที่บอกให้ลองใช้ไลฟ์ไทม์ `'static` แต่ก่อนที่คุณจะระบุ `'static` ให้กับเรเฟอเรนซ์ใดๆ ควรไตร่ตรองให้รอบคอบก่อนว่าเรเฟอเรนซ์นั้นจำเป็นต้องมีชีวิตอยู่ตลอดอายุการทำงานของโปรแกรมจริงๆ หรือไม่ และคุณต้องการให้เป็นเช่นนั้นจริงหรือ เพราะส่วนใหญ่แล้ว ข้อความแสดงข้อผิดพลาดที่แนะนำให้ใช้ไลฟ์ไทม์ `'static` มักเกิดจากความพยายามสร้าง dangling reference หรือเกิดจากไลฟ์ไทม์ที่มีอยู่ไม่สอดคล้องกัน ในกรณีเช่นนั้น วิธีแก้ที่ถูกต้องคือการจัดการกับปัญหาความสัมพันธ์ของไลฟ์ไทม์ ไม่ใช่การแก้ปัญหาเฉพาะหน้าด้วยการยัดเยียดไลฟ์ไทม์ `'static` ลงไป

## พารามิเตอร์ชนิดข้อมูลแบบเจเนอริก บาวด์ของเทรต และไลฟ์ไทม์

มาดูวากยสัมพันธ์ในการระบุทั้งพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก บาวด์ของเทรต (trait bound) และไลฟ์ไทม์พร้อมกันทั้งหมดในฟังก์ชันเดียวกันอย่างกระชับกัน!

```rust
{{#rustdoc_include ../listings/ch10-generic-types-traits-and-lifetimes/no-listing-11-generics-traits-and-lifetimes/src/main.rs:here}}
```

นี่คือฟังก์ชัน `longest` จากลิสติ้ง 10-21 ที่ส่งคืนสตริงสไลซ์ที่ยาวกว่าระหว่างสองตัว แต่คราวนี้มีพารามิเตอร์เพิ่มเติมชื่อ `ann` ซึ่งมีชนิดข้อมูลเจเนอริก `T` โดยสามารถเป็นชนิดข้อมูลใดก็ได้ที่อิมพลีเมนต์เทรต `Display` ตามที่ระบุไว้ในอนุประโยค `where` พารามิเตอร์เพิ่มเติมนี้จะถูกนำไปพิมพ์ด้วย `{}` ซึ่งเป็นเหตุผลที่จำเป็นต้องมีบาวด์ของเทรต `Display` และเนื่องจากไลฟ์ไทม์ก็เป็นเจเนอริกรูปแบบหนึ่ง การประกาศพารามิเตอร์ไลฟ์ไทม์ `'a` และพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก `T` จึงรวมอยู่ในรายการเดียวกันภายในวงเล็บสามเหลี่ยมหลังชื่อฟังก์ชัน

## สรุป

เราได้เรียนรู้เนื้อหาไปมากมายในบทนี้! ตอนนี้คุณเข้าใจทั้งเรื่องพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก เทรตและบาวด์ของเทรต ตลอดจนพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริกแล้ว คุณจึงพร้อมที่จะเขียนโค้ดที่ไม่ต้องทำซ้ำซ้อนและสามารถทำงานได้ในสถานการณ์ที่หลากหลาย พารามิเตอร์ชนิดข้อมูลแบบเจเนอริกช่วยให้คุณนำโค้ดเดิมไปประยุกต์ใช้กับชนิดข้อมูลที่แตกต่างกันได้ เทรตและบาวด์ของเทรตช่วยรับประกันว่าแม้จะเป็นชนิดข้อมูลแบบเจเนอริก แต่พวกมันก็จะมีพฤติกรรมตามที่โค้ดต้องการ และคุณยังได้เรียนรู้วิธีการใช้การระบุไลฟ์ไทม์เพื่อรับประกันว่าโค้ดที่มีความยืดหยุ่นนี้จะไม่มี dangling reference อยู่เลยแม้แต่น้อย ที่สำคัญคือการวิเคราะห์ทั้งหมดนี้เกิดขึ้นในตอนคอมไพล์ จึงไม่ส่งผลกระทบต่อประสิทธิภาพการทำงานตอนรันไทม์เลยแม้แต่นิดเดียว!

เชื่อหรือไม่ว่า ยังมีเนื้อหาให้ศึกษาเพิ่มเติมอีกมากเกี่ยวกับหัวข้อที่เราได้พูดคุยกันในบทนี้: ในบทที่ 18 เราจะพูดถึงเทรตออบเจกต์ (trait objects) ซึ่งเป็นอีกหนึ่งวิธีในการใช้งานเทรต นอกจากนี้ยังมีสถานการณ์ที่ซับซ้อนยิ่งขึ้นเกี่ยวกับการระบุไลฟ์ไทม์ ซึ่งคุณจะได้ใช้งานเฉพาะในกรณีขั้นสูงจริงๆ สำหรับหัวข้อเหล่านั้น คุณสามารถศึกษาเพิ่มเติมได้จาก [Rust Reference][reference] แต่ในบทถัดไป คุณจะได้เรียนรู้วิธีการเขียนชุดทดสอบ (tests) ใน Rust เพื่อให้มั่นใจได้ว่าโค้ดของคุณจะทำงานได้อย่างถูกต้องตามที่คาดหวังเสมอ
