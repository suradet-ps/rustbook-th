## การตรวจสอบความถูกต้องของเรเฟอเรนซ์ด้วยไลฟ์ไทม์

ไลฟ์ไทม์ (lifetime) เป็นเจเนอริก (generic) อีกชนิดหนึ่งที่เราได้ใช้งานมาแล้ว แทนที่จะรับประกันว่าชนิดข้อมูลหนึ่งมีพฤติกรรมตามที่เราต้องการ ไลฟ์ไทม์กลับรับประกันว่าเรเฟอเรนซ์ (reference) จะใช้ได้ตราบเท่าที่เราต้องการให้มันใช้ได้

รายละเอียดหนึ่งที่เรายังไม่ได้พูดคุยกันในหัวข้อ[“เรเฟอเรนซ์และการยืม”][references-and-borrowing]<!-- ignore --> ในบทที่ 4 ก็คือ ทุกเรเฟอเรนซ์ใน Rust มีไลฟ์ไทม์ ซึ่งเป็นสโคปที่เรเฟอเรนซ์นั้นใช้ได้ เวลาส่วนใหญ่ ไลฟ์ไทม์เป็นแบบโดยนัยและถูกอนุมาน เช่นเดียวกับที่เวลาส่วนใหญ่ ชนิดข้อมูลถูกอนุมาน เราจำเป็นต้องระบุชนิดข้อมูลเฉพาะเมื่อมีชนิดข้อมูลที่เป็นไปได้หลายชนิดเท่านั้น ในทำนองเดียวกัน เราต้องระบุไลฟ์ไทม์เมื่อไลฟ์ไทม์ของเรเฟอเรนซ์อาจมีความสัมพันธ์กันได้หลายแบบที่แตกต่างกัน Rust กำหนดให้เราระบุความสัมพันธ์เหล่านั้นโดยใช้พารามิเตอร์ไลฟ์ไทม์แบบเจเนอริก เพื่อให้แน่ใจว่าเรเฟอเรนซ์จริงที่ถูกใช้ตอนรันไทม์จะใช้ได้อย่างแน่นอน

การระบุไลฟ์ไทม์ (lifetime annotation) ไม่ใช่แม้แต่แนวคิดที่ภาษาโปรแกรมอื่นส่วนใหญ่มีด้วยซ้ำ มันจึงรู้สึกไม่คุ้นเคย แม้ว่าเราจะไม่ได้ครอบคลุมไลฟ์ไทม์ทั้งหมดในบทนี้ แต่เราจะพูดคุยถึงวิธีทั่วไปที่คุณอาจพบเจอวากยสัมพันธ์ของไลฟ์ไทม์ เพื่อให้คุณคุ้นเคยกับแนวคิดนี้

### วากยสัมพันธ์ของการระบุไลฟ์ไทม์

การระบุไลฟ์ไทม์ไม่ได้เปลี่ยนว่ามีเรเฟอเรนซ์ใดมีอายุอยู่ได้นานเท่าใด แต่เป็นการอธิบายความสัมพันธ์ระหว่างไลฟ์ไทม์ของเรเฟอเรนซ์หลายตัวซึ่งกันและกันโดยไม่ส่งผลต่อไลฟ์ไทม์เหล่านั้น เช่นเดียวกับที่ฟังก์ชันสามารถรับชนิดใดก็ได้เมื่อซิกเนเจอร์ระบุพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก (generic type parameter) ฟังก์ชันก็สามารถรับเรเฟอเรนซ์ที่มีไลฟ์ไทม์ใดก็ได้โดยการระบุพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริก

การระบุไลฟ์ไทม์มีวากยสัมพันธ์ที่แปลกไปเล็กน้อย: ชื่อของพารามิเตอร์ไลฟ์ไทม์ต้องขึ้นต้นด้วยเครื่องหมายอะพอสทรอฟี (`'`) และมักเป็นตัวพิมพ์เล็กทั้งหมดและสั้นมาก เช่นเดียวกับชนิดข้อมูลเจเนอริก คนส่วนใหญ่ใช้ชื่อ `'a` สำหรับการระบุไลฟ์ไทม์ตัวแรก เราวางการระบุพารามิเตอร์ไลฟ์ไทม์ไว้หลัง `&` ของเรเฟอเรนซ์ โดยใช้ช่องว่างเพื่อแยกการระบุนั้นออกจากชนิดข้อมูลของเรเฟอเรนซ์

นี่คือตัวอย่างบางส่วน—เรเฟอเรนซ์ไปยัง `i32` โดยไม่มีพารามิเตอร์ไลฟ์ไทม์, เรเฟอเรนซ์ไปยัง `i32` ที่มีพารามิเตอร์ไลฟ์ไทม์ชื่อ `'a`, และเรเฟอเรนซ์แบบเปลี่ยนแปลงได้ (mutable reference) ไปยัง `i32` ที่มีไลฟ์ไทม์ `'a` เช่นกัน:

```rust,ignore
&i32        // a reference
&'a i32     // a reference with an explicit lifetime
&'a mut i32 // a mutable reference with an explicit lifetime
```

การระบุไลฟ์ไทม์เพียงอันเดียวไม่มีความหมายมากนัก เพราะการระบุเหล่านั้นมีไว้เพื่อบอก Rust ว่าพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริกของเรเฟอเรนซ์หลายตัวสัมพันธ์กันอย่างไร มาดูกันว่าการระบุไลฟ์ไทม์ต่างๆ สัมพันธ์กันอย่างไรในบริบทของฟังก์ชัน `longest`

โปรดจำไว้ว่า เมื่อเราระบุพารามิเตอร์ไลฟ์ไทม์ในซิกเนเจอร์ของฟังก์ชันนี้ เราไม่ได้เปลี่ยนไลฟ์ไทม์ของค่าใดๆ ที่ถูกส่งเข้าหรือคืนกลับ แต่เรากำลังระบุว่าตัวตรวจการยืมควรปฏิเสธค่าใดๆ ที่ไม่เป็นไปตามข้อจำกัดเหล่านี้ โปรดสังเกตว่าฟังก์ชัน `longest` ไม่จำเป็นต้องรู้ว่า `x` และ `y` จะมีอายุอยู่ได้นานเท่าใดกันแน่ รู้เพียงว่ามีสโคปบางสโคปที่สามารถแทน `'a` ได้ซึ่งจะทำให้ซิกเนเจอร์นี้เป็นที่พอใจ

เมื่อระบุไลฟ์ไทม์ในฟังก์ชัน การระบุจะอยู่ในซิกเนเจอร์ของฟังก์ชัน ไม่ใช่ในบอดี้ของฟังก์ชัน การระบุไลฟ์ไทม์กลายเป็นส่วนหนึ่งของสัญญาของฟังก์ชัน คล้ายกับชนิดข้อมูลในซิกเนเจอร์มาก การที่ซิกเนเจอร์ของฟังก์ชันมีสัญญาเรื่องไลฟ์ไทม์อยู่ด้วยหมายความว่าการวิเคราะห์ที่คอมไพเลอร์ Rust ทำนั้นง่ายกว่าได้ หากมีปัญหาเกี่ยวกับวิธีการระบุไลฟ์ไทม์ของฟังก์ชันหรือวิธีการเรียกมัน ข้อผิดพลาดของคอมไพเลอร์ก็สามารถชี้ไปยังส่วนของโค้ดของเราและข้อจำกัดต่างๆ ได้อย่างแม่นยำยิ่งขึ้น ในทางกลับกัน หากคอมไพเลอร์ Rust อนุมานมากเกินไปว่าเราตั้งใจให้ความสัมพันธ์ของไลฟ์ไทม์เป็นอย่างไร คอมไพเลอร์อาจชี้ไปได้เพียงจุดที่ใช้งานโค้ดของเรา ซึ่งอยู่ห่างจากต้นเหตุของปัญหาหลายขั้นตอน

เมื่อเราส่งเรเฟอเรนซ์จริงไปยัง `longest` ไลฟ์ไทม์จริงที่ถูกแทนให้ `'a` คือส่วนของสโคปของ `x` ที่ทับซ้อนกับสโคปของ `y` พูดอีกนัยหนึ่ง ไลฟ์ไทม์แบบเจเนอริก `'a` จะได้รับไลฟ์ไทม์จริงที่เท่ากับไลฟ์ไทม์ที่เล็กกว่าระหว่างไลฟ์ไทม์ของ `x` และ `y` เพราะเราได้ระบุไลฟ์ไทม์ของเรเฟอเรนซ์ที่คืนกลับด้วยพารามิเตอร์ไลฟ์ไทม์ `'a` ตัวเดียวกัน เรเฟอเรนซ์ที่คืนกลับจึงใช้ได้เป็นระยะเวลาเท่ากับไลฟ์ไทม์ที่เล็กกว่าระหว่างไลฟ์ไทม์ของ `x` และ `y` ด้วย

struct นี้มีฟิลด์เดียวชื่อ `part` ที่เก็บสตริงสไลซ์ ซึ่งเป็นเรเฟอเรนซ์ เช่นเดียวกับชนิดข้อมูลเจเนอริก เราประกาศชื่อของพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริกภายในวงเล็บมุมหลังชื่อของ struct เพื่อให้เราสามารถใช้พารามิเตอร์ไลฟ์ไทม์ในบอดี้ของนิยาม struct ได้ การระบุนี้หมายความว่าอินสแตนซ์ของ `ImportantExcerpt` ไม่สามารถมีอายุยืนกว่าเรเฟอเรนซ์ที่มันเก็บไว้ในฟิลด์ `part` ของมันได้

ฟังก์ชัน `main` ตรงนี้สร้างอินสแตนซ์ของ struct `ImportantExcerpt` ที่เก็บเรเฟอเรนซ์ไปยังประโยคแรกของ `String` ที่ตัวแปร `novel` เป็นเจ้าของ ข้อมูลใน `novel` มีอยู่ก่อนที่อินสแตนซ์ของ `ImportantExcerpt` จะถูกสร้างขึ้น นอกจากนี้ `novel` ยังไม่ออกจากสโคปจนกระทั่งหลังจากที่ `ImportantExcerpt` ออกจากสโคป ดังนั้นเรเฟอเรนซ์ในอินสแตนซ์ของ `ImportantExcerpt` จึงใช้ได้

เหตุผลที่ฟังก์ชันนี้คอมไพล์ผ่านโดยไม่มีการระบุไลฟ์ไทม์นั้นเป็นเรื่องทางประวัติศาสตร์: ใน Rust เวอร์ชันแรกๆ (ก่อน 1.0) โค้ดนี้จะไม่คอมไพล์ เพราะทุกเรเฟอเรนซ์ต้องมีไลฟ์ไทม์ที่ระบุอย่างชัดแจ้ง ในยุคนั้น ซิกเนเจอร์ของฟังก์ชันจะถูกเขียนแบบนี้:

```rust,ignore
fn first_word<'a>(s: &'a str) -> &'a str {
```

หลังจากเขียนโค้ด Rust จำนวนมาก ทีม Rust พบว่านักเขียนโปรแกรม Rust ระบุไลฟ์ไทม์แบบเดียวกันซ้ำแล้วซ้ำเล่าในสถานการณ์เฉพาะบางอย่าง สถานการณ์เหล่านี้สามารถคาดเดาได้และเป็นไปตามแพตเทิร์นที่แน่นอนไม่กี่แบบ นักพัฒนาเหล่านี้เขียนแพตเทิร์นเหล่านั้นเข้าไปในโค้ดของคอมไพเลอร์ เพื่อให้ตัวตรวจการยืมสามารถอนุมานไลฟ์ไทม์ในสถานการณ์เหล่านี้ได้และไม่จำเป็นต้องมีการระบุอย่างชัดแจ้ง

เรื่องราวทางประวัติศาสตร์ของ Rust ส่วนนี้มีความเกี่ยวข้อง เพราะเป็นไปได้ว่าแพตเทิร์นที่แน่นอนมากขึ้นจะปรากฏขึ้นและถูกเพิ่มเข้าไปในคอมไพเลอร์ ในอนาคต อาจต้องระบุไลฟ์ไทม์น้อยลงไปอีก

แพตเทิร์นที่ถูกเขียนเข้าไปในการวิเคราะห์เรเฟอเรนซ์ของ Rust เรียกว่า_กฎการละไลฟ์ไทม์_ (lifetime elision rules) กฎเหล่านี้ไม่ใช่กฎที่นักเขียนโปรแกรมต้องปฏิบัติตาม แต่มันคือชุดของกรณีเฉพาะที่คอมไพเลอร์จะพิจารณา และหากโค้ดของคุณเข้าข่ายกรณีเหล่านี้ คุณก็ไม่จำเป็นต้องเขียนไลฟ์ไทม์อย่างชัดแจ้ง

กฎการละไลฟ์ไทม์ไม่ได้ให้การอนุมานที่สมบูรณ์ หากยังมีความกำกวมว่าเรเฟอเรนซ์มีไลฟ์ไทม์อะไรหลังจากที่ Rust ใช้กฎเหล่านี้แล้ว คอมไพเลอร์จะไม่เดาว่าไลฟ์ไทม์ของเรเฟอเรนซ์ที่เหลือควรเป็นอะไร แทนที่จะเดา คอมไพเลอร์จะให้ข้อผิดพลาดแก่คุณซึ่งคุณสามารถแก้ไขได้โดยการเพิ่มการระบุไลฟ์ไทม์

ไลฟ์ไทม์บนพารามิเตอร์ของฟังก์ชันหรือเมธอดเรียกว่า_ไลฟ์ไทม์ขาเข้า_ (input lifetimes) และไลฟ์ไทม์บนค่าที่คืนกลับเรียกว่า_ไลฟ์ไทม์ขาออก_ (output lifetimes)

คอมไพเลอร์ใช้สามกฎเพื่อหาไลฟ์ไทม์ของเรเฟอเรนซ์เมื่อไม่มีการระบุอย่างชัดแจ้ง กฎข้อแรกใช้กับไลฟ์ไทม์ขาเข้า และกฎข้อที่สองกับข้อที่สามใช้กับไลฟ์ไทม์ขาออก หากคอมไพเลอร์ไปถึงท้ายของกฎทั้งสามข้อแล้วยังมีเรเฟอเรนซ์ที่มันยังหาไลฟ์ไทม์ไม่ได้ คอมไพเลอร์จะหยุดพร้อมข้อผิดพลาด กฎเหล่านี้ใช้กับนิยาม `fn` รวมถึงบล็อก `impl` ด้วย

กฎข้อแรกคือ คอมไพเลอร์กำหนดพารามิเตอร์ไลฟ์ไทม์ให้กับพารามิเตอร์ทุกตัวที่เป็นเรเฟอเรนซ์ พูดอีกนัยหนึ่ง ฟังก์ชันที่มีพารามิเตอร์หนึ่งตัวจะได้พารามิเตอร์ไลฟ์ไทม์หนึ่งตัว: `fn foo<'a>(x: &'a i32)`; ฟังก์ชันที่มีพารามิเตอร์สองตัวจะได้พารามิเตอร์ไลฟ์ไทม์แยกกันสองตัว: `fn foo<'a, 'b>(x: &'a i32, y: &'b i32)`; และอื่นๆ

กฎข้อที่สองคือ หากมีพารามิเตอร์ไลฟ์ไทม์ขาเข้าเพียงตัวเดียวพอดี ไลฟ์ไทม์นั้นจะถูกกำหนดให้กับพารามิเตอร์ไลฟ์ไทม์ขาออกทั้งหมด: `fn foo<'a>(x: &'a i32) -> &'a i32`

กฎข้อที่สามคือ หากมีพารามิเตอร์ไลฟ์ไทม์ขาเข้าหลายตัว แต่ตัวหนึ่งในนั้นเป็น `&self` หรือ `&mut self` เพราะนี่เป็นเมธอด ไลฟ์ไทม์ของ `self` จะถูกกำหนดให้กับพารามิเตอร์ไลฟ์ไทม์ขาออกทั้งหมด กฎข้อที่สามนี้ทำให้เมธอดอ่านและเขียนได้สบายกว่ามาก เพราะต้องใช้สัญลักษณ์น้อยลง

สมมติว่าเราเป็นคอมไพเลอร์กัน เราจะใช้กฎเหล่านี้เพื่อหาไลฟ์ไทม์ของเรเฟอเรนซ์ในซิกเนเจอร์ของฟังก์ชัน `first_word` ในลิสติ้ง 10-25 ซิกเนเจอร์เริ่มต้นโดยไม่มีไลฟ์ไทม์ใดๆ สัมพันธ์กับเรเฟอเรนซ์เหล่านั้น:

```rust,ignore
fn first_word(s: &str) -> &str {
```

จากนั้น คอมไพเลอร์ใช้กฎข้อแรก ซึ่งระบุว่าพารามิเตอร์แต่ละตัวได้ไลฟ์ไทม์ของตัวเอง เราจะเรียกมันว่า `'a` ตามปกติ ตอนนี้ซิกเนเจอร์จึงเป็นแบบนี้:

```rust,ignore
fn first_word<'a>(s: &'a str) -> &str {
```

กฎข้อที่สองถูกนำมาใช้เพราะมีไลฟ์ไทม์ขาเข้าเพียงตัวเดียวพอดี กฎข้อที่สองระบุว่าไลฟ์ไทม์ของพารามิเตอร์ขาเข้าตัวนั้นจะถูกกำหนดให้กับไลฟ์ไทม์ขาออก ซิกเนเจอร์ตอนนี้จึงเป็นแบบนี้:

```rust,ignore
fn first_word<'a>(s: &'a str) -> &'a str {
```

ตอนนี้เรเฟอเรนซ์ทั้งหมดในซิกเนเจอร์ของฟังก์ชันนี้มีไลฟ์ไทม์แล้ว และคอมไพเลอร์สามารถวิเคราะห์ต่อไปได้โดยไม่ต้องให้นักเขียนโปรแกรมระบุไลฟ์ไทม์ในซิกเนเจอร์ของฟังก์ชันนี้

มาดูตัวอย่างอื่น คราวนี้ใช้ฟังก์ชัน `longest` ที่ไม่มีพารามิเตอร์ไลฟ์ไทม์ตอนที่เราเริ่มต้นทำงานกับมันในลิสติ้ง 10-20:

```rust,ignore
fn longest(x: &str, y: &str) -> &str {
```

มาลองใช้กฎข้อแรกกัน: พารามิเตอร์แต่ละตัวได้ไลฟ์ไทม์ของตัวเอง คราวนี้เรามีพารามิเตอร์สองตัวแทนที่จะเป็นหนึ่งตัว เราจึงมีไลฟ์ไทม์สองตัว:

```rust,ignore
fn longest<'a, 'b>(x: &'a str, y: &'b str) -> &str {
```

คุณจะเห็นได้ว่ากฎข้อที่สองไม่ถูกนำมาใช้ เพราะมีไลฟ์ไทม์ขาเข้ามากกว่าหนึ่งตัว กฎข้อที่สามก็ไม่ถูกนำมาใช้เช่นกัน เพราะ `longest` เป็นฟังก์ชันไม่ใช่เมธอด ดังนั้นจึงไม่มีพารามิเตอร์ตัวใดเป็น `self` หลังจากไล่ผ่านกฎทั้งสามข้อแล้ว เราก็ยังไม่รู้ว่าไลฟ์ไทม์ของชนิดที่คืนกลับคืออะไร นี่คือสาเหตุที่เราได้ข้อผิดพลาดเมื่อพยายามคอมไพล์โค้ดในลิสติ้ง 10-20: คอมไพเลอร์ไล่ผ่านกฎการละไลฟ์ไทม์แล้วแต่ก็ยังไม่สามารถหาไลฟ์ไทม์ทั้งหมดของเรเฟอเรนซ์ในซิกเนเจอร์ได้

เนื่องจากกฎข้อที่สามใช้ได้จริงๆ เฉพาะในซิกเนเจอร์ของเมธอดเท่านั้น เราจะดูไลฟ์ไทม์ในบริบทนั้นต่อไป เพื่อดูว่าทำไมกฎข้อที่สามทำให้เราไม่ต้องระบุไลฟ์ไทม์ในซิกเนเจอร์ของเมธอดบ่อยนัก

### ในนิยามของเมธอด

เมื่อเราอิมพลีเมนต์เมธอดบน struct ที่มีไลฟ์ไทม์ เราใช้วากยสัมพันธ์เดียวกันกับพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก ดังที่แสดงในลิสติ้ง 10-11 ตำแหน่งที่เราประกาศและใช้พารามิเตอร์ไลฟ์ไทม์นั้นขึ้นอยู่กับว่าพวกมันเกี่ยวข้องกับฟิลด์ของ struct หรือพารามิเตอร์ของเมธอดและค่าที่คืนกลับ

ชื่อไลฟ์ไทม์สำหรับฟิลด์ของ struct ต้องถูกประกาศหลังคำสงวน `impl` เสมอ แล้วนำไปใช้หลังชื่อของ struct เพราะไลฟ์ไทม์เหล่านั้นเป็นส่วนหนึ่งของชนิดข้อมูลของ struct

ในซิกเนเจอร์ของเมธอดภายในบล็อก `impl` เรเฟอเรนซ์อาจผูกติดกับไลฟ์ไทม์ของเรเฟอเรนซ์ในฟิลด์ของ struct หรืออาจเป็นอิสระจากกันก็ได้ นอกจากนี้ กฎการละไลฟ์ไทม์มักทำให้ไม่จำเป็นต้องระบุไลฟ์ไทม์ในซิกเนเจอร์ของเมธอด มาดูตัวอย่างบางส่วนที่ใช้ struct ชื่อ `ImportantExcerpt` ที่เรานิยามไว้ในลิสติ้ง 10-24

### ไลฟ์ไทม์ `'static`

ไลฟ์ไทม์พิเศษตัวหนึ่งที่เราต้องพูดคุยคือ `'static` ซึ่งหมายความว่าเรเฟอเรนซ์ที่เกี่ยวข้องนั้น_สามารถ_มีอายุอยู่ได้ตลอดทั้งการทำงานของโปรแกรม สตริงลิเทอรัล (string literal) ทั้งหมดมีไลฟ์ไทม์ `'static` ซึ่งเราสามารถระบุได้ดังนี้:

```rust
let s: &'static str = "I have a static lifetime.";
```

ข้อความของสตริงนี้ถูกจัดเก็บไว้โดยตรงในไฟล์ไบนารีของโปรแกรม ซึ่งพร้อมใช้งานเสมอ ดังนั้นไลฟ์ไทม์ของสตริงลิเทอรัลทั้งหมดจึงเป็น `'static`

คุณอาจเห็นคำแนะนำในข้อความแสดงข้อผิดพลาดให้ใช้ไลฟ์ไทม์ `'static` แต่ก่อนจะระบุ `'static` เป็นไลฟ์ไทม์ของเรเฟอเรนซ์ ให้คิดก่อนว่าเรเฟอเรนซ์ที่คุณมีนั้นมีอายุอยู่ตลอดทั้งโปรแกรมของคุณจริงหรือไม่ และคุณต้องการให้มันเป็นเช่นนั้นหรือเปล่า เวลาส่วนใหญ่ ข้อความแสดงข้อผิดพลาดที่แนะนำให้ใช้ไลฟ์ไทม์ `'static` เกิดจากการพยายามสร้างเรเฟอเรนซ์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้ว หรือเกิดจากไลฟ์ไทม์ที่มีอยู่ไม่สอดคล้องกัน ในกรณีเช่นนั้น วิธีแก้คือการแก้ไขปัญหาเหล่านั้น ไม่ใช่การระบุไลฟ์ไทม์ `'static`

## พารามิเตอร์ชนิดข้อมูลแบบเจเนอริก บาวด์ของเทรต และไลฟ์ไทม์

## สรุป

เราครอบคลุมเนื้อหามากมายในบทนี้! ตอนนี้คุณรู้จักพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก เทรตและบาวด์ของเทรต และพารามิเตอร์ไลฟ์ไทม์แบบเจเนอริกแล้ว คุณก็พร้อมที่จะเขียนโค้ดที่ไม่ต้องทำซ้ำและทำงานได้ในหลายสถานการณ์ที่แตกต่างกัน พารามิเตอร์ชนิดข้อมูลแบบเจเนอริกช่วยให้คุณนำโค้ดไปใช้กับชนิดข้อมูลต่างๆ ได้ เทรตและบาวด์ของเทรตช่วยรับประกันว่าแม้ชนิดข้อมูลจะเป็นแบบเจเนอริก แต่ชนิดเหล่านั้นก็จะมีพฤติกรรมที่โค้ดต้องการ คุณได้เรียนรู้วิธีใช้การระบุไลฟ์ไทม์เพื่อรับประกันว่าโค้ดที่ยืดหยุ่นนี้จะไม่มีเรเฟอเรนซ์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้วเลย และการวิเคราะห์ทั้งหมดนี้เกิดขึ้นตอนคอมไพล์ ซึ่งไม่ส่งผลต่อประสิทธิภาพตอนรันไทม์!

เชื่อหรือไม่ว่า ยังมีอะไรให้เรียนรู้อีกมากในหัวข้อที่เราพูดคุยกันในบทนี้: บทที่ 18 พูดคุยถึงเทรตออบเจกต์ (trait object) ซึ่งเป็นอีกวิธีหนึ่งในการใช้เทรต นอกจากนี้ยังมีสถานการณ์ที่ซับซ้อนมากขึ้นซึ่งเกี่ยวข้องกับการระบุไลฟ์ไทม์ที่คุณจะต้องใช้เฉพาะในสถานการณ์ขั้นสูงมากๆ เท่านั้น สำหรับเรื่องเหล่านั้น คุณควรอ่าน[Rust Reference][reference] แต่ต่อไป คุณจะได้เรียนรู้วิธีเขียนเทสต์ใน Rust เพื่อให้คุณมั่นใจได้ว่าโค้ดของคุณทำงานอย่างที่มันควรจะทำ
