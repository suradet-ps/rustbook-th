## การนิยาม enum

ในขณะที่ `struct` เป็นเครื่องมือสำหรับจัดกลุ่มฟิลด์และข้อมูลที่เกี่ยวข้องกันเข้าไว้ด้วยกัน เช่น `Rectangle` ที่มี `width` และ `height` แต่ `enum` กลับเป็นเครื่องมือที่ใช้สำหรับบ่งบอกว่า ค่าหนึ่งๆ นั้นเป็นหนึ่งในกลุ่มของค่าที่เป็นไปได้ ตัวอย่างเช่น เราอาจต้องการระบุว่า `Rectangle` เป็นหนึ่งในรูปทรงเรขาคณิตที่เป็นไปได้ ซึ่งประกอบด้วย `Circle` และ `Triangle` ด้วย เป็นต้น และเพื่อรองรับการทำงานในลักษณะนี้ Rust จึงอนุญาตให้เราเขียนแทนความเป็นไปได้เหล่านี้ด้วย `enum`

ลองมาดูสถานการณ์ตัวอย่างจริงในโค้ด เพื่อทำความเข้าใจว่าทำไม `enum` จึงมีประโยชน์และเหมาะสมกว่า `struct` ในบางกรณี สมมติว่าเราต้องเขียนโปรแกรมจัดการกับที่อยู่ไอพี (IP address) ซึ่งในปัจจุบันมีมาตรฐานหลักอยู่ 2 แบบ คือ IPv4 และ IPv6 และเนื่องจากความเป็นไปได้ของที่อยู่ไอพีที่โปรแกรมของเราจะต้องพบเจอมีเพียง 2 แบบนี้เท่านั้น เราจึงสามารถ _แจกแจง_ (enumerate) วาเรียนต์ (variant) ที่เป็นไปได้ทั้งหมดออกมาได้ ซึ่งนี่คือที่มาของคำว่า enumeration หรือ enum นั่นเอง

ที่อยู่ไอพีใดๆ ย่อมสามารถเป็นได้เพียง IPv4 หรือ IPv6 อย่างใดอย่างหนึ่งเท่านั้น แต่ไม่สามารถเป็นทั้งสองอย่างพร้อมกันได้ในเวลาเดียวกัน คุณลักษณะนี้ตรงกับธรรมชาติของโครงสร้างข้อมูลแบบ `enum` อย่างสมบูรณ์แบบ เพราะค่าของ `enum` หนึ่งๆ จะสามารถเป็นได้เพียงหนึ่งในวาเรียนต์ของมันเท่านั้นในขณะใดขณะหนึ่ง อย่างไรก็ตาม ทั้งที่อยู่ IPv4 และ IPv6 ต่างก็ยังคงถือเป็นที่อยู่ไอพีเหมือนกันในระดับพื้นฐาน ดังนั้นพวกมันจึงควรถูกปฏิบัติเหมือนเป็นชนิดข้อมูลเดียวกันเมื่อโค้ดกำลังทำงานในส่วนที่ใช้ได้กับที่อยู่ไอพีทุกประเภท

การใช้ enum ยังมีข้อได้เปรียบเหนือกว่า struct อีกประการหนึ่งคือ: แต่ละวาเรียนต์สามารถมีชนิดข้อมูลและจำนวนข้อมูลที่ผูกติดอยู่แตกต่างกันได้อย่างอิสระ สำหรับที่อยู่ IPv4 จะประกอบด้วยตัวเลข 4 ส่วนที่มีค่าระหว่าง 0 ถึง 255 เสมอ หากเราต้องการจัดเก็บที่อยู่ `V4` เป็นตัวเลข `u8` จำนวน 4 ค่า แต่ยังคงต้องการจัดเก็บที่อยู่ `V6` เป็นสตริง `String` เพียงค่าเดียว เราจะไม่สามารถทำได้สะดวกด้วย `struct` แต่สำหรับ `enum` แล้ว สามารถจัดการกรณีนี้ได้อย่างง่ายดาย:


เราได้เห็นวิธีต่างๆ ในการจัดโครงสร้างข้อมูลเพื่อจัดเก็บที่อยู่ไอพีทั้งแบบ IPv4 และ IPv6 กันไปแล้ว อย่างไรก็ดี ความต้องการในการจัดเก็บที่อยู่ไอพีพร้อมระบุเวอร์ชันนั้นเป็นเรื่องที่พบได้บ่อยมากในทางปฏิบัติ จนกระทั่ง [ไลบรารีมาตรฐานมีนิยามของ `IpAddr` เตรียมไว้ให้เราใช้งานได้ทันที!][IpAddr]<!-- ignore --> ลองมาดูกันว่าในไลบรารีมาตรฐานนิยาม `IpAddr` ไว้อย่างไร ซึ่งโครงสร้างมีลักษณะเหมือนกับที่เราเขียนไว้ทุกประการ เพียงแต่ข้อมูลของที่อยู่ถูกฝังไว้ในรูปของ struct 2 ตัวที่แยกกันสำหรับแต่ละวาเรียนต์:

```rust
struct Ipv4Addr {
    // --snip--
}

struct Ipv6Addr {
    // --snip--
}

enum IpAddr {
    V4(Ipv4Addr),
    V6(Ipv6Addr),
}
```

โค้ดนี้แสดงให้เห็นว่าคุณสามารถใส่ข้อมูลชนิดใดก็ได้ไว้ในวาเรียนต์ของ enum ไม่ว่าจะเป็นสตริง, ตัวเลข, struct หรือแม้กระทั่งใส่ enum อีกตัวซ้อนเข้าไปข้างในก็ทำได้เช่นกัน! และชนิดข้อมูลต่างๆ ในไลบรารีมาตรฐานก็มักจะไม่ได้ซับซ้อนไปกว่าสิ่งที่คุณสามารถออกแบบขึ้นมาเองได้เลย

โปรดสังเกตว่าแม้ไลบรารีมาตรฐานจะมีนิยามของ `IpAddr` อยู่แล้ว เราก็ยังคงสามารถสร้างและใช้งานนิยาม `IpAddr` ของเราเองได้โดยไม่เกิดข้อขัดแย้งใดๆ เนื่องจากเรายังไม่ได้นำ (import) นิยามของไลบรารีมาตรฐานเข้ามาในขอบเขต (scope) ของโปรแกรม ซึ่งเราจะพูดถึงการนำชนิดข้อมูลเข้าสู่ขอบเขตการใช้งานอย่างละเอียดในบทที่ 7

### enum `Option`

ในหัวข้อนี้ เราจะมาศึกษากรณีตัวอย่างของ `Option` ซึ่งเป็น enum อีกตัวหนึ่งที่ไลบรารีมาตรฐานของ Rust จัดเตรียมไว้ให้ โดยชนิดข้อมูล `Option` ถูกสร้างขึ้นมาเพื่อรองรับสถานการณ์ที่พบบ่อยมากในการเขียนโปรแกรม นั่นคือ **ค่าข้อมูลที่อาจจะมีอยู่จริง หรืออาจไม่มีค่าใดๆ เลยก็ได้**

ตัวอย่างเช่น หากคุณร้องขอสมาชิกตัวแรกจากรายการ (list) ที่มีข้อมูลอยู่ คุณย่อมได้ค่านั้นกลับมา แต่หากคุณร้องขอสมาชิกตัวแรกจากรายการที่ว่างเปล่า คุณย่อมไม่ได้ค่าใดๆ กลับมาเลย การนำแนวคิดนี้มาผนวกเข้าไว้ในระบบชนิดข้อมูลช่วยให้คอมไพเลอร์สามารถตรวจสอบได้ว่า คุณได้เขียนโค้ดรองรับทุกกรณีที่อาจเกิดขึ้นแล้วหรือยัง ซึ่งกลไกนี้สามารถป้องกันบั๊กที่พบบ่อยและสร้างความปวดหัวในภาษาโปรแกรมอื่นๆ ได้อย่างมหาศาล

ในการออกแบบภาษาโปรแกรม สิ่งที่ถูกใส่เข้ามามีความสำคัญฉันใด สิ่งที่ถูกตัดออกไปก็มีความสำคัญไม่ยิ่งหย่อนไปกว่ากัน โดยในภาษา Rust **ไม่มีแนวคิดเรื่อง null** เหมือนอย่างที่ภาษาโปรแกรมส่วนใหญ่มี _Null_ คือค่าพิเศษที่บ่งบอกว่าไม่มีค่าอยู่ตรงนั้น ซึ่งในภาษาที่มี null ตัวแปรจะสามารถตกอยู่ในสถานะใดสถานะหนึ่งจากสองสถานะนี้เสมอ คือ เป็น null หรือ ไม่เป็น null

ในการนำเสนอเมื่อปี 2009 ในหัวข้อ “Null References: The Billion Dollar Mistake” Tony Hoare ผู้คิดค้นแนวคิดเรื่อง null ได้กล่าวไว้ว่า:

> ผมเรียกมันว่าความผิดพลาดมูลค่าพันล้านดอลลาร์ของผม ในตอนนั้น ผมกำลังออกแบบระบบชนิดข้อมูลที่ครอบคลุมสำหรับเรเฟอเรนซ์เป็นครั้งแรกในภาษาเชิงวัตถุ
> เป้าหมายของผมคือต้องการให้การใช้งานเรเฟอเรนซ์ทุกจุดมีความปลอดภัยอย่างสมบูรณ์ โดยมีการตรวจสอบอย่างอัตโนมัติจากคอมไพเลอร์
> แต่ผมกลับต้านทานความเย้ายวนใจที่จะใส่เรเฟอเรนซ์แบบ null เข้าไปไม่ไหว เพียงเพราะว่ามันเขียนอิมพลีเมนต์ได้ง่ายมาก
> และนั่นก็นำไปสู่ข้อผิดพลาด ช่องโหว่ความปลอดภัย และระบบล่มนับครั้งไม่ถ้วน ซึ่งน่าจะสร้างความสูญเสียและความเสียหายคิดเป็นมูลค่ารวมไม่น้อยกว่าหนึ่งพันล้านดอลลาร์ตลอดช่วงสี่สิบปีที่ผ่านมา

ปัญหาสำคัญของค่า null คือ หากคุณพยายามนำค่าที่เป็น null ไปใช้งานเสมือนว่ามันมีค่าอยู่จริง โปรแกรมจะเกิดข้อผิดพลาดรุนแรงขึ้นทันที และเนื่องจากคุณสมบัติของการเป็น null หรือไม่เป็น null นี้สามารถแฝงตัวอยู่ได้ในทุกๆ ตัวแปร จึงทำให้เกิดข้อผิดพลาดในลักษณะนี้ได้ง่ายดายมาก

อย่างไรก็ตาม แนวคิดเบื้องหลังที่ null พยายามจะสื่อนั้นยังมีประโยชน์อยู่ นั่นคือ ความต้องการจะสื่อว่าขณะนี้ยังไม่มีค่าที่ถูกต้อง หรือยังไม่มีข้อมูลอยู่ ณ เวลานั้น

ปัญหาจึงไม่ได้อยู่ที่ตัวแนวคิด แต่อยู่ที่วิธีการอิมพลีเมนต์ที่ผิดพลาด ด้วยเหตุนี้ Rust จึงไม่มีค่า null แต่หันมาใช้ `enum` ในการเข้ารหัสแนวคิดของค่าที่มีอยู่หรือไม่มีอยู่แทน ซึ่ง enum ตัวนี้ก็คือ `Option<T>` โดย [ไลบรารีมาตรฐานได้นิยามไว้][option]<!-- ignore --> ดังนี้:

```rust
enum Option<T> {
    None,
    Some(T),
}
```

enum `Option<T>` มีประโยชน์และใช้งานบ่อยมากจนกระทั่งถูกรวมไว้ในพรีลูด (prelude) ของภาษา ทำให้คุณสามารถเรียกใช้งานได้ทันทีโดยไม่ต้องนำเข้าสโคปด้วยตนเอง และวาเรียนต์ของมันก็ถูกรวมไว้ในพรีลูดเช่นกัน คุณจึงสามารถเขียน `Some` และ `None` ได้โดยตรงโดยไม่ต้องมีคำนำหน้า `Option::` ทั้งนี้ `Option<T>` ก็ยังคงเป็น enum ธรรมดาตัวหนึ่ง และ `Some(T)` กับ `None` ก็ยังคงเป็นวาเรียนต์ของชนิดข้อมูล `Option<T>`

ไวยากรณ์ `<T>` เป็นฟีเจอร์ของ Rust ที่เรายังไม่ได้พูดถึงในรายละเอียด มันคือพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก (generic type parameter) ซึ่งเราจะได้เรียนรู้เรื่องเจเนอริกอย่างเจาะลึกในบทที่ 10 สำหรับตอนนี้ สิ่งที่คุณต้องเข้าใจคือ `<T>` หมายความว่า วาเรียนต์ `Some` ของ enum `Option` สามารถจัดเก็บข้อมูลชนิดใดก็ได้หนึ่งชิ้น และเมื่อนำชนิดข้อมูลจริงมาแทนที่ `T` ก็จะทำให้ `Option<T>` กลายเป็นชนิดข้อมูลที่มีความเฉพาะเจาะจงแตกต่างกันไป ตัวอย่างการนำ `Option` ไปจัดเก็บตัวเลขและอักขระมีดังนี้:

ชนิดข้อมูลของ `some_number` คือ `Option<i32>` ส่วนของ `some_char` คือ `Option<char>` ซึ่งทั้งสองเป็นคนละชนิดข้อมูลกัน Rust สามารถอนุมานชนิดข้อมูลเหล่านี้ได้จากค่าที่เราใส่ไว้ในวาเรียนต์ `Some` ส่วนในกรณีของ `absent_number` เราจำเป็นต้องระบุชนิดข้อมูลของ `Option` ให้ Rust ทราบอย่างชัดเจน เนื่องจากคอมไพเลอร์ไม่สามารถอนุมานได้ว่าวาเรียนต์ `Some` ที่คู่กันควรจะเก็บชนิดข้อมูลใดหากมองเห็นเพียงแค่ค่า `None` ดังนั้นเราจึงบอก Rust ให้ชัดเจนว่า `absent_number` มีชนิดข้อมูลเป็น `Option<i32>`

เมื่อเรามีค่า `Some` เราจะมั่นใจได้ว่ามีข้อมูลอยู่จริง และข้อมูลนั้นบรรจุอยู่ภายใน `Some` และเมื่อเราได้ค่า `None` มันจะมีความหมายเทียบเท่ากับ null นั่นคือไม่มีข้อมูลที่ถูกต้องอยู่ แล้วทำไมการใช้ `Option<T>` จึงปลอดภัยและดีกว่าการใช้ null ล่ะ?

คำตอบสั้นๆ ก็คือ **เนื่องจาก `Option<T>` และ `T` (โดยที่ `T` คือชนิดข้อมูลใดๆ) เป็นคนละชนิดข้อมูลกันโดยสิ้นเชิง คอมไพเลอร์จึงจะไม่อนุญาตให้เรานำค่าของ `Option<T>` ไปใช้งานเสมือนเป็นค่า `T` ที่ถูกต้องโดยตรงได้เลย** ตัวอย่างเช่น โค้ดต่อไปนี้จะไม่สามารถคอมไพล์ผ่านได้ เพราะพยายามนำตัวเลข `i8` ไปบวกเข้ากับ `Option<i8>`:

ชัดเจนและรัดกุมมาก! ใจความของข้อผิดพลาดนี้คือ Rust ไม่สามารถนำ `i8` มาบวกกับ `Option<i8>` ได้ เพราะทั้งสองเป็นคนละชนิดข้อมูลกัน เมื่อเรามีค่าที่เป็นชนิด `i8` ปกติใน Rust คอมไพเลอร์จะรับประกันเสมอว่าค่านั้นมีตัวตนอยู่จริงและถูกต้องแน่นอน เราจึงสามารถเขียนโค้ดนำค่านั้นไปคำนวณต่อได้อย่างมั่นใจ 100% โดยไม่ต้องคอยตรวจสอบเงื่อนไขว่าเป็น null หรือไม่ก่อนใช้งาน แต่หากตัวแปรนั้นเป็นชนิด `Option<i8>` (หรือชนิดข้อมูลใดๆ ที่อยู่ใน Option) นั่นคือจุดเดียวที่เราจะต้องตระหนักว่าค่านั้นอาจจะไม่มีอยู่จริง และคอมไพเลอร์จะบังคับให้เราต้องเขียนโค้ดจัดการกรณีที่ไม่มีค่านั้นก่อนเสมอ จึงจะสามารถดึงค่านั้นออกมาใช้งานได้

กล่าวอีกนัยหนึ่ง คุณจำเป็นต้องแปลง `Option<T>` ให้กลายเป็น `T` เสียก่อน จึงจะสามารถดำเนินการต่างๆ ในแบบของ `T` กับมันได้ ซึ่งกลไกนี้ช่วยกำจัดปัญหาคลาสสิกของ null ไปได้อย่างสิ้นเชิง นั่นคือปัญหาของการเผลอทึกทักเอาเองว่าตัวแปรมีค่าอยู่จริง ทั้งที่ในความจริงแล้วมันเป็น null

การตัดความเสี่ยงจากการทึกทักเอาเองว่าตัวแปรไม่ใช่ null ช่วยให้คุณมั่นใจในความปลอดภัยของโค้ดได้อย่างเต็มที่ หากคุณต้องการให้ตัวแปรใดมีโอกาสที่จะไม่มีค่าได้ คุณจะต้องประกาศชนิดข้อมูลให้เป็น `Option<T>` อย่างชัดเจนเสมอ และเมื่อต้องการนำค่านั้นไปใช้ คุณก็จะต้องเขียนโค้ดรองรับกรณีที่มันไม่มีค่าไว้อย่างชัดเจนด้วยเช่นกัน ในทางกลับกัน ทุกๆ ที่ในโค้ดที่ตัวแปรไม่ได้เป็น `Option<T>` คุณจะสามารถมั่นใจได้อย่างปลอดภัยเสมอว่าค่านั้นไม่มีทางเป็น null อย่างแน่นอน นี่คือการตัดสินใจออกแบบอย่างตั้งใจของภาษา Rust เพื่อควบคุมและจำกัดการแพร่กระจายของปัญหา null พร้อมทั้งยกระดับความปลอดภัยของโค้ดขึ้นสู่ระดับสูงสุด

แล้วเราจะดึงค่า `T` ออกมาจากวาเรียนต์ `Some` เพื่อนำไปใช้งานได้อย่างไรเมื่อมีตัวแปรชนิด `Option<T>`? ใน enum `Option<T>` มีเมธอดที่พร้อมใช้งานและมีประโยชน์อย่างมากในหลากหลายสถานการณ์ ซึ่งคุณสามารถศึกษาได้จาก [เอกสารของ Option][docs]<!-- ignore --> การทำความคุ้นเคยกับเมธอดต่างๆ ของ `Option<T>` จะเป็นประโยชน์อย่างยิ่งตลอดเส้นทางการเขียนโปรแกรมด้วยภาษา Rust ของคุณ

โดยทั่วไปแล้ว ในการใช้งานค่าของ `Option<T>` คุณจะต้องมีโค้ดที่คอยจัดการกับแต่ละวาเรียนต์ โดยจะมีโค้ดส่วนหนึ่งที่ทำงานเฉพาะเมื่อมีค่า `Some(T)` และโค้ดส่วนนี้จะได้รับอนุญาตให้เข้าถึงและใช้งานค่า `T` ที่อยู่ภายในได้ และมีโค้ดอีกส่วนหนึ่งที่จะทำงานเมื่อเป็นค่า `None` ซึ่งจะไม่มีค่า `T` ให้ใช้งาน นิพจน์ `match` คือโครงสร้างควบคุมลำดับการทำงาน (control flow) ที่ถูกออกแบบมาเพื่อจัดการเรื่องนี้กับ enum ได้อย่างสมบูรณ์แบบ โดยมันจะแยกการทำงานของโค้ดตามแต่ละวาเรียนต์ของ enum และเปิดให้โค้ดในแต่ละกิ่งสามารถดึงข้อมูลที่แนบมากับค่านั้นไปใช้งานได้อย่างปลอดภัย
