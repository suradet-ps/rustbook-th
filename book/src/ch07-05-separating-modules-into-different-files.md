## แยกมอดูลออกเป็นไฟล์ต่างๆ

จนถึงตอนนี้ ตัวอย่างทั้งหมดในบทนี้ล้วนเป็นการนิยามหลายๆ มอดูลรวมไว้ภายในไฟล์เดียวกัน แต่เมื่อมอดูลเริ่มมีขนาดใหญ่และซับซ้อนขึ้น คุณอาจต้องการย้ายนิยามของมอดูลเหล่านั้นออกไปไว้ในไฟล์แยกต่างหาก เพื่อให้ง่ายต่อการค้นหาและไล่อ่านโค้ด

ตัวอย่างเช่น เราลองมาเริ่มต้นจากโค้ดในลิสติ้ง 7-17 ที่มีหลายมอดูลของร้านอาหารรวมกันอยู่ เราจะแยกมอดูลต่างๆ ออกเป็นไฟล์ย่อยๆ แทนที่จะนิยามมอดูลทั้งหมดไว้ในไฟล์รากของเครต (crate root) ซึ่งในกรณีนี้ ไฟล์รากของเครตคือ _src/lib.rs_ แต่กระบวนการนี้สามารถนำไปใช้กับเครตไบนารีที่มีไฟล์รากเป็น _src/main.rs_ ได้เช่นเดียวกันทุกประการ

อันดับแรก เราจะแยกมอดูล `front_of_house` ออกไปเป็นไฟล์ของตัวเอง ให้ลบโค้ดที่อยู่ภายในวงเล็บปีกกาของมอดูล `front_of_house` ออกทั้งหมด โดยคงเหลือไว้เพียงคำประกาศ `mod front_of_house;` เท่านั้น ส่งผลให้ไฟล์ _src/lib.rs_ มีเนื้อหาดังที่แสดงในลิสติ้ง 7-21 โปรดทราบว่าโค้ดนี้จะยังคอมไพล์ไม่ผ่าน จนกว่าเราจะสร้างไฟล์ _src/front_of_house.rs_ ตามลิสติ้ง 7-22 ขึ้นมา

โปรดสังเกตว่า คุณจำเป็นต้องโหลดไฟล์ด้วยคำประกาศ `mod` เพียง_ครั้งเดียว_เท่านั้นในต้นไม้มอดูลของคุณ และเมื่อคอมไพเลอร์รับรู้แล้วว่าไฟล์ดังกล่าวเป็นส่วนหนึ่งของโปรเจกต์ (และรู้ว่าโค้ดนั้นอยู่ตรงตำแหน่งใดในต้นไม้มอดูลจากจุดที่คุณเขียนสเตตเมนต์ `mod`) ไฟล์อื่นๆ ในโปรเจกต์ก็ควรจะอ้างอิงถึงโค้ดในไฟล์ที่โหลดมาแล้วนั้น ผ่านทางพาธ (path) ที่ชี้ไปยังตำแหน่งที่มันถูกประกาศเอาไว้ ดังที่เราได้เรียนรู้กันไปในหัวข้อ [“พาธสำหรับอ้างถึงรายการในแผนผังมอดูล”][paths]<!-- ignore --> หรือพูดอีกอย่างก็คือ คำว่า `mod` นั้น _ไม่ใช่_ คำสั่ง “include” เหมือนอย่างที่คุณอาจคุ้นเคยในภาษาโปรแกรมอื่นๆ

ถัดไป เราจะแยกมอดูล `hosting` ออกไปเป็นไฟล์ของตัวเองอีกทอดหนึ่ง ซึ่งขั้นตอนนี้จะแตกต่างออกไปเล็กน้อย เพราะมอดูล `hosting` เป็นมอดูลลูกของ `front_of_house` ไม่ใช่มอดูลลูกของมอดูลราก เราจึงต้องนำไฟล์ของ `hosting` ไปวางไว้ในไดเรกทอรีใหม่ที่ตั้งชื่อตามมอดูลบรรพบุรุษของมันในต้นไม้มอดูล ซึ่งในกรณีนี้ก็คือไดเรกทอรี _src/front_of_house_

> ### พาธไฟล์ทางเลือก
>
> จนถึงตอนนี้ เราได้อธิบายรูปแบบพาธไฟล์ที่เป็นสำนวนนิยมที่สุดซึ่งคอมไพเลอร์ Rust ใช้ แต่จริงๆ แล้ว Rust ยังคงรองรับรูปแบบพาธไฟล์แบบเก่าอยู่อีกด้วย สำหรับมอดูลชื่อ `front_of_house` ที่ประกาศไว้ที่รากของเครต คอมไพเลอร์จะมองหาโค้ดของมอดูลจากตำแหน่งเหล่านี้:
>
> - _src/front_of_house.rs_ (รูปแบบสำนวนนิยมที่เราได้อธิบายไป)
> - _src/front_of_house/mod.rs_ (รูปแบบเก่า ซึ่งยังคงรองรับอยู่)
>
> และสำหรับมอดูลชื่อ `hosting` ซึ่งเป็นมอดูลย่อยของ `front_of_house` คอมไพเลอร์จะมองหาโค้ดของมอดูลจากตำแหน่งเหล่านี้:
>
> - _src/front_of_house/hosting.rs_ (รูปแบบสำนวนนิยมที่เราได้อธิบายไป)
> - _src/front_of_house/hosting/mod.rs_ (รูปแบบเก่า ซึ่งยังคงรองรับอยู่)
>
> หากคุณใช้ทั้งสองรูปแบบซ้ำซ้อนกันในมอดูลเดียวกัน คอมไพเลอร์จะแจ้งข้อผิดพลาดขึ้นมาทันที แม้ว่าการใช้รูปแบบผสมผสานกันในแต่ละมอดูลภายในโปรเจกต์เดียวกันจะสามารถทำได้ แต่ก็อาจสร้างความสับสนให้กับผู้ที่เข้ามาอ่านโค้ดในโปรเจกต์ของคุณ
>
> ข้อเสียสำคัญของรูปแบบที่ใช้ไฟล์ชื่อ _mod.rs_ คือ โปรเจกต์ของคุณอาจเต็มไปด้วยไฟล์ที่ชื่อ _mod.rs_ ซ้ำๆ กันหลายไฟล์ ซึ่งสร้างความสับสนได้ง่ายมากเวลาที่คุณเปิดไฟล์เหล่านั้นขึ้นมาพร้อมๆ กันในโปรแกรมแก้ไขโค้ด

ในตอนนี้ เราได้ย้ายโค้ดของแต่ละมอดูลออกไปยังไฟล์แยกต่างหากเรียบร้อยแล้ว โดยที่โครงสร้างต้นไม้มอดูลยังคงเหมือนเดิมทุกประการ ทำให้การเรียกฟังก์ชันต่างๆ ใน `eat_at_restaurant` ยังคงทำงานได้ตามปกติโดยไม่ต้องแก้ไขโค้ดเลยแม้แต่น้อย แม้ว่านิยามของฟังก์ชันจะกระจายไปอยู่ในคนละไฟล์แล้วก็ตาม เทคนิคนี้จะช่วยให้คุณสามารถแยกมอดูลออกเป็นไฟล์ใหม่ๆ ได้อย่างคล่องตัวเมื่อขนาดของมอดูลเติบโตขึ้น

โปรดสังเกตด้วยว่า สเตตเมนต์ `pub use crate::front_of_house::hosting;` ใน _src/lib.rs_ ก็ไม่ได้มีการเปลี่ยนแปลงใดๆ เช่นกัน และคำสั่ง `use` ก็ไม่มีผลใดๆ ต่อการที่ไฟล์จะถูกนำไปคอมไพล์เป็นส่วนหนึ่งของเครตหรือไม่ เพราะคำว่า `mod` ต่างหากที่เป็นตัวประกาศสร้างมอดูล และ Rust จะคอยค้นหาโค้ดสำหรับมอดูลนั้นจากไฟล์ที่มีชื่อตรงกับชื่อของมอดูลเสมอ

## สรุป

Rust ช่วยให้คุณสามารถแยกแพ็กเกจ (package) ออกเป็นหลายๆ เครต (crates) และแยกเครตออกเป็นมอดูลต่างๆ ได้ เพื่อให้คุณสามารถอ้างอิงถึงไอเทมที่นิยามไว้ในมอดูลหนึ่งจากอีกมอดูลหนึ่งได้อย่างเป็นระบบ โดยทำได้ผ่านการระบุพาธแบบสัมบูรณ์หรือแบบสัมพัทธ์ และพาธเหล่านี้สามารถนำเข้ามาไว้ในสโคปได้ด้วยสเตตเมนต์ `use` เพื่อช่วยลดทอนความยาวของพาธเมื่อต้องเรียกใช้งานซ้ำๆ ในสโคปนั้น โค้ดทั้งหมดในมอดูลจะมีสถานะเป็นแบบส่วนตัว (private) โดยปริยาย แต่คุณก็สามารถเปิดเผยนิยามต่างๆ ให้เป็นสาธารณะ (public) ได้อย่างยืดหยุ่นด้วยการเติมคีย์เวิร์ด `pub`

ในบทถัดไป เราจะมาเรียนรู้เกี่ยวกับโครงสร้างข้อมูลแบบคอลเลกชัน (collection data structures) ในไลบรารีมาตรฐาน ซึ่งคุณสามารถนำมาปรับใช้ร่วมกับโค้ดที่ได้รับการจัดระเบียบอย่างประณีตของคุณได้ทันที
