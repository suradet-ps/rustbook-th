## วิธีเขียนเทสต์

_เทสต์_ (test) คือฟังก์ชัน Rust ที่ตรวจสอบว่าโค้ดที่ไม่ใช่เทสต์ทำงานในลักษณะที่คาดหวังไว้หรือไม่ บอดี้ของฟังก์ชันเทสต์มักทำสามสิ่งนี้:

- เตรียมข้อมูลหรือสถานะที่จำเป็น
- รันโค้ดที่คุณต้องการทดสอบ
- ยืนยันว่าผลลัพธ์เป็นอย่างที่คุณคาดหวัง

มาดูฟีเจอร์ที่ Rust มีให้โดยเฉพาะสำหรับการเขียนเทสต์ที่ทำสิ่งเหล่านี้ ซึ่งรวมถึงแอตทริบิวต์ `test` มาโครสองสามตัว และแอตทริบิวต์ `should_panic`

### โครงสร้างของฟังก์ชันเทสต์

ในรูปแบบที่เรียบง่ายที่สุด เทสต์ใน Rust คือฟังก์ชันที่ถูกกำกับด้วยแอตทริบิวต์ `test` แอตทริบิวต์คือเมทาดาทาเกี่ยวกับโค้ด Rust ส่วนต่างๆ ตัวอย่างหนึ่งคือแอตทริบิวต์ `derive` ที่เราใช้กับ struct ในบทที่ 5 ในการเปลี่ยนฟังก์ชันให้เป็นฟังก์ชันเทสต์ ให้เพิ่ม `#[test]` ไว้บนบรรทัดก่อนหน้า `fn` เมื่อคุณรันเทสต์ด้วยคำสั่ง `cargo test` Rust จะบิลด์ไบนารีตัวรันทดสอบ (test runner) ที่รันฟังก์ชันที่ถูกกำกับและรายงานว่าฟังก์ชันเทสต์แต่ละตัวผ่านหรือล้มเหลว

เมื่อใดก็ตามที่เราสร้างโปรเจกต์ไลบรารีใหม่ด้วย Cargo มอดูลเทสต์ที่บรรจุฟังก์ชันเทสต์อยู่ข้างในจะถูกสร้างขึ้นให้เราอัตโนมัติ มอดูลนี้ให้เทมเพลตสำหรับการเขียนเทสต์ของคุณ เพื่อที่คุณจะไม่ต้องค้นหาโครงสร้างและวากยสัมพันธ์ที่แน่นอนทุกครั้งที่เริ่มโปรเจกต์ใหม่ คุณสามารถเพิ่มฟังก์ชันเทสต์และมอดูลเทสต์เพิ่มเติมได้มากเท่าที่คุณต้องการ!

เราจะสำรวจแง่มุมบางอย่างของการทำงานของเทสต์ด้วยการทดลองกับเทมเพลตเทสต์ก่อนที่เราจะทดสอบโค้ดจริงๆ จากนั้นเราจะเขียนเทสต์ในโลกจริงที่เรียกโค้ดที่เราเขียนไว้ และยืนยันว่าพฤติกรรมของมันถูกต้อง

สำหรับตอนนี้ มาโฟกัสที่ฟังก์ชัน `it_works` เพียงอย่างเดียว โปรดสังเกตแอนโนเทชัน `#[test]` แอตทริบิวต์นี้บ่งชี้ว่านี่คือฟังก์ชันเทสต์ ตัวรันทดสอบจึงรู้ว่าจะปฏิบัติต่อฟังก์ชันนี้เป็นเทสต์ เราอาจมีฟังก์ชันที่ไม่ใช่เทสต์ในมอดูล `tests` เพื่อช่วยตั้งค่าสถานการณ์ทั่วไปหรือทำงานทั่วไป เราจึงต้องระบุเสมอว่าฟังก์ชันใดเป็นเทสต์

บอดี้ของฟังก์ชันตัวอย่างใช้มาโคร `assert_eq!` เพื่อยืนยันว่า `result` ซึ่งบรรจุผลลัพธ์ของการเรียก `add` ด้วย 2 และ 2 นั้นเท่ากับ 4 แอสเซอร์ชัน (assertion) นี้เป็นตัวอย่างของรูปแบบสำหรับเทสต์ทั่วไป มารันมันเพื่อดูว่าเทสต์นี้ผ่าน

Cargo คอมไพล์และรันเทสต์ เราเห็นบรรทัด `running 1 test` บรรทัดถัดไปแสดงชื่อของฟังก์ชันเทสต์ที่ถูกสร้างขึ้น ชื่อ `tests::it_works` และผลลัพธ์ของการรันเทสต์นั้นคือ `ok` สรุปภาพรวม `test result: ok.` หมายความว่าเทสต์ทั้งหมดผ่าน และส่วนที่อ่านว่า `1 passed; 0 failed` นั้นสรุปจำนวนเทสต์ที่ผ่านหรือล้มเหลว

สามารถทำเครื่องหมายเทสต์ว่าถูกข้ามได้ เพื่อให้มันไม่ถูกรันในการรันครั้งใดครั้งหนึ่ง เราจะครอบคลุมเรื่องนี้ในหัวข้อ[“การข้ามเทสต์เว้นแต่จะถูกร้องขออย่างเจาะจง”][ignoring]<!-- ignore --> ช่วงหลังของบทนี้ เนื่องจากเรายังไม่ได้ทำเช่นนั้นในที่นี้ สรุปจึงแสดง `0 ignored` เรายังสามารถส่งอาร์กิวเมนต์ให้คำสั่ง `cargo test` เพื่อรันเฉพาะเทสต์ที่มีชื่อตรงกับสตริงหนึ่งๆ ได้ สิ่งนี้เรียกว่า_การกรอง_ (filtering) และเราจะครอบคลุมในหัวข้อ[“การรันเทสต์บางส่วนตามชื่อ”][subset]<!-- ignore --> ในที่นี้ เราไม่ได้กรองเทสต์ที่กำลังรัน ดังนั้นตอนท้ายของสรุปจึงแสดง `0 filtered out`

สถิติ `0 measured` ใช้สำหรับเทสต์แบบเบนช์มาร์ก (benchmark test) ที่วัดประสิทธิภาพ ณ ขณะที่เขียนนี้ เทสต์แบบเบนช์มาร์กมีให้ใช้เฉพาะใน nightly Rust เท่านั้น ดู[เอกสารเกี่ยวกับเทสต์แบบเบนช์มาร์ก][bench] เพื่อเรียนรู้เพิ่มเติม

ส่วนถัดไปของเอาต์พุตเทสต์ที่เริ่มต้นที่ `Doc-tests adder` เป็นผลลัพธ์ของด็อกเทสต์ (documentation test) ใดๆ เรายังไม่มีด็อกเทสต์เลย แต่ Rust สามารถคอมไพล์ตัวอย่างโค้ดใดๆ ที่ปรากฏในเอกสาร API ของเราได้ ฟีเจอร์นี้ช่วยให้เอกสารและโค้ดของคุณสอดคล้องกันอยู่เสมอ! เราจะพูดคุยถึงวิธีเขียนด็อกเทสต์ในหัวข้อ[“คอมเมนต์เอกสารในฐานะเทสต์”][doc-comments]<!-- ignore --> ของบทที่ 14 สำหรับตอนนี้ เราจะข้ามเอาต์พุต `Doc-tests` ไป

### การตรวจสอบผลลัพธ์ด้วย `assert!`

มาโคร `assert!` ที่ไลบรารีมาตรฐานมีให้มีประโยชน์เมื่อคุณต้องการมั่นใจว่าเงื่อนไขบางอย่างในเทสต์ประเมินค่าเป็น `true` เราส่งอาร์กิวเมนต์ที่ประเมินค่าเป็นบูลีนให้มาโคร `assert!` หากค่าเป็น `true` จะไม่มีอะไรเกิดขึ้นและเทสต์ผ่าน หากค่าเป็น `false` มาโคร `assert!` จะเรียก `panic!` เพื่อทำให้เทสต์ล้มเหลว การใช้มาโคร `assert!` ช่วยให้เราตรวจสอบว่าโค้ดของเราทำงานในแบบที่เราตั้งใจ

โปรดสังเกตบรรทัด `use super::*;` ภายในมอดูล `tests` มอดูล `tests` เป็นมอดูลปกติที่ปฏิบัติตามกฎความเป็นส่วนตัวตามปกติซึ่งเราได้ครอบคลุมในบทที่ 7 ในหัวข้อ[“พาธสำหรับอ้างถึงรายการในแผนผังมอดูล”][paths-for-referring-to-an-item-in-the-module-tree]<!-- ignore --> เนื่องจากมอดูล `tests` เป็นมอดูลภายใน เราจึงต้องนำโค้ดที่อยู่ระหว่างการทดสอบในมอดูลภายนอกเข้าสู่สโคปของมอดูลภายใน เราใช้โกลบ (glob) ที่นี่ ดังนั้นอะไรก็ตามที่เรานิยามในมอดูลภายนอกจะใช้ได้กับมอดูล `tests` นี้

### การทดสอบความเท่ากันด้วย `assert_eq!` และ `assert_ne!`

วิธีทั่วไปในการตรวจสอบการทำงานคือการทดสอบความเท่ากันระหว่างผลลัพธ์ของโค้ดที่อยู่ระหว่างการทดสอบกับค่าที่คุณคาดว่าโค้ดจะคืนกลับ คุณทำได้โดยใช้มาโคร `assert!` และส่งเอ็กซ์เพรสชันที่ใช้ตัวดำเนินการ `==` ให้มัน อย่างไรก็ตาม นี่เป็นการทดสอบที่พบได้ทั่วไปมากจนไลบรารีมาตรฐานมีมาโครคู่หนึ่ง—`assert_eq!` และ `assert_ne!`—มาให้เพื่อทำการทดสอบนี้ได้สะดวกยิ่งขึ้น มาโครเหล่านี้เปรียบเทียบอาร์กิวเมนต์สองตัวเพื่อตรวจสอบความเท่ากันหรือความไม่เท่ากันตามลำดับ มันยังพิมพ์ค่าทั้งสองออกมาหากแอสเซอร์ชันล้มเหลว ซึ่งทำให้เห็นได้ง่ายขึ้นว่า_ทำไม_เทสต์จึงล้มเหลว ในทางกลับกัน มาโคร `assert!` เพียงบ่งชี้ว่ามันได้ค่า `false` สำหรับเอ็กซ์เพรสชัน `==` โดยไม่พิมพ์ค่าที่นำไปสู่ค่า `false` นั้น

โปรดสังเกตว่าในบางภาษาและบางเฟรมเวิร์กการทดสอบ พารามิเตอร์ของฟังก์ชันแอสเซอร์ชันความเท่ากันถูกเรียกว่า `expected` และ `actual` และลำดับที่เราระบุอาร์กิวเมนต์นั้นสำคัญ อย่างไรก็ตาม ใน Rust พวกมันถูกเรียกว่า `left` และ `right` และลำดับที่เราระบุค่าที่เราคาดหวังกับค่าที่โค้ดสร้างขึ้นนั้นไม่สำคัญ เราสามารถเขียนแอสเซอร์ชันในเทสต์นี้เป็น `assert_eq!(4, result)` ซึ่งจะให้ข้อความความล้มเหลวเดียวกันที่แสดง `` assertion `left == right` failed ``

มาโคร `assert_ne!` จะผ่านหากค่าสองค่าที่เราส่งให้มันไม่เท่ากัน และจะล้มเหลวหากค่าทั้งสองเท่ากัน มาโครนี้มีประโยชน์ที่สุดในกรณีที่เราไม่แน่ใจว่าค่า_จะ_เป็นอะไร แต่เรารู้ว่าค่านั้น_ไม่ควร_เป็นอะไรอย่างแน่นอน ตัวอย่างเช่น หากเรากำลังทดสอบฟังก์ชันที่รับประกันได้ว่ามันจะเปลี่ยนอินพุตของมันในบางลักษณะ แต่วิธีที่อินพุตถูกเปลี่ยนนั้นขึ้นอยู่กับวันในสัปดาห์ที่เรารันเทสต์ สิ่งที่ดีที่สุดที่ควรยืนยันก็อาจเป็นการที่เอาต์พุตของฟังก์ชันไม่เท่ากับอินพุต

ภายใต้พื้นผิว มาโคร `assert_eq!` และ `assert_ne!` ใช้ตัวดำเนินการ `==` และ `!=` ตามลำดับ เมื่อแอสเซอร์ชันล้มเหลว มาโครเหล่านี้จะพิมพ์อาร์กิวเมนต์ของมันโดยใช้การจัดรูปแบบดีบัก (debug formatting) ซึ่งหมายความว่าค่าที่ถูกเปรียบเทียบต้องอิมพลีเมนต์เทรต `PartialEq` และ `Debug` ชนิดพื้นฐานทั้งหมดและชนิดส่วนใหญ่ในไลบรารีมาตรฐานอิมพลีเมนต์เทรตเหล่านี้ สำหรับ struct และ enum ที่คุณนิยามเอง คุณจะต้องอิมพลีเมนต์ `PartialEq` เพื่อยืนยันความเท่ากันของชนิดเหล่านั้น คุณยังต้องอิมพลีเมนต์ `Debug` เพื่อพิมพ์ค่าเมื่อแอสเซอร์ชันล้มเหลว เนื่องจากเทรตทั้งสองเป็นเทรตที่ derive ได้ ดังที่กล่าวถึงในลิสติ้ง 5-12 ในบทที่ 5 โดยปกติแล้วก็เพียงเพิ่มแอนโนเทชัน `#[derive(PartialEq, Debug)]` ให้กับนิยาม struct หรือ enum ของคุณเท่านั้น ดูภาคผนวก C [“เทรตที่ derive ได้”][derivable-traits]<!-- ignore --> สำหรับรายละเอียดเพิ่มเติมเกี่ยวกับเทรตเหล่านี้และเทรตอื่นๆ ที่ derive ได้

เทสต์ที่ใช้ `should_panic` อาจไม่แม่นยำ เทสต์ `should_panic` จะผ่านแม้ว่าเทสต์จะแพนิกด้วยเหตุผลที่ต่างจากที่เราคาดหวังไว้ก็ตาม เพื่อให้เทสต์ `should_panic` แม่นยำยิ่งขึ้น เราสามารถเพิ่มพารามิเตอร์ `expected` แบบเสริมให้กับแอตทริบิวต์ `should_panic` ได้ ตัวรันทดสอบ (test harness) จะทำให้แน่ใจว่าข้อความความล้มเหลวบรรจุข้อความที่ให้ไว้ ตัวอย่างเช่น พิจารณาโค้ดที่แก้ไขแล้วสำหรับ `Guess` ในลิสติ้ง 11-9 ซึ่งฟังก์ชัน `new` แพนิกด้วยข้อความที่ต่างกันขึ้นอยู่กับว่าค่าเล็กเกินไปหรือใหญ่เกินไป

### การใช้ `Result<T, E>` ในเทสต์

เทสต์ทั้งหมดของเราจนถึงตอนนี้จะแพนิกเมื่อมันล้มเหลว เรายังสามารถเขียนเทสต์ที่ใช้ `Result<T, E>` ได้ด้วย! นี่คือเทสต์จากลิสติ้ง 11-1 ที่ถูกเขียนใหม่ให้ใช้ `Result<T, E>` และคืนค่า `Err` แทนการแพนิก:

```rust,noplayground
{{#rustdoc_include ../listings/ch11-writing-automated-tests/no-listing-10-result-in-tests/src/lib.rs:here}}
```

ฟังก์ชัน `it_works` ตอนนี้มีชนิดค่าที่คืนกลับเป็น `Result<(), String>` ในบอดี้ของฟังก์ชัน แทนที่จะเรียกมาโคร `assert_eq!` เราคืนค่า `Ok(())` เมื่อเทสต์ผ่าน และคืนค่า `Err` ที่บรรจุ `String` อยู่ข้างในเมื่อเทสต์ล้มเหลว

การเขียนเทสต์ให้คืนค่า `Result<T, E>` ทำให้คุณใช้ตัวดำเนินการเครื่องหมายคำถามในบอดี้ของเทสต์ได้ ซึ่งเป็นวิธีที่สะดวกในการเขียนเทสต์ที่ควรล้มเหลวหากการดำเนินการใดๆ ภายในคืนค่าวาเรียนต์ `Err`

คุณไม่สามารถใช้แอนโนเทชัน `#[should_panic]` กับเทสต์ที่ใช้ `Result<T, E>` ได้ หากต้องการยืนยันว่าการดำเนินการหนึ่งคืนค่าวาเรียนต์ `Err` _อย่า_ ใช้ตัวดำเนินการเครื่องหมายคำถามกับค่า `Result<T, E>` แต่ให้ใช้ `assert!(value.is_err())` แทน

ตอนนี้คุณรู้วิธีเขียนเทสต์หลายวิธีแล้ว มาดูว่าเกิดอะไรขึ้นเมื่อเรารันเทสต์ของเรา และสำรวจตัวเลือกต่างๆ ที่เราใช้กับ `cargo test` ได้
