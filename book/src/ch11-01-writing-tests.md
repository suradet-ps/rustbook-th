## วิธีเขียนเทสต์

_เทสต์_ (test หรือการทดสอบ) คือฟังก์ชันใน Rust ที่ทำหน้าที่ตรวจสอบว่าโค้ดส่วนอื่นๆ ที่ไม่ใช่เทสต์ทำงานได้ถูกต้องตรงตามความคาดหวังหรือไม่ โดยทั่วไปแล้ว เนื้อหาภายในฟังก์ชันเทสต์มักจะดำเนินการตาม 3 ขั้นตอนนี้:

- ตระเตรียมข้อมูลหรือสถานะ (state) ที่จำเป็น
- สั่งทำงานโค้ดส่วนที่คุณต้องการทดสอบ
- ยืนยัน (assert) ว่าผลลัพธ์ที่ได้ตรงตามสิ่งที่คุณคาดหวังไว้

มาดูฟีเจอร์ต่างๆ ที่ Rust มีให้สำหรับการเขียนเทสต์โดยเฉพาะ ซึ่งรวมถึงแอตทริบิวต์ `test` มาโครสำหรับการตรวจสอบค่า และแอตทริบิวต์ `should_panic`

### โครงสร้างของฟังก์ชันเทสต์

ในรูปแบบที่เรียบง่ายที่สุด เทสต์ใน Rust คือฟังก์ชันที่กำกับไว้ด้วยแอตทริบิวต์ (attribute) `test` โดยแอตทริบิวต์คือข้อมูลเมทาดาทาที่ใช้อธิบายส่วนต่างๆ ของโค้ด Rust ตัวอย่างเช่น แอตทริบิวต์ `derive` ที่เราเคยใช้กับ struct ในบทที่ 5 การจะเปลี่ยนฟังก์ชันทั่วไปให้กลายเป็นฟังก์ชันเทสต์ ทำได้โดยเพิ่ม `#[test]` ไว้บนบรรทัดก่อนหน้า `fn` เมื่อคุณสั่งรันเทสต์ด้วยคำสั่ง `cargo test` Rust จะคอมไพล์ไบนารีสำหรับตัวรันทดสอบ (test runner binary) ขึ้นมา เพื่อรันฟังก์ชันทั้งหมดที่มีแอตทริบิวต์นี้กำกับอยู่ พร้อมทั้งรายงานผลลัพธ์ว่าฟังก์ชันเทสต์แต่ละตัวนั้นผ่าน (pass) หรือล้มเหลว (fail)

ทุกครั้งที่เราสร้างโปรเจกต์ไลบรารีใหม่ขึ้นมาด้วย Cargo ระบบจะสร้างมอดูลเทสต์พร้อมฟังก์ชันเทสต์ตัวอย่างมาให้เราโดยอัตโนมัติ มอดูลนี้เปรียบเสมือนแม่แบบ (template) ในการเขียนเทสต์ของคุณ ช่วยให้คุณไม่ต้องคอยเปิดหาโครงสร้างและวากยสัมพันธ์ที่ถูกต้องทุกครั้งที่เริ่มโปรเจกต์ใหม่ และคุณสามารถเพิ่มฟังก์ชันเทสต์รวมถึงมอดูลเทสต์เพิ่มเติมได้มากเท่าที่ต้องการ!

เราจะมาสำรวจแง่มุมต่างๆ เกี่ยวกับการทำงานของเทสต์ด้วยการทดลองปรับแต่งเทมเพลตเทสต์นี้ดูก่อน จากนั้นเราจะเขียนชุดทดสอบสำหรับการใช้งานจริงที่เรียกใช้โค้ดที่เราเขียนขึ้น เพื่อยืนยันว่าโค้ดนั้นทำงานได้อย่างถูกต้อง


สำหรับตอนนี้ ขอให้เราโฟกัสเฉพาะฟังก์ชัน `it_works` เพียงอย่างเดียวก่อน โปรดสังเกตการกำกับด้วย `#[test]` แอตทริบิวต์นี้เป็นตัวบ่งบอกว่านี่คือฟังก์ชันเทสต์ ตัวรันทดสอบจึงทราบว่าจะต้องปฏิบัติต่อฟังก์ชันนี้ในฐานะการทดสอบ เราอาจมีฟังก์ชันที่ไม่ใช่เทสต์อยู่ภายในมอดูล `tests` ด้วย เพื่อช่วยเตรียมสถานการณ์จำลองหรือดำเนินการทั่วไป ดังนั้นเราจึงจำเป็นต้องระบุให้ชัดเจนเสมอว่าฟังก์ชันใดบ้างที่เป็นเทสต์

เนื้อหาภายในฟังก์ชันตัวอย่างจะใช้มาโคร `assert_eq!` เพื่อยืนยันว่า `result` ซึ่งเก็บผลลัพธ์จากการเรียก `add` ด้วยค่า 2 และ 2 มีค่าเท่ากับ 4 การตรวจสอบแบบยืนยันค่า (assertion) นี้เป็นตัวอย่างรูปแบบของเทสต์ทั่วไป มาลองรันคำสั่งเพื่อดูว่าเทสต์นี้ผ่านหรือไม่

Cargo ได้คอมไพล์และรันเทสต์เรียบร้อยแล้ว เราจะเห็นบรรทัด `running 1 test` บรรทัดถัดมาแสดงชื่อของฟังก์ชันเทสต์ที่ถูกสร้างขึ้นคือ `tests::it_works` และผลลัพธ์ของการรันเทสต์นั้นคือ `ok` ส่วนข้อความสรุปภาพรวม `test result: ok.` หมายความว่าเทสต์ทั้งหมดผ่าน และข้อความ `1 passed; 0 failed` เป็นการสรุปยอดรวมของจำนวนเทสต์ที่ผ่านหรือล้มเหลว

เราสามารถทำเครื่องหมายให้ข้าม (ignore) เทสต์บางตัวได้ เพื่อไม่ให้ถูกรันในแต่ละรอบ ซึ่งเราจะอธิบายเรื่องนี้ในหัวข้อ[“การข้ามเทสต์เว้นแต่จะถูกร้องขออย่างเจาะจง”][ignoring]<!-- ignore --> ในช่วงถัดไปของบทนี้ และเนื่องจากตอนนี้เรายังไม่ได้ข้ามเทสต์ใดๆ ข้อความสรุปจึงแสดง `0 ignored` นอกจากนี้ เรายังสามารถส่งอาร์กิวเมนต์ให้กับคำสั่ง `cargo test` เพื่อเลือกสั่งรันเฉพาะเทสต์ที่มีชื่อตรงกับข้อความที่ระบุได้ ซึ่งสิ่งนี้เรียกว่า_การกรอง_ (filtering) โดยจะกล่าวถึงในหัวข้อ[“การรันเทสต์บางส่วนตามชื่อ”][subset]<!-- ignore --> ในที่นี้เราไม่ได้กรองเทสต์ใดๆ ออก ท้ายบรรทัดสรุปจึงแสดง `0 filtered out`

สถิติ `0 measured` มีไว้สำหรับเทสต์วัดประสิทธิภาพ (benchmark tests) ซึ่ง ณ ตอนที่เขียนนี้ เบนช์มาร์กเทสต์มีให้ใช้งานเฉพาะใน Rust เวอร์ชัน nightly เท่านั้น สามารถดูรายละเอียดเพิ่มเติมได้ที่[เอกสารเกี่ยวกับเทสต์แบบเบนช์มาร์ก][bench]

ส่วนถัดไปของเอาต์พุตที่ขึ้นต้นด้วย `Doc-tests adder` เป็นผลลัพธ์ของด็อกเทสต์ (documentation tests) แม้ว่าตอนนี้เราจะยังไม่ได้เขียนด็อกเทสต์ไว้ แต่ Rust มีความสามารถในการนำตัวอย่างโค้ดที่ปรากฏอยู่ในเอกสารประกอบ API มาคอมไพล์และทดสอบได้ ฟีเจอร์นี้ช่วยให้เอกสารและโค้ดของคุณตรงกันอยู่เสมอ! เราจะพูดถึงวิธีการเขียนด็อกเทสต์ในหัวข้อ[“คอมเมนต์เอกสารประกอบในฐานะเทสต์”][doc-comments]<!-- ignore --> ของบทที่ 14 แต่ในตอนนี้เราจะข้ามผลลัพธ์ในส่วน `Doc-tests` ไปก่อน

### การตรวจสอบผลลัพธ์ด้วย `assert!`

มาโคร `assert!` จากไลบรารีมาตรฐาน มีประโยชน์มากเมื่อคุณต้องการตรวจสอบให้มั่นใจว่าเงื่อนไขบางอย่างในการทดสอบให้ผลลัพธ์เป็น `true` เราจะส่งอาร์กิวเมนต์ที่ประเมินค่าออกมาเป็นค่าบูลีนให้กับมาโคร `assert!` หากค่านั้นเป็น `true` จะไม่มีอะไรเกิดขึ้นและเทสต์จะผ่าน แต่หากค่านั้นเป็น `false` มาโคร `assert!` จะเรียกใช้คำสั่ง `panic!` ส่งผลให้เทสต์นั้นล้มเหลวทันที การใช้มาโคร `assert!` จึงช่วยให้เราตรวจสอบยืนยันได้อย่างมั่นใจว่าโค้ดกำลังทำงานได้ตรงตามที่เราตั้งใจไว้

### การทดสอบความเท่ากันด้วย `assert_eq!` และ `assert_ne!`

วิธีทั่วไปในการตรวจสอบการทำงานของโค้ดคือ การทดสอบความเท่ากันระหว่างผลลัพธ์ที่ได้จากการทำงานจริงกับค่าที่เราคาดหวังไว้ คุณสามารถทำสิ่งนี้ได้โดยใช้มาโคร `assert!` แล้วส่งเอ็กซ์เพรสชันที่ใช้ตัวดำเนินการเปรียบเทียบ `==` เข้าไป อย่างไรก็ตาม รูปแบบการทดสอบเช่นนี้พบได้บ่อยมากจนไลบรารีมาตรฐานได้จัดเตรียมมาโครคู่หนึ่งมาให้โดยเฉพาะ นั่นคือ `assert_eq!` และ `assert_ne!` เพื่อให้การทดสอบสะดวกสบายยิ่งขึ้น มาโครทั้งสองจะเปรียบเทียบอาร์กิวเมนต์ 2 ตัวเพื่อดูว่าเท่ากันหรือไม่เท่ากันตามลำดับ และที่สำคัญคือ หากการยืนยันค่านั้นล้มเหลว มาโครเหล่านี้จะพิมพ์ค่าของอาร์กิวเมนต์ทั้งสองตัวออกมาให้เห็นด้วย ซึ่งช่วยให้เราทราบได้ทันทีว่า_เหตุใด_เทสต์จึงล้มเหลว ในทางตรงกันข้าม มาโคร `assert!` จะบอกเพียงแค่ว่าเอ็กซ์เพรสชัน `==` ได้ผลลัพธ์เป็น `false` โดยไม่แสดงให้เห็นค่าที่นำไปสู่ผลลัพธ์ `false` นั้นเลย

โปรดสังเกตว่า ในบางภาษาและบางเฟรมเวิร์กการทดสอบ พารามิเตอร์สำหรับฟังก์ชันตรวจสอบความเท่ากันมักจะใช้ชื่อว่า `expected` (ค่าที่คาดหวัง) และ `actual` (ค่าที่ได้จริง) ซึ่งลำดับการส่งอาร์กิวเมนต์จะมีผลต่อความหมายอย่างมาก แต่ใน Rust พารามิเตอร์เหล่านี้จะเรียกว่า `left` และ `right` ดังนั้นลำดับการส่งระหว่างค่าที่เราคาดหวังกับค่าที่โค้ดสร้างขึ้นจึงไม่มีความแตกต่างกัน เราสามารถเขียนแอสเซอร์ชันในเทสต์นี้เป็น `assert_eq!(4, result)` ก็ได้ ซึ่งจะให้ข้อความแสดงความล้มเหลวแบบเดียวกันว่า `` assertion `left == right` failed ``

สำหรับมาโคร `assert_ne!` จะผ่านเมื่อค่าสองค่าที่ส่งเข้าไปไม่เท่ากัน และจะล้มเหลวหากค่าทั้งสองเท่ากัน มาโครนี้มีประโยชน์อย่างยิ่งในกรณีที่เราไม่อาจทราบแน่ชัดว่าค่าลัพธ์_จะต้อง_เป็นอะไร แต่เรารู้ได้อย่างแน่นอนว่าค่านั้น_ต้องไม่ใช่_อะไร ตัวอย่างเช่น หากเรากำลังทดสอบฟังก์ชันที่รับประกันว่าจะต้องแปลงค่าอินพุตเป็นอย่างอื่นเสมอ แต่วิธีการแปลงขึ้นอยู่กับวันในสัปดาห์ที่เรารันเทสต์ สิ่งที่ดีที่สุดในการยืนยันผลลัพธ์อาจเป็นการตรวจสอบว่าผลลัพธ์ที่ได้ออกมาจะต้องไม่เท่ากับอินพุตเดิม

เบื้องหลังการทำงาน มาโคร `assert_eq!` และ `assert_ne!` จะใช้ตัวดำเนินการ `==` และ `!=` ตามลำดับ และเมื่อแอสเซอร์ชันล้มเหลว มาโครเหล่านี้จะพิมพ์ค่าของอาร์กิวเมนต์ออกมาด้วยรูปแบบการแสดงผลแบบดีบัก (debug formatting) นั่นหมายความว่าค่าที่นำมาเปรียบเทียบกันจะต้องอิมพลีเมนต์เทรต `PartialEq` และ `Debug` เสมอ โดยชนิดข้อมูลพื้นฐานทั้งหมดรวมถึงชนิดข้อมูลส่วนใหญ่ในไลบรารีมาตรฐานต่างก็ได้อิมพลีเมนต์เทรตเหล่านี้ไว้เรียบร้อยแล้ว สำหรับ struct และ enum ที่คุณนิยามขึ้นเอง คุณจำเป็นต้องอิมพลีเมนต์ `PartialEq` เพื่อให้สามารถตรวจสอบความเท่ากันได้ และต้องอิมพลีเมนต์ `Debug` เพื่อให้สามารถพิมพ์ค่าออกมาได้เมื่อการตรวจสอบล้มเหลว เนื่องจากเทรตทั้งสองเป็นเทรตที่สามารถทำ derive ได้ (derivable traits) ดังที่กล่าวไว้ในลิสติ้ง 5-12 ของบทที่ 5 โดยทั่วไปจึงทำได้ง่ายๆ เพียงเพิ่มแอนโนเทชัน `#[derive(PartialEq, Debug)]` กำกับไว้ที่นิยาม struct หรือ enum ของคุณเท่านั้น ดูภาคผนวก C [“เทรตที่ derive ได้”][derivable-traits]<!-- ignore --> สำหรับรายละเอียดเพิ่มเติมเกี่ยวกับเทรตเหล่านี้และเทรตอื่นๆ ที่ derive ได้

### การตรวจสอบการแพนิกด้วย `should_panic`

นอกเหนือจากการตรวจสอบค่าที่ส่งคืนแล้ว การตรวจสอบว่าโค้ดของเราจัดการกับเงื่อนไขข้อผิดพลาดได้อย่างถูกต้องตามที่คาดหวังหรือไม่ก็มีความสำคัญไม่แพ้กัน ตัวอย่างเช่น ชนิดข้อมูล `Guess` ที่เราสร้างขึ้นในบทที่ 9 ลิสติ้ง 9-13 โค้ดส่วนอื่นๆ ที่เรียกใช้ `Guess` จะพึ่งพาการรับประกันว่าอินสแตนซ์ของ `Guess` จะเก็บเฉพาะค่าที่อยู่ระหว่าง 1 ถึง 100 เท่านั้น เราจึงสามารถเขียนเทสต์เพื่อตรวจสอบให้มั่นใจได้ว่าความพยายามสร้างอินสแตนซ์ `Guess` ด้วยค่าที่อยู่นอกช่วงดังกล่าวจะต้องเกิดการแพนิกขึ้น

เราทำเช่นนี้ได้โดยการเพิ่มแอตทริบิวต์ `should_panic` ให้กับฟังก์ชันเทสต์ เทสต์จะถือว่าผ่านหากโค้ดภายในฟังก์ชันเกิดการแพนิก และจะถือว่าล้มเหลวหากโค้ดภายในฟังก์ชันไม่เกิดการแพนิก

### การใช้ `Result<T, E>` ในเทสต์

เทสต์ทั้งหมดที่เราเขียนมาจนถึงตอนนี้จะใช้วิธีการแพนิกเมื่อการทดสอบล้มเหลว แต่เรายังสามารถเขียนเทสต์โดยใช้ชนิดข้อมูล `Result<T, E>` ได้อีกด้วย! นี่คือเทสต์จากลิสติ้ง 11-1 ที่ถูกเขียนขึ้นใหม่ให้ใช้ `Result<T, E>` และส่งคืนค่า `Err` แทนที่จะเป็นการแพนิก:

```rust,noplayground
{{#rustdoc_include ../listings/ch11-writing-automated-tests/no-listing-10-result-in-tests/src/lib.rs:here}}
```

ฟังก์ชัน `it_works` ในตอนนี้มีชนิดข้อมูลที่ส่งคืนเป็น `Result<(), String>` โดยภายในเนื้อหาของฟังก์ชัน แทนที่เราจะเรียกใช้มาโคร `assert_eq!` เราจะส่งคืน `Ok(())` เมื่อเทสต์ผ่าน และส่งคืน `Err` ที่บรรจุข้อความ `String` ไว้ข้างในเมื่อเทสต์ล้มเหลว

การเขียนเทสต์ให้ส่งคืน `Result<T, E>` ช่วยให้คุณสามารถใช้งานตัวดำเนินการเครื่องหมายคำถาม (`?`) ภายในเนื้อหาของเทสต์ได้ ซึ่งเป็นวิธีที่สะดวกมากในการเขียนเทสต์ที่ควรล้มเหลวทันทีหากมีการดำเนินการใดๆ ภายในส่งคืนวาเรียนต์ `Err` ออกมา

คุณไม่สามารถใช้แอนโนเทชัน `#[should_panic]` กับเทสต์ที่ใช้ `Result<T, E>` ได้ หากต้องการยืนยันว่าการดำเนินการหนึ่งคืนค่าวาเรียนต์ `Err` _อย่า_ ใช้ตัวดำเนินการเครื่องหมายคำถามกับค่า `Result<T, E>` แต่ให้ใช้ `assert!(value.is_err())` แทน

เมื่อคุณได้เรียนรู้วิธีการเขียนเทสต์หลากหลายรูปแบบแล้ว ต่อไปเรามาดูสิ่งที่เกิดขึ้นเมื่อสั่งรันเทสต์ และสำรวจตัวเลือกคำสั่งต่างๆ ที่เราสามารถใช้งานร่วมกับ `cargo test` ได้
