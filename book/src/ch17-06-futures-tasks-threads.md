## ประกอบทุกอย่างเข้าด้วยกัน: ฟิวเจอร์ ทาสก์ และเธรด

อย่างที่เราเห็นใน[บทที่ 16][ch16]<!-- ignore --> เธรด (thread) เป็นแนวทางหนึ่งสำหรับการทำงานพร้อมกัน (concurrency) เราก็ได้เห็นอีกแนวทางหนึ่งในบทนี้: การใช้ async กับฟิวเจอร์ (future) และสตรีม (stream) หากคุณสงสัยว่าเมื่อไหร่ควรเลือกวิธีหนึ่งแทนอีกวิธี คำตอบคือ: แล้วแต่สถานการณ์! และในหลายกรณี ทางเลือกไม่ใช่เธรด_หรือ_ async แต่เป็นเธรด_และ_ async ต่างหาก

ระบบปฏิบัติการหลายแห่งได้จัดเตรียมโมเดลการทำงานพร้อมกันแบบใช้เธรดมานานหลายทศวรรษแล้ว และภาษาโปรแกรมหลายภาษาเองก็รองรับโมเดลเหล่านี้ด้วยเหตุนี้ อย่างไรก็ตาม โมเดลเหล่านี้ก็ใช่ว่าจะไม่มีการแลกเปลี่ยน (trade-off) อยู่ บนระบบปฏิบัติการหลายตัว พวกมันใช้หน่วยความจำค่อนข้างมากต่อเธรดหนึ่งตัว เธรดยังเป็นทางเลือกเฉพาะเมื่อระบบปฏิบัติการและฮาร์ดแวร์ของคุณรองรับมันเท่านั้น ต่างจากคอมพิวเตอร์เดสก์ท็อปและมือถือกระแสหลัก ระบบฝังตัว (embedded) บางระบบไม่มีระบบปฏิบัติการเลย พวกมันจึงไม่มีเธรดด้วยเช่นกัน

โมเดล async ให้ชุดของการแลกเปลี่ยนที่แตกต่าง และท้ายที่สุดก็เสริมซึ่งกันและกัน ในโมเดล async การดำเนินการที่ทำงานพร้อมกันไม่จำเป็นต้องมีเธรดของตัวเอง แทนที่จะเป็นเช่นนั้น พวกมันรันบนทาสก์ (task) ได้ เช่นเดียวกับตอนที่เราใช้ `trpl::spawn_task` เพื่อเริ่มงานจากฟังก์ชันซิงโครนัสในหัวข้อสตรีม ทาสก์นั้นคล้ายกับเธรด แต่แทนที่จะถูกจัดการโดยระบบปฏิบัติการ มันถูกจัดการโดยโค้ดระดับไลบรารี นั่นคือรันไทม์ (runtime)

มีเหตุผลที่ API สำหรับการสร้างเธรดและการสร้างทาสก์นั้นคล้ายกันมาก เธรดทำหน้าที่เป็นขอบเขตสำหรับชุดของการดำเนินการแบบซิงโครนัส การทำงานพร้อมกันเป็นไปได้_ระหว่าง_เธรด ทาสก์ทำหน้าที่เป็นขอบเขตสำหรับชุดของการดำเนินการแบบ_อะซิงโครนัส_ (asynchronous) การทำงานพร้อมกันเป็นไปได้ทั้ง_ระหว่าง_และ_ภายใน_ทาสก์ เพราะทาสก์สามารถสลับระหว่างฟิวเจอร์ในบอดี้ของมันได้ สุดท้าย ฟิวเจอร์เป็นหน่วยการทำงานพร้อมกันที่ละเอียดที่สุดของ Rust และฟิวเจอร์แต่ละตัวอาจแทนแผนภูมิของฟิวเจอร์อื่นๆ ได้ รันไทม์—โดยเฉพาะเอ็กซ์ซีกูเตอร์ (executor) ของมัน—จัดการทาสก์ และทาสก์จัดการฟิวเจอร์ ในแง่นั้น ทาสก์ก็คล้ายกับเธรดน้ำหนักเบาที่ถูกรันไทม์จัดการ พร้อมความสามารถเพิ่มเติมที่ได้มาจากการถูกจัดการโดยรันไทม์แทนที่จะเป็นระบบปฏิบัติการ

นี่ไม่ได้หมายความว่าทาสก์แบบ async ดีกว่าเธรดเสมอไป (หรือในทางกลับกัน) การทำงานพร้อมกันด้วยเธรดนั้นในบางแง่เป็นโมเดลการเขียนโปรแกรมที่เรียบง่ายกว่าการทำงานพร้อมกันด้วย `async` นั่นอาจเป็นจุดแข็งหรือจุดอ่อนก็ได้ เธรดเป็นแบบ “ยิงแล้วลืม” อยู่บ้าง พวกมันไม่มีความเทียบเท่าโดยธรรมชาติของฟิวเจอร์ จึงรันจนเสร็จไปเลยโดยไม่ถูกขัดจังหวะ ยกเว้นโดยระบบปฏิบัติการเอง

และปรากฏว่าเธรดกับทาสก์มักทำงานร่วมกันได้ดีมาก เพราะทาสก์สามารถ (อย่างน้อยในรันไทม์บางตัว) ถูกย้ายไปมาระหว่างเธรดได้ อันที่จริง เบื้องหลังแล้ว รันไทม์ที่เราใช้อยู่ รวมถึงฟังก์ชัน `spawn_blocking` และ `spawn_task` เป็นแบบหลายเธรดโดยค่าเริ่มต้น! รันไทม์หลายตัวใช้แนวทางที่เรียกว่า_การขโมยงาน_ (work stealing) เพื่อย้ายทาสก์ไปมาระหว่างเธรดอย่างโปร่งใส โดยพิจารณาจากว่าขณะนี้เธรดต่างๆ ถูกใช้งานมากแค่ไหน เพื่อปรับปรุงประสิทธิภาพโดยรวมของระบบ แนวทางนั้นต้องใช้ทั้งเธรด_และ_ทาสก์ จึงต้องใช้ฟิวเจอร์ด้วย

เมื่อคิดว่าจะใช้วิธีใดเมื่อไหร่ ลองพิจารณากฎคร่าวๆ เหล่านี้:

- หากงานนั้น_สามารถทำขนานได้มาก_ (นั่นคือ จำกัดด้วย CPU) เช่นการประมวลผลข้อมูลจำนวนหนึ่งที่แต่ละส่วนสามารถประมวลผลแยกกันได้ การใช้เธรดเป็นทางเลือกที่ดีกว่า
- หากงานนั้น_ทำงานพร้อมกันได้มาก_ (นั่นคือ จำกัดด้วย I/O) เช่นการจัดการข้อความจากแหล่งต่างๆ มากมายที่อาจเข้ามาในช่วงเวลาหรืออัตราที่แตกต่างกัน async เป็นทางเลือกที่ดีกว่า

และหากคุณต้องการทั้งการทำงานขนานและการทำงานพร้อมกัน คุณก็ไม่จำเป็นต้องเลือกอย่างใดอย่างหนึ่งระหว่างเธรดกับ async คุณใช้ทั้งสองอย่างร่วมกันได้อย่างอิสระ โดยปล่อยให้แต่ละอย่างรับบทที่มันถนัดที่สุด ตัวอย่างเช่น ลิสติ้ง 17-25 แสดงตัวอย่างที่พบได้ค่อนข้างบ่อยของการผสมแบบนี้ในโค้ด Rust ในโลกจริง

เราเริ่มด้วยการสร้างแชนเนลแบบ async จากนั้นสร้างเธรดที่รับความเป็นเจ้าของ (ownership) ฝั่งผู้ส่งของแชนเนลโดยใช้คำสงวน `move` ภายในเธรด เราส่งตัวเลข 1 ถึง 10 โดยนอนหลับหนึ่งวินาทีระหว่างแต่ละตัว สุดท้าย เรารันฟิวเจอร์ที่สร้างขึ้นด้วยบล็อก async ที่ส่งให้ `trpl::block_on` เช่นเดียวกับที่เราทำตลอดทั้งบท ในฟิวเจอร์นั้น เรา await ข้อความเหล่านั้น เช่นเดียวกับในตัวอย่างการส่งผ่านข้อความอื่นๆ ที่เราเห็นมา

เพื่อกลับไปยังสถานการณ์ที่เราเปิดบทนี้ด้วย ลองจินตนาการว่ากำลังรันชุดทาสก์การเข้ารหัสวิดีโอโดยใช้เธรดเฉพาะ (เพราะการเข้ารหัสวิดีโอจำกัดด้วยการประมวลผล) แต่แจ้งเตือน UI ว่าการดำเนินการเหล่านั้นเสร็จแล้วด้วยแชนเนลแบบ async มีตัวอย่างการผสมแบบนี้ในกรณีการใช้งานจริงนับไม่ถ้วน

## สรุป

นี่ไม่ใช่ครั้งสุดท้ายที่คุณจะได้เห็นการทำงานพร้อมกันในหนังสือเล่มนี้ โปรเจกต์ใน[บทที่ 21][ch21]<!-- ignore --> จะนำแนวคิดเหล่านี้ไปใช้ในสถานการณ์ที่สมจริงยิ่งกว่าตัวอย่างง่ายๆ ที่อภิปรายในที่นี้ และเปรียบเทียบการแก้ปัญหาด้วยการใช้เธรดเทียบกับการใช้ทาสก์และฟิวเจอร์อย่างตรงไปตรงมามากขึ้น

ไม่ว่าคุณจะเลือกแนวทางใดในเหล่านี้ Rust ก็มอบเครื่องมือที่คุณต้องการในการเขียนโค้ดที่ปลอดภัย รวดเร็ว และทำงานพร้อมกันได้ ไม่ว่าจะสำหรับเว็บเซิร์ฟเวอร์ที่มีปริมาณงานสูงหรือระบบปฏิบัติการแบบฝังตัว

ต่อไป เราจะพูดถึงวิธีที่เป็นสำนวนนิยมในการจำลองปัญหาและจัดโครงสร้างวิธีแก้ปัญหาเมื่อโปรแกรม Rust ของคุณใหญ่ขึ้น นอกจากนี้ เราจะอภิปรายว่าสำนวนของ Rust เกี่ยวข้องอย่างไรกับสำนวนที่คุณอาจคุ้นเคยจากการเขียนโปรแกรมเชิงวัตถุ (object-oriented programming)
