## วงจรเรเฟอเรนซ์ทำให้หน่วยความจำรั่วไหลได้

การรับประกันความปลอดภัยของหน่วยความจำของ Rust ทำให้การสร้างหน่วยความจำที่ไม่ถูกทำความสะอาดเลยโดยไม่ตั้งใจ ซึ่งเรียกว่า_การรั่วไหลของหน่วยความจำ_ (memory leak) เป็นเรื่องยากแต่ไม่ใช่เรื่องที่เป็นไปไม่ได้ การป้องกันการรั่วไหลของหน่วยความจำโดยสมบูรณ์ไม่ใช่หนึ่งในการรับประกันของ Rust ซึ่งหมายความว่าการรั่วไหลของหน่วยความจำนั้นปลอดภัยต่อหน่วยความจำใน Rust เราจะเห็นว่า Rust ยอมให้มีการรั่วไหลของหน่วยความจำได้โดยใช้ `Rc<T>` และ `RefCell<T>`: เราสามารถสร้างเรเฟอเรนซ์ที่สมาชิกอ้างถึงกันและกันเป็นวงจรได้ สิ่งนี้ทำให้เกิดการรั่วไหลของหน่วยความจำเพราะจำนวนเรเฟอเรนซ์ของสมาชิกแต่ละตัวในวงจรจะไม่มีวันไปถึง 0 และค่าต่างๆ จะไม่มีวันถูกทิ้ง (drop)

หากคุณยกเลิกคอมเมนต์ `println!` ตัวสุดท้ายแล้วรันโปรแกรม Rust จะพยายามพิมพ์วงจรนี้โดยที่ `a` ชี้ไปยัง `b` และ `b` ชี้ไปยัง `a` ไปเรื่อยๆ จนกระทั่งล้นสแตก (stack)

เมื่อเทียบกับโปรแกรมในโลกจริง ผลที่ตามมาของการสร้างวงจรเรเฟอเรนซ์ในตัวอย่างนี้ไม่ได้ร้ายแรงนัก: ทันทีหลังจากที่เราสร้างวงจรเรเฟอเรนซ์ โปรแกรมก็จบลง อย่างไรก็ตาม หากโปรแกรมที่ซับซ้อนกว่านี้จัดสรรหน่วยความจำจำนวนมากเป็นวงจรและยึดมันไว้เป็นเวลานาน โปรแกรมจะใช้หน่วยความจำมากกว่าที่จำเป็นและอาจทำให้ระบบทำงานหนักเกินไปจนหน่วยความจำที่มีอยู่หมด

การสร้างวงจรเรเฟอเรนซ์ไม่ใช่เรื่องที่ทำได้ง่าย แต่ก็ไม่ใช่เรื่องที่เป็นไปไม่ได้เช่นกัน หากคุณมีค่า `RefCell<T>` ที่บรรจุค่า `Rc<T>` หรือการซ้อนกันของชนิดข้อมูลในลักษณะคล้ายกันซึ่งมีการเปลี่ยนแปลงค่าภายใน (interior mutability) และการนับจำนวนเรเฟอเรนซ์ (reference counting) คุณต้องแน่ใจว่าคุณไม่ได้สร้างวงจรขึ้นมา คุณพึ่งพาให้ Rust จับมันไม่ได้ การสร้างวงจรเรเฟอเรนซ์จะเป็นบั๊กเชิงตรรกะในโปรแกรมของคุณ ซึ่งคุณควรใช้การทดสอบอัตโนมัติ การรีวิวโค้ด (code review) และแนวปฏิบัติอื่นๆ ในการพัฒนาซอฟต์แวร์เพื่อลดให้เหลือน้อยที่สุด

วิธีแก้ปัญหาอีกวิธีในการหลีกเลี่ยงวงจรเรเฟอเรนซ์คือการจัดโครงสร้างข้อมูลของคุณใหม่ เพื่อให้เรเฟอเรนซ์บางตัวแสดงความเป็นเจ้าของและบางตัวไม่แสดง ผลก็คือ คุณสามารถมีวงจรที่ประกอบด้วยความสัมพันธ์แบบเป็นเจ้าของบางส่วนและความสัมพันธ์แบบไม่เป็นเจ้าของบางส่วน โดยมีเพียงความสัมพันธ์แบบเป็นเจ้าของเท่านั้นที่ส่งผลว่าค่าหนึ่งจะถูกทิ้งได้หรือไม่ ในลิสติ้ง 15-25 เราต้องการให้วาเรียนต์ `Cons` เป็นเจ้าของลิสต์ของมันเสมอ การจัดโครงสร้างข้อมูลใหม่จึงเป็นไปไม่ได้ มาดูตัวอย่างที่ใช้กราฟซึ่งประกอบด้วยโหนดแม่และโหนดลูก เพื่อดูว่าความสัมพันธ์แบบไม่เป็นเจ้าของเหมาะที่จะใช้ป้องกันวงจรเรเฟอเรนซ์เมื่อใด

### การป้องกันวงจรเรเฟอเรนซ์ด้วย `Weak<T>`

จนถึงตอนนี้ เราได้สาธิตแล้วว่าการเรียก `Rc::clone` เพิ่ม `strong_count` ของอินสแตนซ์ `Rc<T>` และอินสแตนซ์ `Rc<T>` จะถูกทำความสะอาดก็ต่อเมื่อ `strong_count` ของมันเป็น 0 คุณยังสร้างเรเฟอเรนซ์แบบวีค (weak reference) ไปยังค่าภายในอินสแตนซ์ `Rc<T>` ได้โดยเรียก `Rc::downgrade` และส่งเรเฟอเรนซ์ไปยัง `Rc<T>` _เรเฟอเรนซ์แบบสตรอง_ (strong reference) คือวิธีที่คุณแชร์ความเป็นเจ้าของอินสแตนซ์ `Rc<T>` ได้ _เรเฟอเรนซ์แบบวีค_ไม่แสดงความสัมพันธ์แบบเป็นเจ้าของ และจำนวนของมันไม่ส่งผลว่าเมื่อใดอินสแตนซ์ `Rc<T>` จะถูกทำความสะอาด พวกมันจะไม่ทำให้เกิดวงจรเรเฟอเรนซ์ เพราะวงจรใดๆ ที่เกี่ยวข้องกับเรเฟอเรนซ์แบบวีคจะถูกตัดขาดเมื่อจำนวนเรเฟอเรนซ์แบบสตรองของค่าที่เกี่ยวข้องเป็น 0

เมื่อคุณเรียก `Rc::downgrade` คุณจะได้สมาร์ตพอยน์เตอร์ (smart pointer) ชนิด `Weak<T>` แทนที่จะเพิ่ม `strong_count` ในอินสแตนซ์ `Rc<T>` ขึ้น 1 การเรียก `Rc::downgrade` กลับเพิ่ม `weak_count` ขึ้น 1 ชนิด `Rc<T>` ใช้ `weak_count` เพื่อติดตามว่ามีเรเฟอเรนซ์ `Weak<T>` อยู่กี่ตัว คล้ายกับ `strong_count` ข้อแตกต่างคือ `weak_count` ไม่จำเป็นต้องเป็น 0 เพื่อให้อินสแตนซ์ `Rc<T>` ถูกทำความสะอาด

เพราะค่าที่ `Weak<T>` อ้างถึงอาจถูกทิ้งไปแล้ว การจะทำอะไรกับค่าที่ `Weak<T>` ชี้อยู่ คุณต้องแน่ใจว่าค่านั้นยังอยู่ ทำเช่นนี้โดยเรียกเมธอด `upgrade` บนอินสแตนซ์ `Weak<T>` ซึ่งจะคืนค่า `Option<Rc<T>>` คุณจะได้ผลลัพธ์เป็น `Some` หากค่า `Rc<T>` ยังไม่ถูกทิ้ง และได้ผลลัพธ์เป็น `None` หากค่า `Rc<T>` ถูกทิ้งไปแล้ว เพราะ `upgrade` คืนค่า `Option<Rc<T>>` Rust จะรับประกันว่ากรณี `Some` และกรณี `None` ถูกจัดการ และจะไม่มีพอยน์เตอร์ที่ไม่ถูกต้อง

เป็นตัวอย่าง แทนที่จะใช้ลิสต์ที่สมาชิกของมันรู้จักเพียงสมาชิกตัวถัดไป เราจะสร้างทรีที่สมาชิกของมันรู้จักสมาชิกที่เป็นโหนดลูกของมัน_และ_สมาชิกที่เป็นโหนดแม่ของมัน

เราโคลน `Rc<Node>` ใน `leaf` และเก็บมันไว้ใน `branch` หมายความว่า `Node` ใน `leaf` ตอนนี้มีเจ้าของสองราย: `leaf` และ `branch` เราสามารถไปจาก `branch` ถึง `leaf` ผ่าน `branch.children` ได้ แต่ไม่มีทางที่จะไปจาก `leaf` ถึง `branch` ได้ เหตุผลคือ `leaf` ไม่มีเรเฟอเรนซ์ไปยัง `branch` และไม่รู้ว่าพวกมันเกี่ยวข้องกัน เราต้องการให้ `leaf` รู้ว่า `branch` เป็นโหนดแม่ของมัน เราจะทำเช่นนั้นต่อไป

#### การเพิ่มเรเฟอเรนซ์จากโหนดลูกไปยังโหนดแม่

เพื่อให้โหนดลูกรู้จักโหนดแม่ของมัน เราจำเป็นต้องเพิ่มฟิลด์ `parent` เข้าไปในนิยาม struct `Node` ของเรา ปัญหาอยู่ที่การตัดสินใจว่าชนิดของ `parent` ควรเป็นอะไร เรารู้ว่ามันบรรจุ `Rc<T>` ไม่ได้ เพราะนั่นจะสร้างวงจรเรเฟอเรนซ์โดยที่ `leaf.parent` ชี้ไปยัง `branch` และ `branch.children` ชี้ไปยัง `leaf` ซึ่งจะทำให้ค่า `strong_count` ของพวกมันไม่มีวันเป็น 0

เมื่อคิดถึงความสัมพันธ์ในอีกแง่หนึ่ง โหนดแม่ควรเป็นเจ้าของโหนดลูกของมัน: หากโหนดแม่ถูกทิ้ง โหนดลูกของมันก็ควรถูกทิ้งด้วย อย่างไรก็ตาม โหนดลูกไม่ควรเป็นเจ้าของโหนดแม่: หากเราทิ้งโหนดลูก โหนดแม่ก็ควรยังอยู่ นี่เป็นกรณีที่เหมาะกับเรเฟอเรนซ์แบบวีค!

ดังนั้น แทนที่จะเป็น `Rc<T>` เราจะทำให้ชนิดของ `parent` ใช้ `Weak<T>` โดยเฉพาะเจาะจงคือ `RefCell<Weak<Node>>` ตอนนี้การนิยาม struct `Node` ของเรามีหน้าตาแบบนี้:


การสร้างโหนด `leaf` ดูคล้ายกับลิสติ้ง 15-27 ยกเว้นฟิลด์ `parent`: `leaf` เริ่มต้นโดยไม่มีโหนดแม่ ดังนั้นเราจึงสร้างอินสแตนซ์เรเฟอเรนซ์ `Weak<Node>` ใหม่ที่ว่างเปล่า

ณ จุดนี้ เมื่อเราพยายามได้เรเฟอเรนซ์ไปยังโหนดแม่ของ `leaf` โดยใช้เมธอด `upgrade` เราได้ค่า `None` เราจะเห็นสิ่งนี้ในผลลัพธ์จากสเตตเมนต์ `println!` ตัวแรก:

```text
leaf parent = None
```

เมื่อเราสร้างโหนด `branch` มันก็จะมีเรเฟอเรนซ์ `Weak<Node>` ใหม่ในฟิลด์ `parent` ด้วย เพราะ `branch` ไม่มีโหนดแม่ เรายังคงมี `leaf` เป็นหนึ่งในโหนดลูกของ `branch` เมื่อเรามีอินสแตนซ์ `Node` ใน `branch` แล้ว เราสามารถแก้ไข `leaf` เพื่อให้มันมีเรเฟอเรนซ์ `Weak<Node>` ไปยังโหนดแม่ของมันได้ เราใช้เมธอด `borrow_mut` บน `RefCell<Weak<Node>>` ในฟิลด์ `parent` ของ `leaf` จากนั้นเราใช้ฟังก์ชัน `Rc::downgrade` เพื่อสร้างเรเฟอเรนซ์ `Weak<Node>` ไปยัง `branch` จาก `Rc<Node>` ใน `branch`

เมื่อเราพิมพ์โหนดแม่ของ `leaf` อีกครั้ง คราวนี้เราจะได้วาเรียนต์ `Some` ที่ถือ `branch`: ตอนนี้ `leaf` เข้าถึงโหนดแม่ของมันได้แล้ว! เมื่อเราพิมพ์ `leaf` เรายังหลีกเลี่ยงวงจรที่ลงเอยด้วยสแตกโอเวอร์โฟลว์เหมือนที่เรามีในลิสติ้ง 15-26 ด้วย เรเฟอเรนซ์ `Weak<Node>` ถูกพิมพ์เป็น `(Weak)`:

```text
leaf parent = Some(Node { value: 5, parent: RefCell { value: (Weak) },
children: RefCell { value: [Node { value: 3, parent: RefCell { value: (Weak) },
children: RefCell { value: [] } }] } })
```

การที่ไม่มีผลลัพธ์แบบไม่สิ้นสุดบ่งชี้ว่าโค้ดนี้ไม่ได้สร้างวงจรเรเฟอเรนซ์ เรายังบอกได้จากค่าที่เราได้จากการเรียก `Rc::strong_count` และ `Rc::weak_count`

#### การเห็นภาพการเปลี่ยนแปลงของ `strong_count` และ `weak_count`

มาดูว่าค่า `strong_count` และ `weak_count` ของอินสแตนซ์ `Rc<Node>` เปลี่ยนแปลงอย่างไรโดยการสร้างสโคปชั้นในใหม่และย้ายการสร้าง `branch` เข้าไปในสโคปนั้น ด้วยวิธีนี้ เราจะเห็นว่าเกิดอะไรขึ้นเมื่อ `branch` ถูกสร้างแล้วถูกทิ้งเมื่อมันออกจากสโคป การแก้ไขแสดงอยู่ในลิสติ้ง 15-29

หลังจากที่ `leaf` ถูกสร้างขึ้น `Rc<Node>` ของมันมีจำนวนเรเฟอเรนซ์แบบสตรองเป็น 1 และจำนวนเรเฟอเรนซ์แบบวีคเป็น 0 ในสโคปชั้นใน เราสร้าง `branch` และเชื่อมโยงมันกับ `leaf` ตรงจุดนั้นเมื่อเราพิมพ์จำนวน `Rc<Node>` ใน `branch` จะมีจำนวนเรเฟอเรนซ์แบบสตรองเป็น 1 และจำนวนเรเฟอเรนซ์แบบวีคเป็น 1 (เพราะ `leaf.parent` ชี้ไปยัง `branch` ด้วย `Weak<Node>`) เมื่อเราพิมพ์จำนวนใน `leaf` เราจะเห็นว่ามันมีจำนวนเรเฟอเรนซ์แบบสตรองเป็น 2 เพราะ `branch` ตอนนี้มีโคลนของ `Rc<Node>` ของ `leaf` เก็บอยู่ใน `branch.children` แต่จะยังมีจำนวนเรเฟอเรนซ์แบบวีคเป็น 0

เมื่อสโคปชั้นในสิ้นสุดลง `branch` ออกจากสโคปและจำนวนเรเฟอเรนซ์แบบสตรองของ `Rc<Node>` ลดลงเป็น 0 ดังนั้น `Node` ของมันจึงถูกทิ้ง จำนวนเรเฟอเรนซ์แบบวีคเป็น 1 จาก `leaf.parent` ไม่มีผลต่อว่าค่า `Node` จะถูกทิ้งหรือไม่ ดังนั้นเราจึงไม่มีการรั่วไหลของหน่วยความจำเลย!

หากเราพยายามเข้าถึงโหนดแม่ของ `leaf` หลังจากสิ้นสุดสโคป เราจะได้ `None` อีกครั้ง ที่ส่วนท้ายของโปรแกรม `Rc<Node>` ใน `leaf` มีจำนวนเรเฟอเรนซ์แบบสตรองเป็น 1 และจำนวนเรเฟอเรนซ์แบบวีคเป็น 0 เพราะตอนนี้ตัวแปร `leaf` กลายเป็นเรเฟอเรนซ์เดียวที่อ้างถึง `Rc<Node>` อีกครั้ง

ตรรกะทั้งหมดที่จัดการจำนวนและการทิ้งค่าถูกสร้างไว้ใน `Rc<T>` และ `Weak<T>` และการอิมพลีเมนต์เทรต (trait) `Drop` ของพวกมัน การระบุว่าความสัมพันธ์จากโหนดลูกไปยังโหนดแม่ควรเป็นเรเฟอเรนซ์ `Weak<T>` ในการนิยาม `Node` ทำให้คุณมีโหนดแม่ชี้ไปยังโหนดลูกและในทางกลับกันได้โดยไม่สร้างวงจรเรเฟอเรนซ์และการรั่วไหลของหน่วยความจำ

## สรุป

บทนี้ครอบคลุมวิธีใช้สมาร์ตพอยน์เตอร์เพื่อสร้างการรับประกันและข้อแลกเปลี่ยนที่แตกต่างจากการที่ Rust ทำเป็นค่าเริ่มต้นกับเรเฟอเรนซ์ทั่วไป ชนิด `Box<T>` มีขนาดที่รู้ได้และชี้ไปยังข้อมูลที่จัดสรรบนฮีป ชนิด `Rc<T>` คอยติดตามจำนวนเรเฟอเรนซ์ไปยังข้อมูลบนฮีปเพื่อให้ข้อมูลมีเจ้าของหลายรายได้ ชนิด `RefCell<T>` พร้อมการเปลี่ยนแปลงค่าภายในให้ชนิดข้อมูลที่เราใช้ได้เมื่อเราต้องการชนิดที่เปลี่ยนแปลงไม่ได้แต่ต้องการเปลี่ยนค่าภายในของชนิดนั้น มันยังบังคับใช้กฎการยืมตอนรันไทม์แทนที่จะเป็นตอนคอมไพล์ด้วย

นอกจากนี้ยังได้พูดคุยถึงเทรต `Deref` และ `Drop` ซึ่งทำให้ฟังก์ชันการทำงานจำนวนมากของสมาร์ตพอยน์เตอร์เป็นไปได้ เราได้สำรวจวงจรเรเฟอเรนซ์ที่อาจทำให้เกิดการรั่วไหลของหน่วยความจำและวิธีป้องกันโดยใช้ `Weak<T>`

หากบทนี้ทำให้คุณสนใจและคุณต้องการอิมพลีเมนต์สมาร์ตพอยน์เตอร์ของคุณเอง ลองดู[“The Rustonomicon”][nomicon] สำหรับข้อมูลที่เป็นประโยชน์เพิ่มเติม

ต่อไป เราจะพูดคุยถึงการทำงานพร้อมกันใน Rust คุณจะได้เรียนรู้เกี่ยวกับสมาร์ตพอยน์เตอร์ใหม่ๆ สองสามตัวด้วย
