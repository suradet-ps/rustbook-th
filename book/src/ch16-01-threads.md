## ใช้เธรดรันโค้ดพร้อมกัน

ในระบบปฏิบัติการปัจจุบันส่วนใหญ่ โค้ดของโปรแกรมที่ถูกเรียกทำงานจะรันอยู่ภายใน_โปรเซส_ (process) หนึ่ง และระบบปฏิบัติการจะจัดการหลายโปรเซสในเวลาเดียวกัน ภายในโปรแกรมหนึ่งๆ คุณยังสามารถมีส่วนต่างๆ ที่เป็นอิสระต่อกันซึ่งทำงานพร้อมกันได้ กลไกที่รันส่วนอิสระเหล่านี้เรียกว่า_เธรด_ (thread) ตัวอย่างเช่น เว็บเซิร์ฟเวอร์ (web server) อาจมีหลายเธรดเพื่อให้สามารถตอบสนองคำขอมากกว่าหนึ่งคำขอในเวลาเดียวกันได้

การแบ่งการคำนวณในโปรแกรมของคุณออกเป็นหลายเธรดเพื่อรันหลายทาสก์ (task) ในเวลาเดียวกันสามารถปรับปรุงประสิทธิภาพได้ แต่มันก็เพิ่มความซับซ้อนด้วย เพราะเธรดสามารถรันพร้อมกันได้ จึงไม่มีการรับประกันโดยธรรมชาติเกี่ยวกับลำดับที่ส่วนต่างๆ ของโค้ดของคุณบนเธรดที่ต่างกันจะรัน สิ่งนี้อาจนำไปสู่ปัญหา เช่น:

- สภาวะการแข่งกัน (race condition) ซึ่งเธรดต่างๆ เข้าถึงข้อมูลหรือทรัพยากรด้วยลำดับที่ไม่สอดคล้องกัน
- เดดล็อก (deadlock) ซึ่งเธรดสองตัวรอกันและกัน ทำให้ทั้งสองเธรดไม่สามารถดำเนินการต่อได้
- บั๊กที่เกิดขึ้นเฉพาะในสถานการณ์บางอย่างและยากที่จะจำลองขึ้นใหม่และแก้ไขอย่างเชื่อถือได้

Rust พยายามบรรเทาผลกระทบเชิงลบของการใช้เธรด แต่การเขียนโปรแกรมในบริบทแบบหลายเธรดก็ยังต้องใช้ความคิดอย่างรอบคอบและต้องมีโครงสร้างโค้ดที่แตกต่างจากโปรแกรมที่รันในเธรดเดียว

ภาษาโปรแกรมต่างๆ อิมพลีเมนต์เธรดด้วยวิธีที่แตกต่างกันสองสามวิธี และระบบปฏิบัติการหลายตัวจัดเตรียม API ที่ภาษาโปรแกรมสามารถเรียกใช้เพื่อสร้างเธรดใหม่ได้ ไลบรารีมาตรฐานของ Rust ใช้โมเดลการอิมพลีเมนต์เธรดแบบ _1:1_ ซึ่งโปรแกรมจะใช้เธรดของระบบปฏิบัติการหนึ่งตัวต่อเธรดของภาษาหนึ่งตัว มีเครตที่อิมพลีเมนต์โมเดลเธรดแบบอื่นซึ่งมีการแลกเปลี่ยน (trade-off) ที่แตกต่างจากโมเดล 1:1 (ระบบ async ของ Rust ซึ่งเราจะได้เห็นในบทถัดไป ก็จัดเตรียมแนวทางอื่นสำหรับการทำงานพร้อมกัน (concurrency) เช่นกัน)

### การใช้โคลเชอร์ `move` กับเธรด

เรามักใช้คำสงวน `move` กับโคลเชอร์ที่ส่งให้ `thread::spawn` เพราะจากนั้นโคลเชอร์จะรับความเป็นเจ้าของ (ownership) ค่าที่มันใช้จากสภาพแวดล้อม ซึ่งเป็นการถ่ายโอนความเป็นเจ้าของค่าเหล่านั้นจากเธรดหนึ่งไปยังอีกเธรดหนึ่ง ใน[“การจับเรเฟอเรนซ์หรือการย้ายความเป็นเจ้าของ”][capture]<!-- ignore --> ในบทที่ 13 เราได้พูดคุยถึง `move` ในบริบทของโคลเชอร์ ตอนนี้เราจะมุ่งเน้นไปที่ปฏิสัมพันธ์ระหว่าง `move` กับ `thread::spawn` มากขึ้น

เราอาจรู้สึกอยากลองใช้วิธีเดียวกันนี้แก้โค้ดในลิสติ้ง 16-4 ที่เธรดหลักเรียก `drop` โดยใช้โคลเชอร์ `move` อย่างไรก็ตาม การแก้ไขนี้จะใช้ไม่ได้ เพราะสิ่งที่ลิสติ้ง 16-4 พยายามทำนั้นไม่ได้รับอนุญาตด้วยเหตุผลที่แตกต่างออกไป หากเราเพิ่ม `move` ให้โคลเชอร์ เราจะย้าย `v` เข้าไปในสภาพแวดล้อมของโคลเชอร์ และเราจะเรียก `drop` บนมันในเธรดหลักไม่ได้อีกต่อไป เราจะได้ข้อผิดพลาดของคอมไพเลอร์นี้แทน:

กฎความเป็นเจ้าของของ Rust ช่วยเราไว้อีกครั้งแล้ว! เราได้ข้อผิดพลาดจากโค้ดในลิสติ้ง 16-3 เพราะ Rust ระมัดระวังตัวและยืม `v` ให้เธรดเท่านั้น ซึ่งหมายความว่าในทางทฤษฎีแล้วเธรดหลักอาจทำให้เรเฟอเรนซ์ของเธรดที่ถูกสร้างใช้ไม่ได้ การบอก Rust ให้ย้ายความเป็นเจ้าของ `v` ไปยังเธรดที่ถูกสร้างเป็นการรับประกันกับ Rust ว่าเธรดหลักจะไม่ใช้ `v` อีกต่อไป หากเราเปลี่ยนลิสติ้ง 16-4 ด้วยวิธีเดียวกัน เราก็จะละเมิดกฎความเป็นเจ้าของเมื่อเราพยายามใช้ `v` ในเธรดหลัก คำสงวน `move` ลบล้างพฤติกรรมเริ่มต้นแบบระมัดระวังของ Rust ที่จะยืม; มันไม่ได้ทำให้เราละเมิดกฎความเป็นเจ้าของได้
