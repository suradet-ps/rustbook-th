## ภาคผนวก G - Rust ถูกสร้างขึ้นมาอย่างไร และ “Nightly Rust”

ภาคผนวกนี้ว่าด้วยว่า Rust ถูกสร้างขึ้นมาอย่างไร และสิ่งนั้นส่งผลต่อคุณในฐานะนักพัฒนา Rust อย่างไร

### ความเสถียรโดยไม่หยุดนิ่ง

ในฐานะภาษา Rust ให้ความสำคัญกับความเสถียรของโค้ดของคุณ_อย่างมาก_ เราต้องการให้ Rust เป็นรากฐานที่แข็งแกร่งดั่งหินผาที่คุณสร้างต่อยอดได้ และหากทุกอย่างเปลี่ยนแปลงอยู่ตลอดเวลา สิ่งนั้นก็จะเป็นไปไม่ได้ ในขณะเดียวกัน หากเราไม่สามารถทดลองกับฟีเจอร์ใหม่ๆ ได้ เราอาจไม่พบข้อบกพร่องสำคัญจนกระทั่งหลังการเผยแพร่ของมัน ซึ่งตอนนั้นเราเปลี่ยนแปลงอะไรไม่ได้อีกแล้ว

วิธีแก้ปัญหานี้ของเราคือสิ่งที่เราเรียกว่า “ความเสถียรโดยไม่หยุดนิ่ง” และหลักการนำทางของเราคือ: คุณไม่ควรต้องกลัวการอัปเกรดไปยัง Rust เวอร์ชันเสถียรเวอร์ชันใหม่เลย การอัปเกรดแต่ละครั้งควรเจ็บปวดน้อยที่สุด แต่ก็ควรนำฟีเจอร์ใหม่ ข้อบกพร่องที่น้อยลง และเวลาคอมไพล์ที่เร็วขึ้นมาให้คุณด้วย

### ชู ชู! ช่องทางการเผยแพร่และการนั่งรถไฟ

การพัฒนา Rust ดำเนินไปตาม_ตารางเวลารถไฟ_ กล่าวคือ การพัฒนาทั้งหมดเกิดขึ้นบนแบรนช์ main ของรีพอซิทอรี Rust การเผยแพร่เป็นไปตามโมเดลรถไฟการเผยแพร่ซอฟต์แวร์ (software release train) ซึ่ง Cisco IOS และโปรเจกต์ซอฟต์แวร์อื่นๆ เคยใช้ มี_ช่องทางการเผยแพร่_ (release channel) สามช่องทางสำหรับ Rust:

- Nightly
- Beta
- Stable

นักพัฒนา Rust ส่วนใหญ่ใช้ช่องทางการเผยแพร่แบบเสถียรเป็นหลัก แต่ผู้ที่ต้องการลองฟีเจอร์ใหม่เชิงทดลองอาจใช้ nightly หรือ beta

นี่คือตัวอย่างว่ากระบวนการพัฒนาและการเผยแพร่ทำงานอย่างไร: สมมติว่าทีม Rust กำลังทำงานกับการเผยแพร่ Rust 1.5 การเผยแพร่นั้นเกิดขึ้นในเดือนธันวาคม 2015 แต่จะช่วยให้เรามีหมายเลขเวอร์ชันที่สมจริง ฟีเจอร์ใหม่ถูกเพิ่มเข้าไปใน Rust: คอมมิตใหม่ลงบนแบรนช์ main ทุกคืน จะมีเวอร์ชัน nightly ของ Rust ใหม่ถูกสร้างขึ้น ทุกวันคือวันเผยแพร่ และการเผยแพร่เหล่านี้ถูกสร้างขึ้นโดยโครงสร้างพื้นฐานการเผยแพร่ของเราโดยอัตโนมัติ ดังนั้นเมื่อเวลาผ่านไป การเผยแพร่ของเราจึงมีหน้าตาดังนี้ คืนละครั้ง:

```text
nightly: * - - * - - *
```

ทุกๆ หกสัปดาห์ ถึงเวลาที่จะเตรียมการเผยแพร่ครั้งใหม่! แบรนช์ `beta` ของรีพอซิทอรี Rust แยกออกมาจากแบรนช์ main ที่ nightly ใช้ ตอนนี้จึงมีการเผยแพร่สองรายการ:

```text
nightly: * - - * - - *
                     |
beta:                *
```

ผู้ใช้ Rust ส่วนใหญ่ไม่ได้ใช้การเผยแพร่ beta อย่างจริงจัง แต่จะทดสอบกับ beta ในระบบ CI ของตนเพื่อช่วยให้ Rust ค้นพบรีเกรสชัน (regression) ที่อาจเกิดขึ้น ในระหว่างนี้ ก็ยังมีการเผยแพร่ nightly ทุกคืน:

```text
nightly: * - - * - - * - - * - - *
                     |
beta:                *
```

สมมติว่าพบรีเกรสชัน โชคดีที่เรามีเวลาทดสอบการเผยแพร่ beta ก่อนที่รีเกรสชันนั้นจะแอบเข้าไปในการเผยแพร่เวอร์ชันเสถียร! การแก้ไขถูกนำไปใช้กับแบรนช์ main ทำให้ nightly ได้รับการแก้ไข จากนั้นการแก้ไขจึงถูกแบ็กพอร์ต (backport) ไปยังแบรนช์ `beta` และการเผยแพร่ beta ครั้งใหม่ก็ถูกสร้างขึ้น:

```text
nightly: * - - * - - * - - * - - * - - *
                     |
beta:                * - - - - - - - - *
```

หกสัปดาห์หลังจาก beta ตัวแรกถูกสร้างขึ้น ถึงเวลาของการเผยแพร่เวอร์ชันเสถียร! แบรนช์ `stable` ถูกสร้างขึ้นจากแบรนช์ `beta`:

```text
nightly: * - - * - - * - - * - - * - - * - * - *
                     |
beta:                * - - - - - - - - *
                                       |
stable:                                *
```

ไชโย! Rust 1.5 เสร็จแล้ว! อย่างไรก็ตาม เราลืมไปสิ่งหนึ่ง: เพราะหกสัปดาห์ได้ผ่านไปแล้ว เราจึงต้องมี beta ตัวใหม่ของ Rust เวอร์ชัน_ถัดไป_คือ 1.6 ด้วย ดังนั้นหลังจาก `stable` แยกออกจาก `beta` แล้ว เวอร์ชันถัดไปของ `beta` ก็แยกออกจาก `nightly` อีกครั้ง:

```text
nightly: * - - * - - * - - * - - * - - * - * - *
                     |                         |
beta:                * - - - - - - - - *       *
                                       |
stable:                                *
```

โมเดลนี้เรียกว่า “โมเดลรถไฟ” เพราะทุกๆ หกสัปดาห์ การเผยแพร่จะ “ออกจากสถานี” แต่ยังต้องเดินทางผ่านช่องทาง beta ก่อนที่จะมาถึงในฐานะการเผยแพร่เวอร์ชันเสถียร

Rust เผยแพร่ทุกหกสัปดาห์อย่างเที่ยงตรง หากคุณรู้วันที่ของการเผยแพร่ Rust ครั้งหนึ่ง คุณก็รู้วันที่ของการเผยแพร่ครั้งถัดไปได้: นั่นคืออีกหกสัปดาห์ถัดมา แง่ดีของการมีกำหนดการเผยแพร่ทุกหกสัปดาห์คือรถไฟขบวนถัดไปกำลังจะมาถึงในไม่ช้า หากฟีเจอร์บางอย่างพลาดการเผยแพร่ครั้งใดครั้งหนึ่งไป ก็ไม่ต้องกังวล: อีกครั้งหนึ่งกำลังจะเกิดขึ้นในไม่ช้า! สิ่งนี้ช่วยลดแรงกดดันที่จะแอบใส่ฟีเจอร์ที่อาจยังไม่ขัดเกลาเข้าไปใกล้เส้นตายการเผยแพร่

ต้องขอบคุณกระบวนการนี้ คุณจึงสามารถลองบิลด์ถัดไปของ Rust ได้เสมอ และพิสูจน์ด้วยตัวเองว่าการอัปเกรดเป็นเรื่องง่าย: หากการเผยแพร่ beta ทำงานไม่เป็นไปตามที่คาดไว้ คุณสามารถรายงานให้ทีมทราบและทำให้มันได้รับการแก้ไขก่อนที่การเผยแพร่เวอร์ชันเสถียรครั้งถัดไปจะเกิดขึ้น! การเสียหายในการเผยแพร่ beta นั้นพบได้ค่อนข้างน้อย แต่ `rustc` ก็ยังเป็นซอฟต์แวร์ชิ้นหนึ่ง และบั๊กก็มีอยู่จริง

### ช่วงเวลาบำรุงรักษา

โปรเจกต์ Rust สนับสนุนเวอร์ชันเสถียรล่าสุด เมื่อเวอร์ชันเสถียรใหม่ถูกเผยแพร่ เวอร์ชันเก่าจะถึงจุดสิ้นสุดอายุการใช้งาน (end of life หรือ EOL) ซึ่งหมายความว่าแต่ละเวอร์ชันได้รับการสนับสนุนเป็นเวลาหกสัปดาห์

### ฟีเจอร์ที่ยังไม่เสถียร

ยังมีข้อควรระวังอีกประการหนึ่งในโมเดลการเผยแพร่นี้: ฟีเจอร์ที่ยังไม่เสถียร (unstable feature) Rust ใช้เทคนิคที่เรียกว่า “แฟล็กฟีเจอร์” (feature flag) เพื่อกำหนดว่าฟีเจอร์ใดเปิดใช้งานในแต่ละการเผยแพร่ หากฟีเจอร์ใหม่กำลังอยู่ระหว่างการพัฒนาอย่างจริงจัง มันจะลงบนแบรนช์ main และด้วยเหตุนี้จึงอยู่ใน nightly แต่จะอยู่ภายใต้_แฟล็กฟีเจอร์_ หากคุณในฐานะผู้ใช้ต้องการลองฟีเจอร์ที่ยังอยู่ระหว่างการพัฒนา คุณก็ทำได้ แต่คุณต้องใช้การเผยแพร่ nightly ของ Rust และใส่แอนโนเทชันในซอร์สโค้ดของคุณด้วยแฟล็กที่เหมาะสมเพื่อเลือกเปิดใช้

หากคุณใช้การเผยแพร่ beta หรือเวอร์ชันเสถียรของ Rust คุณจะใช้แฟล็กฟีเจอร์ใดๆ ไม่ได้ นี่คือกุญแจที่ทำให้เราได้ใช้งานฟีเจอร์ใหม่ๆ จริงก่อนที่เราจะประกาศว่ามันเสถียรตลอดไป ผู้ที่ต้องการเลือกใช้ของล้ำสมัยก็ทำได้ และผู้ที่ต้องการประสบการณ์ที่แข็งแกร่งดั่งหินผาก็ยึดอยู่กับเวอร์ชันเสถียรและรู้ว่าโค้ดของตนจะไม่พัง ความเสถียรโดยไม่หยุดนิ่ง

หนังสือเล่มนี้บรรจุข้อมูลเกี่ยวกับฟีเจอร์เสถียรเท่านั้น เนื่องจากฟีเจอร์ที่อยู่ระหว่างดำเนินการยังคงเปลี่ยนแปลงอยู่ และแน่นอนว่ามันจะแตกต่างออกไประหว่างตอนที่หนังสือเล่มนี้ถูกเขียนกับตอนที่มันถูกเปิดใช้ในบิลด์เสถียร คุณสามารถหาเอกสารประกอบสำหรับฟีเจอร์ที่มีเฉพาะใน nightly ได้ทางออนไลน์

### Rustup และบทบาทของ nightly Rust

Rustup ทำให้การสลับระหว่างช่องทางการเผยแพร่ต่างๆ ของ Rust เป็นเรื่องง่าย ทั้งในระดับส่วนกลางหรือระดับต่อโปรเจกต์ โดยค่าเริ่มต้น คุณจะมีการติดตั้ง Rust เวอร์ชันเสถียรอยู่แล้ว ตัวอย่างเช่น หากต้องการติดตั้ง nightly:

```console
$ rustup toolchain install nightly
```

คุณยังสามารถดู_ทูลเชน_ (toolchain) ทั้งหมด (การเผยแพร่ของ Rust และคอมโพเนนต์ที่เกี่ยวข้อง) ที่คุณติดตั้งไว้ได้ด้วย `rustup` นี่คือตัวอย่างบนคอมพิวเตอร์ Windows ของผู้เขียนคนหนึ่งของคุณ:

```powershell
> rustup toolchain list
stable-x86_64-pc-windows-msvc (default)
beta-x86_64-pc-windows-msvc
nightly-x86_64-pc-windows-msvc
```

อย่างที่คุณเห็น ทูลเชนเสถียรเป็นค่าเริ่มต้น ผู้ใช้ Rust ส่วนใหญ่ใช้เวอร์ชันเสถียรเกือบตลอดเวลา คุณอาจต้องการใช้เวอร์ชันเสถียรเกือบตลอดเวลา แต่ใช้ nightly กับโปรเจกต์ใดโปรเจกต์หนึ่งโดยเฉพาะ เพราะคุณสนใจฟีเจอร์ล้ำสมัย เมื่อต้องการทำเช่นนั้น คุณสามารถใช้ `rustup override` ในไดเรกทอรีของโปรเจกต์นั้นเพื่อตั้งให้ทูลเชน nightly เป็นทูลเชนที่ `rustup` ควรใช้เมื่อคุณอยู่ในไดเรกทอรีนั้น:

```console
$ cd ~/projects/needs-nightly
$ rustup override set nightly
```

ตอนนี้ ทุกครั้งที่คุณเรียก `rustc` หรือ `cargo` ภายใน _~/projects/needs-nightly_ `rustup` จะทำให้แน่ใจว่าคุณใช้ nightly Rust แทนที่จะเป็นค่าเริ่มต้นอย่าง Rust เวอร์ชันเสถียรของคุณ สิ่งนี้มีประโยชน์มากเมื่อคุณมีโปรเจกต์ Rust จำนวนมาก!

### กระบวนการ RFC และทีมงานต่างๆ

แล้วคุณจะเรียนรู้เกี่ยวกับฟีเจอร์ใหม่เหล่านี้ได้อย่างไร? โมเดลการพัฒนาของ Rust เป็นไปตาม_กระบวนการ Request For Comments (RFC)_ หากคุณอยากเห็นการปรับปรุงใน Rust คุณสามารถเขียนข้อเสนอที่เรียกว่า RFC ได้

ใครๆ ก็เขียน RFC เพื่อปรับปรุง Rust ได้ และข้อเสนอเหล่านี้จะถูกตรวจทานและอภิปรายโดยทีม Rust ซึ่งประกอบด้วยทีมย่อยเฉพาะทางหลายทีม มีรายชื่อทีมทั้งหมด[บนเว็บไซต์ของ Rust](https://www.rust-lang.org/governance) ซึ่งรวมถึงทีมสำหรับแต่ละด้านของโปรเจกต์: การออกแบบภาษา การอิมพลีเมนต์คอมไพเลอร์ (compiler) โครงสร้างพื้นฐาน เอกสารประกอบ และอื่นๆ ทีมที่เกี่ยวข้องจะอ่านข้อเสนอและความเห็นต่างๆ เขียนความเห็นของตนเองเพิ่มเติม และในที่สุดก็เกิดความเห็นพ้องที่จะรับหรือปฏิเสธฟีเจอร์นั้น

หากฟีเจอร์นั้นได้รับการยอมรับ ประเด็น (issue) จะถูกเปิดบนรีพอซิทอรีของ Rust และใครคนหนึ่งก็สามารถอิมพลีเมนต์มันได้ คนที่อิมพลีเมนต์มันอาจไม่ใช่คนที่เสนอฟีเจอร์นั้นตั้งแต่แรกก็ได้! เมื่อการอิมพลีเมนต์พร้อม มันจะลงบนแบรนช์ main ภายใต้เกตฟีเจอร์ (feature gate) ดังที่เราได้พูดคุยกันในหัวข้อ[“ฟีเจอร์ที่ยังไม่เสถียร”](#unstable-features)<!-- ignore -->

หลังจากผ่านไประยะหนึ่ง เมื่อนักพัฒนา Rust ที่ใช้การเผยแพร่ nightly ได้ลองฟีเจอร์ใหม่นั้นแล้ว สมาชิกทีมจะอภิปรายเกี่ยวกับฟีเจอร์นั้น ว่ามันออกมาดีแค่ไหนบน nightly และตัดสินใจว่ามันควรเข้าไปอยู่ใน Rust เวอร์ชันเสถียรหรือไม่ หากตัดสินใจเดินหน้าต่อ เกตฟีเจอร์จะถูกถอดออก และฟีเจอร์นั้นก็ถือว่าเสถียรแล้ว! มันนั่งรถไฟเข้าไปสู่การเผยแพร่ Rust เวอร์ชันเสถียรครั้งใหม่
