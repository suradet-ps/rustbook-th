## รีแฟกเตอร์เพื่อปรับปรุงโครงสร้างและการจัดการข้อผิดพลาด

เพื่อพัฒนาโปรแกรมของเราให้ดียิ่งขึ้น เราจะมาแก้ไขปัญหา 4 ประการที่เกี่ยวข้องกับโครงสร้างของโปรแกรมและวิธีจัดการกับข้อผิดพลาดที่อาจเกิดขึ้น ประการแรก ในตอนนี้ฟังก์ชัน `main` ของเราต้องแบกรับภาระหน้าที่ 2 อย่างพร้อมกัน นั่นคือการแยกวิเคราะห์อาร์กิวเมนต์ (parse arguments) และการอ่านไฟล์ เมื่อโปรแกรมเติบโตขึ้น จำนวนหน้าที่แยกย่อยที่ฟังก์ชัน `main` ต้องดูแลก็จะเพิ่มขึ้นตามไปด้วย และเมื่อฟังก์ชันหนึ่งๆ มีความรับผิดชอบมากเกินไป มันจะกลายเป็นเรื่องยากต่อการทำความเข้าใจ ยากต่อการทดสอบ และยากที่จะแก้ไขโดยไม่ไปกระทบกระเทือนให้ส่วนอื่นๆ พัง ทางเลือกที่ดีที่สุดคือการแยกฟังก์ชันการทำงานออกจากกัน เพื่อให้แต่ละฟังก์ชันรับผิดชอบเพียงหน้าที่เดียวอย่างชัดเจน

ประเด็นนี้ยังเชื่อมโยงกับปัญหาประการที่สอง: แม้ว่าตัวแปร `query` และ `file_path` จะเป็นตัวแปรสำหรับกำหนดค่า (configuration) ของโปรแกรม แต่ตัวแปรอย่าง `contents` กลับถูกนำมาใช้เพื่อดำเนินตรรกะการทำงาน ยิ่งฟังก์ชัน `main` มีขนาดยาวขึ้นเท่าไร เราก็ยิ่งต้องประกาศตัวแปรเข้ามาไว้ในสโคปมากขึ้นเท่านั้น และยิ่งมีตัวแปรในสโคปมากเท่าใด การจะคอยติดตามจุดประสงค์ของแต่ละตัวแปรก็ยิ่งทำได้ยากขึ้น ทางที่ดีที่สุดคือการจัดกลุ่มตัวแปรที่ใช้กำหนดค่าเหล่านี้ไว้ในโครงสร้างเดียวกัน เพื่อให้วัตถุประสงค์ในการใช้งานมีความชัดเจน

ปัญหาประการที่สามคือ เราใช้ `expect` เพื่อพิมพ์ข้อความแจ้งเตือนเมื่อการอ่านไฟล์ล้มเหลว แต่ข้อความนั้นกลับพิมพ์เพียงแค่ `Should have been able to read the file` ทว่าการอ่านไฟล์อาจล้มเหลวได้จากหลายสาเหตุ เช่น ไฟล์อาจไม่มีอยู่จริง หรือเราอาจไม่มีสิทธิ์ (permission) ในการเปิดอ่านไฟล์นั้น ในตอนนี้ ไม่ว่าจะเกิดปัญหาจากสาเหตุใด โปรแกรมก็จะพิมพ์ข้อความเดิมซ้ำๆ ออกมา ซึ่งไม่ได้ให้ข้อมูลที่เป็นประโยชน์แก่ผู้ใช้งานเลยแม้แต่น้อย!

ประการที่สี่ เราใช้ `expect` ในการจัดการข้อผิดพลาด ซึ่งหากผู้ใช้สั่งรันโปรแกรมโดยระบุอาร์กิวเมนต์ไม่ครบถ้วน พวกเขาจะได้รับข้อผิดพลาด `index out of bounds` จาก Rust ซึ่งไม่ได้อธิบายสาเหตุของปัญหาให้ผู้ใช้เข้าใจได้อย่างชัดเจน ทางออกที่ดีที่สุดคือการรวบรวมโค้ดจัดการข้อผิดพลาด (error handling) ทั้งหมดไว้ที่จุดเดียวกัน เพื่อให้ผู้ที่จะเข้ามาดูแลโค้ดในอนาคตมีจุดให้ตรวจสอบเพียงจุดเดียวหากจำเป็นต้องแก้ไขตรรกะการจัดการข้อผิดพลาด และการรวมโค้ดจัดการข้อผิดพลาดไว้ในที่เดียวยังช่วยรับประกันว่าเราจะสามารถพิมพ์ข้อความที่สื่อความหมายและมีประโยชน์ต่อผู้ใช้งานจริงได้เสมอ

เรามาจัดการกับปัญหาทั้ง 4 ประการนี้ด้วยการรีแฟกเตอร์ (refactor) โครงสร้างโปรเจกต์ของเรากัน

### การแยกความรับผิดชอบในโปรเจกต์ไบนารี

ปัญหาเรื่องโครงสร้างจากการมอบหมายหน้าที่ความรับผิดชอบหลายอย่างให้ฟังก์ชัน `main` ถือเป็นเรื่องที่พบได้ทั่วไปในโปรเจกต์ไบนารี ด้วยเหตุนี้ นักพัฒนา Rust จำนวนมากจึงพบว่า การแยกแยะขอบเขตความรับผิดชอบ (separation of concerns) ของโปรแกรมไบนารีให้เป็นสัดส่วนนั้นมีประโยชน์อย่างยิ่งเมื่อฟังก์ชัน `main` เริ่มมีขนาดใหญ่ขึ้น โดยกระบวนการนี้จะประกอบด้วยขั้นตอนดังต่อไปนี้:

- แยกโปรแกรมของคุณออกเป็นไฟล์ _main.rs_ และไฟล์ _lib.rs_ แล้วย้ายตรรกะการทำงานหลักของโปรแกรมไปไว้ใน _lib.rs_
- ตราบใดที่ตรรกะการแยกวิเคราะห์อาร์กิวเมนต์คอมมานด์ไลน์ยังคงมีขนาดเล็ก มันก็สามารถอยู่ในฟังก์ชัน `main` ต่อไปได้
- เมื่อตรรกะการแยกวิเคราะห์คอมมานด์ไลน์เริ่มมีความซับซ้อน ให้แยกมันออกจากฟังก์ชัน `main` ไปสร้างเป็นฟังก์ชันหรือชนิดข้อมูลต่างหาก

หน้าที่ความรับผิดชอบที่ยังคงเหลืออยู่ในฟังก์ชัน `main` หลังผ่านกระบวนการนี้ ควรจำกัดอยู่เพียงเรื่องต่อไปนี้เท่านั้น:

- การเรียกใช้ตรรกะแยกวิเคราะห์คอมมานด์ไลน์ด้วยค่าอาร์กิวเมนต์
- การตั้งค่าคอนฟิกูเรชันอื่นๆ ที่เกี่ยวข้อง
- การเรียกใช้ฟังก์ชัน `run` ใน _lib.rs_
- การจัดการข้อผิดพลาดในกรณีที่ฟังก์ชัน `run` ส่งคืนข้อผิดพลาดกลับมา

รูปแบบ (pattern) นี้คือการแยกความรับผิดชอบอย่างชัดเจน: โดย _main.rs_ จะดูแลเรื่องการเริ่มต้นสั่งทำงานโปรแกรม ส่วน _lib.rs_ จะดูแลตรรกะการทำงานทั้งหมดของโปรแกรม และเนื่องจากคุณไม่สามารถเขียนเทสต์เพื่อทดสอบฟังก์ชัน `main` ได้โดยตรง โครงสร้างนี้จึงเปิดโอกาสให้คุณสามารถทดสอบตรรกะการทำงานทั้งหมดของโปรแกรมได้อย่างทั่วถึง เพราะตรรกะเหล่านั้นถูกย้ายออกจากฟังก์ชัน `main` มาอยู่ในไลบรารีแล้ว ทำให้โค้ดที่หลงเหลืออยู่ในฟังก์ชัน `main` มีขนาดกะทัดรัดพอที่จะตรวจสอบความถูกต้องได้เพียงแค่อ่านด้วยสายตา เรามาปรับปรุงโครงสร้างโปรแกรมของเราตามขั้นตอนเหล่านี้กัน

#### การจัดกลุ่มค่าการกำหนดค่า

เราสามารถก้าวไปอีกขั้นหนึ่งเพื่อปรับปรุงฟังก์ชัน `parse_config` ให้ดียิ่งขึ้น ในขณะนี้ ฟังก์ชันของเราส่งคืนผลลัพธ์เป็นทูเพิล แต่หลังจากนั้นเรากลับแยกทูเพิลออกเป็นตัวแปรเดี่ยวๆ ในทันที ซึ่งเป็นสัญญาณที่บ่งชี้ว่าการออกแบบแอบสแทร็กชันของเราอาจยังไม่เหมาะสมที่สุด

ข้อสังเกตอีกประการหนึ่งคือ คำว่า `config` ในชื่อ `parse_config` สื่อเป็นนัยว่าค่าทั้งสองค่าที่เราส่งคืนนั้นมีความเกี่ยวข้องกันอย่างใกล้ชิด และต่างเป็นส่วนประกอบของค่าคอนฟิกูเรชันชุดเดียวกัน ทว่าในปัจจุบันโครงสร้างข้อมูลของเรายังไม่ได้สื่อความหมายนี้เลย นอกเหนือจากการรวมพวกมันไว้ในทูเพิล ดังนั้น เราจึงควรนำค่าทั้งสองมาจัดเก็บไว้ใน struct เดียวกัน พร้อมทั้งตั้งชื่อฟิลด์ของ struct ให้สื่อความหมายอย่างชัดเจน การทำเช่นนี้จะช่วยให้ผู้ที่จะเข้ามาดูแลโค้ดนี้ในอนาคตเข้าใจได้ง่ายขึ้นว่าค่าต่างๆ มีความสัมพันธ์กันอย่างไรและมีจุดประสงค์เพื่ออะไร

> นักพัฒนา Rust ส่วนใหญ่มักพยายามหลีกเลี่ยงการใช้ `clone` ในการแก้ปัญหาความเป็นเจ้าของ เนื่องจากมีต้นทุนตอนรันไทม์ ใน[บทที่ 13][ch13]<!-- ignore --> คุณจะได้เรียนรู้วิธีการที่มีประสิทธิภาพสูงกว่านี้ในการจัดการกับสถานการณ์ดังกล่าว แต่สำหรับตอนนี้ การทำสำเนาสตริงเพียงไม่กี่ตัวเพื่อช่วยให้การพัฒนาคืบหน้าต่อไปได้ถือเป็นเรื่องที่ยอมรับได้ เพราะเราทำสำเนาเพียงแค่ครั้งเดียว อีกทั้งพาธไฟล์และสตริง query ก็มีขนาดเล็กมาก การมีโปรแกรมที่ทำงานได้ถูกต้องแม้จะด้อยประสิทธิภาพไปบ้าง ย่อมดีกว่าการพยายามปรับแต่งโค้ดให้เร็วที่สุดตั้งแต่รอบแรก เมื่อคุณสั่งสมประสบการณ์กับ Rust มากขึ้น คุณจะสามารถเริ่มต้นด้วยแนวทางที่มีประสิทธิภาพสูงได้อย่างเป็นธรรมชาติ แต่ในเวลานี้ การเรียกใช้ `clone` ถือเป็นเรื่องที่ยอมรับได้อย่างสมบูรณ์

เราได้อัปเดตฟังก์ชัน `main` ให้นำอินสแตนซ์ของ `Config` ที่ส่งคืนจาก `parse_config` ไปเก็บไว้ในตัวแปรชื่อ `config` และอัปเดตโค้ดส่วนที่เคยเรียกใช้ตัวแปร `query` และ `file_path` แยกกัน ให้เปลี่ยนมาเรียกใช้ผ่านฟิลด์ของ struct `Config` แทน

ในตอนนี้ โค้ดของเราสื่อสารได้อย่างชัดเจนแล้วว่า `query` และ `file_path` มีความเกี่ยวข้องกัน และมีวัตถุประสงค์เพื่อใช้กำหนดค่าการทำงานของโปรแกรม ไม่ว่าโค้ดส่วนใดที่ต้องการใช้ค่าเหล่านี้ ก็จะทราบได้ทันทีว่าจะค้นพบมันได้ในอินสแตนซ์ `config` ภายใต้ชื่อฟิลด์ที่ตรงกับจุดประสงค์การใช้งาน

#### การสร้างคอนสตรัคเตอร์ให้ `Config`

จนถึงตอนนี้ เราได้แยกตรรกะการแยกวิเคราะห์อาร์กิวเมนต์คอมมานด์ไลน์ออกจาก `main` มาไว้ในฟังก์ชัน `parse_config` เรียบร้อยแล้ว ซึ่งช่วยให้เรามองเห็นว่าค่า `query` และ `file_path` มีความสัมพันธ์กัน และควรสะท้อนความสัมพันธ์นั้นออกมาในโค้ด จากนั้นเราได้สร้าง struct `Config` เพื่อระบุวัตถุประสงค์ร่วมกันของ `query` และ `file_path` และทำให้สามารถส่งคืนค่าเหล่านั้นในรูปของฟิลด์ภายใน struct ออกมาจากฟังก์ชัน `parse_config` ได้

ดังนั้น ในเมื่อจุดประสงค์ของฟังก์ชัน `parse_config` คือการสร้างอินสแตนซ์ของ `Config` เราจึงสามารถเปลี่ยน `parse_config` จากฟังก์ชันธรรมดาให้กลายเป็นฟังก์ชันชื่อ `new` ที่ผูกอยู่กับ struct `Config` ได้ การปรับเปลี่ยนนี้จะช่วยให้โค้ดเป็นไปตามสำนวนนิยมของ Rust มากยิ่งขึ้น เช่นเดียวกับการสร้างอินสแตนซ์ของชนิดข้อมูลในไลบรารีมาตรฐานอย่าง `String` ด้วยคำสั่ง `String::new` การเปลี่ยน `parse_config` ให้เป็นฟังก์ชัน `new` ของ `Config` ก็จะทำให้เราสามารถสร้างอินสแตนซ์ของ `Config` ได้ด้วยคำสั่ง `Config::new` ลิสติ้ง 12-7 แสดงการปรับเปลี่ยนที่เราต้องทำ

#### การคืนค่า `Result` แทนการเรียก `panic!`

เราสามารถปรับเปลี่ยนมาส่งคืนค่าชนิด `Result` ซึ่งจะบรรจุอินสแตนซ์ของ `Config` ในกรณีที่สำเร็จ และจะอธิบายสาเหตุของปัญหาในกรณีที่เกิดข้อผิดพลาด นอกจากนี้ เราจะเปลี่ยนชื่อฟังก์ชันจาก `new` เป็น `build` เนื่องจากนักพัฒนาส่วนใหญ่มักคาดหวังว่าฟังก์ชัน `new` จะต้องไม่ล้มเหลว เมื่อ `Config::build` ติดต่อสื่อสารกับ `main` เราสามารถใช้ชนิดข้อมูล `Result` เพื่อส่งสัญญาณเตือนว่าเกิดปัญหาขึ้นได้ จากนั้นเราจะปรับแก้ฟังก์ชัน `main` ให้แปลงวาเรียนต์ `Err` ออกมาเป็นข้อความแจ้งข้อผิดพลาดที่เหมาะสมกับผู้ใช้งาน โดยไม่มีข้อความรกรุงรังเกี่ยวกับ `thread 'main'` และ `RUST_BACKTRACE` ที่เกิดจากการเรียก `panic!` ติดมาด้วย

ในลิสติ้งนี้ เราได้ใช้เมธอดที่เรายังไม่ได้อธิบายอย่างละเอียด นั่นคือ `unwrap_or_else` ซึ่งถูกนิยามไว้บน `Result<T, E>` ในไลบรารีมาตรฐาน การใช้ `unwrap_or_else` ช่วยให้เราสามารถกำหนดตรรกะการจัดการข้อผิดพลาดในแบบของเราเองได้โดยไม่ต้องเกิด `panic!` หากค่า `Result` เป็น `Ok` พฤติกรรมของเมธอดนี้จะเหมือนกับ `unwrap` คือจะแกะค่าภายในที่ `Ok` ห่อหุ้มไว้ออกมาให้ แต่หากค่านั้นเป็น `Err` เมธอดนี้จะเรียกใช้โค้ดที่อยู่ใน_โคลเชอร์_ (closure) ซึ่งเป็นฟังก์ชันนิรนามที่เรานิยามและส่งเป็นอาร์กิวเมนต์ให้กับ `unwrap_or_else` เราจะได้เรียนรู้เรื่องโคลเชอร์อย่างละเอียดใน[บทที่ 13][ch13]<!-- ignore --> สำหรับตอนนี้ คุณเพียงแค่ต้องทราบว่า `unwrap_or_else` จะส่งค่าภายในของ `Err` ซึ่งในกรณีนี้คือสตริงสแตติก `"not enough arguments"` ที่เรากำหนดไว้ในลิสติ้ง 12-9 เข้ามายังโคลเชอร์ผ่านทางอาร์กิวเมนต์ `err` ที่อยู่ระหว่างเส้นแนวตั้ง ทำให้โค้ดในโคลเชอร์สามารถนำค่า `err` นี้ไปใช้งานได้

เราได้เพิ่มบรรทัด `use` ใหม่เพื่อนำเข้ามอดูล `process` จากไลบรารีมาตรฐาน โดยโค้ดในโคลเชอร์ที่จะทำงานเมื่อเกิดข้อผิดพลาดมีเพียง 2 บรรทัดเท่านั้น: บรรทัดแรกสั่งพิมพ์ค่า `err` ออกมา และบรรทัดถัดไปเรียกใช้คำสั่ง `process::exit` โดยฟังก์ชัน `process::exit` จะสั่งหยุดการทำงานของโปรแกรมในทันที และส่งคืนตัวเลขที่ระบุเป็นรหัสสถานะการออก สิ่งนี้คล้ายกับการจัดการที่ใช้ `panic!` ซึ่งเราใช้ในลิสติ้ง 12-8 แต่เราไม่ต้องเห็นเอาต์พุตเกินจำเป็นทั้งหมดอีกต่อไป มาลองกัน:

#### การคืนค่าข้อผิดพลาดจาก `run`

เมื่อตรรกะส่วนที่เหลือของโปรแกรมถูกแยกออกมาอยู่ในฟังก์ชัน `run` เรียบร้อยแล้ว เราก็สามารถปรับปรุงการจัดการข้อผิดพลาดให้ดียิ่งขึ้นได้ เช่นเดียวกับที่เราเคยทำกับ `Config::build` ในลิสติ้ง 12-9 แทนที่จะปล่อยให้โปรแกรมเกิดการแพนิกด้วยการเรียก `expect` เราจะให้ฟังก์ชัน `run` ส่งคืนค่า `Result<T, E>` เมื่อมีสิ่งใดผิดพลาด ซึ่งจะช่วยให้เราสามารถรวบรวมตรรกะการจัดการข้อผิดพลาดทั้งหมดไปไว้ที่ `main` ในรูปแบบที่เป็นมิตรต่อผู้ใช้งาน ลิสติ้ง 12-12 แสดงการเปลี่ยนแปลงที่เราต้องทำกับซิกเนเจอร์และเนื้อหาของฟังก์ชัน `run`

เราได้ทำการเปลี่ยนแปลงสำคัญ 3 ประการด้วยกัน อย่างแรก เราเปลี่ยนชนิดข้อมูลที่ส่งคืนของฟังก์ชัน `run` เป็น `Result<(), Box<dyn Error>>` โดยเดิมทีฟังก์ชันนี้ส่งคืนยูนิตไทป์ (unit type) คือ `()` และเรายังคงค่านั้นไว้เป็นค่าที่ส่งคืนในกรณีที่เป็น `Ok`

สำหรับชนิดข้อผิดพลาด เราได้ใช้เทรตออบเจกต์ (trait object) คือ `Box<dyn Error>` (และเราได้นำเข้า `std::error::Error` สู่สโคปด้วยคำสั่ง `use` ที่ด้านบน) เราจะได้เรียนรู้เรื่องเทรตออบเจกต์อย่างละเอียดใน[บทที่ 18][ch18]<!-- ignore --> สำหรับตอนนี้ ขอให้เข้าใจว่า `Box<dyn Error>` หมายความว่าฟังก์ชันจะส่งคืนชนิดข้อมูลใดๆ ก็ตามที่อิมพลีเมนต์เทรต `Error` โดยที่เราไม่ต้องเจาะจงระบุชนิดข้อมูลที่แน่นอน ซึ่งมอบความยืดหยุ่นในการส่งคืนข้อผิดพลาดที่อาจมีชนิดแตกต่างกันในแต่ละสถานการณ์ โดยคีย์เวิร์ด `dyn` ย่อมาจากคำว่า _dynamic_

ประการที่สอง เราได้ตัดการเรียกใช้ `expect` ออก แล้วแทนที่ด้วยตัวดำเนินการ `?` ตามที่เราเคยเรียนรู้ใน[บทที่ 9][ch9-question-mark]<!-- ignore --> แทนที่จะเกิด `panic!` เมื่อมีข้อผิดพลาด ตัวดำเนินการ `?` จะส่งต่อ (propagate) ค่าข้อผิดพลาดนั้นออกจากฟังก์ชันปัจจุบันเพื่อให้ฟังก์ชันผู้เรียกเป็นผู้จัดการแทน

ประการที่สาม ฟังก์ชัน `run` จะส่งคืนค่า `Ok` ในกรณีที่ทำงานสำเร็จ เนื่องจากเราได้ประกาศชนิดข้อมูลสำหรับกรณีสำเร็จในซิกเนเจอร์เป็น `()` เราจึงต้องห่อค่ายูนิตไทป์ไว้ภายใน `Ok` รูปแบบวากยสัมพันธ์ `Ok(())` นี้อาจดูแปลกตาไปบ้างในตอนแรก แต่การใช้ `()` เช่นนี้ถือเป็นสำนวนนิยมใน Rust ที่บ่งบอกว่าเราเรียกใช้ฟังก์ชัน `run` เพื่อผลข้างเคียง (side effects) เท่านั้น โดยไม่ได้ต้องการค่าผลลัพธ์ใดๆ กลับคืนมา

เราเพิ่มคำสั่ง `use minigrep::search;` เพื่อนำฟังก์ชัน `search` จากเครตไลบรารีเข้ามาสู่สโคปของเครตไบนารี จากนั้นในฟังก์ชัน `run` แทนที่เราจะพิมพ์เนื้อหาทั้งหมดของไฟล์ออกมาเฉยๆ เราจะเรียกใช้ฟังก์ชัน `search` โดยส่งค่า `config.query` และ `contents` เข้าไปเป็นอาร์กิวเมนต์ แล้วฟังก์ชัน `run` จะใช้ลูป `for` วนพิมพ์แต่ละบรรทัดที่ฟังก์ชัน `search` ส่งคืนกลับมาซึ่งตรงกับคำค้นหา นอกจากนี้ จังหวะนี้ยังเป็นโอกาสอันดีที่เราจะตัดคำสั่ง `println!` ในฟังก์ชัน `main` ที่เคยพิมพ์ค่า query และพาธไฟล์ออกไป เพื่อให้โปรแกรมของเราพิมพ์เฉพาะผลลัพธ์การค้นหาล้วนๆ (หากไม่เกิดข้อผิดพลาดใดๆ)

โปรดสังเกตว่า ฟังก์ชันค้นหาจะรวบรวมผลลัพธ์ทั้งหมดเก็บไว้ในเวกเตอร์ก่อนที่จะส่งคืนกลับมา แล้วจึงค่อยเริ่มพิมพ์ผลลัพธ์ออกมาทีละบรรทัด การอิมพลีเมนต์เช่นนี้อาจทำให้การแสดงผลลัพธ์เกิดความล่าช้าได้เมื่อค้นหาในไฟล์ขนาดใหญ่มาก เนื่องจากผลลัพธ์ไม่ได้ถูกพิมพ์ออกมาทันทีที่ตรวจพบ ซึ่งเราจะพูดถึงแนวทางแก้ไขปัญหานี้ด้วยการใช้อิเทอเรเตอร์ (iterator) ในบทที่ 13

เฮ้อ! แม้จะต้องลงแรงปรับเปลี่ยนโค้ดไปพอสมควร แต่เราก็ได้วางรากฐานอันมั่นคงไว้สำหรับก้าวต่อไปในอนาคตเรียบร้อยแล้ว ในตอนนี้การจัดการข้อผิดพลาดทำได้ง่ายขึ้นมาก โค้ดก็มีความเป็นโมดูลาร์อย่างเป็นระเบียบ และนับจากนี้เป็นต้นไป การพัฒนาเกือบทั้งหมดของเราจะทำอยู่ในไฟล์ _src/lib.rs_

มาใช้ประโยชน์จากโครงสร้างที่แยกเป็นโมดูลนี้ ทำสิ่งที่จะทำได้ยากยิ่งหากใช้โค้ดแบบเดิม แต่กลับทำได้ง่ายดายด้วยโค้ดโครงสร้างใหม่: เราจะมาเขียนชุดทดสอบกัน!
