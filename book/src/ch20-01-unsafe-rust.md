## Unsafe Rust

โค้ดทั้งหมดที่เราพูดคุยกันมาจนถึงตอนนี้มีการบังคับใช้การรับประกันความปลอดภัยของหน่วยความจำ (memory safety) ของ Rust ในตอนคอมไพล์ อย่างไรก็ตาม Rust มีภาษาที่สองซ่อนอยู่ภายในตัวมันที่ไม่บังคับใช้การรับประกันความปลอดภัยของหน่วยความจำเหล่านี้: มันเรียกว่า _unsafe Rust_ และทำงานเหมือน Rust ปกติทุกประการแต่ให้พลังพิเศษเพิ่มเติมแก่เรา

Unsafe Rust มีอยู่เพราะโดยธรรมชาติแล้ว การวิเคราะห์แบบสแตติก (static analysis) นั้นระมัดระวัง เมื่อคอมไพเลอร์พยายามตัดสินว่าโค้ดรักษาการรับประกันหรือไม่ มันยอมที่จะปฏิเสธโปรแกรมที่ถูกต้องบางโปรแกรมดีกว่าที่ยอมรับโปรแกรมที่ไม่ถูกต้องบางโปรแกรม แม้ว่าโค้ดนั้น_อาจจะ_ใช้ได้ แต่หากคอมไพเลอร์ Rust มีข้อมูลไม่พอที่จะมั่นใจ มันก็จะปฏิเสธโค้ดนั้น ในกรณีเหล่านี้ คุณสามารถใช้โค้ด unsafe เพื่อบอกคอมไพเลอร์ว่า “เชื่อผมสิ ผมรู้ว่าผมกำลังทำอะไรอยู่” แต่ขอเตือนว่า คุณใช้ unsafe Rust ด้วยความเสี่ยงของคุณเอง: หากคุณใช้โค้ด unsafe ไม่ถูกต้อง ปัญหาต่างๆ อาจเกิดขึ้นได้เนื่องจากความไม่ปลอดภัยของหน่วยความจำ เช่น การดีเรเฟอเรนซ์พอยน์เตอร์ null

อีกเหตุผลหนึ่งที่ Rust มีตัวตนอีกด้านที่เป็น unsafe ก็คือฮาร์ดแวร์คอมพิวเตอร์เองนั้นไม่ปลอดภัยโดยธรรมชาติ หาก Rust ไม่ยอมให้คุณดำเนินการที่ไม่ปลอดภัย คุณก็จะทำงานบางอย่างไม่ได้ Rust จำเป็นต้องอนุญาตให้คุณเขียนโปรแกรมระบบระดับต่ำ เช่น การโต้ตอบกับระบบปฏิบัติการโดยตรง หรือแม้แต่การเขียนระบบปฏิบัติการของคุณเอง การทำงานกับโปรแกรมระบบระดับต่ำเป็นหนึ่งในเป้าหมายของภาษา มาสำรวจกันว่าเราทำอะไรได้บ้างกับ unsafe Rust และจะทำอย่างไร

### การใช้พลังพิเศษของ unsafe

ในการสลับไปใช้ unsafe Rust ให้ใช้คำสงวน (keyword) `unsafe` แล้วเริ่มบล็อกใหม่ที่บรรจุโค้ด unsafe คุณสามารถทำการกระทำห้าอย่างใน unsafe Rust ที่คุณทำไม่ได้ใน safe Rust ซึ่งเราเรียกว่า_พลังพิเศษของ unsafe_ พลังพิเศษเหล่านั้นได้แก่ความสามารถในการ:

1. ดีเรเฟอเรนซ์พอยน์เตอร์ดิบ (raw pointer)
1. เรียกฟังก์ชันหรือเมธอด unsafe
1. เข้าถึงหรือแก้ไขตัวแปร static ที่เปลี่ยนแปลงได้
1. อิมพลีเมนต์เทรต (trait) ที่เป็น unsafe
1. เข้าถึงฟิลด์ของ `union`

สิ่งสำคัญคือต้องเข้าใจว่า `unsafe` ไม่ได้ปิดตัวตรวจการยืม (borrow checker) หรือปิดการตรวจสอบความปลอดภัยอื่นๆ ของ Rust: หากคุณใช้เรเฟอเรนซ์ (reference) ในโค้ด unsafe มันก็ยังคงถูกตรวจสอบอยู่ คำสงวน `unsafe` เพียงให้คุณเข้าถึงฟีเจอร์ทั้งห้านี้ที่จากนั้นจะไม่ถูกตรวจสอบโดยคอมไพเลอร์ในเรื่องความปลอดภัยของหน่วยความจำ คุณก็ยังได้รับความปลอดภัยในระดับหนึ่งภายในบล็อก unsafe

นอกจากนี้ `unsafe` ไม่ได้หมายความว่าโค้ดภายในบล็อกนั้นอันตรายเสมอไป หรือจะต้องมีปัญหาความปลอดภัยของหน่วยความจำอย่างแน่นอน: เจตนาก็คือ ในฐานะโปรแกรมเมอร์ คุณจะรับประกันว่าโค้ดภายในบล็อก `unsafe` จะเข้าถึงหน่วยความจำอย่างถูกต้อง

มนุษย์ย่อมผิดพลาดได้และความผิดพลาดจะเกิดขึ้น แต่การกำหนดให้การดำเนินการ unsafe ทั้งห้านี้อยู่ภายในบล็อกที่ระบุ `unsafe` ทำให้คุณรู้ว่าข้อผิดพลาดใดๆ ที่เกี่ยวกับความปลอดภัยของหน่วยความจำนั้นต้องอยู่ภายในบล็อก `unsafe` แน่นอน จงทำให้บล็อก `unsafe` มีขนาดเล็กไว้ แล้วคุณจะขอบคุณตัวเองในภายหลังเมื่อต้องสืบหาบั๊กด้านหน่วยความจำ

เพื่อแยกโค้ด unsafe ให้ได้มากที่สุด ทางที่ดีที่สุดคือล้อมโค้ดดังกล่าวไว้ในแอบสแตรกชัน (abstraction) ที่ปลอดภัยและจัดเตรียม API ที่ปลอดภัย ซึ่งเราจะพูดคุยกันต่อไปในบทนี้เมื่อเราพิจารณาฟังก์ชันและเมธอด unsafe บางส่วนของไลบรารีมาตรฐานถูกอิมพลีเมนต์เป็นแอบสแตรกชันที่ปลอดภัยครอบโค้ด unsafe ที่ผ่านการตรวจสอบแล้ว การห่อโค้ด unsafe ไว้ในแอบสแตรกชันที่ปลอดภัยช่วยป้องกันไม่ให้การใช้งาน `unsafe` รั่วไหลออกไปยังทุกที่ที่คุณหรือผู้ใช้ของคุณอาจต้องการใช้ฟังก์ชันการทำงานที่อิมพลีเมนต์ด้วยโค้ด `unsafe` เพราะการใช้แอบสแตรกชันที่ปลอดภัยนั้นปลอดภัย

มาดูพลังพิเศษของ unsafe แต่ละอย่างจากทั้งห้าตามลำดับกัน เราจะดูแอบสแตรกชันบางส่วนที่จัดเตรียมอินเทอร์เฟซที่ปลอดภัยให้กับโค้ด unsafe ด้วย

### การดีเรเฟอเรนซ์พอยน์เตอร์ดิบ

ในบทที่ 4 ในหัวข้อ[“เรเฟอเรนซ์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้ว”][dangling-references]<!-- ignore
--> เราได้กล่าวไว้ว่าคอมไพเลอร์รับประกันว่าเรเฟอเรนซ์จะใช้ได้เสมอ Unsafe Rust มีชนิดข้อมูลใหม่สองชนิดที่เรียกว่า_พอยน์เตอร์ดิบ_ ซึ่งคล้ายกับเรเฟอเรนซ์ เช่นเดียวกับเรเฟอเรนซ์ พอยน์เตอร์ดิบสามารถเป็นแบบเปลี่ยนแปลงไม่ได้หรือเปลี่ยนแปลงได้ และเขียนเป็น `*const T` และ `*mut T` ตามลำดับ เครื่องหมายดอกจันไม่ใช่ตัวดำเนินการดีเรเฟอเรนซ์ แต่เป็นส่วนหนึ่งของชื่อชนิดข้อมูล ในบริบทของพอยน์เตอร์ดิบ _เปลี่ยนแปลงไม่ได้_ (immutable) หมายความว่าพอยน์เตอร์ไม่สามารถถูกกำหนดค่าโดยตรงหลังจากการดีเรเฟอเรนซ์ได้

ต่างจากเรเฟอเรนซ์และสมาร์ตพอยน์เตอร์ (smart pointer) พอยน์เตอร์ดิบ:

- ได้รับอนุญาตให้เพิกเฉยต่อกฎการยืมได้ โดยสามารถมีทั้งพอยน์เตอร์แบบเปลี่ยนแปลงไม่ได้และแบบเปลี่ยนแปลงได้ หรือมีพอยน์เตอร์แบบเปลี่ยนแปลงได้หลายตัวชี้ไปยังตำแหน่งเดียวกัน
- ไม่ได้รับการรับประกันว่าจะชี้ไปยังหน่วยความจำที่ใช้ได้
- ได้รับอนุญาตให้เป็น null ได้
- ไม่มีการอิมพลีเมนต์การทำความสะอาดอัตโนมัติใดๆ

ด้วยการเลือกงดเว้นไม่ให้ Rust บังคับใช้การรับประกันเหล่านี้ คุณสามารถแลกความปลอดภัยที่รับประกันไว้กับประสิทธิภาพที่มากขึ้น หรือความสามารถในการเชื่อมต่อกับภาษาอื่นหรือฮาร์ดแวร์ที่การรับประกันของ Rust ใช้ไม่ได้

เราได้สร้างพอยน์เตอร์ดิบโดยใช้ตัวดำเนินการยืมแบบ raw: `&raw const num` สร้างพอยน์เตอร์ดิบแบบเปลี่ยนแปลงไม่ได้ชนิด `*const i32` และ `&raw mut num` สร้างพอยน์เตอร์ดิบแบบเปลี่ยนแปลงได้ชนิด `*mut i32` เพราะเราสร้างมันจากตัวแปรภายในเครื่องโดยตรง เราจึงรู้ว่าพอยน์เตอร์ดิบเหล่านี้ใช้ได้ แต่เราตั้งสมมติฐานเช่นนั้นกับพอยน์เตอร์ดิบตัวใดก็ได้ไม่ได้

เพื่อสาธิตสิ่งนี้ ต่อไปเราจะสร้างพอยน์เตอร์ดิบที่เรามั่นใจในความใช้ได้ของมันได้ไม่มากนัก โดยใช้คำสงวน `as` เพื่อแคสต์ค่าแทนการใช้ตัวดำเนินการยืมแบบ raw ลิสติ้ง 20-2 แสดงวิธีสร้างพอยน์เตอร์ดิบไปยังตำแหน่งใดก็ได้ในหน่วยความจำ ความพยายามใช้หน่วยความจำใดก็ได้นั้นเป็นพฤติกรรมที่ไม่ได้นิยามไว้ (undefined behavior): อาจมีข้อมูลอยู่ที่แอดเดรสนั้นหรืออาจไม่มี คอมไพเลอร์อาจปรับแต่งโค้ดจนไม่มีการเข้าถึงหน่วยความจำเลย หรือโปรแกรมอาจสิ้นสุดลงด้วยข้อผิดพลาดแบบ segmentation fault ตามปกติแล้ว ไม่มีเหตุผลที่ดีในการเขียนโค้ดแบบนี้ โดยเฉพาะในกรณีที่คุณสามารถใช้ตัวดำเนินการยืมแบบ raw แทนได้ แต่มันก็เป็นไปได้

เมื่อมีความอันตรายทั้งหมดนี้ ทำไมคุณถึงจะใช้พอยน์เตอร์ดิบเลย? กรณีการใช้งานหลักอย่างหนึ่งคือเมื่อเชื่อมต่อกับโค้ด C ดังที่คุณจะเห็นในหัวข้อถัดไป อีกกรณีหนึ่งคือเมื่อสร้างแอบสแตรกชันที่ปลอดภัยซึ่งตัวตรวจการยืมไม่เข้าใจ เราจะแนะนำฟังก์ชัน unsafe แล้วดูตัวอย่างของแอบสแตรกชันที่ปลอดภัยซึ่งใช้โค้ด unsafe

### การเรียกฟังก์ชันหรือเมธอด unsafe

การดำเนินการประเภทที่สองที่คุณทำได้ในบล็อก unsafe คือการเรียกฟังก์ชัน unsafe ฟังก์ชันและเมธอด unsafe มีหน้าตาเหมือนฟังก์ชันและเมธอดปกติทุกประการ แต่มี `unsafe` เพิ่มมาข้างหน้านิยามส่วนที่เหลือ คำสงวน `unsafe` ในบริบทนี้บ่งบอกว่าฟังก์ชันนี้มีข้อกำหนดที่เราต้องรักษาเมื่อเราเรียกฟังก์ชันนี้ เพราะ Rust ไม่สามารถรับประกันได้ว่าเราได้ทำตามข้อกำหนดเหล่านี้แล้ว การเรียกฟังก์ชัน unsafe ภายในบล็อก `unsafe` เท่ากับเรากำลังบอกว่าเราได้อ่านเอกสารของฟังก์ชันนี้แล้ว และเรารับผิดชอบในการรักษาสัญญาของฟังก์ชันนี้

ในการดำเนินการ unsafe ในบอดี้ของฟังก์ชัน `unsafe` คุณยังต้องใช้บล็อก `unsafe` เช่นเดียวกับในฟังก์ชันปกติ และคอมไพเลอร์จะเตือนคุณหากคุณลืม สิ่งนี้ช่วยให้เรารักษาบล็อก `unsafe` ให้เล็กที่สุดเท่าที่จะเป็นไปได้ เนื่องจากการดำเนินการ unsafe นั้นอาจไม่จำเป็นต้องใช้ทั่วทั้งบอดี้ของฟังก์ชัน

ย้อนนึกจากหัวข้อ[“ชนิดสไลซ์”][the-slice-type]<!-- ignore --> ในบทที่ 4 ว่าสไลซ์คือพอยน์เตอร์ไปยังข้อมูลบางส่วนและความยาวของสไลซ์ เราใช้เมธอด `len` เพื่อหาความยาวของสไลซ์ และเมธอด `as_mut_ptr` เพื่อเข้าถึงพอยน์เตอร์ดิบของสไลซ์ ในกรณีนี้ เพราะเรามีสไลซ์แบบเปลี่ยนแปลงได้ไปยังค่า `i32` `as_mut_ptr` จึงคืนพอยน์เตอร์ดิบที่มีชนิด `*mut i32` ซึ่งเราได้เก็บไว้ในตัวแปร `ptr`

เราคงการยืนยันว่าดัชนี `mid` อยู่ภายในสไลซ์ไว้ จากนั้นเราก็มาถึงโค้ด unsafe: ฟังก์ชัน `slice::from_raw_parts_mut` รับพอยน์เตอร์ดิบและความยาว แล้วสร้างสไลซ์ขึ้นมา เราใช้ฟังก์ชันนี้สร้างสไลซ์ที่เริ่มจาก `ptr` และมีความยาว `mid` รายการ จากนั้น เราเรียกเมธอด `add` บน `ptr` โดยส่ง `mid` เป็นอาร์กิวเมนต์ เพื่อให้ได้พอยน์เตอร์ดิบที่เริ่มที่ `mid` และเราสร้างสไลซ์โดยใช้พอยน์เตอร์นั้นกับจำนวนรายการที่เหลือหลัง `mid` เป็นความยาว

ฟังก์ชัน `slice::from_raw_parts_mut` เป็น unsafe เพราะมันรับพอยน์เตอร์ดิบและต้องเชื่อว่าพอยน์เตอร์นี้ใช้ได้ เมธอด `add` บนพอยน์เตอร์ดิบก็เป็น unsafe เช่นกัน เพราะมันต้องเชื่อว่าตำแหน่งที่บวกเพิ่มไปนั้นเป็นพอยน์เตอร์ที่ใช้ได้ด้วย ดังนั้น เราจึงต้องใส่บล็อก `unsafe` ครอบการเรียก `slice::from_raw_parts_mut` และ `add` ของเราเพื่อให้เรียกพวกมันได้ ด้วยการดูโค้ดและด้วยการเพิ่มการยืนยันว่า `mid` ต้องน้อยกว่าหรือเท่ากับ `len` เราจึงบอกได้ว่าพอยน์เตอร์ดิบทั้งหมดที่ใช้ภายในบล็อก `unsafe` จะเป็นพอยน์เตอร์ที่ใช้ได้ซึ่งชี้ไปยังข้อมูลภายในสไลซ์ นี่เป็นการใช้ `unsafe` ที่ยอมรับได้และเหมาะสม

โปรดสังเกตว่าเราไม่จำเป็นต้องทำเครื่องหมายฟังก์ชัน `split_at_mut` ที่ได้ว่าเป็น `unsafe` และเราสามารถเรียกฟังก์ชันนี้จาก safe Rust ได้ เราได้สร้างแอบสแตรกชันที่ปลอดภัยให้กับโค้ด unsafe ด้วยการอิมพลีเมนต์ฟังก์ชันที่ใช้โค้ด `unsafe` อย่างปลอดภัย เพราะมันสร้างเฉพาะพอยน์เตอร์ที่ใช้ได้จากข้อมูลที่ฟังก์ชันนี้เข้าถึงได้

#### การใช้ฟังก์ชัน `extern` เพื่อเรียกโค้ดภายนอก

บางครั้งโค้ด Rust ของคุณอาจจำเป็นต้องโต้ตอบกับโค้ดที่เขียนด้วยภาษาอื่น ด้วยเหตุนี้ Rust จึงมีคำสงวน `extern` ที่อำนวยความสะดวกในการสร้างและใช้งาน_ส่วนติดต่อกับภาษาอื่น (foreign function interface หรือ FFI)_ ซึ่งเป็นวิธีที่ภาษาโปรแกรมหนึ่งนิยามฟังก์ชันและเปิดให้ภาษาโปรแกรมอื่น (ภาษาต่างถิ่น) เรียกฟังก์ชันเหล่านั้นได้

ลิสติ้ง 20-8 สาธิตวิธีตั้งค่าการเชื่อมต่อกับฟังก์ชัน `abs` จากไลบรารีมาตรฐานของ C ฟังก์ชันที่ประกาศภายในบล็อก `extern` โดยทั่วไปแล้วเป็น unsafe เมื่อเรียกจากโค้ด Rust ดังนั้นบล็อก `extern` จึงต้องถูกทำเครื่องหมาย `unsafe` ด้วย เหตุผลก็คือภาษาอื่นไม่ได้บังคับใช้กฎและการรับประกันของ Rust และ Rust ก็ไม่สามารถตรวจสอบได้ ความรับผิดชอบจึงตกอยู่กับโปรแกรมเมอร์ในการรับประกันความปลอดภัย

#### การเรียกฟังก์ชัน Rust จากภาษาอื่น

เรายังสามารถใช้ `extern` เพื่อสร้างอินเทอร์เฟซที่เปิดให้ภาษาอื่นเรียกฟังก์ชัน Rust ได้ด้วย แทนที่จะสร้างบล็อก `extern` ทั้งบล็อก เราก็เติมคำสงวน `extern` และระบุ ABI ที่จะใช้ไว้ข้างหน้าคำสงวน `fn` ของฟังก์ชันที่เกี่ยวข้อง นอกจากนี้เรายังต้องเติมแอตทริบิวต์ (attribute) `#[unsafe(no_mangle)]` เพื่อบอกคอมไพเลอร์ Rust ไม่ให้ทำ name mangling กับชื่อฟังก์ชันนี้ _การทำ mangling_ คือเวลาที่คอมไพเลอร์เปลี่ยนชื่อที่เราให้ไว้กับฟังก์ชันให้เป็นชื่ออื่นซึ่งมีข้อมูลเพิ่มเติมไว้ให้ส่วนอื่นๆ ของกระบวนการคอมไพล์ใช้งาน แต่เป็นชื่อที่มนุษย์อ่านได้ยากขึ้น คอมไพเลอร์ของทุกภาษาการเขียนโปรแกรมทำ mangling ชื่อแตกต่างกันเล็กน้อย ดังนั้นเพื่อให้ฟังก์ชัน Rust สามารถถูกเรียกชื่อได้โดยภาษาอื่น เราจึงต้องปิดการทำ name mangling ของคอมไพเลอร์ Rust สิ่งนี้เป็น unsafe เพราะอาจเกิดการชนกันของชื่อข้ามไลบรารีได้หากไม่มีการทำ mangling ในตัว เราจึงต้องรับผิดชอบให้แน่ใจว่าชื่อที่เราเลือกนั้นปลอดภัยที่จะเอ็กซ์พอร์ตโดยไม่ทำ mangling

ในตัวอย่างต่อไปนี้ เราทำให้ฟังก์ชัน `call_from_c` เข้าถึงได้จากโค้ด C หลังจากที่มันถูกคอมไพล์เป็นไลบรารีแชร์และลิงก์จาก C แล้ว:

```
#[unsafe(no_mangle)]
pub extern "C" fn call_from_c() {
    println!("Just called a Rust function from C!");
}
```

การใช้ `extern` เช่นนี้ต้องมี `unsafe` เฉพาะในแอตทริบิวต์เท่านั้น ไม่ใช่บนบล็อก `extern`

### การเข้าถึงหรือแก้ไขตัวแปร static ที่เปลี่ยนแปลงได้

เช่นเดียวกับตัวแปรปกติ เราระบุความสามารถในการเปลี่ยนแปลงค่า (mutability) โดยใช้คำสงวน `mut` โค้ดใดก็ตามที่อ่านหรือเขียน `COUNTER` ต้องอยู่ภายในบล็อก `unsafe` โค้ดในลิสติ้ง 20-11 คอมไพล์ผ่านและพิมพ์ `COUNTER: 3` ตามที่เราคาดไว้ เพราะมันทำงานบนเธรดเดียว การให้หลายเธรดเข้าถึง `COUNTER` น่าจะส่งผลให้เกิด data race ดังนั้นมันจึงเป็นพฤติกรรมที่ไม่ได้นิยามไว้ ดังนั้น เราจึงต้องทำเครื่องหมายทั้งฟังก์ชันว่า `unsafe` และจัดทำเอกสารข้อจำกัดด้านความปลอดภัยไว้ เพื่อให้ใครก็ตามที่เรียกฟังก์ชันนี้รู้ว่าตนได้รับอนุญาตและไม่ได้รับอนุญาตให้ทำอะไรได้อย่างปลอดภัยบ้าง

เมื่อใดก็ตามที่เราเขียนฟังก์ชัน unsafe ถือเป็นสำนวนปฏิบัติ (idiomatic) ที่จะเขียนคอมเมนต์ที่ขึ้นต้นด้วย `SAFETY` และอธิบายว่าผู้เรียกต้องทำอะไรจึงจะเรียกฟังก์ชันนี้ได้อย่างปลอดภัย ในทำนองเดียวกัน เมื่อใดก็ตามที่เราดำเนินการ unsafe ถือเป็นสำนวนปฏิบัติที่จะเขียนคอมเมนต์ที่ขึ้นต้นด้วย `SAFETY` เพื่ออธิบายว่ากฎความปลอดภัยต่างๆ ถูกปฏิบัติตามอย่างไร

นอกจากนี้ คอมไพเลอร์จะปฏิเสธโดยค่าเริ่มต้นต่อความพยายามใดๆ ที่จะสร้างเรเฟอเรนซ์ไปยังตัวแปร static แบบเปลี่ยนแปลงได้ ผ่าน lint ของคอมไพเลอร์ คุณต้องเลือกปิดการป้องกันของ lint นั้นอย่างชัดแจ้งโดยการเพิ่มแอตทริบิวต์ `#[allow(static_mut_refs)]` หรือเข้าถึงตัวแปร static แบบเปลี่ยนแปลงได้ผ่านพอยน์เตอร์ดิบที่สร้างด้วยตัวดำเนินการยืมแบบ raw ตัวใดตัวหนึ่ง ซึ่งรวมถึงกรณีที่เรเฟอเรนซ์ถูกสร้างขึ้นแบบมองไม่เห็น เช่นเมื่อมันถูกใช้ใน `println!` ในลิสติ้งโค้ดนี้ การกำหนดให้เรเฟอเรนซ์ไปยังตัวแปร static แบบเปลี่ยนแปลงได้ต้องถูกสร้างผ่านพอยน์เตอร์ดิบช่วยทำให้ข้อกำหนดด้านความปลอดภัยในการใช้ตัวแปรเหล่านี้ชัดเจนยิ่งขึ้น

เมื่อข้อมูลแบบเปลี่ยนแปลงได้นั้นเข้าถึงได้จากทั่วทั้งโปรแกรม เป็นการยากที่จะรับประกันได้ว่าไม่มี data race ซึ่งเป็นเหตุผลที่ Rust มองว่าตัวแปร static แบบเปลี่ยนแปลงได้เป็น unsafe เมื่อทำได้ ควรใช้เทคนิคการทำงานพร้อมกัน (concurrency) และสมาร์ตพอยน์เตอร์ที่ปลอดภัยต่อเธรดซึ่งเราได้พูดคุยกันในบทที่ 16 แทน เพื่อให้คอมไพเลอร์ตรวจสอบว่าการเข้าถึงข้อมูลจากเธรดต่างๆ ถูกทำอย่างปลอดภัย

### การอิมพลีเมนต์เทรต unsafe

เราใช้ `unsafe` เพื่ออิมพลีเมนต์เทรต unsafe ได้ เทรตหนึ่งจะเป็น unsafe เมื่อเมธอดอย่างน้อยหนึ่งตัวของมันมีเงื่อนไขคงที่ (invariant) บางอย่างที่คอมไพเลอร์ตรวจสอบไม่ได้ เราประกาศว่าเทรตหนึ่งเป็น `unsafe` โดยเติมคำสงวน `unsafe` ไว้หน้า `trait` และทำเครื่องหมายการอิมพลีเมนต์เทรตนั้นว่าเป็น `unsafe` ด้วย ดังที่แสดงในลิสติ้ง 20-12

ตัวอย่างเช่น ย้อนนึกถึงเทรตมาร์กเกอร์ (marker trait) `Send` และ `Sync` ที่เราได้พูดคุยกันในหัวข้อ[“การทำงานพร้อมกันแบบขยายได้ด้วย `Send` และ `Sync`”][send-and-sync]<!-- ignore --> ในบทที่ 16: คอมไพเลอร์อิมพลีเมนต์เทรตเหล่านี้โดยอัตโนมัติหากชนิดข้อมูลของเราประกอบขึ้นจากชนิดข้อมูลอื่นที่อิมพลีเมนต์ `Send` และ `Sync` ทั้งหมด หากเราอิมพลีเมนต์ชนิดข้อมูลที่มีชนิดข้อมูลซึ่งไม่อิมพลีเมนต์ `Send` หรือ `Sync` อยู่ภายใน เช่นพอยน์เตอร์ดิบ และเราต้องการทำเครื่องหมายชนิดข้อมูลนั้นว่าเป็น `Send` หรือ `Sync` เราต้องใช้ `unsafe` Rust ตรวจสอบไม่ได้ว่าชนิดข้อมูลของเรารักษาการรับประกันว่ามันสามารถถูกส่งข้ามเธรดหรือเข้าถึงจากหลายเธรดได้อย่างปลอดภัย ดังนั้น เราจึงต้องทำการตรวจสอบเหล่านั้นด้วยตัวเองและบ่งชี้เช่นนั้นด้วย `unsafe`

### การเข้าถึงฟิลด์ของ union

การกระทำสุดท้ายที่ใช้ได้เฉพาะกับ `unsafe` คือการเข้าถึงฟิลด์ของ union *union* นั้นคล้ายกับ `struct` แต่มีเพียงฟิลด์ที่ประกาศไว้ฟิลด์เดียวเท่านั้นที่ถูกใช้ในอินสแตนซ์หนึ่งๆ ในเวลาใดเวลาหนึ่ง union ถูกใช้เป็นหลักเพื่อเชื่อมต่อกับ union ในโค้ด C การเข้าถึงฟิลด์ของ union เป็น unsafe เพราะ Rust ไม่สามารถรับประกันชนิดข้อมูลของข้อมูลที่กำลังถูกจัดเก็บอยู่ในอินสแตนซ์ของ union ได้ คุณสามารถเรียนรู้เพิ่มเติมเกี่ยวกับ union ได้ใน[Rust Reference][unions]

### การใช้ Miri เพื่อตรวจสอบโค้ด unsafe

เมื่อเขียนโค้ด unsafe คุณอาจต้องการตรวจสอบว่าโค้ดที่คุณเขียนนั้นปลอดภัยและถูกต้องจริง วิธีที่ดีที่สุดวิธีหนึ่งคือการใช้ Miri ซึ่งเป็นเครื่องมืออย่างเป็นทางการของ Rust สำหรับตรวจจับพฤติกรรมที่ไม่ได้นิยามไว้ ในขณะที่ตัวตรวจการยืมเป็นเครื่องมือแบบ_สแตติก_ที่ทำงานตอนคอมไพล์ Miri เป็นเครื่องมือแบบ_ไดนามิก_ที่ทำงานตอนรันไทม์ มันตรวจสอบโค้ดของคุณโดยรันโปรแกรมของคุณหรือชุดการทดสอบของโปรแกรม และตรวจจับเมื่อคุณละเมิดกฎที่มันเข้าใจเกี่ยวกับวิธีการทำงานของ Rust

การใช้ Miri ต้องใช้ Rust บิลด์ nightly (ซึ่งเราพูดถึงเพิ่มเติมใน[ภาคผนวก G: วิธีการสร้าง Rust และ “Nightly Rust”][nightly]<!-- ignore -->) คุณสามารถติดตั้งทั้ง Rust เวอร์ชัน nightly และเครื่องมือ Miri ได้โดยพิมพ์ `rustup +nightly component add miri` สิ่งนี้ไม่เปลี่ยนว่าโปรเจกต์ของคุณใช้ Rust เวอร์ชันใด มันเพียงเพิ่มเครื่องมือนี้ลงในระบบของคุณเพื่อให้คุณใช้ได้เมื่อต้องการ คุณสามารถรัน Miri บนโปรเจกต์ได้โดยพิมพ์ `cargo +nightly miri run` หรือ `cargo +nightly miri test`


Miri เตือนเราอย่างถูกต้องว่าเรากำลังแคสต์จำนวนเต็มให้เป็นพอยน์เตอร์ ซึ่งอาจเป็นปัญหาได้ แต่ Miri ไม่สามารถระบุได้ว่ามีปัญหาอยู่จริงหรือไม่ เพราะมันไม่รู้ว่าพอยน์เตอร์นั้นถือกำเนิดมาอย่างไร จากนั้น Miri คืนข้อผิดพลาดตรงที่ลิสติ้ง 20-7 มีพฤติกรรมที่ไม่ได้นิยามไว้ เพราะเรามีพอยน์เตอร์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้ว (dangling pointer) ต้องขอบคุณ Miri ตอนนี้เราจึงรู้ว่ามีความเสี่ยงที่จะเกิดพฤติกรรมที่ไม่ได้นิยามไว้ และเราสามารถคิดหาวิธีทำให้โค้ดปลอดภัยได้ ในบางกรณี Miri ยังสามารถให้คำแนะนำเกี่ยวกับวิธีแก้ไขข้อผิดพลาดได้ด้วย

Miri ไม่ได้จับทุกอย่างที่คุณอาจทำผิดพลาดได้เมื่อเขียนโค้ด unsafe Miri เป็นเครื่องมือวิเคราะห์แบบไดนามิก ดังนั้นมันจึงจับปัญหาได้เฉพาะกับโค้ดที่ถูกเรียกใช้งานจริงเท่านั้น นั่นหมายความว่าคุณจะต้องใช้มันควบคู่กับเทคนิคการทดสอบที่ดีเพื่อเพิ่มความมั่นใจในโค้ด unsafe ที่คุณเขียนขึ้น นอกจากนี้ Miri ยังไม่ครอบคลุมทุกวิธีที่โค้ดของคุณอาจไม่ถูกต้องสมบูรณ์ (unsound) ได้

พูดอีกนัยหนึ่ง: หาก Miri จับปัญหา_ได้_ คุณก็รู้ว่ามีบั๊กอยู่ แต่การที่ Miri จับบั๊ก_ไม่ได้_ไม่ได้หมายความว่าไม่มีปัญหา แม้ว่ามันจะจับได้มากก็ตาม ลองรันมันกับตัวอย่างโค้ด unsafe อื่นๆ ในบทนี้ แล้วดูว่ามันพูดว่าอะไร!

<a id="when-to-use-unsafe-code"></a>

### การใช้โค้ด unsafe อย่างถูกต้อง

การใช้ `unsafe` เพื่อใช้พลังพิเศษอย่างหนึ่งจากทั้งห้าที่เพิ่งพูดคุยกันไปนั้นไม่ใช่เรื่องผิดหรือน่าตำหนิด้วยซ้ำ แต่การทำให้โค้ด `unsafe` ถูกต้องนั้นยากกว่า เพราะคอมไพเลอร์ช่วยรักษาความปลอดภัยของหน่วยความจำให้ไม่ได้ เมื่อคุณมีเหตุผลที่จะใช้โค้ด `unsafe` คุณก็ทำได้ และการมีคำอธิบายประกอบ `unsafe` อย่างชัดแจ้งช่วยให้ตามหาต้นตอของปัญหาได้ง่ายขึ้นเมื่อปัญหาเกิดขึ้น เมื่อใดก็ตามที่คุณเขียนโค้ด unsafe คุณสามารถใช้ Miri ช่วยให้คุณมั่นใจมากขึ้นว่าโค้ดที่คุณเขียนนั้นรักษากฎของ Rust

สำหรับการสำรวจเชิงลึกมากกว่านี้เกี่ยวกับวิธีทำงานกับ unsafe Rust อย่างมีประสิทธิภาพ โปรดอ่านคู่มืออย่างเป็นทางการของ Rust สำหรับ `unsafe` คือ[“The Rustonomicon”][nomicon]
