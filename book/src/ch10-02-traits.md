## นิยามพฤติกรรมร่วมด้วยเทรต

*เทรต (trait)* ทำหน้าที่กำหนดฟังก์ชันการทำงานที่ประเภทข้อมูลหนึ่งๆ มีและสามารถนำไปแบ่งปันให้กับประเภทข้อมูลอื่นๆ ได้ เราสามารถนำเทรตมาใช้ในการนิยามพฤติกรรมร่วม (shared behavior) ในเชิงนามธรรม และสามารถใช้ *บาวด์ของเทรต (trait bounds)* เพื่อระบุว่าประเภทข้อมูลแบบเจเนอริกจะเป็นประเภทใดก็ได้ที่มีพฤติกรรมตามที่กำหนด

> หมายเหตุ: เทรตมีความคล้ายคลึงกับฟีเจอร์ที่ภาษาโปรแกรมอื่นๆ มักเรียกว่า *อินเทอร์เฟซ (interface)* แม้ว่าจะมีรายละเอียดปลีกย่อยที่แตกต่างกันอยู่บ้างก็ตาม

### การนิยามเทรต

พฤติกรรมของประเภทข้อมูลประกอบไปด้วยเมธอดต่างๆ ที่เราสามารถเรียกใช้งานบนประเภทข้อมูลนั้นได้ และประเภทข้อมูลที่แตกต่างกันจะถือว่ามีพฤติกรรมร่วมกัน หากเราสามารถเรียกใช้เมธอดเดียวกันบนประเภทข้อมูลเหล่านั้นได้ทั้งหมด การนิยามเทรตจึงเป็นเสมือนการจัดกลุ่มลายเซ็นของเมธอด (method signatures) เข้าไว้ด้วยกัน เพื่อกำหนดชุดของพฤติกรรมที่จำเป็นต่อการบรรลุเป้าหมายอย่างใดอย่างหนึ่ง

ตัวอย่างเช่น สมมติว่าเรามี struct หลายตัวที่เก็บข้อความประเภทและปริมาณที่แตกต่างกัน: struct `NewsArticle` ใช้เก็บข่าวสารที่รายงานมาจากสถานที่ใดที่หนึ่ง และ `SocialPost` ใช้เก็บข้อความความยาวไม่เกิน 280 ตัวอักษร พร้อมกับข้อมูลเมทาดาตาที่ระบุว่าเป็นโพสต์ใหม่, รีโพสต์ หรือเป็นการตอบกลับโพสต์อื่น

เราต้องการสร้างเครตไลบรารีรวบรวมสื่อชื่อ `aggregator` ที่สามารถแสดงบทสรุปข้อมูลของสิ่งที่จัดเก็บอยู่ในอินสแตนซ์ของ `NewsArticle` หรือ `SocialPost` ได้ ในการทำเช่นนี้ เราจำเป็นต้องดึงบทสรุปออกมาจากแต่ละประเภทข้อมูล โดยการเรียกใช้เมธอด `summarize` บนอินสแตนซ์นั้นๆ ลิสติ้ง 10-12 แสดงการนิยามเทรตสาธารณะ (public trait) ชื่อ `Summary` ที่ทำหน้าที่กำหนดพฤติกรรมนี้

ในตัวอย่างนี้ เราประกาศเทรตโดยใช้คีย์เวิร์ด `trait` ตามด้วยชื่อของเทรต ซึ่งในที่นี้คือ `Summary` นอกจากนี้เรายังประกาศให้เทรตนี้เป็น `pub` เพื่อให้เครตอื่นที่นำเครตนี้ไปใช้เป็น dependency สามารถนำเทรตนี้ไปใช้งานต่อได้ด้วย ดังที่เราจะได้เห็นในตัวอย่างถัดไป ภายในวงเล็บปีกกา เราจะประกาศลายเซ็นของเมธอดที่อธิบายพฤติกรรมของประเภทข้อมูลที่อิมพลีเมนต์เทรตนี้ ซึ่งในที่นี้คือ `fn summarize(&self) -> String`

สังเกตว่าต่อท้ายลายเซ็นของเมธอด แทนที่เราจะใส่วงเล็บปีกกาเพื่อเขียนโค้ดการทำงาน เรากลับลงท้ายด้วยเครื่องหมายเซมิโคลอน (;) แทน นั่นเพราะประเภทข้อมูลแต่ละประเภทที่อิมพลีเมนต์เทรตนี้จะต้องเป็นผู้กำหนดพฤติกรรมเฉพาะของตนเองลงในเนื้อหาของเมธอด โดยคอมไพเลอร์จะคอยบังคับว่า ประเภทข้อมูลใดก็ตามที่ระบุว่าตนเองมีเทรต `Summary` จะต้องมีเมธอด `summarize` ที่มีลายเซ็นตรงตามนี้ทุกประการ

เทรตหนึ่งๆ สามารถบรรจุเมธอดไว้ภายในได้หลายเมธอด โดยระบุลายเซ็นของแต่ละเมธอดไว้บรรทัดละหนึ่งอัน และลงท้ายแต่ละบรรทัดด้วยเซมิโคลอน

### การอิมพลีเมนต์เทรตบนชนิดข้อมูล

เมื่อเราได้นิยามลายเซ็นของเมธอดที่ต้องการในเทรต `Summary` เรียบร้อยแล้ว เราก็สามารถนำมันไปอิมพลีเมนต์ให้กับประเภทข้อมูลต่างๆ ในไลบรารีรวบรวมสื่อของเราได้ ลิสติ้ง 10-13 แสดงการอิมพลีเมนต์เทรต `Summary` ให้กับ struct `NewsArticle` โดยนำพาดหัวข่าว, ผู้เขียน และสถานที่มารวมกันเป็นข้อความสรุปของ `summarize` ส่วนสำหรับ struct `SocialPost` เรานิยาม `summarize` ให้ส่งคืนชื่อผู้ใช้ตามด้วยข้อความทั้งหมดของโพสต์ โดยถือว่าเนื้อหาของโพสต์ถูกจำกัดไว้ที่ไม่เกิน 280 ตัวอักษรอยู่แล้ว

การอิมพลีเมนต์เทรตให้กับประเภทข้อมูลจะคล้ายคลึงกับการเขียนเมธอดทั่วไปเป็นส่วนใหญ่ จุดที่แตกต่างคือ หลังคำสั่ง `impl` เราจะระบุชื่อเทรตที่ต้องการอิมพลีเมนต์ ตามด้วยคีย์เวิร์ด `for` แล้วจึงตามด้วยชื่อของประเภทข้อมูลที่เราต้องการอิมพลีเมนต์เทรตให้ และภายในบล็อก `impl` เราจะใส่ลายเซ็นของเมธอดตามที่เทรตได้กำหนดไว้ แต่แทนที่จะลงท้ายด้วยเซมิโคลอน เราจะเปิดวงเล็บปีกกาแล้วเขียนเนื้อหาของเมธอดเพื่อกำหนดพฤติกรรมเฉพาะของประเภทข้อมูลนั้นๆ ลงไป

หลังจากที่ไลบรารีได้อิมพลีเมนต์เทรต `Summary` ให้กับ `NewsArticle` และ `SocialPost` เรียบร้อยแล้ว ผู้ใช้งานเครตนี้ก็จะสามารถเรียกใช้เมธอดของเทรตบนอินสแตนซ์ของ `NewsArticle` และ `SocialPost` ได้เฉกเช่นเดียวกับการเรียกใช้เมธอดทั่วไป ข้อแตกต่างเพียงอย่างเดียวคือ ผู้ใช้จำเป็นต้อง `use` ดึงตัวเทรตเข้าสู่ขอบเขต (scope) ร่วมกับประเภทข้อมูลด้วย นี่คือตัวอย่างการใช้งานเครตไลบรารี `aggregator` จากเครตไบนารีภายนอก:

เครตอื่นๆ ที่ดึงเครต `aggregator` ไปเป็น dependency ก็สามารถนำเทรต `Summary` เข้าสู่สโคปเพื่อนำไปอิมพลีเมนต์ให้กับประเภทข้อมูลของพวกเขาเองได้เช่นกัน แต่มีข้อจำกัดสำคัญประการหนึ่งที่ต้องรู้ นั่นคือ เราจะสามารถอิมพลีเมนต์เทรตให้กับประเภทข้อมูลใดๆ ได้ก็ต่อเมื่อ *เทรต หรือ ประเภทข้อมูลนั้น (อย่างใดอย่างหนึ่ง หรือทั้งคู่) ต้องเป็นของเครตเราเอง (local)* ตัวอย่างเช่น เราสามารถอิมพลีเมนต์เทรตของไลบรารีมาตรฐานอย่าง `Display` ให้กับประเภทข้อมูลที่เราสร้างขึ้นเองอย่าง `SocialPost` ได้ เพราะ `SocialPost` เป็นประเภทข้อมูลที่อยู่ในเครต `aggregator` ของเรา หรือในทางกลับกัน เราก็สามารถอิมพลีเมนต์ `Summary` ให้กับ `Vec<T>` ในเครต `aggregator` ของเราได้ เพราะเทรต `Summary` เป็นของเครตเรา

ทว่า เราไม่สามารถอิมพลีเมนต์เทรตภายนอกให้กับประเภทข้อมูลภายนอกได้ เช่น เราไม่สามารถอิมพลีเมนต์เทรต `Display` ให้กับ `Vec<T>` ภายในเครต `aggregator` ของเราได้ เพราะทั้ง `Display` และ `Vec<T>` ต่างก็ถูกนิยามขึ้นในไลบรารีมาตรฐาน และไม่ได้เป็นของเครต `aggregator` เลย ข้อจำกัดนี้เป็นส่วนหนึ่งของคุณสมบัติที่เรียกว่า *ความสอดคล้อง (coherence)* หรือที่รู้จักกันอย่างเจาะจงว่า *กฎเด็กกำพร้า (orphan rule)* ซึ่งตั้งชื่อตามลักษณะที่ประเภทข้อมูลต้นกำเนิดไม่ได้อยู่ร่วมด้วย กฎนี้ช่วยรับประกันได้ว่า โค้ดของคนอื่นจะไม่สามารถทำให้โค้ดของคุณพัง และโค้ดของคุณก็จะไม่ไปทำให้โค้ดของคนอื่นพังเช่นกัน เพราะหากไม่มีกฎนี้ เครตสองเครตอาจจะต่างคนต่างอิมพลีเมนต์เทรตเดียวกันให้กับประเภทข้อมูลเดียวกัน จนทำให้ Rust สับสนและไม่รู้ว่าจะเลือกใช้การอิมพลีเมนต์ของใคร

### การใช้การอิมพลีเมนต์ค่าเริ่มต้น

ในบางสถานการณ์ การกำหนดพฤติกรรมเริ่มต้น (default behavior) ให้กับบางเมธอดหรือทุกเมธอดในเทรตก็มีประโยชน์อย่างมาก แทนที่จะต้องบังคับให้ทุกประเภทข้อมูลต้องมานั่งเขียนโค้ดอิมพลีเมนต์ทุกเมธอดใหม่ทั้งหมด จากนั้นเมื่อเรานำเทรตไปอิมพลีเมนต์ให้กับประเภทข้อมูลใด เราจะเลือกคงพฤติกรรมเริ่มต้นนั้นไว้ หรือจะเขียนทับ (override) พฤติกรรมเริ่มต้นของแต่ละเมธอดก็ได้

#### ไวยากรณ์บาวด์ของเทรต

ไวยากรณ์ `impl Trait` นั้นเหมาะกับกรณีที่ตรงไปตรงมา แต่ในความเป็นจริงแล้ว มันคือไวยากรณ์แบบย่อ (syntax sugar) ของรูปแบบที่ยาวกว่าซึ่งเรียกว่า *บาวด์ของเทรต (trait bound)* โดยมีหน้าตาดังนี้:

```rust,ignore
pub fn notify<T: Summary>(item: &T) {
    println!("Breaking news! {}", item.summarize());
}
```

รูปแบบที่ยาวกว่านี้ให้ผลลัพธ์เทียบเท่ากับตัวอย่างในหัวข้อก่อนหน้าทุกประการ เพียงแต่มีความยาวกว่า โดยเราจะวางบาวด์ของเทรตไว้ร่วมกับการประกาศพารามิเตอร์ประเภทข้อมูลเจเนอริก ต่อท้ายเครื่องหมายโคลอน (:) ภายในวงเล็บสามเหลี่ยม

ไวยากรณ์ `impl Trait` ให้ความสะดวกและช่วยให้โค้ดดูกระชับในกรณีง่ายๆ ทว่าไวยากรณ์บาวด์ของเทรตแบบเต็มรูปจะสามารถแสดงความซับซ้อนได้มากกว่าในกรณีอื่นๆ ตัวอย่างเช่น สมมติว่าเรามีสองพารามิเตอร์ที่อิมพลีเมนต์เทรต `Summary` หากเขียนด้วยไวยากรณ์ `impl Trait` จะเป็นดังนี้:

```rust,ignore
pub fn notify(item1: &impl Summary, item2: &impl Summary) {
```

การใช้ `impl Trait` เช่นนี้เหมาะสมหากเราต้องการให้ฟังก์ชันเปิดให้ `item1` และ `item2` เป็นประเภทข้อมูลที่ต่างกันได้ (ตราบใดที่ทั้งคู่ต่างก็อิมพลีเมนต์ `Summary`) แต่หากเราต้องการบังคับให้พารามิเตอร์ทั้งสองต้องเป็นประเภทข้อมูลเดียวกันเสมอ เราจำเป็นต้องใช้บาวด์ของเทรต ดังนี้:

```rust,ignore
pub fn notify<T: Summary>(item1: &T, item2: &T) {
```

การระบุประเภทเจเนอริก `T` ให้เป็นประเภทของทั้งพารามิเตอร์ `item1` และ `item2` จะเป็นการกำหนดข้อจำกัดให้กับฟังก์ชันว่า ค่ารูปธรรมที่ส่งเข้ามาเป็นอาร์กิวเมนต์ของ `item1` และ `item2` จะต้องเป็นประเภทเดียวกันเท่านั้น

#### บาวด์ของเทรตหลายตัวด้วยไวยากรณ์ `+`

เรายังสามารถกำหนดบาวด์ของเทรตมากกว่าหนึ่งตัวได้ด้วย สมมติว่าเราต้องการให้ฟังก์ชัน `notify` สามารถแสดงผลด้วย `{}` ไปพร้อมๆ กับการเรียกใช้ `summarize` บน `item`: เราก็สามารถระบุในนิยามของ `notify` ได้ว่า `item` จะต้องอิมพลีเมนต์ทั้งเทรต `Display` และ `Summary` โดยใช้ไวยากรณ์เครื่องหมายบวก `+` ดังนี้:

```rust,ignore
pub fn notify(item: &(impl Summary + Display)) {
```

ไวยากรณ์ `+` นี้ยังสามารถนำไปใช้กับบาวด์ของเทรตบนประเภทเจเนอริกได้เช่นกัน:

```rust,ignore
pub fn notify<T: Summary + Display>(item: &T) {
```

เมื่อกำหนดบาวด์ของเทรตทั้งสองตัวเรียบร้อยแล้ว เนื้อหาของฟังก์ชัน `notify` ก็จะสามารถเรียกใช้ `summarize` และใช้ `{}` เพื่อจัดรูปแบบการแสดงผลของ `item` ได้อย่างถูกต้อง

#### บาวด์ของเทรตที่ชัดเจนขึ้นด้วยอนุประโยค `where`

การใส่บาวด์ของเทรตมากเกินไปก็มีข้อเสีย เนื่องจากเจเนอริกแต่ละตัวต่างมีบาวด์ของตนเอง ฟังก์ชันที่มีพารามิเตอร์ประเภทข้อมูลเจเนอริกหลายตัวจึงอาจเต็มไปด้วยข้อกำหนดบาวด์ของเทรตที่อัดแน่นอยู่ระหว่างชื่อฟังก์ชันกับรายการพารามิเตอร์ ซึ่งทำให้ลายเซ็นฟังก์ชันอ่านยากมาก ด้วยเหตุนี้ Rust จึงมีไวยากรณ์ทางเลือกสำหรับระบุบาวด์ของเทรตไว้ภายในอนุประโยค (clause) `where` หลังลายเซ็นฟังก์ชัน ดังนั้นแทนที่จะเขียนแบบนี้:

```rust,ignore
impl<T: Display> ToString for T {
    // --snip--
}
```

และด้วยความที่ไลบรารีมาตรฐานมีการอิมพลีเมนต์แบบครอบคลุมเช่นนี้ เราจึงสามารถเรียกใช้เมธอด `to_string` ของเทรต `ToString` บนทุกประเภทข้อมูลที่อิมพลีเมนต์เทรต `Display` ได้ทันที ตัวอย่างเช่น เราสามารถแปลงจำนวนเต็มให้กลายเป็นค่า `String` ได้ดังนี้ เพราะประเภทจำนวนเต็มได้อิมพลีเมนต์ `Display` ไว้แล้ว:

```rust
let s = 3.to_string();
```

การอิมพลีเมนต์แบบครอบคลุมนี้จะปรากฏให้เห็นในเอกสารประกอบของเทรตภายใต้หัวข้อ “Implementors”

เทรตและบาวด์ของเทรตช่วยให้เราสามารถเขียนโค้ดที่ใช้พารามิเตอร์ประเภทข้อมูลเจเนอริกเพื่อลดความซ้ำซ้อน ขณะเดียวกันก็ยังสามารถระบุให้คอมไพเลอร์ทราบได้อย่างแม่นยำว่าเราต้องการให้ประเภทเจเนอริกนั้นมีพฤติกรรมอย่างไร ซึ่งคอมไพเลอร์จะนำข้อมูลบาวด์ของเทรตนี้ไปตรวจสอบว่าประเภทข้อมูลรูปธรรมทั้งหมดที่นำมาใช้กับโค้ดของเรามีพฤติกรรมที่ถูกต้องครบถ้วนหรือไม่ ในภาษาแบบไดนามิก (dynamically typed languages) เราอาจต้องเผชิญกับข้อผิดพลาดในตอนรันไทม์หากเราเผลอเรียกใช้เมธอดบนประเภทข้อมูลที่ไม่ได้นิยามเมธอดนั้นไว้ แต่ Rust ได้เลื่อนการตรวจสอบข้อผิดพลาดเหล่านี้มาไว้ตั้งแต่ตอนคอมไพล์ เพื่อบังคับให้เราแก้ไขปัญหาให้เรียบร้อยตั้งแต่ก่อนที่โค้ดจะสามารถรันได้ด้วยซ้ำ นอกจากนี้ เรายังไม่ต้องเสียเวลาเขียนโค้ดเพื่อตรวจสอบพฤติกรรมในตอนรันไทม์อีก เพราะคอมไพเลอร์ได้ตรวจสอบให้เรียบร้อยแล้ว ซึ่งช่วยเพิ่มประสิทธิภาพการทำงานให้สูงสุดโดยไม่ต้องสูญเสียความยืดหยุ่นของเจเนอริกไปเลย
