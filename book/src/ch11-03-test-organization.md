## การจัดระเบียบเทสต์

ดังที่กล่าวไว้ตอนต้นบท การทดสอบ (test) เป็นสาขาวิชาที่ซับซ้อน และผู้คนต่างกันใช้คำศัพท์และการจัดระเบียบที่ต่างกัน ชุมชน Rust คิดถึงเทสต์ในแง่ของสองหมวดหมู่หลัก: การทดสอบระดับยูนิต (unit test) และการทดสอบแบบอินทิเกรชัน (integration test) _การทดสอบระดับยูนิต_ นั้นมีขนาดเล็กและเจาะจงกว่า โดยทดสอบมอดูล (module) ทีละตัวแบบแยกเดี่ยว และสามารถทดสอบอินเทอร์เฟซแบบส่วนตัว (private) ได้ _การทดสอบแบบอินทิเกรชัน_ นั้นอยู่ภายนอกไลบรารีของคุณโดยสิ้นเชิง และใช้โค้ดของคุณในแบบเดียวกับที่โค้ดภายนอกอื่นๆ จะใช้ โดยใช้อินเทอร์เฟซสาธารณะ (public) เท่านั้น และอาจทดลองใช้หลายมอดูลต่อเทสต์หนึ่งตัว

การเขียนเทสต์ทั้งสองชนิดเป็นสิ่งสำคัญเพื่อให้แน่ใจว่าส่วนประกอบต่างๆ ของไลบรารีของคุณทำในสิ่งที่คุณคาดหวัง ทั้งแบบแยกกันและแบบร่วมกัน

### การทดสอบระดับยูนิต

จุดประสงค์ของการทดสอบระดับยูนิตคือทดสอบโค้ดแต่ละหน่วยแยกจากโค้ดที่เหลือ เพื่อระบุได้อย่างรวดเร็วว่าโค้ดตรงไหนทำงานและไม่ทำงานอย่างที่คาดหวัง คุณจะวางการทดสอบระดับยูนิตไว้ในไดเรกทอรี _src_ ในแต่ละไฟล์ที่มีโค้ดที่มันทดสอบอยู่ ธรรมเนียมปฏิบัติคือสร้างมอดูลชื่อ `tests` ในแต่ละไฟล์เพื่อบรรจุฟังก์ชันเทสต์ และกำกับมอดูลด้วย `cfg(test)`

#### มอดูล `tests` และ `#[cfg(test)]`

แอนโนเทชัน (annotation) `#[cfg(test)]` บนมอดูล `tests` บอก Rust ให้คอมไพล์และรันโค้ดเทสต์เฉพาะเมื่อคุณรัน `cargo test` ไม่ใช่เมื่อคุณรัน `cargo build` สิ่งนี้ประหยัดเวลาคอมไพล์เมื่อคุณต้องการเพียงบิลด์ไลบรารี และประหยัดพื้นที่ในไฟล์ที่คอมไพล์แล้วที่ได้ เพราะเทสต์ไม่ได้ถูกรวมอยู่ด้วย คุณจะเห็นว่าเนื่องจากการทดสอบแบบอินทิเกรชันไปอยู่ในไดเรกทอรีอื่น พวกมันจึงไม่ต้องการแอนโนเทชัน `#[cfg(test)]` อย่างไรก็ตาม เนื่องจากการทดสอบระดับยูนิตอยู่ในไฟล์เดียวกับโค้ด คุณจึงใช้ `#[cfg(test)]` เพื่อระบุว่าพวกมันไม่ควรถูกรวมไว้ในผลลัพธ์ที่คอมไพล์แล้ว

ย้อนกลับไปตอนที่เราสร้างโปรเจกต์ `adder` ใหม่ในหัวข้อแรกของบทนี้ Cargo ได้สร้างโค้ดนี้ให้เรา:

### การทดสอบแบบอินทิเกรชัน

ใน Rust การทดสอบแบบอินทิเกรชันอยู่ภายนอกไลบรารีของคุณโดยสิ้นเชิง พวกมันใช้ไลบรารีของคุณในแบบเดียวกับที่โค้ดอื่นๆ จะใช้ ซึ่งหมายความว่ามันเรียกได้เฉพาะฟังก์ชันที่เป็นส่วนหนึ่งของ API สาธารณะของไลบรารีของคุณเท่านั้น จุดประสงค์ของมันคือทดสอบว่าหลายส่วนของไลบรารีของคุณทำงานร่วมกันอย่างถูกต้องหรือไม่ หน่วยของโค้ดที่ทำงานถูกต้องได้ด้วยตัวเองอาจมีปัญหาเมื่อถูกนำมาอินทิเกรต ดังนั้นความครอบคลุมการทดสอบของโค้ดที่อินทิเกรตแล้วจึงสำคัญเช่นกัน ในการสร้างการทดสอบแบบอินทิเกรชัน ก่อนอื่นคุณต้องมีไดเรกทอรี _tests_

#### ไดเรกทอรี _tests_

เราสร้างไดเรกทอรี _tests_ ที่ระดับบนสุดของไดเรกทอรีโปรเจกต์ของเรา ข้างๆ _src_ Cargo รู้ว่าจะมองหาไฟล์การทดสอบแบบอินทิเกรชันในไดเรกทอรีนี้ จากนั้นเราจะสร้างไฟล์เทสต์ได้มากเท่าที่ต้องการ และ Cargo จะคอมไพล์แต่ละไฟล์เป็นเครต (crate) แยกกัน

มาสร้างการทดสอบแบบอินทิเกรชันกัน โดยให้โค้ดในลิสติ้ง 11-12 ยังอยู่ในไฟล์ _src/lib.rs_ ให้สร้างไดเรกทอรี _tests_ และสร้างไฟล์ใหม่ชื่อ _tests/integration_test.rs_ โครงสร้างไดเรกทอรีของคุณควรมีหน้าตาดังนี้:

```text
adder
├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    └── integration_test.rs
```

#### มอดูลย่อยในการทดสอบแบบอินทิเกรชัน

เมื่อคุณเพิ่มการทดสอบแบบอินทิเกรชันมากขึ้น คุณอาจต้องการสร้างไฟล์เพิ่มขึ้นในไดเรกทอรี _tests_ เพื่อช่วยจัดระเบียบมัน ตัวอย่างเช่น คุณสามารถจัดกลุ่มฟังก์ชันเทสต์ตามฟังก์ชันการทำงานที่มันทดสอบ ดังที่กล่าวไว้ก่อนหน้านี้ แต่ละไฟล์ในไดเรกทอรี _tests_ ถูกคอมไพล์เป็นเครตแยกกันของตัวเอง ซึ่งมีประโยชน์สำหรับการสร้างสโคปแยกกันเพื่อเลียนแบบวิธีที่ผู้ใช้ปลายทางจะใช้เครตของคุณได้ใกล้เคียงยิ่งขึ้น อย่างไรก็ตาม สิ่งนี้หมายความว่าไฟล์ในไดเรกทอรี _tests_ ไม่มีพฤติกรรมเดียวกันกับไฟล์ใน _src_ ดังที่คุณได้เรียนรู้ในบทที่ 7 เกี่ยวกับวิธีแยกโค้ดออกเป็นมอดูลและไฟล์

```text
    │   └── mod.rs
    └── integration_test.rs
```

นี่คือธรรมเนียมการตั้งชื่อแบบเก่าที่ Rust ก็เข้าใจเช่นกัน ซึ่งเราได้กล่าวถึงใน[“พาธไฟล์ทางเลือก”][alt-paths]<!-- ignore --> ในบทที่ 7 การตั้งชื่อไฟล์แบบนี้บอก Rust ว่าอย่าปฏิบัติต่อมอดูล `common` เป็นไฟล์การทดสอบแบบอินทิเกรชัน เมื่อเราย้ายโค้ดฟังก์ชัน `setup` ไปยัง _tests/common/mod.rs_ และลบไฟล์ _tests/common.rs_ ส่วนในเอาต์พุตเทสต์ก็จะไม่ปรากฏอีก ไฟล์ในไดเรกทอรีย่อยของไดเรกทอรี _tests_ จะไม่ถูกคอมไพล์เป็นเครตแยกกันและไม่มีส่วนในเอาต์พุตเทสต์

หลังจากที่เราสร้าง _tests/common/mod.rs_ แล้ว เราสามารถใช้มันเป็นมอดูลจากไฟล์การทดสอบแบบอินทิเกรชันใดๆ ก็ได้ นี่คือตัวอย่างของการเรียกฟังก์ชัน `setup` จากเทสต์ `it_adds_two` ใน _tests/integration_test.rs_:

โปรดสังเกตว่าประกาศ `mod common;` เหมือนกับประกาศมอดูลที่เราสาธิตในลิสติ้ง 7-21 จากนั้นในฟังก์ชันเทสต์ เราสามารถเรียกฟังก์ชัน `common::setup()` ได้

#### การทดสอบแบบอินทิเกรชันสำหรับเครตไบนารี

หากโปรเจกต์ของเราเป็นเครตไบนารี (binary crate) ที่บรรจุเพียงไฟล์ _src/main.rs_ และไม่มีไฟล์ _src/lib.rs_ เราจะไม่สามารถสร้างการทดสอบแบบอินทิเกรชันในไดเรกทอรี _tests_ และนำฟังก์ชันที่นิยามในไฟล์ _src/main.rs_ เข้าสู่สโคปด้วยสเตตเมนต์ `use` ได้ มีเพียงเครตไลบรารี (library crate) เท่านั้นที่เปิดเผยฟังก์ชันที่เครตอื่นๆ ใช้ได้ ส่วนเครตไบนารีมีไว้ให้รันด้วยตัวเอง

นี่เป็นหนึ่งในเหตุผลที่โปรเจกต์ Rust ที่มีไบนารีมักมีไฟล์ _src/main.rs_ ที่ตรงไปตรงมาซึ่งเรียกตรรกะที่อยู่ในไฟล์ _src/lib.rs_ การใช้โครงสร้างนั้นทำให้การทดสอบแบบอินทิเกรชัน_สามารถ_ทดสอบเครตไลบรารีได้ โดยใช้ `use` เพื่อทำให้ฟังก์ชันการทำงานที่สำคัญพร้อมใช้งาน หากฟังก์ชันการทำงานที่สำคัญนั้นทำงานได้ โค้ดจำนวนเล็กน้อยในไฟล์ _src/main.rs_ ก็จะทำงานได้เช่นกัน และโค้ดจำนวนเล็กน้อยนั้นไม่จำเป็นต้องถูกทดสอบ

## สรุป

ฟีเจอร์การทดสอบของ Rust มีวิธีระบุว่าโค้ดควรทำงานอย่างไรเพื่อให้แน่ใจว่ามันยังคงทำงานอย่างที่คุณคาดหวัง แม้ว่าคุณจะทำการเปลี่ยนแปลงก็ตาม การทดสอบระดับยูนิตทดลองใช้ส่วนต่างๆ ของไลบรารีแยกกัน และสามารถทดสอบรายละเอียดการอิมพลีเมนต์แบบส่วนตัวได้ การทดสอบแบบอินทิเกรชันตรวจสอบว่าหลายส่วนของไลบรารีทำงานร่วมกันอย่างถูกต้อง และมันใช้ API สาธารณะของไลบรารีเพื่อทดสอบโค้ดในแบบเดียวกับที่โค้ดภายนอกจะใช้ แม้ว่าระบบชนิดข้อมูลและกฎความเป็นเจ้าของของ Rust จะช่วยป้องกันบั๊กบางชนิดได้ แต่เทสต์ก็ยังคงสำคัญในการลดบั๊กเชิงตรรกะที่เกี่ยวกับวิธีที่โค้ดของคุณควรจะทำงาน

มาผสมผสานความรู้ที่คุณได้เรียนรู้ในบทนี้และบทก่อนๆ เพื่อทำงานกับโปรเจกต์กันเถอะ!
