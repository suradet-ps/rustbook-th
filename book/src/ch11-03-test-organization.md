## การจัดระเบียบเทสต์

ดังที่ได้กล่าวไว้ในตอนต้นบท การทดสอบ (testing) เป็นศาสตร์ที่มีความละเอียดซับซ้อน และแต่ละคนอาจใช้คำศัพท์ตลอดจนวิธีการจัดระเบียบที่แตกต่างกันไป ในชุมชน Rust เราจะแบ่งประเภทของเทสต์ออกเป็น 2 หมวดหมู่หลัก ได้แก่: ยูนิตเทสต์ (unit tests) และอินทิเกรชันเทสต์ (integration tests) โดย _ยูนิตเทสต์_ จะมีขอบเขตขนาดเล็กและมุ่งเน้นความเฉพาะเจาะจง ทำหน้าที่ทดสอบแต่ละมอดูล (module) แบบแยกเดี่ยวทีละส่วน และสามารถเข้าถึงเพื่อทดสอบอินเทอร์เฟซที่เป็นส่วนตัว (private interface) ได้ ส่วน _อินทิเกรชันเทสต์_ จะอยู่ภายนอกไลบรารีของคุณโดยสมบูรณ์ และเรียกใช้งานโค้ดของคุณในลักษณะเดียวกับที่โค้ดภายนอกอื่นๆ ใช้งาน โดยจะเข้าถึงได้เฉพาะอินเทอร์เฟซที่เป็นสาธารณะ (public interface) เท่านั้น และเทสต์แต่ละตัวอาจครอบคลุมการทำงานร่วมกันของหลายๆ มอดูลพร้อมกัน

การเขียนชุดทดสอบทั้งสองประเภทนี้มีความสำคัญอย่างยิ่ง เพื่อให้มั่นใจได้ว่าส่วนประกอบต่างๆ ในไลบรารีของคุณสามารถทำงานได้ตรงตามที่คาดหวัง ทั้งในระดับแยกส่วนเดี่ยวๆ และในระดับการทำงานประสานกัน

### การทดสอบระดับยูนิต

จุดประสงค์ของยูนิตเทสต์คือ การทดสอบโค้ดแต่ละหน่วยย่อยโดยแยกขาดจากโค้ดส่วนอื่นๆ เพื่อให้สามารถระบุตำแหน่งได้อย่างรวดเร็วว่าโค้ดส่วนใดทำงานถูกต้อง และส่วนใดไม่ทำงานตามที่คาดหวัง เราจะวางยูนิตเทสต์ไว้ในไดเรกทอรี _src_ ภายในไฟล์เดียวกันกับโค้ดที่ต้องการทดสอบ โดยธรรมเนียมปฏิบัติคือ ให้สร้างมอดูลชื่อ `tests` ขึ้นมาในแต่ละไฟล์เพื่อบรรจุฟังก์ชันเทสต์ และกำกับมอดูลนั้นไว้ด้วย `cfg(test)`

#### มอดูล `tests` และ `#[cfg(test)]`

แอตทริบิวต์กำกับ `#[cfg(test)]` บนมอดูล `tests` จะสั่งให้ Rust คอมไพล์และรันโค้ดทดสอบเฉพาะเมื่อเราสั่งรันคำสั่ง `cargo test` เท่านั้น ไม่ใช่ตอนที่เราสั่งรัน `cargo build` ซึ่งช่วยประหยัดเวลาในการคอมไพล์เมื่อเราต้องการเพียงแค่บิลด์ไลบรารีไปใช้งาน และช่วยลดขนาดของไฟล์ไบนารีผลลัพธ์ลงเนื่องจากไม่มีโค้ดเทสต์แฝงอยู่ คุณจะเห็นว่าเนื่องจากอินทิเกรชันเทสต์จะถูกจัดเก็บไว้ในอีกไดเรกทอรีหนึ่งต่างหาก จึงไม่จำเป็นต้องใส่ `#[cfg(test)]` กำกับไว้ แต่สำหรับยูนิตเทสต์ที่เขียนอยู่ภายในไฟล์เดียวกับโค้ดหลัก เราจึงต้องใช้ `#[cfg(test)]` เพื่อระบุไม่ให้นำโค้ดเหล่านี้ไปรวมไว้ในผลลัพธ์การบิลด์ทั่วไป

ย้อนกลับไปตอนที่เราสร้างโปรเจกต์ `adder` ใหม่ในหัวข้อแรกของบทนี้ Cargo ได้สร้างโค้ดเริ่มต้นมาให้เราดังนี้:

#### การทดสอบฟังก์ชันแบบส่วนตัว

ในแวดวงการทดสอบซอฟต์แวร์ยังคงมีการถกเถียงกันอยู่เสมอว่า เราควรทดสอบฟังก์ชันแบบส่วนตัว (private functions) โดยตรงหรือไม่ ซึ่งในภาษาโปรแกรมอื่นๆ หลายภาษาอาจทำให้การทดสอบฟังก์ชันส่วนตัวเป็นเรื่องยากหรือทำไม่ได้เลย แต่ไม่ว่าคุณจะยึดถือแนวคิดการทดสอบแบบใด กฎเรื่องการเปิดเผย (privacy rules) ของ Rust อนุญาตให้คุณสามารถทดสอบฟังก์ชันแบบส่วนตัวได้อย่างเต็มที่ ลองพิจารณาโค้ดในลิสติ้ง 11-12 ซึ่งมีฟังก์ชันแบบส่วนตัวชื่อ `internal_adder`

### การทดสอบแบบอินทิเกรชัน

ในภาษา Rust อินทิเกรชันเทสต์ (integration tests) จะอยู่ภายนอกไลบรารีของคุณโดยสมบูรณ์ พวกมันจะเรียกใช้งานไลบรารีในลักษณะเดียวกับที่โค้ดภายนอกอื่นๆ ใช้งาน ซึ่งหมายความว่ามันจะสามารถเรียกใช้ได้เฉพาะฟังก์ชันที่เป็นส่วนหนึ่งของ API สาธารณะ (public API) ของไลบรารีเท่านั้น จุดประสงค์หลักของอินทิเกรชันเทสต์คือการตรวจสอบว่าส่วนประกอบต่างๆ ของไลบรารีสามารถทำงานร่วมกันได้อย่างถูกต้องหรือไม่ เพราะหน่วยของโค้ดที่ทำงานได้ดีเมื่ออยู่เดี่ยวๆ อาจเกิดปัญหาขึ้นได้เมื่อนำมาเชื่อมต่อเข้าด้วยกัน ดังนั้นความครอบคลุมของการทดสอบในระดับบูรณาการจึงมีความสำคัญอย่างยิ่ง ในการสร้างอินทิเกรชันเทสต์ ขั้นตอนแรกที่คุณต้องมีคือไดเรกทอรี _tests_

#### ไดเรกทอรี _tests_

เราจะสร้างไดเรกทอรีชื่อ _tests_ ไว้ที่ระดับบนสุดของไดเรกทอรีโปรเจกต์ ซึ่งจะอยู่คู่กับไดเรกทอรี _src_ โดย Cargo จะทราบโดยอัตโนมัติว่าจะต้องค้นหาไฟล์อินทิเกรชันเทสต์ในไดเรกทอรีนี้ จากนั้นเราสามารถสร้างไฟล์เทสต์ได้มากเท่าที่ต้องการ และ Cargo จะคอมไพล์แต่ละไฟล์ให้เป็นเครต (crate) แยกต่างหากออกจากกัน

มาลองสร้างอินทิเกรชันเทสต์กัน โดยคงโค้ดในลิสติ้ง 11-12 ไว้ในไฟล์ _src/lib.rs_ ให้สร้างไดเรกทอรี _tests_ ขึ้นมา แล้วสร้างไฟล์ใหม่ชื่อ _tests/integration_test.rs_ โครงสร้างไดเรกทอรีของคุณควรมีหน้าตาดังนี้:

```text
adder
├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    └── integration_test.rs
```

#### มอดูลย่อยในการทดสอบแบบอินทิเกรชัน

เมื่อคุณเริ่มมีอินทิเกรชันเทสต์มากขึ้น คุณอาจต้องการสร้างไฟล์เพิ่มเติมในไดเรกทอรี _tests_ เพื่อช่วยจัดหมวดหมู่ให้เป็นระเบียบ เช่น การจัดกลุ่มฟังก์ชันเทสต์ตามฟังก์ชันการทำงานที่ต้องการทดสอบ ดังที่ได้กล่าวไปแล้วว่า แต่ละไฟล์ในไดเรกทอรี _tests_ จะถูกคอมไพล์ให้เป็นเครตแยกจากกัน ซึ่งมีประโยชน์อย่างยิ่งในการจำลองสโคปแบบแยกส่วนให้ใกล้เคียงกับวิธีที่ผู้ใช้งานจริงจะเรียกใช้เครตของคุณ อย่างไรก็ตาม สิ่งนี้ส่งผลให้ไฟล์ในไดเรกทอรี _tests_ มีพฤติกรรมไม่เหมือนกับไฟล์ในไดเรกทอรี _src_ ตามที่คุณเคยเรียนรู้ในบทที่ 7 เกี่ยวกับการแยกโค้ดออกเป็นมอดูลและไฟล์

ความแตกต่างของพฤติกรรมนี้จะเห็นได้ชัดเจนที่สุดเมื่อคุณมีชุดฟังก์ชันตัวช่วย (helper functions) ที่ต้องการใช้ร่วมกันในหลายๆ ไฟล์อินทิเกรชันเทสต์ และคุณพยายามทำตามขั้นตอนในหัวข้อ[“แยกมอดูลออกเป็นไฟล์ต่างๆ”][separating-modules-into-files]<!-- ignore --> ของบทที่ 7 เพื่อแยกโค้ดเหล่านั้นออกมาเป็นมอดูลส่วนกลาง ตัวอย่างเช่น หากเราสร้างไฟล์ _tests/common.rs_ แล้วใส่ฟังก์ชันชื่อ `setup` ไว้ข้างใน เพื่อให้สามารถเรียกใช้ได้จากหลายฟังก์ชันเทสต์ในหลายไฟล์:


การที่ `common` โผล่ขึ้นมาในผลการทดสอบพร้อมข้อความ `running 0 tests` ไม่ใช่สิ่งที่เราต้องการ เพราะเราเพียงแค่ต้องการแชร์โค้ดตัวช่วยร่วมกับไฟล์อินทิเกรชันเทสต์อื่นๆ เท่านั้น เพื่อหลีกเลี่ยงไม่ให้ `common` ปรากฏในเอาต์พุตการทดสอบ แทนที่เราจะสร้างไฟล์ _tests/common.rs_ ให้เราสร้างเป็น _tests/common/mod.rs_ แทน ซึ่งทำให้โครงสร้างไดเรกทอรีมีหน้าตาดังนี้:

```text
├── Cargo.lock
├── Cargo.toml
├── src
│   └── lib.rs
└── tests
    ├── common
    │   └── mod.rs
    └── integration_test.rs
```

นี่คือธรรมเนียมการตั้งชื่อรูปแบบดั้งเดิมที่ Rust เข้าใจได้เช่นกัน ตามที่เราเคยกล่าวถึงใน[“พาธไฟล์ทางเลือก”][alt-paths]<!-- ignore --> ในบทที่ 7 การตั้งชื่อไฟล์ในรูปแบบนี้จะบอกให้ Rust ทราบว่าอย่าปฏิบัติต่อมอดูล `common` ในฐานะไฟล์อินทิเกรชันเทสต์ และเมื่อเราย้ายโค้ดฟังก์ชัน `setup` ไปไว้ใน _tests/common/mod.rs_ พร้อมทั้งลบไฟล์ _tests/common.rs_ ทิ้งไป ส่วนของ `common` ในเอาต์พุตเทสต์ก็จะไม่ปรากฏขึ้นอีก ไฟล์ทั้งหมดที่อยู่ในไดเรกทอรีย่อยของ _tests_ จะไม่ถูกคอมไพล์เป็นเครตแยกเดี่ยว และจะไม่มีส่วนแสดงผลในเอาต์พุตการทดสอบ

หลังจากที่เราสร้างไฟล์ _tests/common/mod.rs_ เรียบร้อยแล้ว เราจะสามารถเรียกใช้งานมันในฐานะมอดูลจากไฟล์อินทิเกรชันเทสต์ใดๆ ก็ได้ ต่อไปนี้เป็นตัวอย่างการเรียกฟังก์ชัน `setup` จากเทสต์ `it_adds_two` ในไฟล์ _tests/integration_test.rs_:

```rust,ignore

```

โปรดสังเกตว่าการประกาศ `mod common;` นั้นเป็นรูปแบบเดียวกับที่เราเคยแสดงไว้ในลิสติ้ง 7-21 จากนั้นภายในฟังก์ชันเทสต์ เราจึงสามารถเรียกใช้คำสั่ง `common::setup()` ได้อย่างราบรื่น

#### การทดสอบแบบอินทิเกรชันสำหรับเครตไบนารี

หากโปรเจกต์ของเราเป็นเครตไบนารี (binary crate) ที่มีเพียงไฟล์ _src/main.rs_ และไม่มีไฟล์ _src/lib.rs_ เราจะไม่สามารถสร้างอินทิเกรชันเทสต์ในไดเรกทอรี _tests_ เพื่อนำฟังก์ชันที่นิยามในไฟล์ _src/main.rs_ เข้ามาสู่สโคปด้วยคำสั่ง `use` ได้ เพราะมีเพียงเครตไลบรารี (library crate) เท่านั้นที่เปิดเผยฟังก์ชันให้เครตอื่นๆ เรียกใช้งานได้ ส่วนเครตไบนารีถูกออกแบบมาเพื่อให้รันการทำงานด้วยตัวมันเองโดยเฉพาะ

นี่จึงเป็นหนึ่งในเหตุผลสำคัญที่โปรเจกต์ Rust ที่เป็นไบนารีมักจะมีไฟล์ _src/main.rs_ ที่เรียบง่ายและทำหน้าที่เพียงแค่เรียกใช้ตรรกะการทำงานหลักที่อยู่ในไฟล์ _src/lib.rs_ การใช้โครงสร้างเช่นนี้ทำให้อินทิเกรชันเทสต์_สามารถ_ทดสอบเครตไลบรารีผ่านคำสั่ง `use` เพื่อเข้าถึงฟังก์ชันการทำงานที่สำคัญได้ และหากฟังก์ชันการทำงานหลักเหล่านั้นทำงานได้ถูกต้อง โค้ดเพียงเล็กน้อยที่อยู่ใน _src/main.rs_ ก็จะทำงานได้อย่างถูกต้องตามไปด้วย โดยไม่จำเป็นต้องเขียนชุดทดสอบให้กับโค้ดส่วนเล็กๆ นั้นแยกต่างหาก

## สรุป

ฟีเจอร์การทดสอบของ Rust มอบแนวทางในการกำหนดและตรวจสอบพฤติกรรมการทำงานของโค้ด เพื่อให้มั่นใจได้ว่าโปรแกรมจะยังคงทำงานได้ถูกต้องตรงตามความคาดหวังเสมอ แม้ในยามที่คุณต้องแก้ไขปรับปรุงโค้ดก็ตาม ยูนิตเทสต์ช่วยให้เราทดสอบชิ้นส่วนต่างๆ ของไลบรารีแยกจากกัน และสามารถทดสอบลงลึกไปถึงรายละเอียดการทำงานแบบส่วนตัวได้ ส่วนอินทิเกรชันเทสต์จะช่วยตรวจสอบว่าส่วนต่างๆ ของไลบรารีสามารถทำงานร่วมกันได้อย่างสมบูรณ์ โดยเรียกใช้ผ่าน API สาธารณะของไลบรารีในลักษณะเดียวกับที่โค้ดภายนอกนำไปใช้งาน แม้ว่าระบบชนิดข้อมูลและกฎความเป็นเจ้าของของ Rust จะช่วยป้องกันข้อผิดพลาดได้มากมายหลายประเภท แต่การเขียนชุดทดสอบก็ยังคงเป็นหัวใจสำคัญในการลดทอนข้อผิดพลาดเชิงตรรกะ (logic bugs) เกี่ยวกับพฤติกรรมที่โค้ดควรจะเป็น

มานำความรู้ทั้งหมดที่คุณได้เรียนรู้ในบทนี้และบทก่อนๆ มาผสมผสานเพื่อร่วมกันลงมือพัฒนาโปรเจกต์จริงกันเถอะ!
