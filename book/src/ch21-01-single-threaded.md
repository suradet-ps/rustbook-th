## สร้างเว็บเซิร์ฟเวอร์แบบเธรดเดียว

เราจะเริ่มจากการทำให้เว็บเซิร์ฟเวอร์ (web server) แบบเธรดเดียว (single-threaded) ทำงานได้ ก่อนที่เราจะเริ่ม มาดูภาพรวมสั้นๆ ของโปรโตคอล (protocol) ที่เกี่ยวข้องกับการสร้างเว็บเซิร์ฟเวอร์กันก่อน รายละเอียดของโปรโตคอลเหล่านั้นอยู่นอกขอบเขตของหนังสือเล่มนี้ แต่ภาพรวมสั้นๆ จะให้ข้อมูลที่คุณต้องการ

โปรโตคอลหลักสองตัวที่เกี่ยวข้องกับเว็บเซิร์ฟเวอร์คือ _Hypertext Transfer Protocol_ _(HTTP)_ และ _Transmission Control Protocol_ _(TCP)_ โปรโตคอลทั้งสองเป็นโปรโตคอลแบบ _คำขอ-การตอบกลับ_ หมายความว่า _ไคลเอนต์_ (client) เป็นฝ่ายเริ่มคำขอ (request) และ _เซิร์ฟเวอร์_ (server) จะรอฟังคำขอเหล่านั้นและให้การตอบกลับ (response) แก่ไคลเอนต์ เนื้อหาของคำขอและการตอบกลับเหล่านั้นถูกนิยามโดยโปรโตคอล

TCP เป็นโปรโตคอลระดับต่ำกว่าที่อธิบายรายละเอียดว่าข้อมูลเดินทางจากเซิร์ฟเวอร์หนึ่งไปยังอีกเซิร์ฟเวอร์หนึ่งได้อย่างไร แต่ไม่ได้ระบุว่าข้อมูลนั้นคืออะไร HTTP สร้างต่อยอดจาก TCP โดยนิยามเนื้อหาของคำขอและการตอบกลับ ในทางเทคนิคแล้วเป็นไปได้ที่จะใช้ HTTP กับโปรโตคอลอื่น แต่ในกรณีส่วนใหญ่ HTTP ส่งข้อมูลของมันผ่าน TCP เราจะทำงานกับไบต์ดิบของคำขอและการตอบกลับ TCP และ HTTP

### การรอฟังการเชื่อมต่อ TCP

เว็บเซิร์ฟเวอร์ของเราจำเป็นต้องรอฟังการเชื่อมต่อ TCP นั่นจึงเป็นส่วนแรกที่เราจะทำ ไลบรารีมาตรฐานมีมอดูล `std::net` ที่ให้เราทำสิ่งนี้ได้ มาสร้างโปรเจกต์ใหม่ตามรูปแบบปกติกัน:

```console
$ cargo new hello
     Created binary (application) `hello` project
$ cd hello
```

เมื่อใช้ `TcpListener` เราสามารถรอฟังการเชื่อมต่อ TCP ที่ที่อยู่ `127.0.0.1:7878` ได้ ในที่อยู่นี้ ส่วนที่อยู่ก่อนเครื่องหมายทวิภาคคือที่อยู่ IP ที่แทนคอมพิวเตอร์ของคุณ (ส่วนนี้เหมือนกันบนคอมพิวเตอร์ทุกเครื่อง และไม่ได้แทนคอมพิวเตอร์ของผู้เขียนโดยเฉพาะ) และ `7878` คือพอร์ต เราเลือกพอร์ตนี้ด้วยเหตุผลสองประการ: โดยปกติ HTTP ไม่ได้รับบนพอร์ตนี้ เซิร์ฟเวอร์ของเราจึงไม่น่าจะขัดแย้งกับเว็บเซิร์ฟเวอร์อื่นที่คุณอาจรันอยู่บนเครื่องของคุณ และ 7878 คือคำว่า _rust_ ที่พิมพ์บนโทรศัพท์

ฟังก์ชัน `bind` ในกรณีนี้ทำงานเหมือนกับฟังก์ชัน `new` ตรงที่มันจะคืนค่าอินสแตนซ์ใหม่ของ `TcpListener` ฟังก์ชันนี้ถูกเรียกว่า `bind` เพราะในระบบเครือข่าย การเชื่อมต่อไปยังพอร์ตเพื่อรอฟังนั้นเป็นที่รู้จักกันในชื่อ “การผูกกับพอร์ต” (binding to a port)

ฟังก์ชัน `bind` คืนค่า `Result<T, E>` ซึ่งบ่งชี้ว่าการผูกอาจล้มเหลวได้ ตัวอย่างเช่น หากเรารันโปรแกรมของเราสองอินสแตนซ์ จึงมีสองโปรแกรมที่รอฟังพอร์ตเดียวกัน เพราะเรากำลังเขียนเซิร์ฟเวอร์พื้นฐานเพียงเพื่อจุดประสงค์ในการเรียนรู้ เราจะไม่กังวลกับการจัดการข้อผิดพลาดประเภทนี้ แต่เราจะใช้ `unwrap` เพื่อหยุดโปรแกรมหากเกิดข้อผิดพลาด

เมธอด `incoming` บน `TcpListener` คืนค่าอิเทอเรเตอร์ (iterator) ที่ให้ลำดับของสตรีมแก่เรา (หรือที่เจาะจงกว่านั้นคือ สตรีมชนิด `TcpStream`) _สตรีม_ หนึ่งตัวแทนการเชื่อมต่อที่เปิดอยู่ระหว่างไคลเอนต์และเซิร์ฟเวอร์ _การเชื่อมต่อ_ เป็นชื่อเรียกของกระบวนการคำขอและการตอบกลับทั้งหมดที่ไคลเอนต์เชื่อมต่อกับเซิร์ฟเวอร์ เซิร์ฟเวอร์สร้างการตอบกลับ และเซิร์ฟเวอร์ปิดการเชื่อมต่อ ดังนั้นเราจะอ่านจาก `TcpStream` เพื่อดูว่าไคลเอนต์ส่งอะไรมาบ้าง แล้วเขียนการตอบกลับของเราลงในสตรีมเพื่อส่งข้อมูลกลับไปยังไคลเอนต์ โดยรวมแล้ว ลูป `for` นี้จะประมวลผลแต่ละการเชื่อมต่อตามลำดับ และสร้างชุดของสตรีมให้เราจัดการ

สำหรับตอนนี้ การจัดการสตรีมของเราประกอบด้วยการเรียก `unwrap` เพื่อยุติโปรแกรมของเราหากสตรีมมีข้อผิดพลาดใดๆ หากไม่มีข้อผิดพลาดใดๆ โปรแกรมจะพิมพ์ข้อความ เราจะเพิ่มฟังก์ชันการทำงานสำหรับกรณีสำเร็จในลิสติ้งถัดไป เหตุผลที่เราอาจได้รับข้อผิดพลาดจากเมธอด `incoming` เมื่อไคลเอนต์เชื่อมต่อกับเซิร์ฟเวอร์ก็คือ จริงๆ แล้วเราไม่ได้วนซ้ำผ่านการเชื่อมต่อ แต่เรากำลังวนซ้ำผ่าน_ความพยายามเชื่อมต่อ_ การเชื่อมต่ออาจไม่สำเร็จได้ด้วยหลายเหตุผล ซึ่งหลายอย่างเป็นความเฉพาะของระบบปฏิบัติการ ตัวอย่างเช่น ระบบปฏิบัติการหลายตัวมีขีดจำกัดจำนวนการเชื่อมต่อที่เปิดอยู่พร้อมกันที่มันรองรับได้ ความพยายามเชื่อมต่อใหม่ที่เกินจำนวนนั้นจะทำให้เกิดข้อผิดพลาดจนกว่าการเชื่อมต่อที่เปิดอยู่บางส่วนจะถูกปิด

มาลองรันโค้ดนี้กัน! เรียก `cargo run` ในเทอร์มินัล แล้วโหลด _127.0.0.1:7878_ ในเว็บเบราว์เซอร์ เบราว์เซอร์ควรแสดงข้อความแสดงข้อผิดพลาดเช่น “Connection reset” เพราะเซิร์ฟเวอร์ยังไม่ได้ส่งข้อมูลใดๆ กลับไป แต่เมื่อคุณดูที่เทอร์มินัลของคุณ คุณควรเห็นข้อความหลายข้อความที่ถูกพิมพ์ออกมาเมื่อเบราว์เซอร์เชื่อมต่อกับเซิร์ฟเวอร์!

```text

Connection established!
Connection established!
Connection established!
```

บางครั้งคุณจะเห็นข้อความหลายข้อความถูกพิมพ์ออกมาสำหรับคำขอจากเบราว์เซอร์เพียงหนึ่งคำขอ สาเหตุอาจเป็นเพราะเบราว์เซอร์กำลังส่งคำขอสำหรับหน้าเว็บรวมทั้งคำขอสำหรับทรัพยากรอื่นๆ เช่นไอคอน _favicon.ico_ ที่ปรากฏในแท็บของเบราว์เซอร์

นอกจากนี้ยังอาจเป็นเพราะเบราว์เซอร์พยายามเชื่อมต่อกับเซิร์ฟเวอร์หลายครั้งเนื่องจากเซิร์ฟเวอร์ไม่ได้ตอบกลับด้วยข้อมูลใดๆ เมื่อ `stream` ออกจากสโคปและถูกทิ้งที่ส่วนท้ายของลูป การเชื่อมต่อจะถูกปิดเป็นส่วนหนึ่งของการอิมพลีเมนต์ `drop` บางครั้งเบราว์เซอร์รับมือกับการเชื่อมต่อที่ถูกปิดโดยการลองใหม่ เพราะปัญหาอาจเป็นเพียงชั่วคราว

บางครั้งเบราว์เซอร์ยังเปิดการเชื่อมต่อหลายรายการไปยังเซิร์ฟเวอร์โดยไม่ส่งคำขอใดๆ เพื่อที่ว่าหากภายหลังมัน*ส่งคำขอ*จริงๆ คำขอเหล่านั้นจะเกิดขึ้นได้เร็วขึ้น เมื่อสิ่งนี้เกิดขึ้น เซิร์ฟเวอร์ของเราจะเห็นการเชื่อมต่อแต่ละรายการ ไม่ว่ามีคำขอใดๆ ผ่านการเชื่อมต่อนั้นหรือไม่ ตัวอย่างเช่น เบราว์เซอร์ที่ใช้ Chrome หลายเวอร์ชันทำเช่นนี้ คุณสามารถปิดการปรับแต่งนั้นได้โดยใช้โหมดท่องเว็บแบบส่วนตัวหรือใช้เบราว์เซอร์อื่น

ปัจจัยสำคัญคือเราได้รับแฮนเดิล (handle) ไปยังการเชื่อมต่อ TCP สำเร็จแล้ว!

อย่าลืมหยุดโปรแกรมโดยกด <kbd>ctrl</kbd>-<kbd>C</kbd> เมื่อคุณรันโค้ดเวอร์ชันหนึ่งๆ เสร็จแล้ว จากนั้นเริ่มโปรแกรมใหม่โดยเรียกคำสั่ง `cargo run` หลังจากคุณแก้โค้ดในแต่ละชุดแล้ว เพื่อให้แน่ใจว่าคุณกำลังรันโค้ดล่าสุด

เรานำ `std::io::BufReader` และ `std::io::prelude` เข้าสู่สโคปเพื่อให้เข้าถึงเทรต (trait) และชนิดข้อมูลที่ให้เราอ่านจากสตรีมและเขียนไปยังสตรีมได้ ในลูป `for` ในฟังก์ชัน `main` แทนที่จะพิมพ์ข้อความที่บอกว่าเราเชื่อมต่อได้แล้ว ตอนนี้เราเรียกฟังก์ชัน `handle_connection` ใหม่และส่ง `stream` ให้มัน

ในฟังก์ชัน `handle_connection` เราสร้างอินสแตนซ์ใหม่ของ `BufReader` ที่ห่อเรเฟอเรนซ์ (reference) ไปยัง `stream` `BufReader` เพิ่มการบัฟเฟอร์ (buffering) โดยจัดการการเรียกเมธอดของเทรต `std::io::Read` ให้เรา

เราสร้างตัวแปรชื่อ `http_request` เพื่อรวบรวมบรรทัดต่างๆ ของคำขอที่เบราว์เซอร์ส่งมาที่เซิร์ฟเวอร์ของเรา เราบ่งชี้ว่าเราต้องการรวบรวมบรรทัดเหล่านี้ไว้ในเวกเตอร์ (vector) โดยเพิ่มการระบุชนิดข้อมูล (type annotation) `Vec<_>`

`BufReader` อิมพลีเมนต์เทรต `std::io::BufRead` ซึ่งจัดเตรียมเมธอด `lines` เมธอด `lines` คืนค่าอิเทอเรเตอร์ของ `Result<String, std::io::Error>` โดยแยกสตรีมข้อมูลทุกครั้งที่มันเห็นไบต์ขึ้นบรรทัดใหม่ เพื่อให้ได้ `String` แต่ละตัว เราจะ `map` และ `unwrap` แต่ละ `Result` ค่า `Result` อาจเป็นข้อผิดพลาดได้หากข้อมูลไม่ใช่ UTF-8 ที่ถูกต้อง หรือหากเกิดปัญหาในการอ่านจากสตรีม อีกครั้งที่โปรแกรมระดับโปรดักชันควรจัดการข้อผิดพลาดเหล่านี้อย่างนุ่มนวลกว่า แต่เราเลือกที่จะหยุดโปรแกรมในกรณีที่เกิดข้อผิดพลาดเพื่อความเรียบง่าย

เบราว์เซอร์ส่งสัญญาณสิ้นสุดของคำขอ HTTP ด้วยการส่งอักขระขึ้นบรรทัดใหม่สองตัวติดกัน ดังนั้นเพื่อให้ได้คำขอหนึ่งคำขอจากสตรีม เราจึงอ่านบรรทัดไปเรื่อยๆ จนกว่าเราจะได้บรรทัดที่เป็นสตริงว่าง เมื่อเรารวบรวมบรรทัดเหล่านั้นเข้าไปในเวกเตอร์แล้ว เราจะพิมพ์มันออกมาโดยใช้การจัดรูปแบบดีบักแบบสวยงาม เพื่อให้เราดูคำสั่งที่เว็บเบราว์เซอร์ส่งมาที่เซิร์ฟเวอร์ของเราได้

### การดูคำขอ HTTP อย่างใกล้ชิดยิ่งขึ้น

HTTP เป็นโปรโตคอลแบบข้อความ และคำขอมีรูปแบบดังนี้:

```text
Method Request-URI HTTP-Version CRLF
headers CRLF
message-body
```

บรรทัดแรกคือ_บรรทัดคำขอ_ (request line) ซึ่งบรรจุข้อมูลเกี่ยวกับสิ่งที่ไคลเอนต์กำลังร้องขอ ส่วนแรกของบรรทัดคำขอระบุเมธอดที่ถูกใช้ เช่น `GET` หรือ `POST` ซึ่งอธิบายว่าไคลเอนต์ส่งคำขอนี้อย่างไร ไคลเอนต์ของเราใช้คำขอ `GET` ซึ่งหมายความว่ามันกำลังขอข้อมูล

ส่วนถัดไปของบรรทัดคำขอคือ _/_ ซึ่งระบุ _uniform resource identifier_ _(URI)_ ที่ไคลเอนต์กำลังร้องขอ URI เกือบจะแต่ไม่ทั้งหมดเหมือนกับ _uniform resource locator_ _(URL)_ ความแตกต่างระหว่าง URI กับ URL ไม่สำคัญสำหรับจุดประสงค์ของเราในบทนี้ แต่สเปกของ HTTP ใช้คำว่า _URI_ เราจึงแทนที่ _URL_ ลงไปในใจสำหรับ _URI_ ตรงนี้ได้

ส่วนสุดท้ายคือเวอร์ชัน HTTP ที่ไคลเอนต์ใช้ จากนั้นบรรทัดคำขอจะจบลงด้วยลำดับ CRLF (_CRLF_ ย่อมาจาก _carriage return_ และ _line feed_ ซึ่งเป็นคำจากยุคเครื่องพิมพ์ดีด!) ลำดับ CRLF ยังเขียนได้เป็น `\r\n` โดย `\r` คือ carriage return และ `\n` คือ line feed _ลำดับ CRLF_ แยกบรรทัดคำขอออกจากข้อมูลคำขอส่วนที่เหลือ โปรดสังเกตว่าเมื่อ CRLF ถูกพิมพ์ออกมา เราจะเห็นการขึ้นบรรทัดใหม่แทนที่จะเห็น `\r\n`

เมื่อดูข้อมูลบรรทัดคำขอที่เราได้รับจากการรันโปรแกรมของเราจนถึงตอนนี้ เราจะเห็นว่า `GET` คือเมธอด _/_ คือ URI ของคำขอ และ `HTTP/1.1` คือเวอร์ชัน

หลังจากบรรทัดคำขอ บรรทัดที่เหลือเริ่มตั้งแต่ `Host:` เป็นต้นไปคือเฮดเดอร์ (header) คำขอ `GET` ไม่มีบอดี้ (body)

ลองส่งคำขอจากเบราว์เซอร์อื่น หรือขอที่อยู่อื่น เช่น _127.0.0.1:7878/test_ เพื่อดูว่าข้อมูลคำขอเปลี่ยนแปลงไปอย่างไร

ตอนนี้ที่เรารู้แล้วว่าเบราว์เซอร์กำลังขออะไร มาส่งข้อมูลกลับไปกัน!

### การเขียนการตอบกลับ

เรากำลังจะอิมพลีเมนต์การส่งข้อมูลเพื่อตอบสนองต่อคำขอของไคลเอนต์ การตอบกลับมีรูปแบบดังต่อไปนี้:

```text
HTTP-Version Status-Code Reason-Phrase CRLF
headers CRLF
message-body
```

บรรทัดแรกคือ_บรรทัดสถานะ_ (status line) ซึ่งบรรจุเวอร์ชัน HTTP ที่ใช้ในการตอบกลับ รหัสสถานะที่เป็นตัวเลขซึ่งสรุปผลลัพธ์ของคำขอ และวลีเหตุผล (reason phrase) ที่ให้คำอธิบายเป็นข้อความของรหัสสถานะ หลังจากลำดับ CRLF จะเป็นเฮดเดอร์ใดๆ ตามด้วยลำดับ CRLF อีกอัน และบอดี้ของการตอบกลับ

นี่คือตัวอย่างการตอบกลับที่ใช้ HTTP เวอร์ชัน 1.1 และมีรหัสสถานะ 200 วลีเหตุผล OK ไม่มีเฮดเดอร์ และไม่มีบอดี้:

```text
HTTP/1.1 200 OK\r\n\r\n
```

รหัสสถานะ 200 คือการตอบกลับความสำเร็จมาตรฐาน ข้อความนี้เป็นการตอบกลับ HTTP ที่สำเร็จขนาดจิ๋ว มาเขียนมันลงในสตรีมเป็นการตอบกลับของเราต่อคำขอที่สำเร็จกัน! จากฟังก์ชัน `handle_connection` ให้ลบ `println!` ที่พิมพ์ข้อมูลคำขอออก และแทนที่ด้วยโค้ดในลิสติ้ง 21-3

ด้วยการเปลี่ยนแปลงเหล่านี้ ให้รันเซิร์ฟเวอร์ของคุณอีกครั้ง การขอ _127.0.0.1:7878_ ควรคืนค่าเนื้อหาของ _hello.html_ และคำขออื่นใด เช่น _127.0.0.1:7878/foo_ ควรคืนค่า HTML ข้อผิดพลาดจาก _404.html_

### การรีแฟกเตอร์

ในขณะนี้ บล็อก `if` และ `else` มีการทำซ้ำกันมาก ทั้งคู่อ่านไฟล์และเขียนเนื้อหาของไฟล์ลงในสตรีม ความแตกต่างเพียงอย่างเดียวคือบรรทัดสถานะและชื่อไฟล์ มาทำให้โค้ดกระชับยิ่งขึ้นโดยดึงความแตกต่างเหล่านั้นออกมาเป็นบรรทัด `if` และ `else` แยกกันที่จะกำหนดค่าของบรรทัดสถานะและชื่อไฟล์ให้กับตัวแปร จากนั้นเราสามารถใช้ตัวแปรเหล่านั้นได้โดยไม่มีเงื่อนไขในโค้ดเพื่ออ่านไฟล์และเขียนการตอบกลับ ลิสติ้ง 21-9 แสดงโค้ดที่ได้หลังจากแทนที่บล็อก `if` และ `else` ขนาดใหญ่

ตอนนี้บล็อก `if` และ `else` คืนค่าเฉพาะค่าที่เหมาะสมสำหรับบรรทัดสถานะและชื่อไฟล์ในทูเพิล (tuple) จากนั้นเราใช้การแยกโครงสร้างข้อมูล (destructuring) เพื่อกำหนดค่าสองค่าเหล่านี้ให้กับ `status_line` และ `filename` โดยใช้แพตเทิร์น (pattern) ในสเตตเมนต์ `let` ดังที่ได้อภิปรายในบทที่ 19

โค้ดที่ก่อนหน้านี้ซ้ำกันตอนนี้อยู่นอกบล็อก `if` และ `else` และใช้ตัวแปร `status_line` และ `filename` สิ่งนี้ทำให้เห็นความแตกต่างระหว่างสองกรณีได้ง่ายขึ้น และหมายความว่าเรามีที่ให้อัปเดตโค้ดเพียงที่เดียวหากเราต้องการเปลี่ยนวิธีที่การอ่านไฟล์และการเขียนการตอบกลับทำงาน พฤติกรรมของโค้ดในลิสติ้ง 21-9 จะเหมือนกับโค้ดในลิสติ้ง 21-7

เยี่ยมมาก! ตอนนี้เรามีเว็บเซิร์ฟเวอร์ง่ายๆ ในโค้ด Rust ประมาณ 40 บรรทัด ที่ตอบสนองต่อคำขอหนึ่งคำขอด้วยหน้าเว็บที่มีเนื้อหา และตอบสนองต่อคำขออื่นๆ ทั้งหมดด้วยการตอบกลับ 404

ในปัจจุบัน เซิร์ฟเวอร์ของเรารันในเธรดเดียว หมายความว่ามันให้บริการได้เพียงหนึ่งคำขอในแต่ละครั้ง มาดูกันว่าสิ่งนั้นกลายเป็นปัญหาได้อย่างไรโดยการจำลองคำขอที่ช้า จากนั้นเราจะแก้ไขมันเพื่อให้เซิร์ฟเวอร์ของเราจัดการหลายคำขอพร้อมกันได้
