## สร้างเว็บเซิร์ฟเวอร์แบบเธรดเดียว

เราจะเริ่มต้นด้วยการสร้างเว็บเซิร์ฟเวอร์ (web server) แบบเธรดเดียว (single-threaded) ให้ทำงานได้ก่อน ก่อนเริ่มลงมือเขียนโค้ด มาดูภาพรวมสั้น ๆ ของโปรโตคอล (protocols) ที่เกี่ยวข้องกับการสร้างเว็บเซิร์ฟเวอร์กันสักนิด แม้รายละเอียดเชิงลึกของโปรโตคอลเหล่านี้จะอยู่นอกเหนือขอบเขตของหนังสือเล่มนี้ แต่ภาพรวมโดยสังเขปจะช่วยปูพื้นฐานข้อมูลที่จำเป็นทั้งหมดที่คุณต้องใช้

โปรโตคอลหลักสองตัวที่เกี่ยวข้องกับเว็บเซิร์ฟเวอร์คือ _Hypertext Transfer Protocol_ _(HTTP)_ และ _Transmission Control Protocol_ _(TCP)_ ทั้งคู่จัดเป็นโปรโตคอลรูปแบบ _คำขอ-การตอบกลับ (request-response)_ ซึ่งหมายความว่า _ไคลเอนต์ (client)_ จะเป็นฝ่ายเริ่มส่งคำขอ (request) ส่วน _เซิร์ฟเวอร์ (server)_ จะคอยรอรับคำขอดังกล่าวแล้วส่งการตอบกลับ (response) แก่ไคลเอนต์ โดยเนื้อหาของคำขอและการตอบกลับจะถูกกำหนดไว้ตามข้อกำหนดของโปรโตคอล

TCP เป็นโปรโตคอลระดับล่าง (lower-level) ที่อธิบายรายละเอียดการเดินทางของข้อมูลจากคอมพิวเตอร์เครื่องหนึ่งไปยังอีกเครื่องหนึ่ง แต่ไม่ได้ระบุว่าข้อมูลนั้นคืออะไร ส่วน HTTP จะสร้างต่อยอดขึ้นมาจาก TCP โดยกำหนดรูปแบบเนื้อหาของคำขอและการตอบกลับ แม้ในทางเทคนิคเราจะใช้ HTTP ร่วมกับโปรโตคอลอื่นได้ ทว่าในกรณีส่วนใหญ่แล้ว HTTP จะส่งข้อมูลผ่าน TCP และในบทนี้ เราจะทำงานกับข้อมูลไบต์ดิบ (raw bytes) ของคำขอและการตอบกลับทั้งในระดับ TCP และ HTTP

### การรอฟังการเชื่อมต่อ TCP

เว็บเซิร์ฟเวอร์ของเราจำเป็นต้องคอยรอรับการเชื่อมต่อ TCP นี่จึงเป็นส่วนแรกที่เราจะลงมือสร้าง ไลบรารีมาตรฐานของ Rust มีมอดูล `std::net` สำหรับจัดการเรื่องนี้โดยเฉพาะ มาเริ่มสร้างโปรเจกต์ใหม่ตามขั้นตอนปกติกัน:

```console
$ cargo new hello
     Created binary (application) `hello` project
$ cd hello
```

การใช้ `TcpListener` ทำให้เราสามารถรอรับการเชื่อมต่อ TCP ที่แอดเดรส `127.0.0.1:7878` ได้ สำหรับแอดเดรสนี้ ส่วนที่อยู่ข้างหน้าเครื่องหมายโคลอนคือ IP address ที่แทนเครื่องคอมพิวเตอร์ของคุณเอง (ซึ่งมีค่าเหมือนกันบนทุกเครื่อง และไม่ได้ระบุถึงเครื่องของผู้เขียนโดยเฉพาะ) ส่วน `7878` คือหมายเลขพอร์ต (port) เราเลือกใช้พอร์ตนี้ด้วยเหตุผลสองประการ: ประการแรก โดยปกติพอร์ตนี้ไม่ได้ใช้รับส่งข้อมูล HTTP เซิร์ฟเวอร์ของเราจึงแทบไม่มีโอกาสชนกับเว็บเซิร์ฟเวอร์อื่นที่คุณอาจรันอยู่บนเครื่อง และประการที่สอง เลข 7878 หากกดแป้นพิมพ์โทรศัพท์ปุ่มตัวเลขจะสะกดได้เป็นคำว่า _rust_

ฟังก์ชัน `bind` ในบริบทนี้ทำงานคล้ายกับฟังก์ชัน `new` โดยจะคืนค่าอินสแตนซ์ใหม่ของ `TcpListener` ฟังก์ชันนี้ใช้ชื่อว่า `bind` เพราะในแวดวงระบบเครือข่าย การเชื่อมต่อไปยังพอร์ตเพื่อรอรับการเชื่อมต่อนั้นเรียกว่า “การผูกติดกับพอร์ต (binding to a port)”

ฟังก์ชัน `bind` จะคืนค่าเป็น `Result<T, E>` ซึ่งบ่งชี้ว่าการผูกพอร์ตอาจล้มเหลวได้ เช่น ในกรณีที่เรารันโปรแกรมนี้ขึ้นมาพร้อมกันสองอินสแตนซ์ ทำให้มีโปรแกรมสองตัวพยายามรอรับการเชื่อมต่อที่พอร์ตเดียวกัน แต่เนื่องจากเรากำลังเขียนเซิร์ฟเวอร์พื้นฐานเพื่อการเรียนรู้ เราจึงยังไม่ต้องกังวลกับการจัดการข้อผิดพลาดเหล่านี้ และจะเลือกใช้ `unwrap` เพื่อหยุดการทำงานของโปรแกรมทันทีหากเกิดข้อผิดพลาดขึ้น

เมธอด `incoming` บน `TcpListener` จะคืนค่าเป็นอิเทอเรเตอร์ (iterator) ที่ส่งมอบลำดับของสตรีม (stream) ให้แก่เรา (เจาะจงคือสตรีมชนิด `TcpStream`) โดย _สตรีม_ หนึ่งตัวจะแทนการเชื่อมต่อที่เปิดอยู่ระหว่างไคลเอนต์กับเซิร์ฟเวอร์ คำว่า _การเชื่อมต่อ (connection)_ เป็นชื่อเรียกกระบวนการรับส่งคำขอและการตอบกลับแบบครบวงจร ตั้งแต่ไคลเอนต์เชื่อมต่อไปยังเซิร์ฟเวอร์ เซิร์ฟเวอร์สร้างการตอบกลับ ไปจนถึงเซิร์ฟเวอร์ปิดการเชื่อมต่อลง ดังนั้นเราจึงสามารถอ่านข้อมูลจาก `TcpStream` เพื่อดูว่าไคลเอนต์ส่งสิ่งใดมา แล้วเขียนข้อมูลการตอบกลับของเราลงในสตรีมเพื่อส่งกลับไปยังไคลเอนต์ โดยสรุปแล้ว ลูป `for` นี้จะประมวลผลการเชื่อมต่อแต่ละรายการตามลำดับ และสร้างชุดของสตรีมออกมาให้เราจัดการ

ในตอนนี้ การจัดการสตรีมของเรามีเพียงการเรียก `unwrap` เพื่อหยุดโปรแกรมหากพบข้อผิดพลาดในสตรีม แต่หากไม่มีข้อผิดพลาด โปรแกรมก็จะพิมพ์ข้อความออกมา เราจะเพิ่มฟังก์ชันการทำงานในกรณีที่สำเร็จในลิสติ้งถัดไป สาเหตุที่เราอาจได้รับข้อผิดพลาดจากเมธอด `incoming` ขณะที่ไคลเอนต์เชื่อมต่อเข้ามาก็คือ ในความเป็นจริงแล้วเราไม่ได้กำลังวนซ้ำการเชื่อมต่อที่สมบูรณ์ แต่เรากำลังวนซ้ำ _ความพยายามในการเชื่อมต่อ (connection attempts)_ ซึ่งการเชื่อมต่ออาจล้มเหลวได้จากหลายสาเหตุ โดยหลายสาเหตุมักขึ้นอยู่กับระบบปฏิบัติการโดยเฉพาะ เช่น ระบบปฏิบัติการหลายระบบมีขีดจำกัดจำนวนการเชื่อมต่อพร้อมกันที่สามารถเปิดค้างไว้ได้ หากมีความพยายามเชื่อมต่อใหม่เข้ามาเกินขีดจำกัดดังกล่าว ก็จะเกิดข้อผิดพลาดขึ้นจนกว่าการเชื่อมต่อที่เปิดอยู่บางส่วนจะปิดลง

มาลองรันโค้ดนี้กัน! เรียกใช้คำสั่ง `cargo run` ในเทอร์มินัล จากนั้นเปิดแอดเดรส _127.0.0.1:7878_ บนเว็บเบราว์เซอร์ เบราว์เซอร์จะแสดงข้อผิดพลาด เช่น “Connection reset” เนื่องจากเซิร์ฟเวอร์ยังไม่ได้ส่งข้อมูลใด ๆ กลับไป แต่เมื่อคุณสลับมาดูที่เทอร์มินัล คุณจะเห็นข้อความปรากฏขึ้นหลายบรรทัดเมื่อเบราว์เซอร์เชื่อมต่อเข้ามายังเซิร์ฟเวอร์!

```text
     Running `target/debug/hello`
Connection established!
Connection established!
Connection established!
```

ในบางครั้งคุณอาจเห็นข้อความพิมพ์ซ้ำหลายครั้งสำหรับการเรียกหน้าเว็บบนเบราว์เซอร์เพียงครั้งเดียว สาเหตุอาจเกิดจากการที่เบราว์เซอร์ส่งคำขอเพื่อดึงหน้าเว็บ ควบคู่ไปกับคำขอทรัพยากรอื่น ๆ เช่น ไอคอน _favicon.ico_ ที่แสดงบนแท็บของเบราว์เซอร์

อีกสาเหตุหนึ่งอาจเป็นเพราะเบราว์เซอร์พยายามเชื่อมต่อกับเซิร์ฟเวอร์ซ้ำหลายครั้งเนื่องจากเซิร์ฟเวอร์ไม่ได้ตอบกลับข้อมูลใด ๆ กลับไป เมื่อตัวแปร `stream` หลุดออกจากขอบเขต (scope) และถูกทำลายทิ้งที่จุดสิ้นสุดของลูป การเชื่อมต่อจะถูกปิดลงโดยอัตโนมัติผ่านการทำงานของ `drop` ซึ่งในบางครั้งเบราว์เซอร์จะรับมือกับการเชื่อมต่อที่ถูกปิดกะทันหันด้วยการลองส่งคำขอใหม่อีกครั้ง เนื่องจากประเมินว่าอาจเป็นปัญหาชั่วคราว

นอกจากนี้ เบราว์เซอร์บางตัวยังอาจเปิดการเชื่อมต่อทิ้งไว้หลายรายการโดยไม่ส่งคำขอใด ๆ เพื่อที่ว่าเมื่อถึงเวลาต้อง *ส่งคำขอจริง* คำขอนั้นจะเกิดขึ้นได้อย่างรวดเร็วทันที เมื่อเกิดเหตุการณ์นี้ขึ้น เซิร์ฟเวอร์ของเราจะมองเห็นการเชื่อมต่อแต่ละรายการเข้ามา ไม่ว่าจะมีข้อมูลคำขอส่งผ่านการเชื่อมต่อนั้นจริงหรือไม่ก็ตาม ตัวอย่างเช่น เบราว์เซอร์ตระกูล Chromium มักใช้วิธีนี้ คุณสามารถปิดการทำงานนี้ได้ด้วยการเปิดโหมดท่องเว็บแบบส่วนตัว (incognito/private mode) หรือเปลี่ยนไปใช้เบราว์เซอร์อื่น

สิ่งที่สำคัญที่สุดคือ ตอนนี้เราได้รับแฮนเดิล (handle) สำหรับการเชื่อมต่อ TCP ได้สำเร็จแล้ว!

อย่าลืมหยุดการทำงานของโปรแกรมโดยกด <kbd>ctrl</kbd>-<kbd>C</kbd> เมื่อคุณทดสอบโค้ดแต่ละรอบเสร็จสิ้น จากนั้นค่อยเริ่มรันโปรแกรมใหม่อีกครั้งด้วยคำสั่ง `cargo run` หลังจากแก้ไขโค้ดในแต่ละช่วง เพื่อให้มั่นใจว่าคุณกำลังรันโปรแกรมเวอร์ชันล่าสุดอยู่เสมอ

เรานำ `std::io::BufReader` และ `std::io::prelude` เข้ามาสู่ขอบเขตการทำงานเพื่อให้สามารถเข้าถึงเทรต (traits) และชนิดข้อมูลที่ใช้ในการอ่านและเขียนข้อมูลลงสตรีมได้ และภายในลูป `for` ของฟังก์ชัน `main` แทนที่จะพิมพ์ข้อความแจ้งว่าเชื่อมต่อสำเร็จ เราจะเปลี่ยนมาเรียกฟังก์ชัน `handle_connection` และส่ง `stream` เข้าไปแทน

ภายในฟังก์ชัน `handle_connection` เราสร้างอินสแตนซ์ใหม่ของ `BufReader` ที่ครอบการอ้างอิง (reference) ไปยัง `stream` เอาไว้ ซึ่ง `BufReader` จะช่วยเพิ่มความสามารถในการบัฟเฟอร์ข้อมูล (buffering) โดยจัดการการเรียกใช้เมธอดต่าง ๆ จากเทรต `std::io::Read` ให้เราโดยอัตโนมัติ

เราสร้างตัวแปรชื่อ `http_request` เพื่อรวบรวมแต่ละบรรทัดของคำขอที่เบราว์เซอร์ส่งมายังเซิร์ฟเวอร์ของเรา และระบุว่าต้องการรวบรวมข้อมูลเหล่านี้ไว้ในเวกเตอร์ (vector) ด้วยการใส่คำกำกับชนิดข้อมูล (type annotation) เป็น `Vec<_>`

`BufReader` อิมพลีเมนต์เทรต `std::io::BufRead` ซึ่งมีเมธอด `lines` ให้ใช้งาน โดยเมธอด `lines` จะคืนค่าเป็นอิเทอเรเตอร์ของ `Result<String, std::io::Error>` จากการตัดแบ่งสตรีมข้อมูลทุกครั้งที่พบไบต์ขึ้นบรรทัดใหม่ (newline byte) และเพื่อให้ได้ข้อความ `String` แต่ละบรรทัด เราจึงใช้ `map` ร่วมกับ `unwrap` บนแต่ละค่า `Result` ทั้งนี้ ค่า `Result` อาจเป็นข้อผิดพลาดได้หากข้อมูลที่อ่านเข้ามาไม่ใช่ UTF-8 ที่ถูกต้อง หรือหากเกิดปัญหาในการอ่านข้อมูลจากสตรีม ซึ่งเช่นเคยว่า ในโปรแกรมระดับโปรดักชันจริงควรจัดการข้อผิดพลาดเหล่านี้อย่างรอบคอบและปลอดภัยกว่านี้ แต่ในที่นี้เราเลือกหยุดโปรแกรมทันทีหากเกิดข้อผิดพลาดเพื่อความกระชับและเข้าใจง่าย

เบราว์เซอร์จะส่งสัญญาณบ่งบอกจุดสิ้นสุดของคำขอ HTTP ด้วยการส่งอักขระขึ้นบรรทัดใหม่ 2 ตัวติดต่อกัน ดังนั้นเพื่อให้ได้คำขอครบถ้วนหนึ่งรายการจากสตรีม เราจึงอ่านข้อมูลทีละบรรทัดไปเรื่อย ๆ จนกระทั่งพบบรรทัดที่เป็นสตริงว่าง เมื่อรวบรวมบรรทัดทั้งหมดลงในเวกเตอร์เรียบร้อยแล้ว เราก็สั่งพิมพ์ข้อมูลออกมาด้วยรูปแบบการดีบักแบบสวยงาม เพื่อให้เราสามารถตรวจสอบเนื้อหาคำขอที่เว็บเบราว์เซอร์ส่งมายังเซิร์ฟเวอร์ได้อย่างชัดเจน

### การดูคำขอ HTTP อย่างใกล้ชิดยิ่งขึ้น

HTTP เป็นโปรโตคอลแบบข้อความ (text-based protocol) โดยคำขอมีรูปแบบมาตรฐานดังนี้:

```text
Method Request-URI HTTP-Version CRLF
headers CRLF
message-body
```

บรรทัดแรกเรียกว่า _บรรทัดคำขอ (request line)_ ซึ่งบรรจุข้อมูลเกี่ยวกับสิ่งที่ไคลเอนต์กำลังร้องขอ ส่วนแรกของบรรทัดคำขอจะระบุเมธอด (method) ที่ใช้ เช่น `GET` หรือ `POST` เพื่ออธิบายว่าไคลเอนต์ต้องการทำสิ่งใด ไคลเอนต์ของเราส่งคำขอเป็น `GET` ซึ่งหมายถึงการขอดึงข้อมูล

ส่วนถัดมาของบรรทัดคำขอคือ _/_ ซึ่งระบุ _uniform resource identifier_ _(URI)_ ของทรัพยากรที่ไคลเอนต์กำลังร้องขอ แม้ว่า URI จะมีความหมายคล้ายคลึงกับ _uniform resource locator_ _(URL)_ เกือบทั้งหมดแต่ก็ไม่เหมือนกันเสียทีเดียว อย่างไรก็ตาม ความแตกต่างระหว่าง URI กับ URL ไม่ได้ส่งผลต่อเนื้อหาในบทนี้ แต่เนื่องจากข้อกำหนดมาตรฐานของ HTTP เลือกใช้คำว่า _URI_ คุณจึงสามารถนึกภาพเปรียบเทียบคำว่า _URI_ ตรงนี้เป็น _URL_ ในใจได้เลย

ส่วนสุดท้ายคือเวอร์ชันของ HTTP ที่ไคลเอนต์ใช้ จากนั้นบรรทัดคำขอจะลงท้ายด้วยลำดับ CRLF (คำว่า _CRLF_ ย่อมาจาก _carriage return_ และ _line feed_ ซึ่งเป็นคำที่สืบทอดมาจากยุคของเครื่องพิมพ์ดีด!) ลำดับ CRLF สามารถเขียนแทนได้ด้วย `\r\n` โดยที่ `\r` คือ carriage return และ `\n` คือ line feed ทั้งนี้ _ลำดับ CRLF_ มีหน้าที่คั่นแบ่งบรรทัดคำขอออกจากข้อมูลส่วนที่เหลือของคำขอ และโปรดสังเกตว่าเมื่อพิมพ์ CRLF ออกมาทางหน้าจอ เราจะเห็นเป็นการขึ้นบรรทัดใหม่ ไม่ใช่ตัวอักษร `\r\n`

เมื่อพิจารณาข้อมูลบรรทัดคำขอที่เราได้รับจากการรันโปรแกรมจนถึงตอนนี้ จะเห็นว่า `GET` คือเมธอด, _/_ คือ URI ของคำขอ และ `HTTP/1.1` คือเวอร์ชัน

ถัดจากบรรทัดคำขอ บรรทัดที่เหลือทั้งหมดตั้งแต่ `Host:` เป็นต้นไปคือส่วนหัวของคำขอ หรือเฮดเดอร์ (headers) โดยคำขอแบบ `GET` จะไม่มีส่วนของเนื้อหา หรือบอดี้ (body)

ลองเปิดส่งคำขอจากเบราว์เซอร์ตัวอื่น หรือลองเรียกแอดเดรสอื่นดู เช่น _127.0.0.1:7878/test_ เพื่อสังเกตดูว่าข้อมูลของคำขอเปลี่ยนแปลงไปอย่างไรบ้าง

เมื่อเราเข้าใจแล้วว่าเบราว์เซอร์ส่งคำขออะไรมา คราวนี้มาเขียนโค้ดเพื่อส่งข้อมูลกลับไปกัน!

### การเขียนการตอบกลับ

เราจะลงมือเขียนส่วนการส่งข้อมูลกลับไปเพื่อตอบรับคำขอจากไคลเอนต์ โดยโครงสร้างของการตอบกลับ (response) มีรูปแบบมาตรฐานดังนี้:

```text
HTTP-Version Status-Code Reason-Phrase CRLF
headers CRLF
message-body
```

บรรทัดแรกเรียกว่า _บรรทัดสถานะ (status line)_ ซึ่งประกอบด้วยเวอร์ชัน HTTP ที่ใช้ตอบกลับ, รหัสสถานะ (status code) แบบตัวเลขที่สรุปผลลัพธ์ของคำขอ และข้อความบอกเหตุผล (reason phrase) ที่อธิบายความหมายของรหัสสถานะนั้นเป็นข้อความ ถัดจากลำดับ CRLF จะเป็นส่วนของเฮดเดอร์ (headers) ตามด้วยลำดับ CRLF อีกชุดหนึ่ง แล้วจึงเป็นส่วนเนื้อหาของการตอบกลับ หรือบอดี้ (message-body)

ตัวอย่างด้านล่างคือข้อความตอบกลับที่ใช้ HTTP เวอร์ชัน 1.1 มีรหัสสถานะ 200 พร้อมข้อความเหตุผล OK โดยไม่มีทั้งเฮดเดอร์และบอดี้:

```text
HTTP/1.1 200 OK\r\n\r\n
```

รหัสสถานะ 200 คือรหัสมาตรฐานที่บ่งบอกว่าการทำงานสำเร็จ ข้อความนี้จึงถือเป็นการตอบกลับ HTTP ที่สำเร็จในขนาดเล็กที่สุดเท่าที่จะทำได้ มาลองเขียนข้อความนี้ลงในสตรีมเพื่อตอบรับคำขอที่สำเร็จกัน! ในฟังก์ชัน `handle_connection` ให้ลบคำสั่ง `println!` ที่ใช้พิมพ์ข้อมูลคำขอออก แล้วแทนที่ด้วยโค้ดในลิสติ้ง 21-3

ในตอนนี้ เรายังไม่ได้นำข้อมูลคำขอในตัวแปร `http_request` มาพิจารณาเลย แต่เลือกส่งเนื้อหาของไฟล์ HTML กลับไปทันทีโดยไม่มีเงื่อนไขใด ๆ นั่นหมายความว่าหากคุณลองเรียก _127.0.0.1:7878/something-else_ บนเบราว์เซอร์ คุณก็จะยังได้รับหน้า HTML เดิมนี้กลับมาอยู่ดี ในขณะนี้ เซิร์ฟเวอร์ของเราจึงยังมีข้อจำกัดอย่างมากและยังทำงานได้ไม่เหมือนเว็บเซิร์ฟเวอร์ทั่วไป สิ่งที่เราต้องการคือการปรับแต่งการตอบกลับให้สอดคล้องกับคำขอ โดยส่งไฟล์ HTML กลับไปเฉพาะคำขอที่ถูกต้องและเรียกมายังพาธ _/_ เท่านั้น

### การตรวจสอบความถูกต้องของคำขอและการตอบกลับอย่างเลือกสรร

ในปัจจุบัน เว็บเซิร์ฟเวอร์ของเราจะส่งไฟล์ HTML กลับไปเสมอไม่ว่าไคลเอนต์จะร้องขอพาธใดก็ตาม มาเพิ่มฟังก์ชันการทำงานเพื่อตรวจสอบว่าเบราว์เซอร์ร้องขอพาธ _/_ หรือไม่ ก่อนจะส่งไฟล์ HTML กลับไป และหากร้องขอพาธอื่นก็ให้ส่งข้อผิดพลาดกลับไปแทน ด้วยเหตุนี้ เราจึงต้องปรับแก้ฟังก์ชัน `handle_connection` ดังที่แสดงในลิสติ้ง 21-6 โค้ดใหม่นี้จะตรวจเช็กเนื้อหาของคำขอที่ได้รับเทียบกับรูปแบบคำขอที่เรียกมายัง _/_ พร้อมทั้งเพิ่มบล็อก `if` และ `else` เพื่อจัดการแต่ละกรณีให้แตกต่างกัน

### การรีแฟกเตอร์

ในตอนนี้ บล็อก `if` และ `else` มีการทำงานที่ซ้ำซ้อนกันมาก ทั้งคู่อ่านไฟล์และเขียนเนื้อหาของไฟล์ลงในสตรีม โดยจุดที่ต่างกันมีเพียงบรรทัดสถานะกับชื่อไฟล์เท่านั้น มาปรับโค้ดให้กระชับยิ่งขึ้นโดยแยกส่วนที่ต่างกันออกมาไว้ในนิพจน์ `if` และ `else` เพื่อกำหนดค่าของบรรทัดสถานะและชื่อไฟล์ให้กับตัวแปร จากนั้นเราจะสามารถนำตัวแปรเหล่านั้นมาใช้งานร่วมกันในโค้ดส่วนที่อ่านไฟล์และเขียนการตอบกลับได้โดยตรง ลิสติ้ง 21-9 แสดงผลลัพธ์ของโค้ดหลังจากปรับแทนที่บล็อก `if` และ `else` เดิม
