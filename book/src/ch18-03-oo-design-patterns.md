## อิมพลีเมนต์แพตเทิร์นการออกแบบเชิงวัตถุ

_แพตเทิร์นสถานะ_ (state pattern) เป็นหนึ่งในแบบแผนการออกแบบเชิงวัตถุ หัวใจสำคัญของแพตเทิร์นนี้คือการนิยามชุดของสถานะที่ค่าหนึ่ง ๆ สามารถมีได้ภายในตัว สถานะเหล่านี้จะถูกแทนด้วยชุดของ_ออบเจกต์สถานะ_ (state objects) และพฤติกรรมของค่านั้นจะเปลี่ยนไปตามสถานะที่เป็นอยู่ เราจะมาลงมือทำตัวอย่าง struct โพสต์บล็อกที่มีฟิลด์เก็บสถานะของมัน ซึ่งจะเป็นออบเจกต์สถานะจากชุด "draft" (ฉบับร่าง), "review" (รอตรวจสอบ) หรือ "published" (เผยแพร่แล้ว)

ออบเจกต์สถานะเหล่านี้จะใช้ฟังก์ชันการทำงานร่วมกัน: แน่นอนว่าใน Rust เราจะใช้ struct และเทรต แทนที่จะเป็นออบเจกต์และการสืบทอด ออบเจกต์สถานะแต่ละตัวจะรับผิดชอบพฤติกรรมของตนเองและคอยควบคุมว่าจะเปลี่ยนผ่านไปยังอีกสถานะหนึ่งเมื่อใด โดยที่ค่าตัวนอกที่ถือออบเจกต์สถานะนั้นไว้ ไม่จำเป็นต้องรู้เรื่องพฤติกรรมที่แตกต่างกันของแต่ละสถานะ หรือจังหวะเวลาในการเปลี่ยนสถานะเลย

ข้อดีของการใช้แพตเทิร์นสถานะคือ เมื่อความต้องการทางธุรกิจของโปรแกรมเปลี่ยนไป เราไม่จำเป็นต้องแก้ไขโค้ดของค่าที่เก็บสถานะหรือโค้ดส่วนอื่นที่เรียกใช้ค่านั้นเลย เราเพียงแค่อัปเดตโค้ดภายในออบเจกต์สถานะตัวใดตัวหนึ่งเพื่อปรับเปลี่ยนกฎเกณฑ์ หรือเพิ่มออบเจกต์สถานะใหม่เข้าไปเท่านั้น

ก่อนอื่น เราจะมาอิมพลีเมนต์แพตเทิร์นสถานะในสไตล์เชิงวัตถุแบบดั้งเดิมกันก่อน จากนั้นเราจะขยับไปใช้วิธีการที่เป็นธรรมชาติและเข้ากับ Rust มากกว่าเดิม ลองมาเจาะลึกเพื่ออิมพลีเมนต์เวิร์กโฟลว์ของโพสต์บล็อกโดยใช้แพตเทิร์นสถานะทีละขั้นตอนกัน

ฟังก์ชันการทำงานขั้นสุดท้ายจะมีหน้าตาดังนี้:

1. โพสต์บล็อกจะเริ่มต้นจากการเป็นแบบร่างที่ว่างเปล่า (empty draft)
1. เมื่อเขียนแบบร่างเสร็จแล้ว จะมีการส่งคำขอให้ตรวจสอบโพสต์ (request review)
1. เมื่อโพสต์ได้รับการอนุมัติ (approved) จึงจะถูกเผยแพร่ (published)
1. มีเพียงโพสต์บล็อกที่เผยแพร่แล้วเท่านั้นที่จะส่งคืนเนื้อหาออกมาพิมพ์ได้ เพื่อป้องกันไม่ให้โพสต์ที่ยังไม่ได้รับอนุมัติถูกเผยแพร่โดยไม่ได้ตั้งใจ

การพยายามเปลี่ยนแปลงอื่นใดนอกเหนือจากนี้กับโพสต์จะต้องไม่มีผลอะไรเกิดขึ้น ตัวอย่างเช่น หากเราพยายามอนุมัติโพสต์บล็อกที่ยังเป็นฉบับร่างอยู่ก่อนที่จะส่งคำขอตรวจสอบ โพสต์นั้นก็จะต้องยังคงเป็นฉบับร่างที่ยังไม่เผยแพร่อยู่เช่นเดิม

### การลองใช้สไตล์เชิงวัตถุแบบดั้งเดิม

มีวิธีจัดโครงสร้างโค้ดเพื่อแก้ปัญหาเดียวกันนี้ได้หลากหลายรูปแบบนับไม่ถ้วน โดยแต่ละวิธีก็มีข้อแลกเปลี่ยนที่ต่างกันไป การอิมพลีเมนต์ในหัวข้อนี้จะเน้นไปที่สไตล์เชิงวัตถุแบบดั้งเดิม ซึ่งแม้จะสามารถเขียนใน Rust ได้ แต่ก็ยังไม่ได้ใช้ประโยชน์จากจุดแข็งหลายประการของ Rust อย่างเต็มที่ ในภายหลังเราจะสาธิตอีกวิธีแก้ปัญหาหนึ่งซึ่งยังคงประยุกต์ใช้แบบแผนการออกแบบเชิงวัตถุอยู่ แต่ถูกจัดโครงสร้างในรูปแบบที่อาจดูแปลกตาสำหรับโปรแกรมเมอร์ที่คุ้นชินกับ OOP มาก่อน เราจะเปรียบเทียบวิธีแก้ปัญหาทั้งสองแบบ เพื่อให้เห็นถึงข้อแลกเปลี่ยนในการออกแบบโค้ด Rust ที่แตกต่างไปจากภาษาอื่น ๆ

ถัดไป เราต้องการให้สามารถส่งคำขอตรวจสอบโพสต์ได้ และต้องการให้ `content` ยังคงคืนสตริงว่างออกมาในระหว่างที่รอการตรวจสอบ และเมื่อโพสต์ได้รับการอนุมัติแล้ว มันก็ควรถูกเผยแพร่ ซึ่งหมายความว่าเมธอด `content` จะคืนข้อความทั้งหมดของโพสต์กลับมาเมื่อถูกเรียกใช้

โปรดสังเกตว่า ชนิดข้อมูลเดียวที่เรามีปฏิสัมพันธ์ด้วยจากเครตนี้คือชนิดข้อมูล `Post` ชนิดข้อมูลนี้จะประยุกต์ใช้แพตเทิร์นสถานะและถือค่าที่จะเป็นหนึ่งในสามออบเจกต์สถานะเพื่อแทนสถานะต่าง ๆ ของโพสต์ ได้แก่ draft (ฉบับร่าง), review (รอตรวจสอบ) หรือ published (เผยแพร่แล้ว) การเปลี่ยนผ่านจากสถานะหนึ่งไปยังอีกสถานะหนึ่งจะถูกจัดการอยู่ภายในชนิดข้อมูล `Post` ทั้งหมด สถานะจะเปลี่ยนไปตามเมธอดต่าง ๆ ที่ผู้ใช้ไลบรารีเรียกใช้บนอินสแตนซ์ของ `Post` โดยที่ผู้ใช้ไม่ต้องมาคอยจัดการการเปลี่ยนสถานะด้วยตนเอง นอกจากนี้ ผู้ใช้ยังไม่สามารถสร้างข้อผิดพลาดเกี่ยวกับสถานะได้ เช่น การเผยแพร่โพสต์ก่อนที่มันจะผ่านการตรวจสอบ

เราเพิ่มพับลิกเมธอดชื่อ `request_review` ให้กับ `Post` ซึ่งจะรับเรเฟอเรนซ์แบบเปลี่ยนแปลงค่าได้ของ `self` จากนั้นเราจะเรียกใช้เมธอด `request_review` ภายในบนสถานะปัจจุบันของ `Post` โดยเมธอด `request_review` ตัวที่สองนี้จะบริโภค (consume) สถานะปัจจุบันแล้วส่งคืนสถานะใหม่ออกมา

เราเพิ่มเมธอด `request_review` เข้าไปในเทรต `State` ดังนั้นทุกชนิดข้อมูลที่อิมพลีเมนต์เทรตนี้จะต้องมีเมธอด `request_review` ด้วย โปรดสังเกตว่า แทนที่จะใช้ `self`, `&self` หรือ `&mut self` เป็นพารามิเตอร์ตัวแรกของเมธอด เรากลับใช้ `self: Box<Self>` ไวยากรณ์นี้หมายความว่า เมธอดนี้จะเรียกใช้ได้เฉพาะเมื่อถูกเรียกบน `Box` ที่ถือชนิดข้อมูลนั้นอยู่เท่านั้น และไวยากรณ์นี้จะรับความเป็นเจ้าของ (ownership) `Box<Self>` ไป ทำให้สถานะเดิมใช้งานไม่ได้อีก เพื่อเปิดทางให้ค่าสถานะของ `Post` แปลงร่างไปเป็นสถานะใหม่

ในการบริโภคสถานะเดิม เมธอด `request_review` จำเป็นต้องรับความเป็นเจ้าของค่าของสถานะนั้น นี่คือจุดที่ `Option` ในฟิลด์ `state` ของ `Post` เข้ามามีบทบาทสำคัญ: เราจะเรียกเมธอด `take` เพื่อดึงค่า `Some` ออกจากฟิลด์ `state` แล้ววางค่า `None` ไว้แทนที่ เพราะ Rust ไม่อนุญาตให้เราปล่อยฟิลด์ใน struct ว่างเปล่าโดยไม่มีค่า สิ่งนี้ช่วยให้เราย้ายค่า (move) ของ `state` ออกจาก `Post` ได้แทนที่จะเป็นการยืม จากนั้นเราจะกำหนดค่า `state` ของโพสต์ให้เป็นผลลัพธ์ที่ได้จากการดำเนินการนี้

เราจำเป็นต้องตั้งค่า `state` ให้เป็น `None` ชั่วคราว แทนที่จะกำหนดค่าทับไปตรง ๆ ด้วยโค้ดอย่าง `self.state = self.state.request_review();` เพื่อให้ได้รับความเป็นเจ้าของค่าของ `state` มา สิ่งนี้รับประกันว่า `Post` จะไม่สามารถนำค่า `state` เดิมกลับมาใช้ได้อีกหลังจากที่เราแปลงมันไปเป็นสถานะใหม่แล้ว

เมธอด `request_review` บน `Draft` จะคืนอินสแตนซ์ใหม่ที่อยู่ในบ็อกซ์ของ struct `PendingReview` ซึ่งเป็นตัวแทนของสถานะที่โพสต์กำลังรอการตรวจสอบ ส่วน struct `PendingReview` ก็อิมพลีเมนต์เมธอด `request_review` เช่นกัน แต่ไม่ได้ทำการแปลงร่างใด ๆ โดยจะคืนตัวมันเองกลับไป เพราะเมื่อเราส่งคำขอตรวจสอบโพสต์ที่อยู่ในสถานะ `PendingReview` อยู่แล้ว โพสต์นั้นก็ควรจะคงอยู่ในสถานะ `PendingReview` ต่อไป

ตอนนี้เราเริ่มเห็นข้อดีของแพตเทิร์นสถานะแล้ว: นั่นคือเมธอด `request_review` บน `Post` จะยังคงทำงานเหมือนเดิมไม่ว่าค่าของ `state` จะเป็นอะไร เพราะแต่ละสถานะจะรับผิดชอบกฎเกณฑ์ของตนเอง

เราจะปล่อยให้เมธอด `content` บน `Post` ทำงานเหมือนเดิม คือคืนค่าสตริงสไลซ์ว่างเปล่า แม้ว่าตอนนี้เราจะมี `Post` ที่อยู่ในสถานะ `PendingReview` เพิ่มขึ้นมา แต่เราก็ยังต้องการพฤติกรรมเดิมในสถานะนี้เช่นกัน ทำให้ตอนนี้โค้ดในลิสติ้ง 18-11 สามารถทำงานได้ถึงการเรียก `assert_eq!` ตัวที่สองแล้ว!

ในทำนองเดียวกับที่ `request_review` บน `PendingReview` ทำงาน หากเราเรียกเมธอด `approve` บน `Draft` มันจะไม่มีผลอะไรเกิดขึ้น เพราะ `approve` จะคืน `self` กลับมา แต่เมื่อเราเรียก `approve` บน `PendingReview` มันจะคืนอินสแตนซ์ใหม่ที่อยู่ในบ็อกซ์ของ struct `Published` กลับมา โดย struct `Published` นี้จะอิมพลีเมนต์เทรต `State` และสำหรับทั้งเมธอด `request_review` และ `approve` มันจะคืนตัวมันเองกลับไป เพราะโพสต์ควรคงอยู่ในสถานะ `Published` ต่อไปในกรณีเหล่านั้น

เนื่องจากเป้าหมายคือการเก็บกฎเกณฑ์ทั้งหมดนี้ไว้ใน struct ที่อิมพลีเมนต์ `State` เราจึงเรียกเมธอด `content` บนค่าที่อยู่ใน `state` พร้อมกับส่งอินสแตนซ์ของโพสต์ (นั่นคือ `self`) ไปเป็นอาร์กิวเมนต์ จากนั้นเราจึงส่งคืนค่าที่ได้จากการเรียกใช้เมธอด `content` บนค่านั้นกลับไป

เราเรียกเมธอด `as_ref` บน `Option` เพราะเราต้องการเพียงเรเฟอเรนซ์ไปยังค่าข้างใน `Option` ไม่ใช่ความเป็นเจ้าของค่านั้น เนื่องจาก `state` มีชนิดข้อมูลเป็น `Option<Box<dyn State>>` เมื่อเราเรียก `as_ref` เราจึงได้ `Option<&Box<dyn State>>` กลับมา หากเราไม่เรียก `as_ref` เราจะเจอกับข้อผิดพลาดของคอมไพเลอร์ เพราะเราไม่สามารถย้าย (move) `state` ออกมาจาก `&self` ที่ถูกยืมมาในพารามิเตอร์ของฟังก์ชันได้

จากนั้นเราจึงเรียกเมธอด `unwrap` ซึ่งเรารู้ดีว่าจะไม่มีทางเกิดการแพนิก (panic) อย่างแน่นอน เพราะเมธอดต่าง ๆ บน `Post` รับประกันว่า `state` จะมีค่าเป็น `Some` เสมอเมื่อเมธอดเหล่านั้นทำงานเสร็จสิ้น นี่คือหนึ่งในกรณีที่เราได้พูดคุยกันในหัวข้อ [“เมื่อคุณมีข้อมูลมากกว่าคอมไพเลอร์”][more-info-than-rustc]<!-- ignore --> ในบทที่ 9 ซึ่งเรารู้แน่ชัดว่าค่า `None` ไม่มีทางเกิดขึ้นได้ แม้ว่าคอมไพเลอร์จะไม่สามารถล่วงรู้ในจุดนี้ก็ตาม

และแล้วก็เสร็จเรียบร้อย—ตอนนี้โค้ดทั้งหมดในลิสติ้ง 18-11 สามารถทำงานได้ครบถ้วนแล้ว! เราได้อิมพลีเมนต์แพตเทิร์นสถานะตามกฎเกณฑ์ของเวิร์กโฟลว์โพสต์บล็อก โดยตรรกะที่เกี่ยวข้องกับกฎเกณฑ์ต่าง ๆ จะรวมศูนย์อยู่ในออบเจกต์สถานะ แทนที่จะกระจัดกระจายอยู่ทั่ว struct `Post`

> ### ทำไมไม่ใช้ Enum?
>
> คุณอาจสงสัยว่าทำไมเราไม่ใช้ enum ที่มีสถานะต่าง ๆ ที่เป็นไปได้ของโพสต์เป็นวาเรียนต์ นั่นก็เป็นหนึ่งในทางออกที่เป็นไปได้อย่างแน่นอน ลองเขียนดูแล้วเปรียบเทียบผลลัพธ์สุดท้ายว่าคุณชอบแบบใดมากกว่า! ข้อเสียประการหนึ่งของการใช้ enum คือ ทุกจุดที่มีการตรวจสอบค่าของ enum จะต้องมีนิพจน์ `match` หรือโครงสร้างที่คล้ายกันเพื่อจัดการกับทุกวาเรียนต์ที่เป็นไปได้ ซึ่งอาจทำให้เกิดโค้ดซ้ำซ้อนมากกว่าแนวทางที่ใช้เทรตออบเจกต์นี้

<a id="trade-offs-of-the-state-pattern"></a>

#### การประเมินแพตเทิร์นสถานะ

เราได้แสดงให้เห็นแล้วว่า Rust สามารถอิมพลีเมนต์แพตเทิร์นสถานะเชิงวัตถุเพื่อห่อหุ้ม (encapsulate) พฤติกรรมต่าง ๆ ที่โพสต์ควรมีในแต่ละสถานะได้ โดยที่เมธอดบน `Post` ไม่จำเป็นต้องรู้เรื่องพฤติกรรมเหล่านั้นเลย ด้วยวิธีการจัดระเบียบโค้ดเช่นนี้ เราจึงเปิดดูเพียงจุดเดียวก็เข้าใจได้ทันทีว่าโพสต์ที่เผยแพร่แล้วมีพฤติกรรมอย่างไร นั่นคือดูที่การอิมพลีเมนต์เทรต `State` บน struct `Published`

หากเราเลือกอิมพลีเมนต์ด้วยวิธีอื่นที่ไม่ใช้แพตเทิร์นสถานะ เราอาจต้องใช้นิพจน์ `match` ในเมธอดต่าง ๆ บน `Post` หรือแม้กระทั่งในโค้ด `main` เพื่อคอยตรวจสอบสถานะของโพสต์แล้วปรับเปลี่ยนพฤติกรรมในแต่ละจุด ซึ่งนั่นจะทำให้เราต้องไล่ดูโค้ดหลายที่มากเพื่อที่จะเข้าใจผลกระทบทั้งหมดของการที่โพสต์อยู่ในสถานะเผยแพร่แล้ว

การใช้แพตเทิร์นสถานะทำให้เมธอดของ `Post` และจุดที่เราเรียกใช้ `Post` ไม่จำเป็นต้องมีนิพจน์ `match` เลย และเมื่อต้องการเพิ่มสถานะใหม่ เราก็เพียงแค่เพิ่ม struct ใหม่ขึ้นมา แล้วอิมพลีเมนต์เมธอดของเทรตบน struct นั้นในที่เดียวจบ

การอิมพลีเมนต์โดยใช้แพตเทิร์นสถานะจึงง่ายต่อการต่อขยายเพื่อเพิ่มฟังก์ชันการทำงาน เพื่อสัมผัสถึงความสะดวกในการบำรุงรักษาโค้ดที่ใช้แพตเทิร์นสถานะ ลองทำตามคำแนะนำเหล่านี้ดู:

- เพิ่มเมธอด `reject` ที่เปลี่ยนสถานะของโพสต์จาก `PendingReview` กลับไปเป็น `Draft`
- กำหนดให้ต้องเรียก `approve` สองครั้งก่อนที่สถานะจะเปลี่ยนเป็น `Published` ได้
- อนุญาตให้ผู้ใช้เพิ่มข้อความได้เฉพาะเมื่อโพสต์อยู่ในสถานะ `Draft` เท่านั้น คำใบ้: ให้ออบเจกต์สถานะเป็นผู้รับผิดชอบว่ามีอะไรเปลี่ยนแปลงเกี่ยวกับเนื้อหาได้บ้าง แต่ไม่ต้องรับผิดชอบการแก้ไข `Post` โดยตรง

ข้อเสียประการหนึ่งของแพตเทิร์นสถานะคือ เนื่องจากแต่ละสถานะเป็นตัวกำหนดการเปลี่ยนผ่านไปยังสถานะถัดไป สถานะบางตัวจึงเกิดการผูกมัดซึ่งกันและกัน (coupled) หากเราต้องการแทรกสถานะใหม่เข้าไปคั่นระหว่าง `PendingReview` กับ `Published` เช่น `Scheduled` เราจะต้องเข้าไปแก้โค้ดใน `PendingReview` ให้เปลี่ยนผ่านไปยัง `Scheduled` แทน ซึ่งคงจะเหนื่อยน้อยลงหาก `PendingReview` ไม่จำเป็นต้องถูกแก้ไขเมื่อมีการเพิ่มสถานะใหม่ แต่นั่นก็หมายความว่าเราต้องเปลี่ยนไปใช้แบบแผนการออกแบบอื่น

ข้อเสียอีกประการหนึ่งคือเราเกิดโค้ดซ้ำซ้อนขึ้นบางส่วน เพื่อกำจัดความซ้ำซ้อนบางส่วน เราอาจลองสร้างการอิมพลีเมนต์ดีฟอลต์สำหรับเมธอด `request_review` และ `approve` บนเทรต `State` ที่คืน `self` อย่างไรก็ตาม วิธีนี้ใช้ไม่ได้: เมื่อใช้ `State` เป็นเทรตออบเจกต์ เทรตไม่รู้ว่า `self` ที่เป็นรูปธรรมจะเป็นอะไรอย่างแน่ชัด ชนิดที่คืนกลับจึงไม่เป็นที่รู้ตอนคอมไพล์ (นี่เป็นหนึ่งในกฎความเข้ากันได้ของ dyn ที่กล่าวถึงก่อนหน้านี้)

ความซ้ำซ้อนอีกจุดหนึ่งคือ โค้ดการทำงานที่คล้ายคลึงกันมากของเมธอด `request_review` และ `approve` บน `Post` โดยทั้งสองเมธอดต่างเรียกใช้ `Option::take` กับฟิลด์ `state` ของ `Post` และหาก `state` มีค่าเป็น `Some` ก็จะส่งต่องานไปยังการอิมพลีเมนต์เมธอดเดียวกันของค่าที่ถูกห่อไว้ แล้วนำผลลัพธ์ที่ได้มาตั้งเป็นค่าใหม่ของฟิลด์ `state` หากเรามีเมธอดบน `Post` จำนวนมากที่ใช้รูปแบบนี้ซ้ำ ๆ เราอาจพิจารณานิยามมาโคร (macro) ขึ้นมาเพื่อลดความซ้ำซ้อนในการเขียนโค้ด (ดูหัวข้อ [“มาโคร”][macros]<!-- ignore --> ในบทที่ 20)

การอิมพลีเมนต์แพตเทิร์นสถานะตามนิยามดั้งเดิมของภาษาเชิงวัตถุอย่างเคร่งครัด ทำให้เรายังไม่ได้ใช้ประโยชน์จากจุดแข็งของ Rust ได้อย่างเต็มที่ มาลองดูการปรับเปลี่ยนบางอย่างที่เราสามารถทำได้กับเครต `blog` ซึ่งจะช่วยเปลี่ยนสถานะและการเปลี่ยนสถานะที่ไม่ถูกต้อง ให้กลายเป็นข้อผิดพลาดตั้งแต่ตอนคอมไพล์กันดีกว่า

### การเข้ารหัสสถานะและพฤติกรรมเป็นชนิดข้อมูล

เราจะแสดงวิธีคิดใหม่กับแพตเทิร์นสถานะเพื่อให้ได้ข้อแลกเปลี่ยนอีกแบบหนึ่ง แทนที่จะห่อหุ้มสถานะและการเปลี่ยนผ่านไว้อย่างมิดชิดจนโค้ดภายนอกไม่รู้เรื่องเลย เราจะเข้ารหัสสถานะต่าง ๆ ลงไปในชนิดข้อมูลที่แตกต่างกัน ด้วยวิธีนี้ ระบบตรวจสอบชนิดข้อมูลของ Rust จะป้องกันความพยายามในการนำโพสต์ฉบับร่างไปใช้ในจุดที่อนุญาตเฉพาะโพสต์ที่เผยแพร่แล้ว โดยแจ้งเตือนเป็นข้อผิดพลาดจากคอมไพเลอร์ทันที

ลองนำโจทย์แบบฝึกหัดที่แนะนำไว้ในตอนต้นของหัวข้อนี้ มาทดลองทำกับเครต `blog` ในเวอร์ชันหลังลิสติ้ง 18-21 ดู เพื่อสัมผัสว่าคุณรู้สึกอย่างไรกับการออกแบบโค้ดในรูปแบบนี้ และโปรดสังเกตว่าโจทย์บางข้ออาจได้รับการแก้ไขเสร็จสิ้นไปแล้วในตัวการออกแบบนี้เอง

เราได้เห็นแล้วว่า แม้ว่า Rust จะมีความสามารถในการอิมพลีเมนต์แบบแผนการออกแบบเชิงวัตถุได้ แต่แพตเทิร์นอื่น ๆ เช่น การเข้ารหัสสถานะลงในระบบชนิดข้อมูล ก็เป็นทางเลือกที่มีประสิทธิภาพใน Rust เช่นกัน แพตเทิร์นแต่ละแบบย่อมมีข้อแลกเปลี่ยนที่แตกต่างกัน แม้ว่าคุณอาจคุ้นเคยกับแพตเทิร์นเชิงวัตถุเป็นอย่างดี แต่การคิดทบทวนโจทย์ใหม่เพื่อดึงประโยชน์จากฟีเจอร์อันทรงพลังของ Rust ก็สามารถมอบคุณประโยชน์ที่ยอดเยี่ยมได้ เช่น การป้องกันบั๊กตั้งแต่ตอนคอมไพล์ โดยแบบแผนเชิงวัตถุอาจไม่ได้เป็นคำตอบที่ดีที่สุดเสมอไปใน Rust เนื่องจากฟีเจอร์เฉพาะตัวอย่างระบบความเป็นเจ้าของ (ownership) ที่ภาษาเชิงวัตถุทั่วไปไม่มี

## สรุป

ไม่ว่าหลังจากอ่านบทนี้จบแล้ว คุณจะมองว่า Rust เป็นภาษาเชิงวัตถุหรือไม่ก็ตาม แต่ตอนนี้คุณได้ทราบแล้วว่า คุณสามารถใช้เทรตออบเจกต์เพื่อดึงฟีเจอร์บางประการของเชิงวัตถุมาใช้ใน Rust ได้ การดิสแพตช์แบบไดนามิก (dynamic dispatch) ช่วยเพิ่มความยืดหยุ่นให้กับโค้ดของคุณโดยแลกกับต้นทุนด้านประสิทธิภาพตอนรันไทม์เพียงเล็กน้อย คุณสามารถนำความยืดหยุ่นนี้ไปใช้อิมพลีเมนต์แพตเทิร์นเชิงวัตถุที่ช่วยให้โค้ดของคุณดูแลรักษาง่ายขึ้น ยิ่งไปกว่านั้น Rust ยังมีฟีเจอร์อื่น ๆ เช่น ระบบความเป็นเจ้าของ (ownership) ซึ่งภาษาเชิงวัตถุทั่วไปไม่มี แม้แบบแผนเชิงวัตถุอาจไม่ได้เป็นหนทางที่ดีที่สุดเสมอไปในการดึงจุดแข็งของ Rust ออกมาใช้ แต่มันก็เป็นทางเลือกหนึ่งที่มีพร้อมให้คุณหยิบมาใช้งานเสมอ

ในบทต่อไป เราจะไปดูเรื่อง "แพตเทิร์น" (patterns) ซึ่งเป็นอีกหนึ่งฟีเจอร์สำคัญของ Rust ที่ช่วยเปิดประตูสู่ความยืดหยุ่นอย่างมากมาย แม้เราจะเคยเห็นผ่านตากันมาบ้างแล้วตลอดทั้งเล่ม แต่เรายังไม่เคยเห็นศักยภาพเต็มรูปแบบของมันเลย ไปลุยกันต่อเลย!
