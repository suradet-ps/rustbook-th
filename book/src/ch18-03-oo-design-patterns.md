## อิมพลีเมนต์แพตเทิร์นการออกแบบเชิงวัตถุ

_แพตเทิร์นสถานะ_ (state pattern) เป็นแพตเทิร์นการออกแบบเชิงวัตถุ จุดสำคัญของแพตเทิร์นคือเรานิยามชุดของสถานะที่ค่าหนึ่งสามารถมีได้ภายใน สถานะเหล่านี้ถูกแทนด้วยชุดของ_ออบเจกต์สถานะ_ (state object) และพฤติกรรมของค่าจะเปลี่ยนไปตามสถานะของมัน เรากำลังจะลงมือทำตัวอย่าง struct โพสต์บล็อกที่มีฟิลด์เก็บสถานะของมัน ซึ่งจะเป็นออบเจกต์สถานะจากชุด “ฉบับร่าง” “รอตรวจสอบ” หรือ “เผยแพร่แล้ว”

ออบเจกต์สถานะเหล่านี้ใช้ฟังก์ชันการทำงานร่วมกัน: แน่นอนว่าใน Rust เราใช้ struct และเทรต (trait) แทนออบเจกต์ (object) และการสืบทอด (inheritance) ออบเจกต์สถานะแต่ละตัวรับผิดชอบพฤติกรรมของตัวเองและรับผิดชอบกำกับว่ามันควรเปลี่ยนไปเป็นอีกสถานะหนึ่งเมื่อใด ค่าที่เก็บออบเจกต์สถานะไม่รู้อะไรเลยเกี่ยวกับพฤติกรรมที่แตกต่างกันของสถานะต่างๆ หรือเวลาเปลี่ยนผ่านระหว่างสถานะ

ข้อดีของการใช้แพตเทิร์นสถานะคือ เมื่อความต้องการทางธุรกิจของโปรแกรมเปลี่ยน เราไม่จำเป็นต้องเปลี่ยนโค้ดของค่าที่เก็บสถานะหรือโค้ดที่ใช้ค่านั้น เราจะต้องอัปเดตเฉพาะโค้ดภายในออบเจกต์สถานะตัวใดตัวหนึ่งเพื่อเปลี่ยนกฎของมัน หรืออาจเพิ่มออบเจกต์สถานะใหม่ๆ เท่านั้น

ก่อนอื่น เราจะอิมพลีเมนต์แพตเทิร์นสถานะในแบบเชิงวัตถุที่ดั้งเดิมมากกว่า จากนั้นเราจะใช้แนวทางที่เป็นธรรมชาติกว่าเล็กน้อยใน Rust มาลงลึกกันเพื่ออิมพลีเมนต์เวิร์กโฟลว์ของโพสต์บล็อกโดยใช้แพตเทิร์นสถานะแบบค่อยเป็นค่อยไป

ฟังก์ชันการทำงานสุดท้ายจะมีหน้าตาดังนี้:

1. โพสต์บล็อกเริ่มต้นเป็นฉบับร่างว่างเปล่า
1. เมื่อฉบับร่างเสร็จสิ้น มีการขอให้ตรวจสอบโพสต์
1. เมื่อโพสต์ได้รับอนุมัติ มันจะถูกเผยแพร่
1. มีเพียงโพสต์บล็อกที่เผยแพร่แล้วเท่านั้นที่คืนเนื้อหาเพื่อพิมพ์ออกมา เพื่อไม่ให้โพสต์ที่ยังไม่อนุมัติ
   ถูกเผยแพร่โดยไม่ตั้งใจ

การเปลี่ยนแปลงอื่นๆ ที่พยายามทำกับโพสต์ควรไม่มีผลใดๆ ตัวอย่างเช่น หากเราพยายามอนุมัติโพสต์บล็อกฉบับร่างก่อนที่เราจะขอให้ตรวจสอบ โพสต์นั้นควรยังคงเป็นฉบับร่างที่ยังไม่เผยแพร่

### การลองใช้สไตล์เชิงวัตถุแบบดั้งเดิม

มีวิธีจัดโครงสร้างโค้ดเพื่อแก้ปัญหาเดียวกันได้ไม่จำกัด แต่ละวิธีมีข้อแลกเปลี่ยนที่แตกต่างกัน การอิมพลีเมนต์ในหัวข้อนี้เป็นสไตล์เชิงวัตถุแบบดั้งเดิมมากกว่า ซึ่งเขียนใน Rust ได้ แต่ไม่ได้ใช้ประโยชน์จากจุดแข็งบางประการของ Rust ต่อมา เราจะสาธิตวิธีแก้ปัญหาที่แตกต่างออกไปซึ่งยังใช้แพตเทิร์นการออกแบบเชิงวัตถุ แต่ว่าจัดโครงสร้างในแบบที่อาจดูไม่คุ้นเคยสำหรับโปรแกรมเมอร์ที่มีประสบการณ์เชิงวัตถุ เราจะเปรียบเทียบวิธีแก้ปัญหาทั้งสองเพื่อสัมผัสข้อแลกเปลี่ยนของการออกแบบโค้ด Rust ให้ต่างจากโค้ดในภาษาอื่น

เราเพิ่มเมธอด `request_review` เข้าไปในเทรต `State`; ตอนนี้ทุกชนิดข้อมูลที่อิมพลีเมนต์เทรตนี้จะต้องอิมพลีเมนต์เมธอด `request_review` โปรดสังเกตว่าแทนที่จะมี `self`, `&self` หรือ `&mut self` เป็นพารามิเตอร์ตัวแรกของเมธอด เรากลับมี `self: Box<Self>` วากยสัมพันธ์นี้หมายความว่าเมธอดนี้ใช้ได้เฉพาะเมื่อถูกเรียกบน `Box` ที่บรรจุชนิดนั้น วากยสัมพันธ์นี้รับความเป็นเจ้าของ (ownership) `Box<Self>` ทำให้สถานะเดิมใช้ไม่ได้ เพื่อให้ค่าสถานะของ `Post` แปลงร่างเป็นสถานะใหม่ได้

ในการบริโภคสถานะเดิม เมธอด `request_review` จำเป็นต้องรับความเป็นเจ้าของค่าสถานะ นี่คือจุดที่ `Option` ในฟิลด์ `state` ของ `Post` เข้ามามีบทบาท: เราเรียกเมธอด `take` เพื่อนำค่า `Some` ออกจากฟิลด์ `state` และทิ้ง `None` ไว้แทน เพราะ Rust ไม่อนุญาตให้เรามีฟิลด์ที่ไม่มีค่าใน struct สิ่งนี้ทำให้เราย้ายค่าของ `state` ออกจาก `Post` ได้แทนที่จะยืมมัน จากนั้นเราจะตั้งค่าของ `state` ของโพสต์เป็นผลลัพธ์ของการดำเนินการนี้

เราจำเป็นต้องตั้ง `state` เป็น `None` ชั่วคราวแทนที่จะตั้งมันโดยตรงด้วยโค้ดอย่าง `self.state = self.state.request_review();` เพื่อให้ได้ความเป็นเจ้าของค่าของ `state` สิ่งนี้รับประกันว่า `Post` ไม่สามารถใช้ค่าของ `state` เดิมได้หลังจากที่เราแปลงมันเป็นสถานะใหม่

เมธอด `request_review` บน `Draft` คืนอินสแตนซ์ใหม่ที่ถูกห่อในบ็อกซ์ของ struct `PendingReview` ใหม่ ซึ่งแทนสถานะเมื่อโพสต์กำลังรอการตรวจสอบ struct `PendingReview` ก็อิมพลีเมนต์เมธอด `request_review` แต่ไม่ทำการแปลงร่างใดๆ แต่คืนตัวมันเองแทน เพราะเมื่อเราขอให้ตรวจสอบโพสต์ที่อยู่ในสถานะ `PendingReview` อยู่แล้ว มันควรคงอยู่ในสถานะ `PendingReview`

ตอนนี้เราเริ่มเห็นข้อดีของแพตเทิร์นสถานะแล้ว: เมธอด `request_review` บน `Post` เหมือนกันไม่ว่าค่าของ `state` จะเป็นอะไร แต่ละสถานะรับผิดชอบกฎของตัวเอง

เราจะปล่อยเมธอด `content` บน `Post` ไว้เหมือนเดิม โดยคืนสตริงสไลซ์ว่างเปล่า ตอนนี้เราสามารถมี `Post` ในสถานะ `PendingReview` ได้เช่นเดียวกับในสถานะ `Draft` แต่เราต้องการพฤติกรรมเดียวกันในสถานะ `PendingReview` ตอนนี้ลิสติ้ง 18-11 ทำงานได้ถึงการเรียก `assert_eq!` ตัวที่สองแล้ว!

> ### ทำไมไม่ใช้ Enum?
>
> คุณอาจสงสัยว่าทำไมเราไม่ใช้ enum ที่มีสถานะต่างๆ ที่เป็นไปได้ของโพสต์เป็นวาเรียนต์ นั่นก็เป็นวิธีแก้ปัญหาที่เป็นไปได้แน่นอน ลองทำดูแล้วเปรียบเทียบผลลัพธ์สุดท้ายว่าคุณชอบแบบใดมากกว่า! ข้อเสียอย่างหนึ่งของการใช้ enum คือทุกจุดที่ตรวจสอบค่าของ enum จะต้องมีเอ็กซ์เพรสชัน (expression) `match` หรือสิ่งที่คล้ายกันเพื่อจัดการวาเรียนต์ที่เป็นไปได้ทุกตัว สิ่งนี้อาจซ้ำซากมากกว่าวิธีแก้ปัญหาแบบเทรตออบเจกต์นี้

<a id="trade-offs-of-the-state-pattern"></a>

#### การประเมินแพตเทิร์นสถานะ

เราได้แสดงให้เห็นว่า Rust สามารถอิมพลีเมนต์แพตเทิร์นสถานะเชิงวัตถุเพื่อห่อหุ้ม (encapsulation) พฤติกรรมชนิดต่างๆ ที่โพสต์ควรมีในแต่ละสถานะได้ เมธอดบน `Post` ไม่รู้อะไรเลยเกี่ยวกับพฤติกรรมต่างๆ เพราะวิธีที่เราจัดระเบียบโค้ด เราจึงต้องดูเพียงที่เดียวเพื่อรู้วิธีต่างๆ ที่โพสต์ที่เผยแพร่แล้วสามารถมีพฤติกรรมได้ นั่นคือการอิมพลีเมนต์เทรต `State` บน struct `Published`

หากเราสร้างการอิมพลีเมนต์ทางเลือกที่ไม่ใช้แพตเทิร์นสถานะ เราอาจใช้เอ็กซ์เพรสชัน `match` ในเมธอดบน `Post` หรือแม้แต่ในโค้ด `main` ที่ตรวจสอบสถานะของโพสต์และเปลี่ยนพฤติกรรมในจุดเหล่านั้นแทน นั่นจะหมายความว่าเราต้องดูหลายที่เพื่อเข้าใจผลกระทบทั้งหมดของการที่โพสต์อยู่ในสถานะเผยแพร่แล้ว

ด้วยแพตเทิร์นสถานะ เมธอดของ `Post` และจุดที่เราใช้ `Post` ไม่จำเป็นต้องมีเอ็กซ์เพรสชัน `match` และการเพิ่มสถานะใหม่ เราจะต้องเพิ่มเพียง struct ใหม่และอิมพลีเมนต์เมธอดของเทรตบน struct เดียวนั้นในที่เดียว

การอิมพลีเมนต์ที่ใช้แพตเทิร์นสถานะนั้นขยายเพื่อเพิ่มฟังก์ชันการทำงานได้ง่าย เพื่อสัมผัสความง่ายในการดูแลโค้ดที่ใช้แพตเทิร์นสถานะ ลองทำตามคำแนะนำเหล่านี้สักสองสามข้อ:

- เพิ่มเมธอด `reject` ที่เปลี่ยนสถานะของโพสต์จาก `PendingReview` กลับ
  ไปเป็น `Draft`
- กำหนดให้ต้องเรียก `approve` สองครั้งก่อนที่สถานะจะเปลี่ยนเป็น `Published` ได้
- อนุญาตให้ผู้ใช้เพิ่มเนื้อหาข้อความเฉพาะเมื่อโพสต์อยู่ในสถานะ `Draft` เท่านั้น
  คำใบ้: ให้ออบเจกต์สถานะเป็นผู้รับผิดชอบว่าอะไรอาจเปลี่ยนแปลงเกี่ยวกับเนื้อหา แต่ไม่รับผิดชอบการแก้ไข `Post`

ข้อเสียอย่างหนึ่งของแพตเทิร์นสถานะคือ เพราะสถานะต่างๆ อิมพลีเมนต์การเปลี่ยนผ่านระหว่างสถานะ สถานะบางส่วนจึงผูกติดกัน หากเราเพิ่มสถานะอื่นระหว่าง `PendingReview` และ `Published` เช่น `Scheduled` เราจะต้องเปลี่ยนโค้ดใน `PendingReview` ให้เปลี่ยนผ่านไปยัง `Scheduled` แทน จะเป็นงานที่น้อยลงหาก `PendingReview` ไม่จำเป็นต้องเปลี่ยนเมื่อมีการเพิ่มสถานะใหม่ แต่นั่นจะหมายถึงการเปลี่ยนไปใช้แพตเทิร์นการออกแบบอื่น

ข้อเสียอีกอย่างคือเราได้ทำตรรกะบางส่วนซ้ำซ้อน เพื่อกำจัดความซ้ำซ้อนบางส่วน เราอาจลองสร้างการอิมพลีเมนต์ค่าเริ่มต้นสำหรับเมธอด `request_review` และ `approve` บนเทรต `State` ที่คืน `self` อย่างไรก็ตาม วิธีนี้ใช้ไม่ได้: เมื่อใช้ `State` เป็นเทรตออบเจกต์ เทรตไม่รู้ว่า `self` ที่เป็นรูปธรรมจะเป็นอะไรอย่างแน่ชัด ชนิดที่คืนกลับจึงไม่เป็นที่รู้ตอนคอมไพล์ (นี่เป็นหนึ่งในกฎความเข้ากันได้ของ dyn ที่กล่าวถึงก่อนหน้านี้)

ความซ้ำซ้อนอื่นๆ รวมถึงการอิมพลีเมนต์ที่คล้ายกันของเมธอด `request_review` และ `approve` บน `Post` ทั้งสองเมธอดใช้ `Option::take` กับฟิลด์ `state` ของ `Post` และหาก `state` เป็น `Some` พวกมันจะมอบหมายไปยังการอิมพลีเมนต์เมธอดเดียวกันของค่าที่ถูกห่อไว้ และตั้งค่าใหม่ของฟิลด์ `state` เป็นผลลัพธ์ หากเรามีเมธอดบน `Post` จำนวนมากที่เป็นไปตามรูปแบบนี้ เราอาจพิจารณานิยามมาโคร (macro) เพื่อกำจัดการเขียนซ้ำ (ดูหัวข้อ[“มาโคร”][macros]<!-- ignore --> ในบทที่ 20)

ด้วยการอิมพลีเมนต์แพตเทิร์นสถานะตามที่มันถูกนิยามไว้สำหรับภาษาเชิงวัตถุอย่างเคร่งครัด เราไม่ได้ใช้ประโยชน์จากจุดแข็งของ Rust อย่างเต็มที่เท่าที่ทำได้ มาดูการเปลี่ยนแปลงบางอย่างที่เราทำกับเครต `blog` ได้ ซึ่งสามารถเปลี่ยนสถานะและการเปลี่ยนผ่านที่ไม่ถูกต้องให้กลายเป็นข้อผิดพลาดตอนคอมไพล์

### การเข้ารหัสสถานะและพฤติกรรมเป็นชนิดข้อมูล

เราจะแสดงวิธีคิดใหม่กับแพตเทิร์นสถานะเพื่อให้ได้ชุดข้อแลกเปลี่ยนที่ต่างออกไป แทนที่จะห่อหุ้มสถานะและการเปลี่ยนผ่านอย่างสมบูรณ์จนโค้ดภายนอกไม่รู้เรื่องพวกมันเลย เราจะเข้ารหัสสถานะลงในชนิดข้อมูลที่แตกต่างกัน ดังนั้น ระบบตรวจสอบชนิดข้อมูลของ Rust จะป้องกันความพยายามใช้โพสต์ฉบับร่างในที่ที่อนุญาตเฉพาะโพสต์ที่เผยแพร่แล้ว โดยออกข้อผิดพลาดของคอมไพเลอร์

ลองทำโจทย์ที่แนะนำไว้ตอนต้นของหัวข้อนี้บนเครต `blog` ตามที่เป็นอยู่หลังลิสติ้ง 18-21 เพื่อดูว่าคุณคิดอย่างไรกับการออกแบบโค้ดเวอร์ชันนี้ โปรดสังเกตว่าโจทย์บางข้ออาจถูกทำเสร็จแล้วในการออกแบบนี้

เราได้เห็นว่าแม้ว่า Rust จะสามารถอิมพลีเมนต์แพตเทิร์นการออกแบบเชิงวัตถุได้ แต่แพตเทิร์นอื่นๆ เช่น การเข้ารหัสสถานะลงในระบบชนิดข้อมูล ก็มีให้ใช้ใน Rust เช่นกัน แพตเทิร์นเหล่านี้มีข้อแลกเปลี่ยนที่แตกต่างกัน แม้ว่าคุณอาจคุ้นเคยกับแพตเทิร์นเชิงวัตถุเป็นอย่างดี การคิดโจทย์ใหม่เพื่อใช้ประโยชน์จากฟีเจอร์ของ Rust ก็ให้ประโยชน์ได้ เช่น การป้องกันบั๊กบางอย่างตอนคอมไพล์ แพตเทิร์นเชิงวัตถุจะไม่ใช่ทางออกที่ดีที่สุดเสมอไปใน Rust เนื่องจากฟีเจอร์บางอย่าง เช่น ความเป็นเจ้าของ ที่ภาษาเชิงวัตถุไม่มี

## สรุป

ไม่ว่าคุณจะคิดว่า Rust เป็นภาษาเชิงวัตถุหรือไม่หลังอ่านบทนี้ ตอนนี้คุณรู้แล้วว่าคุณใช้เทรตออบเจกต์เพื่อได้ฟีเจอร์เชิงวัตถุบางอย่างใน Rust ได้ การดิสแพตช์แบบไดนามิก (dynamic dispatch) ให้ความยืดหยุ่นแก่โค้ดของคุณโดยแลกกับประสิทธิภาพตอนรันไทม์เล็กน้อย คุณใช้ความยืดหยุ่นนี้เพื่ออิมพลีเมนต์แพตเทิร์นเชิงวัตถุที่ช่วยให้โค้ดของคุณดูแลรักษาง่ายขึ้นได้ Rust ยังมีฟีเจอร์อื่นๆ เช่น ความเป็นเจ้าของ ที่ภาษาเชิงวัตถุไม่มี แพตเทิร์นเชิงวัตถุไม่ใช่ทางที่ดีที่สุดเสมอไปในการใช้ประโยชน์จากจุดแข็งของ Rust แต่มันเป็นทางเลือกหนึ่งที่มีให้ใช้

ต่อไป เราจะดูแพตเทิร์น ซึ่งเป็นอีกหนึ่งฟีเจอร์ของ Rust ที่เปิดให้มีความยืดหยุ่นมากมาย เราได้ดูมันผ่านๆ ตลอดทั้งเล่มแต่ยังไม่เห็นความสามารถเต็มรูปแบบของมัน ไปกันเลย!
