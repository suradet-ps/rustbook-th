## ข้อผิดพลาดที่กู้คืนได้ด้วย `Result`

ข้อผิดพลาดส่วนใหญ่ไม่ได้ร้ายแรงพอที่จะทำให้โปรแกรมต้องหยุดทำงานทั้งหมด บางครั้งเมื่อฟังก์ชันล้มเหลว มันเป็นเพราะเหตุผลที่คุณตีความและตอบสนองได้ง่าย ตัวอย่างเช่น หากคุณพยายามเปิดไฟล์และการดำเนินการนั้นล้มเหลวเพราะไม่มีไฟล์นั้นอยู่ คุณอาจต้องการสร้างไฟล์นั้นแทนที่จะยุติโปรเซส

ย้อนนึกถึง[“การจัดการความล้มเหลวที่อาจเกิดขึ้นด้วย `Result`”][handle_failure]<!--
ignore --> ในบทที่ 2 ว่า enum `Result` ถูกนิยามให้มีสองวาเรียนต์ คือ `Ok` และ `Err` ดังนี้:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

`T` และ `E` เป็นพารามิเตอร์ชนิดข้อมูล (type parameter) แบบเจเนอริก (generic): เราจะพูดถึงเจเนอริกในรายละเอียดเพิ่มเติมในบทที่ 10 สิ่งที่คุณต้องรู้ตอนนี้คือ `T` แทนชนิดของค่าที่จะถูกคืนกลับในกรณีสำเร็จภายในวาเรียนต์ `Ok` และ `E` แทนชนิดของข้อผิดพลาดที่จะถูกคืนกลับในกรณีล้มเหลวภายในวาเรียนต์ `Err` เนื่องจาก `Result` มีพารามิเตอร์ชนิดข้อมูลแบบเจเนอริกเหล่านี้ เราจึงใช้ชนิด `Result` และฟังก์ชันที่นิยามบนมันได้ในหลายสถานการณ์ที่แตกต่างกัน ซึ่งค่าสำเร็จและค่าข้อผิดพลาดที่เราต้องการคืนกลับอาจแตกต่างกัน

มาเรียกฟังก์ชันที่คืนค่า `Result` กัน เพราะฟังก์ชันนั้นอาจล้มเหลวได้ ในลิสติ้ง 9-3 เราพยายามเปิดไฟล์

ในกรณีที่ `File::open` สำเร็จ ค่าในตัวแปร `greeting_file_result` จะเป็นอินสแตนซ์ของ `Ok` ที่บรรจุแฮนเดิลไฟล์ ในกรณีที่มันล้มเหลว ค่าใน `greeting_file_result` จะเป็นอินสแตนซ์ของ `Err` ที่บรรจุข้อมูลเพิ่มเติมเกี่ยวกับชนิดของข้อผิดพลาดที่เกิดขึ้น

### การจับคู่กับข้อผิดพลาดที่แตกต่างกัน

โค้ดในลิสติ้ง 9-4 จะ `panic!` ไม่ว่า `File::open` จะล้มเหลวด้วยเหตุผลใดก็ตาม อย่างไรก็ตาม เราต้องการดำเนินการที่แตกต่างกันสำหรับเหตุผลความล้มเหลวที่แตกต่างกัน หาก `File::open` ล้มเหลวเพราะไม่มีไฟล์อยู่ เราต้องการสร้างไฟล์และคืนแฮนเดิลไปยังไฟล์ใหม่ หาก `File::open` ล้มเหลวด้วยเหตุผลอื่นใด เช่น เพราะเราไม่มีสิทธิ์เปิดไฟล์ เราก็ยังต้องการให้โค้ด `panic!` ในแบบเดียวกับที่มันทำในลิสติ้ง 9-4 สำหรับกรณีนี้ เราเพิ่มเอ็กซ์เพรสชัน `match` ซ้อนกัน ดังที่แสดงในลิสติ้ง 9-5

เงื่อนไขที่เราต้องการตรวจสอบในการจับคู่ซ้อนคือว่าค่าที่ `error.kind()` คืนกลับเป็นวาเรียนต์ `NotFound` ของ enum `ErrorKind` หรือไม่ หากเป็นเช่นนั้น เราพยายามสร้างไฟล์ด้วย `File::create` อย่างไรก็ตาม เนื่องจาก `File::create` ก็อาจล้มเหลวได้เช่นกัน เราจึงต้องการอาร์มที่สองในเอ็กซ์เพรสชัน `match` ซ้อน เมื่อไม่สามารถสร้างไฟล์ได้ จะมีการพิมพ์ข้อความแสดงข้อผิดพลาดที่แตกต่างออกไป อาร์มที่สองของ `match` ชั้นนอกยังคงเหมือนเดิม โปรแกรมจึงแพนิก (panic) กับข้อผิดพลาดใดๆ นอกเหนือจากข้อผิดพลาดไฟล์หายไป

> #### ทางเลือกอื่นนอกจากการใช้ `match` กับ `Result<T, E>`
>
> นั่นใช้ `match` เยอะมาก! เอ็กซ์เพรสชัน `match` มีประโยชน์มาก แต่ก็เป็นเครื่องมือพื้นฐานมากเช่นกัน ในบทที่ 13 คุณจะได้เรียนรู้เกี่ยวกับโคลเชอร์ (closure) ซึ่งใช้กับเมธอดหลายตัวที่นิยามบน `Result<T, E>` เมธอดเหล่านี้กระชับกว่าการใช้ `match` เมื่อจัดการค่า `Result<T, E>` ในโค้ดของคุณ
>
> ตัวอย่างเช่น นี่เป็นอีกวิธีหนึ่งในการเขียนลอจิกเดียวกันกับที่แสดงในลิสติ้ง 9-5 ครั้งนี้ใช้โคลเชอร์และเมธอด `unwrap_or_else`:
>
> <!-- CAN'T EXTRACT SEE https://github.com/rust-lang/mdBook/issues/1127 -->
>
> ```rust,ignore
> use std::fs::File;
> use std::io::ErrorKind;
>
> fn main() {
>     let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {
>         if error.kind() == ErrorKind::NotFound {
>             File::create("hello.txt").unwrap_or_else(|error| {
>                 panic!("Problem creating the file: {error:?}");
>             })
>         } else {
>             panic!("Problem opening the file: {error:?}");
>         }
>     });
> }
> ```
>
> แม้ว่าโค้ดนี้มีพฤติกรรมเหมือนกับลิสติ้ง 9-5 แต่มันไม่มีเอ็กซ์เพรสชัน `match` ใดๆ เลย และอ่านได้สะอาดตากว่า กลับมาดูตัวอย่างนี้หลังจากคุณอ่านบทที่ 13 แล้ว และค้นหาเมธอด `unwrap_or_else` ในเอกสารไลบรารีมาตรฐาน เมธอดในทำนองนี้ยังมีอีกมากที่ช่วยทำความสะอาดเอ็กซ์เพรสชัน `match` ที่ซ้อนกันมากมายเมื่อคุณจัดการกับข้อผิดพลาด

ฟังก์ชันนี้เขียนให้สั้นลงได้มาก แต่เราจะเริ่มด้วยการทำเองหลายอย่างเพื่อสำรวจการจัดการข้อผิดพลาด (error handling) ก่อน และในตอนท้ายเราจะแสดงวิธีที่สั้นกว่า มาดูชนิดที่คืนกลับของฟังก์ชันก่อน: `Result<String, io::Error>` ซึ่งหมายความว่าฟังก์ชันคืนค่าชนิด `Result<T, E>` โดยที่พารามิเตอร์เจเนอริก `T` ถูกเติมด้วยชนิดที่เป็นรูปธรรม `String` และชนิดเจเนอริก `E` ถูกเติมด้วยชนิดที่เป็นรูปธรรม `io::Error`

หากฟังก์ชันนี้สำเร็จโดยไม่มีปัญหาใดๆ โค้ดที่เรียกฟังก์ชันนี้จะได้รับค่า `Ok` ที่บรรจุ `String` ซึ่งก็คือ `username` ที่ฟังก์ชันนี้อ่านจากไฟล์ หากฟังก์ชันนี้พบปัญหาใดๆ โค้ดที่เรียกใช้จะได้รับค่า `Err` ที่บรรจุอินสแตนซ์ของ `io::Error` ซึ่งมีข้อมูลเพิ่มเติมว่าปัญหาคืออะไรบ้าง เราเลือก `io::Error` เป็นชนิดที่คืนกลับของฟังก์ชันนี้ เพราะมันบังเอิญเป็นชนิดของค่าข้อผิดพลาดที่คืนกลับจากการดำเนินการทั้งสองที่เราเรียกในเนื้อในของฟังก์ชันนี้ซึ่งอาจล้มเหลว: ฟังก์ชัน `File::open` และเมธอด `read_to_string`

เนื้อในของฟังก์ชันเริ่มด้วยการเรียกฟังก์ชัน `File::open` จากนั้นเราจัดการค่า `Result` ด้วย `match` ที่คล้ายกับ `match` ในลิสติ้ง 9-4 หาก `File::open` สำเร็จ แฮนเดิลไฟล์ในตัวแปรแพตเทิร์น `file` จะกลายเป็นค่าในตัวแปรที่เปลี่ยนแปลงได้ `username_file` และฟังก์ชันดำเนินต่อไป ในกรณี `Err` แทนที่จะเรียก `panic!` เราใช้คำสงวน `return` เพื่อคืนค่าออกนอกฟังก์ชันทั้งหมดแต่เนิ่นๆ และส่งค่าข้อผิดพลาดจาก `File::open` ซึ่งตอนนี้อยู่ในตัวแปรแพตเทิร์น `e` กลับไปยังโค้ดที่เรียกใช้ในฐานะค่าข้อผิดพลาดของฟังก์ชันนี้

ดังนั้น หากเรามีแฮนเดิลไฟล์ใน `username_file` ฟังก์ชันก็จะสร้าง `String` ใหม่ในตัวแปร `username` และเรียกเมธอด `read_to_string` บนแฮนเดิลไฟล์ใน `username_file` เพื่ออ่านเนื้อหาของไฟล์เข้าไปใน `username` เมธอด `read_to_string` ก็คืนค่า `Result` เช่นกันเพราะมันอาจล้มเหลวได้ แม้ว่า `File::open` จะสำเร็จก็ตาม ดังนั้น เราจึงต้องการ `match` อีกตัวเพื่อจัดการ `Result` นั้น: หาก `read_to_string` สำเร็จ ฟังก์ชันของเราก็สำเร็จ และเราคืนชื่อผู้ใช้จากไฟล์ที่ตอนนี้อยู่ใน `username` โดยห่อด้วย `Ok` หาก `read_to_string` ล้มเหลว เราคืนค่าข้อผิดพลาดในแบบเดียวกับที่เราคืนค่าข้อผิดพลาดใน `match` ที่จัดการค่าที่คืนกลับของ `File::open` อย่างไรก็ตาม เราไม่จำเป็นต้องระบุ `return` อย่างชัดแจ้ง เพราะนี่คือเอ็กซ์เพรสชันสุดท้ายในฟังก์ชัน

โค้ดที่เรียกโค้ดนี้จะจัดการกับการได้รับค่า `Ok` ที่บรรจุชื่อผู้ใช้หรือค่า `Err` ที่บรรจุ `io::Error` ขึ้นอยู่กับโค้ดที่เรียกใช้ในการตัดสินใจว่าจะทำอะไรกับค่าเหล่านั้น หากโค้ดที่เรียกใช้ได้รับค่า `Err` มันอาจเรียก `panic!` และทำให้โปรแกรมแครช ใช้ชื่อผู้ใช้เริ่มต้น หรือค้นหาชื่อผู้ใช้จากที่อื่นที่ไม่ใช่ไฟล์ เป็นต้น เราไม่มีข้อมูลเพียงพอว่าโค้ดที่เรียกใช้พยายามทำอะไรจริงๆ เราจึงส่งต่อข้อมูลความสำเร็จหรือข้อผิดพลาดทั้งหมดขึ้นไปให้มันจัดการอย่างเหมาะสม

ข้อความแสดงข้อผิดพลาดยังกล่าวด้วยว่า `?` สามารถใช้กับค่า `Option<T>` ได้เช่นกัน เช่นเดียวกับการใช้ `?` กับ `Result` คุณใช้ `?` กับ `Option` ได้เฉพาะในฟังก์ชันที่คืนค่า `Option` เท่านั้น พฤติกรรมของตัวดำเนินการ `?` เมื่อเรียกบน `Option<T>` นั้นคล้ายกับพฤติกรรมของมันเมื่อเรียกบน `Result<T, E>`: หากค่าเป็น `None` `None` จะถูกคืนออกจากฟังก์ชันแต่เนิ่นๆ ณ จุดนั้น หากค่าเป็น `Some` ค่าที่อยู่ภายใน `Some` คือค่าผลลัพธ์ของเอ็กซ์เพรสชัน และฟังก์ชันดำเนินต่อไป ลิสติ้ง 9-11 มีตัวอย่างของฟังก์ชันที่ค้นหาอักขระตัวสุดท้ายของบรรทัดแรกในข้อความที่กำหนดให้

ฟังก์ชันนี้คืนค่า `Option<char>` เพราะเป็นไปได้ว่ามีอักขระอยู่ตรงนั้น แต่ก็เป็นไปได้เช่นกันว่าไม่มี โค้ดนี้รับอาร์กิวเมนต์สตริงสไลซ์ (string slice) `text` และเรียกเมธอด `lines` บนมัน ซึ่งคืนค่าอิเทอเรเตอร์ (iterator) เหนือบรรทัดต่างๆ ในสตริง เนื่องจากฟังก์ชันนี้ต้องการตรวจสอบบรรทัดแรก มันจึงเรียก `next` บนอิเทอเรเตอร์เพื่อรับค่าแรกจากอิเทอเรเตอร์ หาก `text` เป็นสตริงว่าง การเรียก `next` นี้จะคืนค่า `None` ซึ่งในกรณีนั้นเราใช้ `?` เพื่อหยุดและคืนค่า `None` จาก `last_char_of_first_line` หาก `text` ไม่ใช่สตริงว่าง `next` จะคืนค่า `Some` ที่บรรจุสตริงสไลซ์ของบรรทัดแรกใน `text`

`?` ดึงสตริงสไลซ์ออกมา และเราเรียก `chars` บนสตริงสไลซ์นั้นเพื่อรับอิเทอเรเตอร์ของอักขระในนั้น เราสนใจอักขระตัวสุดท้ายในบรรทัดแรกนี้ เราจึงเรียก `last` เพื่อคืนรายการสุดท้ายในอิเทอเรเตอร์ นี่เป็น `Option` เพราะเป็นไปได้ว่าบรรทัดแรกเป็นสตริงว่าง ตัวอย่างเช่น หาก `text` เริ่มต้นด้วยบรรทัดว่างแต่มีอักขระในบรรทัดอื่นๆ อย่างใน `"\nhi"` อย่างไรก็ตาม หากมีอักขระตัวสุดท้ายในบรรทัดแรก มันจะถูกคืนกลับในวาเรียนต์ `Some` ตัวดำเนินการ `?` ที่อยู่ตรงกลางให้วิธีกระชับในการแสดงลอจิกนี้ ทำให้เราอิมพลีเมนต์ฟังก์ชันได้ในบรรทัดเดียว หากเราใช้ตัวดำเนินการ `?` กับ `Option` ไม่ได้ เราจะต้องอิมพลีเมนต์ลอจิกนี้โดยใช้การเรียกเมธอดเพิ่มเติมหรือเอ็กซ์เพรสชัน `match`

โปรดสังเกตว่าคุณใช้ตัวดำเนินการ `?` กับ `Result` ในฟังก์ชันที่คืนค่า `Result` ได้ และคุณใช้ตัวดำเนินการ `?` กับ `Option` ในฟังก์ชันที่คืนค่า `Option` ได้ แต่คุณผสมกันไม่ได้ ตัวดำเนินการ `?` จะไม่แปลง `Result` เป็น `Option` หรือในทางกลับกันโดยอัตโนมัติ ในกรณีเหล่านั้น คุณสามารถใช้เมธอดอย่างเมธอด `ok` บน `Result` หรือเมธอด `ok_or` บน `Option` เพื่อทำการแปลงอย่างชัดแจ้งได้

จนถึงตอนนี้ ฟังก์ชัน `main` ทั้งหมดที่เราใช้คืนค่า `()` ฟังก์ชัน `main` นั้นพิเศษเพราะมันเป็นจุดเข้าและจุดออกของโปรแกรมที่รันได้ และมีข้อจำกัดว่าชนิดที่คืนกลับของมันเป็นอะไรได้บ้างเพื่อให้โปรแกรมทำงานได้ตามที่คาดหวัง

โชคดีที่ `main` คืนค่า `Result<(), E>` ได้ด้วย ลิสติ้ง 9-12 มีโค้ดจากลิสติ้ง 9-10 แต่เราเปลี่ยนชนิดที่คืนกลับของ `main` เป็น `Result<(), Box<dyn Error>>` และเพิ่มค่า `Ok(())` ที่ท้ายเป็นค่าที่คืนกลับ โค้ดนี้จะคอมไพล์ผ่านแล้ว

ชนิด `Box<dyn Error>` เป็นเทรตออบเจกต์ (trait object) ซึ่งเราจะพูดถึงใน[“การใช้เทรตออบเจกต์เพื่อนามธรรมพฤติกรรมร่วม”][trait-objects]<!-- ignore --> ในบทที่ 18 สำหรับตอนนี้ คุณอ่าน `Box<dyn Error>` ได้ว่า “ข้อผิดพลาดชนิดใดก็ได้” การใช้ `?` กับค่า `Result` ในฟังก์ชัน `main` ที่มีชนิดข้อผิดพลาดเป็น `Box<dyn Error>` นั้นได้รับอนุญาต เพราะมันยอมให้ค่า `Err` ใดๆ ถูกคืนกลับแต่เนิ่นๆ แม้ว่าเนื้อในของฟังก์ชัน `main` นี้จะคืนข้อผิดพลาดชนิด `std::io::Error` เท่านั้น แต่การระบุ `Box<dyn Error>` ทำให้ลายเซ็นนี้ยังคงถูกต้องต่อไป แม้จะมีโค้ดที่คืนข้อผิดพลาดอื่นเพิ่มเข้าไปในเนื้อในของ `main`

เมื่อฟังก์ชัน `main` คืนค่า `Result<(), E>` โปรแกรมที่รันได้จะออกด้วยค่า `0` หาก `main` คืนค่า `Ok(())` และจะออกด้วยค่าที่ไม่เป็นศูนย์หาก `main` คืนค่า `Err` โปรแกรมที่รันได้ซึ่งเขียนด้วยภาษา C จะคืนค่าจำนวนเต็มเมื่อออกจากโปรแกรม: โปรแกรมที่ออกอย่างสำเร็จจะคืนค่าจำนวนเต็ม `0` และโปรแกรมที่เกิดข้อผิดพลาดจะคืนค่าจำนวนเต็มอื่นที่ไม่ใช่ `0` Rust ก็คืนค่าจำนวนเต็มจากโปรแกรมที่รันได้เช่นกันเพื่อให้เข้ากันได้กับธรรมเนียมนี้

ฟังก์ชัน `main` อาจคืนค่าชนิดใดก็ได้ที่อิมพลีเมนต์[เทรต `std::process::Termination`][termination]<!-- ignore --> ซึ่งมีฟังก์ชัน `report` ที่คืนค่า `ExitCode` ปรึกษาเอกสารไลบรารีมาตรฐานสำหรับข้อมูลเพิ่มเติมเกี่ยวกับการอิมพลีเมนต์เทรต `Termination` ให้กับชนิดข้อมูลของคุณเอง
