### การคืนการควบคุมให้รันไทม์

ย้อนนึกจากหัวข้อ[“โปรแกรม async โปรแกรมแรกของเรา”][async-program]<!-- ignore -->ว่า ณ จุด await แต่ละจุด Rust จะเปิดโอกาสให้รันไทม์ (runtime) หยุดทาสก์ (task) ชั่วคราวและสลับไปทำอีกทาสก์หนึ่งได้หากฟิวเจอร์ (future) ที่กำลังถูก await นั้นยังไม่พร้อม ในทางกลับกันก็เป็นจริงเช่นกัน: Rust จะหยุดบล็อก async ชั่วคราวและคืนการควบคุมกลับให้รันไทม์_เฉพาะ_ที่จุด await เท่านั้น ทุกสิ่งระหว่างจุด await นั้นเป็นแบบซิงโครนัส

นั่นหมายความว่าหากคุณทำงานจำนวนมากในบล็อก async โดยไม่มีจุด await ฟิวเจอร์นั้นจะขัดขวางไม่ให้ฟิวเจอร์อื่นๆ ทำความคืบหน้าได้ คุณอาจเคยได้ยินกรณีนี้เรียกกันว่าฟิวเจอร์หนึ่ง_ทำให้ฟิวเจอร์อื่นอดอยาก_ (starving) ในบางกรณี นั่นอาจไม่ใช่เรื่องใหญ่ อย่างไรก็ตาม หากคุณกำลังทำการตั้งค่าที่มีค่าใช้จ่ายสูงหรือทำงานที่ใช้เวลานาน หรือหากคุณมีฟิวเจอร์ที่จะทำงานเฉพาะบางอย่างต่อไปเรื่อยๆ อย่างไม่สิ้นสุด คุณจะต้องคิดว่าเมื่อไหร่และที่ไหนควรคืนการควบคุมกลับให้รันไทม์

โค้ดนี้ทั้งชัดเจนกว่าในแง่เจตนาที่แท้จริงและอาจเร็วกว่าการใช้ `sleep` อย่างมีนัยสำคัญ เพราะตัวจับเวลาเช่นตัวที่ `sleep` ใช้นั้นมักมีขีดจำกัดว่าละเอียดได้แค่ไหน ตัวอย่างเช่น เวอร์ชันของ `sleep` ที่เราใช้นี้จะนอนหลับอย่างน้อยหนึ่งมิลลิวินาทีเสมอ แม้เราจะส่ง `Duration` หนึ่งนาโนวินาทีให้มันก็ตาม ย้ำอีกครั้งว่าคอมพิวเตอร์สมัยใหม่นั้น_เร็ว_: มันทำอะไรได้มากมายในหนึ่งมิลลิวินาที!

นั่นหมายความว่า async สามารถมีประโยชน์ได้แม้กับงานที่จำกัดด้วยการประมวลผล ขึ้นอยู่กับว่าโปรแกรมของคุณกำลังทำอะไรอย่างอื่นอยู่ เพราะมันให้เครื่องมือที่มีประโยชน์สำหรับจัดโครงสร้างความสัมพันธ์ระหว่างส่วนต่างๆ ของโปรแกรม (แต่แลกมาด้วยค่าใช้จ่ายส่วนเกินของสเตตแมชชีน async) นี่เป็นรูปแบบหนึ่งของ_การทำหลายงานแบบร่วมมือกัน_ (cooperative multitasking) ซึ่งฟิวเจอร์แต่ละตัวมีอำนาจตัดสินใจว่าเมื่อไหร่มันจะส่งต่อการควบคุมผ่านจุด await ด้วยเหตุนี้ ฟิวเจอร์แต่ละตัวจึงมีความรับผิดชอบที่จะหลีกเลี่ยงการบล็อกนานเกินไปด้วย ในระบบปฏิบัติการแบบฝังตัวบางตัวที่ใช้ Rust นี่คือรูปแบบ_เดียว_ของการทำหลายงานที่มี!

แน่นอนว่าในโค้ดจริง คุณมักจะไม่สลับการเรียกฟังก์ชันกับจุด await ในทุกบรรทัด แม้ว่าการคืนการควบคุมแบบนี้จะค่อนข้างมีค่าใช้จ่ายต่ำ แต่มันก็ไม่ฟรี ในหลายกรณี การพยายามแบ่งงานที่จำกัดด้วยการประมวลผลออกอาจทำให้มันช้าลงอย่างมีนัยสำคัญ ดังนั้นบางครั้งการปล่อยให้การดำเนินการบล็อกชั่วครู่ก็ให้ประสิทธิภาพ_โดยรวม_ที่ดีกว่า จงวัดผลเสมอเพื่อดูว่าคอขวดด้านประสิทธิภาพที่แท้จริงของโค้ดคุณคืออะไร อย่างไรก็ตาม พลวัตพื้นฐานนี้เป็นสิ่งสำคัญที่ควรคำนึงถึง หากคุณ_กำลัง_เห็นงานจำนวนมากเกิดขึ้นแบบอนุกรมทั้งที่คุณคาดหวังว่ามันจะเกิดขึ้นพร้อมกัน!

### การสร้างนามธรรม async ของเราเอง

มาลองอิมพลีเมนต์กัน! เริ่มต้นด้วยการคิดถึง API ของ `timeout`:

- มันต้องเป็นฟังก์ชัน async เสียเองเพื่อให้เรา await มันได้
- พารามิเตอร์ตัวแรกควรเป็นฟิวเจอร์ที่จะรัน เราทำให้มันเป็นเจเนอริก (generic) เพื่อให้มันทำงานกับฟิวเจอร์ใดก็ได้
- พารามิเตอร์ตัวที่สองจะเป็นเวลารอสูงสุด หากเราใช้ `Duration` มันจะทำให้ส่งต่อไปยัง `trpl::sleep` ได้ง่าย

การอิมพลีเมนต์ `trpl::select` นั้นไม่ยุติธรรม: มันจะทำการโพลล์ (polling) อาร์กิวเมนต์ตามลำดับที่พวกมันถูกส่งเข้ามาเสมอ (การอิมพลีเมนต์ `select` อื่นๆ จะสุ่มเลือกว่าจะโพลล์อาร์กิวเมนต์ใดก่อน) ดังนั้น เราจึงส่ง `future_to_try` ให้ `select` เป็นตัวแรกเพื่อให้มันมีโอกาสเสร็จสมบูรณ์แม้ `max_time` จะเป็นระยะเวลาที่สั้นมาก หาก `future_to_try` เสร็จก่อน `select` จะคืนค่า `Left` พร้อมเอาต์พุตจาก `future_to_try` หาก `timer` เสร็จก่อน `select` จะคืนค่า `Right` พร้อมเอาต์พุต `()` ของตัวจับเวลา

หาก `future_to_try` สำเร็จและเราได้ `Left(output)` เราจะคืนค่า `Ok(output)` หากตัวจับเวลาการนอนหลับหมดเวลาก่อนและเราได้ `Right(())` เราจะไม่สนใจ `()` ด้วย `_` แล้วคืนค่า `Err(max_time)` แทน

เท่านี้เราก็ได้ `timeout` ที่ใช้งานได้ ซึ่งสร้างขึ้นจากตัวช่วย async อีกสองตัว หากเรารันโค้ดของเรา มันจะพิมพ์โหมดล้มเหลวหลังหมดเวลา:

```text
Failed after 2 seconds
```

เพราะฟิวเจอร์สามารถประกอบเข้ากับฟิวเจอร์อื่นได้ คุณจึงสร้างเครื่องมือที่ทรงพลังมากจากชิ้นส่วนพื้นฐาน async ที่เล็กกว่าได้ ตัวอย่างเช่น คุณใช้แนวทางเดียวกันนี้รวมไทม์เอาต์เข้ากับการลองใหม่ (retries) และนำสิ่งเหล่านั้นไปใช้กับการดำเนินการอย่างการเรียกเครือข่าย (เช่นที่อยู่ในลิสติ้ง 17-5) ได้

ในทางปฏิบัติ คุณมักจะทำงานโดยตรงกับ `async` และ `await` และเป็นลำดับรองลงมากับฟังก์ชันอย่าง `select` และมาโคร (macro) อย่างมาโคร `join!` เพื่อควบคุมว่าฟิวเจอร์ชั้นนอกสุดถูกเรียกใช้อย่างไร

ตอนนี้เราได้เห็นหลายวิธีในการทำงานกับฟิวเจอร์หลายตัวในเวลาเดียวกันแล้ว ต่อไปนี้ เราจะดูว่าเราทำงานกับฟิวเจอร์หลายตัวที่เรียงต่อกันตามเวลาด้วย_สตรีม_ (stream) ได้อย่างไร
