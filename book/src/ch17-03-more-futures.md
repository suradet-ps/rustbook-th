### การคืนการควบคุมให้รันไทม์

หากยังจำได้จากหัวข้อ[“โปรแกรม async โปรแกรมแรกของเรา”][async-program]<!-- ignore --> ณ จุด await แต่ละจุดนั้น Rust จะเปิดโอกาสให้รันไทม์ (runtime) พักการทำงานของทาสก์ (task) ไว้ชั่วคราว แล้วสลับไปทำงานอื่นแทนได้หากฟิวเจอร์ (future) ที่กำลังถูก await ยังไม่พร้อมทำงาน และในทางตรงกันข้ามก็เป็นจริงเช่นกัน: นั่นคือ Rust จะหยุดพักบล็อก async และส่งมอบการควบคุมกลับคืนให้แก่รันไทม์_เฉพาะ_ ณ จุด await เท่านั้น การทำงานทุกอย่างที่อยู่คั่นระหว่างจุด await จะดำเนินไปแบบซิงโครนัสเสมอ

นั่นหมายความว่า หากคุณเขียนการประมวลผลไว้เป็นจำนวนมากภายในบล็อก async โดยไม่มีจุด await เลยแม้แต่จุดเดียว ฟิวเจอร์นั้นจะบล็อกการทำงานจนฟิวเจอร์ตัวอื่นๆ ไม่สามารถคืบหน้าไปได้เลย บางครั้งคุณอาจได้ยินคำเรียกปรากฏการณ์นี้ว่า ฟิวเจอร์หนึ่ง_แย่งทรัพยากรจนฟิวเจอร์อื่นอดอยาก (starving)_ แม้ในบางกรณีสิ่งนี้อาจไม่ใช่เรื่องใหญ่นัก แต่หากคุณกำลังทำงานที่มีการเตรียมทรัพยากรหนักๆ หรืองานที่กินเวลายาวนาน หรือมีฟิวเจอร์ที่ต้องรันงานเฉพาะบางอย่างวนซ้ำไปเรื่อยๆ อย่างไม่มีที่สิ้นสุด คุณจำเป็นต้องพิจารณาอย่างรอบคอบว่าเมื่อใดและ ณ จุดใดที่ควรจะส่งมอบการควบคุมกลับคืนให้แก่รันไทม์

โค้ดนี้ไม่เพียงแต่สื่อเจตนาที่แท้จริงได้ชัดเจนยิ่งขึ้นเท่านั้น แต่ยังทำงานได้เร็วกว่าการใช้ `sleep` อย่างมีนัยสำคัญอีกด้วย เนื่องจากตัวจับเวลาที่ `sleep` ใช้นั้นมักจะมีขีดจำกัดในเรื่องความละเอียดของเวลา ตัวอย่างเช่น ฟังก์ชัน `sleep` เวอร์ชันที่เราใช้นี้จะหยุดหลับอย่างน้อย 1 มิลลิวินาทีเสมอ แม้ว่าเราจะส่งค่า `Duration` เพียง 1 นาโนวินาทีเข้าไปก็ตาม และขอเน้นย้ำอีกครั้งว่า คอมพิวเตอร์ยุคปัจจุบันนั้น_เร็วมาก_: ในเวลาเพียง 1 มิลลิวินาที มันสามารถคำนวณและประมวลผลงานได้มหาศาล!

นั่นหมายความว่า async มีประโยชน์แม้กระทั่งกับงานประเภทประมวลผลหนัก (compute-bound) ขึ้นอยู่กับว่าโปรแกรมของคุณกำลังทำงานอื่นใดควบคู่ไปด้วยหรือไม่ เพราะมันเป็นเครื่องมือชั้นยอดในการจัดโครงสร้างความสัมพันธ์ระหว่างแต่ละส่วนของโปรแกรม (แม้จะมีต้นทุน overhead จากสเตตแมชชีนของ async แลกมาด้วยก็ตาม) นี่คือรูปแบบหนึ่งของ_การทำงานหลายงานแบบร่วมมือกัน (cooperative multitasking)_ ซึ่งฟิวเจอร์แต่ละตัวมีอำนาจตัดสินใจว่าเมื่อใดจะยอมส่งมอบการควบคุมผ่านจุด await และด้วยเหตุนี้ ฟิวเจอร์แต่ละตัวจึงมีความรับผิดชอบที่จะต้องไม่บล็อกการทำงานไว้นานจนเกินไปด้วย ในระบบปฏิบัติการสมองกลฝังตัว (embedded OS) บางระบบที่พัฒนาด้วย Rust นี่คือรูปแบบการทำงานหลายงาน_เพียงรูปแบบเดียว_ที่มีให้ใช้งาน!

แน่นอนว่าในโค้ดการใช้งานจริง คุณคงไม่ได้เขียนสลับการเรียกฟังก์ชันกับจุด await ในทุกๆ บรรทัดเช่นนี้ แม้ว่าการยอมสละการควบคุม (yielding control) ในลักษณะนี้จะมีต้นทุนค่อนข้างต่ำ แต่ก็ไม่ได้เกิดขึ้นฟรีๆ ในหลายกรณี การพยายามแบ่งย่อยงานที่ประมวลผลหนักๆ อาจทำให้การทำงานโดยรวมช้าลงอย่างเห็นได้ชัด ดังนั้นบางครั้งการยอมให้งานบล็อกเพียงครู่สั้นๆ อาจให้ประสิทธิภาพ_โดยรวม_ที่ดีกว่า จงคอยตรวจวัดประสิทธิภาพจริงของโค้ดอยู่เสมอเพื่อค้นหาว่าคอขวดที่แท้จริงอยู่ที่ใด แต่ไม่ว่าอย่างไร กลไกพื้นฐานนี้คือหัวใจสำคัญที่คุณควรตระหนักไว้ หากคุณ_เริ่มสังเกตเห็น_ว่างานจำนวนมากกำลังรันเรียงลำดับกันไป ทั้งๆ ที่คุณตั้งใจให้มันทำงานพร้อมกัน!

### การสร้างนามธรรม async ของเราเอง

เรายังสามารถนำฟิวเจอร์มาประกอบเข้าด้วยกัน (compose) เพื่อสร้างแพตเทิร์นใหม่ๆ ได้อีกด้วย ตัวอย่างเช่น เราสามารถสร้างฟังก์ชัน `timeout` ขึ้นมาจากองค์ประกอบ async พื้นฐานที่เรามีอยู่แล้ว และเมื่อเสร็จสิ้น ฟังก์ชันนี้ก็จะกลายเป็นองค์ประกอบพื้นฐานชิ้นใหม่ที่เราสามารถนำไปต่อยอดสร้างแอ็บสแตรกชัน async อื่นๆ เพิ่มขึ้นไปได้อีก

เรามาลองลงมืออิมพลีเมนต์สิ่งนี้กัน! เริ่มต้นจากการวางแผน API ของ `timeout`:

- ฟังก์ชันนี้ต้องเป็นฟังก์ชัน async ในตัวเอง เพื่อให้เราสามารถ await มันได้
- พารามิเตอร์แรกควรเป็นฟิวเจอร์ที่ต้องการสั่งให้รัน โดยเราสามารถกำหนดให้เป็นเจเนอริก (generic) เพื่อให้ทำงานกับฟิวเจอร์ชนิดใดก็ได้
- พารามิเตอร์ที่สองคือระยะเวลาสูงสุดที่จะรอ ซึ่งหากเราใช้ `Duration` ก็จะทำให้ส่งต่อให้แก่ `trpl::sleep` ได้อย่างง่ายดาย
- ฟังก์ชันควรคืนค่าเป็น `Result` โดยหากฟิวเจอร์ทำงานสำเร็จ `Result` จะเป็น `Ok` พร้อมกับค่าที่ฟิวเจอร์สร้างขึ้น แต่หากหมดเวลาเสียก่อน `Result` จะเป็น `Err` พร้อมระยะเวลาที่ตัวไทม์เอาต์รอไป

การอิมพลีเมนต์ของ `trpl::select` นั้นไม่ได้กระจายความยุติธรรมเท่ากัน: กล่าวคือ มันจะทำการโพลล์ (poll) อาร์กิวเมนต์ตามลำดับที่ส่งเข้ามาเสมอ (ในขณะที่การอิมพลีเมนต์ `select` แบบอื่นๆ อาจสุ่มเลือกว่าจะโพลล์อาร์กิวเมนต์ใดก่อน) ดังนั้น เราจึงส่ง `future_to_try` เข้าไปยัง `select` เป็นตัวแรก เพื่อให้มันมีโอกาสทำงานจนเสร็จแม้ว่า `max_time` จะสั้นมากก็ตาม หาก `future_to_try` ทำงานเสร็จก่อน `select` จะคืนค่า `Left` พร้อมข้อมูลเอาต์พุตจาก `future_to_try` แต่หาก `timer` เสร็จก่อน `select` จะคืนค่า `Right` พร้อมเอาต์พุต `()` ของตัวจับเวลา

หาก `future_to_try` ทำงานสำเร็จและเราได้รับ `Left(output)` เราจะคืนค่า `Ok(output)` แต่หากตัวจับเวลานับถอยหลังหมดลงก่อนและเราได้รับ `Right(())` เราจะละเลยค่า `()` ด้วยเครื่องหมาย `_` แล้วคืนค่า `Err(max_time)` ออกไปแทน

เพียงเท่านี้เราก็ได้ฟังก์ชัน `timeout` ที่ใช้งานได้จริง ซึ่งประกอบขึ้นจากตัวช่วย async สองตัว และหากเรารันโค้ด มันจะแสดงผลกรณีหมดเวลาดังนี้:

```text
Failed after 2 seconds
```

และเนื่องจากฟิวเจอร์สามารถนำมาประกอบร่วมกับฟิวเจอร์อื่นๆ ได้ คุณจึงสามารถสร้างเครื่องมือที่ทรงพลังอย่างยิ่งขึ้นมาจากองค์ประกอบย่อยๆ แบบ async ตัวอย่างเช่น คุณสามารถใช้แนวทางนี้ผสานไทม์เอาต์เข้ากับระบบลองใหม่ (retries) แล้วนำไปประยุกต์ใช้กับการเรียกใช้งานเครือข่าย (ดังเช่นในลิสติ้ง 17-5) ได้

ในทางปฏิบัติ คุณมักจะเขียนโค้ดโดยใช้ `async` และ `await` เป็นหลัก และใช้งานฟังก์ชันอย่าง `select` ตลอดจนมาโครอย่าง `join!` ในลำดับรองลงมา เพื่อควบคุมจังหวะการประมวลผลของฟิวเจอร์ชั้นนอกสุด

จนถึงตอนนี้ เราได้เห็นหลากหลายวิธีในการทำงานกับฟิวเจอร์หลายๆ ตัวไปพร้อมกันแล้ว ในหัวข้อถัดไป เราจะมาดูกันว่าเราสามารถจัดการกับฟิวเจอร์ที่ทยอยมาอย่างต่อเนื่องตามลำดับเวลาด้วย_สตรีม (stream)_ ได้อย่างไร
