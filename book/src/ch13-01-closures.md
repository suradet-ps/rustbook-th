## โคลเชอร์

โคลเชอร์ (closure) ในภาษา Rust คือฟังก์ชันแบบไม่ระบุชื่อ (anonymous function) ที่คุณสามารถจัดเก็บไว้ในตัวแปร หรือส่งเป็นอาร์กิวเมนต์ไปยังฟังก์ชันอื่นได้ คุณสามารถนิยามโคลเชอร์ขึ้นมาที่จุดหนึ่ง แล้วนำไปเรียกประมวลผลที่จุดอื่นในบริบทที่แตกต่างออกไปได้ นอกจากนี้ โคลเชอร์ยังมีความพิเศษต่างจากฟังก์ชันทั่วไปตรงที่มันสามารถจับค่า (capture) จากสโคปที่มันถูกสร้างขึ้นมาได้ด้วย เราจะมาดูกันว่าฟีเจอร์เหล่านี้ของโคลเชอร์ช่วยให้เราสามารถนำโค้ดกลับมาใช้ซ้ำ (code reuse) และปรับแต่งพฤติกรรมการทำงานได้อย่างไร

### การจับสภาพแวดล้อม

อันดับแรก เราจะมาดูวิธีใช้โคลเชอร์เพื่อจับค่าจากสภาพแวดล้อมที่มันถูกนิยามขึ้นมาสำหรับนำไปใช้งานในภายหลัง ลองพิจารณาสถานการณ์จำลองนี้: ในบางโอกาส บริษัทเสื้อยืดของเราจะแจกเสื้อรุ่นพิเศษแบบลิมิเต็ดเอดิชันให้กับผู้โชคดีในรายชื่ออีเมลของเราเพื่อการส่งเสริมการขาย โดยผู้รับอีเมลสามารถเลือกใส่สีเสื้อที่ตนชอบลงในโปรไฟล์ได้ตามความสมัครใจ หากผู้โชคดีที่ได้รับรางวัลได้ระบุสีโปรดไว้ พวกเขาก็จะได้เสื้อสีนั้นไป แต่หากไม่ได้ระบุสีโปรดไว้ พวกเขาจะได้เสื้อสีที่ทางบริษัทมีอยู่ในสต็อกมากที่สุดในขณะนั้นแทน

เราสามารถพัฒนาโจทย์นี้ได้หลากหลายวิธี สำหรับตัวอย่างนี้ เราจะใช้ enum ชื่อ `ShirtColor` ซึ่งมีวาเรียนต์ `Red` และ `Blue` (เพื่อความเรียบง่าย เราจะจำกัดไว้เพียงสองสี) เราจะจำลองคลังสินค้าของบริษัทด้วย struct ชื่อ `Inventory` ที่มีฟิลด์ `shirts` เก็บข้อมูลชนิด `Vec<ShirtColor>` แทนสีของเสื้อที่ยังมีอยู่ในสต็อกปัจจุบัน ส่วนเมธอด `giveaway` ที่นิยามบน `Inventory` จะรับค่าความชอบเรื่องสีเสื้อของผู้โชคดี (ซึ่งอาจระบุหรือไม่ระบุก็ได้) และจะส่งคืนสีเสื้อที่คนนั้นจะได้รับ โครงสร้างทั้งหมดนี้แสดงไว้ในลิสติ้ง 13-1

เช่นเดิม โค้ดนี้สามารถเขียนได้หลายแบบ แต่เพื่อให้เรามุ่งเน้นไปที่เรื่องโคลเชอร์ เราจึงเลือกใช้แนวคิดพื้นฐานที่คุณคุ้นเคยกันดีอยู่แล้ว ยกเว้นเนื้อในเมธอด `giveaway` ที่นำโคลเชอร์เข้ามาช่วย ในเมธอด `giveaway` เราได้รับความชอบของผู้ใช้ผ่านพารามิเตอร์ชนิด `Option<ShirtColor>` แล้วเรียกเมธอด `unwrap_or_else` บน `user_preference` โดย[เมธอด `unwrap_or_else` บน `Option<T>`][unwrap-or-else]<!-- ignore --> นี้ถูกนิยามไว้ในไลบรารีมาตรฐาน ซึ่งรับอาร์กิวเมนต์หนึ่งตัวเป็นโคลเชอร์ที่ไม่ต้องรับพารามิเตอร์ใดๆ แต่ส่งคืนค่าชนิด `T` ออกมา (ซึ่งเป็นชนิดเดียวกับที่เก็บอยู่ในวาเรียนต์ `Some` ของ `Option<T>` ซึ่งในที่นี้ก็คือ `ShirtColor`) หาก `Option<T>` เป็นวาเรียนต์ `Some` เมธอด `unwrap_or_else` จะดึงค่าที่อยู่ข้างใน `Some` ออกมาส่งกลับให้ทันที แต่ถ้า `Option<T>` เป็นวาเรียนต์ `None` เมธอด `unwrap_or_else` จะเรียกสั่งรันโคลเชอร์ แล้วนำค่าที่โคลเชอร์ส่งกลับมานั้นมาส่งคืนต่อไป

เราระบุนิพจน์ของโคลเชอร์เป็น `|| self.most_stocked()` ส่งเป็นอาร์กิวเมนต์ให้กับ `unwrap_or_else` โคลเชอร์นี้เป็นโคลเชอร์ที่ไม่รับพารามิเตอร์ใดๆ เลย (หากโคลเชอร์มีพารามิเตอร์ พารามิเตอร์เหล่านั้นจะอยู่ระหว่างเส้นขีดแนวตั้งหรือเครื่องหมายไปป์ `| |` สองอัน) และบอดี้ของโคลเชอร์จะสั่งเรียก `self.most_stocked()` ตรงนี้เราแค่นิยามโคลเชอร์เตรียมไว้ แล้วการทำงานภายในของ `unwrap_or_else` จะเป็นฝ่ายเรียกประเมินผลโคลเชอร์นี้ในภายหลังเมื่อมีความจำเป็นต้องใช้ผลลัพธ์เท่านั้น

### การอนุมานและการระบุชนิดของโคลเชอร์

ยังมีข้อแตกต่างอื่นๆ ระหว่างฟังก์ชันกับโคลเชอร์อีก โดยทั่วไปแล้วโคลเชอร์ไม่จำเป็นต้องให้คุณระบุชนิดข้อมูล (type annotation) ของพารามิเตอร์หรือค่าที่ส่งกลับเหมือนกับฟังก์ชัน `fn` เหตุผลที่ฟังก์ชันจำเป็นต้องระบุชนิดข้อมูลกำกับไว้เสมอ เพราะชนิดข้อมูลเป็นส่วนหนึ่งของอินเทอร์เฟซสาธารณะที่เปิดเผยต่อผู้เรียกใช้งาน การกำหนดอินเทอร์เฟซนี้ไว้อย่างชัดเจนและตายตัวจึงมีความสำคัญต่อการรับประกันว่าทุกคนเข้าใจตรงกันว่าฟังก์ชันนั้นรับและส่งกลับข้อมูลชนิดใด ในทางกลับกัน โคลเชอร์ไม่ได้ถูกนำไปใช้งานเป็นอินเทอร์เฟซที่เปิดเผยภายนอกเช่นนั้น โดยมากมันจะถูกจัดเก็บไว้ในตัวแปร และถูกเรียกใช้งานเฉพาะจุดโดยไม่ต้องตั้งชื่อหรือเปิดเผยให้ผู้ใช้ไลบรารีเห็น

โคลเชอร์มักจะมีขนาดสั้นและเกี่ยวข้องอยู่เฉพาะในบริบทที่แคบ แทนที่จะเป็นบริบทกว้างๆ ทั่วไป ภายในขอบเขตจำกัดเหล่านี้ คอมไพเลอร์จึงสามารถอนุมาน (infer) ชนิดข้อมูลของพารามิเตอร์และชนิดของค่าที่ส่งกลับได้เอง คล้ายกับวิธีที่มันอนุมานชนิดของตัวแปรส่วนใหญ่ (แม้ว่าจะมีกรณีที่พบได้ยากอยู่บ้างที่คอมไพเลอร์ต้องการให้ระบุชนิดของโคลเชอร์ด้วยเช่นกัน)

เช่นเดียวกับตัวแปร หากเราต้องการเพิ่มความชัดเจนให้เห็นอย่างชัดเจน เราก็สามารถเขียนระบุชนิดข้อมูลกำกับไว้ได้ แม้จะต้องแลกมาด้วยความยาวของโค้ดที่มากกว่าที่จำเป็นก็ตาม การระบุชนิดข้อมูลให้โคลเชอร์จะมีหน้าตาดังแสดงในลิสติ้ง 13-2 ซึ่งในตัวอย่างนี้ เราจะนิยามโคลเชอร์แล้วเก็บไว้ในตัวแปร แทนที่จะนิยามตรงจุดที่ส่งเป็นอาร์กิวเมนต์แบบที่เราทำในลิสติ้ง 13-1

เมื่อใส่การระบุชนิดข้อมูลเข้าไปแล้ว ไวยากรณ์ของโคลเชอร์จะดูคล้ายกับไวยากรณ์ของฟังก์ชันมากยิ่งขึ้น ในตัวอย่างนี้ เราจะนิยามฟังก์ชันที่บวกค่า 1 ให้กับพารามิเตอร์ เทียบกับโคลเชอร์ที่มีพฤติกรรมเดียวกันเพื่อเปรียบเทียบให้เห็นชัดเจน โดยเราได้เว้นวรรคช่องว่างบางส่วนเพื่อให้ส่วนที่ตรงกันวางเรียงตรงกันพอดี ซึ่งจะแสดงให้เห็นว่าไวยากรณ์ของโคลเชอร์คล้ายกับฟังก์ชันเพียงใด ยกเว้นการเปลี่ยนมาใช้เครื่องหมายไปป์และปริมาณไวยากรณ์ที่เป็นทางเลือก:

```rust,ignore
fn  add_one_v1   (x: u32) -> u32 { x + 1 }
let add_one_v2 = |x: u32| -> u32 { x + 1 };
let add_one_v3 = |x|             { x + 1 };
let add_one_v4 = |x|               x + 1  ;
```

บรรทัดแรกแสดงการนิยามฟังก์ชัน ส่วนบรรทัดที่สองแสดงการนิยามโคลเชอร์แบบระบุชนิดข้อมูลอย่างสมบูรณ์ ในบรรทัดที่สาม เราตัดการระบุชนิดข้อมูลออกจากโคลเชอร์ และในบรรทัดที่สี่ เราตัดเครื่องหมายปีกกาออกด้วย ซึ่งสามารถทำได้เนื่องจากบอดี้ของโคลเชอร์มีเพียงนิพจน์เดียว ทั้งหมดนี้ถือเป็นนิยามที่ถูกต้องตามไวยากรณ์และจะให้ผลลัพธ์เหมือนกันทุกประการเมื่อถูกเรียกใช้งาน สำหรับบรรทัด `add_one_v3` และ `add_one_v4` นั้น จำเป็นต้องมีการเรียกใช้งานโคลเชอร์ในโค้ดด้วยจึงจะคอมไพล์ผ่าน เพราะคอมไพเลอร์จำเป็นต้องอนุมานชนิดข้อมูลจากการนำไปใช้งานจริง ซึ่งคล้ายกับคำสั่ง `let v = Vec::new();` ที่จำเป็นต้องมี type annotation หรือต้องมีการเพิ่มสมาชิกบางชนิดเข้าไปใน `Vec` ก่อน เพื่อให้ Rust อนุมานชนิดข้อมูลที่แน่นอนได้

สำหรับการนิยามโคลเชอร์ คอมไพเลอร์จะอนุมานชนิดข้อมูลที่เป็นรูปธรรม (concrete type) เพียงชนิดเดียวให้กับแต่ละพารามิเตอร์และค่าที่ส่งกลับ ตัวอย่างเช่น ลิสติ้ง 13-3 แสดงการนิยามโคลเชอร์สั้นๆ ที่ทำหน้าที่เพียงส่งค่าพารามิเตอร์ที่ได้รับกลับไปทันที โคลเชอร์นี้ไม่ได้มีประโยชน์ในทางปฏิบัติมากนักนอกจากใช้เป็นตัวอย่างประกอบ โปรดสังเกตว่าเราไม่ได้ระบุชนิดข้อมูลกำกับไว้เลย ซึ่งหมายความว่าเราสามารถเรียกใช้โคลเชอร์นี้กับข้อมูลชนิดใดก็ได้ โดยในการเรียกครั้งแรกเราได้ส่งค่า `String` เข้าไป แต่หากหลังจากนั้นเราพยายามเรียก `example_closure` ซ้ำด้วยตัวเลขจำนวนเต็ม เราจะพบกับข้อผิดพลาด

### การย้ายค่าที่ถูกจับออกจากโคลเชอร์

เมื่อโคลเชอร์ได้จับเรเฟอเรนซ์หรือรับสิทธิ์ความเป็นเจ้าของในค่าต่างๆ จากสภาพแวดล้อมที่มันถูกนิยาม (ซึ่งส่งผลต่อสิ่งที่จะถูกย้าย_เข้าไป_ในโคลเชอร์ หากมี) โค้ดในบอดี้ของโคลเชอร์จะเป็นตัวกำหนดต่อไปว่า จะเกิดอะไรขึ้นกับเรเฟอเรนซ์หรือค่านั้นเมื่อโคลเชอร์ถูกประเมินค่าในภายหลัง (ซึ่งส่งผลต่อสิ่งที่จะถูกย้าย_ออกจาก_โคลเชอร์ หากมี)

บอดี้ของโคลเชอร์สามารถกระทำการอย่างใดอย่างหนึ่งต่อไปนี้ได้: ย้ายค่าที่ถูกจับออกจากโคลเชอร์, เปลี่ยนแปลงค่าที่ถูกจับ, ไม่ย้ายและไม่เปลี่ยนแปลงค่า หรือไม่จับสิ่งใดจากสภาพแวดล้อมมาตั้งแต่แรก

วิธีที่โคลเชอร์จับและจัดการค่าจากสภาพแวดล้อมจะส่งผลต่อว่าโคลเชอร์นั้นอิมพลีเมนต์เทรต (trait) ใด และเทรตคือวิธีที่ฟังก์ชันและ struct ระบุได้ว่ามันรองรับการใช้งานโคลเชอร์ชนิดใดได้บ้าง โดยโคลเชอร์จะอิมพลีเมนต์เทรตกลุ่ม `Fn` หนึ่งตัว สองตัว หรือทั้งสามตัวนี้โดยอัตโนมัติ ในลักษณะเพิ่มพูนสะสม ขึ้นอยู่กับว่าบอดี้ของโคลเชอร์จัดการกับค่านั้นอย่างไร:

* `FnOnce` ใช้กับโคลเชอร์ที่เรียกได้ครั้งเดียว โคลเชอร์ทั้งหมดจะอิมพลีเมนต์เทรตนี้เป็นอย่างน้อย เพราะโคลเชอร์ทั้งหมดสามารถถูกเรียกได้ โคลเชอร์ที่ย้ายค่าที่ถูกจับออกจากบอดี้ของมันจะอิมพลีเมนต์เพียง `FnOnce` และไม่อิมพลีเมนต์เทรต `Fn` อื่นๆ เลย เพราะมันสามารถเรียกได้เพียงครั้งเดียวเท่านั้น
* `FnMut` ใช้กับโคลเชอร์ที่ไม่ย้ายค่าที่ถูกจับออกจากบอดี้ของมัน แต่อาจเปลี่ยนแปลงค่าที่ถูกจับได้ โคลเชอร์เหล่านี้สามารถเรียกได้มากกว่าหนึ่งครั้ง
* `Fn` ใช้กับโคลเชอร์ที่ไม่ย้ายค่าที่ถูกจับออกจากบอดี้ของมันและไม่เปลี่ยนแปลงค่าที่ถูกจับ รวมถึงโคลเชอร์ที่ไม่จับสิ่งใดจากสภาพแวดล้อมของมันเลย โคลเชอร์เหล่านี้สามารถเรียกได้มากกว่าหนึ่งครั้งโดยไม่เปลี่ยนแปลงสภาพแวดล้อม ซึ่งมีความสำคัญอย่างยิ่งในกรณีเช่นการเรียกใช้โคลเชอร์หลายครั้งพร้อมกัน

มาดูนิยามของเมธอด `unwrap_or_else` บน `Option<T>` ที่เราใช้ในลิสติ้ง 13-1:

```rust,ignore
impl<T> Option<T> {
    pub fn unwrap_or_else<F>(self, f: F) -> T
    where
        F: FnOnce() -> T
    {
        match self {
            Some(x) => x,
            None => f(),
        }
    }
}
```

ย้อนนึกว่า `T` คือชนิดข้อมูลแบบเจเนอริก (generic) ที่เป็นตัวแทนของชนิดค่าภายในวาเรียนต์ `Some` ของ `Option` ชนิด `T` นั้นยังเป็นชนิดที่ส่งกลับของฟังก์ชัน `unwrap_or_else` ด้วย: ตัวอย่างเช่น โค้ดที่เรียก `unwrap_or_else` บน `Option<String>` จะได้ `String` ออกมา

ต่อไป โปรดสังเกตว่าฟังก์ชัน `unwrap_or_else` มีพารามิเตอร์ชนิดข้อมูลแบบเจเนอริกเพิ่มเติมคือ `F` ซึ่งชนิด `F` คือชนิดของพารามิเตอร์ชื่อ `f` อันเป็นโคลเชอร์ที่เราส่งเข้าไปเมื่อเรียกใช้ `unwrap_or_else`

ข้อกำหนดเทรต (trait bound) ที่ระบุบนชนิดเจเนอริก `F` คือ `FnOnce() -> T` ซึ่งหมายความว่า `F` ต้องสามารถถูกเรียกได้หนึ่งครั้ง ไม่รับอาร์กิวเมนต์ และส่งกลับค่าชนิด `T` การใช้ `FnOnce` ในข้อกำหนดเทรตเป็นการระบุข้อจำกัดว่า `unwrap_or_else` จะไม่เรียก `f` มากกว่าหนึ่งครั้งแน่นอน ในบอดี้ของ `unwrap_or_else` เราจะเห็นว่าหาก `Option` เป็น `Some` ตัวฟังก์ชัน `f` จะไม่ถูกเรียกเลย แต่หาก `Option` เป็น `None` ตัวฟังก์ชัน `f` จะถูกเรียกทำงานหนึ่งครั้ง และเนื่องจากโคลเชอร์ทั้งหมดอิมพลีเมนต์ `FnOnce` อยู่แล้ว เมธอด `unwrap_or_else` จึงยอมรับโคลเชอร์ได้ทั้งสามชนิดและมีความยืดหยุ่นสูงสุดเท่าที่จะเป็นไปได้

> หมายเหตุ: หากสิ่งที่เราต้องการทำไม่จำเป็นต้องจับค่าจากสภาพแวดล้อม เราสามารถใช้ชื่อของฟังก์ชันธรรมดาแทนโคลเชอร์ในจุดที่ต้องการบางสิ่งที่อิมพลีเมนต์เทรต `Fn` ตัวใดตัวหนึ่งได้ ตัวอย่างเช่น บนค่า `Option<Vec<T>>` เราสามารถเรียก `unwrap_or_else(Vec::new)` เพื่อสร้างเวกเตอร์ใหม่ที่ว่างเปล่าหากค่าเป็น `None` โดยคอมไพเลอร์จะอิมพลีเมนต์เทรต `Fn` ตัวใดก็ตามที่เข้ากันได้กับนิยามของฟังก์ชันนั้นให้โดยอัตโนมัติ

ตอนนี้ มาดูเมธอด `sort_by_key` ของไลบรารีมาตรฐาน ซึ่งนิยามไว้บนสไลซ์ เพื่อดูว่ามันแตกต่างจาก `unwrap_or_else` อย่างไร และเพราะเหตุใด `sort_by_key` จึงใช้ `FnMut` แทน `FnOnce` สำหรับข้อกำหนดเทรต โดยโคลเชอร์จะได้รับอาร์กิวเมนต์หนึ่งตัวในรูปของเรเฟอเรนซ์ไปยังสมาชิกปัจจุบันในสไลซ์ที่กำลังพิจารณา และจะส่งกลับค่าชนิด `K` ที่สามารถนำไปจัดเรียงลำดับได้ ฟังก์ชันนี้มีประโยชน์มากเมื่อคุณต้องการเรียงลำดับสมาชิกในสไลซ์ตามคุณลักษณะเฉพาะอย่างของแต่ละสมาชิก ในลิสติ้ง 13-7 เรามีรายการของอินสแตนซ์ `Rectangle` และเราใช้ `sort_by_key` เพื่อจัดเรียงพวกมันตามคุณลักษณะ `width` จากน้อยไปมาก
