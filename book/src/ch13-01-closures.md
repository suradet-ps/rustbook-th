## โคลเชอร์

โคลเชอร์ (closure) ของ Rust คือฟังก์ชันนิรนามที่คุณสามารถบันทึกไว้ในตัวแปรหรือส่งเป็นอาร์กิวเมนต์ให้ฟังก์ชันอื่นได้ คุณสามารถสร้างโคลเชอร์ในที่หนึ่งแล้วเรียกโคลเชอร์นั้นที่อื่นเพื่อประเมินค่ามันในบริบทที่แตกต่างออกไปได้ ต่างจากฟังก์ชัน โคลเชอร์สามารถจับค่าจากสโคปที่มันถูกนิยามได้ เราจะสาธิตว่าฟีเจอร์ของโคลเชอร์เหล่านี้ช่วยให้ใช้โค้ดซ้ำและปรับแต่งพฤติกรรมได้อย่างไร

### การจับสภาพแวดล้อม

เราจะเริ่มต้นด้วยการพิจารณาว่าเราจะใช้โคลเชอร์จับค่าจากสภาพแวดล้อมที่มันถูกนิยามไว้เพื่อใช้ในภายหลังได้อย่างไร นี่คือสถานการณ์: เป็นครั้งคราว บริษัทเสื้อยืดของเราจะแจกเสื้อรุ่นพิเศษจำนวนจำกัดให้กับคนในรายชื่ออีเมลของเราเป็นการส่งเสริมการขาย คนในรายชื่ออีเมลสามารถเพิ่มสีโปรดของตนลงในโปรไฟล์ได้ตามความสมัครใจ หากคนที่ถูกเลือกให้ได้เสื้อฟรีได้ตั้งสีโปรดไว้ พวกเขาจะได้เสื้อสีนั้น หากคนนั้นไม่ได้ระบุสีโปรด พวกเขาจะได้สีที่บริษัทมีมากที่สุดในขณะนั้น

มีหลายวิธีในการอิมพลีเมนต์สิ่งนี้ สำหรับตัวอย่างนี้ เราจะใช้ enum ชื่อ `ShirtColor` ที่มีวาเรียนต์ `Red` และ `Blue` (จำกัดจำนวนสีที่มีเพื่อความเรียบง่าย) เราแทนสต็อกสินค้าของบริษัทด้วย struct `Inventory` ที่มีฟิลด์ชื่อ `shirts` ซึ่งบรรจุ `Vec<ShirtColor>` ที่เป็นตัวแทนของสีเสื้อที่อยู่ในสต็อกปัจจุบัน เมธอด `giveaway` ที่นิยามบน `Inventory` จะรับความต้องการสีเสื้อแบบไม่บังคับของผู้ชนะเสื้อฟรี และคืนค่าสีเสื้อที่คนนั้นจะได้รับ การตั้งค่านี้แสดงอยู่ในลิสติ้ง 13-1

เช่นเดิม โค้ดนี้สามารถอิมพลีเมนต์ได้หลายวิธี และในที่นี้ เพื่อโฟกัสที่โคลเชอร์ เราได้ยึดตามแนวคิดที่คุณเรียนรู้มาแล้ว ยกเว้นบอดี้ของเมธอด `giveaway` ที่ใช้โคลเชอร์ ในเมธอด `giveaway` เราได้รับความต้องการของผู้ใช้เป็นพารามิเตอร์ชนิด `Option<ShirtColor>` และเรียกเมธอด `unwrap_or_else` บน `user_preference` [เมธอด `unwrap_or_else` บน `Option<T>`][unwrap-or-else]<!-- ignore --> ถูกนิยามโดยไลบรารีมาตรฐาน มันรับอาร์กิวเมนต์หนึ่งตัว: โคลเชอร์ที่ไม่มีอาร์กิวเมนต์ใดๆ ซึ่งคืนค่า `T` (ชนิดเดียวกับที่จัดเก็บในวาเรียนต์ `Some` ของ `Option<T>` ในกรณีนี้คือ `ShirtColor`) หาก `Option<T>` เป็นวาเรียนต์ `Some` `unwrap_or_else` จะคืนค่าจากภายใน `Some` หาก `Option<T>` เป็นวาเรียนต์ `None` `unwrap_or_else` จะเรียกโคลเชอร์และคืนค่าที่โคลเชอร์คืนกลับมา

เราระบุเอ็กซ์เพรสชันโคลเชอร์ `|| self.most_stocked()` เป็นอาร์กิวเมนต์ให้กับ `unwrap_or_else` นี่คือโคลเชอร์ที่ตัวมันเองไม่รับพารามิเตอร์ใดๆ (หากโคลเชอร์มีพารามิเตอร์ พวกมันจะปรากฏระหว่างเครื่องหมายไปป์สองตัว) บอดี้ของโคลเชอร์เรียก `self.most_stocked()` เรากำลังนิยามโคลเชอร์ตรงนี้ และการอิมพลีเมนต์ของ `unwrap_or_else` จะประเมินค่าโคลเชอร์ในภายหลังหากต้องการผลลัพธ์นั้น

### การอนุมานและการระบุชนิดของโคลเชอร์

ยังมีความแตกต่างเพิ่มเติมระหว่างฟังก์ชันและโคลเชอร์ โดยปกติโคลเชอร์ไม่กำหนดให้คุณระบุชนิดของพารามิเตอร์หรือค่าที่คืนกลับเหมือนที่ฟังก์ชัน `fn` ทำ การระบุชนิดเป็นสิ่งจำเป็นบนฟังก์ชันเพราะชนิดเป็นส่วนหนึ่งของอินเทอร์เฟซที่ชัดเจนซึ่งเปิดเผยต่อผู้ใช้ของคุณ การนิยามอินเทอร์เฟซนี้อย่างตายตัวเป็นสิ่งสำคัญเพื่อให้มั่นใจว่าทุกคนเห็นพ้องตรงกันว่าฟังก์ชันใช้และคืนค่าชนิดใด ในทางกลับกัน โคลเชอร์ไม่ได้ถูกใช้ในอินเทอร์เฟซที่เปิดเผยเช่นนี้: พวกมันถูกเก็บไว้ในตัวแปร และถูกใช้โดยไม่ต้องตั้งชื่อและเปิดเผยให้ผู้ใช้ไลบรารีของเราเห็น

โดยทั่วไปโคลเชอร์นั้นสั้นและเกี่ยวข้องเฉพาะภายในบริบทที่แคบมากกว่าจะใช้ในสถานการณ์ใดๆ ก็ได้ ภายในบริบทที่จำกัดเหล่านี้ คอมไพเลอร์สามารถอนุมานชนิดของพารามิเตอร์และชนิดที่คืนกลับได้ คล้ายกับวิธีที่มันอนุมานชนิดของตัวแปรส่วนใหญ่ได้ (มีบางกรณีที่พบได้ยากซึ่งคอมไพเลอร์ต้องการการระบุชนิดของโคลเชอร์เช่นกัน)

เช่นเดียวกับตัวแปร เราสามารถเพิ่มการระบุชนิดได้หากเราต้องการความชัดเจนและความแจ่มแจ้งมากขึ้น โดยมีค่าใช้จ่ายคือความยาวมากกว่าที่จำเป็นอย่างเคร่งครัด การระบุชนิดให้โคลเชอร์จะมีหน้าตาเหมือนนิยามที่แสดงในลิสติ้ง 13-2 ในตัวอย่างนี้ เรานิยามโคลเชอร์และเก็บมันไว้ในตัวแปร แทนที่จะนิยามโคลเชอร์ตรงจุดที่เราส่งมันเป็นอาร์กิวเมนต์เหมือนที่เราทำในลิสติ้ง 13-1

เมื่อเพิ่มการระบุชนิดแล้ว วากยสัมพันธ์ของโคลเชอร์จะดูคล้ายกับวากยสัมพันธ์ของฟังก์ชันมากขึ้น ที่นี่ เรานิยามฟังก์ชันที่บวก 1 ให้กับพารามิเตอร์ของมัน และโคลเชอร์ที่มีพฤติกรรมเดียวกันเพื่อเปรียบเทียบ เราได้เพิ่มช่องว่างบางส่วนเพื่อจัดเรียงส่วนที่เกี่ยวข้องให้ตรงกัน สิ่งนี้แสดงให้เห็นว่าวากยสัมพันธ์ของโคลเชอร์คล้ายกับวากยสัมพันธ์ของฟังก์ชันอย่างไร ยกเว้นการใช้เครื่องหมายไปป์และปริมาณวากยสัมพันธ์ที่เป็นทางเลือก:

```rust,ignore
fn  add_one_v1   (x: u32) -> u32 { x + 1 }
let add_one_v2 = |x: u32| -> u32 { x + 1 };
let add_one_v3 = |x|             { x + 1 };
let add_one_v4 = |x|               x + 1  ;
```

บรรทัดแรกแสดงนิยามของฟังก์ชัน และบรรทัดที่สองแสดงนิยามของโคลเชอร์ที่ระบุชนิดครบถ้วน ในบรรทัดที่สาม เราลบการระบุชนิดออกจากนิยามของโคลเชอร์ ในบรรทัดที่สี่ เราลบวงเล็บปีกกา ซึ่งเป็นทางเลือกได้เพราะบอดี้ของโคลเชอร์มีเพียงเอ็กซ์เพรสชันเดียว ทั้งหมดนี้เป็นนิยามที่ถูกต้องซึ่งจะให้พฤติกรรมเดียวกันเมื่อถูกเรียก บรรทัด `add_one_v3` และ `add_one_v4` กำหนดให้โคลเชอร์ต้องถูกประเมินค่าจึงจะคอมไพล์ได้ เพราะชนิดจะถูกอนุมานจากการใช้งานของมัน ซึ่งคล้ายกับ `let v = Vec::new();` ที่ต้องการการระบุชนิดหรือค่าชนิดใดชนิดหนึ่งที่ถูกใส่เข้าไปใน `Vec` เพื่อให้ Rust สามารถอนุมานชนิดได้

สำหรับนิยามของโคลเชอร์ คอมไพเลอร์จะอนุมานชนิดที่เป็นรูปธรรมหนึ่งชนิดสำหรับพารามิเตอร์แต่ละตัวและสำหรับค่าที่คืนกลับของมัน ตัวอย่างเช่น ลิสติ้ง 13-3 แสดงนิยามของโคลเชอร์สั้นๆ ที่เพียงคืนค่าที่มันได้รับเป็นพารามิเตอร์ โคลเชอร์นี้ไม่มีประโยชน์มากนักนอกจากเพื่อจุดประสงค์ของตัวอย่างนี้ โปรดสังเกตว่าเราไม่ได้เพิ่มการระบุชนิดใดๆ ลงในนิยาม เพราะไม่มีการระบุชนิด เราจึงเรียกโคลเชอร์ด้วยชนิดใดก็ได้ ซึ่งเราได้ทำที่นี่กับ `String` ในครั้งแรก หากหลังจากนั้นเราพยายามเรียก `example_closure` ด้วยจำนวนเต็ม เราจะได้ข้อผิดพลาด

### การจับเรเฟอเรนซ์หรือการย้ายความเป็นเจ้าของ

### การย้ายค่าที่ถูกจับออกจากโคลเชอร์

เมื่อโคลเชอร์จับเรเฟอเรนซ์หรือจับความเป็นเจ้าของค่าจากสภาพแวดล้อมที่โคลเชอร์ถูกนิยาม (จึงส่งผลต่อสิ่งที่จะถูกย้าย_เข้าไป_ในโคลเชอร์ หากมี) โค้ดในบอดี้ของโคลเชอร์จะกำหนดว่าเกิดอะไรขึ้นกับเรเฟอเรนซ์หรือค่าเหล่านั้นเมื่อโคลเชอร์ถูกประเมินค่าในภายหลัง (จึงส่งผลต่อสิ่งที่จะถูกย้าย_ออกจาก_โคลเชอร์ หากมี)

บอดี้ของโคลเชอร์สามารถทำสิ่งใดสิ่งหนึ่งต่อไปนี้ได้: ย้ายค่าที่ถูกจับออกจากโคลเชอร์ เปลี่ยนแปลงค่าที่ถูกจับ ไม่ย้ายและไม่เปลี่ยนแปลงค่า หรือไม่จับอะไรจากสภาพแวดล้อมตั้งแต่แรก

วิธีที่โคลเชอร์จับและจัดการค่าจากสภาพแวดล้อมส่งผลต่อว่าโคลเชอร์อิมพลีเมนต์เทรต (trait) ใด และเทรตคือวิธีที่ฟังก์ชันและ struct ระบุได้ว่ามันใช้โคลเชอร์ชนิดใดได้บ้าง โคลเชอร์จะอิมพลีเมนต์เทรต `Fn` หนึ่งตัว สองตัว หรือทั้งสามตัวนี้โดยอัตโนมัติ ในลักษณะเพิ่มพูน ขึ้นอยู่กับว่าบอดี้ของโคลเชอร์จัดการค่าอย่างไร:

* `FnOnce` ใช้กับโคลเชอร์ที่เรียกได้ครั้งเดียว โคลเชอร์ทั้งหมดอิมพลีเมนต์เทรตนี้เป็นอย่างน้อย เพราะโคลเชอร์ทั้งหมดสามารถถูกเรียกได้ โคลเชอร์ที่ย้ายค่าที่ถูกจับออกจากบอดี้ของมันจะอิมพลีเมนต์เพียง `FnOnce` และไม่อิมพลีเมนต์เทรต `Fn` อื่นๆ เลย เพราะมันเรียกได้เพียงครั้งเดียว
* `FnMut` ใช้กับโคลเชอร์ที่ไม่ย้ายค่าที่ถูกจับออกจากบอดี้ของมันแต่อาจเปลี่ยนแปลงค่าที่ถูกจับ โคลเชอร์เหล่านี้เรียกได้มากกว่าหนึ่งครั้ง
* `Fn` ใช้กับโคลเชอร์ที่ไม่ย้ายค่าที่ถูกจับออกจากบอดี้ของมันและไม่เปลี่ยนแปลงค่าที่ถูกจับ รวมถึงโคลเชอร์ที่ไม่จับอะไรจากสภาพแวดล้อมของมัน โคลเชอร์เหล่านี้เรียกได้มากกว่าหนึ่งครั้งโดยไม่เปลี่ยนแปลงสภาพแวดล้อมของมัน ซึ่งสำคัญในกรณีเช่นการเรียกโคลเชอร์หลายครั้งพร้อมกัน

มาดูนิยามของเมธอด `unwrap_or_else` บน `Option<T>` ที่เราใช้ในลิสติ้ง 13-1:

```rust,ignore
impl<T> Option<T> {
    pub fn unwrap_or_else<F>(self, f: F) -> T
    where
        F: FnOnce() -> T
    {
        match self {
            Some(x) => x,
            None => f(),
        }
    }
}
```

ย้อนนึกว่า `T` คือชนิดเจเนอริก (generic) ที่เป็นตัวแทนของชนิดค่าภายในวาเรียนต์ `Some` ของ `Option` ชนิด `T` นั้นยังเป็นชนิดที่คืนกลับของฟังก์ชัน `unwrap_or_else` ด้วย: ตัวอย่างเช่น โค้ดที่เรียก `unwrap_or_else` บน `Option<String>` จะได้ `String`

ต่อไป โปรดสังเกตว่าฟังก์ชัน `unwrap_or_else` มีพารามิเตอร์ชนิดข้อมูลแบบเจเนอริกเพิ่มเติมคือ `F` ชนิด `F` คือชนิดของพารามิเตอร์ชื่อ `f` ซึ่งเป็นโคลเชอร์ที่เราจัดเตรียมไว้เมื่อเรียก `unwrap_or_else`

บาวด์ของเทรต (trait bound) ที่ระบุบนชนิดเจเนอริก `F` คือ `FnOnce() -> T` ซึ่งหมายความว่า `F` ต้องสามารถถูกเรียกได้ครั้งเดียว ไม่รับอาร์กิวเมนต์ และคืนค่า `T` การใช้ `FnOnce` ในบาวด์ของเทรตแสดงข้อจำกัดว่า `unwrap_or_else` จะไม่เรียก `f` มากกว่าหนึ่งครั้ง ในบอดี้ของ `unwrap_or_else` เราจะเห็นว่าหาก `Option` เป็น `Some` `f` จะไม่ถูกเรียก หาก `Option` เป็น `None` `f` จะถูกเรียกหนึ่งครั้ง เพราะโคลเชอร์ทั้งหมดอิมพลีเมนต์ `FnOnce` `unwrap_or_else` จึงยอมรับโคลเชอร์ทั้งสามชนิดและยืดหยุ่นเท่าที่จะเป็นไปได้

> หมายเหตุ: หากสิ่งที่เราต้องการทำไม่จำเป็นต้องจับค่าจากสภาพแวดล้อม เราสามารถใช้ชื่อของฟังก์ชันแทนโคลเชอร์ในจุดที่ต้องการบางสิ่งที่อิมพลีเมนต์เทรต `Fn` ตัวใดตัวหนึ่งได้ ตัวอย่างเช่น บนค่า `Option<Vec<T>>` เราสามารถเรียก `unwrap_or_else(Vec::new)` เพื่อได้เวกเตอร์ใหม่ที่ว่างเปล่าหากค่าเป็น `None` คอมไพเลอร์จะอิมพลีเมนต์เทรต `Fn` ตัวใดก็ตามที่ใช้ได้กับนิยามของฟังก์ชันโดยอัตโนมัติ

นี่เป็นวิธีที่ประดิษฐ์ขึ้นอย่างซับซ้อน (ซึ่งใช้ไม่ได้ผล) เพื่อพยายามนับจำนวนครั้งที่ `sort_by_key` เรียกโคลเชอร์เมื่อจัดเรียง `list` โค้ดนี้พยายามนับโดยการพุช `value`—ซึ่งเป็น `String` จากสภาพแวดล้อมของโคลเชอร์—เข้าไปในเวกเตอร์ `sort_operations` โคลเชอร์จับ `value` แล้วย้าย `value` ออกไปจากโคลเชอร์โดยโอนความเป็นเจ้าของ `value` ให้กับเวกเตอร์ `sort_operations` โคลเชอร์นี้เรียกได้ครั้งเดียว การพยายามเรียกมันครั้งที่สองจะใช้ไม่ได้ผล เพราะ `value` จะไม่อยู่ในสภาพแวดล้อมให้พุชเข้าไปใน `sort_operations` อีกต่อไป! ดังนั้น โคลเชอร์นี้จึงอิมพลีเมนต์เพียง `FnOnce` เมื่อเราพยายามคอมไพล์โค้ดนี้ เราจะได้ข้อผิดพลาดนี้ว่า `value` ไม่สามารถถูกย้ายออกไปจากโคลเชอร์ได้เพราะโคลเชอร์ต้องอิมพลีเมนต์ `FnMut`:
