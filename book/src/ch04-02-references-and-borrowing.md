## เรเฟอเรนซ์และการยืม

ปัญหาของโค้ดทูเพิลในลิสติ้ง 4-5 คือเราจำเป็นต้องคืนค่า `String` กลับมายังฟังก์ชันผู้เรียก เพื่อให้เรายังสามารถนำ `String` นั้นไปใช้งานต่อได้หลังจากการเรียกใช้ `calculate_length` เพราะความเป็นเจ้าของของ `String` ได้ถูกย้ายเข้าไปใน `calculate_length` ไปแล้ว แต่เราสามารถส่ง _การอ้างอิง_ หรือ _เรเฟอเรนซ์_ (reference) ไปยังค่าของ `String` แทนได้ เรเฟอเรนซ์ทำงานคล้ายกับพอยน์เตอร์ (pointer) ตรงที่เป็นการเก็บที่อยู่ (address) ในหน่วยความจำที่เราสามารถตามไปเข้าถึงข้อมูลจริงที่ถูกจัดเก็บไว้ ณ ตำแหน่งนั้นได้ โดยที่ข้อมูลนั้นยังคงเป็นของตัวแปรอื่นอยู่ แต่สิ่งที่แตกต่างจากพอยน์เตอร์ทั่วไปคือ เรเฟอเรนซ์ใน Rust ได้รับการรับประกันว่าจะชี้ไปยังค่าที่ถูกต้องและมีตัวตนอยู่จริงของชนิดข้อมูลนั้นๆ เสมอตลอดอายุขัยของเรเฟอเรนซ์

### เรเฟอเรนซ์แบบเปลี่ยนแปลงได้

เราสามารถปรับแก้โค้ดจากลิสติ้ง 4-6 เพื่อให้สามารถแก้ไขค่าที่ถูกยืมมาได้ ด้วยการปรับเปลี่ยนเพียงเล็กน้อยโดยหันมาใช้ _เรเฟอเรนซ์แบบเปลี่ยนแปลงได้_ (mutable reference) แทน ดังนี้:

<Listing file-name="src/main.rs">

```rust
{{#rustdoc_include ../listings/ch04-understanding-ownership/no-listing-09-fixes-listing-04-06/src/main.rs}}
```

</Listing>

ประการแรก เราเปลี่ยนการประกาศ `s` ให้เป็นตัวแปรแบบ `mut` จากนั้นจึงสร้างเรเฟอเรนซ์แบบเปลี่ยนแปลงได้ด้วยคำสั่ง `&mut s` ในจุดที่เราเรียกฟังก์ชัน `change` และปรับลายเซ็นของฟังก์ชันให้รับเรเฟอเรนซ์แบบเปลี่ยนแปลงได้ด้วย `some_string: &mut String` ซึ่งทำให้เห็นได้อย่างชัดเจนว่าฟังก์ชัน `change` จะเข้าไปแก้ไขค่าที่มันขอยืมมา

อย่างไรก็ดี เรเฟอเรนซ์แบบเปลี่ยนแปลงได้มีข้อจำกัดที่สำคัญอย่างยิ่งหนึ่งข้อคือ: **หากคุณมีเรเฟอเรนซ์แบบเปลี่ยนแปลงได้ไปยังค่าใดค่าหนึ่งอยู่แล้ว คุณจะไม่สามารถมีเรเฟอเรนซ์อื่นใดไปยังค่านั้นได้อีกเลย** โค้ดที่พยายามสร้างเรเฟอเรนซ์แบบเปลี่ยนแปลงได้สองตัวพร้อมกันไปยัง `s` ต่อไปนี้จะคอมไพล์ไม่ผ่าน:

ข้อจำกัดที่ป้องกันไม่ให้มีเรเฟอเรนซ์แบบเปลี่ยนแปลงได้หลายตัวไปยังข้อมูลเดียวกันในเวลาเดียวกันนี้ ช่วยให้การแก้ไขข้อมูลเป็นไปอย่างรัดกุมและปลอดภัย ซึ่งอาจเป็นเรื่องที่ผู้เริ่มเขียน Rust ต้องปรับตัว เนื่องจากภาษาโปรแกรมส่วนใหญ่ยอมให้คุณแก้ไขข้อมูลได้ทุกที่ทุกเวลา แต่ข้อดีอย่างมหาศาลของข้อจำกัดนี้คือ Rust สามารถป้องกันปัญหา **ดาต้าเรซ (data race)** ได้ตั้งแต่ตอนคอมไพล์ ปัญหาดาต้าเรซคล้ายคลึงกับภาวะแย่งชิงทรัพยากร (race condition) และจะเกิดขึ้นเมื่อมีพฤติกรรมทั้ง 3 ข้อต่อไปนี้เกิดขึ้นพร้อมกัน:

- มีพอยน์เตอร์ตั้งแต่สองตัวขึ้นไปเข้าถึงข้อมูลชุดเดียวกันในเวลาเดียวกัน
- มีพอยน์เตอร์อย่างน้อยหนึ่งตัวที่กำลังถูกใช้เพื่อเขียนข้อมูล
- ไม่ได้ใช้กลไกการซิงโครไนซ์ใดๆ ในการควบคุมการเข้าถึงข้อมูลนั้น

ดาต้าเรซจะทำให้เกิดพฤติกรรมที่ไม่สามารถคาดเดาได้ (undefined behavior) และมักจะเป็นปัญหาที่ยากมากในการตรวจหาและแก้ไขในระหว่างรันไทม์ Rust ขจัดปัญหานี้ให้หมดสิ้นโดยการปฏิเสธที่จะคอมไพล์โค้ดที่อาจก่อให้เกิดดาต้าเรซ!


ขอบเขตของเรเฟอเรนซ์แบบเปลี่ยนแปลงไม่ได้ `r1` และ `r2` สิ้นสุดลงทันทีหลังบรรทัด `println!` ที่พวกมันถูกเรียกใช้งานเป็นครั้งสุดท้าย ซึ่งเป็นตำแหน่งก่อนที่เรเฟอเรนซ์แบบเปลี่ยนแปลงได้ `r3` จะถูกสร้างขึ้นมา ขอบเขตการทำงานของทั้งสองกลุ่มจึงไม่ได้ทับซ้อนกัน โค้ดนี้จึงได้รับอนุญาตให้ทำงานได้ เนื่องจากคอมไพเลอร์สามารถตรวจสอบได้ว่าเรเฟอเรนซ์เดิมไม่ได้ถูกนำมาใช้งานต่ออีกแล้ว ณ จุดดังกล่าวก่อนจะสิ้นสุดบล็อก

แม้ว่ากฎเรื่องการยืมอาจสร้างความหงุดหงิดให้บ้างในบางครั้ง แต่ขอให้ตระหนักไว้เสมอว่า คอมไพเลอร์ของ Rust กำลังช่วยชี้จุดที่อาจเกิดบั๊กขึ้นได้ล่วงหน้าตั้งแต่เนิ่นๆ (ตั้งแต่ตอนคอมไพล์แทนที่จะไปเกิดข้อผิดพลาดตอนรันจริง) พร้อมระบุตำแหน่งของปัญหาให้อย่างชัดเจน ทำให้คุณไม่ต้องเสียเวลาตามหาว่าทำไมข้อมูลของคุณจึงไม่เป็นไปตามที่คาดหวังในภายหลัง

### เรเฟอเรนซ์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้ว

ในภาษาโปรแกรมที่มีพอยน์เตอร์ เป็นเรื่องง่ายมากที่จะเผลอสร้าง _พอยน์เตอร์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้ว_ (dangling pointer) ซึ่งเป็นพอยน์เตอร์ที่อ้างอิงไปยังตำแหน่งในหน่วยความจำที่อาจถูกคืนหรือถูกจัดสรรให้กับข้อมูลอื่นไปแล้ว โดยเกิดจากการสั่งคืนหน่วยความจำในขณะที่ยังมีพอยน์เตอร์ชี้ค้างไว้อยู่ ในทางตรงกันข้าม สำหรับภาษา Rust คอมไพเลอร์จะรับประกันอย่างเด็ดขาดว่าจะไม่มีเรเฟอเรนซ์ใดกลายเป็นเรเฟอเรนซ์ที่ชี้ไปยังหน่วยความจำที่ถูกคืนแล้ว: หากคุณมีเรเฟอเรนซ์ไปยังข้อมูลชุดหนึ่ง คอมไพเลอร์จะตรวจสอบให้มั่นใจเสมอว่าข้อมูลจริงนั้นจะไม่หลุดออกจากขอบเขตก่อนที่เรเฟอเรนซ์ที่ชี้ไปยังข้อมูลนั้นจะหมดอายุการใช้งาน

### กฎของเรเฟอเรนซ์

เรามาสรุปกฎสำคัญเกี่ยวกับเรเฟอเรนซ์กันอีกครั้ง:

- ณ เวลาใดเวลาหนึ่ง คุณสามารถมีเรเฟอเรนซ์แบบเปลี่ยนแปลงได้เพียงหนึ่งตัว _หรือ_ มีเรเฟอเรนซ์แบบเปลี่ยนแปลงไม่ได้กี่ตัวก็ได้
- เรเฟอเรนซ์จะต้องชี้ไปยังข้อมูลที่ถูกต้องและมีตัวตนอยู่เสมอ

ในหัวข้อถัดไป เราจะมาดูเรเฟอเรนซ์อีกรูปแบบหนึ่ง นั่นก็คือ สไลซ์ (slice)
