## ใช้ `Box<T>` ชี้ไปยังข้อมูลบนฮีป

สมาร์ตพอยน์เตอร์ (smart pointer) ที่เข้าใจง่ายและตรงไปตรงมาที่สุดก็คือบ็อกซ์ (box) ซึ่งเขียนแทนด้วยชนิดข้อมูล `Box<T>` โดย _บ็อกซ์_ ช่วยให้คุณสามารถเก็บข้อมูลไว้บนฮีป (heap) แทนที่จะเป็นบนสแตก (stack) สิ่งที่ยังคงอยู่บนสแตกจะมีเพียงแค่พอยน์เตอร์ที่ชี้ไปยังข้อมูลบนฮีปเท่านั้น หากต้องการทบทวนความแตกต่างระหว่างสแตกและฮีป สามารถย้อนกลับไปอ่านได้ในบทที่ 4

บ็อกซ์แทบไม่มีต้นทุนประสิทธิภาพส่วนเกิน (overhead) นอกเหนือจากการนำข้อมูลไปจัดเก็บไว้บนฮีปแทนที่จะเป็นบนสแตก แต่ในขณะเดียวกัน บ็อกซ์ก็ไม่ได้มีความสามารถพิเศษเพิ่มเติมมากมายนักเช่นกัน โดยคุณมักจะได้ใช้งานบ็อกซ์บ่อยที่สุดในสถานการณ์ดังต่อไปนี้:

- เมื่อคุณมีชนิดข้อมูลที่ไม่สามารถทราบขนาดได้ในขณะคอมไพล์ และคุณต้องการนำค่าของชนิดข้อมูลนั้นไปใช้ในบริบทที่ต้องการขนาดของหน่วยความจำที่แน่นอน
- เมื่อคุณมีข้อมูลขนาดใหญ่มาก และต้องการโอนย้ายสิทธิ์ความเป็นเจ้าของ แต่ต้องการรับประกันว่าข้อมูลจะไม่ถูกคัดลอกซ้ำซ้อน
- เมื่อคุณต้องการครอบครองค่าหนึ่ง และสนใจเพียงแค่ว่าค่านั้นต้องเป็นชนิดข้อมูลที่อิมพลีเมนต์เทรต (trait) ตัวใดตัวหนึ่ง มากกว่าที่จะเจาะจงชนิดข้อมูลที่แท้จริง

เราจะแสดงให้เห็นสถานการณ์แรกใน [“การเปิดใช้ชนิดข้อมูลแบบเรียกซ้ำด้วยบ็อกซ์”](#การเปิดใชชนิดขอมูลแบบเรียกซำดวยบอกซ)<!-- ignore --> ส่วนกรณีที่สอง การโอนย้ายสิทธิ์ความเป็นเจ้าของข้อมูลขนาดใหญ่อาจใช้เวลานานหากข้อมูลต้องถูกคัดลอกไปมาบนสแตก เพื่อปรับปรุงประสิทธิภาพในกรณีนี้ เราสามารถนำข้อมูลขนาดใหญ่นั้นไปเก็บไว้บนฮีปภายในบ็อกซ์ ซึ่งจะทำให้มีเพียงข้อมูลพอยน์เตอร์ขนาดเล็กเท่านั้นที่ถูกคัดลอกไปมาบนสแตก ในขณะที่ตัวข้อมูลจริงยังคงอยู่ที่เดิมบนฮีป สำหรับกรณีที่สามนั้นเรียกว่า _เทรตออบเจกต์ (trait object)_ ซึ่งหัวข้อ [“การใช้เทรตออบเจกต์เพื่อนามธรรมพฤติกรรมร่วม”][trait-objects]<!-- ignore --> ในบทที่ 18 ได้อุทิศเนื้อหาให้กับเรื่องนี้โดยเฉพาะ ดังนั้นสิ่งที่คุณได้เรียนรู้ที่นี่ จะได้นำไปต่อยอดใช้อีกครั้งในบทนั้น!

### การเปิดใช้ชนิดข้อมูลแบบเรียกซ้ำด้วยบ็อกซ์

ค่าของ_ชนิดข้อมูลแบบเรียกซ้ำ (recursive type)_ สามารถมีค่าอื่นที่เป็นชนิดเดียวกันเป็นส่วนประกอบภายในตัวมันเองได้ แต่ชนิดข้อมูลแบบเรียกซ้ำจะก่อให้เกิดปัญหา เพราะ Rust จำเป็นต้องรู้ตั้งแต่ตอนคอมไพล์ว่าชนิดข้อมูลนั้น ๆ ต้องใช้พื้นที่หน่วยความจำเท่าใด ทว่าการซ้อนทับกันของค่าในชนิดข้อมูลแบบเรียกซ้ำอาจเกิดขึ้นต่อไปเรื่อย ๆ ได้อย่างไม่สิ้นสุดในทางทฤษฎี ทำให้ Rust ไม่สามารถรู้ได้ว่าค่านั้นต้องใช้พื้นที่เท่าใด แต่เนื่องจากบ็อกซ์มีขนาดที่แน่นอนและทราบได้ล่วงหน้าเสมอ เราจึงสามารถเปิดใช้ชนิดข้อมูลแบบเรียกซ้ำได้โดยการแทรกบ็อกซ์เข้าไปในนิยามของชนิดข้อมูลนั้น

ในฐานะตัวอย่างของชนิดข้อมูลแบบเรียกซ้ำ เรามาลองศึกษา cons list กัน นี่คือโครงสร้างข้อมูลที่พบได้ทั่วไปในภาษาโปรแกรมเชิงฟังก์ชัน (functional programming) โดยชนิดข้อมูล cons list ที่เราจะนิยามนั้นมีโครงสร้างที่ตรงไปตรงมามาก เว้นแต่เพียงส่วนที่มีการเรียกซ้ำเท่านั้น ดังนั้นแนวคิดจากตัวอย่างนี้จะมีประโยชน์อย่างยิ่งเมื่อใดก็ตามที่คุณต้องเผชิญกับสถานการณ์ที่ซับซ้อนยิ่งขึ้นซึ่งเกี่ยวข้องกับชนิดข้อมูลแบบเรียกซ้ำ

#### การทำความเข้าใจ Cons List

_cons list_ เป็นโครงสร้างข้อมูลที่มาจากภาษาโปรแกรม Lisp และภาษาในตระกูลของมัน ซึ่งประกอบขึ้นจากคู่ข้อมูล (pairs) ซ้อนกัน และเทียบได้กับลิงก์ลิสต์ (linked list) ในเวอร์ชันของ Lisp โดยชื่อของมันมาจากฟังก์ชัน `cons` (ย่อมาจาก _construct function_) ใน Lisp ที่ใช้สร้างคู่ข้อมูลใหม่ขึ้นมาจากอาร์กิวเมนต์สองตัว การเรียกฟังก์ชัน `cons` ซ้อนกันโดยส่งค่าและคู่อื่นเข้าไป ทำให้เราสามารถสร้าง cons list ที่ประกอบด้วยคู่ข้อมูลแบบเรียกซ้ำได้

ตัวอย่างเช่น ซูโดโค้ดด้านล่างนี้แสดง cons list ที่เก็บลิสต์ `1, 2, 3` โดยแต่ละคู่จะอยู่ในวงเล็บ:

```text
(1, (2, (3, Nil)))
```

แต่ละไอเท็มใน cons list จะประกอบด้วยสององค์ประกอบ ได้แก่ ค่าของไอเท็มปัจจุบัน และไอเท็มตัวถัดไป ส่วนไอเท็มสุดท้ายในลิสต์จะมีเพียงค่าที่เรียกว่า `Nil` โดยไม่มีไอเท็มตัวถัดไป cons list ถูกสร้างขึ้นจากการเรียกฟังก์ชัน `cons` ซ้ำ ๆ โดยชื่อมาตรฐานที่ใช้แสดงกรณีฐาน (base case) เพื่อหยุดการเรียกซ้ำคือ `Nil` โปรดสังเกตว่าสิ่งนี้ไม่เหมือนกับแนวคิดเรื่อง “null” หรือ “nil” ที่เราพูดถึงในบทที่ 6 ซึ่งหมายถึงค่าที่ไม่ถูกต้องหรือการไม่มีค่า

cons list ไม่ใช่โครงสร้างข้อมูลที่นิยมใช้กันทั่วไปใน Rust เพราะเวลาส่วนใหญ่ที่คุณต้องการเก็บรายการของสิ่งต่าง ๆ ใน Rust ชนิดข้อมูล `Vec<T>` จะเป็นตัวเลือกที่ดีและเหมาะสมกว่า โครงสร้างข้อมูลแบบเรียกซ้ำชนิดอื่น ๆ ที่ซับซ้อนกว่านี้_มี_ประโยชน์ในสถานการณ์ต่าง ๆ แต่การเริ่มต้นด้วย cons list ในบทนี้จะช่วยให้เราเห็นภาพได้ชัดเจนว่าบ็อกซ์ช่วยให้เรานิยามชนิดข้อมูลแบบเรียกซ้ำได้อย่างไรโดยไม่ทำให้เนื้อหาซับซ้อนเกินไป

คราวนี้ลองเปรียบเทียบกับสิ่งที่เกิดขึ้นเมื่อ Rust พยายามคำนวณพื้นที่สำหรับชนิดข้อมูลแบบเรียกซ้ำอย่าง enum `List` ในลิสติ้ง 15-2 ดูบ้าง คอมไพเลอร์จะเริ่มจากการดูวาเรียนต์ `Cons` ซึ่งเก็บค่าชนิด `i32` และค่าชนิด `List` ดังนั้น `Cons` จึงต้องใช้พื้นที่เท่ากับขนาดของ `i32` บวกกับขนาดของ `List` และในการคำนวณว่าชนิด `List` ต้องใช้หน่วยความจำเท่าใด คอมไพเลอร์ก็ต้องกลับไปดูแต่ละวาเรียนต์อีกครั้ง โดยเริ่มจาก `Cons` ซึ่ง `Cons` ก็เก็บ `i32` และ `List` ต่อไปอีกเรื่อย ๆ กระบวนการนี้จึงดำเนินไปอย่างไม่สิ้นสุด ดังที่แสดงในรูปที่ 15-1

#### การได้มาซึ่งชนิดข้อมูลแบบเรียกซ้ำที่มีขนาดที่รู้ได้

เนื่องจาก Rust ไม่สามารถคำนวณได้ว่าต้องจัดสรรพื้นที่เท่าใดสำหรับชนิดข้อมูลที่นิยามแบบเรียกซ้ำ คอมไพเลอร์จึงแจ้งข้อผิดพลาดพร้อมคำแนะนำที่เป็นประโยชน์นี้:

2 |     Cons(i32, Box<List>),
  |               ++++    +

ในคำแนะนำนี้ คำว่า _การชี้ทางอ้อม (indirection)_ หมายความว่าแทนที่จะเก็บค่าไว้โดยตรง เราควรปรับโครงสร้างข้อมูลให้เก็บค่าทางอ้อมด้วยการเก็บพอยน์เตอร์ที่ชี้ไปยังค่านั้นแทน

เนื่องจาก `Box<T>` มีสถานะเป็นพอยน์เตอร์ตัวหนึ่ง Rust จึงรู้ขนาดที่แน่นอนของ `Box<T>` เสมอ เพราะขนาดของพอยน์เตอร์จะไม่เปลี่ยนแปลงไปตามปริมาณข้อมูลที่มันชี้ไป นั่นหมายความว่าเราสามารถใส่ `Box<T>` ไว้ข้างในวาเรียนต์ `Cons` แทนที่จะเก็บค่า `List` อีกค่าหนึ่งโดยตรงได้ โดย `Box<T>` จะชี้ไปยังค่า `List` ถัดไปซึ่งถูกนำไปวางไว้บนฮีปแทนที่จะอยู่ภายในวาเรียนต์ `Cons` ในเชิงมโนทัศน์แล้ว เราก็ยังคงมีลิสต์ที่เกิดจากการซ้อนกันของลิสต์อื่น ๆ อยู่เช่นเดิม เพียงแต่การอิมพลีเมนต์ในลักษณะนี้จะเหมือนกับการนำไอเท็มมาวางเคียงข้างกัน มากกว่าที่จะนำมาบรรจุซ้อนไว้ข้างในกัน
