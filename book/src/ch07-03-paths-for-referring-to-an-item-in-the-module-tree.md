## พาธสำหรับอ้างถึงรายการในแผนผังมอดูล

ในการบอก Rust ว่าจะหารายการหนึ่งๆ ในแผนผังมอดูล (module tree) ได้ที่ใด เราใช้พาธ (path) ในลักษณะเดียวกับที่เราใช้พาธเมื่อนำทางในระบบไฟล์ ในการเรียกฟังก์ชัน เราจำเป็นต้องรู้พาธของมัน

พาธมีได้สองรูปแบบ:

- _พาธแบบสัมบูรณ์_ (absolute path) คือพาธเต็มที่เริ่มจากรากของเครต (crate root) สำหรับโค้ดจากเครต (crate) ภายนอก พาธแบบสัมบูรณ์จะเริ่มต้นด้วยชื่อเครต และสำหรับโค้ดจากเครตปัจจุบัน มันจะเริ่มต้นด้วยคำ `crate` ตามตัวอักษร
- _พาธแบบสัมพัทธ์_ (relative path) เริ่มจากมอดูลปัจจุบันและใช้ `self`, `super` หรือชื่อเรียก (identifier) ในมอดูลปัจจุบัน

ทั้งพาธแบบสัมบูรณ์และแบบสัมพัทธ์จะตามด้วยชื่อเรียกหนึ่งตัวหรือมากกว่าที่คั่นด้วยโคลอนคู่ (`::`)

ย้อนกลับไปที่ลิสติ้ง 7-1 สมมติว่าเราต้องการเรียกฟังก์ชัน `add_to_waitlist` นี่ก็เหมือนกับการถามว่า: พาธของฟังก์ชัน `add_to_waitlist` คืออะไร? ลิสติ้ง 7-3 แสดงลิสติ้ง 7-1 ที่ตัดมอดูลและฟังก์ชันบางส่วนออกไป

เราจะแสดงสองวิธีในการเรียกฟังก์ชัน `add_to_waitlist` จากฟังก์ชันใหม่ชื่อ `eat_at_restaurant` ที่นิยามไว้ในรากของเครต พาธเหล่านี้ถูกต้อง แต่ยังมีปัญหาอีกอย่างที่ทำให้ตัวอย่างนี้คอมไพล์ไม่ผ่านตามที่เป็นอยู่ เราจะอธิบายเหตุผลอีกสักครู่

ฟังก์ชัน `eat_at_restaurant` เป็นส่วนหนึ่งของ API สาธารณะ (public) ของเครตไลบรารีของเรา เราจึงทำเครื่องหมายมันด้วยคำสงวน `pub` ในหัวข้อ[“การเปิดเผยพาธด้วยคำสงวน `pub`”][pub]<!-- ignore --> เราจะลงรายละเอียดเพิ่มเติมเกี่ยวกับ `pub`

ครั้งแรกที่เราเรียกฟังก์ชัน `add_to_waitlist` ใน `eat_at_restaurant` เราใช้พาธแบบสัมบูรณ์ ฟังก์ชัน `add_to_waitlist` ถูกนิยามในเครตเดียวกับ `eat_at_restaurant` ซึ่งหมายความว่าเราใช้คำสงวน `crate` เป็นจุดเริ่มต้นของพาธแบบสัมบูรณ์ได้ จากนั้นเราระบุมอดูลที่ต่อเนื่องกันไปเรื่อยๆ จนกระทั่งไปถึง `add_to_waitlist` คุณสามารถจินตนาการถึงระบบไฟล์ที่มีโครงสร้างแบบเดียวกันได้: เราจะระบุพาธ `/front_of_house/hosting/add_to_waitlist` เพื่อรันโปรแกรม `add_to_waitlist` การใช้ชื่อ `crate` เพื่อเริ่มจากรากของเครตก็เหมือนกับการใช้ `/` เพื่อเริ่มจากรากของระบบไฟล์ในเชลล์ของคุณ

ครั้งที่สองที่เราเรียก `add_to_waitlist` ใน `eat_at_restaurant` เราใช้พาธแบบสัมพัทธ์ พาธเริ่มต้นด้วย `front_of_house` ซึ่งเป็นชื่อของมอดูลที่นิยามไว้ในระดับเดียวกับ `eat_at_restaurant` ในแผนผังมอดูล ในที่นี้สิ่งที่เทียบเท่าในระบบไฟล์คือการใช้พาธ `front_of_house/hosting/add_to_waitlist` การเริ่มต้นด้วยชื่อมอดูลหมายความว่าพาธนั้นเป็นแบบสัมพัทธ์

การเลือกว่าจะใช้พาธแบบสัมพัทธ์หรือแบบสัมบูรณ์เป็นการตัดสินใจที่คุณจะทำโดยอิงจากโปรเจกต์ของคุณ และมันขึ้นอยู่กับว่าคุณมีแนวโน้มจะย้ายโค้ดที่นิยามรายการแยกจากหรือไปพร้อมกับโค้ดที่ใช้รายการนั้นมากกว่ากัน ตัวอย่างเช่น หากเราย้ายมอดูล `front_of_house` และฟังก์ชัน `eat_at_restaurant` ไปไว้ในมอดูลชื่อ `customer_experience` เราจะต้องอัปเดตพาธแบบสัมบูรณ์ไปยัง `add_to_waitlist` แต่พาธแบบสัมพัทธ์จะยังใช้ได้เหมือนเดิม อย่างไรก็ตาม หากเราย้ายฟังก์ชัน `eat_at_restaurant` แยกไปไว้ในมอดูลชื่อ `dining` พาธแบบสัมบูรณ์ไปยังการเรียก `add_to_waitlist` จะคงเดิม แต่พาธแบบสัมพัทธ์จะต้องได้รับการอัปเดต โดยทั่วไปเราชอบที่จะระบุพาธแบบสัมบูรณ์เพราะมีแนวโน้มมากกว่าว่าเราจะต้องการย้ายนิยามโค้ดและการเรียกรายการแยกจากกันอย่างอิสระ

ข้อความแสดงข้อผิดพลาดบอกว่ามอดูล `hosting` เป็นแบบส่วนตัว (private) กล่าวอีกนัยหนึ่ง เรามีพาธที่ถูกต้องสำหรับมอดูล `hosting` และฟังก์ชัน `add_to_waitlist` แต่ Rust ไม่ยอมให้เราใช้มันเพราะมันไม่มีสิทธิ์เข้าถึงส่วนที่เป็นแบบส่วนตัว ใน Rust รายการทั้งหมด (ฟังก์ชัน เมธอด struct enum มอดูล และค่าคงที่) เป็นแบบส่วนตัวเมื่อเทียบกับมอดูลแม่โดยค่าเริ่มต้น หากคุณต้องการทำให้รายการอย่างฟังก์ชันหรือ struct เป็นแบบส่วนตัว คุณก็วางมันไว้ในมอดูล

รายการในมอดูลแม่ไม่สามารถใช้รายการที่เป็นแบบส่วนตัวภายในมอดูลลูกได้ แต่รายการในมอดูลลูกสามารถใช้รายการในมอดูลบรรพบุรุษของมันได้ นี่เป็นเพราะมอดูลลูกห่อหุ้มและซ่อนรายละเอียดการอิมพลีเมนต์ของมัน แต่มอดูลลูกสามารถมองเห็นบริบทที่มันถูกนิยามไว้ได้ เพื่อกล่าวตามอุปมาต่อไป ลองคิดว่ากฎความเป็นส่วนตัวเปรียบเสมือนสำนักงานด้านหลังของร้านอาหาร: สิ่งที่เกิดขึ้นในนั้นเป็นเรื่องส่วนตัวสำหรับลูกค้าของร้านอาหาร แต่ผู้จัดการสำนักงานสามารถมองเห็นและทำทุกอย่างในร้านอาหารที่พวกเขาดูแลได้

Rust เลือกให้ระบบมอดูลทำงานแบบนี้เพื่อให้การซ่อนรายละเอียดการอิมพลีเมนต์ภายในเป็นค่าเริ่มต้น ด้วยวิธีนี้ คุณจะรู้ว่าส่วนใดของโค้ดภายในที่คุณสามารถเปลี่ยนแปลงได้โดยไม่ทำให้โค้ดภายนอกพัง อย่างไรก็ตาม Rust ให้ตัวเลือกแก่คุณในการเปิดเผยส่วนภายในของโค้ดในมอดูลลูกต่อมอดูลบรรพบุรุษภายนอก โดยใช้คำสงวน `pub` เพื่อทำให้รายการเป็นแบบสาธารณะ

ในพาธแบบสัมบูรณ์ เราเริ่มด้วย `crate` ซึ่งเป็นรากของแผนผังมอดูลของเครตเรา มอดูล `front_of_house` ถูกนิยามในรากของเครต แม้ว่า `front_of_house` ไม่ได้เป็นแบบสาธารณะ แต่เนื่องจากฟังก์ชัน `eat_at_restaurant` ถูกนิยามในมอดูลเดียวกับ `front_of_house` (กล่าวคือ `eat_at_restaurant` และ `front_of_house` เป็นมอดูลพี่น้องกัน) เราจึงสามารถอ้างถึง `front_of_house` จาก `eat_at_restaurant` ได้ ต่อไปคือมอดูล `hosting` ที่ทำเครื่องหมายด้วย `pub` เราเข้าถึงมอดูลแม่ของ `hosting` ได้ เราจึงเข้าถึง `hosting` ได้ สุดท้าย ฟังก์ชัน `add_to_waitlist` ทำเครื่องหมายด้วย `pub` และเราเข้าถึงมอดูลแม่ของมันได้ การเรียกฟังก์ชันนี้จึงได้ผล!

ในพาธแบบสัมพัทธ์ ตรรกะเหมือนกับพาธแบบสัมบูรณ์ทุกอย่าง ยกเว้นขั้นตอนแรก: พาธไม่ได้เริ่มจากรากของเครต แต่เริ่มจาก `front_of_house` มอดูล `front_of_house` ถูกนิยามไว้ในมอดูลเดียวกับ `eat_at_restaurant` พาธแบบสัมพัทธ์ที่เริ่มจากมอดูลซึ่ง `eat_at_restaurant` ถูกนิยามไว้จึงใช้ได้ จากนั้น เนื่องจาก `hosting` และ `add_to_waitlist` ทำเครื่องหมายด้วย `pub` ส่วนที่เหลือของพาธจึงใช้ได้ และการเรียกฟังก์ชันนี้ก็ถูกต้อง!

หากคุณวางแผนจะแชร์เครตไลบรารีของคุณเพื่อให้โปรเจกต์อื่นใช้โค้ดของคุณได้ API สาธารณะของคุณคือสัญญาระหว่างคุณกับผู้ใช้เครตของคุณ ซึ่งกำหนดว่าพวกเขาสามารถมีปฏิสัมพันธ์กับโค้ดของคุณได้อย่างไร มีข้อควรพิจารณามากมายเกี่ยวกับการจัดการการเปลี่ยนแปลงต่อ API สาธารณะของคุณเพื่อให้ผู้คนพึ่งพาเครตของคุณได้ง่ายขึ้น ข้อควรพิจารณาเหล่านี้อยู่นอกขอบเขตของหนังสือเล่มนี้ หากคุณสนใจหัวข้อนี้ ดู[แนวทาง API ของ Rust][api-guidelines]

> #### แนวปฏิบัติที่ดีสำหรับแพ็กเกจที่มีทั้งไบนารีและไลบรารี

> เราได้กล่าวว่าแพ็กเกจ (package) สามารถบรรจุทั้งรากของเครตไบนารี (binary crate) _src/main.rs_ และรากของเครตไลบรารี (library crate) _src/lib.rs_ โดยค่าเริ่มต้นเครตทั้งสองจะมีชื่อเดียวกับแพ็กเกจ โดยทั่วไป แพ็กเกจที่มีรูปแบบบรรจุทั้งไลบรารีและเครตไบนารีเช่นนี้จะมีโค้ดในเครตไบนารีเพียงพอที่จะเริ่มไฟล์รันได้ (executable) ที่เรียกโค้ดซึ่งนิยามไว้ในเครตไลบรารีเท่านั้น วิธีนี้ทำให้โปรเจกต์อื่นได้รับประโยชน์จากฟังก์ชันการทำงานส่วนใหญ่ที่แพ็กเกจมีให้ เพราะโค้ดของเครตไลบรารีสามารถแชร์ได้
>
> แผนผังมอดูลควรถูกนิยามใน _src/lib.rs_ จากนั้นรายการที่เป็นแบบสาธารณะใดๆ ก็สามารถใช้ในเครตไบนารีได้โดยเริ่มพาธด้วยชื่อของแพ็กเกจ เครตไบนารีจะกลายเป็นผู้ใช้ของเครตไลบรารี เช่นเดียวกับที่เครตภายนอกโดยสิ้นเชิงจะใช้เครตไลบรารี: มันใช้ได้เฉพาะ API สาธารณะเท่านั้น สิ่งนี้ช่วยให้คุณออกแบบ API ที่ดีได้ เพราะคุณไม่ใช่แค่ผู้เขียน แต่คุณยังเป็นลูกค้าด้วย!
>
> ใน[บทที่ 12][ch12]<!-- ignore --> เราจะสาธิตแนวปฏิบัติด้านการจัดระเบียบนี้ด้วยโปรแกรมบรรทัดคำสั่งที่จะบรรจุทั้งเครตไบนารีและเครตไลบรารี

### การเริ่มพาธแบบสัมพัทธ์ด้วย `super`

เราสามารถสร้างพาธแบบสัมพัทธ์ที่เริ่มต้นในมอดูลแม่ แทนที่จะเป็นมอดูลปัจจุบันหรือรากของเครตได้ โดยใช้ `super` ที่จุดเริ่มต้นของพาธ นี่เหมือนกับการเริ่มพาธในระบบไฟล์ด้วยวากยสัมพันธ์ `..` ที่หมายถึงการไปยังไดเรกทอรีแม่ การใช้ `super` ช่วยให้เราอ้างถึงรายการที่เรารู้ว่าอยู่ในมอดูลแม่ ซึ่งทำให้การจัดเรียงแผนผังมอดูลใหม่ทำได้ง่ายขึ้นเมื่อมอดูลนั้นเกี่ยวข้องอย่างใกล้ชิดกับมอดูลแม่ แต่มอดูลแม่อาจถูกย้ายไปที่อื่นในแผนผังมอดูลในสักวัน

พิจารณาโค้ดในลิสติ้ง 7-8 ที่จำลองสถานการณ์ซึ่งเชฟแก้ไขออร์เดอร์ที่ผิดและนำออกไปให้ลูกค้าด้วยตัวเอง ฟังก์ชัน `fix_incorrect_order` ที่นิยามในมอดูล `back_of_house` เรียกฟังก์ชัน `deliver_order` ที่นิยามในมอดูลแม่ โดยระบุพาธไปยัง `deliver_order` ที่เริ่มต้นด้วย `super`

### การทำให้ struct และ enum เป็นแบบสาธารณะ

เรายังใช้ `pub` เพื่อกำหนดให้ struct และ enum เป็นแบบสาธารณะได้ แต่การใช้งาน `pub` กับ struct และ enum มีรายละเอียดเพิ่มเติมเล็กน้อย หากเราใช้ `pub` ไว้หน้าประกาศนิยาม struct เราจะทำให้ struct เป็นแบบสาธารณะ แต่ฟิลด์ของ struct จะยังคงเป็นแบบส่วนตัว เราสามารถเลือกทำให้แต่ละฟิลด์เป็นแบบสาธารณะหรือไม่ก็ได้เป็นรายกรณี ในลิสติ้ง 7-9 เราได้นิยาม struct `back_of_house::Breakfast` แบบสาธารณะที่มีฟิลด์ `toast` แบบสาธารณะแต่มีฟิลด์ `seasonal_fruit` แบบส่วนตัว สิ่งนี้จำลองกรณีในร้านอาหารที่ลูกค้าเลือกชนิดของขนมปังที่มาพร้อมมื้ออาหารได้ แต่เชฟเป็นผู้ตัดสินใจว่าผลไม้ชนิดใดจะมาคู่กับมื้ออาหารโดยดูจากฤดูกาลและสต็อก ผลไม้ที่มีให้เปลี่ยนไปอย่างรวดเร็ว ลูกค้าจึงเลือกผลไม้ไม่ได้หรือแม้แต่จะเห็นก็ไม่ได้ว่าจะได้ผลไม้ชนิดใด

เพราะฟิลด์ `toast` ใน struct `back_of_house::Breakfast` เป็นแบบสาธารณะ ใน `eat_at_restaurant` เราสามารถเขียนและอ่านฟิลด์ `toast` ได้โดยใช้สัญกรณ์จุด สังเกตว่าเราใช้ฟิลด์ `seasonal_fruit` ใน `eat_at_restaurant` ไม่ได้ เพราะ `seasonal_fruit` เป็นแบบส่วนตัว ลองยกเลิกคอมเมนต์บรรทัดที่แก้ไขค่าของฟิลด์ `seasonal_fruit` ดูว่าคุณจะได้ข้อผิดพลาดอะไร!

นอกจากนี้ โปรดสังเกตว่าเพราะ `back_of_house::Breakfast` มีฟิลด์ที่เป็นแบบส่วนตัว struct จึงต้องมีฟังก์ชันที่เชื่อมโยงกับชนิดข้อมูลแบบสาธารณะที่ใช้สร้างอินสแตนซ์ของ `Breakfast` (ในที่นี้เราตั้งชื่อมันว่า `summer`) หาก `Breakfast` ไม่มีฟังก์ชันเช่นนั้น เราจะสร้างอินสแตนซ์ของ `Breakfast` ใน `eat_at_restaurant` ไม่ได้ เพราะเราตั้งค่าฟิลด์ `seasonal_fruit` ที่เป็นแบบส่วนตัวใน `eat_at_restaurant` ไม่ได้

enum ไม่ค่อยมีประโยชน์เท่าไรถ้าวาเรียนต์ของมันไม่เป็นแบบสาธารณะ การต้องระบุ `pub` ให้วาเรียนต์ของ enum ทุกตัวในทุกกรณีคงน่ารำคาญ ดังนั้นค่าเริ่มต้นของวาเรียนต์ enum จึงเป็นแบบสาธารณะ struct มักมีประโยชน์ได้แม้ฟิลด์ของมันไม่เป็นแบบสาธารณะ ฟิลด์ของ struct จึงเป็นไปตามกฎทั่วไปที่ว่าทุกอย่างเป็นแบบส่วนตัวโดยค่าเริ่มต้นเว้นแต่จะระบุ `pub`

ยังมีอีกหนึ่งสถานการณ์ที่เกี่ยวข้องกับ `pub` ที่เรายังไม่ได้ครอบคลุม นั่นคือฟีเจอร์สุดท้ายของระบบมอดูล: คำสงวน `use` เราจะครอบคลุม `use` ด้วยตัวเองก่อน จากนั้นจะแสดงวิธีรวม `pub` และ `use` เข้าด้วยกัน
