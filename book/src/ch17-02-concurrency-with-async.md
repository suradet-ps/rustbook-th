## การนำ async มาประยุกต์ใช้กับการทำงานพร้อมกัน

ในหัวข้อนี้ เราจะนำ async มาประยุกต์ใช้กับความท้าทายด้านการทำงานพร้อมกัน (concurrency) บางส่วนที่เราเคยจัดการด้วยเธรด (thread) ในบทที่ 16 เพราะเราได้พูดถึงแนวคิดสำคัญๆ หลายอย่างไปแล้วในบทนั้น ในหัวข้อนี้เราจะเน้นสิ่งที่แตกต่างระหว่างเธรดกับฟิวเจอร์ (future)

ในหลายกรณี API สำหรับการทำงานพร้อมกันด้วย async นั้นคล้ายกับ API สำหรับการใช้เธรดมาก ในกรณีอื่นๆ พวกมันกลับแตกต่างกันค่อนข้างมาก แม้ในยามที่ API ของเธรดและ async ดู_คล้ายกัน_ พวกมันก็มักมีพฤติกรรมที่แตกต่างกัน—และเกือบทุกครั้งก็มีลักษณะด้านประสิทธิภาพที่แตกต่างกัน

> หมายเหตุ: จากจุดนี้เป็นต้นไปในบทนี้ ตัวอย่างทุกตัวอย่างจะมีการห่อโค้ดแบบเดียวกันนี้เป๊ะๆ ด้วย `trpl::block_on` ใน `main` เราจึงมักจะข้ามมันไปเหมือนที่เราทำกับ `main` อย่าลืมใส่ไว้ในโค้ดของคุณด้วย!

จากนั้นเราเขียนสองลูปภายในบล็อกนั้น แต่ละลูปมีการเรียก `trpl::sleep` ซึ่งรอครึ่งวินาที (500 มิลลิวินาที) ก่อนส่งข้อความถัดไป เราวางลูปหนึ่งไว้ในบอดี้ของ `trpl::spawn_task` และอีกลูปไว้ในลูป `for` ระดับบนสุด เรายังเพิ่ม `await` หลังการเรียก `sleep` ด้วย

ความแตกต่างที่ใหญ่กว่าคือ เราไม่จำเป็นต้องสร้างเธรดของระบบปฏิบัติการอีกเธรดเพื่อทำสิ่งนี้ อันที่จริง เราไม่จำเป็นต้องสร้างทาสก์เลยด้วยซ้ำ เพราะบล็อก async คอมไพล์เป็นฟิวเจอร์นิรนาม เราจึงวางแต่ละลูปในบล็อก async และให้รันไทม์ (runtime) รันทั้งสองจนเสร็จโดยใช้ฟังก์ชัน `trpl::join` ได้

ตอนนี้ คุณจะเห็นลำดับเดิมเป๊ะๆ ทุกครั้ง ซึ่งแตกต่างอย่างมากจากสิ่งที่เราเห็นกับเธรดและกับ `trpl::spawn_task` ในลิสติ้ง 17-7 นั่นเป็นเพราะฟังก์ชัน `trpl::join` นั้น_ยุติธรรม_ หมายความว่ามันตรวจสอบฟิวเจอร์แต่ละตัวบ่อยครั้งเท่าๆ กัน สลับไปมาระหว่างกัน และไม่ปล่อยให้ตัวหนึ่งนำหน้าไปหากอีกตัวพร้อมอยู่ กับเธรด ระบบปฏิบัติการเป็นผู้ตัดสินใจว่าจะตรวจสอบเธรดใดและปล่อยให้มันรันนานแค่ไหน กับ async ใน Rust รันไทม์เป็นผู้ตัดสินใจว่าจะตรวจสอบทาสก์ใด (ในทางปฏิบัติ รายละเอียดจะซับซ้อนขึ้นเพราะรันไทม์แบบ async อาจใช้เธรดของระบบปฏิบัติการอยู่เบื้องหลังเป็นส่วนหนึ่งของวิธีจัดการการทำงานพร้อมกัน การรับประกันความยุติธรรมจึงเป็นงานที่ยากขึ้นสำหรับรันไทม์—แต่มันก็ยังเป็นไปได้!) รันไทม์ไม่จำเป็นต้องรับประกันความยุติธรรมสำหรับการดำเนินการใดๆ และบ่อยครั้งก็มี API ที่แตกต่างกันให้คุณเลือกว่าจะเอาความยุติธรรมหรือไม่

ลองปรับเปลี่ยนวิธี await ฟิวเจอร์เหล่านี้ดูบ้าง แล้วดูว่ามันทำอะไร:

- ลบบล็อก async ที่ห่อรอบลูปตัวใดตัวหนึ่งหรือทั้งสองตัวออก
- Await บล็อก async แต่ละตัวทันทีหลังจากนิยามมัน
- ห่อเฉพาะลูปแรกด้วยบล็อก async แล้ว await ฟิวเจอร์ที่ได้หลังบอดี้ของลูปที่สอง

สำหรับโจทย์ท้าทายเพิ่มเติม ลองดูว่าคุณสามารถคาดเดาได้ไหมว่าเอาต์พุตจะเป็นอย่างไรในแต่ละกรณี_ก่อน_จะรันโค้ด!

### การส่งข้อมูลระหว่างสองทาสก์ด้วยการส่งผ่านข้อความ

การแชร์ข้อมูลระหว่างฟิวเจอร์ก็จะดูคุ้นเคยเช่นกัน: เราจะใช้การส่งผ่านข้อความ (message passing) อีกครั้ง แต่ครั้งนี้ด้วยเวอร์ชัน async ของชนิดข้อมูลและฟังก์ชัน เราจะใช้เส้นทางที่ต่างออกไปเล็กน้อยจากที่เราทำในหัวข้อ[“ส่งข้อมูลระหว่างเธรดด้วยการส่งผ่านข้อความ”][message-passing-threads]<!-- ignore --> ในบทที่ 16 เพื่อแสดงให้เห็นความแตกต่างสำคัญบางประการระหว่างการทำงานพร้อมกันแบบใช้เธรดกับแบบใช้ฟิวเจอร์ ในลิสติ้ง 17-9 เราจะเริ่มด้วยบล็อก async เพียงบล็อกเดียว—_ไม่ใช่_การสร้างทาสก์แยกต่างหากอย่างที่เราเคยสร้างเธรดแยกต่างหาก

ในที่นี้ เราใช้ `trpl::channel` ซึ่งเป็นเวอร์ชัน async ของ API แชนเนล (channel) แบบผู้ผลิตหลายราย ผู้บริโภครายเดียว (multiple producer, single consumer) ที่เราใช้กับเธรดในบทที่ 16 เวอร์ชัน async ของ API นี้ต่างจากเวอร์ชันที่ใช้เธรดเพียงเล็กน้อย: มันใช้ตัวรับ `rx` ที่เปลี่ยนแปลงได้แทนแบบที่เปลี่ยนแปลงไม่ได้ และเมธอด `recv` ของมันสร้างฟิวเจอร์ที่เราต้อง await แทนที่จะสร้างค่าโดยตรง ตอนนี้เราสามารถส่งข้อความจากฝั่งผู้ส่งไปยังฝั่งผู้รับได้ โปรดสังเกตว่าเราไม่จำเป็นต้องสร้างเธรดแยกหรือแม้แต่ทาสก์ เราเพียงต้อง await การเรียก `rx.recv` เท่านั้น

เมธอด `Receiver::recv` แบบซิงโครนัสใน `std::mpsc::channel` จะบล็อกจนกว่าจะได้รับข้อความ ส่วนเมธอด `trpl::Receiver::recv` ไม่บล็อก เพราะมันเป็น async แทนที่จะบล็อก มันส่งคืนการควบคุมกลับให้รันไทม์จนกว่าจะได้รับข้อความหรือฝั่งส่งของแชนเนลปิดลง ตรงกันข้าม เราจะไม่ await การเรียก `send` เพราะมันไม่บล็อก มันไม่จำเป็นต้องบล็อก เพราะแชนเนลที่เราส่งข้อความเข้าไปนั้นไม่มีขีดจำกัด

> หมายเหตุ: เพราะโค้ด async ทั้งหมดนี้รันอยู่ในบล็อก async ภายในการเรียก `trpl::block_on` ทุกสิ่งภายในมันจึงหลีกเลี่ยงการบล็อกได้ อย่างไรก็ตาม โค้ด_ภายนอก_มันจะบล็อกรอการคืนค่าของฟังก์ชัน `block_on` นั่นคือจุดประสงค์ทั้งหมดของฟังก์ชัน `trpl::block_on`: มันให้คุณ_เลือก_ว่าจะบล็อกตรงไหนกับโค้ด async ชุดหนึ่ง และด้วยเหตุนี้จึงเลือกได้ว่าจะเปลี่ยนผ่านระหว่างโค้ดซิงก์กับโค้ด async ที่จุดใด

โปรดสังเกตสองสิ่งเกี่ยวกับตัวอย่างนี้ อย่างแรก ข้อความจะมาถึงทันที อย่างที่สอง แม้เราจะใช้ฟิวเจอร์ที่นี่ แต่ยังไม่มีการทำงานพร้อมกัน ทุกอย่างในลิสติ้งนี้เกิดขึ้นตามลำดับ เช่นเดียวกับที่จะเกิดขึ้นหากไม่มีฟิวเจอร์เข้ามาเกี่ยวข้อง

นอกจากการส่งข้อความแล้ว เรายังต้องรับข้อความด้วย ในกรณีนี้ เพราะเรารู้ว่าจะมีข้อความเข้ามากี่ข้อความ เราจึงทำด้วยมือได้โดยเรียก `rx.recv().await` สี่ครั้ง อย่างไรก็ตาม ในโลกจริง โดยทั่วไปเราจะรอข้อความจำนวนหนึ่งที่_ไม่รู้_แน่นอน เราจึงต้องรอต่อไปจนกว่าเราจะแน่ใจว่าไม่มีข้อความอีกแล้ว

ในลิสติ้ง 16-10 เราใช้ลูป `for` เพื่อประมวลผลสมาชิกทั้งหมดที่รับมาจากแชนเนลแบบซิงโครนัส อย่างไรก็ตาม Rust ยังไม่มีวิธีใช้ลูป `for` กับลำดับสมาชิกที่_ถูกสร้างขึ้นแบบอะซิงโครนัส_ เราจึงต้องใช้ลูปที่เราไม่เคยเห็นมาก่อน: ลูปแบบมีเงื่อนไข `while let` นี่คือเวอร์ชันลูปของโครงสร้าง `if let` ที่เราเห็นไปแล้วในหัวข้อ[“การควบคุมโฟลว์แบบกระชับด้วย `if
let` และ `let...else`”][if-let]<!-- ignore --> ในบทที่ 6 ลูปจะทำงานต่อไปตราบเท่าที่แพตเทิร์นที่มันระบุยังจับคู่กับค่าอยู่

การเรียก `rx.recv` สร้างฟิวเจอร์ ซึ่งเรา await รันไทม์จะหยุดฟิวเจอร์ชั่วคราวจนกว่ามันจะพร้อม เมื่อข้อความมาถึง ฟิวเจอร์จะคลี่คลายเป็น `Some(message)` กี่ครั้งก็ตามที่มีข้อความมาถึง เมื่อแชนเนลปิด ไม่ว่าจะมีข้อความมาถึง_หรือไม่_ ฟิวเจอร์จะคลี่คลายเป็น `None` แทน เพื่อบ่งชี้ว่าไม่มีค่าอีกแล้ว เราจึงควรหยุดการโพลล์ (polling)—นั่นคือ หยุด await

ลูป `while let` รวบรวมทั้งหมดนี้เข้าด้วยกัน หากผลลัพธ์ของการเรียก `rx.recv().await` เป็น `Some(message)` เราจะเข้าถึงข้อความได้และใช้มันในบอดี้ของลูปได้ เช่นเดียวกับที่เราทำได้กับ `if let` หากผลลัพธ์เป็น `None` ลูปก็จบลง ทุกครั้งที่ลูปทำงานครบรอบ มันจะแตะจุด await อีกครั้ง รันไทม์จึงหยุดมันชั่วคราวอีกครั้งจนกว่าข้อความใหม่จะมาถึง

ตอนนี้โค้ดส่งและรับข้อความทั้งหมดได้สำเร็จแล้ว น่าเสียดายที่ยังมีปัญหาอีกสองสามข้อ อย่างแรก ข้อความไม่ได้มาถึงเป็นช่วงๆ ครึ่งวินาที พวกมันมาถึงพร้อมกันทั้งหมด 2 วินาที (2,000 มิลลิวินาที) หลังจากที่เราเริ่มโปรแกรม อย่างที่สอง โปรแกรมนี้ก็ไม่ยอมออกเหมือนกัน! มันกลับรอข้อความใหม่ไปตลอดกาล คุณจะต้องปิดมันด้วย <kbd>ctrl</kbd>-<kbd>C</kbd>

#### โค้ดภายในบล็อก async หนึ่งบล็อกทำงานเป็นเส้นตรง

มาเริ่มด้วยการตรวจสอบว่าทำไมข้อความจึงเข้ามาพร้อมกันทั้งหมดหลังความหน่วงเต็มจำนวน แทนที่จะเข้ามาโดยมีความหน่วงคั่นระหว่างกัน ภายในบล็อก async ที่กำหนด ลำดับที่คำสงวน `await` ปรากฏในโค้ดก็คือลำดับที่พวกมันถูกเรียกใช้เมื่อโปรแกรมรันเช่นกัน

มีบล็อก async เพียงบล็อกเดียวในลิสติ้ง 17-10 ทุกอย่างในนั้นจึงทำงานเป็นเส้นตรง ยังไม่มีการทำงานพร้อมกันอยู่ดี การเรียก `tx.send` ทั้งหมดเกิดขึ้น โดยมีคำเรียก `trpl::sleep` และจุด await ที่เกี่ยวข้องคั่นสลับอยู่ตลอด จากนั้นลูป `while let` จึงจะได้เริ่มผ่านจุด `await` ใดๆ บนการเรียก `recv`

เพื่อให้ได้พฤติกรรมที่เราต้องการ ซึ่งก็คือมีความหน่วงจากการนอนหลับคั่นระหว่างแต่ละข้อความ เราต้องวางการดำเนินการของ `tx` และ `rx` ไว้ในบล็อก async ของตัวเอง ดังแสดงในลิสติ้ง 17-11 จากนั้นรันไทม์จึงจะเรียกใช้แต่ละบล็อกแยกกันโดยใช้ `trpl::join` ได้ เช่นเดียวกับในลิสติ้ง 17-8 และอีกครั้ง เราจะ await ผลลัพธ์ของการเรียก `trpl::join` ไม่ใช่ await ฟิวเจอร์แต่ละตัว หากเรา await ฟิวเจอร์แต่ละตัวตามลำดับ เราก็จะกลับไปสู่โฟลว์แบบเรียงลำดับเหมือนเดิม—ซึ่งเป็นสิ่งที่เราพยายาม_ไม่_ทำอย่างยิ่ง

#### การย้ายความเป็นเจ้าของเข้าสู่บล็อก async

อย่างไรก็ตาม โปรแกรมก็ยังไม่ยอมออก เพราะวิธีที่ลูป `while let` โต้ตอบกับ `trpl::join`:

- ฟิวเจอร์ที่ถูกคืนกลับจาก `trpl::join` จะเสร็จสิ้นก็ต่อเมื่อฟิวเจอร์_ทั้งสอง_ที่ส่งให้มันเสร็จสิ้นแล้วเท่านั้น
- ฟิวเจอร์ `tx_fut` เสร็จสิ้นเมื่อมันนอนหลับหลังส่งข้อความสุดท้ายใน `vals` จบ
- ฟิวเจอร์ `rx_fut` จะไม่เสร็จสิ้นจนกว่าลูป `while let` จะจบลง
- ลูป `while let` จะไม่จบลงจนกว่าการ await `rx.recv` จะสร้าง `None`
- การ await `rx.recv` จะคืน `None` ก็ต่อเมื่ออีกฝั่งของแชนเนลปิดลงเท่านั้น
- แชนเนลจะปิดก็ต่อเมื่อเราเรียก `rx.close` หรือเมื่อฝั่งผู้ส่ง `tx` ถูกทิ้ง (drop)
- เราไม่ได้เรียก `rx.close` ที่ไหนเลย และ `tx` จะไม่ถูกทิ้งจนกว่าบล็อก async ชั้นนอกสุดที่ส่งให้ `trpl::block_on` จะจบลง
- บล็อกนั้นจบไม่ได้เพราะมันถูกบล็อกรอ `trpl::join` เสร็จสิ้น ซึ่งพาเรากลับไปยังต้นรายการนี้

ตอนนี้ บล็อก async ที่เราส่งข้อความนั้นเพียง_ยืม_ `tx` เพราะการส่งข้อความไม่ต้องใช้ความเป็นเจ้าของ แต่หากเราย้าย `tx` เข้าไปในบล็อก async นั้นได้ มันจะถูกทิ้งเมื่อบล็อกนั้นจบลง ในหัวข้อ[“การจับเรเฟอเรนซ์หรือการย้ายความเป็นเจ้าของ”][capture-or-move]<!-- ignore --> ในบทที่ 13 คุณได้เรียนรู้วิธีใช้คำสงวน `move` กับโคลเชอร์ และดังที่อภิปรายในหัวข้อ[“การใช้โคลเชอร์ `move` กับเธรด”][move-threads]<!-- ignore --> ในบทที่ 16 เรามักต้องย้ายข้อมูลเข้าไปในโคลเชอร์เมื่อทำงานกับเธรด พลวัตพื้นฐานเดียวกันนี้ใช้กับบล็อก async ด้วย คำสงวน `move` จึงทำงานกับบล็อก async ได้เช่นเดียวกับที่มันทำกับโคลเชอร์

ก่อนอื่น เราโคลน `tx` โดยสร้าง `tx1` ไว้นอกบล็อก async แรก เราย้าย `tx1` เข้าไปในบล็อกนั้นเหมือนที่เราทำกับ `tx` ก่อนหน้านี้ จากนั้นเราย้าย `tx` ตัวเดิมเข้าไปในบล็อก async _ใหม่_ ซึ่งเราส่งข้อความเพิ่มเติมด้วยความหน่วงที่ช้ากว่าเล็กน้อย เราเผอิญวางบล็อก async ใหม่นี้ไว้หลังบล็อก async สำหรับรับข้อความ แต่มันจะวางไว้ก่อนก็ได้เช่นกัน หัวใจสำคัญคือลำดับที่ฟิวเจอร์ถูก await ไม่ใช่ลำดับที่พวกมันถูกสร้าง

บล็อก async ทั้งสองสำหรับส่งข้อความต้องเป็นบล็อก `async move` เพื่อให้ทั้ง `tx` และ `tx1` ถูกทิ้งเมื่อบล็อกเหล่านั้นทำงานเสร็จ มิฉะนั้น เราจะกลับไปติดอยู่ในลูปอนันต์เดิมที่เราเริ่มต้น

สุดท้าย เราเปลี่ยนจาก `trpl::join` เป็น `trpl::join!` เพื่อจัดการฟิวเจอร์ที่เพิ่มเข้ามา: มาโคร `join!` จะ await ฟิวเจอร์ตามจำนวนใดก็ได้โดยที่เรารู้จำนวนฟิวเจอร์ตอนคอมไพล์ เราจะพูดถึงการ await คอลเลกชันของฟิวเจอร์จำนวนไม่ทราบแน่นอนในบทนี้ต่อไป
