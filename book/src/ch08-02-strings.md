## เก็บข้อความที่เข้ารหัส UTF-8 ด้วยสตริง

เราได้พูดถึงสตริง (string) ไปแล้วในบทที่ 4 แต่ตอนนี้เราจะมาดูพวกมันในเชิงลึกยิ่งขึ้น ชาว Rustacean มือใหม่มักติดขัดกับสตริงด้วยเหตุผลสามประการรวมกัน ได้แก่ แนวโน้มของ Rust ที่เปิดเผยข้อผิดพลาดที่อาจเกิดขึ้น การที่สตริงเป็นโครงสร้างข้อมูลที่ซับซ้อนกว่าที่โปรแกรมเมอร์หลายคนให้เครดิตไว้ และ UTF-8 ปัจจัยเหล่านี้ออกฤทธิ์ร่วมกันในแบบที่อาจดูยากเมื่อคุณมาจากภาษาโปรแกรมอื่นๆ

เราพูดถึงสตริงในบริบทของคอลเลกชัน (collection) เพราะสตริงถูกอิมพลีเมนต์เป็นคอลเลกชันของไบต์ บวกกับเมธอดบางอย่างที่ให้ฟังก์ชันการทำงานที่มีประโยชน์เมื่อไบต์เหล่านั้นถูกตีความเป็นข้อความ ในหัวข้อนี้ เราจะพูดถึงการดำเนินการกับ `String` ที่ชนิดคอลเลกชันทุกชนิดมี เช่น การสร้าง การอัปเดต และการอ่าน เราจะพูดถึงวิธีที่ `String` แตกต่างจากคอลเลกชันอื่นๆ ด้วย กล่าวคือ การจัดดัชนี (indexing) เข้าไปใน `String` นั้นซับซ้อนเพราะความแตกต่างระหว่างวิธีที่มนุษย์และคอมพิวเตอร์ตีความข้อมูล `String`

### การนิยามสตริง

อันดับแรกเราจะนิยามว่าคำว่า _สตริง_ นั้นหมายถึงอะไร Rust มีชนิดสตริงเพียงชนิดเดียวในภาษาหลัก นั่นคือสตริงสไลซ์ (string slice) `str` ซึ่งมักพบในรูปแบบที่ถูกยืมของมัน คือ `&str` ในบทที่ 4 เราได้พูดถึงสตริงสไลซ์ ซึ่งเป็นเรเฟอเรนซ์ไปยังข้อมูลสตริงที่เข้ารหัส UTF-8 ที่จัดเก็บอยู่ที่อื่น ตัวอย่างเช่น สตริงลิเทอรัล (string literal) ถูกจัดเก็บไว้ในไบนารีของโปรแกรม จึงเป็นสตริงสไลซ์

ชนิด `String` ซึ่งไลบรารีมาตรฐานของ Rust มีให้ แทนที่จะถูกเขียนไว้ในภาษาหลัก เป็นชนิดสตริงที่ขยายขนาดได้ เปลี่ยนแปลงได้ เป็นเจ้าของค่า และเข้ารหัส UTF-8 เมื่อชาว Rustacean พูดถึง “สตริง” ใน Rust พวกเขาอาจหมายถึงชนิด `String` หรือสตริงสไลซ์ `&str` ก็ได้ ไม่ใช่แค่ชนิดใดชนิดหนึ่ง แม้ว่าหัวข้อนี้จะเน้นไปที่ `String` เป็นส่วนใหญ่ แต่ทั้งสองชนิดถูกใช้อย่างหนักในไลบรารีมาตรฐานของ Rust และทั้ง `String` และสตริงสไลซ์ต่างก็เข้ารหัส UTF-8

#### การเชื่อมด้วย `+` หรือ `format!`

บ่อยครั้ง คุณจะต้องการรวมสตริงสองสตริงที่มีอยู่เข้าด้วยกัน วิธีหนึ่งในการทำเช่นนั้นคือการใช้ตัวดำเนินการ `+` ดังที่แสดงในลิสติ้ง 8-18

```rust
{{#rustdoc_include ../listings/ch08-common-collections/listing-08-18/src/main.rs:here}}
```

สตริง `s3` จะบรรจุ `Hello, world!` เหตุผลที่ `s1` ไม่สามารถใช้ได้อีกต่อไปหลังการบวก และเหตุผลที่เราใช้เรเฟอเรนซ์ไปยัง `s2` เกี่ยวข้องกับซิกเนเจอร์ของเมธอดที่ถูกเรียกเมื่อเราใช้ตัวดำเนินการ `+` ตัวดำเนินการ `+` ใช้เมธอด `add` ซึ่งซิกเนเจอร์มีหน้าตาประมาณนี้:

```rust,ignore
fn add(self, s: &str) -> String {
```

ในไลบรารีมาตรฐาน คุณจะเห็น `add` ถูกนิยามโดยใช้เจเนอริกและชนิดข้อมูลที่เชื่อมโยง (associated type) ในที่นี้ เราได้แทนที่ด้วยชนิดที่เป็นรูปธรรม ซึ่งเป็นสิ่งที่เกิดขึ้นเมื่อเราเรียกเมธอดนี้กับค่า `String` เราจะพูดถึงเจเนอริกในบทที่ 10 ซิกเนเจอร์นี้ให้เบาะแสที่เราต้องการเพื่อทำความเข้าใจส่วนที่ชวนสับสนของตัวดำเนินการ `+`

ประการแรก `s2` มี `&` หมายความว่าเรากำลังบวกเรเฟอเรนซ์ของสตริงตัวที่สองเข้ากับสตริงตัวแรก นี่เป็นเพราะพารามิเตอร์ `s` ในฟังก์ชัน `add`: เราบวกสตริงสไลซ์เข้ากับ `String` ได้เท่านั้น เราบวกค่า `String` สองค่าด้วยกันไม่ได้ แต่เดี๋ยวก่อน—ชนิดของ `&s2` คือ `&String` ไม่ใช่ `&str` ตามที่ระบุในพารามิเตอร์ตัวที่สองของ `add` แล้วทำไมลิสติ้ง 8-18 จึงคอมไพล์ผ่าน?

เหตุผลที่เราใช้ `&s2` ในการเรียก `add` ได้ก็คือคอมไพเลอร์สามารถบังคับอาร์กิวเมนต์ `&String` ให้เป็น `&str` ได้ เมื่อเราเรียกเมธอด `add` Rust จะใช้การบังคับดีเรฟ (deref coercion) ซึ่งในที่นี้เปลี่ยน `&s2` ให้เป็น `&s2[..]` เราจะพูดถึงการบังคับดีเรฟในเชิงลึกมากขึ้นในบทที่ 15 เพราะ `add` ไม่รับความเป็นเจ้าของพารามิเตอร์ `s` `s2` จึงยังคงเป็น `String` ที่ใช้ได้หลังการดำเนินการนี้

ประการที่สอง เราจะเห็นได้ในซิกเนเจอร์ว่า `add` รับความเป็นเจ้าของ `self` เพราะ `self` _ไม่_ มี `&` ซึ่งหมายความว่า `s1` ในลิสติ้ง 8-18 จะถูกย้ายเข้าไปในการเรียก `add` และจะไม่สามารถใช้ได้อีกต่อไปหลังจากนั้น ดังนั้น แม้ว่า `let s3 = s1 + &s2;` ดูเหมือนจะคัดลอกสตริงทั้งสองและสร้างอันใหม่ขึ้นมา แต่สเตตเมนต์นี้รับความเป็นเจ้าของ `s1` จริงๆ ต่อท้ายด้วยสำเนาของเนื้อหาใน `s2` แล้วคืนความเป็นเจ้าของของผลลัพธ์กลับมา พูดอีกนัยหนึ่ง มันดูเหมือนกำลังคัดลอกหลายต่อหลายครั้ง แต่ไม่ใช่เช่นนั้น การอิมพลีเมนต์มีประสิทธิภาพมากกว่าการคัดลอก

หากมีคนถามคุณว่าสตริงนี้ยาวเท่าใด คุณอาจตอบว่า 12 อันที่จริงคำตอบของ Rust คือ 24: นั่นคือจำนวนไบต์ที่ใช้เข้ารหัส “Здравствуйте” ใน UTF-8 เพราะค่าสเกลาร์ยูนิโคดแต่ละค่าในสตริงนั้นใช้พื้นที่จัดเก็บ 2 ไบต์ ดังนั้น ดัชนีเข้าไปในไบต์ของสตริงจึงไม่สอดคล้องกับค่าสเกลาร์ยูนิโคดที่ถูกต้องเสมอไป เพื่อสาธิต ลองพิจารณาโค้ด Rust ที่ไม่ถูกต้องนี้:

```rust,ignore,does_not_compile
let hello = "Здравствуйте";
let answer = &hello[0];
```

คุณรู้อยู่แล้วว่า `answer` จะไม่ใช่ `З` ซึ่งเป็นตัวอักษรตัวแรก เมื่อเข้ารหัสเป็น UTF-8 ไบต์แรกของ `З` คือ `208` และไบต์ที่สองคือ `151` ดังนั้นดูเหมือนว่า `answer` ควรจะเป็น `208` จริงๆ แต่ `208` ไม่ใช่อักขระที่ถูกต้องในตัวเอง การคืนค่า `208` คงไม่ใช่สิ่งที่ผู้ใช้ต้องการหากพวกเขาถามหาตัวอักษรตัวแรกของสตริงนี้ อย่างไรก็ตาม นั่นคือข้อมูลเดียวที่ Rust มีอยู่ที่ดัชนีไบต์ 0 ผู้ใช้โดยทั่วไปไม่ต้องการให้คืนค่าไบต์ออกมา แม้ว่าสตริงจะมีเฉพาะตัวอักษรละตินเท่านั้น: หาก `&"hi"[0]` เป็นโค้ดที่ถูกต้องที่คืนค่าไบต์ มันจะคืน `104` ไม่ใช่ `h`

คำตอบก็คือ เพื่อหลีกเลี่ยงการคืนค่าที่ไม่คาดคิดและก่อให้เกิดบั๊กที่อาจไม่ถูกค้นพบในทันที Rust จึงไม่คอมไพล์โค้ดนี้เลย และป้องกันความเข้าใจผิดตั้งแต่เนิ่นๆ ในกระบวนการพัฒนา

#### ไบต์ ค่าสเกลาร์ และกลุ่มกราฟีม

อีกประเด็นเกี่ยวกับ UTF-8 ก็คือ แท้จริงแล้วมีสามวิธีที่เกี่ยวข้องในการมองสตริงจากมุมมองของ Rust: ในฐานะไบต์ ในฐานะค่าสเกลาร์ และในฐานะกลุ่มกราฟีม (grapheme cluster) (สิ่งที่ใกล้เคียงที่สุดกับสิ่งที่เราเรียกว่า _ตัวอักษร_)

หากเราดูคำภาษาฮินดี “नमस्ते” ที่เขียนด้วยอักษรเทวนาครี มันถูกจัดเก็บเป็นเวกเตอร์ของค่า `u8` ที่มีหน้าตาดังนี้:

```text
[224, 164, 168, 224, 164, 174, 224, 164, 184, 224, 165, 141, 224, 164, 164,
224, 165, 135]
```

นั่นคือ 18 ไบต์ และเป็นวิธีที่คอมพิวเตอร์จัดเก็บข้อมูลนี้ในที่สุด หากเรามองพวกมันเป็นค่าสเกลาร์ยูนิโคด ซึ่งเป็นสิ่งที่ชนิด `char` ของ Rust แทน ไบต์เหล่านั้นจะมีหน้าตาดังนี้:

```text
['न', 'म', 'स', '्', 'त', 'े']
```

มีค่า `char` หกค่าตรงนี้ แต่ค่าที่สี่และที่หกไม่ใช่ตัวอักษร: พวกมันเป็นเครื่องหมายเสริมสัทอักษร (diacritic) ที่ไม่มีความหมายในตัวเอง สุดท้าย หากเรามองพวกมันเป็นกลุ่มกราฟีม เราจะได้สิ่งที่มนุษย์เรียกว่าสี่ตัวอักษรที่ประกอบขึ้นเป็นคำภาษาฮินดีนี้:

```text
["न", "म", "स्", "ते"]
```

Rust มีวิธีตีความข้อมูลสตริงดิบที่คอมพิวเตอร์จัดเก็บไว้ให้เลือกหลายแบบ เพื่อให้แต่ละโปรแกรมเลือกการตีความที่มันต้องการได้ ไม่ว่าข้อมูลจะอยู่ในภาษามนุษย์ใดก็ตาม

เหตุผลสุดท้ายที่ Rust ไม่ยอมให้เราจัดดัชนีเข้าไปใน `String` เพื่อดึงอักขระออกมาคือ การดำเนินการจัดดัชนีคาดหวังว่าจะใช้เวลาคงที่ (O(1)) เสมอ แต่เราไม่สามารถรับประกันประสิทธิภาพนั้นกับ `String` ได้ เพราะ Rust จะต้องไล่ผ่านเนื้อหาตั้งแต่ต้นจนถึงดัชนีเพื่อหาว่ามีอักขระที่ถูกต้องอยู่กี่ตัว

### การสไลซ์สตริง

การจัดดัชนีเข้าไปในสตริงมักเป็นความคิดที่ไม่ดี เพราะไม่ชัดเจนว่าชนิดที่คืนกลับของการดำเนินการจัดดัชนีสตริงควรเป็นอะไร: ค่าไบต์ อักขระ กลุ่มกราฟีม หรือสตริงสไลซ์ ดังนั้น หากคุณจำเป็นต้องใช้ดัชนีเพื่อสร้างสตริงสไลซ์จริงๆ Rust ก็ขอให้คุณระบุให้เฉพาะเจาะจงมากกว่านั้น

แทนที่จะจัดดัชนีโดยใช้ `[]` กับตัวเลขเดี่ยวๆ คุณสามารถใช้ `[]` กับเรนจ์เพื่อสร้างสตริงสไลซ์ที่บรรจุไบต์ที่ต้องการได้:

```rust
let hello = "Здравствуйте";

let s = &hello[0..4];
```

ในที่นี้ `s` จะเป็น `&str` ที่บรรจุ 4 ไบต์แรกของสตริง ก่อนหน้านี้เราได้กล่าวว่าอักขระแต่ละตัวใช้ 2 ไบต์ ซึ่งหมายความว่า `s` จะเป็น `Зд`

หากเราพยายามสไลซ์เพียงบางส่วนของไบต์ของอักขระด้วยสิ่งอย่าง `&hello[0..1]` Rust จะแพนิก (panic) ตอนรันไทม์เช่นเดียวกับกรณีที่เข้าถึงดัชนีที่ไม่ถูกต้องในเวกเตอร์:

```console
{{#include ../listings/ch08-common-collections/output-only-01-not-char-boundary/output.txt}}
```

คุณควรใช้ความระมัดระวังเมื่อสร้างสตริงสไลซ์ด้วยเรนจ์ เพราะการทำเช่นนั้นอาจทำให้โปรแกรมของคุณแครชได้

### การวนซ้ำบนสตริง

วิธีที่ดีที่สุดในการดำเนินการกับชิ้นส่วนของสตริงคือการระบุให้ชัดเจนว่าคุณต้องการอักขระหรือไบต์ สำหรับค่าสเกลาร์ยูนิโคดแต่ละค่า ให้ใช้เมธอด `chars` การเรียก `chars` บน “Зд” จะแยกและคืนค่าสองค่าที่มีชนิด `char` และคุณสามารถวนซ้ำบนผลลัพธ์เพื่อเข้าถึงแต่ละองค์ประกอบได้:

```rust
for c in "Зд".chars() {
    println!("{c}");
}
```

โค้ดนี้จะพิมพ์ดังต่อไปนี้:

```text
З
д
```

อีกทางเลือกหนึ่ง เมธอด `bytes` คืนค่าไบต์ดิบแต่ละตัว ซึ่งอาจเหมาะสมกับโดเมนของคุณ:

```rust
for b in "Зд".bytes() {
    println!("{b}");
}
```

โค้ดนี้จะพิมพ์ 4 ไบต์ที่ประกอบขึ้นเป็นสตริงนี้:

```text
208
151
208
180
```

แต่อย่าลืมว่าค่าสเกลาร์ยูนิโคดที่ถูกต้องอาจประกอบขึ้นจากมากกว่า 1 ไบต์

การดึงกลุ่มกราฟีมออกจากสตริง เช่นในกรณีของอักษรเทวนาครีนั้นซับซ้อน ฟังก์ชันการทำงานนี้จึงไม่ได้ถูกจัดเตรียมไว้โดยไลบรารีมาตรฐาน เครต (crate) ต่างๆ มีอยู่บน [crates.io](https://crates.io/)<!-- ignore --> หากนี่คือฟังก์ชันการทำงานที่คุณต้องการ

### การจัดการความซับซ้อนของสตริง

สรุปแล้ว สตริงเป็นเรื่องซับซ้อน ภาษาโปรแกรมต่างๆ กันทำทางเลือกที่แตกต่างกันเกี่ยวกับวิธีนำเสนอความซับซ้อนนี้ต่อโปรแกรมเมอร์ Rust เลือกที่จะทำให้การจัดการข้อมูล `String` อย่างถูกต้องเป็นพฤติกรรมเริ่มต้นของโปรแกรม Rust ทุกโปรแกรม ซึ่งหมายความว่าโปรแกรมเมอร์ต้องครุ่นคิดมากขึ้นในการจัดการข้อมูล UTF-8 ตั้งแต่ต้น การแลกเปลี่ยนนี้เปิดเผยความซับซ้อนของสตริงมากกว่าที่ปรากฏชัดในภาษาโปรแกรมอื่น แต่ก็ช่วยให้คุณไม่ต้องคอยจัดการข้อผิดพลาดที่เกี่ยวข้องกับอักขระที่ไม่ใช่ ASCII ในภายหลังในวงจรชีวิตการพัฒนาของคุณ

ข่าวดีก็คือ ไลบรารีมาตรฐานมีฟังก์ชันการทำงานมากมายที่สร้างขึ้นบนชนิด `String` และ `&str` เพื่อช่วยจัดการสถานการณ์ที่ซับซ้อนเหล่านี้อย่างถูกต้อง อย่าลืมดูเอกสารประกอบสำหรับเมธอดที่มีประโยชน์ เช่น `contains` สำหรับค้นหาในสตริง และ `replace` สำหรับแทนที่บางส่วนของสตริงด้วยสตริงอื่น

มาหันไปดูสิ่งที่ซับซ้อนน้อยลงหน่อยกัน: แฮชแมป!
