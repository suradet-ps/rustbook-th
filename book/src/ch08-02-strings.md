## เก็บข้อความที่เข้ารหัส UTF-8 ด้วยสตริง

เราได้เคยพูดถึงสตริง (strings) กันไปบ้างแล้วในบทที่ 4 แต่ในหัวข้อนี้ เราจะมาเจาะลึกรายละเอียดการทำงานของมันกันอย่างจริงจัง ชาว Rustacean มือใหม่มักจะรู้สึกติดขัดและสับสนกับเรื่องสตริงอยู่บ่อยครั้ง ซึ่งเกิดจากปัจจัย 3 ประการรวมกัน ได้แก่: ความมุ่งมั่นของ Rust ที่พยายามเปิดเผยข้อผิดพลาดที่อาจเกิดขึ้นทั้งหมดออกมาตั้งแต่ต้น, ความจริงที่ว่าสตริงเป็นโครงสร้างข้อมูลที่มีความซับซ้อนมากกว่าที่โปรแกรมเมอร์หลายคนคิด และการเข้ารหัสแบบ UTF-8 ปัจจัยเหล่านี้เมื่อมารวมเข้าด้วยกัน จึงทำให้เรื่องสตริงดูยากขึ้น โดยเฉพาะอย่างยิ่งหากคุณย้ายมาจากภาษาโปรแกรมอื่นๆ

สาเหตุที่เรานำเรื่องสตริงมาพูดคุยในบริบทของคอลเลกชัน ก็เพราะว่าสตริงถูกอิมพลีเมนต์ขึ้นมาในฐานะคอลเลกชันของไบต์ ร่วมกับเมธอดอำนวยความสะดวกต่างๆ เพื่อช่วยจัดการเมื่อไบต์เหล่านั้นถูกนำมาตีความเป็นตัวอักษรหรือข้อความ ในหัวข้อนี้ เราจะมาเรียนรู้การดำเนินการพื้นฐานกับ `String` ที่พบได้ในคอลเลกชันทุกชนิด เช่น การสร้าง, การอัปเดต และการอ่านค่า นอกจากนี้ เรายังจะได้สำรวจข้อแตกต่างระหว่าง `String` กับคอลเลกชันอื่นๆ โดยเฉพาะอย่างยิ่ง เหตุใดการเข้าถึงข้อมูลผ่านดัชนี (indexing) ของ `String` จึงกลายเป็นเรื่องซับซ้อน อันเนื่องมาจากความแตกต่างระหว่างมุมมองของมนุษย์กับคอมพิวเตอร์ในการตีความข้อมูลสตริง

### การนิยามสตริง

อันดับแรก เรามานิยามความหมายของคำว่า _สตริง (string)_ ให้ตรงกันก่อน ในแก่นของภาษา Rust (core language) มีชนิดข้อมูลสตริงเพียงชนิดเดียวเท่านั้น นั่นคือสตริงสไลซ์ (string slice) `str` ซึ่งเรามักจะพบเห็นในรูปแบบที่ถูกยืมมาใช้งานคือ `&str` โดยในบทที่ 4 เราได้เรียนรู้แล้วว่า สตริงสไลซ์คือการอ้างอิง (reference) ไปยังข้อมูลสตริงที่เข้ารหัสแบบ UTF-8 ซึ่งถูกจัดเก็บไว้ที่อื่น ตัวอย่างเช่น สตริงลิเทอรัล (string literals) จะถูกฝังเก็บไว้ภายในไฟล์ไบนารีของตัวโปรแกรม ดังนั้นพวกมันจึงมีชนิดข้อมูลเป็นสตริงสไลซ์

ส่วนชนิดข้อมูล `String` นั้น เป็นสิ่งที่เตรียมไว้ให้โดยไลบรารีมาตรฐานของ Rust ไม่ได้ถูกฮาร์ดโค้ดไว้ในแก่นของตัวภาษา โดย `String` จะเป็นสตริงชนิดที่สามารถขยายขนาดได้, แก้ไขเปลี่ยนแปลงข้อมูลได้, เป็นเจ้าของข้อมูลในตัวเอง (owned) และเข้ารหัสด้วย UTF-8 เสมอ เมื่อชาว Rustacean พูดถึงคำว่า “สตริง” ในภาษา Rust จึงอาจหมายถึงชนิดข้อมูล `String` หรือสตริงสไลซ์ `&str` ตัวใดตัวหนึ่งก็ได้ และแม้ว่าเนื้อหาในหัวข้อนี้จะเน้นหนักไปที่ `String` เป็นหลัก แต่ทั้งสองชนิดต่างก็ถูกนำมาใช้งานอย่างหนักหน่วงในไลบรารีมาตรฐานของ Rust และทั้งคู่ต่างก็เข้ารหัสด้วย UTF-8 เหมือนกันทั้งสิ้น

สตริง `s3` จะมีข้อความเป็น `Hello, world!` สาเหตุที่ทำให้ `s1` ไม่สามารถนำมาใช้งานได้อีกต่อไปหลังจากการบวก และสาเหตุที่เราต้องส่งเรเฟอเรนซ์ของ `s2` เข้าไปนั้น มีความเกี่ยวข้องโดยตรงกับซิกเนเจอร์ของเมธอดที่ถูกเรียกทำงานเบื้องหลังเมื่อเราใช้ตัวดำเนินการ `+` โดยตัวดำเนินการ `+` จะเรียกใช้เมธอด `add` ซึ่งมีหน้าตาของซิกเนเจอร์ประมาณนี้:

```rust,ignore
fn add(self, s: &str) -> String {
```

ในไลบรารีมาตรฐานจริงๆ เมธอด `add` จะถูกนิยามขึ้นโดยใช้เจเนอริกและชนิดข้อมูลร่วม (associated types) แต่ในที่นี้เราแทนที่ด้วยชนิดข้อมูลรูปธรรมเพื่อให้เห็นภาพชัดเจน ซึ่งตรงกับสิ่งที่จะเกิดขึ้นเมื่อเราเรียกใช้เมธอดนี้กับค่าของ `String` (เราจะได้เรียนรู้เรื่องเจเนอริกในบทที่ 10) ซิกเนเจอร์นี้จะช่วยไขข้อข้องใจว่าเหตุใดตัวดำเนินการ `+` จึงมีพฤติกรรมเช่นนั้น

ประการแรก พารามิเตอร์ `s2` มีเครื่องหมาย `&` นำหน้า ซึ่งหมายความว่าเรากำลังนำเรเฟอเรนซ์ของสตริงตัวที่สองไปบวกเข้ากับสตริงตัวแรก นั่นเป็นไปตามที่กำหนดไว้ในพารามิเตอร์ `s` ของฟังก์ชัน `add`: นั่นคือเราสามารถนำสตริงสไลซ์มาบวกต่อท้าย `String` ได้เท่านั้น แต่ไม่สามารถนำค่า `String` สองตัวมาบวกกันตรงๆ ได้ ทว่าคุณอาจสังเกตว่าชนิดข้อมูลของ `&s2` จริงๆ แล้วคือ `&String` ไม่ใช่ `&str` ตามที่ระบุไว้ในพารามิเตอร์ตัวที่สองของ `add` แล้วเหตุใดโค้ดในลิสติ้ง 8-18 จึงคอมไพล์ผ่านได้ล่ะ?

สาเหตุที่เราสามารถส่ง `&s2` เข้าไปในการเรียก `add` ได้ เป็นเพราะคอมไพเลอร์สามารถแปลงค่าอาร์กิวเมนต์จาก `&String` ให้กลายเป็น `&str` ได้โดยอัตโนมัติ เมื่อเราเรียกเมธอด `add` ทาง Rust จะใช้กลไกที่เรียกว่า **deref coercion** ซึ่งในกรณีนี้จะช่วยแปลง `&s2` ให้กลายเป็น `&s2[..]` (เราจะได้พูดคุยเกี่ยวกับ deref coercion อย่างละเอียดในบทที่ 15) และเนื่องจาก `add` ไม่ได้ยึดสิทธิ์ความเป็นเจ้าของของพารามิเตอร์ `s` ไป ตัวแปร `s2` จึงยังคงเป็น `String` ที่สามารถนำไปใช้งานต่อได้ตามปกติหลังจากการบวกนี้

ประการที่สอง เมื่อสังเกตในซิกเนเจอร์ของฟังก์ชัน จะเห็นว่า `add` รับความเป็นเจ้าของของ `self` ไป เนื่องจากตัวแปร `self` _ไม่มี_ เครื่องหมาย `&` กำกับอยู่ ซึ่งหมายความว่าตัวแปร `s1` ในลิสติ้ง 8-18 จะถูกย้ายกรรมสิทธิ์ (moved) เข้าไปในฟังก์ชัน `add` และจะไม่สามารถนำมาใช้งานได้อีกต่อไปหลังจากนั้น ดังนั้น แม้ว่าคำสั่ง `let s3 = s1 + &s2;` จะดูเหมือนการคัดลอกสตริงทั้งสองตัวเพื่อสร้างสตริงตัวที่สามขึ้นมาใหม่ แต่ในความเป็นจริงแล้ว สเตตเมนต์นี้จะยึดเอา `s1` เข้าไป แล้วนำสำเนาของข้อความใน `s2` มาต่อท้าย จากนั้นจึงส่งมอบกรรมสิทธิ์ของผลลัพธ์กลับออกมา ซึ่งการทำเช่นนี้มีประสิทธิภาพในการทำงานสูงกว่าการสร้างและคัดลอกข้อมูลใหม่ทั้งหมดหลายเท่า

ดังนั้น คำตอบก็คือ เพื่อหลีกเลี่ยงการส่งค่าที่ไม่ตรงกับความคาดหวังกลับออกมา ซึ่งอาจกลายเป็นบั๊กที่ตรวจพบได้ยากในภายหลัง Rust จึงเลือกที่จะไม่อนุญาตให้คอมไพล์โค้ดประเภทนี้ผ่านเลยตั้งแต่แรก เพื่อช่วยตัดไฟแต่ต้นลมตั้งแต่ในขั้นตอนการพัฒนา

#### ไบต์ ค่าสเกลาร์ และกลุ่มกราฟีม

อีกประเด็นหนึ่งที่สำคัญเกี่ยวกับ UTF-8 ก็คือ ในมุมมองของภาษา Rust นั้น มีวิธีการมองข้อมูลสตริงที่เกี่ยวข้องอยู่ 3 มุมมองด้วยกัน: นั่นคือมองเป็น ไบต์ (bytes), มองเป็น ค่าสเกลาร์ (scalar values) และมองเป็น กลุ่มกราฟีม (grapheme clusters - ซึ่งเป็นสิ่งที่ใกล้เคียงกับคำว่า _ตัวอักษร_ ในสายตามนุษย์มากที่สุด)

หากเราลองดูคำในภาษาฮินดีว่า “नमस्ते” ซึ่งเขียนด้วยอักษรเทวนาครี มันจะถูกจัดเก็บไว้ในหน่วยความจำเป็นเวกเตอร์ของค่า `u8` ดังนี้:

```text
[224, 164, 168, 224, 164, 174, 224, 164, 184, 224, 165, 141, 224, 164, 164,
224, 165, 135]
```

รวมทั้งหมด 18 ไบต์ และนี่คือรูปแบบที่คอมพิวเตอร์ใช้จัดเก็บข้อมูลนี้จริงๆ ในระดับล่าง แต่หากเรามองข้อมูลชุดนี้เป็นค่าสเกลาร์ยูนิโคด ซึ่งตรงกับชนิดข้อมูล `char` ของ Rust ไบต์เหล่านั้นจะถูกแปลงออกมาได้ดังนี้:

```text
['न', 'म', 'स', '्', 'त', 'े']
```

ตรงนี้จะมีค่า `char` ทั้งหมด 6 ตัว แต่ตัวที่ 4 และตัวที่ 6 ไม่ใช่ตัวพยัญชนะเดี่ยวๆ: หากแต่เป็นเครื่องหมายวรรณยุกต์หรือสระผสม (diacritics) ที่ไม่สามารถสื่อความหมายได้ด้วยตัวเอง และสุดท้าย หากเรามองพวกมันในฐานะกลุ่มกราฟีม (grapheme clusters) เราก็จะได้สิ่งที่มนุษย์ทั่วไปมองเห็นเป็นตัวอักษร 4 ตัวที่ประกอบกันเป็นคำภาษาฮินดีนี้:

```text
["न", "म", "स्", "ते"]
```

Rust ได้จัดเตรียมวิธีการตีความข้อมูลสตริงดิบที่คอมพิวเตอร์จัดเก็บไว้ในหลากหลายมุมมอง เพื่อให้แต่ละโปรแกรมสามารถเลือกวิธีการตีความที่เหมาะสมกับความต้องการของตนเองได้ ไม่ว่าข้อมูลนั้นจะเขียนขึ้นด้วยภาษาใดในโลกก็ตาม

และเหตุผลประการสุดท้ายที่ Rust ไม่อนุญาตให้เราเข้าถึงตัวอักษรใน `String` ผ่านดัชนีได้ ก็คือ โดยทั่วไปแล้วการเข้าถึงผ่านดัชนีจะถูกคาดหวังว่าต้องใช้เวลาคงที่ระดับ O(1) เสมอ แต่สำหรับ `String` นั้น Rust ไม่สามารถการันตีประสิทธิภาพระดับดังกล่าวได้เลย เพราะ Rust จะต้องคอยไล่อ่านข้อมูลตั้งแต่ต้นข้อความไปจนถึงตำแหน่งดัชนี เพื่อตรวจสอบว่ามีตัวอักษรที่สมบูรณ์อยู่กี่ตัว

### การสไลซ์สตริง

การเข้าถึงข้อมูลในสตริงด้วยดัชนีมักเป็นแนวทางที่ไม่ดี เพราะไม่สามารถระบุได้อย่างชัดเจนว่าผลลัพธ์ที่ได้ควรเป็นชนิดข้อมูลใด: จะเป็นค่าไบต์, ตัวอักษร, กลุ่มกราฟีม หรือสตริงสไลซ์กันแน่ ดังนั้น หากคุณมีความจำเป็นต้องใช้ดัชนีเพื่อตัดแบ่งสตริงสไลซ์จริงๆ Rust จึงบังคับให้คุณต้องระบุอย่างเฉพาะเจาะจงมากยิ่งขึ้น

แทนที่จะใช้เครื่องหมายก้ามปู `[]` กับตัวเลขเดี่ยวๆ คุณสามารถใช้ `[]` ร่วมกับช่วง (range) เพื่อตัดแบ่งสตริงสไลซ์ที่ครอบคลุมช่วงของไบต์ที่ต้องการออกมาได้:

```rust
let hello = "Здравствуйте";

let s = &hello[0..4];
```

ในตัวอย่างนี้ `s` จะมีชนิดข้อมูลเป็น `&str` ที่บรรจุข้อมูล 4 ไบต์แรกของข้อความ และเนื่องจากเราทราบมาก่อนหน้านี้แล้วว่าอักษรแต่ละตัวในข้อความนี้ใช้พื้นที่ 2 ไบต์ นั่นหมายความว่าค่าของ `s` ก็คือ `Зд`

### การวนซ้ำบนสตริง

วิธีที่ดีที่สุดในการจัดการกับส่วนประกอบย่อยๆ ของสตริง คือการระบุอย่างชัดเจนว่าคุณต้องการแยกเป็นรายตัวอักษรหรือแยกเป็นรายไบต์ หากคุณต้องการทำงานกับค่าสเกลาร์ยูนิโคดแต่ละตัว ให้เรียกใช้เมธอด `chars` โดยการเรียก `chars` บนข้อความ “Зд” จะแยกและส่งค่าชนิด `char` 2 ตัวกลับออกมา ซึ่งคุณสามารถวนลูปเพื่อเข้าถึงสมาชิกแต่ละตัวได้ดังนี้:

```rust
for c in "Зд".chars() {
    println!("{c}");
}
```

โค้ดนี้จะพิมพ์ผลลัพธ์ออกมาดังนี้:

```text
З
д
```

หรืออีกทางเลือกหนึ่ง หากงานของคุณต้องการข้อมูลในระดับไบต์ดิบ เมธอด `bytes` ก็จะส่งแต่ละไบต์กลับออกมา ซึ่งอาจเหมาะสมกับโดเมนงานของคุณมากกว่า:

```rust
for b in "Зд".bytes() {
    println!("{b}");
}
```

โค้ดนี้จะพิมพ์ค่าทั้ง 4 ไบต์ที่ประกอบกันเป็นข้อความนี้ออกมา:

```text
208
151
208
180
```

แต่โปรดจำไว้เสมอว่า ค่าสเกลาร์ยูนิโคดที่ถูกต้องหนึ่งตัว อาจประกอบขึ้นจากข้อมูลมากกว่า 1 ไบต์

ส่วนการดึงข้อมูลออกมาเป็นกลุ่มกราฟีม (grapheme clusters) จากสตริง เช่น ในกรณีของอักษรเทวนาครีนั้น มีความซับซ้อนอย่างมาก ไลบรารีมาตรฐานของ Rust จึงไม่ได้รวมฟังก์ชันการทำงานนี้ไว้ในตัว แต่คุณสามารถค้นหาเครตที่มีฟังก์ชันดังกล่าวมาใช้งานได้จาก [crates.io](https://crates.io/)<!-- ignore --> หากโปรเจกต์ของคุณต้องการความสามารถนี้

### การจัดการความซับซ้อนของสตริง

โดยสรุปแล้ว เรื่องของสตริงนั้นมีความซับซ้อนอย่างยิ่ง ภาษาโปรแกรมแต่ละภาษาต่างก็เลือกแนวทางในการนำเสนอความซับซ้อนนี้แก่โปรแกรมเมอร์แตกต่างกันไป แต่สำหรับภาษา Rust นั้น ได้เลือกที่จะให้ความถูกต้องแม่นยำในการจัดการข้อมูล `String` เป็นพฤติกรรมเริ่มต้นของโปรแกรมทุกโปรแกรม ซึ่งหมายความว่าโปรแกรมเมอร์จะต้องใส่ใจและคิดทบทวนเกี่ยวกับการจัดการข้อมูล UTF-8 อย่างรอบคอบตั้งแต่ขั้นตอนแรก แม้ว่าการแลกเปลี่ยนนี้จะทำให้เราต้องเผชิญกับความซับซ้อนของสตริงอย่างตรงไปตรงมามากกว่าภาษาอื่นๆ แต่ก็ช่วยป้องกันไม่ให้คุณต้องไปปวดหัวกับข้อผิดพลาดที่เกี่ยวกับอักขระที่ไม่ใช่ ASCII ในช่วงท้ายของการพัฒนาซอฟต์แวร์

และข่าวดีก็คือ ไลบรารีมาตรฐานของ Rust ได้จัดเตรียมฟังก์ชันและเมธอดที่มีประโยชน์มากมายที่สร้างขึ้นบนชนิดข้อมูล `String` และ `&str` เพื่อช่วยให้คุณสามารถจัดการกับสถานการณ์ที่ซับซ้อนเหล่านี้ได้อย่างถูกต้องและปลอดภัย อย่าลืมศึกษาเอกสารประกอบเพื่อค้นหาเมธอดดีๆ เช่น `contains` สำหรับค้นหาข้อความภายในสตริง หรือ `replace` สำหรับแทนที่ข้อความบางส่วนด้วยข้อความอื่น

คราวนี้ เราลองมาดูคอลเลกชันอีกตัวที่มีความซับซ้อนน้อยกว่ากันดีกว่า: นั่นคือ แฮชแมป (hash maps)!
