## ทุกจุดที่ใช้แพตเทิร์นได้

แพตเทิร์นปรากฏอยู่ในหลายจุดทั่วทั้งภาษา Rust และความจริงแล้วคุณอาจได้ใช้งานมันมาบ่อยครั้งโดยไม่รู้ตัว! หัวข้อนี้จะพาไปสำรวจทุกตำแหน่งในโค้ดที่สามารถนำแพตเทิร์นไปใช้งานได้

### อาร์มของ `match`

ดังที่เราได้พูดคุยกันในบทที่ 6 เราใช้แพตเทิร์นในอาร์ม (arm) ของนิพจน์ `match` โดยตามรูปแบบโครงสร้างแล้ว นิพจน์ `match` ถูกนิยามขึ้นจากคีย์เวิร์ด `match`, ค่าที่ต้องการนำมาเปรียบเทียบจับคู่ และอาร์มของ match อย่างน้อยหนึ่งอาร์มขึ้นไป ซึ่งแต่ละอาร์มจะประกอบด้วยแพตเทิร์นและนิพจน์ที่จะถูกประมวลผล หากค่านั้นจับคู่กับแพตเทิร์นของอาร์มดังกล่าวได้สำเร็จ ดังนี้:

<!--
  Manually formatted rather than using Markdown intentionally: Markdown does not
  support italicizing code in the body of a block like this!
-->

<pre><code>match <em>VALUE</em> {
    <em>PATTERN</em> => <em>EXPRESSION</em>,
    <em>PATTERN</em> => <em>EXPRESSION</em>,
    <em>PATTERN</em> => <em>EXPRESSION</em>,
}</code></pre>

ตัวอย่างเช่น นี่คือนิพจน์ `match` จากลิสติ้ง 6-5 ที่จับคู่กับค่า `Option<i32>` ในตัวแปร `x`:

```rust,ignore
match x {
    None => None,
    Some(i) => Some(i + 1),
}
```

แพตเทิร์นในนิพจน์ `match` นี้คือ `None` และ `Some(i)` ซึ่งอยู่ทางด้านซ้ายของลูกศรในแต่ละบรรทัด

ข้อกำหนดสำคัญประการหนึ่งของนิพจน์ `match` คือ มันต้องครอบคลุมครบถ้วนทุกกรณี (exhaustive) ซึ่งหมายความว่า ทุกความเป็นไปได้ของค่าในนิพจน์ `match` จะต้องถูกนำมาพิจารณาและจัดการทั้งหมด วิธีหนึ่งที่จะช่วยรับประกันว่าคุณได้ครอบคลุมครบทุกกรณีแล้ว คือการมีแพตเทิร์นแบบครอบคลุมทั้งหมด (catch-all pattern) ไว้ในอาร์มสุดท้าย ตัวอย่างเช่น การใช้ชื่อตัวแปรที่สามารถจับคู่กับค่าใด ๆ ก็ได้ ซึ่งไม่มีวันจับคู่ล้มเหลว จึงช่วยเก็บตกทุกกรณีที่เหลืออยู่ได้ทั้งหมด

โดยเฉพาะแพตเทิร์น `_` นั้นจะสามารถจับคู่ได้กับทุกค่า แต่จะไม่ผูกค่านั้นเข้ากับตัวแปรใด ๆ จึงมักนิยมนำมาใช้ในอาร์มสุดท้ายของ match ตัวอย่างเช่น แพตเทิร์น `_` จะมีประโยชน์อย่างยิ่งเมื่อคุณต้องการเพิกเฉยต่อค่าอื่น ๆ ทั้งหมดที่ไม่ได้ระบุไว้ เราจะอธิบายรายละเอียดของแพตเทิร์น `_` เพิ่มเติมในหัวข้อ [“การเพิกเฉยต่อค่าในแพตเทิร์น”][ignoring-values-in-a-pattern]<!-- ignore --> ในช่วงท้ายของบทนี้

### สเตตเมนต์ `let`

ก่อนจะถึงบทนี้ เราได้พูดถึงการใช้แพตเทิร์นกับ `match` และ `if let` เป็นหลัก แต่ความจริงแล้ว เรายังใช้แพตเทิร์นในจุดอื่น ๆ อีกด้วย รวมถึงในสเตตเมนต์ (statement) `let` ตัวอย่างเช่น ลองพิจารณาการกำหนดค่าตัวแปรแบบเรียบง่ายด้วย `let` ต่อไปนี้:

```rust
let x = 5;
```

ทุกครั้งที่คุณใช้สเตตเมนต์ `let` เช่นนี้ คุณกำลังใช้งานแพตเทิร์นอยู่ แม้คุณอาจจะไม่ทันสังเกตก็ตาม! โดยตามโครงสร้างที่เป็นทางการแล้ว สเตตเมนต์ `let` จะมีรูปแบบดังนี้:

<!--
  Manually formatted rather than using Markdown intentionally: Markdown does not
  support italicizing code in the body of a block like this!
-->

<pre>
<code>let <em>PATTERN</em> = <em>EXPRESSION</em>;</code>
</pre>

ในสเตตเมนต์อย่าง `let x = 5;` ที่มีชื่อตัวแปรอยู่ในตำแหน่ง PATTERN นั้น ชื่อตัวแปรก็เป็นเพียงรูปแบบหนึ่งของแพตเทิร์นที่เรียบง่ายมาก โดย Rust จะเปรียบเทียบนิพจน์ทางขวากับแพตเทิร์นทางซ้าย แล้วผูกค่าเข้ากับชื่อตัวแปรทั้งหมดที่พบ ดังนั้นในตัวอย่าง `let x = 5;` ตัว `x` จึงเป็นแพตเทิร์นที่มีความหมายว่า "จงผูกค่าที่จับคู่ได้ตรงนี้เข้ากับตัวแปร `x`" และเพราะชื่อ `x` เป็นตัวแทนของแพตเทิร์นทั้งหมด มันจึงหมายถึง "ผูกค่าทุกอย่างเข้ากับตัวแปร `x` ไม่ว่าค่านั้นจะเป็นอะไรก็ตาม"

เพื่อให้เห็นภาพของการจับคู่แพตเทิร์น (pattern matching) ใน `let` ได้ชัดเจนยิ่งขึ้น ลองพิจารณาลิสติ้ง 19-1 ซึ่งใช้แพตเทิร์นร่วมกับ `let` เพื่อแยกส่วนโครงสร้างข้อมูล (destructure) ของทูเพิล

### เอ็กซ์เพรสชัน `if let` แบบมีเงื่อนไข

ในบทที่ 6 เราได้อธิบายการใช้งานนิพจน์ `if let` โดยหลักแล้วเพื่อเป็นวิธีเขียนแบบสั้นที่เทียบเท่ากับ `match` ที่ต้องการจับคู่เพียงกรณีเดียว นอกจากนี้ `if let` ยังสามารถมีบล็อก `else` ควบคู่กัน ซึ่งบรรจุโค้ดที่จะทำงานเมื่อแพตเทิร์นใน `if let` จับคู่ไม่สำเร็จ

ลิสติ้ง 19-3 แสดงให้เห็นว่าเราสามารถนำนิพจน์ `if let`, `else if` และ `else if let` มาผสมผสานเข้าด้วยกันได้ ซึ่งจะให้ความยืดหยุ่นมากกว่านิพจน์ `match` ที่กำหนดให้เราส่งค่าเข้าเปรียบเทียบกับแพตเทิร์นได้เพียงค่าเดียว ยิ่งไปกว่านั้น Rust ไม่ได้บังคับว่าเงื่อนไขในสายของ `if let`, `else if` และ `else if let` จะต้องมีความเกี่ยวข้องกันแต่อย่างใด

โค้ดในลิสติ้ง 19-3 จะตัดสินใจเลือกว่าสีพื้นหลังควรเป็นสีอะไร โดยตรวจสอบเงื่อนไขหลายประการต่อเนื่องกัน สำหรับตัวอย่างนี้ เราได้สร้างตัวแปรที่กำหนดค่าคงที่ไว้ล่วงหน้า (hardcode) ซึ่งในโปรแกรมจริงอาจเป็นค่าที่ได้รับมาจากผู้ใช้

โครงสร้างเงื่อนไขแบบนี้ช่วยให้เรารองรับความต้องการที่ซับซ้อนได้เป็นอย่างดี จากค่าที่กำหนดไว้ในตัวอย่างนี้ โปรแกรมจะพิมพ์ `Using purple as the background color`

คุณจะสังเกตเห็นว่า `if let` สามารถประกาศตัวแปรใหม่ที่บดบัง (shadow) ตัวแปรเดิมที่มีอยู่ได้ในลักษณะเดียวกับอาร์มของ `match`: เช่นในบรรทัด `if let Ok(age) = age` จะสร้างตัวแปร `age` ตัวใหม่ขึ้นมาเพื่อเก็บค่าที่อยู่ภายในวาเรียนต์ `Ok` ซึ่งจะไปบดบังตัวแปร `age` ตัวเดิม สิ่งนี้ทำให้เราต้องวางเงื่อนไข `if age > 30` ไว้ภายในบล็อกนั้น: เราไม่สามารถรวมเงื่อนไขทั้งสองเข้าด้วยกันเป็น `if let Ok(age) = age && age > 30` ได้ เพราะตัวแปร `age` ตัวใหม่ที่เราต้องการนำไปเปรียบเทียบกับ 30 จะยังไม่มีผลให้เรียกใช้ได้ จนกว่าจะเริ่มขอบเขตการทำงาน (scope) ใหม่หลังวงเล็บปีกกาเปิด

ข้อเสียของการใช้นิพจน์ `if let` คือคอมไพเลอร์จะไม่ช่วยตรวจสอบความครอบคลุมทุกกรณี (exhaustiveness) เหมือนอย่างที่ทำให้นิพจน์ `match` หากเราละเว้นบล็อก `else` สุดท้ายไปจนทำให้ตกหล่นบางกรณี คอมไพเลอร์จะไม่สามารถแจ้งเตือนให้เราทราบถึงบั๊กทางตรรกะที่อาจเกิดขึ้นได้

นอกจากนี้ เรายังสามารถใช้แพตเทิร์นในรายการพารามิเตอร์ของโคลเชอร์ (closure) ได้ในทำนองเดียวกับพารามิเตอร์ของฟังก์ชัน เพราะโคลเชอร์มีลักษณะคล้ายคลึงกับฟังก์ชันดังที่เราได้พูดคุยกันไปในบทที่ 13
