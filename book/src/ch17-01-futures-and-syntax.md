## ฟิวเจอร์และวากยสัมพันธ์ async

องค์ประกอบสำคัญของการเขียนโปรแกรมแบบอะซิงโครนัส (asynchronous programming) ใน Rust คือ_ฟิวเจอร์_ (future) และคำสงวน `async` และ `await` ของ Rust

_ฟิวเจอร์_ คือค่าที่อาจยังไม่พร้อมในตอนนี้แต่จะพร้อม ณ จุดหนึ่งในอนาคต (แนวคิดเดียวกันนี้ปรากฏในหลายภาษา บางครั้งใช้ชื่ออื่นเช่น _ทาสก์_ (task) หรือ _พรอมิส_ (promise)) Rust มีเทรต (trait) `Future` ให้เป็นชิ้นส่วนพื้นฐานเพื่อให้การดำเนินการแบบอะซิงโครนัสต่างๆ สามารถอิมพลีเมนต์ได้ด้วยโครงสร้างข้อมูลที่แตกต่างกันแต่มีอินเทอร์เฟซร่วมกัน ใน Rust ฟิวเจอร์คือชนิดข้อมูลที่อิมพลีเมนต์เทรต `Future` ฟิวเจอร์แต่ละตัวเก็บข้อมูลของตัวเองเกี่ยวกับความคืบหน้าที่เกิดขึ้นแล้วและความหมายของคำว่า “พร้อม”

คุณสามารถใช้คำสงวน `async` กับบล็อกและฟังก์ชันเพื่อระบุว่าพวกมันสามารถถูกขัดจังหวะและกลับมาทำต่อได้ ภายในบล็อก async หรือฟังก์ชัน async คุณสามารถใช้คำสงวน `await` เพื่อ_รอฟิวเจอร์_ (นั่นคือ รอให้มันพร้อม) จุดใดก็ตามที่คุณ await ฟิวเจอร์ภายในบล็อกหรือฟังก์ชัน async เป็นจุดที่บล็อกหรือฟังก์ชันนั้นอาจหยุดชั่วคราวและกลับมาทำต่อ กระบวนการตรวจสอบกับฟิวเจอร์ว่าค่าของมันพร้อมใช้งานหรือยังเรียกว่า_การโพลล์_ (polling)

ภาษาอื่นบางภาษา เช่น C# และ JavaScript ก็ใช้คำสงวน `async` และ `await` สำหรับการเขียนโปรแกรมแบบ async เช่นกัน หากคุณคุ้นเคยกับภาษาเหล่านั้น คุณอาจสังเกตเห็นความแตกต่างที่มีนัยสำคัญบางประการในวิธีที่ Rust จัดการวากยสัมพันธ์นั้น นั่นมีเหตุผลที่ดีทีเดียว ดังที่เราจะได้เห็นกัน!

เมื่อเขียน Rust แบบ async เราใช้คำสงวน `async` และ `await` เกือบตลอดเวลา Rust คอมไพล์พวกมันเป็นโค้ดที่เทียบเท่ากันโดยใช้เทรต `Future` คล้ายกับที่มันคอมไพล์ลูป `for` เป็นโค้ดที่เทียบเท่ากันโดยใช้เทรต `Iterator` อย่างไรก็ตาม เพราะ Rust มีเทรต `Future` คุณจึงสามารถอิมพลีเมนต์มันสำหรับชนิดข้อมูลของคุณเองได้เมื่อจำเป็น ฟังก์ชันหลายตัวที่เราจะเห็นตลอดบทนี้คืนค่าชนิดข้อมูลที่มีการอิมพลีเมนต์ `Future` เป็นของตัวเอง เราจะกลับมาที่นิยามของเทรตนี้ตอนท้ายบทและเจาะลึกว่ามันทำงานอย่างไรอีกมาก แต่นี่ก็เป็นรายละเอียดเพียงพอที่จะพาเราไปต่อได้

ทั้งหมดนี้อาจรู้สึกนามธรรมไปสักหน่อย ดังนั้นมาเขียนโปรแกรม async โปรแกรมแรกของเรากัน: เว็บสแครปเปอร์เล็กๆ เราจะส่ง URL สองรายการผ่านบรรทัดคำสั่ง ดึงข้อมูลทั้งสองรายการมาพร้อมกัน และคืนผลลัพธ์ของรายการที่เสร็จก่อน ตัวอย่างนี้จะมีวากยสัมพันธ์ใหม่พอสมควร แต่ไม่ต้องกังวล—เราจะอธิบายทุกอย่างที่คุณจำเป็นต้องรู้ไปตามทาง

## โปรแกรม async โปรแกรมแรกของเรา

เพื่อให้จุดสนใจของบทนี้อยู่ที่การเรียนรู้ async มากกว่าการวุ่นอยู่กับชิ้นส่วนต่างๆ ของระบบนิเวศ เราได้สร้างเครต `trpl` ขึ้น (`trpl` ย่อมาจาก “The Rust Programming Language”) มันส่งออกชนิดข้อมูล เทรต และฟังก์ชันทั้งหมดที่คุณจะต้องใช้อีกครั้ง โดยส่วนใหญ่มาจากเครต [`futures`][futures-crate]<!-- ignore --> และ [`tokio`][tokio]<!-- ignore --> เครต `futures` เป็นบ้านอย่างเป็นทางการสำหรับการทดลองกับโค้ด async ใน Rust และจริงๆ แล้วเป็นที่ที่เทรต `Future` ถูกออกแบบขึ้นแต่แรก Tokio เป็นรันไทม์ (runtime) แบบ async ที่ใช้กันอย่างแพร่หลายที่สุดใน Rust ทุกวันนี้ โดยเฉพาะสำหรับเว็บแอปพลิเคชัน ยังมีรันไทม์อื่นๆ ที่ยอดเยี่ยมอีก และอาจเหมาะกับวัตถุประสงค์ของคุณมากกว่า เราใช้เครต `tokio` อยู่เบื้องหลังของ `trpl` เพราะมันผ่านการทดสอบมาอย่างดีและถูกใช้อย่างแพร่หลาย

ในบางกรณี `trpl` ยังเปลี่ยนชื่อหรือห่อ API ต้นฉบับเพื่อให้คุณจดจ่อกับรายละเอียดที่เกี่ยวข้องกับบทนี้ หากคุณต้องการเข้าใจว่าเครตนี้ทำอะไร เราขอแนะนำให้ดู[ซอร์สโค้ดของมัน][crate-source] คุณจะเห็นได้ว่าการส่งออกซ้ำแต่ละรายการมาจากเครตใด และเราได้ทิ้งคอมเมนต์ไว้มากมายเพื่ออธิบายว่าเครตนี้ทำอะไร

สร้างโปรเจกต์ไบนารีใหม่ชื่อ `hello-async` และเพิ่มเครต `trpl` เป็นดีเพนเดนซี:

```console
$ cargo new hello-async
$ cd hello-async
$ cargo add trpl
```

ตอนนี้เราสามารถใช้ชิ้นส่วนต่างๆ ที่ `trpl` จัดเตรียมไว้เพื่อเขียนโปรแกรม async โปรแกรมแรกของเราได้ เราจะสร้างเครื่องมือบรรทัดคำสั่งเล็กๆ ที่ดึงเว็บเพจสองหน้า ดึงเอลิเมนต์ `<title>` จากแต่ละหน้า และพิมพ์ชื่อเรื่องของเพจที่ทำกระบวนการทั้งหมดนั้นเสร็จก่อน

เราต้อง await ฟิวเจอร์ทั้งสองตัวนี้อย่างชัดเจน เพราะฟิวเจอร์ใน Rust เป็นแบบ_เลซี่_: พวกมันไม่ทำอะไรเลยจนกว่าคุณจะสั่งให้มันทำด้วยคำสงวน `await` (อันที่จริง Rust จะแสดงคำเตือนจากคอมไพเลอร์หากคุณไม่ใช้ฟิวเจอร์) สิ่งนี้อาจทำให้คุณนึกถึงการอภิปรายเรื่องอิเทอเรเตอร์ (iterator) ในหัวข้อ[“ประมวลผลลำดับรายการด้วยอิเทอเรเตอร์”][iterators-lazy]<!-- ignore --> ในบทที่ 13 อิเทอเรเตอร์ไม่ทำอะไรเลยจนกว่าคุณจะเรียกเมธอด `next` ของมัน—ไม่ว่าจะโดยตรงหรือโดยใช้ลูป `for` หรือเมธอดอย่าง `map` ที่ใช้ `next` อยู่เบื้องหลัง ในทำนองเดียวกัน ฟิวเจอร์ก็ไม่ทำอะไรเลยจนกว่าคุณจะสั่งให้มันทำอย่างชัดเจน ความเลซี่นี้ทำให้ Rust หลีกเลี่ยงการรันโค้ด async จนกว่าจะจำเป็นจริงๆ

> หมายเหตุ: สิ่งนี้แตกต่างจากพฤติกรรมที่เราเห็นเมื่อใช้ `thread::spawn` ในหัวข้อ[“การสร้างเธรดใหม่ด้วย spawn”][thread-spawn]<!-- ignore --> ในบทที่ 16 ซึ่งโคลเชอร์ (closure) ที่เราส่งให้เธรด (thread) อื่นเริ่มทำงานทันที มันยังแตกต่างจากวิธีที่ภาษาอื่นๆ จำนวนมากเข้ามาจัดการ async แต่สิ่งสำคัญคือ Rust ต้องสามารถมอบการรับประกันด้านประสิทธิภาพของมันได้ เช่นเดียวกับที่ทำได้กับอิเทอเรเตอร์

เมื่อเราได้ `response_text` มาแล้ว เราสามารถแยกวิเคราะห์มันเป็นอินสแตนซ์ (instance) ของชนิด `Html` ได้โดยใช้ `Html::parse` แทนที่จะเป็นสตริงดิบ ตอนนี้เรามีชนิดข้อมูลที่ใช้ทำงานกับ HTML ในฐานะโครงสร้างข้อมูลที่สมบูรณ์กว่าเดิม โดยเฉพาะอย่างยิ่ง เราสามารถใช้เมธอด `select_first` เพื่อค้นหาตัวอย่างแรกของ CSS ซีเล็กเตอร์ที่กำหนดได้ ด้วยการส่งสตริง `"title"` เราจะได้เอลิเมนต์ `<title>` ตัวแรกในเอกสาร หากมีอยู่ เพราะอาจไม่มีเอลิเมนต์ที่ตรงกันเลย `select_first` จึงคืนค่า `Option<ElementRef>` สุดท้าย เราใช้เมธอด `Option::map` ซึ่งให้เราทำงานกับสมาชิกใน `Option` หากมีอยู่ และไม่ทำอะไรเลยหากไม่มี (เราจะใช้เอ็กซ์เพรสชัน `match` ตรงนี้ก็ได้ แต่ `map` เป็นสำนวนมากกว่า) ในบอดี้ของฟังก์ชันที่เราส่งให้ `map` เราเรียก `inner_html` บน `title` เพื่อดึงเนื้อหาของมัน ซึ่งเป็น `String` เมื่อทุกอย่างเสร็จสิ้น เราจะได้ `Option<String>`

โปรดสังเกตว่าคำสงวน `await` ของ Rust อยู่_หลัง_เอ็กซ์เพรสชันที่คุณกำลัง await ไม่ใช่ก่อนหน้า นั่นคือ มันเป็นคำสงวนแบบ_postfix_ สิ่งนี้อาจแตกต่างจากสิ่งที่คุณเคยชินหากคุณเคยใช้ `async` ในภาษาอื่น แต่ใน Rust มันทำให้การเชื่อมเมธอดต่อกันทำงานได้สะดวกขึ้นมาก ด้วยเหตุนี้ เราจึงเปลี่ยนบอดี้ของ `page_title` ให้เชื่อมการเรียกฟังก์ชัน `trpl::get` และ `text` เข้าด้วยกันโดยมี `await` คั่นกลางได้ ดังแสดงในลิสติ้ง 17-2

เท่านี้เราก็เขียนฟังก์ชัน async ฟังก์ชันแรกของเราสำเร็จแล้ว! ก่อนที่เราจะเพิ่มโค้ดใน `main` เพื่อเรียกมัน มาพูดถึงสิ่งที่เราเขียนและความหมายของมันกันอีกสักหน่อย

เมื่อ Rust พบ_บล็อก_ที่ทำเครื่องหมายด้วยคำสงวน `async` มันจะคอมไพล์บล็อกนั้นเป็นชนิดข้อมูลนิรนามที่ไม่ซ้ำใครและอิมพลีเมนต์เทรต `Future` เมื่อ Rust พบ_ฟังก์ชัน_ที่ทำเครื่องหมายด้วย `async` มันจะคอมไพล์ฟังก์ชันนั้นเป็นฟังก์ชันที่ไม่ใช่ async ซึ่งมีบอดี้เป็นบล็อก async ชนิดที่คืนกลับของฟังก์ชัน async คือชนิดของข้อมูลนิรนามที่คอมไพเลอร์สร้างขึ้นสำหรับบล็อก async นั้น

ดังนั้น การเขียน `async fn` จึงเทียบเท่ากับการเขียนฟังก์ชันที่คืนค่า_ฟิวเจอร์_ของชนิดที่คืนกลับ สำหรับคอมไพเลอร์แล้ว นิยามฟังก์ชันอย่าง `async fn page_title` ในลิสติ้ง 17-1 นั้นเทียบเท่ากับฟังก์ชันที่ไม่ใช่ async ซึ่งนิยามแบบนี้โดยประมาณ:

```rust
# extern crate trpl; // required for mdbook test
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}
```

มาดูแต่ละส่วนของเวอร์ชันที่ถูกแปลงแล้วกัน:

- มันใช้ไวยากรณ์ `impl Trait` ที่เราอภิปรายไปแล้วในบทที่ 10 ในหัวข้อ[“การใช้เทรตเป็นพารามิเตอร์”][impl-trait]<!-- ignore -->
- ค่าที่ถูกคืนกลับอิมพลีเมนต์เทรต `Future` ด้วยชนิดข้อมูลที่เชื่อมโยง (associated type) ชื่อ `Output` โปรดสังเกตว่าชนิด `Output` คือ `Option<String>` ซึ่งเหมือนกับชนิดที่คืนกลับเดิมของเวอร์ชัน `async fn` ของ `page_title`
- โค้ดทั้งหมดที่ถูกเรียกในบอดี้ของฟังก์ชันต้นฉบับถูกห่อไว้ในบล็อก `async move` ย้อนนึกว่าบล็อกเป็นเอ็กซ์เพรสชัน บล็อกทั้งหมดนี้คือเอ็กซ์เพรสชันที่ถูกคืนกลับจากฟังก์ชัน
- บล็อก async นี้สร้างค่าที่มีชนิด `Option<String>` ตามที่เพิ่งอธิบายไป ค่านั้นตรงกับชนิด `Output` ในชนิดที่คืนกลับ นี่ก็เหมือนกับบล็อกอื่นๆ ที่คุณเคยเห็น
- บอดี้ของฟังก์ชันใหม่เป็นบล็อก `async move` เพราะวิธีที่มันใช้พารามิเตอร์ `url` (เราจะพูดถึง `async` กับ `async move` กันอีกมากในบทนี้)

ตอนนี้เราสามารถเรียก `page_title` ใน `main` ได้แล้ว

ภาษาโดยส่วนใหญ่ที่รองรับ async นั้นรวมรันไทม์มาให้ในตัว แต่ Rust ไม่ได้ทำเช่นนั้น ในทางกลับกัน มีรันไทม์แบบ async ที่แตกต่างกันมากมายให้เลือกใช้ ซึ่งแต่ละตัวก็มีการแลกเปลี่ยนที่แตกต่างกันให้เหมาะกับกรณีการใช้งานที่มันมุ่งเป้าไปที่ ตัวอย่างเช่น เว็บเซิร์ฟเวอร์ที่มีปริมาณงานสูง พร้อมแกน CPU จำนวนมากและ RAM ปริมาณมาก มีความต้องการที่แตกต่างอย่างมากจากไมโครคอนโทรลเลอร์ที่มีแกนเดียว RAM ปริมาณน้อย และไม่มีความสามารถในการจัดสรรหน่วยความจำบนฮีป เครตที่จัดเตรียมรันไทม์เหล่านั้นมักมีฟังก์ชันการทำงานทั่วไปเวอร์ชัน async เช่น I/O สำหรับไฟล์หรือเครือข่ายให้ด้วย

ในที่นี้ และตลอดบทที่เหลือ เราจะใช้ฟังก์ชัน `block_on` จากเครต `trpl` ซึ่งรับฟิวเจอร์เป็นอาร์กิวเมนต์และบล็อกเธรดปัจจุบันจนกว่าฟิวเจอร์นี้จะรันจนเสร็จ เบื้องหลังแล้ว การเรียก `block_on` จะตั้งค่ารันไทม์โดยใช้เครต `tokio` ซึ่งใช้รันฟิวเจอร์ที่ถูกส่งเข้ามา (พฤติกรรมของ `block_on` ในเครต `trpl` นั้นคล้ายกับฟังก์ชัน `block_on` ของเครตที่ให้รันไทม์อื่นๆ) เมื่อฟิวเจอร์เสร็จสิ้น `block_on` จะคืนค่าใดก็ตามที่ฟิวเจอร์สร้างขึ้น

เราจะส่งฟิวเจอร์ที่ `page_title` คืนกลับให้ `block_on` โดยตรงก็ได้ และเมื่อมันเสร็จสิ้น เราก็จะจับคู่กับ `Option<String>` ที่ได้ตามที่เราพยายามทำในลิสติ้ง 17-3 อย่างไรก็ตาม สำหรับตัวอย่างส่วนใหญ่ในบทนี้ (และโค้ด async ส่วนใหญ่ในโลกจริง) เราจะทำมากกว่าแค่เรียกฟังก์ชัน async ครั้งเดียว ดังนั้นเราจะส่งบล็อก `async` เข้าไปแทนและ await ผลลัพธ์ของการเรียก `page_title` อย่างชัดเจน ดังในลิสติ้ง 17-4

เราเริ่มด้วยการเรียก `page_title` สำหรับ URL แต่ละรายการที่ผู้ใช้ส่งมา เราบันทึกฟิวเจอร์ที่ได้เป็น `title_fut_1` และ `title_fut_2` ย้อนนึกว่าพวกมันยังไม่ทำอะไรเลย เพราะฟิวเจอร์เป็นแบบเลซี่และเรายังไม่ได้ await พวกมัน จากนั้นเราส่งฟิวเจอร์เหล่านั้นให้ `trpl::select` ซึ่งคืนค่าเพื่อบ่งชี้ว่าฟิวเจอร์ตัวใดที่ส่งให้มันเสร็จก่อน

> หมายเหตุ: เบื้องหลังแล้ว `trpl::select` สร้างขึ้นบนฟังก์ชัน `select` ที่ทั่วไปกว่าซึ่งนิยามในเครต `futures` ฟังก์ชัน `select` ของเครต `futures` ทำได้หลายอย่างที่ฟังก์ชัน `trpl::select` ทำไม่ได้ แต่ก็มีความซับซ้อนเพิ่มเติมบางอย่างที่เราข้ามไปได้ในตอนนี้

ฟิวเจอร์ตัวใดก็สามารถ “ชนะ” ได้อย่างถูกต้องตามกติกา การคืนค่า `Result` จึงไม่สมเหตุสมผล แทนที่จะเป็นเช่นนั้น `trpl::select` คืนค่าชนิดที่เราไม่เคยเห็นมาก่อน คือ `trpl::Either` ชนิด `Either` คล้ายกับ `Result` ตรงที่มีสองกรณี อย่างไรก็ตาม ต่างจาก `Result` ตรงที่ `Either` ไม่ได้ฝังแนวคิดเรื่องความสำเร็จหรือความล้มเหลวไว้เลย มันใช้ `Left` และ `Right` เพื่อบ่งชี้ว่า “อย่างใดอย่างหนึ่ง”:

```rust
enum Either<A, B> {
    Left(A),
    Right(B),
}
```

ฟังก์ชัน `select` จะคืนค่า `Left` พร้อมเอาต์พุตของฟิวเจอร์นั้นหากอาร์กิวเมนต์แรกชนะ และคืนค่า `Right` พร้อมเอาต์พุตของอาร์กิวเมนต์ฟิวเจอร์ตัวที่สองหากตัว_นั้น_ชนะ ซึ่งสอดคล้องกับลำดับที่อาร์กิวเมนต์ปรากฏเมื่อเรียกฟังก์ชัน: อาร์กิวเมนต์แรกอยู่ทางซ้ายของอาร์กิวเมนต์ที่สอง

เรายังอัปเดต `page_title` ให้คืน URL เดียวกันที่ถูกส่งเข้ามาด้วย วิธีนี้ หากเพจที่คืนค่าก่อนไม่มี `<title>` ที่เราแปลงได้ เราก็ยังพิมพ์ข้อความที่มีความหมายได้ เมื่อมีข้อมูลนั้นแล้ว เราก็ปิดท้ายด้วยการอัปเดตเอาต์พุตของ `println!` เพื่อบ่งชี้ทั้งว่า URL ใดเสร็จก่อน และ `<title>` ของเว็บเพจที่ URL นั้นคืออะไร หากมี

ตอนนี้คุณสร้างเว็บสแครปเปอร์เล็กๆ ที่ใช้งานได้แล้ว! ลองเลือก URL สักสองสามรายการแล้วรันเครื่องมือบรรทัดคำสั่งนี้ดู คุณอาจพบว่าไซต์บางแห่งเร็วกว่าแห่งอื่นอย่างสม่ำเสมอ ขณะที่ในกรณีอื่นๆ ไซต์ที่เร็วกว่าจะเปลี่ยนไปมาในแต่ละครั้งที่รัน ที่สำคัญยิ่งกว่านั้น คุณได้เรียนรู้พื้นฐานของการทำงานกับฟิวเจอร์แล้ว ตอนนี้เราจึงเจาะลึกได้มากขึ้นว่าเราทำอะไรกับ async ได้บ้าง
