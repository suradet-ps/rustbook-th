## เจาะลึกเทรตสำหรับ async

ตลอดบทนี้ เราได้ใช้เทรต (trait) `Future`, `Stream` และ `StreamExt` ในรูปแบบต่างๆ อย่างไรก็ตาม จนถึงตอนนี้เราได้หลีกเลี่ยงการลงลึกเกินไปในรายละเอียดว่าพวกมันทำงานอย่างไรหรือประกอบเข้าด้วยกันอย่างไร ซึ่งโดยปกติก็เพียงพอแล้วสำหรับงาน Rust ในชีวิตประจำวันของคุณ อย่างไรก็ตาม บางครั้งคุณจะเจอสถานการณ์ที่คุณจำเป็นต้องเข้าใจรายละเอียดเพิ่มเติมอีกเล็กน้อยของเทรตเหล่านี้ พร้อมกับชนิด `Pin` และเทรต `Unpin` ในหัวข้อนี้ เราจะเจาะลึกพอให้ช่วยในสถานการณ์เหล่านั้น โดยยังคงเหลือการดำดิ่ง_ลึกจริงๆ_ ไว้ให้เอกสารอื่นๆ

### เทรต `Future`

มาเริ่มด้วยการพิจารณาใกล้ชิดขึ้นว่าเทรต `Future` ทำงานอย่างไร นี่คือวิธีที่ Rust นิยามมัน:

```rust
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

คำนิยามเทรตนั้นมีชนิดข้อมูลใหม่ๆ หลายอย่างรวมอยู่ด้วย และยังมีวากยสัมพันธ์บางอย่างที่เราไม่เคยเห็นมาก่อน ดังนั้นมาพิจารณาคำนิยามนี้ทีละส่วนกัน

อย่างแรก ชนิดที่เชื่อมโยง (associated type) `Output` ของ `Future` บอกว่าฟิวเจอร์ (future) คลี่คลายเป็นอะไร สิ่งนี้เทียบได้กับชนิดที่เชื่อมโยง `Item` ของเทรต `Iterator` อย่างที่สอง `Future` มีเมธอด `poll` ซึ่งรับเรเฟอเรนซ์ (reference) `Pin` แบบพิเศษเป็นพารามิเตอร์ `self` และรับเรเฟอเรนซ์แบบเปลี่ยนแปลงได้ไปยังชนิด `Context` แล้วคืนค่า `Poll<Self::Output>` เราจะพูดถึง `Pin` และ `Context` กันมากขึ้นอีกสักครู่ ตอนนี้มาดูที่สิ่งที่เมธอดคืนกลับ นั่นคือชนิด `Poll`:

```rust
pub enum Poll<T> {
    Ready(T),
    Pending,
}
```

ชนิด `Poll` นี้คล้ายกับ `Option` มันมีวาเรียนต์ (variant) หนึ่งที่มีค่า `Ready(T)` และอีกหนึ่งที่ไม่มีค่า `Pending` อย่างไรก็ตาม `Poll` มีความหมายที่ต่างจาก `Option` อย่างมาก! วาเรียนต์ `Pending` บ่งชี้ว่าฟิวเจอร์ยังมีงานต้องทำอยู่ ผู้เรียกจึงต้องตรวจสอบอีกครั้งในภายหลัง วาเรียนต์ `Ready` บ่งชี้ว่า `Future` ทำงานเสร็จแล้วและค่า `T` พร้อมใช้งาน

> หมายเหตุ: เป็นเรื่องหายากที่เราจะต้องเรียก `poll` โดยตรง แต่ถ้าคุณจำเป็นต้องเรียกจริงๆ
> พึงระลึกไว้ว่าสำหรับฟิวเจอร์ส่วนใหญ่ ผู้เรียกไม่ควรเรียก `poll` อีกครั้งหลังจาก
> ฟิวเจอร์คืนค่า `Ready` แล้ว ฟิวเจอร์หลายตัวจะแพนิกหากถูกโพลล์อีกครั้งหลังจากที่
> พร้อมแล้ว ฟิวเจอร์ที่ปลอดภัยต่อการโพลล์ซ้ำจะระบุไว้อย่างชัดเจนในเอกสารของมัน
> สิ่งนี้คล้ายกับพฤติกรรมของ `Iterator::next`

เมื่อคุณเห็นโค้ดที่ใช้ `await` เบื้องหลังแล้ว Rust คอมไพล์มันเป็นโค้ดที่เรียก `poll` หากคุณย้อนกลับไปดูลิสติ้ง 17-4 ซึ่งเราพิมพ์ชื่อเรื่องของเพจสำหรับ URL เดียวเมื่อมันคลี่คลายแล้ว Rust จะคอมไพล์มันเป็นอะไรบางอย่างที่ประมาณ (แม้จะไม่ใช่เป๊ะๆ) แบบนี้:

```rust,ignore
match page_title(url).poll() {
    Ready(page_title) => match page_title {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
    Pending => {
        // But what goes here?
    }
}
```

เมื่อฟิวเจอร์ยัง `Pending` อยู่ เราควรทำอย่างไร? เราจำเป็นต้องมีวิธีลองใหม่ ซ้ำแล้วซ้ำอีก จนกระทั่งฟิวเจอร์พร้อมในที่สุด หรือพูดอีกนัยหนึ่ง เราจำเป็นต้องมีลูป:

```rust,ignore
let mut page_title_fut = page_title(url);
loop {
    match page_title_fut.poll() {
        Ready(value) => match page_title {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
        Pending => {
            // continue
        }
    }
}
```

อย่างไรก็ตาม หาก Rust คอมไพล์มันเป็นโค้ดแบบนั้นเป๊ะๆ ทุก `await` ก็จะกลายเป็นแบบบล็อก ซึ่งตรงข้ามกับสิ่งที่เราต้องการเลย! แทนที่จะเป็นเช่นนั้น Rust ทำให้แน่ใจว่าลูปนั้นสามารถส่งต่อการควบคุมให้อะไรบางอย่างที่หยุดงานบนฟิวเจอร์นี้ชั่วคราวเพื่อไปทำงานกับฟิวเจอร์อื่น แล้วค่อยกลับมาตรวจสอบฟิวเจอร์นี้ใหม่ในภายหลังได้ อย่างที่เราเห็นแล้ว อะไรบางอย่างนั้นคือรันไทม์ (runtime) แบบ async และการจัดตารางเวลาและประสานงานนี้ก็เป็นหนึ่งในงานหลักของมัน

ในหัวข้อ[“การส่งข้อมูลระหว่างสองทาสก์ด้วยการส่งผ่านข้อความ”][message-passing]<!-- ignore --> เราได้อธิบายการรอ `rx.recv` การเรียก `recv` คืนค่าฟิวเจอร์ และการ await ฟิวเจอร์นั้นก็จะทำการโพลล์ (polling) มัน เราสังเกตว่ารันไทม์จะหยุดฟิวเจอร์ชั่วคราวจนกว่ามันจะพร้อมด้วย `Some(message)` หรือ `None` เมื่อแชนเนลปิด ด้วยความเข้าใจที่ลึกขึ้นของเราเกี่ยวกับเทรต `Future` และโดยเฉพาะ `Future::poll` เราจึงเห็นได้ว่ามันทำงานอย่างไร รันไทม์รู้ว่าฟิวเจอร์ยังไม่พร้อมเมื่อมันคืนค่า `Poll::Pending` ในทางกลับกัน รันไทม์รู้ว่าฟิวเจอร์_พร้อม_แล้วและเดินหน้ามันต่อเมื่อ `poll` คืนค่า `Poll::Ready(Some(message))` หรือ `Poll::Ready(None)`

รายละเอียดที่แน่นอนว่ารันไทม์ทำเช่นนั้นได้อย่างไรนั้นอยู่นอกขอบเขตของหนังสือเล่มนี้ แต่สิ่งสำคัญคือการเห็นกลไกพื้นฐานของฟิวเจอร์: รันไทม์_โพลล์_ฟิวเจอร์แต่ละตัวที่มันรับผิดชอบ แล้วทำให้ฟิวเจอร์กลับไปหลับเมื่อมันยังไม่พร้อม

เราใส่ฟิวเจอร์แต่ละตัวไว้ใน `Box` เพื่อทำให้มันกลายเป็น_เทรตออบเจกต์_ (trait object) เช่นเดียวกับที่เราทำในหัวข้อ “การคืนค่าข้อผิดพลาดจาก `run`” ในบทที่ 12 (เราจะครอบคลุมเทรตออบเจกต์โดยละเอียดในบทที่ 18) การใช้เทรตออบเจกต์ทำให้เราปฏิบัติกับฟิวเจอร์นิรนามแต่ละตัวที่ชนิดข้อมูลเหล่านี้สร้างขึ้นเป็นชนิดเดียวกันได้ เพราะทั้งหมดอิมพลีเมนต์เทรต `Future`

สิ่งนี้อาจน่าประหลาดใจ เพราะท้ายที่สุดแล้ว ไม่มีบล็อก async ตัวใดคืนค่าใดๆ ดังนั้นแต่ละตัวจึงสร้าง `Future<Output = ()>` แต่พึงระลึกว่า `Future` เป็นเทรต และคอมไพเลอร์ (compiler) สร้าง enum ที่ไม่ซ้ำใครสำหรับแต่ละบล็อก async แม้พวกมันจะมีชนิดเอาต์พุตที่เหมือนกันก็ตาม เช่นเดียวกับที่คุณใส่ struct ที่เขียนด้วยมือสองชนิดที่ต่างกันลงใน `Vec` เดียวกันไม่ได้ คุณก็ผสม enum ที่คอมไพเลอร์สร้างขึ้นต่างชนิดกันไม่ได้เช่นกัน

จากนั้นเราส่งคอลเลกชันของฟิวเจอร์ให้ฟังก์ชัน `trpl::join_all` และ await ผลลัพธ์ อย่างไรก็ตาม โค้ดนี้คอมไพล์ไม่ผ่าน นี่คือส่วนที่เกี่ยวข้องของข้อความแสดงข้อผิดพลาด

หมายเหตุในข้อความแสดงข้อผิดพลาดนี้บอกเราว่าเราควรใช้มาโคร `pin!` เพื่อ_ตรึง_ (pin) ค่าเหล่านั้น ซึ่งหมายถึงการใส่ค่าลงในชนิด `Pin` ที่รับประกันว่าค่าจะไม่ถูกย้ายในหน่วยความจำ ข้อความแสดงข้อผิดพลาดบอกว่าจำเป็นต้องตรึงเพราะ `dyn Future<Output = ()>` ต้องอิมพลีเมนต์เทรต `Unpin` แต่ตอนนี้มันยังไม่ได้ทำ

ฟังก์ชัน `trpl::join_all` คืนค่า struct ที่ชื่อ `JoinAll` struct นั้นเป็นเจเนอริก (generic) เหนือชนิด `F` ซึ่งถูกจำกัดให้อิมพลีเมนต์เทรต `Future` การ await ฟิวเจอร์โดยตรงด้วย `await` จะตรึงฟิวเจอร์โดยปริยาย นั่นคือเหตุผลที่เราไม่จำเป็นต้องใช้ `pin!` ทุกแห่งที่เราต้องการ await ฟิวเจอร์

อย่างไรก็ตาม เรากำลังไม่ได้ await ฟิวเจอร์โดยตรงตรงนี้ แทนที่จะเป็นเช่นนั้น เราสร้างฟิวเจอร์ใหม่ชื่อ JoinAll ด้วยการส่งคอลเลกชันของฟิวเจอร์ให้ฟังก์ชัน `join_all` ซิกเนเจอร์ (signature) ของ `join_all` กำหนดให้ชนิดของสมาชิกในคอลเลกชันทั้งหมดอิมพลีเมนต์เทรต `Future` และ `Box<T>` อิมพลีเมนต์ `Future` ได้ก็ต่อเมื่อ `T` ที่มันห่ออยู่นั้นเป็นฟิวเจอร์ที่อิมพลีเมนต์เทรต `Unpin`

นั่นเป็นสิ่งที่ต้องทำความเข้าใจค่อนข้างมาก! เพื่อให้เข้าใจอย่างแท้จริง มาดำดิ่งลงไปอีกเล็กน้อยว่าจริงๆ แล้วเทรต `Future` ทำงานอย่างไร โดยเฉพาะในส่วนที่เกี่ยวกับการตรึง มาดูนิยามของเทรต `Future` อีกครั้ง:

```rust
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    // Required method
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

พารามิเตอร์ `cx` และชนิด `Context` ของมันเป็นกุญแจสำคัญว่าจริงๆ แล้วรันไทม์รู้ได้อย่างไรว่าเมื่อไหร่ควรตรวจสอบฟิวเจอร์ตัวใดตัวหนึ่ง ขณะที่ยังคงความเลซี่อยู่ ย้ำอีกครั้งว่า รายละเอียดว่ามันทำงานอย่างไรนั้นอยู่นอกขอบเขตของบทนี้ และโดยทั่วไปคุณต้องคิดถึงเรื่องนี้เฉพาะตอนเขียนการอิมพลีเมนต์ `Future` แบบกำหนดเองเท่านั้น เราจะเน้นที่ชนิดของ `self` แทน เพราะนี่เป็นครั้งแรกที่เราเห็นเมธอดที่ `self` มีการระบุชนิดข้อมูล (type annotation) การระบุชนิดข้อมูลสำหรับ `self` ทำงานเหมือนการระบุชนิดข้อมูลสำหรับพารามิเตอร์อื่นๆ ของฟังก์ชัน แต่มีความแตกต่างสำคัญสองประการ:

- มันบอก Rust ว่า `self` ต้องเป็นชนิดใดจึงจะเรียกเมธอดได้
- มันเป็นชนิดใดก็ได้ไม่ได้ แต่มันถูกจำกัดให้เป็นชนิดที่เมธอดถูกอิมพลีเมนต์อยู่ เรเฟอเรนซ์หรือสมาร์ตพอยน์เตอร์ไปยังชนิดนั้น หรือ `Pin` ที่ห่อเรเฟอเรนซ์ไปยังชนิดนั้น

เราจะเห็นวากยสัมพันธ์นี้เพิ่มเติมใน[บทที่ 18][ch-18]<!-- ignore --> ตอนนี้ รู้แค่ว่าหากเราต้องการโพลล์ฟิวเจอร์เพื่อตรวจสอบว่ามันเป็น `Pending` หรือ `Ready(Output)` เราจำเป็นต้องมีเรเฟอเรนซ์แบบเปลี่ยนแปลงได้ที่ถูกห่อด้วย `Pin` ไปยังชนิดนั้นก็เพียงพอ

`Pin` เป็นตัวห่อสำหรับชนิดที่คล้ายพอยน์เตอร์ เช่น `&`, `&mut`, `Box` และ `Rc` (ในทางเทคนิค `Pin` ทำงานกับชนิดที่อิมพลีเมนต์เทรต `Deref` หรือ `DerefMut` แต่ในทางปฏิบัติแล้วเทียบเท่ากับการทำงานกับเรเฟอเรนซ์และสมาร์ตพอยน์เตอร์เท่านั้น) `Pin` ไม่ใช่พอยน์เตอร์ด้วยตัวเองและไม่มีพฤติกรรมใดๆ เป็นของตัวเองเหมือนที่ `Rc` และ `Arc` มีการนับจำนวนเรเฟอเรนซ์ (reference counting) มันเป็นเพียงเครื่องมือที่คอมไพเลอร์ใช้บังคับข้อจำกัดในการใช้พอยน์เตอร์เท่านั้น

การระลึกว่า `await` ถูกอิมพลีเมนต์ในรูปของการเรียก `poll` เริ่มอธิบายข้อความแสดงข้อผิดพลาดที่เราเห็นไปก่อนหน้านี้ได้ แต่ข้อความนั้นพูดถึง `Unpin` ไม่ใช่ `Pin` แล้ว `Pin` สัมพันธ์กับ `Unpin` อย่างไรกันแน่ และทำไม `Future` จึงต้องการให้ `self` อยู่ในชนิด `Pin` เพื่อเรียก `poll`?

ย้อนนึกจากตอนต้นบทนี้ว่าชุดของจุด await ในฟิวเจอร์จะถูกคอมไพล์เป็นสเตตแมชชีน และคอมไพเลอร์ทำให้แน่ใจว่าสเตตแมชชีนนั้นปฏิบัติตามกฎความปลอดภัยปกติทั้งหมดของ Rust รวมถึงการยืมและความเป็นเจ้าของ เพื่อให้สิ่งนั้นทำงานได้ Rust จะดูว่าจำเป็นต้องใช้ข้อมูลใดระหว่างจุด await หนึ่งกับจุด await ถัดไปหรือจุดสิ้นสุดของบล็อก async จากนั้นมันจะสร้างวาเรียนต์ที่สอดคล้องกันในสเตตแมชชีนที่ถูกคอมไพล์แล้ว วาเรียนต์แต่ละตัวจะได้รับการเข้าถึงข้อมูลที่จำเป็นซึ่งจะถูกใช้ในส่วนนั้นของโค้ดซอร์ส ไม่ว่าจะโดยการรับความเป็นเจ้าของข้อมูลนั้นหรือโดยการได้เรเฟอเรนซ์แบบเปลี่ยนแปลงได้หรือแบบเปลี่ยนแปลงไม่ได้ไปยังข้อมูลนั้น

จนถึงตอนนี้ก็ราบรื่นดี: หากเราทำอะไรผิดเกี่ยวกับความเป็นเจ้าของหรือเรเฟอเรนซ์ในบล็อก async ตัวใดตัวหนึ่ง ตัวตรวจการยืม (borrow checker) จะบอกเรา เมื่อเราต้องการย้ายฟิวเจอร์ที่สอดคล้องกับบล็อกนั้นไปมา เช่นย้ายมันเข้าไปใน `Vec` เพื่อส่งให้ `join_all` เรื่องก็จะยุ่งยากขึ้น

เมื่อเราย้ายฟิวเจอร์ ไม่ว่าจะโดยการพุชมันเข้าไปในโครงสร้างข้อมูลเพื่อใช้เป็นอิเทอเรเตอร์กับ `join_all` หรือโดยการคืนมันกลับจากฟังก์ชัน นั่นหมายถึงการย้ายสเตตแมชชีนที่ Rust สร้างขึ้นให้เราจริงๆ และต่างจากชนิดข้อมูลอื่นๆ ส่วนใหญ่ใน Rust ฟิวเจอร์ที่ Rust สร้างขึ้นสำหรับบล็อก async อาจมีเรเฟอเรนซ์ไปยังตัวเองอยู่ในฟิลด์ (field) ของวาเรียนต์ใดวาเรียนต์หนึ่งได้ ดังแสดงในภาพประกอบแบบง่ายในรูปที่ 17-4

ในทางทฤษฎี คอมไพเลอร์ Rust อาจพยายามอัปเดตทุกเรเฟอเรนซ์ไปยังวัตถุทุกครั้งที่มันถูกย้าย แต่นั่นอาจเพิ่มค่าใช้จ่ายด้านประสิทธิภาพอย่างมาก โดยเฉพาะอย่างยิ่งหากต้องอัปเดตเครือข่ายเรเฟอเรนซ์ทั้งข่าย หากเราทำให้แน่ใจได้ว่าโครงสร้างข้อมูลนั้น_ไม่เคลื่อนที่ในหน่วยความจำ_แทน เราก็ไม่จำเป็นต้องอัปเดตเรเฟอเรนซ์ใดๆ เลย นี่คือสิ่งที่ตัวตรวจการยืมของ Rust มีไว้เพื่อการนี้พอดี: ในโค้ดที่ปลอดภัย มันป้องกันไม่ให้คุณย้ายรายการใดๆ ที่มีเรเฟอเรนซ์ที่ยังใช้งานอยู่ชี้ไปยังมัน

`Pin` ต่อยอดจากสิ่งนั้นเพื่อมอบการรับประกันที่เราต้องการพอดี เมื่อเรา_ตรึง_ค่าด้วยการห่อพอยน์เตอร์ไปยังค่านั้นใน `Pin` มันจะไม่สามารถเคลื่อนที่ได้อีก ดังนั้น หากคุณมี `Pin<Box<SomeType>>` คุณจะตรึงค่า `SomeType` จริงๆ _ไม่ใช่_ พอยน์เตอร์ `Box` รูปที่ 17-6 แสดงกระบวนการนี้

อย่างไรก็ตาม ชนิดข้อมูลส่วนใหญ่ปลอดภัยอย่างสมบูรณ์ต่อการย้ายไปมา แม้มันจะอยู่หลังพอยน์เตอร์ `Pin` ก็ตาม เราจำเป็นต้องคิดถึงการตรึงเฉพาะเมื่อรายการมีเรเฟอเรนซ์ภายในเท่านั้น ค่าดั้งเดิมอย่างตัวเลขและบูลีนนั้นปลอดภัยเพราะเห็นได้ชัดว่าพวกมันไม่มีเรเฟอเรนซ์ภายใน ชนิดข้อมูลส่วนใหญ่ที่คุณทำงานด้วยเป็นปกติใน Rust ก็เช่นกัน คุณย้าย `Vec` ไปมาได้โดยไม่ต้องกังวล ตัวอย่างเช่น จากสิ่งที่เราเห็นมาแล้ว หากคุณมี `Pin<Vec<String>>` คุณจะต้องทำทุกอย่างผ่าน API ที่ปลอดภัยแต่จำกัดที่ `Pin` จัดเตรียมไว้ แม้ว่า `Vec<String>` จะปลอดภัยต่อการย้ายเสมอหากไม่มีเรเฟอเรนซ์อื่นชี้ไปยังมันก็ตาม เราจำเป็นต้องมีวิธีบอกคอมไพเลอร์ว่าการย้ายรายการไปมาในกรณีแบบนี้เป็นเรื่องที่โอเค และนั่นคือจุดที่ `Unpin` เข้ามามีบทบาท

`Unpin` เป็นเทรตมาร์กเกอร์ (marker trait) คล้ายกับเทรต `Send` และ `Sync` ที่เราเห็นในบทที่ 16 จึงไม่มีฟังก์ชันการทำงานเป็นของตัวเอง เทรตมาร์กเกอร์มีอยู่เพียงเพื่อบอกคอมไพเลอร์ว่าการใช้ชนิดที่อิมพลีเมนต์เทรตที่กำหนดในบริบทเฉพาะนั้นปลอดภัย `Unpin` แจ้งให้คอมไพเลอร์ทราบว่าชนิดที่กำหนด_ไม่_จำเป็นต้องยึดถือการรับประกันใดๆ ว่าค่านั้นสามารถถูกย้ายได้อย่างปลอดภัยหรือไม่

เช่นเดียวกับ `Send` และ `Sync` คอมไพเลอร์อิมพลีเมนต์ `Unpin` โดยอัตโนมัติสำหรับทุกชนิดที่มันพิสูจน์ได้ว่าปลอดภัย กรณีพิเศษ ซึ่งก็คล้ายกับ `Send` และ `Sync` อีกเช่นกัน คือกรณีที่ `Unpin` ถูก_ไม่_อิมพลีเมนต์สำหรับชนิดหนึ่ง สัญกรณ์สำหรับกรณีนี้คือ <code>impl !Unpin for <em>SomeType</em></code> โดยที่ <code><em>SomeType</em></code> คือชื่อของชนิดที่_ต้อง_ยึดถือการรับประกันเหล่านั้นเพื่อให้ปลอดภัยทุกครั้งที่พอยน์เตอร์ไปยังชนิดนั้นถูกใช้ใน `Pin`

กล่าวอีกนัยหนึ่ง มีสองสิ่งที่ต้องจำเกี่ยวกับความสัมพันธ์ระหว่าง `Pin` กับ `Unpin` อย่างแรก `Unpin` คือกรณี “ปกติ” และ `!Unpin` คือกรณีพิเศษ อย่างที่สอง ไม่ว่าชนิดจะอิมพลีเมนต์ `Unpin` หรือ `!Unpin` จะ_มีผล_เฉพาะเมื่อคุณใช้พอยน์เตอร์ที่ถูกตรึงไปยังชนิดนั้นอย่าง <code>Pin<&mut
<em>SomeType</em>></code> เท่านั้น

### เทรต `Stream`

ตอนนี้คุณเข้าใจเทรต `Future`, `Pin` และ `Unpin` ลึกซึ้งขึ้นแล้ว เราจึงหันความสนใจไปที่เทรต `Stream` ได้ อย่างที่คุณได้เรียนรู้ไปตอนต้นบท สตรีม (stream) นั้นคล้ายกับอิเทอเรเตอร์แบบอะซิงโครนัส (asynchronous) อย่างไรก็ตาม ต่างจาก `Iterator` และ `Future` ตรงที่ ณ เวลาที่เขียนนี้ `Stream` ไม่มีคำนิยามในไลบรารีมาตรฐาน แต่_มี_คำนิยามที่พบได้ทั่วไปมากจากเครต `futures` ซึ่งใช้กันทั่วทั้งระบบนิเวศ

มาทบทวนคำนิยามของเทรต `Iterator` และ `Future` กันก่อนดูว่าเทรต `Stream` อาจรวมพวกมันเข้าด้วยกันได้อย่างไร จาก `Iterator` เรามีแนวคิดเรื่องลำดับ: เมธอด `next` ของมันให้ `Option<Self::Item>` จาก `Future` เรามีแนวคิดเรื่องความพร้อมเมื่อเวลาผ่านไป: เมธอด `poll` ของมันให้ `Poll<Self::Output>` เพื่อแทนลำดับของรายการที่พร้อมขึ้นเมื่อเวลาผ่านไป เราจึงนิยามเทรต `Stream` ที่รวมคุณสมบัติเหล่านั้นเข้าด้วยกัน:

```rust
use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;

    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>
    ) -> Poll<Option<Self::Item>>;
}
```

เทรต `Stream` นิยามชนิดที่เชื่อมโยงชื่อ `Item` สำหรับชนิดของรายการที่สตรีมสร้างขึ้น สิ่งนี้คล้ายกับ `Iterator` ซึ่งอาจมีรายการตั้งแต่ศูนย์ไปจนถึงหลายรายการ และต่างจาก `Future` ซึ่งมี `Output` เพียงหนึ่งเดียวเสมอ แม้มันจะเป็นยูนิตไทป์ `()` ก็ตาม

`Stream` ยังนิยามเมธอดสำหรับดึงรายการเหล่านั้นด้วย เราเรียกมันว่า `poll_next` เพื่อให้ชัดเจนว่ามันโพลล์ในแบบเดียวกับที่ `Future::poll` ทำ และสร้างลำดับของรายการในแบบเดียวกับที่ `Iterator::next` ทำ ชนิดที่มันคืนกลับรวม `Poll` เข้ากับ `Option` ชนิดชั้นนอกคือ `Poll` เพราะต้องถูกตรวจสอบความพร้อมเหมือนที่ฟิวเจอร์ต้องถูกตรวจสอบ ชนิดชั้นในคือ `Option` เพราะมันต้องส่งสัญญาณว่ายังมีข้อความอีกหรือไม่ เหมือนที่อิเทอเรเตอร์ต้องส่งสัญญาณ

บางสิ่งที่จะคล้ายกับคำนิยามนี้มากน่าจะได้กลายเป็นส่วนหนึ่งของไลบรารีมาตรฐานของ Rust ในที่สุด ในระหว่างนี้ มันเป็นส่วนหนึ่งของชุดเครื่องมือของรันไทม์ส่วนใหญ่ คุณจึงพึ่งพามันได้ และทุกสิ่งที่เราจะครอบคลุมต่อไปนี้ก็ควรใช้ได้โดยทั่วไป!

>
> ```rust,ignore
> fn next(&mut self) -> Next<'_, Self> where Self: Unpin;
> ```
>
> ชนิด `Next` นั้นเป็น `struct` ที่อิมพลีเมนต์ `Future` และช่วยให้เราระบุชื่อ

ในเวอร์ชันของ `StreamExt` ที่ใช้ในเครต `trpl` เทรตนี้ไม่เพียงนิยามเมธอด `next` เท่านั้น แต่ยังจัดเตรียมการอิมพลีเมนต์เริ่มต้นของ `next` ที่จัดการรายละเอียดของการเรียก `Stream::poll_next` อย่างถูกต้องด้วย ซึ่งหมายความว่าแม้คุณต้องเขียนชนิดข้อมูลสตรีมของคุณเอง คุณก็_เพียง_ต้องอิมพลีเมนต์ `Stream` แล้วใครก็ตามที่ใช้ชนิดข้อมูลของคุณก็จะใช้ `StreamExt` และเมธอดของมันกับมันได้โดยอัตโนมัติ
