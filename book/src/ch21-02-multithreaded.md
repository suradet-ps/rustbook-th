## จากเว็บเซิร์ฟเวอร์แบบเธรดเดียวสู่เว็บเซิร์ฟเวอร์แบบหลายเธรด

ในตอนนี้ เซิร์ฟเวอร์จะประมวลผลแต่ละคำขอทีละคำขอ หมายความว่ามันจะไม่ประมวลผลการเชื่อมต่อที่สองจนกว่าการเชื่อมต่อแรกจะประมวลผลเสร็จสิ้น หากเซิร์ฟเวอร์ได้รับคำขอมากขึ้นเรื่อยๆ การทำงานแบบอนุกรม (serial execution) นี้จะยิ่งมีประสิทธิภาพลดลงเรื่อยๆ หากเซิร์ฟเวอร์ได้รับคำขอที่ใช้เวลาประมวลผลนาน คำขอถัดไปจะต้องรอจนกว่าคำขอที่ใช้เวลานานนั้นจะเสร็จสิ้น แม้ว่าคำขอใหม่จะสามารถประมวลผลได้อย่างรวดเร็วก็ตาม เราจะต้องแก้ปัญหานี้ แต่ก่อนอื่นมาดูปัญหานี้ในสถานการณ์จริงกันก่อน

คุณจะเห็นได้ว่าเซิร์ฟเวอร์ของเราดิบแค่ไหน: ไลบรารีจริงจะจัดการการรู้จักคำขอหลายๆ แบบด้วยวิธีที่กระชับกว่านี้มาก!

เริ่มเซิร์ฟเวอร์โดยใช้ `cargo run` จากนั้นเปิดหน้าต่างเบราว์เซอร์สองหน้าต่าง: หน้าต่างหนึ่งสำหรับ _http://127.0.0.1:7878_ และอีกหน้าต่างสำหรับ _http://127.0.0.1:7878/sleep_ หากคุณป้อน URI _/_ หลายๆ ครั้งเหมือนเดิม คุณจะเห็นว่ามันตอบกลับอย่างรวดเร็ว แต่ถ้าคุณป้อน _/sleep_ แล้วโหลด _/_ คุณจะเห็นว่า _/_ รอจนกว่า `sleep` จะหลับครบห้าวินาทีเต็มก่อนที่จะโหลด

มีเทคนิคหลายอย่างที่เราสามารถใช้เพื่อหลีกเลี่ยงไม่ให้คำขอต่างๆ ไปติดค้างอยู่ข้างหลังคำขอที่ช้าได้ รวมถึงการใช้ async อย่างที่เราทำในบทที่ 17; สิ่งที่เราจะอิมพลีเมนต์คือพูลเธรด (thread pool)

### การปรับปรุงทรูพุตด้วยพูลเธรด

_พูลเธรด_ คือกลุ่มของเธรด (thread) ที่ถูกสร้างขึ้นและพร้อมรอที่จะจัดการงาน เมื่อโปรแกรมได้รับงานใหม่ มันจะมอบหมายเธรดตัวใดตัวหนึ่งในพูลให้กับงานนั้น และเธรดนั้นจะประมวลผลงานนั้น เธรดที่เหลือในพูลจะพร้อมใช้งานสำหรับจัดการงานอื่นๆ ที่เข้ามาในระหว่างที่เธรดแรกกำลังประมวลผล เมื่อเธรดแรกประมวลผลงานของมันเสร็จ มันจะถูกส่งกลับคืนสู่พูลของเธรดที่ว่างอยู่ พร้อมที่จะจัดการงานใหม่ พูลเธรดช่วยให้คุณประมวลผลการเชื่อมต่อได้พร้อมกัน ซึ่งเพิ่มทรูพุต (throughput) ของเซิร์ฟเวอร์ของคุณ

เราจะจำกัดจำนวนเธรดในพูลไว้ที่จำนวนน้อยๆ เพื่อป้องกันเราจากการโจมตีแบบ DoS; หากเราปล่อยให้โปรแกรมของเราสร้างเธรดใหม่สำหรับทุกคำขอที่เข้ามา ใครสักคนที่ส่งคำขอ 10 ล้านคำขอมาที่เซิร์ฟเวอร์ของเราก็อาจก่อความเสียหายได้โดยใช้ทรัพยากรของเซิร์ฟเวอร์ของเราจนหมดและทำให้การประมวลผลคำขอหยุดชะงักไปเลย

ดังนั้น แทนที่จะสร้างเธรดแบบไม่จำกัด เราจะมีเธรดจำนวนคงที่รออยู่ในพูล คำขอที่เข้ามาจะถูกส่งไปยังพูลเพื่อประมวลผล พูลจะดูแลคิวของคำขอที่เข้ามา เธรดแต่ละตัวในพูลจะดึงคำขอออกจากคิวนี้ จัดการคำขอ แล้วขอคำขอถัดไปจากคิว ด้วยการออกแบบนี้ เราจึงประมวลผลคำขอได้พร้อมกันสูงสุดถึง _`N`_ คำขอ โดยที่ _`N`_ คือจำนวนเธรด หากแต่ละเธรดกำลังตอบสนองคำขอที่ใช้เวลานาน คำขอถัดไปก็ยังคงติดค้างในคิวได้ แต่มันได้เพิ่มจำนวนคำขอที่ใช้เวลานานที่เราจัดการได้ก่อนที่จะถึงจุดนั้น

เทคนิคนี้เป็นเพียงหนึ่งในหลายวิธีในการปรับปรุงทรูพุตของเว็บเซิร์ฟเวอร์ ทางเลือกอื่นๆ ที่คุณอาจสำรวจได้แก่โมเดล fork/join, โมเดล single-threaded async I/O และโมเดล multithreaded async I/O หากคุณสนใจหัวข้อนี้ คุณสามารถอ่านเพิ่มเติมเกี่ยวกับวิธีแก้ปัญหาอื่นๆ และลองอิมพลีเมนต์พวกมันดูได้; ด้วยภาษาระดับต่ำอย่าง Rust ทางเลือกทั้งหมดนี้ล้วนเป็นไปได้

ก่อนที่เราจะเริ่มอิมพลีเมนต์พูลเธรด มาพูดคุยกันว่าการใช้พูลควรมีหน้าตาอย่างไร เมื่อคุณกำลังพยายามออกแบบโค้ด การเขียนอินเทอร์เฟซฝั่งไคลเอนต์ก่อนสามารถช่วยนำทางการออกแบบของคุณได้ ให้เขียน API ของโค้ดในลักษณะที่มีโครงสร้างอย่างที่คุณต้องการเรียกใช้มัน; จากนั้นอิมพลีเมนต์ฟังก์ชันการทำงานภายในโครงสร้างนั้น แทนที่จะอิมพลีเมนต์ฟังก์ชันการทำงานก่อนแล้วค่อยออกแบบ API สาธารณะ

คล้ายกับวิธีที่เราใช้การพัฒนาแบบขับเคลื่อนด้วยเทสต์ (test-driven development) ในโปรเจกต์ในบทที่ 12 เราจะใช้การพัฒนาแบบขับเคลื่อนด้วยคอมไพเลอร์ (compiler) ที่นี่ เราจะเขียนโค้ดที่เรียกฟังก์ชันที่เราต้องการ จากนั้นเราจะดูข้อผิดพลาดจากคอมไพเลอร์เพื่อกำหนดว่าเราควรเปลี่ยนแปลงอะไรต่อไปเพื่อให้โค้ดทำงานได้ อย่างไรก็ตาม ก่อนที่เราจะทำเช่นนั้น เราจะสำรวจเทคนิคที่เราจะไม่ใช้เป็นจุดเริ่มต้นกันก่อน

ตอนนี้ข้อผิดพลาดเกิดขึ้นเพราะเราไม่มีเมธอด `execute` บน `ThreadPool` ย้อนนึกจากหัวข้อ[“การสร้างเธรดจำนวนจำกัด”](#creating-a-finite-number-of-threads)<!-- ignore --> ว่าเราตัดสินใจว่าพูลเธรดของเราควรมีอินเทอร์เฟซที่คล้ายกับ `thread::spawn` นอกจากนี้ เราจะอิมพลีเมนต์ฟังก์ชัน `execute` เพื่อให้มันรับโคลเชอร์ที่ได้รับมาแล้วมอบให้เธรดที่ว่างอยู่ในพูลรัน

เราจะนิยามเมธอด `execute` บน `ThreadPool` ให้รับโคลเชอร์เป็นพารามิเตอร์ ย้อนนึกจาก[“การย้ายค่าที่ถูกจับออกจากโคลเชอร์”][moving-out-of-closures]<!-- ignore --> ในบทที่ 13 ว่าเรารับโคลเชอร์เป็นพารามิเตอร์ได้ด้วยเทรต (trait) สามตัวที่แตกต่างกัน: `Fn`, `FnMut` และ `FnOnce` เราจำเป็นต้องตัดสินใจว่าจะใช้โคลเชอร์ชนิดใดที่นี่ เรารู้ว่าในที่สุดเราจะทำอะไรคล้ายกับการอิมพลีเมนต์ `thread::spawn` ของไลบรารีมาตรฐาน ดังนั้นเราจึงดูได้ว่าซิกเนเจอร์ของ `thread::spawn` มีบาวด์ (bound) อะไรกับพารามิเตอร์ของมัน เอกสารแสดงให้เราเห็นดังนี้:

```rust,ignore
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
    where
        F: FnOnce() -> T,
        F: Send + 'static,
        T: Send + 'static,
```

พารามิเตอร์ชนิดข้อมูล (type parameter) `F` คือตัวที่เราสนใจตรงนี้; พารามิเตอร์ชนิดข้อมูล `T` เกี่ยวข้องกับค่าที่คืนกลับ ซึ่งเราไม่ได้สนใจ เราจะเห็นได้ว่า `spawn` ใช้ `FnOnce` เป็นบาวด์ของเทรตบน `F` นี่น่าจะเป็นสิ่งที่เราต้องการเช่นกัน เพราะในที่สุดเราจะส่งอาร์กิวเมนต์ที่เราได้ใน `execute` ต่อไปให้ `spawn` เรามั่นใจได้ยิ่งขึ้นว่า `FnOnce` คือเทรตที่เราต้องการใช้ เพราะเธรดสำหรับรันคำขอจะรันโคลเชอร์ของคำขอนั้นเพียงครั้งเดียว ซึ่งสอดคล้องกับ `Once` ใน `FnOnce`

พารามิเตอร์ชนิดข้อมูล `F` ยังมีบาวด์ของเทรต `Send` และบาวด์ของไลฟ์ไทม์ (lifetime) `'static` ซึ่งมีประโยชน์ในสถานการณ์ของเรา: เราจำเป็นต้องมี `Send` เพื่อโอนโคลเชอร์จากเธรดหนึ่งไปยังอีกเธรดหนึ่ง และ `'static` เพราะเราไม่รู้ว่าเธรดจะใช้เวลานานเท่าใดในการรัน มาสร้างเมธอด `execute` บน `ThreadPool` ที่จะรับพารามิเตอร์เจเนอริก (generic) ชนิด `F` ที่มีบาวด์เหล่านี้กัน:

#### การสร้างพื้นที่สำหรับจัดเก็บเธรด

ตอนนี้ที่เรามีวิธีรู้ว่าเรามีจำนวนเธรดที่ถูกต้องสำหรับจัดเก็บในพูลแล้ว เราสามารถสร้างเธรดเหล่านั้นและจัดเก็บพวกมันใน struct `ThreadPool` ก่อนคืนค่า struct ได้ แต่เราจะ “จัดเก็บ” เธรดได้อย่างไร? มาดูซิกเนเจอร์ของ `thread::spawn` กันอีกครั้ง:

```rust,ignore

```

#### การส่งโค้ดจาก `ThreadPool` ไปยังเธรด

เราได้ทิ้งคอมเมนต์ไว้ในลูป `for` ในลิสติ้ง 21-14 เกี่ยวกับการสร้างเธรด ตรงนี้เราจะมาดูว่าเราสร้างเธรดจริงๆ อย่างไร ไลบรารีมาตรฐานจัดเตรียม `thread::spawn` เป็นวิธีสร้างเธรด และ `thread::spawn` คาดหวังว่าจะได้รับโค้ดบางอย่างที่เธรดควรจะรันทันทีที่เธรดถูกสร้างขึ้น อย่างไรก็ตาม ในกรณีของเรา เราต้องการสร้างเธรดและให้พวกมัน_รอ_โค้ดที่เราจะส่งไปในภายหลัง การอิมพลีเมนต์เธรดของไลบรารีมาตรฐานไม่ได้มีวิธีทำเช่นนั้นเลย เราจึงต้องอิมพลีเมนต์มันด้วยตัวเอง

เราจะอิมพลีเมนต์พฤติกรรมนี้โดยแนะนำโครงสร้างข้อมูลใหม่ระหว่าง `ThreadPool` กับเธรดต่างๆ ซึ่งจะจัดการพฤติกรรมใหม่นี้ เราจะเรียกโครงสร้างข้อมูลนี้ว่า _Worker_ ซึ่งเป็นคำที่พบได้ทั่วไปในการอิมพลีเมนต์ระบบพูล `Worker` จะหยิบโค้ดที่ต้องรันขึ้นมาแล้วรันโค้ดนั้นในเธรดของมัน

ให้คิดถึงคนที่ทำงานในครัวของร้านอาหาร: เวิร์กเกอร์ (worker) จะรอจนกว่าจะมีออร์เดอร์เข้ามาจากลูกค้า จากนั้นพวกเขาก็มีหน้าที่รับออร์เดอร์เหล่านั้นและทำมันให้สำเร็จ

แทนที่จะจัดเก็บเวกเตอร์ของอินสแตนซ์ `JoinHandle<()>` ในพูลเธรด เราจะจัดเก็บอินสแตนซ์ของ struct `Worker` แต่ละ `Worker` จะจัดเก็บอินสแตนซ์ `JoinHandle<()>` หนึ่งตัว จากนั้นเราจะอิมพลีเมนต์เมธอดบน `Worker` ที่จะรับโคลเชอร์ของโค้ดที่จะรันและส่งมันไปยังเธรดที่กำลังรันอยู่แล้วเพื่อดำเนินการ เราจะมอบ `id` ให้แต่ละ `Worker` ด้วย เพื่อให้เราสามารถแยกแยะระหว่างอินสแตนซ์ `Worker` ต่างๆ ในพูลได้เมื่อบันทึกล็อกหรือดีบัก

นี่คือกระบวนการใหม่ที่จะเกิดขึ้นเมื่อเราสร้าง `ThreadPool` เราจะอิมพลีเมนต์โค้ดที่ส่งโคลเชอร์ไปยังเธรดหลังจากที่เราตั้งค่า `Worker` ในลักษณะนี้เสร็จแล้ว:

1. นิยาม struct `Worker` ที่เก็บ `id` และ `JoinHandle<()>`
2. เปลี่ยน `ThreadPool` ให้เก็บเวกเตอร์ของอินสแตนซ์ `Worker`
3. นิยามฟังก์ชัน `Worker::new` ที่รับหมายเลข `id` และคืนค่าอินสแตนซ์ `Worker` ที่เก็บ `id` และเธรดที่ถูกสร้างขึ้นด้วยโคลเชอร์ว่างเปล่า
4. ใน `ThreadPool::new` ใช้ตัวนับของลูป `for` เพื่อสร้าง `id` สร้าง `Worker` ใหม่ด้วย `id` นั้น และจัดเก็บ `Worker` ไว้ในเวกเตอร์

#### การส่งคำขอไปยังเธรดผ่านแชนเนล

ปัญหาถัดไปที่เราจะจัดการคือโคลเชอร์ที่ให้กับ `thread::spawn` ไม่ได้ทำอะไรเลย ในปัจจุบัน เราได้โคลเชอร์ที่ต้องการรันในเมธอด `execute` แต่เราจำเป็นต้องให้โคลเชอร์แก่ `thread::spawn` เพื่อรันเมื่อเราสร้าง `Worker` แต่ละตัวในระหว่างการสร้าง `ThreadPool`

เราต้องการให้ struct `Worker` ที่เราเพิ่งสร้างขึ้นไปดึงโค้ดที่จะรันจากคิวที่อยู่ใน `ThreadPool` แล้วส่งโค้ดนั้นไปยังเธรดของมันเพื่อรัน

แชนเนล (channel) ที่เราเรียนรู้ในบทที่ 16—วิธีง่ายๆ ในการสื่อสารระหว่างสองเธรด—จะเหมาะที่สุดสำหรับกรณีการใช้งานนี้ เราจะใช้แชนเนลทำหน้าที่เป็นคิวของงาน (job) และ `execute` จะส่งงานจาก `ThreadPool` ไปยังอินสแตนซ์ `Worker` ซึ่งจะส่งงานนั้นต่อไปยังเธรดของมัน นี่คือแผนของเรา:

1. `ThreadPool` จะสร้างแชนเนลและเก็บฝั่งส่งไว้
2. `Worker` แต่ละตัวจะเก็บฝั่งรับไว้
3. เราจะสร้าง struct `Job` ใหม่ที่จะเก็บโคลเชอร์ที่เราต้องการส่งไปตามแชนเนล
4. เมธอด `execute` จะส่งงานที่ต้องการรันผ่านฝั่งส่ง
5. ในเธรดของมัน `Worker` จะวนซ้ำบนฝั่งรับของมันและรันโคลเชอร์ของงานใดๆ ที่มันได้รับ

โค้ดนี้คอมไพล์และรันได้ แต่ไม่ได้ให้พฤติกรรมการใช้เธรดที่ต้องการ: คำขอที่ช้าจะยังคงทำให้คำขออื่นๆ ต้องรอการประมวลผลอยู่ดี เหตุผลค่อนข้างละเอียดอ่อน: struct `Mutex` ไม่มีเมธอด `unlock` แบบสาธารณะ เพราะความเป็นเจ้าของล็อกอิงตามไลฟ์ไทม์ของ `MutexGuard<T>` ภายใน `LockResult<MutexGuard<T>>` ที่เมธอด `lock` คืนกลับ ในเวลาคอมไพล์ ตัวตรวจการยืม (borrow checker) จึงสามารถบังคับใช้กฎที่ว่าทรัพยากรที่ถูกเฝ้าปกป้องด้วย `Mutex` ไม่สามารถเข้าถึงได้เว้นแต่เราถือล็อกอยู่ อย่างไรก็ตาม การอิมพลีเมนต์นี้ยังอาจทำให้ล็อกถูกถือไว้นานเกินกว่าที่ตั้งใจได้หากเราไม่ระวังไลฟ์ไทม์ของ `MutexGuard<T>`
