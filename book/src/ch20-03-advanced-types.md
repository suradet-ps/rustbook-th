### ความปลอดภัยของชนิดข้อมูลและแอบสแตรกชันด้วยแพตเทิร์นนิวไทป์

หัวข้อนี้สมมติว่าคุณได้อ่านหัวข้อ[“การอิมพลีเมนต์เทรตภายนอกด้วยแพตเทิร์นนิวไทป์”][newtype]<!-- ignore -->ก่อนหน้านี้แล้ว แพตเทิร์นนิวไทป์ยังมีประโยชน์สำหรับงานอื่นนอกเหนือจากที่เราได้พูดคุยกันไปแล้ว ซึ่งรวมถึงการบังคับในระดับสแตติกให้ค่าต่างๆ ไม่ถูกสับสนกัน และการระบุหน่วยของค่า คุณได้เห็นตัวอย่างการใช้นิวไทป์เพื่อระบุหน่วยในลิสติ้ง 20-16: ย้อนนึกว่า struct `Millimeters` และ `Meters` ห่อค่าของ `u32` ไว้ในนิวไทป์ หากเราเขียนฟังก์ชันที่มีพารามิเตอร์ชนิด `Millimeters` เราจะไม่สามารถคอมไพล์โปรแกรมที่บังเอิญพยายามเรียกฟังก์ชันนั้นด้วยค่าชนิด `Meters` หรือ `u32` ธรรมดาได้

เรายังใช้แพตเทิร์นนิวไทป์เพื่อซ่อนรายละเอียดการอิมพลีเมนต์บางส่วนของชนิดข้อมูลได้ด้วย: ชนิดข้อมูลใหม่สามารถเปิดเผย API แบบสาธารณะที่แตกต่างจาก API ของชนิดข้อมูลภายในที่เป็นแบบส่วนตัวได้

นิวไทป์ยังซ่อนการอิมพลีเมนต์ภายในได้ด้วย ตัวอย่างเช่น เราสามารถจัดเตรียมชนิดข้อมูล `People` เพื่อห่อ `HashMap<i32, String>` ที่เก็บ ID ของบุคคลคู่กับชื่อของบุคคลนั้น โค้ดที่ใช้ `People` จะโต้ตอบกับเฉพาะ API แบบสาธารณะที่เราจัดเตรียมไว้ เช่นเมธอดสำหรับเพิ่มสตริงชื่อลงในคอลเลกชัน (collection) `People`; โค้ดนั้นไม่จำเป็นต้องรู้ว่าเรากำหนด ID แบบ `i32` ให้กับชื่อต่างๆ ภายใน แพตเทิร์นนิวไทป์เป็นวิธีที่เบาในการบรรลุการห่อหุ้ม (encapsulation) เพื่อซ่อนรายละเอียดการอิมพลีเมนต์ ซึ่งเราได้พูดคุยกันในหัวข้อ[“การห่อหุ้มที่ซ่อนรายละเอียดการอิมพลีเมนต์”][encapsulation-that-hides-implementation-details]<!-- ignore --> ในบทที่ 18

### ชนิดไม่คืนค่าที่ไม่คืนค่าเลย

Rust มีชนิดข้อมูลพิเศษชื่อ `!` ที่ในศัพท์ทางทฤษฎีชนิดข้อมูลรู้จักกันในชื่อ_ชนิดว่าง_ (empty type) เพราะมันไม่มีค่าใดๆ เราชอบเรียกมันว่า_ชนิดไม่คืนค่า_ (never type) เพราะมันเข้าแทนที่ตำแหน่งของชนิดข้อมูลที่คืนกลับเมื่อฟังก์ชันจะไม่คืนค่ากลับเลย นี่คือตัวอย่าง:

```rust,noplayground
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-07-never-type/src/lib.rs:here}}
```

โค้ดนี้อ่านได้ว่า “ฟังก์ชัน `bar` ไม่คืนค่ากลับเลย” ฟังก์ชันที่ไม่คืนค่ากลับเลยเรียกว่า_ฟังก์ชันลู่ออก_ (diverging function) เราสร้างค่าใดๆ ของชนิด `!` ไม่ได้ ดังนั้น `bar` จึงไม่มีทางคืนค่ากลับมาได้เลย

แต่ชนิดข้อมูลที่คุณไม่สามารถสร้างค่าใดๆ ได้เลยจะมีประโยชน์อะไร? ย้อนนึกถึงโค้ดจากลิสติ้ง 2-5 ซึ่งเป็นส่วนหนึ่งของเกมทายตัวเลข เราได้ทำซ้ำบางส่วนของมันไว้ที่นี่ในลิสติ้ง 20-27

```rust,ignore

```

ในตอนนั้น เราได้ข้ามรายละเอียดบางอย่างในโค้ดนี้ไป ในหัวข้อ[“โครงสร้างควบคุมโฟลว์ `match`”][the-match-control-flow-construct]<!-- ignore --> ในบทที่ 6 เราได้พูดคุยว่าอาร์ม (arm) ของ `match` ทุกอาร์มต้องคืนค่าเป็นชนิดเดียวกัน ดังนั้น ตัวอย่างเช่น โค้ดต่อไปนี้จึงใช้ไม่ได้:

ชนิดของ `guess` ในโค้ดนี้จะต้องเป็นจำนวนเต็ม_และ_สตริงในเวลาเดียวกัน และ Rust กำหนดว่า `guess` ต้องมีเพียงชนิดเดียวเท่านั้น แล้ว `continue` คืนค่าอะไรล่ะ? ทำไมเราจึงได้รับอนุญาตให้คืนค่า `u32` จากอาร์มหนึ่งและมีอีกอาร์มที่ลงท้ายด้วย `continue` ในลิสติ้ง 20-27?

อย่างที่คุณอาจเดาได้ `continue` มีค่าเป็น `!` นั่นคือ เมื่อ Rust คำนวณชนิดของ `guess` มันจะดูที่อาร์มของ match ทั้งสอง อาร์มแรกมีค่าเป็น `u32` และอาร์มหลังมีค่าเป็น `!` เพราะ `!` ไม่มีทางมีค่าได้เลย Rust จึงตัดสินใจว่าชนิดของ `guess` คือ `u32`

วิธีอธิบายพฤติกรรมนี้อย่างเป็นทางการคือ เอ็กซ์เพรสชันที่มีชนิด `!` สามารถถูกบังคับให้เป็นชนิดอื่นใดก็ได้ เราได้รับอนุญาตให้ลงท้ายอาร์มของ `match` นี้ด้วย `continue` เพราะ `continue` ไม่คืนค่า แต่จะย้ายการควบคุมกลับไปยังด้านบนของลูปแทน ดังนั้นในกรณี `Err` เราจึงไม่กำหนดค่าให้กับ `guess` เลย

ในที่นี้ ลูปไม่สิ้นสุดเลย ดังนั้น `!` จึงเป็นค่าของเอ็กซ์เพรสชัน อย่างไรก็ตาม สิ่งนี้จะไม่เป็นจริงหากเราใส่ `break` เพราะลูปจะสิ้นสุดลงเมื่อไปถึง `break`

### ชนิดข้อมูลขนาดไดนามิกและเทรต `Sized`

Rust จำเป็นต้องรู้รายละเอียดบางอย่างเกี่ยวกับชนิดข้อมูลของมัน เช่นต้องจัดสรรพื้นที่เท่าใดสำหรับค่าของชนิดข้อมูลหนึ่งๆ สิ่งนี้ทำให้มุมหนึ่งของระบบชนิดข้อมูลของมันสับสนเล็กน้อยในตอนแรก: แนวคิดของ_ชนิดข้อมูลขนาดไดนามิก_ ซึ่งบางครั้งเรียกว่า _DST_ หรือ _ชนิดข้อมูลที่ไม่มีขนาด (unsized type)_ ชนิดข้อมูลเหล่านี้ให้เราเขียนโค้ดโดยใช้ค่าที่เรารู้ขนาดได้เพียงตอนรันไทม์เท่านั้น

มาดำดิ่งลงในรายละเอียดของชนิดข้อมูลขนาดไดนามิกชื่อ `str` ซึ่งเราใช้มาตลอดทั้งเล่มกัน ถูกต้องแล้ว ไม่ใช่ `&str` แต่ `str` เพียงลำพังเป็น DST ในหลายกรณี เช่นเมื่อจัดเก็บข้อความที่ผู้ใช้ป้อน เราไม่สามารถรู้ได้ว่าสตริงยาวเท่าใดจนกว่าจะถึงตอนรันไทม์ นั่นหมายความว่าเราสร้างตัวแปรชนิด `str` ไม่ได้ และรับอาร์กิวเมนต์ชนิด `str` ก็ไม่ได้ พิจารณาโค้ดต่อไปนี้ซึ่งใช้ไม่ได้:

```rust,ignore,does_not_compile
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-11-cant-create-str/src/main.rs:here}}
```

Rust จำเป็นต้องรู้ว่าต้องจัดสรรหน่วยความจำเท่าใดสำหรับค่าใดๆ ของชนิดข้อมูลหนึ่งๆ และค่าทุกค่าของชนิดข้อมูลหนึ่งๆ ต้องใช้หน่วยความจำเท่ากัน หาก Rust ยอมให้เราเขียนโค้ดนี้ ค่า `str` สองค่าจะต้องใช้พื้นที่เท่ากัน แต่ทั้งสองมีความยาวต่างกัน: `s1` ต้องใช้พื้นที่จัดเก็บ 12 ไบต์ และ `s2` ต้องใช้ 15 ด้วยเหตุนี้จึงเป็นไปไม่ได้ที่จะสร้างตัวแปรที่บรรจุชนิดข้อมูลขนาดไดนามิก

แล้วเราทำอย่างไรดี? ในกรณีนี้ คุณรู้คำตอบอยู่แล้ว: เราทำให้ชนิดของ `s1` และ `s2` เป็นสตริงสไลซ์ (string slice) (`&str`) แทนที่จะเป็น `str` ย้อนนึกจากหัวข้อ[“สตริงสไลซ์”][string-slices]<!-- ignore --> ในบทที่ 4 ว่าโครงสร้างข้อมูลสไลซ์เก็บเพียงตำแหน่งเริ่มต้นและความยาวของสไลซ์ ดังนั้น แม้ว่า `&T` จะเป็นค่าเดียวที่เก็บแอดเดรสหน่วยความจำของตำแหน่งที่ `T` อยู่ สตริงสไลซ์ก็เป็น_สอง_ค่า: แอดเดรสของ `str` และความยาวของมัน ด้วยเหตุนี้ เราจึงรู้ขนาดของค่าสตริงสไลซ์ได้ตอนคอมไพล์: มันเป็นสองเท่าของความยาวของ `usize` นั่นคือ เรารู้ขนาดของสตริงสไลซ์เสมอ ไม่ว่าสตริงที่มันอ้างถึงจะยาวเท่าใดก็ตาม โดยทั่วไป นี่คือวิธีที่ชนิดข้อมูลขนาดไดนามิกถูกใช้ใน Rust: พวกมันมีเมทาดาทา (metadata) เพิ่มเติมเล็กน้อยที่เก็บขนาดของข้อมูลไดนามิก กฎทองของชนิดข้อมูลขนาดไดนามิกคือเราต้องวางค่าของชนิดข้อมูลขนาดไดนามิกไว้หลังพอยน์เตอร์เสมอ

เราสามารถรวม `str` กับพอยน์เตอร์ได้ทุกแบบ: ตัวอย่างเช่น `Box<str>` หรือ `Rc<str>` อันที่จริง คุณเคยเห็นสิ่งนี้มาก่อนแล้วแต่กับชนิดข้อมูลขนาดไดนามิกอีกชนิดหนึ่ง: เทรต ทุกเทรตเป็นชนิดข้อมูลขนาดไดนามิกที่เราสามารถอ้างถึงได้โดยใช้ชื่อของเทรต ในหัวข้อ[“การใช้เทรตออบเจกต์เพื่อนามธรรมพฤติกรรมร่วม”][using-trait-objects-to-abstract-over-shared-behavior]<!--
ignore --> ในบทที่ 18 เราได้กล่าวว่าในการใช้เทรตเป็นเทรตออบเจกต์ (trait object) เราต้องวางมันไว้หลังพอยน์เตอร์ เช่น `&dyn Trait` หรือ `Box<dyn Trait>` (`Rc<dyn Trait>` ก็ใช้ได้เช่นกัน)

ในการทำงานกับ DST นั้น Rust จัดเตรียมเทรต `Sized` ไว้เพื่อระบุว่าขนาดของชนิดข้อมูลหนึ่งๆ เป็นที่รู้กันตอนคอมไพล์หรือไม่ เทรตนี้ถูกอิมพลีเมนต์โดยอัตโนมัติให้กับทุกสิ่งที่มีขนาดเป็นที่รู้กันตอนคอมไพล์ นอกจากนี้ Rust ยังเพิ่มบาวด์ (bound) บน `Sized` ให้กับฟังก์ชันเจเนอริก (generic) ทุกตัวโดยปริยาย นั่นคือ นิยามฟังก์ชันเจเนอริกแบบนี้:

```rust,ignore
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-12-generic-fn-definition/src/lib.rs}}
```

จริงๆ แล้วถูกปฏิบัติเสมือนว่าเราได้เขียนแบบนี้:

```rust,ignore
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-13-generic-implicit-sized-bound/src/lib.rs}}
```

โดยค่าเริ่มต้น ฟังก์ชันเจเนอริกจะทำงานกับเฉพาะชนิดข้อมูลที่มีขนาดเป็นที่รู้กันตอนคอมไพล์เท่านั้น อย่างไรก็ตาม คุณสามารถใช้วากยสัมพันธ์พิเศษต่อไปนี้เพื่อผ่อนปรนข้อจำกัดนี้:

```rust,ignore

```

บาวด์ของเทรต (trait bound) บน `?Sized` หมายความว่า “`T` อาจเป็น `Sized` หรือไม่เป็นก็ได้” และสัญกรณ์นี้แทนที่ค่าเริ่มต้นที่ว่าชนิดข้อมูลเจเนอริกต้องมีขนาดเป็นที่รู้กันตอนคอมไพล์ วากยสัมพันธ์ `?Trait` ที่มีความหมายนี้ใช้ได้กับเฉพาะ `Sized` เท่านั้น ไม่ใช่เทรตอื่นใด

โปรดสังเกตด้วยว่าเราเปลี่ยนชนิดของพารามิเตอร์ `t` จาก `T` เป็น `&T` เพราะชนิดข้อมูลอาจไม่เป็น `Sized` เราจึงต้องใช้มันผ่านพอยน์เตอร์บางรูปแบบ ในกรณีนี้ เราเลือกใช้เรเฟอเรนซ์ (reference)
