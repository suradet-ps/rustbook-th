## ชนิดข้อมูลขั้นสูง

ระบบชนิดข้อมูลของ Rust ยังมีฟีเจอร์บางประการที่เราเคยกล่าวถึงมาบ้างแล้ว แต่ยังไม่ได้อธิบายในรายละเอียด เราจะเริ่มต้นด้วยการศึกษาเกี่ยวกับรูปแบบนิวไทป์ (newtypes) ในภาพรวม พร้อมทั้งพิจารณาว่าเหตุใดรูปแบบนี้จึงมีประโยชน์ในฐานะชนิดข้อมูล จากนั้นเราจะไปต่อกันที่นามแฝงชนิดข้อมูล (type aliases) ซึ่งเป็นฟีเจอร์ที่คล้ายกับนิวไทป์แต่มีความหมายเชิงความหมาย (semantics) แตกต่างกันเล็กน้อย นอกจากนี้เรายังจะกล่าวถึงชนิดข้อมูล `!` (never type) และชนิดข้อมูลที่กำหนดขนาดแบบไดนามิก (dynamically sized types) อีกด้วย

### ความปลอดภัยของชนิดข้อมูลและแอบสแตรกชันด้วยแพตเทิร์นนิวไทป์

หัวข้อนี้ตั้งอยู่บนสมมติฐานว่าคุณได้อ่านหัวข้อ[“การอิมพลีเมนต์เทรตภายนอกด้วยแพตเทิร์นนิวไทป์”][newtype]<!-- ignore --> ในตอนต้นมาแล้ว รูปแบบนิวไทป์ (newtype pattern) ยังมีประโยชน์ต่องานอื่น ๆ นอกเหนือจากที่เราได้กล่าวไปแล้ว ซึ่งรวมถึงการบังคับความถูกต้องในระดับสแตติก (statically enforcing) เพื่อป้องกันไม่ให้เกิดความสับสนในการใช้งานค่าต่าง ๆ และการใช้ระบุหน่วยวัดของค่าข้อมูล คุณได้เห็นตัวอย่างการนำนิวไทป์มาใช้ระบุหน่วยวัดในลิสติ้ง 20-16 ไปแล้ว: ย้อนนึกถึง struct `Millimeters` และ `Meters` ที่นำค่า `u32` มาห่อหุ้มไว้ในนิวไทป์ หากเราเขียนฟังก์ชันที่รับพารามิเตอร์ชนิด `Millimeters` คอมไพเลอร์จะไม่อนุญาตให้โปรแกรมคอมไพล์ผ่าน หากเผลอเรียกใช้ฟังก์ชันนั้นด้วยค่าชนิด `Meters` หรือค่า `u32` ธรรมดา

นอกจากนี้ เรายังสามารถใช้รูปแบบนิวไทป์เพื่อซ่อนรายละเอียดการอิมพลีเมนต์บางส่วนของชนิดข้อมูลได้ด้วย โดยชนิดข้อมูลใหม่สามารถเปิดเผย API สาธารณะที่แตกต่างไปจาก API ของชนิดข้อมูลภายในซึ่งถูกซ่อนไว้เป็นส่วนตัว

นิวไทป์ยังสามารถช่วยซ่อนการทำงานภายในได้เป็นอย่างดี ตัวอย่างเช่น เราสามารถสร้างชนิดข้อมูล `People` ขึ้นมาเพื่อห่อหุ้ม `HashMap<i32, String>` ที่จัดเก็บ ID ของบุคคลคู่กับชื่อของบุคคลนั้น โค้ดที่เรียกใช้ `People` จะโต้ตอบเฉพาะกับ API สาธารณะที่เราเตรียมไว้ให้เท่านั้น เช่น เมธอดสำหรับเพิ่มชื่อสตริงลงในคอลเลกชัน `People` โดยโค้ดภายนอกไม่จำเป็นต้องรับรู้เลยว่าภายในเรากำหนด ID ชนิด `i32` ให้กับชื่อต่าง ๆ อย่างไร รูปแบบนิวไทป์จึงเป็นวิธีที่เบาและเรียบง่ายในการสร้างการห่อหุ้ม (encapsulation) เพื่อซ่อนรายละเอียดการอิมพลีเมนต์ ดังที่เราได้พูดคุยกันในหัวข้อ[“การห่อหุ้มที่ซ่อนรายละเอียดการอิมพลีเมนต์”][encapsulation-that-hides-implementation-details]<!-- ignore --> ในบทที่ 18

### ชนิดไม่คืนค่าที่ไม่คืนค่าเลย

Rust มีชนิดข้อมูลพิเศษที่มีชื่อว่า `!` ซึ่งในเชิงทฤษฎีชนิดข้อมูล (type theory) จะเรียกว่า _ชนิดข้อมูลว่าง (empty type)_ เนื่องจากชนิดข้อมูลนี้ไม่มีค่าใด ๆ เลย แต่เรานิยมเรียกว่า _ชนิดไม่คืนค่า (never type)_ เพราะมันจะถูกนำมาวางแทนตำแหน่งของชนิดข้อมูลคืนค่า เมื่อฟังก์ชันนั้นจะไม่มีวันคืนค่ากลับมาเลย นี่คือตัวอย่าง:

```rust,noplayground
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-07-never-type/src/lib.rs:here}}
```

โค้ดนี้อ่านความหมายได้ว่า “ฟังก์ชัน `bar` ไม่คืนค่าใด ๆ เลย” โดยฟังก์ชันที่ไม่เคยคืนค่ากลับมาจะเรียกว่า _ฟังก์ชันลู่ออก (diverging functions)_ เราไม่สามารถสร้างค่าของชนิดข้อมูล `!` ขึ้นมาได้ ดังนั้น `bar` จึงไม่มีทางส่งค่าคืนกลับมาได้อย่างแน่นอน

แต่ชนิดข้อมูลที่ไม่สามารถสร้างค่าได้เลยจะมีประโยชน์อย่างไร? ย้อนนึกถึงโค้ดจากลิสติ้ง 2-5 ซึ่งเป็นส่วนหนึ่งของเกมทายตัวเลข เราได้คัดลอกบางส่วนของโค้ดนั้นมาแสดงอีกครั้งในลิสติ้ง 20-27

ชนิดข้อมูลของ `guess` ในโค้ดนี้จะต้องเป็นทั้งจำนวนเต็ม _และ_ สตริงในเวลาเดียวกัน ซึ่ง Rust กำหนดไว้ว่า `guess` จะต้องมีเพียงชนิดข้อมูลเดียวเท่านั้น แล้วคำสั่ง `continue` คืนค่าอะไรกลับมาล่ะ? เหตุใดเราจึงได้รับอนุญาตให้คืนค่า `u32` จากกิ่งหนึ่ง และมีอีกกิ่งหนึ่งที่ลงท้ายด้วย `continue` ในลิสติ้ง 20-27 ได้?

อย่างที่คุณอาจเดาได้ ค่าของ `continue` คือชนิดข้อมูล `!` กล่าวคือ เมื่อ Rust ประเมินชนิดข้อมูลของ `guess` คอมไพเลอร์จะดูที่กิ่งทั้งสองของ match โดยกิ่งแรกให้ค่าเป็น `u32` และกิ่งหลังให้ค่าเป็น `!` และเนื่องจาก `!` ไม่มีวันมีค่าอยู่จริง Rust จึงตัดสินว่าชนิดข้อมูลของ `guess` คือ `u32`

หากจะอธิบายพฤติกรรมนี้อย่างเป็นทางการก็คือ นิพจน์ที่มีชนิดข้อมูล `!` สามารถแปลงชนิดข้อมูลแบบบังคับ (coerce) ไปเป็นชนิดข้อมูลอื่นใดก็ได้ เราจึงสามารถลงท้ายกิ่งของ `match` ด้วย `continue` ได้อย่างถูกต้อง เพราะ `continue` ไม่ได้คืนค่า แต่จะส่งการควบคุมกลับไปยังจุดเริ่มต้นของลูปแทน ดังนั้นในกรณี `Err` เราจึงไม่ต้องกำหนดค่าใด ๆ ให้กับ `guess` เลย

ในโค้ดนี้ เกิดกระบวนการแบบเดียวกับ `match` ในลิสติ้ง 20-27: Rust ตรวจพบว่า `val` มีชนิดข้อมูล `T` และ `panic!` มีชนิดข้อมูล `!` ดังนั้นผลลัพธ์ของนิพจน์ `match` โดยรวมจึงเป็น `T` โค้ดนี้ทำงานได้ถูกต้องเพราะ `panic!` ไม่ได้สร้างค่าส่งกลับมา แต่เป็นการยุติการทำงานของโปรแกรม ในกรณีที่เป็น `None` เราจะไม่คืนค่าใด ๆ จาก `unwrap` โค้ดนี้จึงถูกต้องสมบูรณ์

นิพจน์สุดท้ายที่มีชนิดข้อมูลเป็น `!` คือลูปที่ไม่รู้จบ:

```rust,ignore
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-10-loop-returns-never/src/main.rs:here}}
```

ในกรณีนี้ ลูปไม่มีวันสิ้นสุดลง ค่าของนิพจน์จึงเป็น `!` อย่างไรก็ตาม สิ่งนี้จะไม่เป็นจริงหากเราใส่คำสั่ง `break` เข้าไป เพราะลูปจะหยุดทำงานเมื่อทำงานไปถึงจุดที่มี `break`

### ชนิดข้อมูลขนาดไดนามิกและเทรต `Sized`

Rust จำเป็นต้องทราบรายละเอียดบางอย่างเกี่ยวกับชนิดข้อมูล เช่น ต้องจัดสรรพื้นที่หน่วยความจำเท่าใดสำหรับค่าของชนิดข้อมูลหนึ่ง ๆ จุดนี้อาจทำให้ระบบชนิดข้อมูลของ Rust ดูชวนสับสนอยู่บ้างในตอนแรก นั่นคือแนวคิดเรื่อง _ชนิดข้อมูลที่กำหนดขนาดแบบไดนามิก (dynamically sized types)_ ซึ่งบางครั้งเรียกว่า _DSTs_ หรือ _ชนิดข้อมูลที่ไม่มีขนาดแน่นอน (unsized types)_ ชนิดข้อมูลเหล่านี้ช่วยให้เราสามารถเขียนโค้ดเพื่อจัดการกับค่าข้อมูลที่เราจะทราบขนาดได้ในตอนรันไทม์เท่านั้น

ลองมาเจาะลึกในรายละเอียดของชนิดข้อมูลที่กำหนดขนาดแบบไดนามิกตัวหนึ่งที่ชื่อว่า `str` ซึ่งเราใช้งานกันมาตลอดทั้งเล่ม ถูกต้องแล้วครับ เราไม่ได้หมายถึง `&str` แต่หมายถึง `str` เดี่ยว ๆ ซึ่งจัดเป็น DST ในหลายกรณี เช่น การจัดเก็บข้อความที่ผู้ใช้ป้อนเข้ามา เราไม่สามารถทราบล่วงหน้าได้ว่าสตริงจะมีความยาวเท่าใดจนกว่าจะถึงตอนรันไทม์ นั่นหมายความว่าเราไม่สามารถสร้างตัวแปรชนิด `str` ขึ้นมาโดยตรง และไม่สามารถรับอาร์กิวเมนต์เป็นชนิด `str` ได้ ลองพิจารณาโค้ดต่อไปนี้ซึ่งจะไม่สามารถทำงานได้:

```rust,ignore,does_not_compile
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-11-cant-create-str/src/main.rs:here}}
```

Rust จำเป็นต้องทราบว่าต้องจัดสรรหน่วยความจำเท่าใดสำหรับค่าใด ๆ ของชนิดข้อมูลนั้น และค่าทุกค่าของชนิดข้อมูลเดียวกันจะต้องใช้พื้นที่หน่วยความจำเท่ากันเสมอ หาก Rust อนุญาตให้เราเขียนโค้ดนี้ได้ ค่า `str` ทั้งสองตัวนี้ก็จะต้องใช้พื้นที่เท่ากัน แต่ในความเป็นจริงทั้งคู่มีความยาวต่างกัน: `s1` ต้องใช้พื้นที่ 12 ไบต์ ส่วน `s2` ต้องใช้ 15 ไบต์ นี่คือเหตุผลว่าทำไมเราจึงไม่สามารถสร้างตัวแปรที่เก็บชนิดข้อมูลที่กำหนดขนาดแบบไดนามิกได้โดยตรง

แล้วเรามีวิธีแก้อย่างไร? ในกรณีนี้ คุณคงทราบคำตอบดีอยู่แล้ว: เราเปลี่ยนชนิดข้อมูลของ `s1` และ `s2` ให้เป็นสตริงสไลซ์ (`&str`) แทนที่จะเป็น `str` ย้อนนึกถึงหัวข้อ[“สตริงสไลซ์”][string-slices]<!-- ignore --> ในบทที่ 4 ซึ่งระบุว่าโครงสร้างข้อมูลของสไลซ์จะเก็บเพียงตำแหน่งเริ่มต้นและความยาวของสไลซ์เท่านั้น ดังนั้น แม้ว่า `&T` จะเป็นค่าเดี่ยว ๆ ที่เก็บแอดเดรสหน่วยความจำที่ `T` วางอยู่ แต่สตริงสไลซ์จะประกอบด้วยค่า _สอง_ ค่า ได้แก่ แอดเดรสของ `str` และความยาวของมัน ด้วยเหตุนี้ เราจึงสามารถทราบขนาดของค่าสตริงสไลซ์ได้ในตอนคอมไพล์ ซึ่งก็คือมีขนาดเป็น 2 เท่าของความยาวของชนิด `usize` นั่นหมายความว่าเราทราบขนาดของสตริงสไลซ์เสมอ ไม่ว่าข้อความสตริงที่มันอ้างอิงถึงจะมีความยาวเท่าใดก็ตาม โดยทั่วไปแล้ว นี่คือวิธีการที่ Rust ใช้จัดการกับชนิดข้อมูลที่กำหนดขนาดแบบไดนามิก: มีการแนบข้อมูลเมทาดาทา (metadata) เพิ่มเติมเล็กน้อยเพื่อเก็บขนาดของข้อมูลแบบไดนามิกนั้น กฎเหล็กของชนิดข้อมูลที่กำหนดขนาดแบบไดนามิกคือ เราจะต้องวางค่าของชนิดข้อมูลดังกล่าวไว้เบื้องหลังพอยน์เตอร์เสมอ

เราสามารถใช้งาน `str` ร่วมกับพอยน์เตอร์ได้ทุกรูปแบบ เช่น `Box<str>` หรือ `Rc<str>` อันที่จริง คุณเคยพบเห็นรูปแบบนี้มาก่อนแล้วกับชนิดข้อมูลที่กำหนดขนาดแบบไดนามิกอีกประเภทหนึ่ง นั่นคือ เทรต (traits) ทุกเทรตถือเป็นชนิดข้อมูลที่กำหนดขนาดแบบไดนามิกที่เราสามารถอ้างอิงถึงได้โดยใช้ชื่อของเทรตนั้น ในหัวข้อ[“การใช้เทรตออบเจกต์เพื่อนามธรรมพฤติกรรมร่วม”][using-trait-objects-to-abstract-over-shared-behavior]<!--
ignore --> ในบทที่ 18 เราได้อธิบายว่าในการใช้งานเทรตในฐานะเทรตออบเจกต์ (trait object) เราจะต้องวางเทรตไว้เบื้องหลังพอยน์เตอร์เสมอ เช่น `&dyn Trait` หรือ `Box<dyn Trait>` (`Rc<dyn Trait>` ก็ใช้ได้เช่นกัน)

ในการทำงานร่วมกับ DST นั้น Rust ได้เตรียมเทรต `Sized` ไว้เพื่อใช้ตัดสินว่าขนาดของชนิดข้อมูลหนึ่ง ๆ เป็นที่ทราบแน่ชัดในตอนคอมไพล์หรือไม่ เทรตนี้จะได้รับการอิมพลีเมนต์ให้โดยอัตโนมัติสำหรับทุกชนิดข้อมูลที่ทราบขนาดในตอนคอมไพล์ นอกจากนี้ Rust ยังเพิ่มข้อกำหนดบนเทรต `Sized` ให้กับฟังก์ชันเจเนอริกทุกฟังก์ชันโดยปริยาย กล่าวคือนิยามฟังก์ชันเจเนอริกที่มีลักษณะดังนี้:

```rust,ignore
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-12-generic-fn-definition/src/lib.rs}}
```

แท้จริงแล้วจะได้รับการปฏิบัติต่อเสมือนว่าเราเขียนไว้เช่นนี้:

```rust,ignore
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-13-generic-implicit-sized-bound/src/lib.rs}}
```

โดยค่าเริ่มต้น ฟังก์ชันเจเนอริกจะทำงานได้เฉพาะกับชนิดข้อมูลที่ทราบขนาดในตอนคอมไพล์เท่านั้น อย่างไรก็ตาม คุณสามารถใช้ไวยากรณ์พิเศษต่อไปนี้เพื่อผ่อนปรนข้อจำกัดดังกล่าวได้:

```rust,ignore
{{#rustdoc_include ../listings/ch20-advanced-features/no-listing-14-generic-maybe-sized/src/lib.rs}}
```

ข้อกำหนดเทรตบน `?Sized` มีความหมายว่า “`T` อาจทราบขนาด (`Sized`) หรือไม่ทราบขนาดก็ได้” และสัญลักษณ์นี้จะเข้าแทนที่ข้อกำหนดเริ่มต้นที่ว่าชนิดข้อมูลเจเนอริกต้องทราบขนาดในตอนคอมไพล์ ไวยากรณ์ `?Trait` ที่มีความหมายในลักษณะนี้เปิดให้ใช้งานได้เฉพาะกับเทรต `Sized` เท่านั้น ไม่สามารถใช้กับเทรตอื่นใดได้

โปรดสังเกตด้วยว่าเราเปลี่ยนชนิดข้อมูลของพารามิเตอร์ `t` จาก `T` เป็น `&T` เนื่องจากชนิดข้อมูลอาจไม่ทราบขนาด (`!Sized`) เราจึงจำเป็นต้องเรียกใช้งานผ่านพอยน์เตอร์รูปแบบใดรูปแบบหนึ่ง ซึ่งในกรณีนี้เราเลือกใช้การอ้างอิง (reference)

ในหัวข้อถัดไป เราจะมาพูดคุยกันถึงเรื่องฟังก์ชันและโคลเชอร์ขั้นสูงกันต่อ!
