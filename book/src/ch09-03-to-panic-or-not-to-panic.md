## จะ `panic!` หรือไม่ `panic!`

แล้วคุณจะตัดสินใจอย่างไรว่าเมื่อใดควรเรียก `panic!` และเมื่อใดควรคืนค่า `Result`? เมื่อโค้ดแพนิก (panic) ก็ไม่มีทางกู้คืนได้ คุณอาจเรียก `panic!` กับทุกสถานการณ์ที่เกิดข้อผิดพลาด ไม่ว่าจะมีทางกู้คืนได้หรือไม่ก็ตาม แต่การทำเช่นนั้นคุณกำลังตัดสินใจแทนโค้ดที่เรียกใช้ว่าสถานการณ์หนึ่งเป็นสิ่งที่กู้คืนไม่ได้ เมื่อคุณเลือกที่จะคืนค่า `Result` คุณให้ทางเลือกแก่โค้ดที่เรียกใช้ โค้ดที่เรียกใช้อาจเลือกพยายามกู้คืนในแบบที่เหมาะสมกับสถานการณ์ของมัน หรืออาจตัดสินว่าค่า `Err` ในกรณีนี้กู้คืนไม่ได้ จึงเรียก `panic!` และเปลี่ยนข้อผิดพลาดที่กู้คืนได้ (recoverable error) ของคุณให้กลายเป็นข้อผิดพลาดที่กู้คืนไม่ได้ (unrecoverable error) ดังนั้น การคืนค่า `Result` จึงเป็นตัวเลือกเริ่มต้นที่ดีเมื่อคุณนิยามฟังก์ชันที่อาจล้มเหลว

ในสถานการณ์อย่างตัวอย่าง โค้ดต้นแบบ (prototype) และการทดสอบ การเขียนโค้ดที่แพนิกเหมาะสมกว่าแทนที่จะคืนค่า `Result` มาสำรวจกันว่าทำไม แล้วเราจะพูดคุยถึงสถานการณ์ที่คอมไพเลอร์บอกไม่ได้ว่าความล้มเหลวเป็นไปไม่ได้ แต่คุณในฐานะมนุษย์บอกได้ บทนี้จะสรุปด้วยแนวทางทั่วไปบางประการเกี่ยวกับวิธีตัดสินใจว่าจะแพนิกหรือไม่ในโค้ดไลบรารี

### ตัวอย่าง โค้ดต้นแบบ และการทดสอบ

เมื่อคุณเขียนตัวอย่างเพื่ออธิบายแนวคิดบางอย่าง การรวมโค้ดจัดการข้อผิดพลาด (error handling) ที่ทนทานเข้าไปด้วยอาจทำให้ตัวอย่างชัดเจนน้อยลง ในตัวอย่าง เป็นที่เข้าใจกันว่าการเรียกเมธอดอย่าง `unwrap` ที่อาจแพนิกนั้นมีเจตนาเป็นตัวยึดตำแหน่ง (placeholder) สำหรับวิธีที่คุณต้องการให้แอปพลิเคชันของคุณจัดการข้อผิดพลาด ซึ่งอาจแตกต่างกันไปตามสิ่งที่โค้ดส่วนอื่นๆ ของคุณทำอยู่

ในทำนองเดียวกัน เมธอด `unwrap` และ `expect` มีประโยชน์มากเมื่อคุณกำลังทำต้นแบบและยังไม่พร้อมตัดสินใจว่าจะจัดการข้อผิดพลาดอย่างไร พวกมันทิ้งเครื่องหมายที่ชัดเจนไว้ในโค้ดของคุณสำหรับตอนที่คุณพร้อมจะทำให้โปรแกรมของคุณทนทานมากขึ้น

หากการเรียกเมธอดล้มเหลวในการทดสอบ คุณคงต้องการให้การทดสอบทั้งหมดล้มเหลว แม้ว่าเมธอดนั้นจะไม่ใช่ฟังก์ชันการทำงานที่กำลังทดสอบก็ตาม เนื่องจากการแพนิกเป็นวิธีที่ทำให้การทดสอบถูกทำเครื่องหมายว่าล้มเหลว การเรียก `unwrap` หรือ `expect` จึงเป็นสิ่งที่ควรเกิดขึ้นพอดี

### เมื่อคุณมีข้อมูลมากกว่าคอมไพเลอร์

การเรียก `expect` ก็เหมาะสมเช่นกันเมื่อคุณมีลอจิกอื่นที่รับประกันว่าค่า `Result` จะมีค่าเป็น `Ok` แต่ลอจิกนั้นไม่ใช่สิ่งที่คอมไพเลอร์เข้าใจ คุณยังคงมีค่า `Result` ที่คุณต้องจัดการ: ไม่ว่าคุณจะเรียกการดำเนินการใด มันก็ยังมีความเป็นไปได้ที่จะล้มเหลวโดยทั่วไป แม้ว่ามันจะเป็นไปไม่ได้ในเชิงตรรกะในสถานการณ์เฉพาะของคุณ หากคุณมั่นใจได้ด้วยการตรวจสอบโค้ดด้วยตนเองว่าคุณจะไม่มีวาเรียนต์ `Err` เลย การเรียก `expect` และบันทึกเหตุผลที่คุณคิดว่าจะไม่มีวาเรียนต์ `Err` ลงในข้อความอาร์กิวเมนต์นั้นเป็นสิ่งที่ยอมรับได้อย่างสมบูรณ์ นี่คือตัวอย่าง:

```rust
{{#rustdoc_include ../listings/ch09-error-handling/no-listing-08-unwrap-that-cant-fail/src/main.rs:here}}
```

เรากำลังสร้างอินสแตนซ์ `IpAddr` ด้วยการแยกวิเคราะห์ (parse) สตริงที่ฮาร์ดโค้ดไว้ เราจะเห็นว่า `127.0.0.1` เป็นที่อยู่ IP ที่ถูกต้อง จึงยอมรับได้ที่จะใช้ `expect` ที่นี่ อย่างไรก็ตาม การมีสตริงที่ถูกต้องและฮาร์ดโค้ดไว้ไม่ได้เปลี่ยนชนิดที่คืนกลับของเมธอด `parse`: เรายังคงได้ค่า `Result` และคอมไพเลอร์ก็ยังบังคับให้เราจัดการ `Result` ราวกับว่าวาเรียนต์ `Err` เป็นไปได้ เพราะคอมไพเลอร์ฉลาดไม่พอที่จะเห็นว่าสตริงนี้เป็นที่อยู่ IP ที่ถูกต้องเสมอ หากสตริงที่อยู่ IP มาจากผู้ใช้แทนที่จะฮาร์ดโค้ดไว้ในโปรแกรม จึง_มี_ความเป็นไปได้ที่จะล้มเหลว เราก็ควรจัดการ `Result` ด้วยวิธีที่ทนทานกว่าอย่างแน่นอน การกล่าวถึงสมมติฐานที่ว่าที่อยู่ IP นี้ถูกฮาร์ดโค้ดไว้จะเตือนให้เราเปลี่ยน `expect` เป็นโค้ดจัดการข้อผิดพลาดที่ดีกว่า หากในอนาคตเราต้องรับที่อยู่ IP จากแหล่งอื่นแทน

### แนวทางสำหรับการจัดการข้อผิดพลาด

ขอแนะนำให้โค้ดของคุณแพนิกเมื่อเป็นไปได้ว่าโค้ดของคุณอาจลงเอยในสถานะที่ไม่ดี ในบริบทนี้ _สถานะที่ไม่ดี_ (bad state) คือเมื่อสมมติฐาน การรับประกัน สัญญา (contract) หรืออินวาเรียนต์ (invariant) บางอย่างถูกละเมิด เช่นเมื่อค่าที่ไม่ถูกต้อง ค่าที่ขัดแย้งกัน หรือค่าที่หายไปถูกส่งเข้ามาในโค้ดของคุณ รวมกับหนึ่งข้อหรือมากกว่าดังต่อไปนี้:

- สถานะที่ไม่ดีนั้นเป็นสิ่งที่ไม่คาดคิด ตรงข้ามกับสิ่งที่น่าจะเกิดขึ้นเป็นครั้งคราวตามธรรมชาติ เช่นผู้ใช้ป้อนข้อมูลในรูปแบบที่ผิด
- โค้ดของคุณหลังจากจุดนี้ต้องพึ่งพาการที่ไม่ได้อยู่ในสถานะที่ไม่ดีนี้ มากกว่าการตรวจสอบหาปัญหาในทุกขั้นตอน
- ไม่มีวิธีที่ดีในการเข้ารหัสข้อมูลนี้ในชนิดข้อมูลที่คุณใช้ เราจะทำตัวอย่างเพื่ออธิบายสิ่งที่เราหมายถึงใน[“การเข้ารหัสสถานะและพฤติกรรมเป็นชนิดข้อมูล”][encoding]<!-- ignore --> ในบทที่ 18

หากมีคนเรียกโค้ดของคุณและส่งค่าที่ไม่สมเหตุสมผลเข้ามา ทางที่ดีที่สุดคือคืนข้อผิดพลาดหากคุณทำได้ เพื่อให้ผู้ใช้ไลบรารีตัดสินใจได้ว่าพวกเขาต้องการทำอะไรในกรณีนั้น อย่างไรก็ตาม ในกรณีที่การดำเนินต่อไปอาจไม่ปลอดภัยหรือเป็นอันตราย ทางเลือกที่ดีที่สุดอาจเป็นการเรียก `panic!` และแจ้งเตือนผู้ที่ใช้ไลบรารีของคุณถึงบั๊กในโค้ดของพวกเขา เพื่อให้พวกเขาแก้ไขได้ระหว่างการพัฒนา ในทำนองเดียวกัน `panic!` มักเหมาะสมหากคุณกำลังเรียกโค้ดภายนอกที่อยู่นอกเหนือการควบคุมของคุณและคืนสถานะที่ไม่ถูกต้องซึ่งคุณไม่มีทางแก้ไขได้

อย่างไรก็ตาม เมื่อความล้มเหลวเป็นสิ่งที่คาดหมายได้ การคืนค่า `Result` เหมาะสมกว่าการเรียก `panic!` ตัวอย่างเช่น ตัวแยกวิเคราะห์ (parser) ที่ได้รับข้อมูลที่ผิดรูปแบบ หรือคำขอ HTTP ที่คืนสถานะซึ่งบ่งชี้ว่าคุณได้ชนขีดจำกัดอัตราการเรียกใช้งานแล้ว ในกรณีเหล่านี้ การคืนค่า `Result` บ่งชี้ว่าความล้มเหลวเป็นความเป็นไปได้ที่คาดหมายได้ซึ่งโค้ดที่เรียกใช้ต้องตัดสินใจว่าจะจัดการอย่างไร

เมื่อโค้ดของคุณดำเนินการที่อาจทำให้ผู้ใช้ตกอยู่ในความเสี่ยงหากถูกเรียกด้วยค่าที่ไม่ถูกต้อง โค้ดของคุณควรตรวจสอบว่าค่านั้นถูกต้องก่อนและแพนิกหากค่าไม่ถูกต้อง ส่วนใหญ่เป็นเหตุผลด้านความปลอดภัย: การพยายามดำเนินการกับข้อมูลที่ไม่ถูกต้องอาจเปิดเผยโค้ดของคุณต่อช่องโหว่ นี่คือเหตุผลหลักที่ไลบรารีมาตรฐานจะเรียก `panic!` หากคุณพยายามเข้าถึงหน่วยความจำนอกขอบเขต: การพยายามเข้าถึงหน่วยความจำที่ไม่ได้เป็นของโครงสร้างข้อมูลปัจจุบันเป็นปัญหาความปลอดภัยที่พบบ่อย ฟังก์ชันมักมี_สัญญา_: พฤติกรรมของมันถูกรับประกันก็ต่อเมื่ออินพุตตรงตามข้อกำหนดเฉพาะ การแพนิกเมื่อสัญญาถูกละเมิดนั้นสมเหตุสมผล เพราะการละเมิดสัญญาบ่งชี้ถึงบั๊กฝั่งผู้เรียกเสมอ และมันไม่ใช่ข้อผิดพลาดชนิดที่คุณต้องการให้โค้ดที่เรียกใช้ต้องจัดการอย่างชัดแจ้ง อันที่จริง ไม่มีวิธีที่สมเหตุสมผลให้โค้ดที่เรียกใช้กู้คืนได้ _โปรแกรมเมอร์_ ที่เรียกใช้ต้องแก้ไขโค้ด สัญญาของฟังก์ชัน โดยเฉพาะเมื่อการละเมิดจะทำให้เกิดการแพนิก ควรอธิบายไว้ในเอกสาร API ของฟังก์ชันนั้น

อย่างไรก็ตาม การมีการตรวจสอบข้อผิดพลาดจำนวนมากในทุกฟังก์ชันของคุณจะทำให้โค้ดยาวและน่ารำคาญ โชคดีที่คุณสามารถใช้ระบบชนิดข้อมูลของ Rust (และด้วยเหตุนี้การตรวจสอบชนิดข้อมูลที่คอมไพเลอร์ทำ) เพื่อทำการตรวจสอบหลายอย่างให้คุณได้ หากฟังก์ชันของคุณมีชนิดข้อมูลเฉพาะเป็นพารามิเตอร์ คุณสามารถดำเนินการตามลอจิกของโค้ดของคุณได้โดยรู้ว่าคอมไพเลอร์ได้ทำให้แน่ใจแล้วว่าคุณมีค่าที่ถูกต้อง ตัวอย่างเช่น หากคุณมีชนิดข้อมูลแทนที่จะเป็น `Option` โปรแกรมของคุณคาดว่าจะมี_อะไรบางอย่าง_แทนที่จะ_ไม่มีอะไรเลย_ จากนั้นโค้ดของคุณก็ไม่ต้องจัดการสองกรณีสำหรับวาเรียนต์ `Some` และ `None`: มันจะมีเพียงกรณีเดียวสำหรับการมีค่าอย่างแน่นอน โค้ดที่พยายามส่งค่าไม่มีอะไรให้ฟังก์ชันของคุณจะไม่คอมไพล์ด้วยซ้ำ ดังนั้นฟังก์ชันของคุณจึงไม่ต้องตรวจสอบกรณีนั้นตอนรันไทม์ อีกตัวอย่างคือการใช้ชนิดจำนวนเต็มไม่มีเครื่องหมายอย่าง `u32` ซึ่งรับประกันว่าพารามิเตอร์จะไม่เป็นค่าลบ

### ชนิดข้อมูลที่กำหนดเองสำหรับการตรวจสอบความถูกต้อง

มาขยายแนวคิดการใช้ระบบชนิดข้อมูลของ Rust เพื่อรับประกันว่าเรามีค่าที่ถูกต้องไปอีกขั้น และดูการสร้างชนิดข้อมูลที่กำหนดเองสำหรับการตรวจสอบความถูกต้อง ย้อนนึกถึงเกมทายตัวเลขในบทที่ 2 ซึ่งโค้ดของเราขอให้ผู้ใช้ทายตัวเลขระหว่าง 1 ถึง 100 เราไม่เคยตรวจสอบว่าคำทายของผู้ใช้อยู่ระหว่างตัวเลขเหล่านั้นก่อนตรวจสอบกับเลขลับของเรา เราตรวจสอบเพียงว่าคำทายเป็นค่าบวกเท่านั้น ในกรณีนี้ ผลลัพธ์ไม่ได้ร้ายแรงนัก: เอาต์พุต “สูงเกินไป” หรือ “ต่ำเกินไป” ของเราก็ยังถูกต้อง แต่จะเป็นการปรับปรุงที่มีประโยชน์ที่จะแนะนำผู้ใช้ไปสู่คำทายที่ถูกต้อง และมีพฤติกรรมที่แตกต่างกันเมื่อผู้ใช้ทายตัวเลขที่อยู่นอกช่วง เทียบกับเมื่อผู้ใช้พิมพ์ตัวอักษรแทน เป็นต้น

วิธีหนึ่งที่จะทำเช่นนี้คือแยกวิเคราะห์คำทายเป็น `i32` แทนที่จะเป็นเพียง `u32` เพื่ออนุญาตตัวเลขที่อาจเป็นค่าลบ แล้วเพิ่มการตรวจสอบว่าตัวเลขอยู่ในช่วงหรือไม่ ดังนี้:

เอ็กซ์เพรสชัน `if` ตรวจสอบว่าค่าของเราอยู่นอกช่วงหรือไม่ แจ้งให้ผู้ใช้ทราบเกี่ยวกับปัญหา และเรียก `continue` เพื่อเริ่มการวนซ้ำครั้งถัดไปของลูปและขอคำทายใหม่ หลังจากเอ็กซ์เพรสชัน `if` เราสามารถดำเนินการเปรียบเทียบระหว่าง `guess` กับเลขลับได้โดยรู้ว่า `guess` อยู่ระหว่าง 1 ถึง 100

อย่างไรก็ตาม นี่ไม่ใช่วิธีแก้ที่สมบูรณ์แบบ: หากเป็นเรื่องวิกฤตอย่างยิ่งที่โปรแกรมจะดำเนินการกับค่าเฉพาะระหว่าง 1 ถึง 100 เท่านั้น และมันมีฟังก์ชันหลายฟังก์ชันที่มีข้อกำหนดนี้ การมีการตรวจสอบแบบนี้ในทุกฟังก์ชันจะน่าเบื่อ (และอาจส่งผลต่อประสิทธิภาพ)

แต่เราสามารถสร้างชนิดข้อมูลใหม่ในมอดูล (module) เฉพาะทาง และใส่การตรวจสอบความถูกต้องไว้ในฟังก์ชันสำหรับสร้างอินสแตนซ์ของชนิดข้อมูลนั้น แทนที่จะทำการตรวจสอบซ้ำๆ ทุกที่ ด้วยวิธีนี้ ฟังก์ชันต่างๆ จะปลอดภัยที่จะใช้ชนิดข้อมูลใหม่ในลายเซ็นของพวกมันและใช้ค่าที่ได้รับอย่างมั่นใจ ลิสติ้ง 9-13 แสดงวิธีหนึ่งในการนิยามชนิด `Guess` ที่จะสร้างอินสแตนซ์ของ `Guess` ก็ต่อเมื่อฟังก์ชัน `new` ได้รับค่าระหว่าง 1 ถึง 100

โปรดสังเกตว่าโค้ดใน *src/guessing_game.rs* นี้ขึ้นอยู่กับการเพิ่มการประกาศมอดูล `mod guessing_game;` ใน *src/lib.rs* ที่เราไม่ได้แสดงไว้ที่นี่ ภายในไฟล์ของมอดูลใหม่นี้ เรานิยาม struct ชื่อ `Guess` ที่มีฟิลด์ชื่อ `value` ซึ่งบรรจุค่า `i32` นี่คือที่ที่ตัวเลขจะถูกจัดเก็บ

จากนั้น เราอิมพลีเมนต์ฟังก์ชันที่เชื่อมโยงกับชนิดข้อมูล (associated function) ชื่อ `new` บน `Guess` ที่สร้างอินสแตนซ์ของค่า `Guess` ฟังก์ชัน `new` ถูกนิยามให้มีพารามิเตอร์หนึ่งตัวชื่อ `value` ชนิด `i32` และคืนค่า `Guess` โค้ดในเนื้อในของฟังก์ชัน `new` ทดสอบ `value` เพื่อทำให้แน่ใจว่ามันอยู่ระหว่าง 1 ถึง 100 หาก `value` ไม่ผ่านการทดสอบนี้ เราจะเรียก `panic!` ซึ่งจะแจ้งเตือนโปรแกรมเมอร์ที่เขียนโค้ดที่เรียกใช้ว่าพวกเขามีบั๊กที่ต้องแก้ไข เพราะการสร้าง `Guess` ที่มี `value` นอกช่วงนี้จะละเมิดสัญญาที่ `Guess::new` พึ่งพาอยู่ เงื่อนไขที่ `Guess::new` อาจแพนิกควรถูกพูดคุยในเอกสาร API สาธารณะของมัน เราจะครอบคลุมธรรมเนียมการทำเอกสารที่บ่งชี้ความเป็นไปได้ของการ `panic!` ในเอกสาร API ที่คุณสร้างในบทที่ 14 หาก `value` ผ่านการทดสอบ เราจะสร้าง `Guess` ใหม่โดยตั้งฟิลด์ `value` ของมันเป็นพารามิเตอร์ `value` และคืนค่า `Guess`

ต่อไป เราอิมพลีเมนต์เมธอดชื่อ `value` ที่ยืม `self` ไม่มีพารามิเตอร์อื่น และคืนค่า `i32` เมธอดแบบนี้บางครั้งเรียกว่า_เก็ตเตอร์_ (getter) เพราะจุดประสงค์ของมันคือดึงข้อมูลบางอย่างจากฟิลด์ของมันและคืนค่านั้น เมธอดสาธารณะนี้จำเป็นเพราะฟิลด์ `value` ของ struct `Guess` เป็นแบบส่วนตัว สิ่งสำคัญคือฟิลด์ `value` ต้องเป็นแบบส่วนตัว เพื่อให้โค้ดที่ใช้ struct `Guess` ไม่ได้รับอนุญาตให้ตั้งค่า `value` โดยตรง: โค้ดนอกมอดูล `guessing_game` _ต้อง_ ใช้ฟังก์ชัน `Guess::new` ในการสร้างอินสแตนซ์ของ `Guess` ซึ่งจะรับประกันว่าไม่มีทางที่ `Guess` จะมี `value` ที่ยังไม่ผ่านการตรวจสอบจากเงื่อนไขในฟังก์ชัน `Guess::new`

ฟังก์ชันที่มีพารามิเตอร์หรือคืนค่าเฉพาะตัวเลขระหว่าง 1 ถึง 100 ก็สามารถประกาศในลายเซ็นของมันว่ารับหรือคืนค่า `Guess` แทนที่จะเป็น `i32` และไม่จำเป็นต้องทำการตรวจสอบเพิ่มเติมในเนื้อในของมัน

## สรุป

ฟีเจอร์การจัดการข้อผิดพลาดของ Rust ถูกออกแบบมาเพื่อช่วยให้คุณเขียนโค้ดที่ทนทานมากขึ้น มาโคร `panic!` ส่งสัญญาณว่าโปรแกรมของคุณอยู่ในสถานะที่มันจัดการไม่ได้ และให้คุณบอกโปรเซสให้หยุด แทนที่จะพยายามดำเนินการต่อด้วยค่าที่ไม่ถูกต้องหรือผิดพลาด enum `Result` ใช้ระบบชนิดข้อมูลของ Rust เพื่อบ่งชี้ว่าการดำเนินการอาจล้มเหลวในแบบที่โค้ดของคุณกู้คืนได้ คุณใช้ `Result` เพื่อบอกโค้ดที่เรียกโค้ดของคุณว่ามันต้องจัดการกับความสำเร็จหรือความล้มเหลวที่อาจเกิดขึ้นด้วย การใช้ `panic!` และ `Result` ในสถานการณ์ที่เหมาะสมจะทำให้โค้ดของคุณเชื่อถือได้มากขึ้นเมื่อเผชิญกับปัญหาที่หลีกเลี่ยงไม่ได้

ตอนนี้คุณได้เห็นวิธีที่มีประโยชน์ที่ไลบรารีมาตรฐานใช้เจเนอริกกับ enum `Option` และ `Result` แล้ว เราจะพูดถึงว่าเจเนอริกทำงานอย่างไรและคุณจะใช้มันในโค้ดของคุณได้อย่างไร
