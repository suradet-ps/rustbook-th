## ข้อผิดพลาดที่กู้คืนไม่ได้ด้วย `panic!`

บางครั้งสิ่งเลวร้ายก็เกิดขึ้นในโค้ดของคุณ และไม่มีอะไรที่คุณทำได้ ในกรณีเหล่านี้ Rust มีมาโคร `panic!` ในทางปฏิบัติ มีสองวิธีที่จะทำให้เกิดการแพนิก (panic): ด้วยการทำการกระทำที่ทำให้โค้ดของเราแพนิก (เช่นการเข้าถึงอาร์เรย์ที่เลยจุดสิ้นสุด) หรือด้วยการเรียกมาโคร `panic!` อย่างชัดแจ้ง ในทั้งสองกรณี เราทำให้เกิดการแพนิกในโปรแกรมของเรา โดยค่าเริ่มต้น การแพนิกเหล่านี้จะพิมพ์ข้อความแสดงความล้มเหลว คลี่คลายสแตก ทำความสะอาดสแตก และออกจากโปรแกรม ผ่านตัวแปรสภาพแวดล้อม คุณยังสามารถให้ Rust แสดงสแตกการเรียก (call stack) เมื่อเกิดการแพนิก เพื่อให้ติดตามต้นตอของการแพนิกได้ง่ายขึ้น

> ### การคลี่คลายสแตกหรือการยกเลิกทันทีเมื่อเกิดการแพนิก
>
> โดยค่าเริ่มต้น เมื่อเกิดการแพนิก โปรแกรมจะเริ่ม_คลี่คลายสแตก_ (unwinding) ซึ่งหมายความว่า Rust จะไล่ย้อนกลับขึ้นไปตามสแตกและทำความสะอาดข้อมูลจากแต่ละฟังก์ชันที่มันพบ อย่างไรก็ตาม การไล่ย้อนกลับและทำความสะอาดต้องใช้การทำงานมากมาย Rust จึงอนุญาตให้คุณเลือกทางเลือกอื่นคือ_การยกเลิกทันที_ (aborting) ซึ่งจบโปรแกรมโดยไม่ทำความสะอาด
>
> หน่วยความจำที่โปรแกรมใช้อยู่จะต้องถูกทำความสะอาดโดยระบบปฏิบัติการ หากในโปรเจกต์ของคุณต้องการทำให้ไบนารีที่ได้มีขนาดเล็กที่สุด คุณสามารถเปลี่ยนจากการคลี่คลายสแตกเป็นการยกเลิกทันทีเมื่อเกิดการแพนิกได้ โดยเพิ่ม `panic = 'abort'` ลงในส่วน `[profile]` ที่เหมาะสมในไฟล์ _Cargo.toml_ ของคุณ ตัวอย่างเช่น หากคุณต้องการยกเลิกทันทีเมื่อเกิดการแพนิกในโหมดรีลีส ให้เพิ่มสิ่งนี้:
>
> ```toml
> [profile.release]
> panic = 'abort'
> ```

การเรียก `panic!` ทำให้เกิดข้อความแสดงข้อผิดพลาดที่อยู่ในสองบรรทัดสุดท้าย บรรทัดแรกแสดงข้อความแพนิกของเราและตำแหน่งในโค้ดซอร์สของเราที่การแพนิกเกิดขึ้น: _src/main.rs:2:5_ บ่งชี้ว่ามันคือบรรทัดที่สอง อักขระตัวที่ห้าของไฟล์ _src/main.rs_ ของเรา

ในกรณีนี้ บรรทัดที่ถูกระบุเป็นส่วนหนึ่งของโค้ดเรา และหากเราไปที่บรรทัดนั้น เราจะเห็นการเรียกมาโคร `panic!` ในกรณีอื่น การเรียก `panic!` อาจอยู่ในโค้ดที่โค้ดของเราเรียกใช้ และชื่อไฟล์กับหมายเลขบรรทัดที่ข้อความแสดงข้อผิดพลาดรายงานจะเป็นโค้ดของคนอื่นที่เรียกมาโคร `panic!` ไม่ใช่บรรทัดในโค้ดของเราที่นำไปสู่การเรียก `panic!` ในที่สุด

เราใช้แบ็กเทรซ (backtrace) ของฟังก์ชันที่การเรียก `panic!` มาจาก เพื่อหาว่าส่วนไหนของโค้ดเราที่ทำให้เกิดปัญหา เพื่อทำความเข้าใจวิธีใช้แบ็กเทรซของ `panic!` มาดูตัวอย่างอื่นและดูว่ามันเป็นอย่างไรเมื่อการเรียก `panic!` มาจากไลบรารีเพราะบั๊กในโค้ดของเรา แทนที่จะมาจากโค้ดของเราเรียกมาโครโดยตรง ลิสติ้ง 9-1 มีโค้ดที่พยายามเข้าถึงดัชนีในเวกเตอร์ (vector) ที่เลยช่วงของดัชนีที่ถูกต้อง

ในที่นี้ เรากำลังพยายามเข้าถึงองค์ประกอบที่ 100 ของเวกเตอร์เรา (ซึ่งอยู่ที่ดัชนี 99 เพราะการจัดดัชนีเริ่มจากศูนย์) แต่เวกเตอร์มีเพียงสามองค์ประกอบ ในสถานการณ์นี้ Rust จะแพนิก การใช้ `[]` ควรจะคืนค่าองค์ประกอบ แต่หากคุณส่งดัชนีที่ไม่ถูกต้อง จะไม่มีองค์ประกอบใดที่ Rust จะคืนค่ากลับมาได้อย่างถูกต้อง ณ ที่นี้

ในภาษา C การพยายามอ่านเลยจุดสิ้นสุดของโครงสร้างข้อมูลถือเป็นพฤติกรรมที่ไม่ได้นิยามไว้ (undefined behavior) คุณอาจได้อะไรก็ตามที่อยู่ในตำแหน่งหน่วยความจำที่สอดคล้องกับองค์ประกอบนั้นในโครงสร้างข้อมูล แม้ว่าหน่วยความจำนั้นไม่ได้เป็นของโครงสร้างนั้นก็ตาม สิ่งนี้เรียกว่า_การอ่านเกินบัฟเฟอร์_ (buffer overread) และอาจนำไปสู่ช่องโหว่ด้านความปลอดภัยได้ หากผู้โจมตีสามารถจัดการดัชนีในลักษณะที่จะอ่านข้อมูลที่พวกเขาไม่ควรได้รับอนุญาตซึ่งถูกจัดเก็บไว้หลังโครงสร้างข้อมูล

เพื่อปกป้องโปรแกรมของคุณจากช่องโหว่ประเภทนี้ หากคุณพยายามอ่านองค์ประกอบที่ดัชนีซึ่งไม่มีอยู่ Rust จะหยุดการทำงานและปฏิเสธที่จะดำเนินการต่อ มาลองดูกัน:

บรรทัด `note:` บอกเราว่าเราสามารถตั้งค่าตัวแปรสภาพแวดล้อม `RUST_BACKTRACE` เพื่อรับแบ็กเทรซของสิ่งที่เกิดขึ้นจริงซึ่งทำให้เกิดข้อผิดพลาดนี้ได้ _แบ็กเทรซ_ คือรายการของฟังก์ชันทั้งหมดที่ถูกเรียกเพื่อมาถึงจุดนี้ แบ็กเทรซใน Rust ทำงานเหมือนกับในภาษาอื่นๆ: กุญแจสำคัญในการอ่านแบ็กเทรซคือเริ่มจากด้านบนและอ่านลงมาจนกว่าจะเห็นไฟล์ที่คุณเขียนเอง นั่นคือจุดที่ปัญหาเกิดขึ้น บรรทัดที่อยู่เหนือจุดนั้นคือโค้ดที่โค้ดของคุณเรียกใช้ บรรทัดที่อยู่ด้านล่างคือโค้ดที่เรียกโค้ดของคุณ บรรทัดก่อนและหลังเหล่านี้อาจรวมโค้ดหลักของ Rust โค้ดไลบรารีมาตรฐาน หรือเครต (crate) ที่คุณใช้อยู่ มาลองรับแบ็กเทรซโดยตั้งค่าตัวแปรสภาพแวดล้อม `RUST_BACKTRACE` เป็นค่าใดก็ได้ยกเว้น `0` ลิสติ้ง 9-2 แสดงเอาต์พุตที่คล้ายกับสิ่งที่คุณจะเห็น

นั่นเป็นเอาต์พุตเยอะมาก! เอาต์พุตที่คุณเห็นจริงอาจแตกต่างกันไป ขึ้นอยู่กับระบบปฏิบัติการและเวอร์ชัน Rust ของคุณ การจะได้แบ็กเทรซที่มีข้อมูลนี้ ต้องเปิดใช้สัญลักษณ์ดีบัก (debug symbol) สัญลักษณ์ดีบักถูกเปิดใช้โดยค่าเริ่มต้นเมื่อใช้ `cargo build` หรือ `cargo run` โดยไม่มีแฟล็ก `--release` อย่างที่เราทำในที่นี้

ในเอาต์พุตของลิสติ้ง 9-2 บรรทัดที่ 6 ของแบ็กเทรซชี้ไปที่บรรทัดในโปรเจกต์ของเราที่ทำให้เกิดปัญหา นั่นคือบรรทัดที่ 4 ของ _src/main.rs_ หากเราไม่ต้องการให้โปรแกรมของเราแพนิก เราควรเริ่มการสืบสวนที่ตำแหน่งซึ่งบรรทัดแรกที่กล่าวถึงไฟล์ที่เราเขียนชี้ไป ในลิสติ้ง 9-1 ซึ่งเราตั้งใจเขียนโค้ดที่จะทำให้เกิดการแพนิก วิธีแก้การแพนิกคืออย่าร้องขอองค์ประกอบที่เลยช่วงของดัชนีของเวกเตอร์ เมื่อโค้ดของคุณแพนิกในอนาคต คุณจะต้องหาว่าโค้ดกำลังทำการกระทำใดกับค่าใดที่ทำให้เกิดการแพนิก และโค้ดควรทำอะไรแทน

เราจะกลับมาที่ `panic!` และว่าเมื่อใดเราควรและไม่ควรใช้ `panic!` เพื่อจัดการเงื่อนไขข้อผิดพลาด ในหัวข้อ[“จะ `panic!` หรือไม่ `panic!`”][to-panic-or-not-to-panic]<!-- ignore --> ช่วงหลังของบทนี้ ต่อไป เราจะดูวิธีกู้คืนจากข้อผิดพลาดโดยใช้ `Result`
