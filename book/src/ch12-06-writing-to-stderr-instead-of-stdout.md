## เปลี่ยนเส้นทางข้อผิดพลาดไปยัง standard error

ตอนนี้ เรากำลังเขียนเอาต์พุตทั้งหมดของเราไปยังเทอร์มินัลโดยใช้มาโคร `println!` ในเทอร์มินัลส่วนใหญ่ มีเอาต์พุตสองชนิด: _เอาต์พุตมาตรฐาน_ (standard output, `stdout`) สำหรับข้อมูลทั่วไป และ _ข้อผิดพลาดมาตรฐาน_ (standard error, `stderr`) สำหรับข้อความแสดงข้อผิดพลาด ความแตกต่างนี้ช่วยให้ผู้ใช้เลือกส่งเอาต์พุตที่สำเร็จของโปรแกรมไปยังไฟล์ได้ แต่ยังคงพิมพ์ข้อความแสดงข้อผิดพลาดไปยังหน้าจอ

มาโคร `println!` สามารถพิมพ์ไปยังเอาต์พุตมาตรฐานเท่านั้น เราจึงต้องใช้อย่างอื่นในการพิมพ์ไปยังข้อผิดพลาดมาตรฐาน

### การตรวจสอบว่าข้อผิดพลาดถูกเขียนไปที่ใด

ก่อนอื่น มาสังเกตว่าเนื้อหาที่ `minigrep` พิมพ์อยู่ในขณะนี้ถูกเขียนไปยังเอาต์พุตมาตรฐานอย่างไร รวมถึงข้อความแสดงข้อผิดพลาดใดๆ ที่เราต้องการให้เขียนไปยังข้อผิดพลาดมาตรฐานแทน เราจะทำเช่นนั้นโดยเปลี่ยนเส้นทางสตรีมเอาต์พุตมาตรฐานไปยังไฟล์พร้อมกับจงใจทำให้เกิดข้อผิดพลาด เราจะไม่เปลี่ยนเส้นทางสตรีมข้อผิดพลาดมาตรฐาน เนื้อหาใดๆ ที่ถูกส่งไปยังข้อผิดพลาดมาตรฐานจึงยังคงแสดงบนหน้าจอ

โปรแกรมบรรทัดคำสั่ง (command line) ถูกคาดหวังให้ส่งข้อความแสดงข้อผิดพลาดไปยังสตรีมข้อผิดพลาดมาตรฐาน เพื่อให้เรายังเห็นข้อความแสดงข้อผิดพลาดบนหน้าจอได้แม้เราเปลี่ยนเส้นทางสตรีมเอาต์พุตมาตรฐานไปยังไฟล์ โปรแกรมของเรายังไม่ประพฤติดีเท่าที่ควร: เรากำลังจะเห็นว่ามันบันทึกเอาต์พุตข้อความแสดงข้อผิดพลาดลงไฟล์แทน!

เพื่อสาธิตพฤติกรรมนี้ เราจะรันโปรแกรมด้วย `>` และพาธไฟล์ _output.txt_ ที่เราต้องการเปลี่ยนเส้นทางสตรีมเอาต์พุตมาตรฐานไปยัง เราจะไม่ส่งอาร์กิวเมนต์ (argument) ใดๆ ซึ่งควรทำให้เกิดข้อผิดพลาด:

```console
$ cargo run > output.txt
```

ไวยากรณ์ `>` บอกเชลล์ให้เขียนเนื้อหาของเอาต์พุตมาตรฐานไปยัง _output.txt_ แทนหน้าจอ เราไม่เห็นข้อความแสดงข้อผิดพลาดที่เราคาดว่าจะถูกพิมพ์ไปยังหน้าจอ แสดงว่ามันต้องไปอยู่ในไฟล์ นี่คือสิ่งที่ _output.txt_ บรรจุ:

```text
Problem parsing arguments: not enough arguments
```

ใช่แล้ว ข้อความแสดงข้อผิดพลาดของเราถูกพิมพ์ไปยังเอาต์พุตมาตรฐาน การพิมพ์ข้อความแสดงข้อผิดพลาดแบบนี้ไปยังข้อผิดพลาดมาตรฐานมีประโยชน์กว่ามาก เพื่อให้เฉพาะข้อมูลจากการรันที่สำเร็จลงเอยในไฟล์เท่านั้น เราจะเปลี่ยนมัน

### การพิมพ์ข้อผิดพลาดไปยังข้อผิดพลาดมาตรฐาน

เราจะใช้โค้ดในลิสติ้ง 12-24 เพื่อเปลี่ยนวิธีพิมพ์ข้อความแสดงข้อผิดพลาด เนื่องจากการรีแฟกเตอร์ (refactor) ที่เราทำไปก่อนหน้าในบทนี้ โค้ดทั้งหมดที่พิมพ์ข้อความแสดงข้อผิดพลาดจึงอยู่ในฟังก์ชันเดียวคือ `main` ไลบรารีมาตรฐานมีมาโคร `eprintln!` ที่พิมพ์ไปยังสตรีมข้อผิดพลาดมาตรฐาน ดังนั้นมาเปลี่ยนสองจุดที่เราเรียก `println!` เพื่อพิมพ์ข้อผิดพลาดให้ใช้ `eprintln!` แทนกัน

ตอนนี้มาลองรันโปรแกรมอีกครั้งในแบบเดียวกัน โดยไม่ใส่อาร์กิวเมนต์และเปลี่ยนเส้นทางเอาต์พุตมาตรฐานด้วย `>`:

```console
$ cargo run > output.txt
Problem parsing arguments: not enough arguments
```

ตอนนี้เราเห็นข้อผิดพลาดบนหน้าจอ และ _output.txt_ ไม่บรรจุอะไรเลย ซึ่งเป็นพฤติกรรมที่เราคาดหวังจากโปรแกรมบรรทัดคำสั่ง

มาลองรันโปรแกรมอีกครั้งด้วยอาร์กิวเมนต์ที่ไม่ทำให้เกิดข้อผิดพลาด แต่ยังเปลี่ยนเส้นทางเอาต์พุตมาตรฐานไปยังไฟล์ ดังนี้:

```console
$ cargo run -- to poem.txt > output.txt
```

เราจะไม่เห็นเอาต์พุตใดๆ ไปยังเทอร์มินัล และ _output.txt_ จะบรรจุผลลัพธ์ของเรา:

<span class="filename">ชื่อไฟล์: output.txt</span>

```text
Are you nobody, too?
How dreary to be somebody!
```

สิ่งนี้แสดงให้เห็นว่าตอนนี้เราใช้เอาต์พุตมาตรฐานสำหรับเอาต์พุตที่สำเร็จ และใช้ข้อผิดพลาดมาตรฐานสำหรับเอาต์พุตข้อผิดพลาดอย่างเหมาะสมแล้ว

## สรุป

บทนี้ได้ทบทวนแนวคิดสำคัญบางส่วนที่คุณได้เรียนรู้มาจนถึงตอนนี้ และครอบคลุมวิธีดำเนินการ I/O พื้นฐานใน Rust ด้วยการใช้อาร์กิวเมนต์บรรทัดคำสั่ง ไฟล์ ตัวแปรสภาพแวดล้อม (environment variable) และมาโคร `eprintln!` สำหรับพิมพ์ข้อผิดพลาด ตอนนี้คุณพร้อมที่จะเขียนแอปพลิเคชันบรรทัดคำสั่งแล้ว เมื่อรวมกับแนวคิดในบทก่อนๆ โค้ดของคุณจะถูกจัดระเบียบอย่างดี จัดเก็บข้อมูลอย่างมีประสิทธิภาพในโครงสร้างข้อมูลที่เหมาะสม จัดการข้อผิดพลาดได้อย่างดี และผ่านการทดสอบมาอย่างดี

ต่อไป เราจะสำรวจฟีเจอร์ของ Rust บางอย่างที่ได้รับอิทธิพลจากภาษาเชิงฟังก์ชัน: โคลเชอร์ (closure) และอิเทอเรเตอร์ (iterator)
