## มาโคร

เราได้ใช้มาโคร (macro) อย่าง `println!` มาตลอดทั้งเล่มนี้ แต่เรายังไม่ได้สำรวจอย่างเต็มที่ว่ามาโครคืออะไรและทำงานอย่างไร คำว่า_มาโคร_ หมายถึงกลุ่มของฟีเจอร์ใน Rust—มาโครแบบประกาศ (declarative macro) ด้วย `macro_rules!` และมาโครแบบโพรซีเยอร์ (procedural macro) สามชนิด:

- มาโคร `#[derive]` แบบกำหนดเองที่ระบุโค้ดที่ถูกเพิ่มด้วยแอตทริบิวต์ (attribute) `derive` ที่ใช้บน struct และ enum
- มาโครคล้ายแอตทริบิวต์ (attribute-like macro) ที่นิยามแอตทริบิวต์แบบกำหนดเองซึ่งใช้ได้กับรายการใดๆ
- มาโครคล้ายฟังก์ชัน (function-like macro) ที่มีหน้าตาเหมือนการเรียกฟังก์ชันแต่ทำงานกับโทเค็น (token) ที่ระบุเป็นอาร์กิวเมนต์ของมัน

เราจะพูดคุยถึงแต่ละชนิดตามลำดับ แต่ก่อนอื่น มาดูกันว่าทำไมเราจึงยังต้องการมาโครทั้งที่เรามีฟังก์ชันอยู่แล้ว

### ความแตกต่างระหว่างมาโครกับฟังก์ชัน

โดยพื้นฐานแล้ว มาโครเป็นวิธีเขียนโค้ดที่เขียนโค้ดอื่น ซึ่งรู้จักกันในชื่อ_เมตาโปรแกรมมิ่ง_ (metaprogramming) ในภาคผนวก C เราพูดคุยถึงแอตทริบิวต์ `derive` ที่สร้างการอิมพลีเมนต์ของเทรตต่างๆ ให้คุณ เรายังได้ใช้มาโคร `println!` และ `vec!` มาตลอดทั้งเล่มด้วย มาโครทั้งหมดนี้_ขยาย_ (expand) ออกไปเพื่อสร้างโค้ดมากกว่าโค้ดที่คุณเขียนเองด้วยมือ

เมตาโปรแกรมมิ่งมีประโยชน์ในการลดปริมาณโค้ดที่คุณต้องเขียนและดูแลรักษา ซึ่งก็เป็นหนึ่งในบทบาทของฟังก์ชันเช่นกัน อย่างไรก็ตาม มาโครมีพลังเพิ่มเติมบางอย่างที่ฟังก์ชันไม่มี

ซิกเนเจอร์ของฟังก์ชันต้องประกาศจำนวนและชนิดของพารามิเตอร์ที่ฟังก์ชันมี ในทางกลับกัน มาโครรับพารามิเตอร์จำนวนที่แปรผันได้: เราสามารถเรียก `println!("hello")` ด้วยอาร์กิวเมนต์เดียว หรือ `println!("hello {}", name)` ด้วยสองอาร์กิวเมนต์ได้ นอกจากนี้ มาโครถูกขยายก่อนที่คอมไพเลอร์จะตีความหมายของโค้ด มาโครจึงสามารถอิมพลีเมนต์เทรต (trait) บนชนิดข้อมูลที่กำหนดได้ ตัวอย่างเช่น ฟังก์ชันทำแบบนั้นไม่ได้เพราะมันถูกเรียกตอนรันไทม์ และเทรตจำเป็นต้องถูกอิมพลีเมนต์ตอนคอมไพล์

ข้อเสียของการอิมพลีเมนต์มาโครแทนฟังก์ชันคือ นิยามมาโครซับซ้อนกว่านิยามฟังก์ชัน เพราะคุณกำลังเขียนโค้ด Rust ที่เขียนโค้ด Rust เนื่องจากความอ้อมนี้ นิยามมาโครจึงโดยทั่วไปอ่าน เข้าใจ และดูแลรักษาได้ยากกว่านิยามฟังก์ชัน

ความแตกต่างที่สำคัญอีกประการระหว่างมาโครกับฟังก์ชันคือ คุณต้องนิยามมาโครหรือนำมันเข้าสู่สโคป_ก่อน_ที่คุณจะเรียกมันในไฟล์ ต่างจากฟังก์ชันที่คุณนิยามที่ใดก็ได้และเรียกที่ใดก็ได้

### มาโครแบบประกาศสำหรับเมตาโปรแกรมมิ่งทั่วไป

รูปแบบของมาโครที่ถูกใช้อย่างแพร่หลายที่สุดใน Rust คือ_มาโครแบบประกาศ_ บางครั้งสิ่งเหล่านี้ยังถูกเรียกว่า “มาโครแบบตัวอย่าง (macros by example)” “มาโคร `macro_rules!`” หรือเรียกสั้นๆ ว่า “มาโคร” เฉยๆ โดยแก่นแท้แล้ว มาโครแบบประกาศให้คุณเขียนสิ่งที่คล้ายกับเอ็กซ์เพรสชัน `match` ของ Rust ดังที่พูดคุยกันในบทที่ 6 เอ็กซ์เพรสชัน `match` เป็นโครงสร้างการควบคุมที่รับเอ็กซ์เพรสชัน เปรียบเทียบค่าที่ได้จากเอ็กซ์เพรสชันกับแพตเทิร์น แล้วรันโค้ดที่เชื่อมโยงกับแพตเทิร์นที่จับคู่ได้ มาโครก็เปรียบเทียบค่ากับแพตเทิร์นที่เชื่อมโยงกับโค้ดเฉพาะเช่นกัน: ในสถานการณ์นี้ ค่าคือโค้ดซอร์ส (source code) Rust ตามตัวอักษรที่ส่งให้มาโคร; แพตเทิร์นถูกเปรียบเทียบกับโครงสร้างของโค้ดซอร์สนั้น; และโค้ดที่เชื่อมโยงกับแต่ละแพตเทิร์น เมื่อจับคู่ได้ จะแทนที่โค้ดที่ส่งให้มาโคร ทั้งหมดนี้เกิดขึ้นระหว่างการคอมไพล์

ในการนิยามมาโคร คุณใช้โครงสร้าง `macro_rules!` มาสำรวจวิธีใช้ `macro_rules!` โดยดูจากการนิยามมาโคร `vec!` กัน บทที่ 8 ครอบคลุมวิธีที่เราใช้มาโคร `vec!` เพื่อสร้างเวกเตอร์ใหม่ที่มีค่าต่างๆ ที่กำหนด ตัวอย่างเช่น มาโครต่อไปนี้สร้างเวกเตอร์ใหม่ที่บรรจุจำนวนเต็มสามตัว:

```rust
let v: Vec<u32> = vec![1, 2, 3];
```

เรายังใช้มาโคร `vec!` เพื่อสร้างเวกเตอร์ของจำนวนเต็มสองตัว หรือเวกเตอร์ของสตริงสไลซ์ห้าตัวได้ด้วย เราไม่สามารถใช้ฟังก์ชันทำแบบเดียวกันได้เพราะเราจะไม่รู้จำนวนหรือชนิดของค่าล่วงหน้า

คำอธิบายประกอบ `#[macro_export]` บ่งชี้ว่ามาโครนี้ควรถูกทำให้พร้อมใช้งานเมื่อใดก็ตามที่เครต (crate) ที่มาโครนี้ถูกนิยามอยู่ถูกนำเข้าสู่สโคป หากไม่มีคำอธิบายประกอบนี้ มาโครจะไม่สามารถถูกนำเข้าสู่สโคปได้

จากนั้นเราเริ่มนิยามมาโครด้วย `macro_rules!` และชื่อของมาโครที่เรากำลังนิยามโดย_ไม่ต้องมี_เครื่องหมายอัศเจรีย์ ชื่อในกรณีนี้คือ `vec` ตามด้วยวงเล็บปีกกาที่แสดงถึงบอดี้ของนิยามมาโคร

โครงสร้างในบอดี้ของ `vec!` คล้ายกับโครงสร้างของเอ็กซ์เพรสชัน `match` ในที่นี้เรามีอาร์มหนึ่งอาร์มที่มีแพตเทิร์น `( $( $x:expr ),* )` ตามด้วย `=>` และบล็อกโค้ดที่เชื่อมโยงกับแพตเทิร์นนี้ หากแพตเทิร์นจับคู่ได้ บล็อกโค้ดที่เชื่อมโยงจะถูกปล่อยออกมา เนื่องจากนี่เป็นแพตเทิร์นเดียวในมาโครนี้ จึงมีวิธีจับคู่ที่ถูกต้องเพียงวิธีเดียวเท่านั้น แพตเทิร์นอื่นใดจะส่งผลให้เกิดข้อผิดพลาด มาโครที่ซับซ้อนกว่าจะมีอาร์มมากกว่าหนึ่งอาร์ม

วากยสัมพันธ์ของแพตเทิร์นที่ถูกต้องในนิยามมาโครแตกต่างจากวากยสัมพันธ์ของแพตเทิร์นที่ครอบคลุมในบทที่ 19 เพราะแพตเทิร์นของมาโครถูกจับคู่กับโครงสร้างโค้ด Rust แทนที่จะเป็นค่า มาดูกันว่าชิ้นส่วนของแพตเทิร์นในลิสติ้ง 20-29 หมายถึงอะไร สำหรับวากยสัมพันธ์แพตเทิร์นของมาโครแบบเต็ม โปรดดู [Rust Reference][ref]

ก่อนอื่น เราใช้วงเล็บหนึ่งคู่เพื่อครอบแพตเทิร์นทั้งหมด เราใช้เครื่องหมายดอลลาร์ (`$`) เพื่อประกาศตัวแปรในระบบมาโครที่จะบรรจุโค้ด Rust ที่จับคู่กับแพตเทิร์น เครื่องหมายดอลลาร์ทำให้ชัดเจนว่านี่คือตัวแปรของมาโคร ไม่ใช่ตัวแปร Rust ปกติ ต่อไปคือวงเล็บหนึ่งคู่ที่ดักจับค่าที่จับคู่กับแพตเทิร์นภายในวงเล็บเพื่อใช้ในโค้ดที่ใช้แทนที่ ภายใน `$()` คือ `$x:expr` ซึ่งจับคู่กับเอ็กซ์เพรสชัน Rust ใดก็ได้และตั้งชื่อเอ็กซ์เพรสชันนั้นว่า `$x`

เครื่องหมายจุลภาคที่ตามหลัง `$()` บ่งชี้ว่าตัวอักขระคั่นอย่างจุลภาคตามตัวอักษรต้องปรากฏระหว่างแต่ละอินสแตนซ์ของโค้ดที่จับคู่กับโค้ดใน `$()` เครื่องหมาย `*` ระบุว่าแพตเทิร์นจับคู่กับสิ่งที่อยู่หน้า `*` ตั้งแต่ศูนย์ครั้งขึ้นไป

เมื่อเราเรียกมาโครนี้ด้วย `vec![1, 2, 3];` แพตเทิร์น `$x` จะจับคู่สามครั้งกับเอ็กซ์เพรสชันสามตัวคือ `1`, `2` และ `3`

ตอนนี้มาดูแพตเทิร์นในบอดี้ของโค้ดที่เชื่อมโยงกับอาร์มนี้: `temp_vec.push()` ภายใน `$()*` ถูกสร้างขึ้นสำหรับแต่ละส่วนที่จับคู่กับ `$()` ในแพตเทิร์นตั้งแต่ศูนย์ครั้งขึ้นไป ขึ้นอยู่กับว่าแพตเทิร์นจับคู่ได้กี่ครั้ง `$x` ถูกแทนที่ด้วยเอ็กซ์เพรสชันที่จับคู่ได้แต่ละตัว เมื่อเราเรียกมาโครนี้ด้วย `vec![1, 2, 3];` โค้ดที่ถูกสร้างขึ้นซึ่งแทนที่การเรียกมาโครนี้จะเป็นดังนี้:

```rust,ignore
{
    let mut temp_vec = Vec::new();
    temp_vec.push(1);
    temp_vec.push(2);
    temp_vec.push(3);
    temp_vec
}
```

เราได้นิยามมาโครที่รับอาร์กิวเมนต์จำนวนเท่าใดก็ได้และชนิดใดก็ได้ และสามารถสร้างโค้ดเพื่อสร้างเวกเตอร์ที่บรรจุสมาชิกที่ระบุไว้ได้

หากต้องการเรียนรู้เพิ่มเติมเกี่ยวกับวิธีเขียนมาโคร โปรดดูเอกสารออนไลน์หรือแหล่งข้อมูลอื่นๆ เช่น [“The Little Book of Rust Macros”][tlborm] ที่เริ่มต้นโดย Daniel Keep และสานต่อโดย Lukas Wirth

### มาโครแบบโพรซีเยอร์สำหรับสร้างโค้ดจากแอตทริบิวต์

รูปแบบที่สองของมาโครคือมาโครแบบโพรซีเยอร์ ซึ่งทำงานคล้ายกับฟังก์ชันมากกว่า (และเป็นโพรซีเยอร์ชนิดหนึ่ง) _มาโครแบบโพรซีเยอร์_ รับโค้ดบางส่วนเป็นอินพุต ทำงานกับโค้ดนั้น และสร้างโค้ดบางส่วนเป็นเอาต์พุต แทนที่จะจับคู่กับแพตเทิร์นและแทนที่โค้ดด้วยโค้ดอื่นเหมือนที่มาโครแบบประกาศทำ มาโครแบบโพรซีเยอร์ทั้งสามชนิดคือ `derive` แบบกำหนดเอง แบบคล้ายแอตทริบิวต์ และแบบคล้ายฟังก์ชัน และทั้งหมดทำงานในลักษณะที่คล้ายกัน

ในการสร้างมาโครแบบโพรซีเยอร์ นิยามต้องอยู่ในเครตของตัวเองที่มีชนิดเครตพิเศษ นี่เป็นเพราะเหตุผลทางเทคนิคที่ซับซ้อนซึ่งเราหวังว่าจะกำจัดได้ในอนาคต ในลิสติ้ง 20-36 เราแสดงวิธีนิยามมาโครแบบโพรซีเยอร์ โดยที่ `some_attribute` เป็นตัวยึดตำแหน่งสำหรับการใช้มาโครชนิดเฉพาะ

<Listing number="20-36" file-name="src/lib.rs" caption="ตัวอย่างการนิยามมาโครแบบโพรซีเยอร์">

```rust,ignore
use proc_macro::TokenStream;

#[some_attribute]
pub fn some_name(input: TokenStream) -> TokenStream {
}
```

</Listing>

ฟังก์ชันที่นิยามมาโครแบบโพรซีเยอร์รับ `TokenStream` เป็นอินพุตและสร้าง `TokenStream` เป็นเอาต์พุต ชนิด `TokenStream` ถูกนิยามโดยเครต `proc_macro` ที่มาพร้อมกับ Rust และเป็นตัวแทนของลำดับโทเค็น นี่คือแก่นของมาโคร: โค้ดซอร์สที่มาโครกำลังทำงานด้วยประกอบขึ้นเป็น `TokenStream` ขาเข้า และโค้ดที่มาโครสร้างขึ้นคือ `TokenStream` ขาออก ฟังก์ชันนี้ยังมีแอตทริบิวต์แนบอยู่กับมันซึ่งระบุว่าเรากำลังสร้างมาโครแบบโพรซีเยอร์ชนิดใด เราสามารถมีมาโครแบบโพรซีเยอร์หลายชนิดในเครตเดียวกันได้

มาดูมาโครแบบโพรซีเยอร์ชนิดต่างๆ กัน เราเริ่มจากมาโคร `derive` แบบกำหนดเอง แล้วอธิบายความแตกต่างเล็กน้อยที่ทำให้รูปแบบอื่นๆ ต่างออกไป

นอกจากนี้ เรายังไม่สามารถจัดเตรียมการอิมพลีเมนต์เริ่มต้นให้กับฟังก์ชัน `hello_macro` ที่จะพิมพ์ชื่อของชนิดข้อมูลที่เทรตถูกอิมพลีเมนต์บนมันได้: Rust ไม่มีความสามารถด้านการสะท้อน (reflection) จึงไม่สามารถค้นหาชื่อของชนิดข้อมูลได้ตอนรันไทม์ เราจำเป็นต้องมีมาโครเพื่อสร้างโค้ดตอนคอมไพล์

ขั้นตอนต่อไปคือการนิยามมาโครแบบโพรซีเยอร์ ในขณะที่เขียนหนังสือเล่มนี้ มาโครแบบโพรซีเยอร์จำเป็นต้องอยู่ในเครตของตัวเอง ในที่สุดข้อจำกัดนี้อาจถูกยกเลิก ข้อตกลงปฏิบัติ (convention) ในการจัดโครงสร้างเครตและเครตมาโครมีดังนี้: สำหรับเครตชื่อ `foo` เครตมาโครแบบโพรซีเยอร์ `derive` แบบกำหนดเองจะถูกเรียกว่า `foo_derive` มาสร้างเครตใหม่ชื่อ `hello_macro_derive` ภายในโปรเจกต์ `hello_macro` ของเรากัน:

```console

```

เครตทั้งสองของเรามีความเกี่ยวข้องกันอย่างแนบแน่น เราจึงสร้างเครตมาโครแบบโพรซีเยอร์ไว้ในไดเรกทอรีของเครต `hello_macro` ของเรา หากเราเปลี่ยนนิยามเทรตใน `hello_macro` เราจะต้องเปลี่ยนการอิมพลีเมนต์ของมาโครแบบโพรซีเยอร์ใน `hello_macro_derive` ด้วย เครตทั้งสองจะต้องถูกเผยแพร่แยกจากกัน และโปรแกรมเมอร์ที่ใช้เครตเหล่านี้จะต้องเพิ่มทั้งคู่เป็นดีเพนเดนซีและนำทั้งคู่เข้าสู่สโคป เราอาจให้เครต `hello_macro` ใช้ `hello_macro_derive` เป็นดีเพนเดนซีและรีเอ็กซ์พอร์ตโค้ดมาโครแบบโพรซีเยอร์แทนก็ได้ อย่างไรก็ตาม การจัดโครงสร้างโปรเจกต์แบบที่เราทำทำให้โปรแกรมเมอร์สามารถใช้ `hello_macro` ได้แม้ว่าพวกเขาไม่ต้องการฟังก์ชัน `derive` ก็ตาม

โปรดสังเกตว่าเราได้แยกโค้ดออกเป็นฟังก์ชัน `hello_macro_derive` ซึ่งรับผิดชอบการแยกวิเคราะห์ (parse) `TokenStream` และฟังก์ชัน `impl_hello_macro` ซึ่งรับผิดชอบการแปลงทรีวากยสัมพันธ์ (syntax tree): สิ่งนี้ทำให้การเขียนมาโครแบบโพรซีเยอร์สะดวกขึ้น โค้ดในฟังก์ชันชั้นนอก (`hello_macro_derive` ในกรณีนี้) จะเหมือนกันสำหรับเครตมาโครแบบโพรซีเยอร์แทบทุกตัวที่คุณพบเห็นหรือสร้างขึ้น โค้ดที่คุณระบุในบอดี้ของฟังก์ชันชั้นใน (`impl_hello_macro` ในกรณีนี้) จะแตกต่างกันไปตามจุดประสงค์ของมาโครแบบโพรซีเยอร์ของคุณ

เราได้แนะนำเครตใหม่สามตัว: `proc_macro`, [`syn`][syn]<!-- ignore --> และ [`quote`][quote]<!-- ignore --> เครต `proc_macro` มาพร้อมกับ Rust เราจึงไม่จำเป็นต้องเพิ่มมันเข้าไปในดีเพนเดนซีใน _Cargo.toml_ เครต `proc_macro` เป็น API ของคอมไพเลอร์ที่ช่วยให้เราอ่านและจัดการโค้ด Rust จากโค้ดของเราได้

เครต `syn` แยกวิเคราะห์โค้ด Rust จากสตริงให้เป็นโครงสร้างข้อมูลที่เราสามารถดำเนินการกับมันได้ เครต `quote` เปลี่ยนโครงสร้างข้อมูลของ `syn` กลับเป็นโค้ด Rust เครตเหล่านี้ทำให้การแยกวิเคราะห์โค้ด Rust ชนิดใดก็ตามที่เราอาจต้องการจัดการง่ายขึ้นมาก: การเขียนตัวแยกวิเคราะห์แบบเต็มรูปแบบสำหรับโค้ด Rust ไม่ใช่เรื่องง่ายเลย

ฟังก์ชัน `hello_macro_derive` จะถูกเรียกเมื่อผู้ใช้ไลบรารีของเราระบุ `#[derive(HelloMacro)]` บนชนิดข้อมูลหนึ่ง สิ่งนี้เป็นไปได้เพราะเราได้ใส่คำอธิบายประกอบฟังก์ชัน `hello_macro_derive` ตรงนี้ด้วย `proc_macro_derive` และระบุชื่อ `HelloMacro` ซึ่งตรงกับชื่อเทรตของเรา นี่คือข้อตกลงปฏิบัติที่มาโครแบบโพรซีเยอร์ส่วนใหญ่ยึดตาม

ฟังก์ชัน `hello_macro_derive` แปลง `input` จาก `TokenStream` ให้เป็นโครงสร้างข้อมูลที่เราสามารถตีความและดำเนินการกับมันได้ก่อน นี่คือจุดที่ `syn` เข้ามามีบทบาท ฟังก์ชัน `parse` ใน `syn` รับ `TokenStream` และคืน struct `DeriveInput` ที่เป็นตัวแทนของโค้ด Rust ที่ถูกแยกวิเคราะห์แล้ว ลิสติ้ง 20-41 แสดงส่วนที่เกี่ยวข้องของ struct `DeriveInput` ที่เราได้จากการแยกวิเคราะห์สตริง `struct Pancakes;`

ในไม่ช้าเราจะนิยามฟังก์ชัน `impl_hello_macro` ซึ่งเป็นที่ที่เราจะสร้างโค้ด Rust ใหม่ที่เราต้องการใส่เข้าไป แต่ก่อนที่เราจะทำเช่นนั้น โปรดสังเกตว่าเอาต์พุตของมาโคร `derive` ของเราก็เป็น `TokenStream` เช่นกัน `TokenStream` ที่ถูกคืนกลับจะถูกเพิ่มเข้าไปในโค้ดที่ผู้ใช้เครตของเราเขียน ดังนั้นเมื่อพวกเขาคอมไพล์เครตของตน พวกเขาจะได้ฟังก์ชันการทำงานเพิ่มเติมที่เราจัดเตรียมไว้ใน `TokenStream` ที่ถูกแก้ไข

คุณอาจสังเกตว่าเรากำลังเรียก `unwrap` เพื่อทำให้ฟังก์ชัน `hello_macro_derive` แพนิก (panic) หากการเรียกฟังก์ชัน `syn::parse` ล้มเหลวตรงนี้ มาโครแบบโพรซีเยอร์ของเราจำเป็นต้องแพนิกเมื่อเกิดข้อผิดพลาด เพราะฟังก์ชัน `proc_macro_derive` ต้องคืน `TokenStream` แทนที่จะเป็น `Result` เพื่อให้สอดคล้องกับ API ของมาโครแบบโพรซีเยอร์ เราได้ทำให้ตัวอย่างนี้ง่ายขึ้นโดยใช้ `unwrap`; ในโค้ดสำหรับใช้งานจริง คุณควรจัดเตรียมข้อความแสดงข้อผิดพลาดที่เจาะจงกว่านี้ว่าอะไรผิดพลาด โดยใช้ `panic!` หรือ `expect`

</Listing>

เราได้อินสแตนซ์ของ struct `Ident` ที่บรรจุชื่อ (identifier) ของชนิดข้อมูลที่มีคำอธิบายประกอบโดยใช้ `ast.ident` struct ในลิสติ้ง 20-41 แสดงว่าเมื่อเรารันฟังก์ชัน `impl_hello_macro` กับโค้ดในลิสติ้ง 20-37 `ident` ที่เราได้จะมีฟิลด์ `ident` ที่มีค่าเป็น `"Pancakes"` ดังนั้น ตัวแปร `name` ในลิสติ้ง 20-42 จะบรรจุอินสแตนซ์ของ struct `Ident` ซึ่งเมื่อพิมพ์ออกมาจะเป็นสตริง `"Pancakes"` ซึ่งเป็นชื่อของ struct ในลิสติ้ง 20-37

มาโคร `quote!` ให้เรานิยามโค้ด Rust ที่เราต้องการคืนค่ากลับ คอมไพเลอร์คาดหวังสิ่งที่แตกต่างจากผลลัพธ์โดยตรงของการทำงานของมาโคร `quote!` เราจึงต้องแปลงมันเป็น `TokenStream` เราทำเช่นนี้โดยเรียกเมธอด `into` ซึ่งบริโภคตัวแทนระดับกลาง (intermediate representation) นี้และคืนค่าที่มีชนิด `TokenStream` ที่ต้องการ

มาโคร `quote!` ยังมีกลไกการทำเทมเพลตที่ยอดเยี่ยมมาก: เราสามารถใส่ `#name` แล้ว `quote!` จะแทนที่มันด้วยค่าในตัวแปร `name` คุณยังทำการวนซ้ำคล้ายกับวิธีที่มาโครทั่วไปทำงานได้ด้วย โปรดดู[เอกสารของเครต `quote`][quote-docs] สำหรับบทนำที่ละเอียดถี่ถ้วน

เราต้องการให้มาโครแบบโพรซีเยอร์ของเราสร้างการอิมพลีเมนต์เทรต `HelloMacro` สำหรับชนิดข้อมูลที่ผู้ใช้ใส่คำอธิบายประกอบ ซึ่งเราได้มาจากการใช้ `#name` การอิมพลีเมนต์เทรตมีฟังก์ชันหนึ่งเดียวคือ `hello_macro` ซึ่งบอดี้บรรจุฟังก์ชันการทำงานที่เราต้องการจัดเตรียมไว้: พิมพ์ `Hello, Macro! My name is` แล้วตามด้วยชื่อของชนิดข้อมูลที่มีคำอธิบายประกอบ

มาโคร `stringify!` ที่ใช้ตรงนี้เป็นมาโครที่มาพร้อมกับ Rust มันรับเอ็กซ์เพรสชัน Rust เช่น `1 + 2` แล้วเปลี่ยนเอ็กซ์เพรสชันนั้นให้เป็นสตริงลิเทอรัล (string literal) ตอนคอมไพล์ เช่น `"1 + 2"` สิ่งนี้แตกต่างจาก `format!` หรือ `println!` ซึ่งเป็นมาโครที่ประเมินค่าเอ็กซ์เพรสชันแล้วเปลี่ยนผลลัพธ์เป็น `String` มีความเป็นไปได้ว่าอินพุต `#name` อาจเป็นเอ็กซ์เพรสชันที่ต้องพิมพ์ออกมาตรงๆ เราจึงใช้ `stringify!` การใช้ `stringify!` ยังประหยัดการจัดสรรหน่วยความจำหนึ่งครั้งโดยการแปลง `#name` เป็นสตริงลิเทอรัลตอนคอมไพล์

ณ จุดนี้ `cargo build` ควรทำงานสำเร็จในทั้ง `hello_macro` และ `hello_macro_derive` มาเชื่อมเครตเหล่านี้เข้ากับโค้ดในลิสติ้ง 20-37 เพื่อดูมาโครแบบโพรซีเยอร์ทำงานจริงกัน! สร้างโปรเจกต์ไบนารีใหม่ในไดเรกทอรี _projects_ ของคุณโดยใช้ `cargo new pancakes` เราจำเป็นต้องเพิ่ม `hello_macro` และ `hello_macro_derive` เป็นดีเพนเดนซีในไฟล์ _Cargo.toml_ ของเครต `pancakes` หากคุณกำลังเผยแพร่เวอร์ชันของ `hello_macro` และ `hello_macro_derive` ของคุณไปยัง [crates.io](https://crates.io/)<!-- ignore --> พวกมันจะเป็นดีเพนเดนซีปกติ หากไม่ คุณสามารถระบุพวกมันเป็นดีเพนเดนซีแบบ `path` ได้ดังนี้:

```toml
{{#include ../listings/ch20-advanced-features/no-listing-21-pancakes/pancakes/Cargo.toml:6:8}}
```

นำโค้ดในลิสติ้ง 20-37 ไปใส่ในไฟล์ _src/main.rs_ แล้วรัน `cargo run`: มันควรพิมพ์ `Hello, Macro! My name is Pancakes!` การอิมพลีเมนต์เทรต `HelloMacro` จากมาโครแบบโพรซีเยอร์ถูกใส่เข้ามาโดยที่เครต `pancakes` ไม่จำเป็นต้องอิมพลีเมนต์มันเอง; `#[derive(HelloMacro)]` ได้เพิ่มการอิมพลีเมนต์เทรตให้

ต่อไป มาสำรวจว่ามาโครแบบโพรซีเยอร์ชนิดอื่นๆ แตกต่างจากมาโคร `derive` แบบกำหนดเองอย่างไร

### มาโครคล้ายแอตทริบิวต์

มาโครคล้ายแอตทริบิวต์คล้ายกับมาโคร `derive` แบบกำหนดเอง แต่แทนที่จะสร้างโค้ดสำหรับแอตทริบิวต์ `derive` พวกมันให้คุณสร้างแอตทริบิวต์ใหม่ได้ พวกมันยังยืดหยุ่นกว่า: `derive` ทำงานกับเฉพาะ struct และ enum เท่านั้น ส่วนแอตทริบิวต์สามารถนำไปใช้กับรายการอื่นๆ ได้ด้วย เช่นฟังก์ชัน นี่คือตัวอย่างการใช้มาโครคล้ายแอตทริบิวต์ สมมติว่าคุณมีแอตทริบิวต์ชื่อ `route` ที่ใส่คำอธิบายประกอบให้ฟังก์ชันเมื่อใช้เฟรมเวิร์กเว็บแอปพลิเคชัน:

```rust,ignore
#[route(GET, "/")]
fn index() {
```

แอตทริบิวต์ `#[route]` นี้จะถูกนิยามโดยเฟรมเวิร์กเป็นมาโครแบบโพรซีเยอร์ ซิกเนเจอร์ของฟังก์ชันนิยามมาโครจะมีหน้าตาแบบนี้:

```rust,ignore
#[proc_macro_attribute]
pub fn route(attr: TokenStream, item: TokenStream) -> TokenStream {
```

ในที่นี้ เรามีพารามิเตอร์สองตัวที่มีชนิด `TokenStream` ตัวแรกสำหรับเนื้อหาของแอตทริบิวต์: ส่วน `GET, "/"` ตัวที่สองคือบอดี้ของรายการที่แอตทริบิวต์แนบอยู่ด้วย: ในกรณีนี้คือ `fn index() {}` และส่วนที่เหลือของบอดี้ฟังก์ชัน

นอกเหนือจากนั้น มาโครคล้ายแอตทริบิวต์ทำงานเหมือนกับมาโคร `derive` แบบกำหนดเอง: คุณสร้างเครตที่มีชนิดเครต `proc-macro` และอิมพลีเมนต์ฟังก์ชันที่สร้างโค้ดที่คุณต้องการ!

### มาโครคล้ายฟังก์ชัน

มาโครคล้ายฟังก์ชันนิยามมาโครที่มีหน้าตาเหมือนการเรียกฟังก์ชัน คล้ายกับมาโคร `macro_rules!` พวกมันยืดหยุ่นกว่าฟังก์ชัน ตัวอย่างเช่น พวกมันรับอาร์กิวเมนต์จำนวนที่ไม่รู้ได้ อย่างไรก็ตาม มาโคร `macro_rules!` ถูกนิยามได้โดยใช้เฉพาะวากยสัมพันธ์คล้าย match ที่เราได้พูดคุยกันในหัวข้อ[“มาโครแบบประกาศสำหรับเมตาโปรแกรมมิ่งทั่วไป”][decl]<!-- ignore --> ก่อนหน้านี้ มาโครคล้ายฟังก์ชันรับพารามิเตอร์ `TokenStream` และนิยามของพวกมันจัดการ `TokenStream` นั้นโดยใช้โค้ด Rust เหมือนที่มาโครแบบโพรซีเยอร์อีกสองชนิดทำ ตัวอย่างหนึ่งของมาโครคล้ายฟังก์ชันคือมาโคร `sql!` ที่อาจถูกเรียกแบบนี้:

```rust,ignore
let sql = sql!(SELECT * FROM posts WHERE id=1);
```

มาโครนี้จะแยกวิเคราะห์คำสั่ง SQL ที่อยู่ข้างในและตรวจสอบว่าถูกต้องตามวากยสัมพันธ์หรือไม่ ซึ่งเป็นการประมวลผลที่ซับซ้อนกว่าที่มาโคร `macro_rules!` จะทำได้มาก มาโคร `sql!` จะถูกนิยามแบบนี้:

```rust,ignore
#[proc_macro]
pub fn sql(input: TokenStream) -> TokenStream {
```

นิยามนี้คล้ายกับซิกเนเจอร์ของมาโคร `derive` แบบกำหนดเอง: เรารับโทเค็นที่อยู่ภายในวงเล็บและคืนโค้ดที่เราต้องการสร้าง

## สรุป

เฮ้อ! ตอนนี้คุณมีฟีเจอร์ Rust บางอย่างในกล่องเครื่องมือของคุณที่คุณอาจไม่ค่อยได้ใช้บ่อยนัก แต่คุณจะรู้ว่าฟีเจอร์เหล่านั้นมีให้ใช้ในสถานการณ์ที่เฉพาะเจาะจงมากๆ เราได้แนะนำหัวข้อที่ซับซ้อนหลายหัวข้อ เพื่อที่ว่าเมื่อคุณพบเจอสิ่งเหล่านี้ในคำแนะนำจากข้อความแสดงข้อผิดพลาดหรือในโค้ดของคนอื่น คุณจะสามารถจดจำแนวคิดและวากยสัมพันธ์เหล่านี้ได้ ใช้บทนี้เป็นข้อมูลอ้างอิงเพื่อนำทางคุณไปสู่ทางออกต่างๆ

ต่อไป เราจะนำทุกอย่างที่ได้พูดคุยกันมาตลอดทั้งเล่มไปปฏิบัติจริงและทำโปรเจกต์อีกหนึ่งโปรเจกต์!
