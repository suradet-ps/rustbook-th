## ลักษณะเด่นของภาษาเชิงวัตถุ

ในแวดวงการเขียนโปรแกรมไม่มีความเห็นพ้องกันว่าภาษาหนึ่งๆ ต้องมีฟีเจอร์อะไรบ้างจึงจะถือว่าเป็นภาษาเชิงวัตถุ Rust ได้รับอิทธิพลจากกระบวนทัศน์การเขียนโปรแกรมหลายแบบ รวมถึงการเขียนโปรแกรมเชิงวัตถุ (object-oriented programming) ตัวอย่างเช่น เราได้สำรวจฟีเจอร์ที่มาจากการเขียนโปรแกรมเชิงฟังก์ชัน (functional programming) ในบทที่ 13 อาจกล่าวได้ว่าภาษาเชิงวัตถุมีลักษณะเด่นบางอย่างร่วมกัน กล่าวคือ ออบเจกต์ (object) การห่อหุ้ม (encapsulation) และการสืบทอด (inheritance) มาดูกันว่าลักษณะเด่นแต่ละอย่างหมายความว่าอะไร และ Rust รองรับมันหรือไม่

### ออบเจกต์บรรจุข้อมูลและพฤติกรรม

หนังสือ _Design Patterns: Elements of Reusable Object-Oriented Software_ ของ Erich Gamma, Richard Helm, Ralph Johnson และ John Vlissides (Addison-Wesley, 1994) ซึ่งมักถูกเรียกอย่างไม่เป็นทางการว่าหนังสือ _The Gang of Four_ เป็นแค็ตตาล็อกของแพตเทิร์นการออกแบบเชิงวัตถุ หนังสือเล่มนี้ให้นิยามการเขียนโปรแกรมเชิงวัตถุไว้เช่นนี้

> โปรแกรมเชิงวัตถุประกอบขึ้นจากออบเจกต์ **ออบเจกต์** ห่อหุ้มทั้งข้อมูลและกระบวนการที่ดำเนินการกับข้อมูลนั้น โดยทั่วไปกระบวนการเหล่านี้ถูกเรียกว่า **เมธอด** (method) หรือ **การดำเนินการ** (operation)

เมื่อใช้คำนิยามนี้ Rust ก็เป็นภาษาเชิงวัตถุ: struct และ enum มีข้อมูล และบล็อก `impl` จัดเตรียมเมธอดบน struct และ enum แม้ว่า struct และ enum ที่มีเมธอดจะไม่ถูก_เรียก_ว่าออบเจกต์ แต่พวกมันก็ให้ฟังก์ชันการทำงานเดียวกัน ตามคำนิยามออบเจกต์ของ Gang of Four

### การห่อหุ้มที่ซ่อนรายละเอียดการอิมพลีเมนต์

อีกแง่มุมหนึ่งที่มักเกี่ยวข้องกับการเขียนโปรแกรมเชิงวัตถุคือแนวคิดเรื่อง_การห่อหุ้ม_ (encapsulation) ซึ่งหมายความว่ารายละเอียดการอิมพลีเมนต์ของออบเจกต์ไม่สามารถเข้าถึงได้จากโค้ดที่ใช้ออบเจกต์นั้น ดังนั้น วิธีเดียวในการโต้ตอบกับออบเจกต์คือผ่าน API แบบสาธารณะของมัน โค้ดที่ใช้ออบเจกต์ไม่ควรสามารถเข้าถึงภายในของออบเจกต์และเปลี่ยนแปลงข้อมูลหรือพฤติกรรมได้โดยตรง สิ่งนี้ทำให้โปรแกรมเมอร์สามารถเปลี่ยนแปลงและรีแฟกเตอร์ภายในของออบเจกต์ได้โดยไม่จำเป็นต้องเปลี่ยนโค้ดที่ใช้ออบเจกต์

เราได้พูดคุยถึงวิธีควบคุมการห่อหุ้มในบทที่ 7: เราใช้คำสงวน `pub` เพื่อตัดสินว่ามอดูล ชนิดข้อมูล ฟังก์ชัน และเมธอดใดในโค้ดของเราควรเป็นแบบสาธารณะ (public) และโดยค่าเริ่มต้นทุกอย่างอื่นจะเป็นแบบส่วนตัว (private) ตัวอย่างเช่น เราสามารถนิยาม struct `AveragedCollection` ที่มีฟิลด์ (field) บรรจุเวกเตอร์ (vector) ของค่า `i32` ได้ struct นี้ยังมีฟิลด์ที่บรรจุค่าเฉลี่ยของค่าในเวกเตอร์ได้ด้วย ซึ่งหมายความว่าไม่จำเป็นต้องคำนวณค่าเฉลี่ยใหม่ทุกครั้งที่มีคนต้องการมัน กล่าวอีกนัยหนึ่ง `AveragedCollection` จะแคชค่าเฉลี่ยที่คำนวณไว้ให้เรา ลิสติ้ง 18-1 มีนิยามของ struct `AveragedCollection`

เมธอดแบบสาธารณะ `add`, `remove` และ `average` เป็นวิธีเดียวในการเข้าถึงหรือแก้ไขข้อมูลในอินสแตนซ์ (instance) ของ `AveragedCollection` เมื่อสมาชิกถูกเพิ่มเข้าไปใน `list` ด้วยเมธอด `add` หรือถูกลบด้วยเมธอด `remove` การอิมพลีเมนต์ของแต่ละเมธอดจะเรียกเมธอด `update_average` แบบส่วนตัวซึ่งจัดการอัปเดตฟิลด์ `average` ด้วย

เราเก็บฟิลด์ `list` และ `average` ไว้เป็นแบบส่วนตัว เพื่อไม่ให้โค้ดภายนอกสามารถเพิ่มหรือลบสมาชิกในฟิลด์ `list` ได้โดยตรง มิฉะนั้น ฟิลด์ `average` อาจไม่ซิงก์กันเมื่อ `list` เปลี่ยนแปลง เมธอด `average` คืนค่าในฟิลด์ `average` ทำให้โค้ดภายนอกอ่าน `average` ได้แต่แก้ไขไม่ได้

เนื่องจากเราได้ห่อหุ้มรายละเอียดการอิมพลีเมนต์ของ struct `AveragedCollection` แล้ว ในอนาคตเราจึงเปลี่ยนแง่มุมต่างๆ เช่น โครงสร้างข้อมูล ได้อย่างง่ายดาย ตัวอย่างเช่น เราอาจใช้ `HashSet<i32>` แทน `Vec<i32>` สำหรับฟิลด์ `list` ตราบใดที่ซิกเนเจอร์ของเมธอดแบบสาธารณะ `add`, `remove` และ `average` ยังเหมือนเดิม โค้ดที่ใช้ `AveragedCollection` ก็ไม่จำเป็นต้องเปลี่ยน ในทางกลับกัน หากเราทำให้ `list` เป็นแบบสาธารณะ มันอาจไม่เป็นเช่นนั้น: `HashSet<i32>` และ `Vec<i32>` มีเมธอดสำหรับเพิ่มและลบสมาชิกที่แตกต่างกัน โค้ดภายนอกจึงอาจต้องเปลี่ยนหากมันแก้ไข `list` โดยตรง

หากการห่อหุ้มเป็นแง่มุมที่จำเป็นสำหรับภาษาที่จะถือว่าเป็นภาษาเชิงวัตถุ Rust ก็ตรงตามข้อกำหนดนั้น ตัวเลือกในการใช้ `pub` หรือไม่ใช้กับส่วนต่างๆ ของโค้ดทำให้สามารถห่อหุ้มรายละเอียดการอิมพลีเมนต์ได้

### การสืบทอดในฐานะระบบชนิดข้อมูลและในฐานะการแบ่งปันโค้ด

_การสืบทอด_ (inheritance) เป็นกลไกที่ออบเจกต์หนึ่งสามารถสืบทอดองค์ประกอบต่างๆ จากนิยามของออบเจกต์อื่นได้ จึงได้ข้อมูลและพฤติกรรมของออบเจกต์แม่โดยที่คุณไม่ต้องนิยามมันซ้ำอีกครั้ง

หากภาษาหนึ่งต้องมีการสืบทอดจึงจะเป็นภาษาเชิงวัตถุได้ Rust ก็ไม่ใช่ภาษาเช่นนั้น ไม่มีวิธีนิยาม struct ที่สืบทอดฟิลด์และพฤติกรรมการอิมพลีเมนต์เมธอดของ struct แม่ได้โดยไม่ใช้มาโคร

อย่างไรก็ตาม หากคุณคุ้นเคยกับการมีการสืบทอดอยู่ในชุดเครื่องมือการเขียนโปรแกรมของคุณ คุณก็ใช้วิธีแก้ปัญหาอื่นๆ ใน Rust ได้ ขึ้นอยู่กับเหตุผลที่คุณเอื้อมไปหยิบการสืบทอดมาใช้ตั้งแต่แรก

คุณจะเลือกใช้การสืบทอดด้วยเหตุผลหลักสองประการ เหตุผลหนึ่งคือการนำโค้ดกลับมาใช้ซ้ำ: คุณสามารถอิมพลีเมนต์พฤติกรรมเฉพาะอย่างสำหรับชนิดข้อมูลหนึ่ง และการสืบทอดทำให้คุณนำการอิมพลีเมนต์นั้นกลับมาใช้ซ้ำกับชนิดข้อมูลอื่นได้ คุณทำเช่นนี้ได้ในขอบเขตจำกัดในโค้ด Rust โดยใช้การอิมพลีเมนต์เมธอดของเทรต (trait) แบบค่าเริ่มต้น ซึ่งคุณได้เห็นในลิสติ้ง 10-14 เมื่อเราเพิ่มการอิมพลีเมนต์ค่าเริ่มต้นของเมธอด `summarize` บนเทรต `Summary` ชนิดข้อมูลใดก็ตามที่อิมพลีเมนต์เทรต `Summary` จะมีเมธอด `summarize` ใช้ได้โดยไม่ต้องมีโค้ดเพิ่มเติม ซึ่งคล้ายกับคลาสแม่ที่มีการอิมพลีเมนต์เมธอด และคลาสลูกที่สืบทอดก็มีการอิมพลีเมนต์เมธอดนั้นด้วย เรายังเขียนทับการอิมพลีเมนต์ค่าเริ่มต้นของเมธอด `summarize` ได้ด้วยเมื่อเราอิมพลีเมนต์เทรต `Summary` ซึ่งคล้ายกับคลาสลูกที่เขียนทับการอิมพลีเมนต์เมธอดที่สืบทอดมาจากคลาสแม่

อีกเหตุผลหนึ่งในการใช้การสืบทอดเกี่ยวข้องกับระบบชนิดข้อมูล: เพื่อให้ชนิดข้อมูลลูกถูกใช้ในตำแหน่งเดียวกับชนิดข้อมูลแม่ได้ สิ่งนี้ยังเรียกว่า_พอลิมอร์ฟิซึม_ (polymorphism) ซึ่งหมายความว่าคุณสามารถใช้หลายออบเจกต์แทนกันได้ตอนรันไทม์หากพวกมันมีลักษณะบางอย่างร่วมกัน

> ### พอลิมอร์ฟิซึม
>
> สำหรับคนจำนวนมาก พอลิมอร์ฟิซึมเป็นคำพ้องความหมายของการสืบทอด แต่มันเป็นแนวคิดที่กว้างกว่านั้นจริงๆ โดยหมายถึงโค้ดที่ทำงานกับข้อมูลหลายชนิดได้ สำหรับการสืบทอด ชนิดข้อมูลเหล่านั้นโดยทั่วไปคือคลาสย่อย
>
> Rust ใช้เจเนอริก (generic) เพื่อนามธรรมเหนือชนิดข้อมูลที่เป็นไปได้ต่างๆ และใช้บาวด์ของเทรต (trait bound) เพื่อกำหนดข้อจำกัดว่าชนิดข้อมูลเหล่านั้นต้องจัดเตรียมอะไรบ้าง สิ่งนี้บางครั้งเรียกว่า_พอลิมอร์ฟิซึมแบบพาราเมตริกที่มีขอบเขต_ (bounded parametric polymorphism)

Rust เลือกชุดข้อแลกเปลี่ยนที่แตกต่างออกไปโดยไม่เสนอการสืบทอด การสืบทอดมักมีความเสี่ยงที่จะแบ่งปันโค้ดมากเกินความจำเป็น คลาสลูกไม่ควรมีลักษณะเด่นทั้งหมดของคลาสแม่เสมอไป แต่จะได้มาเมื่อใช้การสืบทอด สิ่งนี้ทำให้การออกแบบโปรแกรมยืดหยุ่นน้อยลง มันยังเพิ่มโอกาสในการเรียกเมธอดบนคลาสลูกที่ไม่สมเหตุสมผลหรือทำให้เกิดข้อผิดพลาด เพราะเมธอดเหล่านั้นใช้ไม่ได้กับคลาสลูก นอกจากนี้ ภาษาบางภาษายอมให้มี_การสืบทอดเชิงเดี่ยว_ (single inheritance) เท่านั้น (หมายความว่าคลาสลูกสืบทอดจากคลาสเดียวได้เท่านั้น) ซึ่งยิ่งจำกัดความยืดหยุ่นของการออกแบบโปรแกรมมากขึ้น

ด้วยเหตุผลเหล่านี้ Rust จึงใช้แนวทางที่แตกต่างออกไปโดยใช้เทรตออบเจกต์ (trait object) แทนการสืบทอดเพื่อบรรลุพอลิมอร์ฟิซึมตอนรันไทม์ มาดูกันว่าเทรตออบเจกต์ทำงานอย่างไร
