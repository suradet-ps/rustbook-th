## การทำงานพร้อมกันแบบใช้สถานะร่วมกัน

การส่งผ่านข้อความ (message passing) เป็นวิธีที่ดีในการจัดการการทำงานพร้อมกัน (concurrency) แต่นั่นไม่ใช่วิธีเดียว อีกวิธีหนึ่งคือการให้หลายๆ เธรดสามารถเข้าถึงข้อมูลที่ใช้งานร่วมกัน (shared data) ได้ ลองพิจารณาส่วนหนึ่งของสโลแกนจากเอกสารภาษา Go อีกครั้ง: “อย่าสื่อสารกันด้วยการแชร์หน่วยความจำ”

แล้วการสื่อสารด้วยการแชร์หน่วยความจำจะมีลักษณะเป็นอย่างไร? นอกจากนี้ ทำไมผู้ที่สนับสนุนการส่งผ่านข้อความจึงเตือนไม่ให้ใช้การแชร์หน่วยความจำ?

ในแง่หนึ่ง แชนเนล (channel) ในภาษาโปรแกรมใดๆ จะมีความคล้ายคลึงกับระบบความเป็นเจ้าของแบบเดี่ยว (single ownership) เพราะเมื่อคุณส่งค่าผ่านแชนเนลไปแล้ว คุณก็ไม่ควรนำค่านั้นกลับมาใช้งานอีกต่อไป ส่วนการทำงานพร้อมกันโดยใช้หน่วยความจำร่วมกันนั้นจะคล้ายกับความเป็นเจ้าของหลายราย (multiple ownership) นั่นคือหลายเธรดสามารถเข้าถึงตำแหน่งหน่วยความจำเดียวกันได้ในเวลาเดียวกัน ดังที่คุณได้เห็นในบทที่ 15 ว่าสมาร์ตพอยน์เตอร์ (smart pointer) ช่วยให้สามารถมีความเป็นเจ้าของหลายรายได้ แต่ความเป็นเจ้าของหลายรายก็เพิ่มความซับซ้อนตามมา เพราะเราจำเป็นต้องบริหารจัดการเจ้าของแต่ละรายให้ถูกต้อง อย่างไรก็ตาม ระบบชนิดข้อมูลและกฎความเป็นเจ้าของของ Rust จะช่วยให้คุณจัดการเรื่องเหล่านี้ได้อย่างถูกต้องและปลอดภัย ตัวอย่างเช่น ลองมาดูมิวเท็กซ์ (mutex) ซึ่งเป็นหนึ่งในพริมิทีฟการทำงานพร้อมกัน (concurrency primitive) ที่นิยมใช้กันทั่วไปสำหรับหน่วยความจำร่วม

### การควบคุมการเข้าถึงด้วยมิวเท็กซ์

คำว่า _มิวเท็กซ์_ (mutex) เป็นคำย่อของ _mutual exclusion_ (การกีดกันซึ่งกันและกัน) ซึ่งหมายความว่ามิวเท็กซ์จะอนุญาตให้มีเพียงเธรดเดียวเท่านั้นที่สามารถเข้าถึงข้อมูลได้ ณ ขณะใดขณะหนึ่ง ในการเข้าถึงข้อมูลในมิวเท็กซ์ เธรดจะต้องส่งสัญญาณขอก่อนโดยการขอถือครองล็อก (acquire the lock) ของมิวเท็กซ์ โดยที่_ล็อก_ (lock) เป็นโครงสร้างข้อมูลส่วนหนึ่งของมิวเท็กซ์ที่คอยติดตามว่าใครคือผู้ที่ถือครองสิทธิ์การเข้าถึงข้อมูลแต่เพียงผู้เดียวในขณะนั้น ดังนั้น เราจึงมักพูดว่ามิวเท็กซ์ทำหน้าที่_เฝ้าปกป้อง_ (guard) ข้อมูลที่มันเก็บรักษาไว้ผ่านระบบล็อก

มิวเท็กซ์ขึ้นชื่อเรื่องความยุ่งยากในการใช้งาน เพราะคุณต้องจำกฎเหล็กสองข้อนี้ให้ดี:

1. คุณต้องพยายามขอถือครองล็อกก่อนจะนำข้อมูลไปใช้งาน
2. เมื่อคุณใช้งานข้อมูลที่มิวเท็กซ์เฝ้าปกป้องเสร็จเรียบร้อยแล้ว คุณต้องปลดล็อกข้อมูลเพื่อให้เธรดอื่นสามารถเข้ามาถือครองล็อกได้

หากจะเปรียบเทียบมิวเท็กซ์กับสถานการณ์ในชีวิตจริง ลองนึกภาพเวทีเสวนาในงานประชุมที่มีไมโครโฟนเพียงตัวเดียว ก่อนที่นักเสวนาจะพูดได้ พวกเขาจะต้องขอหรือส่งสัญญาณว่าต้องการใช้ไมโครโฟน เมื่อได้รับไมโครโฟนมาแล้ว พวกเขาสามารถพูดได้นานเท่าที่ต้องการ แล้วจึงส่งไมโครโฟนต่อให้นักเสวนาคนถัดไปที่ขอพูด หากนักเสวนาคนหนึ่งลืมส่งต่อไมโครโฟนเมื่อใช้เสร็จแล้ว ก็จะไม่มีใครอื่นสามารถพูดได้เลย และหากการบริหารจัดการไมโครโฟนที่ใช้ร่วมกันนี้ผิดพลาด การเสวนาก็จะไม่เป็นไปตามที่วางแผนไว้!

การจัดการมิวเท็กซ์ให้ถูกต้องสมบูรณ์นั้นอาจซับซ้อนอย่างเหลือเชื่อ ซึ่งเป็นเหตุผลที่หลายคนชื่นชอบแชนเนลมาก อย่างไรก็ตาม ต้องขอบคุณระบบชนิดข้อมูลและกฎความเป็นเจ้าของของ Rust คุณจึงแทบไม่มีโอกาสทำการล็อกและปลดล็อกผิดพลาดเลย

เช่นเดียวกับหลายๆ ชนิดข้อมูล เราสร้าง `Mutex<T>` ขึ้นมาได้โดยใช้ฟังก์ชันสัมพันธ์ (associated function) `new` และหากต้องการเข้าถึงข้อมูลภายในมิวเท็กซ์ เราจะต้องเรียกใช้เมธอด `lock` เพื่อขอถือครองล็อก ซึ่งการเรียกนี้จะบล็อก (block) การทำงานของเธรดปัจจุบันไว้ จนกว่าจะถึงคิวที่เธรดของเราได้รับล็อกมาครอบครอง

การเรียก `lock` จะล้มเหลวหากเธรดอื่นที่ถือครองล็อกอยู่ก่อนหน้าเกิดแพนิก (panic) ขึ้น เพราะในกรณีนั้นจะไม่มีใครสามารถขอถือครองล็อกได้อีกต่อไป เราจึงเลือกใช้ `unwrap` เพื่อให้เธรดนี้แพนิกตามไปด้วยหากตกอยู่ในสถานการณ์ดังกล่าว

เมื่อถือครองล็อกสำเร็จแล้ว เราสามารถปฏิบัติต่อค่าที่ได้รับกลับมา (ซึ่งในที่นี้คือ `num`) เสมือนเป็นเรเฟอเรนซ์แบบเปลี่ยนแปลงค่าได้ (mutable reference) ไปยังข้อมูลข้างในได้ทันที โดยระบบชนิดข้อมูลจะคอยรับประกันว่าเราต้องถือครองล็อกก่อนใช้งานค่าใน `m` เสมอ ชนิดข้อมูลของ `m` คือ `Mutex<i32>` ไม่ใช่ `i32` เราจึง_จำเป็นต้อง_เรียก `lock` ก่อนจึงจะเข้าถึงค่า `i32` ได้ เราไม่มีทางลืมขั้นตอนนี้ได้เลย เพราะหากไม่ทำ ระบบชนิดข้อมูลจะไม่ยอมให้เราเข้าถึงค่า `i32` ข้างในอย่างเด็ดขาด

แท้จริงแล้วการเรียก `lock` จะคืนค่าชนิด `MutexGuard` ที่ถูกห่อหุ้มไว้ใน `LockResult` ซึ่งเราจัดการด้วยการเรียก `unwrap` โดยชนิดข้อมูล `MutexGuard` นั้นได้อิมพลีเมนต์ `Deref` เพื่อชี้ไปยังข้อมูลภายใน และยังอิมพลีเมนต์ `Drop` เพื่อปล่อยล็อกโดยอัตโนมัติเมื่อ `MutexGuard` หลุดออกจากสโคป (ซึ่งเกิดขึ้นเมื่อสิ้นสุดบล็อกสโคปชั้นใน) ส่งผลให้เราไม่ต้องกังวลว่าจะลืมปล่อยล็อกจนขัดขวางไม่ให้เธรดอื่นใช้งานมิวเท็กซ์ เพราะกระบวนการปล่อยล็อกจะทำงานโดยอัตโนมัติเสมอ

หลังจากทิ้งล็อกไปแล้ว เราสามารถพิมพ์ค่าของมิวเท็กซ์ออกมาดู และจะเห็นว่าค่า `i32` ภายในถูกแก้ไขเป็น `6` ได้เรียบร้อยแล้ว

น่าเสียดายที่ `Rc<T>` ไม่ปลอดภัยสำหรับการแชร์ข้ามเธรด เพราะในขณะที่ `Rc<T>` จัดการจำนวนเรเฟอเรนซ์ มันจะเพิ่มค่านับทุกครั้งที่มีการเรียก `clone` และลดค่านับลงเมื่อโคลนแต่ละตัวถูกทำลาย (drop) ทว่ามันไม่ได้ใช้พริมิทีฟการทำงานพร้อมกันใดๆ มาควบคุมเพื่อให้แน่ใจว่าการปรับเปลี่ยนค่านับจะไม่ถูกขัดจังหวะโดยเธรดอื่น ซึ่งอาจส่งผลให้การนับจำนวนคลาดเคลื่อน—กลายเป็นบั๊กที่แอบแฝงและอาจนำไปสู่ปัญหาหน่วยความจำรั่วไหล (memory leak) หรือทำให้ค่าถูกทำลายไปก่อนที่เราจะใช้งานเสร็จ สิ่งที่เราต้องการอย่างแท้จริงคือชนิดข้อมูลที่ทำงานเหมือน `Rc<T>` ทุกประการ แต่ปรับเปลี่ยนจำนวนเรเฟอเรนซ์ด้วยวิธีการที่ปลอดภัยต่อเธรด (thread-safe)

#### การนับจำนวนเรเฟอเรนซ์แบบอะตอมมิกด้วย `Arc<T>`

โชคดีที่ `Arc<T>` _คือ_ชนิดข้อมูลลักษณะเดียวกับ `Rc<T>` ที่ปลอดภัยต่อการใช้งานในสถานการณ์การทำงานพร้อมกัน ตัวอักษร _a_ นั้นย่อมาจาก _atomic_ ซึ่งหมายความว่าเป็นชนิดข้อมูลที่_นับจำนวนเรเฟอเรนซ์แบบอะตอมมิก (atomically reference-counted)_ ทั้งนี้ อะตอมมิก (atomic) เป็นพริมิทีฟการทำงานพร้อมกันอีกรูปแบบหนึ่งที่เราจะไม่ลงลึกในรายละเอียดที่นี่ หากสนใจโปรดดูเอกสารของไลบรารีมาตรฐานสำหรับ [`std::sync::atomic`][atomic]<!-- ignore --> เพิ่มเติม ณ จุดนี้ คุณเพียงแค่ต้องรู้ว่าการทำงานแบบอะตอมมิกนั้นทำหน้าที่คล้ายกับชนิดข้อมูลพื้นฐานทั่วไป แต่ปลอดภัยสำหรับการแชร์ข้ามเธรด

คุณอาจสงสัยว่าแล้วทำไมชนิดข้อมูลพื้นฐานทั้งหมดจึงไม่ถูกทำเป็นแบบอะตอมมิกไปเสียเลย และทำไมชนิดข้อมูลในไลบรารีมาตรฐานถึงไม่ถูกสร้างให้ใช้ `Arc<T>` เป็นค่าเริ่มต้น เหตุผลก็คือความปลอดภัยต่อเธรดนั้นมีต้นทุนด้านประสิทธิภาพ (performance penalty) แลกมาด้วย ซึ่งเป็นต้นทุนที่คุณควรจ่ายเฉพาะเมื่อจำเป็นต้องใช้จริงๆ เท่านั้น หากคุณเพียงแค่จัดการค่าต่างๆ ภายในเธรดเดียว โค้ดของคุณจะทำงานได้เร็วกว่าหากไม่ต้องแบกรับการบังคับใช้มาตรการความปลอดภัยที่อะตอมมิกจัดเตรียมไว้

คราวนี้กลับมาที่ตัวอย่างของเรา: เนื่องจาก `Arc<T>` และ `Rc<T>` มี API เหมือนกันทุกประการ เราจึงแก้โปรแกรมได้ง่ายๆ เพียงเปลี่ยนบรรทัด `use`, การเรียก `new` และการเรียก `clone` แล้วโค้ดในลิสติ้ง 16-15 ก็จะคอมไพล์และรันได้สำเร็จในที่สุด

### การเปรียบเทียบ `RefCell<T>`/`Rc<T>` กับ `Mutex<T>`/`Arc<T>`

คุณอาจสังเกตเห็นว่า `counter` เป็นตัวแปรที่เปลี่ยนแปลงค่าไม่ได้ แต่เรากลับได้รับเรเฟอเรนซ์แบบเปลี่ยนแปลงค่าได้ไปยังข้อมูลข้างใน นั่นหมายความว่า `Mutex<T>` มอบความสามารถในการเปลี่ยนแปลงค่าภายใน (interior mutability) ให้เช่นเดียวกับที่ตระกูล `Cell` ทำ และในทำนองเดียวกับที่เราใช้ `RefCell<T>` ในบทที่ 15 เพื่อให้สามารถแก้ไขข้อมูลภายใน `Rc<T>` ได้ เราจึงใช้ `Mutex<T>` เพื่อแก้ไขข้อมูลภายใน `Arc<T>` นั่นเอง

รายละเอียดอีกประการที่พึงระวังคือ Rust ไม่สามารถป้องกันข้อผิดพลาดทางตรรกะ (logic error) ได้ทุกรูปแบบเมื่อคุณใช้งาน `Mutex<T>` หากยังจำได้จากบทที่ 15 การใช้ `Rc<T>` มีความเสี่ยงที่จะเกิดวงจรเรเฟอเรนซ์ (reference cycle) ที่ค่า `Rc<T>` สองตัวชี้อ้างอิงถึงกันจนทำให้หน่วยความจำรั่วไหล ในทำนองเดียวกัน `Mutex<T>` ก็มาพร้อมกับความเสี่ยงที่จะเกิด_เดดล็อก (deadlock)_ ซึ่งจะเกิดขึ้นเมื่อการทำงานหนึ่งจำเป็นต้องล็อกทรัพยากรสองชิ้นพร้อมกัน และมีเธรดสองตัวถือครองล็อกไปคนละชิ้น ทำให้ต่างฝ่ายต่างรอคอยกันไปตลอดกาล หากคุณสนใจศึกษาเรื่องเดดล็อกเพิ่มเติม ลองเขียนโปรแกรม Rust ที่ทำให้เกิดเดดล็อกขึ้นมาดู จากนั้นค้นคว้ากลยุทธ์การป้องกันและบรรเทาปัญหาเดดล็อกสำหรับมิวเท็กซ์ในภาษาใดก็ได้ แล้วลองนำมาอิมพลีเมนต์ใน Rust ซึ่งเอกสาร API ของไลบรารีมาตรฐานสำหรับ `Mutex<T>` และ `MutexGuard` มีข้อมูลที่เป็นประโยชน์อย่างยิ่ง

เราจะปิดท้ายบทนี้ด้วยการกล่าวถึงเทรต `Send` และ `Sync` รวมถึงวิธีนำพวกมันไปประยุกต์ใช้กับชนิดข้อมูลที่เราสร้างขึ้นเอง
