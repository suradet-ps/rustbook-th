## การใช้เทรตออบเจกต์เพื่อนามธรรมพฤติกรรมร่วม

ในบทที่ 8 เราได้พูดถึงข้อจำกัดประการหนึ่งของเวกเตอร์ นั่นคือสามารถเก็บสมาชิกได้เพียงชนิดเดียวเท่านั้น ซึ่งเราได้ทำวิธีแก้ไขชั่วคราวไว้ในลิสติ้ง 8-9 โดยการนิยาม enum `SpreadsheetCell` ที่มีวาเรียนต์สำหรับเก็บจำนวนเต็ม จำนวนทศนิยม และข้อความ ซึ่งช่วยให้เราสามารถเก็บข้อมูลต่างชนิดกันในแต่ละเซลล์ และยังคงใช้เวกเตอร์เป็นตัวแทนของแถวเซลล์ได้ นี่เป็นทางออกที่ยอดเยี่ยมเมื่อสมาชิกที่สับเปลี่ยนกันได้ของเราเป็นชุดชนิดข้อมูลที่คงที่และทราบล่วงหน้าอยู่แล้วในตอนที่โค้ดถูกคอมไพล์

อย่างไรก็ตาม บางครั้งเราต้องการให้ผู้ใช้ไลบรารีสามารถต่อขยายชุดของชนิดข้อมูลที่นำมาใช้ในสถานการณ์นั้น ๆ ได้ เพื่อแสดงให้เห็นว่าทำได้อย่างไร เราจะสร้างตัวอย่างเครื่องมือส่วนติดต่อผู้ใช้แบบกราฟิก (graphical user interface หรือ GUI) ที่วนลูปผ่านรายการของไอเทม แล้วเรียกใช้เมธอด `draw` กับแต่ละตัวเพื่อวาดมันลงบนหน้าจอ ซึ่งเป็นเทคนิคที่พบได้ทั่วไปสำหรับเครื่องมือ GUI เราจะสร้างเครตไลบรารีชื่อ `gui` ที่บรรจุโครงสร้างของไลบรารี GUI ไว้ เครตนี้อาจมีชนิดข้อมูลบางตัวเตรียมไว้ให้ใช้งาน เช่น `Button` หรือ `TextField` นอกจากนี้ ผู้ใช้ `gui` ยังต้องการสร้างชนิดข้อมูลของตนเองที่สามารถวาดลงจอได้ด้วย เช่น โปรแกรมเมอร์คนหนึ่งอาจเพิ่ม `Image` ขณะที่อีกคนอาจเพิ่ม `SelectBox`

ในขณะที่เขียนไลบรารี เราไม่มีทางรู้ล่วงหน้าหรือนิยามชนิดข้อมูลทั้งหมดที่โปรแกรมเมอร์คนอื่นอาจต้องการสร้างขึ้นได้ แต่สิ่งที่เรารู้คือ `gui` จำเป็นต้องติดตามค่าจำนวนมากที่มีชนิดข้อมูลแตกต่างกัน และต้องเรียกเมธอด `draw` บนค่าแต่ละตัวเหล่านั้น โดยตัวไลบรารีไม่จำเป็นต้องรู้รายละเอียดที่แน่ชัดว่าเกิดอะไรขึ้นเมื่อเรียกเมธอด `draw` ขอเพียงแค่ค่านั้นมีเมธอดดังกล่าวให้เรียกใช้ก็พอ

หากทำสิ่งนี้ในภาษาที่มีการสืบทอด เราอาจนิยามคลาสชื่อ `Component` ที่มีเมธอดชื่อ `draw` ขึ้นมา จากนั้นคลาสอื่น ๆ เช่น `Button`, `Image` และ `SelectBox` ก็จะสืบทอดมาจาก `Component` ทำให้ได้รับเมธอด `draw` ติดตัวมาด้วย แต่ละคลาสสามารถเขียนทับ (override) เมธอด `draw` เพื่อกำหนดพฤติกรรมเฉพาะของตนเองได้ โดยตัวเฟรมเวิร์กสามารถปฏิบัติต่อทุกชนิดข้อมูลราวกับว่าเป็นอินสแตนซ์ของ `Component` และเรียก `draw` บนพวกมันได้เลย แต่เนื่องจาก Rust ไม่มีการสืบทอด เราจึงต้องใช้วิธีอื่นในการจัดโครงสร้างไลบรารี `gui` เพื่อเปิดทางให้ผู้ใช้นำชนิดข้อมูลใหม่เข้ามาทำงานร่วมกับไลบรารีได้

### การนิยามเทรตสำหรับพฤติกรรมร่วม

เพื่ออิมพลีเมนต์พฤติกรรมที่เราต้องการให้ `gui` มี เราจะนิยามเทรตชื่อ `Draw` ที่มีเมธอดหนึ่งตัวชื่อ `draw` จากนั้นเรานิยามเวกเตอร์ที่รับเทรตออบเจกต์ได้ _เทรตออบเจกต์_ (trait object) ชี้ไปยังทั้งอินสแตนซ์ (instance) ของชนิดข้อมูลที่อิมพลีเมนต์เทรตที่เราระบุ และตารางที่ใช้ค้นหาเมธอดของเทรตบนชนิดข้อมูลนั้นตอนรันไทม์ เราสร้างเทรตออบเจกต์โดยระบุพอยน์เตอร์บางชนิด เช่น เรเฟอเรนซ์ (reference) หรือสมาร์ตพอยน์เตอร์ (smart pointer) `Box<T>` จากนั้นตามด้วยคำสงวน `dyn` แล้วระบุเทรตที่เกี่ยวข้อง (เราจะพูดถึงเหตุผลที่เทรตออบเจกต์ต้องใช้พอยน์เตอร์ใน[“ชนิดข้อมูลขนาดไม่คงที่และเทรต `Sized`”][dynamically-sized]<!-- ignore --> ในบทที่ 20) เราใช้เทรตออบเจกต์แทนชนิดเจเนอริก (generic) หรือชนิดที่เป็นรูปธรรมได้ ทุกที่ที่เราใช้เทรตออบเจกต์ ระบบชนิดข้อมูลของ Rust จะรับประกันตอนคอมไพล์ว่าค่าใดก็ตามที่ใช้ในบริบทนั้นจะอิมพลีเมนต์เทรตของเทรตออบเจกต์นั้น ดังนั้น เราจึงไม่จำเป็นต้องรู้ชนิดข้อมูลที่เป็นไปได้ทั้งหมดตอนคอมไพล์

เราเคยกล่าวไว้ก่อนหน้านี้ว่า ใน Rust เราจะหลีกเลี่ยงการเรียก struct และ enum ว่า "ออบเจกต์" เพื่อแยกความแตกต่างจากออบเจกต์ในภาษาอื่น ๆ ใน struct หรือ enum ข้อมูลในฟิลด์และพฤติกรรมในบล็อก `impl` จะถูกแยกออกจากกัน ในขณะที่ภาษาอื่น ๆ ข้อมูลและพฤติกรรมที่รวมอยู่ด้วยกันในแนวคิดเดียวนั้นมักจะถูกเรียกว่าออบเจกต์ ส่วนเทรตออบเจกต์จะแตกต่างจากออบเจกต์ในภาษาอื่นตรงที่เราไม่สามารถใส่ข้อมูลเพิ่มเข้าไปในเทรตออบเจกต์ได้ เทรตออบเจกต์จึงไม่ได้มีประโยชน์ครอบคลุมรอบด้านเหมือนออบเจกต์ในภาษาอื่น แต่มีจุดประสงค์เฉพาะทางคือเพื่อสร้างนามธรรมครอบคลุมพฤติกรรมที่มีร่วมกัน

แนวคิดนี้—คือการสนใจเพียงแค่ว่าค่านั้น ๆ ตอบสนองต่อคำสั่งหรือเมธอดใดได้บ้าง แทนที่จะสนใจชนิดข้อมูลรูปธรรมที่แท้จริง—มีความคล้ายคลึงกับแนวคิด _duck typing_ ในภาษาที่มีระบบชนิดข้อมูลแบบไดนามิก: กล่าวคือ "ถ้ามันเดินเหมือนเป็ดและร้องก้าบ ๆ เหมือนเป็ด มันก็คือเป็ด!" ในการอิมพลีเมนต์ `run` บน `Screen` ในลิสติ้ง 18-5 เมธอด `run` จึงไม่จำเป็นต้องรู้เลยว่าชนิดข้อมูลรูปธรรมที่แท้จริงของแต่ละคอมโพเนนต์คืออะไร และไม่จำเป็นต้องตรวจเช็กว่าคอมโพเนนต์ตัวนั้นเป็นอินสแตนซ์ของ `Button` หรือ `SelectBox` หรือไม่ มันเพียงแค่เรียกใช้เมธอด `draw` บนคอมโพเนนต์นั้นเท่านั้น ด้วยการระบุ `Box<dyn Draw>` เป็นชนิดข้อมูลของสมาชิกในเวกเตอร์ `components` เราจึงได้กำหนดไว้ว่า `Screen` ต้องการเพียงค่าใดก็ตามที่เราสามารถเรียกเมธอด `draw` ได้

ข้อดีของการใช้เทรตออบเจกต์และระบบชนิดข้อมูลของ Rust เพื่อเขียนโค้ดในลักษณะที่คล้ายกับ duck typing คือ เราไม่จำเป็นต้องคอยตรวจสอบว่าค่านั้น ๆ อิมพลีเมนต์เมธอดที่ต้องการหรือไม่ในตอนรันไทม์ และไม่ต้องกังวลว่าจะเกิด runtime error หากเผลอไปเรียกเมธอดที่ค่านั้นไม่ได้อิมพลีเมนต์ไว้ เพราะ Rust จะไม่ยอมคอมไพล์โค้ดของเราตั้งแต่แรก หากค่าเหล่านั้นไม่ได้อิมพลีเมนต์เทรตที่เทรตออบเจกต์กำหนดไว้

### การดิสแพตช์แบบไดนามิก

ย้อนกลับไปในหัวข้อ [“ประสิทธิภาพของโค้ดที่ใช้เจเนอริก”][performance-of-code-using-generics]<!-- ignore --> ในบทที่ 10 ที่เราได้อธิบายถึงกระบวนการมอโนมอร์ไฟเซชัน (monomorphization) ซึ่งคอมไพเลอร์จะทำให้กับโค้ดเจเนอริก: โดยคอมไพเลอร์จะสร้างการอิมพลีเมนต์ฟังก์ชันและเมธอดแบบไม่ใช้เจเนอริกขึ้นมาสำหรับแต่ละชนิดข้อมูลรูปธรรมที่เรานำมาแทนที่พารามิเตอร์ชนิดข้อมูลเจเนอริก โค้ดที่ได้จากกระบวนการนี้จะทำงานแบบ_การดิสแพตช์แบบสแตติก_ (static dispatch) ซึ่งหมายถึงคอมไพเลอร์รู้ตั้งแต่ตอนคอมไพล์แล้วว่าจะต้องเรียกใช้เมธอดตัวใด สิ่งนี้ตรงกันข้ามกับ_การดิสแพตช์แบบไดนามิก_ (dynamic dispatch) ซึ่งคอมไพเลอร์ไม่สามารถบอกได้ในตอนคอมไพล์ว่าเมธอดใดจะถูกเรียก โดยในกรณีนี้ คอมไพเลอร์จะสร้างโค้ดที่ไปค้นหาและตัดสินใจ ณ ตอนรันไทม์ว่าจะต้องเรียกใช้เมธอดใด

เมื่อเราใช้เทรตออบเจกต์ Rust จำเป็นต้องใช้การดิสแพตช์แบบไดนามิก เนื่องจากคอมไพเลอร์ไม่อาจล่วงรู้ชนิดข้อมูลทั้งหมดที่จะถูกนำมาใช้ร่วมกับโค้ดส่วนนั้น จึงไม่รู้ว่าควรเรียกเมธอดของชนิดข้อมูลใด แต่ ณ ตอนรันไทม์ Rust จะใช้พอยน์เตอร์ที่อยู่ภายในเทรตออบเจกต์เพื่อระบุเมธอดที่ต้องเรียกใช้ การค้นหาเมธอดนี้มีต้นทุนการประมวลผล (overhead) เพิ่มเติมตอนรันไทม์ซึ่งไม่เกิดขึ้นกับการดิสแพตช์แบบสแตติก นอกจากนี้ การดิสแพตช์แบบไดนามิกยังทำให้คอมไพเลอร์ไม่สามารถเลือกทำอินไลน์ (inline) โค้ดของเมธอดได้ ซึ่งส่งผลให้ไม่สามารถทำออปติไมเซชัน (optimization) บางอย่างได้ตามไปด้วย ทั้งนี้ Rust ยังมีกฎเกณฑ์ที่กำหนดว่าจุดใดบ้างที่สามารถหรือไม่สามารถใช้การดิสแพตช์แบบไดนามิกได้ ซึ่งเรียกว่า _ความเข้ากันได้ของ dyn_ (dyn compatibility) กฎเหล่านั้นอยู่นอกเหนือขอบเขตของเนื้อหาในส่วนนี้ แต่คุณสามารถอ่านเพิ่มเติมได้[ในเรเฟอเรนซ์][dyn-compatibility]<!-- ignore --> อย่างไรก็ดี เราได้รับความยืดหยุ่นเพิ่มขึ้นอย่างมากในโค้ดที่เราเขียนไว้ในลิสติ้ง 18-5 และลิสติ้ง 18-9 จึงถือเป็นข้อแลกเปลี่ยนที่คุณควรพิจารณาให้เหมาะสมกับการใช้งาน
