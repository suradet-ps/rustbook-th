## การใช้เทรตออบเจกต์เพื่อนามธรรมพฤติกรรมร่วม

ในบทที่ 8 เราได้กล่าวถึงข้อจำกัดประการหนึ่งของเวกเตอร์ (vector) นั่นคือมันเก็บสมาชิกได้เพียงชนิดเดียว เราสร้างวิธีเลี่ยงในลิสติ้ง 8-9 โดยนิยาม enum `SpreadsheetCell` ที่มีวาเรียนต์สำหรับเก็บจำนวนเต็ม จำนวนทศนิยม และข้อความ ซึ่งหมายความว่าเราเก็บข้อมูลต่างชนิดกันในแต่ละเซลล์ได้ และยังคงมีเวกเตอร์ที่แทนแถวของเซลล์ได้ นี่เป็นวิธีแก้ปัญหาที่ดีเยี่ยมเมื่อสมาชิกที่สับเปลี่ยนกันได้ของเราเป็นชุดชนิดข้อมูลคงที่ที่เรารู้ตอนที่โค้ดถูกคอมไพล์

อย่างไรก็ตาม บางครั้งเราต้องการให้ผู้ใช้ไลบรารีของเราสามารถขยายชุดชนิดข้อมูลที่ใช้ได้ในสถานการณ์หนึ่งๆ เพื่อแสดงว่าเราทำเช่นนี้ได้อย่างไร เราจะสร้างเครื่องมือส่วนต่อประสานผู้ใช้แบบกราฟิก (graphical user interface หรือ GUI) ตัวอย่างหนึ่งที่วนผ่านรายการของสมาชิก เรียกเมธอด `draw` บนแต่ละตัวเพื่อวาดมันลงบนหน้าจอ ซึ่งเป็นเทคนิคทั่วไปสำหรับเครื่องมือ GUI เราจะสร้างเครตไลบรารี (library crate) ชื่อ `gui` ที่บรรจุโครงสร้างของไลบรารี GUI เครตนี้มีชนิดข้อมูลบางอย่างให้ผู้คนใช้ เช่น `Button` หรือ `TextField` นอกจากนี้ ผู้ใช้ `gui` จะต้องการสร้างชนิดข้อมูลของตัวเองที่วาดได้: ตัวอย่างเช่น โปรแกรมเมอร์คนหนึ่งอาจเพิ่ม `Image` และอีกคนอาจเพิ่ม `SelectBox`

ในตอนที่เขียนไลบรารี เราไม่สามารถรู้และนิยามชนิดข้อมูลทั้งหมดที่โปรแกรมเมอร์คนอื่นอาจต้องการสร้างได้ แต่เรารู้ว่า `gui` จำเป็นต้องติดตามค่าจำนวนมากที่มีชนิดข้อมูลต่างกัน และจำเป็นต้องเรียกเมธอด `draw` บนค่าเหล่านี้ที่มีชนิดต่างกันแต่ละตัว มันไม่จำเป็นต้องรู้ว่าเกิดอะไรขึ้นเมื่อเราเรียกเมธอด `draw` อย่างแน่ชัด เพียงแค่ว่าค่านั้นจะมีเมธอดนั้นให้เราเรียกใช้

การทำเช่นนี้ในภาษาที่มีการสืบทอด เราอาจนิยามคลาสชื่อ `Component` ที่มีเมธอดชื่อ `draw` คลาสอื่นๆ เช่น `Button`, `Image` และ `SelectBox` จะสืบทอดจาก `Component` จึงได้เมธอด `draw` มา แต่ละคลาสเขียนทับเมธอด `draw` เพื่อนิยามพฤติกรรมกำหนดเองได้ แต่เฟรมเวิร์กก็ปฏิบัติต่อทุกชนิดข้อมูลเสมือนเป็นอินสแตนซ์ `Component` และเรียก `draw` บนพวกมันได้ แต่เนื่องจาก Rust ไม่มีการสืบทอด เราจึงต้องมีวิธีอื่นในการจัดโครงสร้างไลบรารี `gui` เพื่อให้ผู้ใช้สร้างชนิดข้อมูลใหม่ที่เข้ากันได้กับไลบรารีได้

### การนิยามเทรตสำหรับพฤติกรรมร่วม

เพื่ออิมพลีเมนต์พฤติกรรมที่เราต้องการให้ `gui` มี เราจะนิยามเทรตชื่อ `Draw` ที่มีเมธอดหนึ่งตัวชื่อ `draw` จากนั้นเรานิยามเวกเตอร์ที่รับเทรตออบเจกต์ได้ _เทรตออบเจกต์_ (trait object) ชี้ไปยังทั้งอินสแตนซ์ (instance) ของชนิดข้อมูลที่อิมพลีเมนต์เทรตที่เราระบุ และตารางที่ใช้ค้นหาเมธอดของเทรตบนชนิดข้อมูลนั้นตอนรันไทม์ เราสร้างเทรตออบเจกต์โดยระบุพอยน์เตอร์บางชนิด เช่น เรเฟอเรนซ์ (reference) หรือสมาร์ตพอยน์เตอร์ (smart pointer) `Box<T>` จากนั้นตามด้วยคำสงวน `dyn` แล้วระบุเทรตที่เกี่ยวข้อง (เราจะพูดถึงเหตุผลที่เทรตออบเจกต์ต้องใช้พอยน์เตอร์ใน[“ชนิดข้อมูลขนาดไม่คงที่และเทรต `Sized`”][dynamically-sized]<!-- ignore --> ในบทที่ 20) เราใช้เทรตออบเจกต์แทนชนิดเจเนอริก (generic) หรือชนิดที่เป็นรูปธรรมได้ ทุกที่ที่เราใช้เทรตออบเจกต์ ระบบชนิดข้อมูลของ Rust จะรับประกันตอนคอมไพล์ว่าค่าใดก็ตามที่ใช้ในบริบทนั้นจะอิมพลีเมนต์เทรตของเทรตออบเจกต์นั้น ดังนั้น เราจึงไม่จำเป็นต้องรู้ชนิดข้อมูลที่เป็นไปได้ทั้งหมดตอนคอมไพล์

เราได้กล่าวไว้ว่าใน Rust เราหลีกเลี่ยงการเรียก struct และ enum ว่า “ออบเจกต์” เพื่อแยกความแตกต่างจากออบเจกต์ในภาษาอื่น ใน struct หรือ enum ข้อมูลในฟิลด์ของ struct และพฤติกรรมในบล็อก `impl` แยกออกจากกัน ในขณะที่ในภาษาอื่น ข้อมูลและพฤติกรรมที่รวมกันเป็นแนวคิดเดียวมักถูกเรียกว่าออบเจกต์ เทรตออบเจกต์แตกต่างจากออบเจกต์ในภาษาอื่นตรงที่เราเพิ่มข้อมูลเข้าไปในเทรตออบเจกต์ไม่ได้ เทรตออบเจกต์มีประโยชน์โดยทั่วไปไม่เท่าออบเจกต์ในภาษาอื่น: จุดประสงค์เฉพาะของมันคือเพื่อนามธรรมเหนือพฤติกรรมร่วม

แนวคิดนี้—การสนใจเพียงข้อความที่ค่าหนึ่งตอบสนอง แทนที่จะสนใจชนิดที่เป็นรูปธรรมของค่า—คล้ายกับแนวคิด_ดักไทปิง_ (duck typing) ในภาษาที่มีชนิดข้อมูลแบบไดนามิก: หากมันเดินเหมือนเป็ดและร้องก้าบเหมือนเป็ด มันก็ต้องเป็นเป็ด! ในการอิมพลีเมนต์ `run` บน `Screen` ในลิสติ้ง 18-5 `run` ไม่จำเป็นต้องรู้ว่าชนิดที่เป็นรูปธรรมของแต่ละคอมโพเนนต์คืออะไร มันไม่ตรวจสอบว่าคอมโพเนนต์เป็นอินสแตนซ์ของ `Button` หรือ `SelectBox` มันเพียงเรียกเมธอด `draw` บนคอมโพเนนต์เท่านั้น ด้วยการระบุ `Box<dyn Draw>` เป็นชนิดของค่าในเวกเตอร์ `components` เราได้นิยาม `Screen` ว่าต้องการค่าที่เราเรียกเมธอด `draw` บนมันได้

ข้อดีของการใช้เทรตออบเจกต์และระบบชนิดข้อมูลของ Rust เพื่อเขียนโค้ดคล้ายกับโค้ดที่ใช้ดักไทปิงคือ เราไม่ต้องตรวจสอบว่าค่าหนึ่งอิมพลีเมนต์เมธอดหนึ่งๆ ตอนรันไทม์หรือไม่ และไม่ต้องกังวลว่าจะเกิดข้อผิดพลาดหากค่าไม่ได้อิมพลีเมนต์เมธอดนั้นแต่เรากลับเรียกมัน Rust จะไม่คอมไพล์โค้ดของเราหากค่าเหล่านั้นไม่ได้อิมพลีเมนต์เทรตที่เทรตออบเจกต์ต้องการ

### การดิสแพตช์แบบไดนามิก

ย้อนนึกถึง[“ประสิทธิภาพของโค้ดที่ใช้เจเนอริก”][performance-of-code-using-generics]<!-- ignore --> ในบทที่ 10 ที่เราพูดคุยถึงกระบวนการมอโนมอร์ไฟเซชันที่คอมไพเลอร์ทำกับเจเนอริก: คอมไพเลอร์สร้างการอิมพลีเมนต์ฟังก์ชันและเมธอดแบบไม่ใช้เจเนอริกสำหรับชนิดที่เป็นรูปธรรมแต่ละชนิดที่เราใช้แทนพารามิเตอร์ชนิดข้อมูลแบบเจเนอริก โค้ดที่เป็นผลลัพธ์จากการมอโนมอร์ไฟเซชันทำ_การดิสแพตช์แบบสแตติก_ (static dispatch) ซึ่งคือกรณีที่คอมไพเลอร์รู้ว่าคุณกำลังเรียกเมธอดใดตอนคอมไพล์ สิ่งนี้ตรงข้ามกับ_การดิสแพตช์แบบไดนามิก_ (dynamic dispatch) ซึ่งคือกรณีที่คอมไพเลอร์บอกไม่ได้ตอนคอมไพล์ว่าคุณกำลังเรียกเมธอดใด ในกรณีการดิสแพตช์แบบไดนามิก คอมไพเลอร์สร้างโค้ดที่จะรู้ตอนรันไทม์ว่าต้องเรียกเมธอดใด

เมื่อเราใช้เทรตออบเจกต์ Rust ต้องใช้การดิสแพตช์แบบไดนามิก คอมไพเลอร์ไม่รู้ชนิดข้อมูลทั้งหมดที่อาจถูกใช้กับโค้ดที่ใช้เทรตออบเจกต์ จึงไม่รู้ว่าจะเรียกเมธอดใดที่อิมพลีเมนต์บนชนิดใด แต่ตอนรันไทม์ Rust ใช้พอยน์เตอร์ภายในเทรตออบเจกต์เพื่อรู้ว่าต้องเรียกเมธอดใด การค้นหานี้มีค่าใช้จ่ายตอนรันไทม์ซึ่งไม่เกิดขึ้นกับการดิสแพตช์แบบสแตติก การดิสแพตช์แบบไดนามิกยังป้องกันไม่ให้คอมไพเลอร์เลือกอินไลน์โค้ดของเมธอด ซึ่งก็นำไปสู่การป้องกันการปรับให้เหมาะที่สุด (optimization) บางอย่าง และ Rust มีกฎบางข้อเกี่ยวกับตำแหน่งที่คุณใช้และไม่ใช้การดิสแพตช์แบบไดนามิกได้ เรียกว่า _ความเข้ากันได้ของ dyn_ (dyn compatibility) กฎเหล่านั้นอยู่นอกขอบเขตของการอภิปรายนี้ แต่คุณอ่านเพิ่มเติมเกี่ยวกับมันได้[ในเรเฟอเรนซ์][dyn-compatibility]<!-- ignore --> อย่างไรก็ตาม เราก็ได้ความยืดหยุ่นเพิ่มเติมในโค้ดที่เราเขียนในลิสติ้ง 18-5 และรองรับได้ในลิสติ้ง 18-9 ดังนั้นจึงเป็นข้อแลกเปลี่ยนที่ต้องพิจารณา
