## `RefCell<T>` และแพตเทิร์นการเปลี่ยนแปลงค่าภายใน

_การเปลี่ยนแปลงค่าภายใน_ (interior mutability) เป็นดีไซน์แพตเทิร์นใน Rust ที่ให้คุณเปลี่ยนแปลงข้อมูลได้แม้จะมีเรเฟอเรนซ์ (reference) แบบเปลี่ยนแปลงไม่ได้ไปยังข้อมูลนั้น โดยปกติ การกระทำนี้ถูกห้ามโดยกฎการยืม ในการเปลี่ยนแปลงข้อมูล แพตเทิร์นนี้ใช้โค้ด `unsafe` ภายในโครงสร้างข้อมูลเพื่อผ่อนปรนกฎตามปกติของ Rust ที่ควบคุมการเปลี่ยนแปลงและการยืม โค้ด unsafe บ่งบอกต่อคอมไพเลอร์ว่าเรากำลังตรวจสอบกฎด้วยตนเองแทนที่จะพึ่งพาให้คอมไพเลอร์ตรวจสอบให้เรา เราจะพูดคุยถึงโค้ด unsafe มากขึ้นในบทที่ 20

เราใช้ชนิดข้อมูลที่ใช้แพตเทิร์นการเปลี่ยนแปลงค่าภายในได้เฉพาะเมื่อเรามั่นใจได้ว่ากฎการยืมจะถูกปฏิบัติตามตอนรันไทม์ แม้ว่าคอมไพเลอร์จะรับประกันสิ่งนั้นไม่ได้ก็ตาม โค้ด `unsafe` ที่เกี่ยวข้องจะถูกห่อไว้ใน API ที่ปลอดภัย และชนิดข้อมูลชั้นนอกก็ยังคงเปลี่ยนแปลงไม่ได้

มาสำรวจแนวคิดนี้โดยดูที่ชนิด `RefCell<T>` ซึ่งทำตามแพตเทิร์นการเปลี่ยนแปลงค่าภายใน

<a id="enforcing-borrowing-rules-at-runtime-with-refcellt"></a>

### การบังคับใช้กฎการยืมตอนรันไทม์

ต่างจาก `Rc<T>` ชนิด `RefCell<T>` แสดงถึงความเป็นเจ้าของแบบเดี่ยวเหนือข้อมูลที่มันถืออยู่ แล้วอะไรทำให้ `RefCell<T>` แตกต่างจากชนิดอย่าง `Box<T>`? ย้อนนึกถึงกฎการยืมที่คุณเรียนรู้ในบทที่ 4:

- ในเวลาใดเวลาหนึ่ง คุณสามารถมีเรเฟอเรนซ์แบบเปลี่ยนแปลงได้หนึ่งตัว _หรือ_ เรเฟอเรนซ์แบบเปลี่ยนแปลงไม่ได้จำนวนเท่าใดก็ได้ (แต่ไม่ใช่ทั้งสองอย่างพร้อมกัน)
- เรเฟอเรนซ์ต้องใช้ได้เสมอ

กับเรเฟอเรนซ์และ `Box<T>` เงื่อนไขคงที่ (invariant) ของกฎการยืมถูกบังคับใช้ตอนคอมไพล์ กับ `RefCell<T>` เงื่อนไขคงที่เหล่านี้ถูกบังคับใช้_ตอนรันไทม์_ กับเรเฟอเรนซ์ หากคุณละเมิดกฎเหล่านี้ คุณจะได้ข้อผิดพลาดจากคอมไพเลอร์ กับ `RefCell<T>` หากคุณละเมิดกฎเหล่านี้ โปรแกรมของคุณจะแพนิก (panic) และออกจากการทำงาน

ข้อดีของการตรวจสอบกฎการยืมตอนคอมไพล์คือข้อผิดพลาดจะถูกจับได้เร็วขึ้นในกระบวนการพัฒนา และไม่มีผลกระทบต่อประสิทธิภาพตอนรันไทม์เพราะการวิเคราะห์ทั้งหมดเสร็จสิ้นล่วงหน้า ด้วยเหตุผลเหล่านั้น การตรวจสอบกฎการยืมตอนคอมไพล์จึงเป็นทางเลือกที่ดีที่สุดในกรณีส่วนใหญ่ ซึ่งเป็นเหตุผลว่าทำไมสิ่งนี้จึงเป็นค่าเริ่มต้นของ Rust

ข้อดีของการตรวจสอบกฎการยืมตอนรันไทม์แทนคือ สถานการณ์ที่ปลอดภัยต่อหน่วยความจำบางสถานการณ์จะได้รับอนุญาต ทั้งที่การตรวจสอบตอนคอมไพล์จะห้ามไว้ การวิเคราะห์แบบสแตติก (static analysis) อย่างคอมไพเลอร์ Rust นั้นอนุรักษนิยมโดยเนื้อแท้ คุณสมบัติบางอย่างของโค้ดเป็นไปไม่ได้ที่จะตรวจจับได้ด้วยการวิเคราะห์โค้ด ตัวอย่างที่โด่งดังที่สุดคือปัญหาการหยุด (Halting Problem) ซึ่งอยู่นอกขอบเขตของหนังสือเล่มนี้แต่เป็นหัวข้อที่น่าสนใจศึกษาค้นคว้า

เนื่องจากการวิเคราะห์บางอย่างเป็นไปไม่ได้ หากคอมไพเลอร์ Rust ไม่มั่นใจว่าโค้ดเป็นไปตามกฎความเป็นเจ้าของ มันอาจปฏิเสธโปรแกรมที่ถูกต้องได้ ในแง่นี้ มันจึงอนุรักษนิยม หาก Rust ยอมรับโปรแกรมที่ไม่ถูกต้อง ผู้ใช้ก็จะไม่สามารถไว้วางใจการรับประกันที่ Rust ให้ได้ อย่างไรก็ตาม หาก Rust ปฏิเสธโปรแกรมที่ถูกต้อง นักเขียนโปรแกรมจะได้รับความไม่สะดวก แต่ก็ไม่มีอะไรเลวร้ายเกิดขึ้นได้ ชนิด `RefCell<T>` มีประโยชน์เมื่อคุณมั่นใจว่าโค้ดของคุณเป็นไปตามกฎการยืมแต่คอมไพเลอร์ไม่สามารถเข้าใจและรับประกันสิ่งนั้นได้

เช่นเดียวกับ `Rc<T>` `RefCell<T>` ใช้ได้เฉพาะในสถานการณ์แบบเธรดเดียว (single-threaded) และจะให้ข้อผิดพลาดตอนคอมไพล์หากคุณพยายามใช้มันในบริบทแบบหลายเธรด เราจะพูดคุยถึงวิธีทำให้ได้ฟังก์ชันการทำงานของ `RefCell<T>` ในโปรแกรมแบบหลายเธรดในบทที่ 16

นี่คือสรุปเหตุผลในการเลือก `Box<T>`, `Rc<T>` หรือ `RefCell<T>`:

- `Rc<T>` ทำให้ข้อมูลเดียวกันมีเจ้าของหลายราย ส่วน `Box<T>` และ `RefCell<T>` มีเจ้าของรายเดียว
- `Box<T>` ยอมให้มีการยืมแบบเปลี่ยนแปลงไม่ได้หรือเปลี่ยนแปลงได้ที่ตรวจสอบตอนคอมไพล์ `Rc<T>` ยอมให้เฉพาะการยืมแบบเปลี่ยนแปลงไม่ได้ที่ตรวจสอบตอนคอมไพล์ `RefCell<T>` ยอมให้มีการยืมแบบเปลี่ยนแปลงไม่ได้หรือเปลี่ยนแปลงได้ที่ตรวจสอบตอนรันไทม์
- เพราะ `RefCell<T>` ยอมให้มีการยืมแบบเปลี่ยนแปลงได้ที่ตรวจสอบตอนรันไทม์ คุณจึงเปลี่ยนแปลงค่าภายใน `RefCell<T>` ได้แม้ `RefCell<T>` จะเป็นค่าที่เปลี่ยนแปลงไม่ได้

การเปลี่ยนแปลงค่าภายในค่าที่เปลี่ยนแปลงไม่ได้คือแพตเทิร์นการเปลี่ยนแปลงค่าภายใน มาดูสถานการณ์ที่การเปลี่ยนแปลงค่าภายในมีประโยชน์และพิจารณาว่ามันเป็นไปได้อย่างไร

<a id="a-use-case-for-interior-mutability-mock-objects"></a>

#### การทดสอบด้วยม็อกออบเจกต์

บางครั้งในระหว่างการทดสอบ นักเขียนโปรแกรมจะใช้ชนิดข้อมูลหนึ่งแทนอีกชนิดหนึ่ง เพื่อสังเกตพฤติกรรมเฉพาะและยืนยันว่ามันถูกอิมพลีเมนต์อย่างถูกต้อง ชนิดข้อมูลที่ใช้แทนนี้เรียกว่า_ตัวแทนทดสอบ_ (test double) ลองนึกถึงความหมายของตัวแสดงแทนในภาพยนตร์ ซึ่งมีคนหนึ่งเข้ามาแทนนักแสดงเพื่อเล่นฉากที่ยุ่งยากเป็นพิเศษ ตัวแทนทดสอบใช้แทนชนิดข้อมูลอื่นเมื่อเรารันการทดสอบ_ม็อกออบเจกต์_ (mock object) เป็นตัวแทนทดสอบชนิดเฉพาะที่บันทึกสิ่งที่เกิดขึ้นระหว่างการทดสอบ เพื่อให้คุณยืนยันได้ว่าการกระทำที่ถูกต้องได้เกิดขึ้น

Rust ไม่มีออบเจกต์ในความหมายเดียวกับที่ภาษาอื่นมีออบเจกต์ และ Rust ไม่มีฟังก์ชันการทำงานของม็อกออบเจกต์ที่สร้างไว้ในไลบรารีมาตรฐานเหมือนที่บางภาษามี อย่างไรก็ตาม คุณสามารถสร้าง struct ที่ทำหน้าที่เดียวกันกับม็อกออบเจกต์ได้แน่นอน

นี่คือสถานการณ์ที่เราจะทดสอบ: เราจะสร้างไลบรารีที่ติดตามค่าหนึ่งเทียบกับค่าสูงสุด และส่งข้อความตามว่าค่าปัจจุบันใกล้ค่าสูงสุดเพียงใด ตัวอย่างเช่น ไลบรารีนี้ใช้ติดตามโควตาของผู้ใช้สำหรับจำนวนการเรียก API ที่พวกเขาได้รับอนุญาตให้ทำได้

ไลบรารีของเราจะให้เฉพาะฟังก์ชันการทำงานในการติดตามว่าค่าหนึ่งใกล้ค่าสูงสุดเพียงใดและข้อความควรเป็นอะไรเมื่อใด แอปพลิเคชันที่ใช้ไลบรารีของเราจะต้องจัดเตรียมกลไกในการส่งข้อความ: แอปพลิเคชันอาจแสดงข้อความให้ผู้ใช้เห็นโดยตรง ส่งอีเมล ส่งข้อความตัวอักษร หรือทำอย่างอื่น ไลบรารีไม่จำเป็นต้องรู้รายละเอียดนั้น สิ่งที่มันต้องการคือบางสิ่งที่อิมพลีเมนต์เทรต (trait) ที่เราจะให้ไว้ ชื่อ `Messenger` ลิสติ้ง 15-20 แสดงโค้ดของไลบรารี

ในเทสต์ เรากำลังทดสอบว่าเกิดอะไรขึ้นเมื่อ `LimitTracker` ถูกสั่งให้ตั้ง `value` เป็นค่าที่มากกว่าร้อยละ 75 ของค่า `max` ก่อนอื่น เราสร้าง `MockMessenger` ใหม่ ซึ่งจะเริ่มต้นด้วยลิสต์ข้อความว่างเปล่า จากนั้น เราสร้าง `LimitTracker` ใหม่และให้เรเฟอเรนซ์ไปยัง `MockMessenger` ใหม่และค่า `max` เป็น `100` เราเรียกเมธอด `set_value` บน `LimitTracker` ด้วยค่า `80` ซึ่งมากกว่าร้อยละ 75 ของ 100 จากนั้น เราแอสเซอร์ตว่าลิสต์ข้อความที่ `MockMessenger` กำลังติดตามอยู่ควรมีข้อความหนึ่งข้อความอยู่ในนั้นแล้ว

#### การติดตามการยืมตอนรันไทม์

เมื่อสร้างเรเฟอเรนซ์แบบเปลี่ยนแปลงไม่ได้และแบบเปลี่ยนแปลงได้ เราใช้วากยสัมพันธ์ `&` และ `&mut` ตามลำดับ กับ `RefCell<T>` เราใช้เมธอด `borrow` และ `borrow_mut` ซึ่งเป็นส่วนหนึ่งของ API ที่ปลอดภัยซึ่งเป็นของ `RefCell<T>` เมธอด `borrow` คืนค่าชนิดสมาร์ตพอยน์เตอร์ (smart pointer) `Ref<T>` และ `borrow_mut` คืนค่าชนิดสมาร์ตพอยน์เตอร์ `RefMut<T>` ทั้งสองชนิดอิมพลีเมนต์ `Deref` เราจึงปฏิบัติกับมันเหมือนเรเฟอเรนซ์ทั่วไปได้

`RefCell<T>` คอยติดตามว่ามีสมาร์ตพอยน์เตอร์ `Ref<T>` และ `RefMut<T>` ทำงานอยู่กี่ตัวในขณะนั้น ทุกครั้งที่เราเรียก `borrow` `RefCell<T>` จะเพิ่มจำนวนการยืมแบบเปลี่ยนแปลงไม่ได้ที่ทำงานอยู่ เมื่อค่า `Ref<T>` ออกจากสโคป จำนวนการยืมแบบเปลี่ยนแปลงไม่ได้จะลดลง 1 เช่นเดียวกับกฎการยืมตอนคอมไพล์ `RefCell<T>` ยอมให้เรามีการยืมแบบเปลี่ยนแปลงไม่ได้หลายครั้งหรือการยืมแบบเปลี่ยนแปลงได้หนึ่งครั้ง ณ จุดใดจุดหนึ่งของเวลา

หากเราพยายามละเมิดกฎเหล่านี้ แทนที่จะได้ข้อผิดพลาดจากคอมไพเลอร์เหมือนที่เราจะได้กับเรเฟอเรนซ์ การอิมพลีเมนต์ของ `RefCell<T>` จะแพนิกตอนรันไทม์ ลิสติ้ง 15-23 แสดงการแก้ไขการอิมพลีเมนต์ของ `send` ในลิสติ้ง 15-22 เราจงใจพยายามสร้างการยืมแบบเปลี่ยนแปลงได้สองรายการที่ทำงานอยู่พร้อมกันในสโคปเดียวกันเพื่อแสดงให้เห็นว่า `RefCell<T>` ป้องกันไม่ให้เราทำเช่นนั้นตอนรันไทม์

### การอนุญาตเจ้าของหลายรายของข้อมูลที่เปลี่ยนแปลงได้

วิธีที่ใช้ `RefCell<T>` บ่อยครั้งคือใช้ร่วมกับ `Rc<T>` ย้อนนึกว่า `Rc<T>` ทำให้คุณมีเจ้าของหลายรายของข้อมูลบางอย่างได้ แต่ให้เพียงการเข้าถึงข้อมูลนั้นแบบเปลี่ยนแปลงไม่ได้เท่านั้น หากคุณมี `Rc<T>` ที่ถือ `RefCell<T>` คุณจะได้ค่าที่มีเจ้าของหลายราย_และ_เปลี่ยนแปลงมันได้!

ตัวอย่างเช่น ย้อนนึกถึงตัวอย่าง cons list ในลิสติ้ง 15-18 ที่เราใช้ `Rc<T>` เพื่อให้หลายลิสต์แชร์ความเป็นเจ้าของลิสต์อีกลิสต์หนึ่งได้ เพราะ `Rc<T>` ถือเพียงค่าที่เปลี่ยนแปลงไม่ได้ เราจึงเปลี่ยนค่าใดๆ ในลิสต์ไม่ได้เมื่อเราสร้างมันขึ้นมาแล้ว มาเพิ่ม `RefCell<T>` เข้าไปเพื่อความสามารถในการเปลี่ยนค่าในลิสต์กัน ลิสติ้ง 15-24 แสดงว่าโดยการใช้ `RefCell<T>` ในนิยาม `Cons` เราสามารถแก้ไขค่าที่เก็บอยู่ในลิสต์ทั้งหมดได้
