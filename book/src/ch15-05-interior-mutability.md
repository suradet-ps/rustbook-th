## `RefCell<T>` และแพตเทิร์นการเปลี่ยนแปลงค่าภายใน

_ความสามารถในการเปลี่ยนแปลงค่าภายใน (interior mutability)_ เป็นรูปแบบการออกแบบ (design pattern) ใน Rust ที่ช่วยให้คุณสามารถแก้ไขข้อมูลได้ แม้ว่าจะมีเรเฟอเรนซ์แบบแก้ไขไม่ได้ (immutable references) ชี้ไปยังข้อมูลนั้นอยู่ก็ตาม ซึ่งตามปกติแล้วการกระทำเช่นนี้จะถูกห้ามโดยกฎการยืม ในการแก้ไขข้อมูล รูปแบบนี้จะใช้โค้ด `unsafe` ภายในโครงสร้างข้อมูลเพื่อผ่อนปรนกฎเกณฑ์ตามปกติของ Rust ที่ควบคุมการแก้ไขข้อมูลและการยืม โค้ด unsafe จะเป็นการส่งสัญญาณบอกคอมไพเลอร์ว่าเรากำลังตรวจสอบกฎเกณฑ์ต่าง ๆ ด้วยตนเอง แทนที่จะพึ่งพาให้คอมไพเลอร์ตรวจสอบให้เรา โดยเราจะพูดถึงโค้ด unsafe กันอย่างละเอียดมากขึ้นในบทที่ 20

เราสามารถเลือกใช้ชนิดข้อมูลที่ใช้รูปแบบการเปลี่ยนแปลงค่าภายในได้ ก็ต่อเมื่อเรามั่นใจได้ว่ากฎการยืมจะได้รับการปฏิบัติตามอย่างถูกต้องในขณะรันไทม์ แม้ว่าคอมไพเลอร์จะไม่สามารถรับประกันสิ่งนั้นในขณะคอมไพล์ได้ก็ตาม โดยโค้ด `unsafe` ที่เกี่ยวข้องจะถูกห่อหุ้มไว้ภายใน API ที่ปลอดภัย ทำให้ชนิดข้อมูลภายนอกยังคงมีสถานะเป็นชนิดข้อมูลที่แก้ไขไม่ได้ตามปกติ

เรามาลองสำรวจแนวคิดนี้ผ่านชนิดข้อมูล `RefCell<T>` ซึ่งนำรูปแบบการเปลี่ยนแปลงค่าภายในมาใช้งานกัน

<a id="enforcing-borrowing-rules-at-runtime-with-refcellt"></a>

### การบังคับใช้กฎการยืมตอนรันไทม์

สิ่งที่ต่างจาก `Rc<T>` คือ ชนิดข้อมูล `RefCell<T>` แสดงถึงความเป็นเจ้าของเพียงรายเดียว (single ownership) เหนือข้อมูลที่มันถืออยู่ แล้วอะไรที่ทำให้ `RefCell<T>` แตกต่างจากชนิดข้อมูลอย่าง `Box<T>`? ลองนึกย้อนกลับไปถึงกฎการยืมที่คุณได้เรียนรู้ในบทที่ 4:

- ในเวลาใดเวลาหนึ่ง คุณสามารถมีเรเฟอเรนซ์แบบแก้ไขได้เพียงหนึ่งตัว _หรือ_ เรเฟอเรนซ์แบบแก้ไขไม่ได้กี่ตัวก็ได้ (แต่ต้องไม่ใช่ทั้งสองแบบพร้อมกัน)
- เรเฟอเรนซ์ต้องถูกต้องและชี้ไปยังข้อมูลที่ยังมีอยู่เสมอ (valid)

สำหรับเรเฟอเรนซ์ทั่วไปและ `Box<T>` เงื่อนไขคงที่ (invariants) ของกฎการยืมจะถูกบังคับใช้ตั้งแต่ตอนคอมไพล์ แต่สำหรับ `RefCell<T>` เงื่อนไขเหล่านี้จะถูกตรวจสอบและบังคับใช้_ในขณะรันไทม์_ หากคุณละเมิดกฎเหล่านี้เมื่อใช้เรเฟอเรนซ์ทั่วไป คุณจะได้รับข้อผิดพลาดจากคอมไพเลอร์ แต่หากคุณละเมิดกฎเหล่านี้เมื่อใช้ `RefCell<T>` โปรแกรมของคุณจะแพนิก (`panic!`) และยุติการทำงานลงทันที

ข้อดีของการตรวจสอบกฎการยืมในขั้นตอนคอมไพล์คือ ข้อผิดพลาดจะถูกตรวจพบได้อย่างรวดเร็วตั้งแต่ในกระบวนการพัฒนา และไม่มีต้นทุนสูญเปล่าด้านประสิทธิภาพในขณะรันไทม์ เพราะการวิเคราะห์ทั้งหมดได้เสร็จสิ้นล่วงหน้าไปแล้ว ด้วยเหตุผลเหล่านี้ การตรวจสอบกฎการยืมตอนคอมไพล์จึงเป็นทางเลือกที่ดีที่สุดในกรณีส่วนใหญ่ และเป็นเหตุผลว่าทำไม Rust จึงกำหนดให้สิ่งนี้เป็นพฤติกรรมเริ่มต้น

ส่วนข้อดีของการตรวจสอบกฎการยืมในขณะรันไทม์ก็คือ มันจะเปิดโอกาสให้สามารถทำบางสิ่งที่ปลอดภัยต่อหน่วยความจำได้ ซึ่งหากเป็นการตรวจสอบในขณะคอมไพล์อาจจะไม่อนุญาต เนื่องจากการวิเคราะห์โค้ดแบบสถิต (static analysis) เช่นเดียวกับที่คอมไพเลอร์ของ Rust ทำนั้น โดยเนื้อแท้แล้วจำเป็นต้องระมัดระวังเป็นพิเศษ (conservative) เพราะมีคุณสมบัติบางประการของโค้ดที่ไม่สามารถตรวจจับได้ผ่านการวิเคราะห์โค้ด ตัวอย่างที่โด่งดังที่สุดคือปัญหาการยุติการทำงาน (Halting Problem) ซึ่งอยู่นอกเหนือขอบเขตของหนังสือเล่มนี้ แต่นับเป็นหัวข้อที่น่าสนใจอย่างยิ่ง

เนื่องจากการวิเคราะห์บางอย่างเป็นไปไม่ได้ในทางทฤษฎี หากคอมไพเลอร์ของ Rust ไม่มั่นใจว่าโค้ดนั้นปฏิบัติตามกฎความเป็นเจ้าของอย่างสมบูรณ์ มันก็อาจจะปฏิเสธโปรแกรมที่เขียนมาอย่างถูกต้องได้ ซึ่งในแง่นี้ถือว่าคอมไพเลอร์เลือกที่จะปลอดภัยไว้ก่อน เพราะหาก Rust ยอมรับโปรแกรมที่มีข้อผิดพลาด ผู้ใช้ก็จะไม่สามารถเชื่อถือการรับประกันความปลอดภัยของ Rust ได้อีกต่อไป ทว่าหาก Rust ปฏิเสธโปรแกรมที่ทำงานถูกต้อง แม้นักพัฒนาจะรู้สึกไม่สะดวกสบาย แต่ก็ไม่มีความเสียหายร้ายแรงใด ๆ เกิดขึ้นกับระบบ ชนิดข้อมูล `RefCell<T>` จึงมีประโยชน์อย่างยิ่งเมื่อคุณมั่นใจว่าโค้ดของคุณปฏิบัติตามกฎการยืมอย่างแน่นอน แต่คอมไพเลอร์ไม่ฉลาดพอที่จะเข้าใจและรับประกันสิ่งนั้นให้คุณได้

เช่นเดียวกับ `Rc<T>` ชนิดข้อมูล `RefCell<T>` มีไว้สำหรับใช้งานในบริบทแบบเธรดเดียว (single-threaded) เท่านั้น และจะเกิดข้อผิดพลาดในการคอมไพล์ทันทีหากคุณพยายามนำมันไปใช้ในงานแบบหลายเธรด โดยเราจะพูดถึงวิธีการนำความสามารถของ `RefCell<T>` ไปใช้ในโปรแกรมแบบหลายเธรดในบทที่ 16

นี่คือข้อสรุปในการเลือกระหว่าง `Box<T>`, `Rc<T>` หรือ `RefCell<T>`:

- `Rc<T>` เปิดให้ข้อมูลเดียวกันมีเจ้าของได้หลายราย ส่วน `Box<T>` และ `RefCell<T>` มีเจ้าของได้เพียงรายเดียว
- `Box<T>` อนุญาตให้มีการยืมแบบแก้ไขไม่ได้หรือแก้ไขได้ โดยตรวจสอบในขั้นตอนคอมไพล์ ส่วน `Rc<T>` อนุญาตเฉพาะการยืมแบบแก้ไขไม่ได้ที่ตรวจสอบตอนคอมไพล์ และ `RefCell<T>` อนุญาตให้มีการยืมแบบแก้ไขไม่ได้หรือแก้ไขได้ โดยตรวจสอบในขณะรันไทม์
- เนื่องจาก `RefCell<T>` อนุญาตให้มีการยืมแบบแก้ไขได้ที่ตรวจสอบในขณะรันไทม์ คุณจึงสามารถแก้ไขค่าที่อยู่ภายใน `RefCell<T>` ได้ แม้ว่าตัวแปร `RefCell<T>` นั้นจะมีสถานะเป็นค่าที่แก้ไขไม่ได้ก็ตาม

การแก้ไขค่าที่อยู่ภายในค่าที่ไม่สามารถแก้ไขได้นี้ก็คือ รูปแบบความสามารถในการเปลี่ยนแปลงค่าภายใน (interior mutability pattern) เรามาดูสถานการณ์ที่รูปแบบนี้มีประโยชน์และศึกษาว่ามันทำงานได้อย่างไร

#### การทดสอบด้วยม็อกออบเจกต์

บางครั้งในระหว่างการทดสอบ นักพัฒนามักจะใช้ชนิดข้อมูลจำลองขึ้นมาแทนที่ชนิดข้อมูลจริง เพื่อคอยสังเกตพฤติกรรมเฉพาะเจาะจงและตรวจสอบยืนยันว่าโค้ดได้รับการอิมพลีเมนต์อย่างถูกต้อง ชนิดข้อมูลตัวแทนนี้เรียกว่า _ตัวแทนทดสอบ (test double)_ เปรียบได้กับตัวแสดงแทน (stunt double) ในการถ่ายทำภาพยนตร์ ที่จะมีคนเข้ามาแสดงแทนดารานำในฉากที่ยากหรืออันตรายเป็นพิเศษ ตัวแทนทดสอบจะทำหน้าที่เป็นตัวแสดงแทนให้กับชนิดข้อมูลอื่น ๆ เมื่อเรารันการทดสอบ โดย _ม็อกออบเจกต์ (mock object)_ เป็นชนิดหนึ่งของตัวแทนทดสอบที่คอยบันทึกสิ่งที่เกิดขึ้นระหว่างการทดสอบ เพื่อให้คุณสามารถตรวจสอบยืนยันได้ว่าการทำงานต่าง ๆ เกิดขึ้นอย่างถูกต้องตรงตามที่คาดหมาย

Rust ไม่ได้มีแนวคิดของออบเจกต์ในความหมายเดียวกับที่ภาษาอื่นมี และ Rust ก็ไม่มีฟังก์ชันการทำงานของม็อกออบเจกต์สำเร็จรูปมาให้ในไลบรารีมาตรฐานเหมือนกับบางภาษา อย่างไรก็ตาม คุณสามารถสร้าง struct ขึ้นมาทำหน้าที่เช่นเดียวกับม็อกออบเจกต์ได้อย่างแน่นอน

นี่คือสถานการณ์จำลองที่เราจะใช้ทดสอบ: เราจะสร้างไลบรารีสำหรับติดตามค่าตัวเลขหนึ่งเปรียบเทียบกับค่าสูงสุด และส่งข้อความแจ้งเตือนตามระดับความใกล้ของค่าปัจจุบันเทียบกับค่าสูงสุด ตัวอย่างเช่น ไลบรารีนี้อาจนำไปใช้ติดตามโควตาการเรียกใช้งาน API ของผู้ใช้ที่ได้รับอนุญาต

ไลบรารีของเราจะทำหน้าที่เฉพาะการติดตามดูว่าค่าตัวเลขใกล้ถึงค่าสูงสุดเพียงใด และควรส่งข้อความอะไรในเวลาใด โดยแอปพลิเคชันที่นำไลบรารีของเราไปใช้จะต้องเป็นผู้จัดเตรียมกลไกในการส่งข้อความจริงเอง เช่น แอปพลิเคชันอาจแสดงข้อความบนหน้าจอ, ส่งอีเมล, ส่งข้อความ SMS หรืออื่น ๆ โดยที่ไลบรารีไม่จำเป็นต้องรับรู้รายละเอียดเหล่านั้น สิ่งที่ไลบรารีต้องการมีเพียงแค่บางสิ่งที่อิมพลีเมนต์เทรตที่เราเตรียมไว้ให้ ซึ่งมีชื่อว่า `Messenger` โดยลิสติ้ง 15-20 แสดงโค้ดของไลบรารีนี้

เราจึงต้องการม็อกออบเจกต์ที่เมื่อถูกเรียกใช้เมธอด `send` แทนที่จะส่งอีเมลหรือข้อความ SMS จริง ๆ มันจะทำเพียงแค่คอยบันทึกข้อความที่ได้รับคำสั่งให้ส่งเอาไว้ เราสามารถสร้างอินสแตนซ์ใหม่ของม็อกออบเจกต์, สร้าง `LimitTracker` ที่เรียกใช้ม็อกออบเจกต์นั้น, เรียกเมธอด `set_value` บน `LimitTracker` แล้วจึงตรวจสอบว่าม็อกออบเจกต์มีข้อความบันทึกไว้ตรงตามที่เราคาดหวังหรือไม่ ลิสติ้ง 15-21 แสดงความพยายามในการสร้างม็อกออบเจกต์ดังกล่าว แต่ตัวตรวจสอบการยืมของ Rust จะไม่อนุญาตให้โค้ดนี้ผ่านได้

#### การติดตามการยืมตอนรันไทม์

เมื่อเราต้องการสร้างเรเฟอเรนซ์แบบแก้ไขไม่ได้และแบบแก้ไขได้ เราจะใช้ไวยากรณ์ `&` และ `&mut` ตามลำดับ แต่สำหรับ `RefCell<T>` เราจะใช้เมธอด `borrow` และ `borrow_mut` ซึ่งเป็นส่วนหนึ่งของ API ที่ปลอดภัยของ `RefCell<T>` โดยเมธอด `borrow` จะส่งคืนสมาร์ตพอยน์เตอร์ชนิด `Ref<T>` และ `borrow_mut` จะส่งคืนสมาร์ตพอยน์เตอร์ชนิด `RefMut<T>` ซึ่งทั้งสองชนิดต่างอิมพลีเมนต์เทรต `Deref` จึงทำให้เราสามารถปฏิบัติต่อพวกมันได้เสมือนเป็นเรเฟอเรนซ์ทั่วไป

ตัว `RefCell<T>` จะคอยติดตามอยู่ตลอดเวลาว่ามีสมาร์ตพอยน์เตอร์ `Ref<T>` และ `RefMut<T>` กำลังทำงานอยู่จำนวนเท่าใด ทุกครั้งที่เราเรียกใช้ `borrow` ทาง `RefCell<T>` จะเพิ่มตัวนับการยืมแบบแก้ไขไม่ได้ที่กำลังทำงานอยู่ขึ้นหนึ่ง และเมื่อค่า `Ref<T>` หลุดออกจากขอบเขต ตัวนับการยืมแบบแก้ไขไม่ได้ก็จะลดลงหนึ่ง และเช่นเดียวกับกฎการยืมในขั้นตอนคอมไพล์ `RefCell<T>` จะอนุญาตให้เรามีการยืมแบบแก้ไขไม่ได้หลายตัวพร้อมกัน หรือมีการยืมแบบแก้ไขได้เพียงตัวเดียว ณ ช่วงเวลาใดเวลาหนึ่งเท่านั้น

หากเราพยายามละเมิดกฎเหล่านี้ แทนที่จะได้รับข้อผิดพลาดจากคอมไพเลอร์เหมือนตอนใช้เรเฟอเรนซ์ทั่วไป ตัว `RefCell<T>` จะสั่งให้โปรแกรมแพนิก (`panic!`) ในขณะรันไทม์ทันที ลิสติ้ง 15-23 แสดงการปรับปรุงโค้ดเมธอด `send` จากลิสติ้ง 15-22 โดยเราจงใจสร้างการยืมแบบแก้ไขได้สองตัวพร้อมกันในขอบเขตเดียวกัน เพื่อแสดงให้เห็นว่า `RefCell<T>` จะป้องกันไม่ให้เราทำเช่นนั้นในขณะรันไทม์ได้อย่างไร

### การอนุญาตเจ้าของหลายรายของข้อมูลที่เปลี่ยนแปลงได้

วิธีหนึ่งที่นิยมใช้ `RefCell<T>` กันมากคือการนำไปใช้งานร่วมกับ `Rc<T>` จำได้ไหมว่า `Rc<T>` ช่วยให้ข้อมูลชิ้นหนึ่งสามารถมีเจ้าของได้หลายราย แต่จะให้สิทธิ์การเข้าถึงข้อมูลนั้นแบบอ่านได้อย่างเดียว (immutable) เท่านั้น หากคุณมี `Rc<T>` ที่ถือครอง `RefCell<T>` อยู่ข้างใน คุณก็จะได้ค่าข้อมูลที่สามารถมีเจ้าของได้หลายราย _และ_ สามารถแก้ไขข้อมูลนั้นได้ด้วยพร้อมกัน!

ตัวอย่างเช่น ลองนึกย้อนกลับไปถึงตัวอย่าง cons list ในลิสติ้ง 15-18 ที่เราใช้ `Rc<T>` เพื่อให้ลิสต์หลายชุดแชร์ความเป็นเจ้าของลิสต์อีกชุดหนึ่งร่วมกัน เนื่องจาก `Rc<T>` เก็บได้เฉพาะค่าที่ไม่สามารถแก้ไขได้ เราจึงไม่สามารถเปลี่ยนแปลงค่าใด ๆ ในลิสต์ได้เลยหลังจากสร้างมันขึ้นมาแล้ว คราวนี้เราจะนำ `RefCell<T>` เข้ามาเสริมเพื่อเพิ่มความสามารถในการแก้ไขค่าในลิสต์ ลิสติ้ง 15-24 แสดงให้เห็นว่าการใช้ `RefCell<T>` ในนิยามของ `Cons` ช่วยให้เราสามารถปรับปรุงแก้ไขค่าที่จัดเก็บอยู่ในลิสต์ทั้งหมดได้

เราสร้างค่าอินสแตนซ์ของ `Rc<RefCell<i32>>` แล้วเก็บไว้ในตัวแปรชื่อ `value` เพื่อให้เราสามารถเข้าถึงมันได้โดยตรงในภายหลัง จากนั้นเราสร้าง `List` ในตัวแปร `a` ด้วยวาเรียนต์ `Cons` ที่ถือครอง `value` ไว้ โดยเราจำเป็นต้องทำการโคลน `value` เพื่อให้ทั้ง `a` และ `value` ต่างมีสิทธิ์ความเป็นเจ้าของในค่า `5` ที่อยู่ภายใน แทนที่จะเป็นการโอนย้ายสิทธิ์ความเป็นเจ้าของจาก `value` ไปให้ `a` หรือให้ `a` ยืมจาก `value`

เราห่อหุ้มลิสต์ `a` ไว้ใน `Rc<T>` เพื่อให้เมื่อเราสร้างลิสต์ `b` และ `c` ทั้งสองลิสต์จะสามารถอ้างอิงมายัง `a` ได้ เช่นเดียวกับที่เราเคยทำในลิสติ้ง 15-18

หลังจากที่เราสร้างลิสต์ใน `a`, `b` และ `c` เรียบร้อยแล้ว เราต้องการบวก 10 เพิ่มเข้าไปในค่าของ `value` เราทำสิ่งนี้ได้โดยการเรียก `borrow_mut` บน `value` ซึ่งจะใช้ฟีเจอร์การดีเรเฟอเรนซ์อัตโนมัติ (automatic dereferencing) ที่เราเคยพูดถึงในหัวข้อ [“ตัวดำเนินการ `->` อยู่ที่ไหน?”][wheres-the---operator]<!-- ignore --> ในบทที่ 5 เพื่อทำการดีเรเฟอเรนซ์ `Rc<T>` ไปยังค่า `RefCell<T>` ที่อยู่ภายใน เมธอด `borrow_mut` จะส่งคืนสมาร์ตพอยน์เตอร์ `RefMut<T>` ออกมา แล้วเราจึงใช้ตัวดำเนินการดีเรเฟอเรนซ์กับมันเพื่อแก้ไขค่าที่อยู่ข้างใน
